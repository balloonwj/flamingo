# 主面板被其它窗口盖住问题排查（最小化聊天窗后主面板"沉底"）

> 状态：**已修复（2026-08-12）**，采用第四节的方案 C，实测验证通过。
>
> 相关代码：
> - `flamingoclient/Source/BalloonMain/BalloonMainPanel.cpp` —— `CreateAndShow` 建窗处
> - `flamingoclient/Source/BalloonChatWnd/BalloonChatWindow.cpp` —— 最小化处理
> - `flamingoclient/Source/BalloonMain/WindowZOrderDiag.h` —— 本次排查用的临时诊断日志

## 一、问题描述

在主面板前面打开一个聊天窗（聊天窗盖住主面板），然后点聊天窗标题栏的最小化按钮。

**期望**：聊天窗最小化后露出它后面的主面板，主面板成为最前面的窗口。

**实际**：主面板没有露出来，反而是桌面上另一个不相干的程序（复现时是资源管理器窗口）跳到了最前面，把主面板盖住。用户观感是"主面板下沉到了最底层"。

复现截图见 `snapshots/a1.png`（最小化前）与 `snapshots/a2.png`（最小化后）。

该问题长期存在，此前多次尝试未能定位。

## 二、排查过程

### 2.1 先排除"代码主动压窗"

全仓库搜索 `HWND_BOTTOM`，无任何匹配；`DuiMenuPopup` 之外也没有别处主动改主面板 Z 序的代码。聊天窗的最小化按钮走的是标准路径 —— `DuiFrameWindow` 把三按钮点击转成 `WM_SYSCOMMAND / SC_MINIMIZE`（见 `balloonui/Controls/Window/DuiFrameWindow.cpp`），并没有做额外的窗口操作。

两个窗口都是 `Create(NULL, ...)` 建的，**owner 均为 NULL**，彼此没有归属关系。

### 2.2 走过的弯路：黑盒试探

一度写了 PowerShell 脚本在外部造窗口做对照实验（记事本 + 客户端调试入口 + Z 序名次测量）。这条路**不可靠，最终结论是错的**，教训值得记下来：

- `Process.MainWindowHandle` 取到的是输入法的 `HuayuIME.ToolBarWindow`，不是应用主窗口。必须枚举进程的可见顶层窗口取面积最大的那个。
- 从后台进程调 `SetForegroundWindow` 受前台锁限制，经常静默失败，导致实验的"前置 Z 序"根本没建立起来，据此得出的结论全部作废。
- 运行脚本的控制台窗口本身也在 Z 序里，会成为最小化后的激活候选，污染结果。

当时据此错误地得出过"`WS_EX_TOOLWINDOW` 不是原因"的结论。**黑盒试探在窗口激活这类问题上不适用**，应当直接在被测程序内部打日志。

### 2.3 有效手段：在客户端内部打诊断日志

新增 `BalloonMain/WindowZOrderDiag.h`（header-only，日志统一带 `[ZDIAG]` 前缀），在两侧挂钩：

- **聊天窗**：收到 `SC_MINIMIZE` 时记录自身与主面板状态、打一份"最小化之前"的 Z 序快照，再启一个 400ms 定时器打一份"最小化完成之后"的快照（最小化与随之而来的激活切换是异步的，立刻抓拍只会拍到中间态）。
- **主面板**：`WM_WINDOWPOSCHANGING` / `WM_WINDOWPOSCHANGED`（只在这次调整真的动了 Z 序时才记，否则拖动窗口就会刷屏）、`WM_ACTIVATE`、`WM_SHOWWINDOW`。

Z 序快照自上而下列出最上面 12 个可见且未最小化的顶层窗口，标出哪些属于本进程，并单独点名当前前台窗口。

### 2.4 第一份日志：排除两种可能

日志 `Bin/Logs/20260812171111_17016.log`，复现时刻 17:11:16。

最小化前的 Z 序：

```
#0 本进程  HuayuIME.ToolBarWindow                          输入法工具条
#1 本进程  __DuiHost__ '<对方昵称>'  exStyle=0x00000100     聊天窗
#2 本进程  __DuiHost__ 'FlamingoIM'  exStyle=0x00000180     主面板（含 TOOLWINDOW 位）
#3         CabinetWClass 'Bin […]'                          资源管理器
前台窗口 = 聊天窗
```

最小化后：

```
#0         CabinetWClass 'Bin […]'                          资源管理器跳到最上面
#1 本进程  __DuiHost__ 'FlamingoIM'                          主面板
前台窗口 = 资源管理器
```

三条关键事实：

1. **主面板的 Z 序一次都没被改过。** 整个最小化时段（17:11:16.547 → 16.989）主面板没有收到任何 `WM_WINDOWPOSCHANGING(动了Z序)`。它唯一一次 Z 序变动发生在 17:11:12 的启动阶段。→ 排除"我们的代码把它压下去了"。
2. **它也没有被隐藏。** 全程没有 `WM_SHOWWINDOW show=0`，快照里始终 `可见=1`。→ 排除"被隐藏到托盘"。
3. **它的绝对位置反而上升了一位**（#2 → #1），因为聊天窗和输入法工具条离开了可见列表。

结论：不是主面板下沉，而是**资源管理器被系统激活后浮到了它上面**。"沉底"是视觉错觉。

### 2.5 第二份日志：对照实验确认因果

把主面板建窗时的扩展样式临时改成 `0`（去掉 `WS_EX_TOOLWINDOW`），其余一律不动，重编后按同样三步复现。日志 `Bin/Logs/20260812172156_12332.log`，复现时刻 17:22:01。

| | 有 `WS_EX_TOOLWINDOW`（原版） | 去掉之后（验证版） |
| --- | --- | --- |
| 主面板 exStyle | `0x00000180` | `0x00000100` |
| 最小化时主面板收到 Z 序变动 | **一条都没有** | 收到 `WINDOWPOSCHANGING(动了Z序)` |
| 最小化时主面板收到激活 | **没有** | 收到 `WM_ACTIVATE state=1(被激活)`，另一侧为聊天窗 |
| 最小化后最上面是谁 | 资源管理器 | **主面板** |
| 最小化后前台窗口 | 资源管理器 `Bin […]` | **`FlamingoIM`** |

同一台机器、同样的操作、Z 序里同样摆着那个资源管理器窗口，**唯一变量就是那一个样式位**，行为随之翻转。因果成立。

## 三、问题原因

主面板建窗时带了 `WS_EX_TOOLWINDOW`（`BalloonMainPanel.cpp` 的 `CreateAndShow`）：

```cpp
Create(NULL, CWindow::rcDefault, _T("FlamingoIM"),
       WS_OVERLAPPEDWINDOW, WS_EX_TOOLWINDOW)
```

加这个样式的**本意**是让主面板不出现在任务栏、也不进 Alt+Tab，改由系统托盘图标调出。这个目的本身是达到了的。

**副作用**是：工具窗口在系统眼里属于辅助性的调色板窗口，会被排除在"最小化某个窗口之后该激活谁"的候选之外。于是最小化聊天窗时，系统跳过紧挨在它下面的主面板，把激活权交给 Z 序里下一个普通窗口（复现时是资源管理器）；该窗口被激活后自然浮到主面板上方，主面板就被盖住了。

需要强调的是：**主面板既没有被移动，也没有被隐藏**，问题出在"它拿不到激活权"，而不是"它被压下去了"。这一点决定了修复方向——不能去找哪里把它压下去了，那里什么都没有。

同一机理会波及**所有**在主面板前面打开、又可以被最小化的独立顶层窗口（群聊窗、历史记录窗、个人资料窗等），不止单聊窗。

## 四、解决方案

> **已采用方案 C，2026-08-12 实测验证通过。**

### 4.1 候选方案与取舍

**方案 A：聊天窗最小化时主动把激活交还主面板。**
在聊天窗最小化完成后，若主面板可见且未最小化，就把前台交给它。不动样式、不动归属关系；缺点是每个可最小化的独立窗口都要照做一遍，且属于手工补偿系统行为。

**方案 B：把聊天窗的 owner 设成主面板。**
系统最小化被拥有的窗口时会自动激活其 owner，无需手写激活逻辑。代价：被拥有的窗口默认不进任务栏，要补 `WS_EX_APPWINDOW`；且被拥有的窗口永远压在 owner 之上，用户再也无法把主面板调到聊天窗前面——这是用户可感知的行为退化。另外主面板收进托盘时被拥有的窗口会如何，尚需验证。

**方案 C（<u>已采用</u>）：主面板改做普通窗口，用 `ITaskbarList::DeleteTab` 摘掉任务栏按钮。**
窗口恢复普通的激活语义，问题从根上消失，任何窗口里都不用补代码。代价是 Alt+Tab 的收录规则与任务栏不是一回事，主面板会重新出现在 Alt+Tab 列表里——**该代价经权衡后接受**。

选 C 而不选 A 的理由：A 是在系统行为之外手工打补丁，而且要在每个可最小化的窗口上重复一遍，将来新增窗口容易漏；C 把窗口放回普通语义，问题不再存在，也就不需要任何补偿代码。

### 4.2 实现

改动集中在 `BalloonMain/BalloonMainPanel.cpp`：

1. **建窗扩展样式由 `WS_EX_TOOLWINDOW` 改为 `0`**（`CreateAndShow`），窗口成为普通顶层窗口。
2. **新增静态函数 `RemoveFromTaskbar(HWND)`**，走 `CoCreateInstance(CLSID_TaskbarList)` → `HrInit` → `DeleteTab` 摘掉任务栏按钮。
3. **两处调用**：`CreateAndShow` 里 `ShowWindow(SW_SHOW)` 之后一次；`OnShowWindowForTaskbar`（新增的 `WM_SHOWWINDOW` handler）里每次显示再摘一次。

两个实现要点：

- **COM 初始化**：UI 线程并没有全局初始化过 COM（客户端只在个别对话框里就地 `CoInitialize`），所以 `RemoveFromTaskbar` 自行 `CoInitialize` 并配平；已初始化时返回 `S_FALSE`，同样要 `CoUninitialize` 才不改变引用计数语义。
- **按钮会反复出现**：任务栏按钮在窗口显示<u>之后</u>才存在，且每次重新显示都会再长出来（托盘收起主面板再调出即属此列），所以建窗那次与后续每次 `WM_SHOWWINDOW` 都要各调一次。只做其中一处都不够。

`DeleteTab` 失败不影响功能（顶多任务栏上多一个按钮），但会记一条 `LOG_WARNING` 留痕——这类问题只在特定系统或时序下出现，没有日志无从查起。

### 4.3 验证结果

验证日志 `Bin/Logs/20260812180055_21904.log`（复现时刻 18:01:17），三项均通过：

| 验证项 | 结果 |
| --- | --- |
| 主面板扩展样式 | `exStyle=0x00000100`，工具窗口位已去掉 |
| 任务栏按钮是否摘掉 | `DeleteTab` 共 4 次调用全部返回 `S_OK`（含托盘收起再调出时补摘的 2 次），界面确认任务栏无按钮 |
| 最小化聊天窗后 | 主面板依次收到 `WINDOWPOSCHANGING(动了Z序)` → `WINDOWPOSCHANGED` → `WM_ACTIVATE state=1(被激活)`（另一侧为聊天窗） |
| 最终 Z 序 | 主面板排 #1、资源管理器退到 #2，前台窗口 = `FlamingoIM` |

对比修复前（日志 `20260812171111_17016.log`）：主面板在整个最小化过程中一条 Z 序变动、一次激活都没收到。
