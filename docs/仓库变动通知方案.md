# 仓库变动通知方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-06
> 用途：记录「管理台配置 GitHub / GitLab Token，服务端定时拉取仓库变动并以机器人身份通知某个人或某个群」的整体方案与开发步骤。后续每步开工前据此细化、收尾后回填实际结果。

---

## 1. 背景与目标

研发团队希望在 Flamingo 里直接看到代码仓库的变动：谁往哪个分支推送了什么提交、哪个 PR / MR 被合并了、CI 有没有失败，而不必另开浏览器盯着 GitHub / GitLab。本方案让企业管理员在 flamingoAdmin 里填写一个 GitHub 或 GitLab 的 Access Token，选择要关注的仓库与事件，再指定通知对象（某个人或某个群）；chatserver 定时调用平台 API 拉取变动，由一个机器人账号把变动以 Markdown 消息发给通知对象。

以下口径已与用户确认（2026-10-06），实现时不再另行请示：

| 决策点 | 取值 | 详见 |
| --- | --- | --- |
| 凭据 | **只支持 Access Token**（GitHub 细粒度 PAT / classic PAT，GitLab 个人或项目访问令牌）；不做 SSH 密钥，不做账号密码 | §3.1 |
| 获取变动的方式 | **只做服务端定时拉取**；不做 Webhook，因此不需要对外开放任何端口 | §5.3 |
| 通知对象 | 每条订阅一个对象：**某个人**（机器人单聊发给他）或**某个群**（机器人入群后在群里发） | §4.3 |
| 选群的方式 | **两种都支持**：按群名或群号搜索本企业已有的群；或在向导里当场新建群 | §4.3、§6.3 |
| 消息格式 | Markdown 文字消息（`msgtype = 1`、`content.format = "markdown"`），现有客户端不改即可渲染 | §5.4 |
| 支持的平台 | GitHub.com、GitHub Enterprise Server、gitlab.com、自建 GitLab | §5.3 |
| 安卓端 | 不在本方案范围内 | — |

最终形态：管理员在企业详情页的「仓库通知」页签里点「新建订阅」，粘贴 Token 并验证，勾选仓库与事件，选择通知对象后保存。此后每隔一个拉取周期（默认 60 秒），通知对象就会收到「GitHub 通知」或「GitLab 通知」发来的消息，例如：

```
**balloonwj/flamingo** · 张三 向 `master` 推送了 3 个提交
- `a1b2c3d` 修复登录窗口崩溃
- `e4f5a6b` 调整群聊输入框高度
- `c7d8e9f` 更新依赖
[查看对比](https://github.com/balloonwj/flamingo/compare/111...222)
```

### 2.2 缺口

2. **机器人的名字解析不到。** 服务端下发通讯录时只放部门成员（`ChatSession.cpp`）。机器人不属于任何部门，客户端就会把它显示成「用户<id>」，头像字形为「用」（`Source/UI/BalloonChatWnd/GroupSenderRefresh.cpp`；`BalloonMainPanel.cpp`）。
5. **没有敏感字段加密存储的先例。** `filetokenkey`、`relaytokenkey` 都是明文写在配置文件里。

9. **管理台到 chatserver 是明文 HTTP**（`flamingoAdmin/Util/AppConfig.h` 约 26-30 行；服务端 `HttpServer` 没有 TLS），Token 提交时需要额外保护。

## 3. 外部平台约束

### 3.1 凭据

- 据实证（GitHub 官方公告）：GitHub 自 2020-11-13 起 REST API 不再接受账号密码，只接受 Token；Git 操作也已取消密码认证。所以「账号」在本方案里就是 Access Token。
- 本方案只读不写，Token 只需要只读权限。据推测（实施前对照官方文档核对）：
  - GitHub 细粒度 PAT：只读的 Metadata、Contents、Pull requests；要通知 Issue、CI 时再加 Issues、Actions。classic PAT 访问私有仓库需要 `repo` 范围，权限过大，界面上建议改用细粒度 PAT。
  - GitLab：`read_api` 范围、在项目上至少有 Reporter 角色。

### 3.2 拉取接口的选择

- 据实证（GitHub 文档）：GitHub 的仓库事件接口 `/repos/{owner}/{repo}/events` 延迟为 30 秒到 6 小时，不能作为主通道；该接口支持 ETag，没有新事件时返回 304，且不消耗配额。因此 GitHub 侧改为分别拉取分支、PR 等具体接口（§5.3.1）。
- GitLab 的项目事件接口 `/projects/:id/events` 一次就能拿到推送、标签、MR、Issue、评论，据推测延迟很小，作为 GitLab 侧的主通道（§5.3.2）。

### 3.3 配额（据推测，实施前核对）

- GitHub：PAT 每小时 5000 次。每个仓库每轮 2～5 次请求，60 秒一轮约 120～300 次 / 小时，一个 Token 大约能带 15～40 个仓库。条件请求返回 304 时是否计入配额，`/events` 已据实证不计入，其它接口据推测相同。
- gitlab.com：已认证请求的限额远高于本方案的用量。自建 GitLab 由其管理员配置。
- 服务端读取应答头里的剩余配额（GitHub 为 `X-RateLimit-Remaining`，GitLab 为 `RateLimit-Remaining`），余量不足时自动拉长周期（§5.3.4）。

## 4. 交互设计

### 4.1 入口

企业详情页新增「仓库通知」子页签，与「服务号」并列（`flamingoAdmin/Screens/EnterpriseDetailScreen`）。订阅按企业划分，放在这里最自然。平台超管与本企业管理员都能看到这个页签。

### 4.2 列表页

| 列 | 内容 |
| --- | --- |
| 名称 | 管理员起的名字，缺省为第一个仓库名 |
| 平台 | GitHub / GitLab，自建实例显示主机名 |
| 仓库 | 第一个仓库名，多个时加「等 N 个」 |
| 通知对象 | 人名或群名，前面带「个人」「群」标签 |
| 状态 | 正常 / 已暂停 / Token 失效（红） / 异常（橙，悬停显示最近一次错误）/ Token 即将到期（橙） |
| 最近事件 | 最近一次发出通知的时间 |
| 操作 | 编辑、发送测试消息、立即拉取、暂停 / 恢复、删除 |

### 4.3 新建 / 编辑向导

向导做成叠层弹窗（与 `ServiceModal`、`GroupModal` 相同的形态），分三步：

1. **Token**
   - 平台：GitHub / GitLab。
   - 平台地址：默认 `https://api.github.com` / `https://gitlab.com`，自建实例时填写主机地址，服务端拼出 API 前缀（GitHub Enterprise 为 `/api/v3`，GitLab 为 `/api/v4`）。
   - Token：密码框，粘贴。编辑已有订阅时留空表示沿用原 Token。
   - 「验证」按钮：服务端调用平台接口，显示 Token 所属账号、到期时间（取得到时）、权限是否满足所选事件。验证通过才能进入下一步。
2. **仓库与内容**
   - 仓库：从 Token 能访问的仓库列表里勾选（可按名称过滤），也可以手动填写 `owner/repo` 或 GitLab 的 `group/subgroup/project`。一条订阅可以有多个仓库。
   - 事件：推送（默认勾选，含强制推送提示）、分支与标签的新建 / 删除、PR / MR（默认勾选：新建、合并、关闭、重新打开）、Issue（新建、关闭）、CI 失败与恢复、Release 发布。
   - 分支过滤：逗号分隔的通配规则，例如 `main, release/*`；留空表示全部分支。只作用于推送与分支事件。
   - 拉取周期：默认 60 秒，下限取服务端配置（§5.8）。
3. **通知对象**
   - 「个人」：在组织架构树里选一个人。
   - 「已有的群」：按群名或群号搜索本企业的群（§5.6 的 `group/search.do`），选一个。
   - 「新建群」：填写群名（默认「<仓库名> 通知」），选择群主、管理员与成员，交互与现有 `GroupModal` 相同。
   - 选群时都会提示「机器人『GitHub 通知』将在该群发送通知」。机器人不加入群成员（见 §5.2）。

保存成功后列表刷新，并提示「已开始拉取，首轮只记录当前状态，之后的变动才会通知」。

### 4.4 通知对象一侧看到的效果

- **个人**：会话列表里出现与「GitHub 通知」的单聊。
- **群**：机器人不入群，也不出现入群提示；它出现在群聊窗成员页签的「机器人」分组里，发出的消息带「机器人」标识（`docs/机器人方案.md` §4.2）。仅通知模式（原称全员禁言）不影响机器人发消息。
- **Token 失效或即将到期**：通知对象收到一条机器人消息说明情况与处理办法（联系管理员更新 Token），同一状态只发一次。

## 5. 服务端

### 5.1 公开的发消息函数（步骤 1a）

`ChatServer` 上的这个函数已由 `docs/机器人方案.md` 第一期 1a 实现（`ChatServer.h`），本方案直接使用：

```cpp
/**
 *  以指定用户的身份写入一条消息并推送给接收方（单聊推给对方，群聊推给全体成员）。
 *  不经过发言权限与敏感词检查，供服务端模块（如仓库通知机器人）主动发消息。
 *  可在任意线程调用，调用时不得持有 m_sessionMutex。
 *  @return 新消息的 msgid；clientMsgId 已存在时返回已有消息的 msgid；失败返回 0。
 */
int64_t postMessageAs(int32_t ctype, int32_t fromUserId, int64_t targetId,
                      int32_t msgtype, const std::string& contentJson,
                      const std::string& clientMsgId);
```

内部按 `buildStoredContent → getMsgIdByClientId（判重）→ saveMessage → buildMessageNotify → pushToUsers` 实现。现有的几份副本本期不迁移，避免扩大改动范围。

### 5.2 机器人账号（步骤 1b，2026-10-08 修订）

- **创建**：每个企业、每个平台一个机器人，第一次保存该平台的订阅时经 `BotManager` 创建为企业机器人（`docs/机器人方案.md` §3.2、§5.5：`t_user.f_usertype = 2`，`t_bot.f_owner_type = 1`），名称「GitHub 通知」/「GitLab 通知」，简介「仓库变动通知」。机器人与平台的对应关系记在 `t_bot` 上（列名开工时与机器人方案一并确定），不再建 `t_repo_bot`。这类机器人没有规则，只由 `RepoPoller` 调用 `postMessageAs` 发消息；在管理台「机器人」页显示为只读，编辑入口在「仓库通知」页签。
- **拒绝登录、统计排除、软删除**：由机器人方案第 1a 步统一实现，本方案不另做。
- **通知群**：机器人不加入群成员。通知对象为群时，把该群加进这个机器人的「所选的群」（`t_bot_group`），客户端经 2801 取得机器人资料；删除订阅或改了通知对象后，若已没有其它订阅指向原来的群，从「所选的群」里去掉。不推 1317，也不发入群系统提示。
- **通知个人**：以单聊发给通知对象（`from` 为机器人）。机器人方案没有给企业机器人设计单聊，这里的单聊只用于接收通知，客户端名字解析见 §7。
- **企业删除**：随机器人方案的级联删除一并处理。

### 5.3 拉取逻辑（步骤 1e～1g）

#### 5.3.1 GitHub

API 前缀：`https://api.github.com`，GitHub Enterprise Server 为 `https://<主机>/api/v3`。请求头带 `Authorization: Bearer <token>`、`Accept: application/vnd.github+json`、`If-None-Match: <上次的 ETag>`。

| 事件 | 接口 | 判定方法 |
| --- | --- | --- |
| 推送 | `GET /repos/{owner}/{repo}/branches?per_page=100`（按 `Link` 头翻页） | 与上次的分支快照（分支名 → SHA）比对；SHA 变化的分支再调 `GET /repos/{owner}/{repo}/compare/{旧}...{新}` 取提交列表；`status` 为 `diverged` 或 `behind` 时按强制推送处理 |
| 分支新建 / 删除 | 同上 | 快照里新增或消失的分支 |
| 标签新建 / 删除 | `GET /repos/{owner}/{repo}/tags?per_page=100` | 与标签快照比对；只在勾选了该事件时请求 |
| PR | `GET /repos/{owner}/{repo}/pulls?state=all&sort=updated&direction=desc&per_page=30` | `updated_at` 晚于游标的条目，按本地记下的状态（open / closed / merged）判断新建、合并、关闭、重新打开 |
| Issue | `GET /repos/{owner}/{repo}/issues?state=all&since=<游标>&per_page=30` | 结果里带 `pull_request` 字段的是 PR，排除；按状态变化判断新建、关闭 |
| CI | `GET /repos/{owner}/{repo}/actions/runs?per_page=20` | 只报 `conclusion = failure`，以及同一工作流在同一分支上失败之后的第一次成功（「已恢复」） |
| Release | `GET /repos/{owner}/{repo}/releases?per_page=10` | id 大于游标且不是草稿 |

#### 5.3.2 GitLab

API 前缀：`https://gitlab.com/api/v4` 或 `https://<主机>/api/v4`。请求头带 `PRIVATE-TOKEN: <token>`。项目 id 用 URL 编码后的完整路径（如 `group%2Fproject`）。

| 事件 | 接口 | 判定方法 |
| --- | --- | --- |
| 推送、分支与标签、MR、Issue | `GET /projects/:id/events?after=<日期>&sort=asc&per_page=100` | 事件 id 大于游标的条目；`push_data` 带分支名、提交数、首尾 SHA 与首条提交标题，需要提交列表时再调 `GET /projects/:id/repository/compare?from=&to=`。据推测 `after` 只精确到日期，因此靠事件 id 去重 |
| CI | `GET /projects/:id/pipelines?updated_after=<游标>&per_page=20` | 规则同 GitHub |
| Release | `GET /projects/:id/releases?per_page=10` | 发布时间晚于游标 |

#### 5.3.3 共用规则

- **首轮不发消息**：新订阅或新加的仓库，第一轮只建立快照与游标，不发通知。
- **去重**：每条通知的 clientmsgid 为 `repo-<订阅id>-<仓库序号>-<事件键>`（事件键如 `push-<分支>-<新SHA>`、`pr-<编号>-<状态>`、`gl-<事件id>`），发送前用 `getMsgIdByClientId` 判重。游标在消息发出后才写回数据库；即使发出后、写回前进程退出，重启后重发的同一事件也会被判重拦下。
- **合并**：同一轮里同一分支的多次推送合并成一条；一次推送最多列 5 个提交，其余写「还有 N 个」。
- **限流**：每个订阅单轮最多发 10 条，超出部分合并为一条「另有 N 个事件，请到平台查看」并附仓库链接。
- **分支过滤**：按 §4.3 的通配规则过滤推送与分支事件。
- **快照上限**：每个仓库最多跟踪 500 个分支、最近 200 个 PR / MR 的状态，避免游标无限增长。

#### 5.3.4 调度与出错处理

- **调度**：`RepoPoller` 持有一个专用 `EventLoopThread`（线程名 `repo-poll`），每 10 秒检查一次哪些订阅到了拉取时间，把到期的订阅放进工作队列；2 个工作线程（可配置）执行阻塞的 HTTPS 请求。同一订阅同一时刻只在一个工作线程上执行。
- **401 / 403（权限类）**：订阅状态改为「Token 失效」，停止拉取，向通知对象发一次说明，写系统审计。管理员更新 Token 后恢复。
- **403 / 429（配额类）**：按应答头里的重置时间推迟下次拉取，不改订阅状态。
- **404**：该仓库标为「仓库不存在或没有权限」，同订阅的其它仓库照常拉取。
- **5xx、超时、网络错误**：按指数退避（60 秒起，最长 30 分钟）重试；连续失败超过 1 小时，状态改为「异常」并通知一次；恢复后自动回到「正常」。
- **Token 到期提醒**：据推测 GitHub 在应答头 `github-authentication-token-expiration` 里给出到期时间，GitLab 可通过 `GET /personal_access_tokens/self` 查询。到期前 7 天向通知对象发一次提醒，管理台列表显示「Token 即将到期」。
- **关键路径日志**：每轮拉取的开始与结束（订阅 id、仓库数、请求数、发出条数、耗时）、每次 HTTP 失败（状态码、平台返回的错误摘要）、状态迁移，全部写英文日志；**任何日志都不打印 Token 与 Authorization 请求头**。

### 5.4 消息格式

- 一律为 Markdown 文字消息：`msgtype = 1`，`content` 为 `{"text": "<Markdown 源文本>", "format": "markdown"}`，外层按 `buildStoredContent` 包装。FlamingoMarkdown.dll 不可用时客户端显示源文本，链接仍可点击。
- 每条消息第一行固定为「**仓库名** · 事件摘要」，会话列表摘要显示的就是这一行的源文本。
- 单条消息的源文本不超过 16 KB（`t_chatmsg.f_content` 在 MySQL 上是 blob，上限 64 KB，见 `bugs.md` BUG-108），超出时截断提交列表并注明。
- 提交说明只取第一行，最长 100 字。
- 消息文字固定为简体中文。服务端生成的 Markdown 无法像系统提示那样按客户端界面语言切换，这是本期的已知限制。
- 机器人消息不经过敏感词检查，与系统提示相同。

### 5.6 管理台接口（步骤 1h）

全部挂在 `HttpServer` 上，请求体为 JSON、带 `token`，企业管理员的请求强制落在本企业。写操作成功后写审计，动作名 `repo.create`、`repo.update`、`repo.status`、`repo.delete`。最终格式写进 `docs/Admin控制台接口文档.md`。

| 接口 | 用途 |
| --- | --- |
| `POST /admin/repo/verify.do` | 输入平台、API 前缀、Token（或订阅 id，表示用已存的 Token）；返回 Token 所属账号、到期时间、可访问的仓库列表（GitHub `GET /user/repos`，GitLab `GET /projects?membership=true&simple=true`，各取前 300 个） |
| `POST /admin/repo/list.do` | 本企业的订阅列表 |
| `POST /admin/repo/detail.do` | 订阅详情（不含 Token 明文） |
| `POST /admin/repo/save.do` | 新建或编辑；`target` 为 `{"type":1,"userid":N}`、`{"type":2,"groupid":N}` 或 `{"type":3,"groupname":"...","ownerid":N,"adminids":[],"memberids":[]}`（新建群） |
| `POST /admin/repo/setstatus.do` | 暂停 / 恢复 |
| `POST /admin/repo/delete.do` | 删除订阅；历史消息保留 |
| `POST /admin/repo/test.do` | 给通知对象发一条测试消息 |
| `POST /admin/repo/pollnow.do` | 立即拉取一次 |
| `POST /admin/group/search.do` | 按群名或群号搜索本企业的群（群主属于本企业的群），返回群号、群名、人数、群主姓名；通用接口，以后其它功能也可使用 |

**`save.do` 的处理顺序**：校验参数与 Token → 经 `BotManager` 取得或创建机器人 → 新建群时调用 `ChatServer::adminCreateGroup`（成员里不带机器人）→ 把通知群加进机器人的「所选的群」→ 写订阅（事务）。写订阅失败时已建好的群保留（它本身是一个完整可用的群），应答里带回群号并记日志。

`HttpSession` 不能 include `Protocol.h`（两边的 `error_code` 冲突，`AdminApiCodes.h` 约 11-15 行），所以涉及 v2 协议的编排放在 `ChatServer` 或单独的 service 文件里，做法参照 `FileShareAdminService`。

### 5.7 Token 安全

- **落库加密**：libsodium `crypto_secretbox_easy`，每条密文随机 nonce。主密钥放在独立的密钥文件里（配置项 `repokeyfile`，默认 `repo_secret.key`，路径相对配置文件所在目录），首次启动自动生成，Linux 下权限 0600，做法参照服务端身份密钥 `serverkeyfile`（`net/FrameCrypto.cpp` 约 232-296 行）。数据库被拖走也拿不到 Token 明文。密钥文件丢失则所有订阅变为「Token 失效」，需重新填写。
- **只写不读**：任何接口都不返回 Token 明文，只返回末 4 位。
- **传输保护**：据推测可以用登录应答里的服务端身份公钥 `linkpubkey`（Ed25519）转换为 X25519 后做 sealed box，把 Token 字段单独加密后提交，服务端用身份私钥解开。服务端未开启协议加密时公钥为空，向导里显示风险提示，建议给管理端口加 HTTPS 反向代理。管理台是否已能调用 libsodium（`FlamingoLink.dll` 的握手用到了加密）在步骤 1h 开工时核对。
- **证书校验**：出站 HTTPS 一律校验证书。自建 GitLab 使用私有 CA 时，Linux 通过配置项 `repocafile` 指定 CA 文件，Windows 需把 CA 装进系统证书库。不提供跳过校验的选项。

### 5.8 HTTPS 客户端与配置（步骤 1d）

- `utils/HttpsClient.h/.cpp` 已由 `docs/机器人方案.md` 第一期 1k 实现：Windows 用系统自带的 WinHTTP，Linux 用 POSIX 套接字 + OpenSSL（没有 OpenSSL 时只能访问 http），支持 HTTP 代理（`SetProxy`），两套实现共用同一份接口。目前只提供同步 POST、应答只带状态码与应答体；本方案要用的 GET 请求与应答头（ETag、剩余配额、到期时间）在步骤 1d 补上。
- 新增配置项（全部可选，缺失时取默认值，老配置文件不改也能启动）：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `repopollenabled` | 1 | 0 表示不启动拉取线程（订阅仍可管理） |
| `repopollthreads` | 2 | 工作线程数 |
| `repopollmininterval` | 30 | 订阅可设置的最短拉取周期（秒） |
| `repohttptimeout` | 15 | 单次 HTTPS 请求超时（秒） |
| `repohttpproxy` | 空 | 出站代理，如 `http://10.0.0.1:3128` |
| `repocafile` | 空 | 额外信任的 CA 文件（仅 Linux） |
| `repokeyfile` | `repo_secret.key` | Token 加密主密钥文件 |

注意 `ConfigFileReader` 把行内任何位置的 `#` 视为注释开始（`base/ConfigFileReader.cpp` 约 94 行），代理地址里不能含 `#`。
