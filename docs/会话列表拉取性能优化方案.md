# 会话列表拉取性能优化方案

> 一个加了很多群、群里积了很多消息的用户登录时，服务端 `onSyncConversations` 这一趟
> 要跑几十上百条 SQL，实测最坏两秒多，而且**这段时间是同步占着网络 I/O 线程的**。
> 本文记录实测曲线、根因，以及分三步的改法。

2026-08-12

---

## 1. 先澄清一件事：登录时不下发消息本体

排查缘起是「用户有大量离线消息时，登录会不会有带宽压力」。查下来**带宽不是问题**：

- 服务端不在登录时推送离线消息。消息发出即无条件落进 `t_chatmsg`
  （`chatserversrc/ChatSession.cpp`），对端在线才推 `cmd_message_notify`，
  离线就留在库里等对方来拉。`cmd_message_notify` 的全部发送点都在发消息、转发、群系统消息这几条路上，
  **登录路径一条都不发**。
- 客户端登录后发出的请求（`UI/BalloonMain/MainPanelSessionController.cpp` 的登录成功分支）是通讯录、最近会话列表、
  我加入的群列表、平台公告等。消息体要等用户**点开某个会话**才按会话拉，一次最多 100 条。

所以在 500 个群里积了 150 万条未读，登录时下发的也只是 500 条会话摘要。
**真正的代价不在客户端下载，而在服务端为了拼出这 500 条摘要所跑的 SQL。**

（顺带一处小事：会话摘要里最后一条消息的文本是**取全文、不截断**的，
见 `MessageProtocol.cpp` 的 `buildMessageDigest`。谁在群里发一段长文，
这段长文就原样跟着会话列表下来。几百个会话都摊上长文本才显得出来，可顺手改。）

## 2. 实测曲线

用例：`flamingoserver/tests/test_conversationbench.cpp`（CVB 套），对着临时 SQLite 库
真建会话、真灌消息，分别量 `getConversationBriefs`（单聊段）与
`getGroupConversationBriefs`（群聊段）。

### 群数量的影响（每群固定 200 条）

| 群数量 | 单聊段 | 群聊段 | 合计 |
| --- | --- | --- | --- |
| 10 | 19 ms | 36 ms | 55 ms |
| 50 | 47 ms | 304 ms | 351 ms |
| 200 | 23 ms | 656 ms | 679 ms |

群聊段随群数量**线性增长** —— 每群两条 SQL。

### 消息总量的影响（固定 50 个群）

| 每群消息 | 消息总数 | 群聊段 | 合计 |
| --- | --- | --- | --- |
| 100 条 | 5,500 | 82 ms | 97 ms |
| 1,000 条 | 50,500 | 446 ms | 466 ms |
| 5,000 条 | 250,500 | **2058 ms** | **2091 ms** |

**这一组是最要命的。**群数量没变，只是消息攒多了，群聊段就涨了 25 倍。
聊天记录只会一天天变多，所以这条曲线的含义是：**系统用得越久，登录越慢，且会持续恶化。**

### 单聊会话数量的影响（固定 10 个群）

| 单聊会话数 | 单聊段 | 群聊段 | 合计 |
| --- | --- | --- | --- |
| 20 | 38 ms | 30 ms | 68 ms |
| 100 | 130 ms | 30 ms | 160 ms |
| 300 | 358 ms | 30 ms | 388 ms |

同样线性增长，同样是逐会话补最后一条消息与未读数。

### 折算到真实用户

50 个群 × 每群 5000 条历史 + 300 个单聊，按上面的曲线叠起来约 **2.5 秒**。

## 3. 根因

### 3.1 未读数用 `COUNT(*)` 逐行数

群聊那条（`MessageManager.cpp` 的 `getGroupConversationBriefs`）：

```
SELECT COUNT(*) FROM t_chatmsg
 WHERE f_ctype = 2 AND f_to = <群id> AND f_from != <本人>
   AND f_msgid > <已读位点>
   AND f_msgid NOT IN (SELECT f_msgid FROM t_message_deleted WHERE f_userid = <本人>)
```

未读多少条就要数多少行，还给每一行套一个 `NOT IN` 子查询。用户离线越久、群越活跃，
这个数越大。**第 2 节第二组曲线就是它画出来的。**

注意 `f_msgid` 是**全局自增**（见 `table_mysql.sql` 中 `t_chatmsg` 的字段注释），
所以<u>不能</u>用「最新 msgid − 已读位点」来推算未读数 —— 那个差值跨会话，毫无意义。

### 3.2 逐会话两条 SQL

`getGroupConversationBriefs`（`MessageManager.cpp`）对每个群跑两条：一条
`ORDER BY f_msgid DESC LIMIT 1` 取最后一条消息，一条上面的 `COUNT(*)`。
单聊侧同理（`getConversationBriefs` 里的循环）。N 个会话 = 2N 条 SQL。

### 3.3 同步跑在网络 I/O 线程上

`ChatServer` 起 6 条 I/O 线程（配置项 `iothreadnum`，默认值 `ChatServer::kDefaultIoThreadCount`），会话读回调
直接在其上执行，中途**没有**交给数据库线程池。故上面那 2.5 秒期间，落在同一条线程上的
其他连接全部排队等待。几十人同时登录就足以让整个服务卡顿。

另外 `getConversationBriefs` 每次调用**新建一个数据库连接**（`MessageManager.cpp`
里的 `DbFactory::createConnection()`）。SQLite 下这只是开个文件，换成 MySQL 还要多一次
TCP 握手加认证。

## 4. 改法（三步，按收益排序）

### 第一步：未读数封顶 + 补索引（已完成，2026-08-12）

> **落地结果与原方案有出入，先记在这里。**原方案只写了"未读数封顶"，做下来发现它
> **只解决了一半**：封顶后每群 5000 条那一档从 2058 ms 降到 1046 ms，曲线仍随消息量涨。
> 剩下一半在**取每个会话最后一条消息**那条 `ORDER BY f_msgid DESC LIMIT 1` 上 ——
> `t_chatmsg` 没有 `(f_to, f_msgid)` 索引，取一次最新消息就得把该会话的全部消息扫一遍
> 再排序。补上索引才真正拉平。故这一步实际做了两件事。
>
> 实测（50 个群，只变每群消息条数，群聊段耗时）：
>
> | 每群消息 | 消息总数 | 改前 | 只封顶 | 封顶 + 索引 |
> | --- | --- | --- | --- | --- |
> | 100 条 | 5,500 | 82 ms | 164 ms | **66 ms** |
> | 1,000 条 | 50,500 | 446 ms | 294 ms | **61 ms** |
> | 5,000 条 | 250,500 | **2058 ms** | 1046 ms | **68 ms** |
>
> 消息量涨 45 倍而耗时基本不动，曲线拉平。最坏那一档快了约 30 倍。
> 按会话数量增长的另两条曲线仍在（群 200 个 346 ms、单聊 300 个 328 ms），交由第二步。
>
> **两种数据库后端都要落到**，这里各自的路子不同（漏一条就等于没改）：
>
> | | SQLite | MySQL |
> | --- | --- | --- |
> | 封顶 SQL | 已生效 | 语法通用（派生表带别名 `t`）；方言层只处理 `INTERVAL` 与 `UPSERT`，不改写它 |
> | 新库索引 | 改 `table_mysql.sql` 后重跑 `tools/gen_table_sqlite.py` 生成 `SqliteSchema.cpp` | **另需**补进 `mysqlmgr/MysqlManager.cpp` 的 `m_strKeyString` —— MySQL 建表读的是那份硬编码定义，<u>不读 `table_mysql.sql`</u> |
> | 存量库索引 | 自动补上（每次启动重放 `CREATE INDEX IF NOT EXISTS`） | **不会自动补**（`ensureTable` 对已存在的表不做任何改动），已有的库须手工建索引 |



**核心依据：客户端的未读角标本来就封顶显示 "99+"**（`BadgeRender.cpp:24-25` 的
`kBadgeMaxShown = 99`、44 行的 `_T("99+")`，Tab 上那个同理），而"全部未读求和"目前
写死为 0、尚未接入（`MainPanelUserData.cpp:87-88`）。**服务端数到 100 以上的部分，
今天没有任何地方用得上。**

做法：把 `COUNT(*)` 改成"最多数到 101 就停"：

```
SELECT COUNT(*) FROM (SELECT 1 FROM t_chatmsg WHERE <原条件> LIMIT 101) t
```

数到 101 而不是 100：客户端要判断"是不是超过 99"才决定显示 99+，多留一格便于日后
把阈值调成"100 以上"也不必再动服务端。

- **效果**：每个会话的这条查询从"未读多少数多少"变成"最多数 101 行"，
  第 2 节第二组那条"越用越慢"的曲线**直接掰平**。
- **代价**：未读数超过 101 时返回 101，语义变成"≥101"。今天无影响；将来若要做
  "全部未读求和"，得知道这个上限的存在（本文档即为记录）。
- **单聊侧同样处理**，两处口径必须一致。

### 第二步：逐会话查改成批量查

把每群一条的"取最后一条消息"合并成两条固定 SQL：

1. `SELECT f_to, MAX(f_msgid) FROM t_chatmsg WHERE f_ctype=2 AND f_to IN (...) GROUP BY f_to`
2. 再按上一步拿到的 msgid 集合，一条 `WHERE f_msgid IN (...)` 取回消息体。

单聊侧同理。未读数那条**保持逐会话**——第一步之后它已经是"最多 101 行"的固定小开销，
硬要合并成一条就得为每个会话拼各自的已读位点阈值（`CASE` 或一长串 `OR`），SQL 变得
难读难维护，收益却有限。

- **效果**：N 个会话的 SQL 条数从 2N 降到 N+2，压下第 2 节第一、三组的线性增长。
- **风险**：`IN (...)` 的元素个数受 SQL 长度限制，群/会话极多时需分批（每批如 200 个）。

### 第三步：挪出网络 I/O 线程（**暂缓，2026-08-12 决定不做**）

把这一趟查询交给数据库工作线程执行，查完再把应答发回连接。

**先说清楚它不解决什么**：这一步一毫秒都不会让单次查询变快。它解决的是"一个重度用户
登录时，别把同一条 I/O 线程上其他人的收发消息也堵住"。

#### 前提与原设想不同：手头没有现成的异步机制

调研结论（据实证）：

- **`CMysqlThrdMgr` 是死代码**。全仓库除 `mysqlmgr/` 目录内部，没有任何调用点；
  `main.cpp` 只初始化了 `CMysqlManager`（建表检查），从未启动过这个线程池。
- 它还**绑死 MySQL**：任务接口是 `IMysqlTask::execute(CDatabaseMysql*)`，直接递一条
  MySQL 连接进来，SQLite 模式用不了。

所以第三步不是"接上现成的线程池"，而是**要新建一个两种后端通用的池**。这正是它改动面
最大的原因。

好消息：发送端没有障碍。`TcpConnection::send` 本身线程安全（`net/TcpConnection.cpp:79`
起，内部判 `isInLoopThread()`，不在就 `runInLoop` 转投），worker 线程里直接发应答合法。

#### 设计

**一、新增 `dbapi/DbWorkerPool`。** 固定 N 条线程，每条线程持有<u>一条常驻数据库连接</u>。
任务接口按仓库习惯定义成纯虚类（不用 lambda）：

```
class IDbTask {
    virtual void run(IDatabase* conn) = 0;   // 在工作线程上执行
    virtual void release() { delete this; }
};
```

顺带解决一个既有问题：`getConversationBriefs` 现在**每次调用都新建一条连接**
（`MessageManager.cpp`），改成常驻连接即可省掉；MySQL 下还省一次握手加认证。

**二、`onSyncConversations` 改成提交任务。** 任务里按值捕获三样：`userid`、`m_seq`
（不能事后回去读会话成员）、`std::weak_ptr<TcpConnection>`。工作线程里调
`MessageManager` 那两个方法拼出应答 JSON，再 `lock()` 那个 weak_ptr —— 连接还在就发，
已断开就丢弃。

**关键点：全程不碰 `ChatSession`。** 应答只需要"连接 + seq + 一段 JSON"，不需要会话状态。
这样绕开了会话生命周期这个最容易出事的地方，也不必给 `ChatSession` 加
`enable_shared_from_this`。

**三、按 userid 哈希分配线程**，而不是随便挑一条空闲的。同一个用户的请求固定落到同一条
线程。现在只挪只读查询，乱序影响不大；但一旦以后把写操作也挪进来，不定序就会出
"先写后读却读到旧值"。一开始就按哈希分配，省得将来返工。

**四、必须处理的边界：**

| 边界 | 处理 |
| --- | --- |
| 队列堆积 | 给上限；超了要么就地同步执行、要么回错误码。**两种取舍不同，须先定** |
| SQLite 并发 | 多连接并发读没问题，但每条连接要设 `busy_timeout`，免得与写连接撞上直接失败 |
| 停服时序 | 先停收新任务 → 等队列排空 → 再关连接；顺序错了会在退出时崩 |
| 线程数 | 加一项配置（如 `dbthreadnum`），默认 4 |

#### 测试怎么写

仍按"先测后改"：哈希分配是否稳定、队列上限触发时的行为、停服时任务排空 —— 这些是纯逻辑，
可单测；"查询期间连接断开"构造 weak_ptr 已失效的任务，确认安静丢弃、不崩、不泄漏；
并发正确性则是多线程提交同一用户请求、结果与单线程一致。

注意**这一步没有"变快"的指标可测**：CVB 计时用例量的是单次耗时，挪线程不会让它变小。
真要量得测"多用户并发登录时的互相影响"，需要另造一套压测，成本不低。

#### 为什么暂缓

前两步做完，最坏那档已从 2 秒多降到 270 毫秒左右。是否值得为剩下这 270 毫秒去动并发模型，
取决于两点：

1. **实际同时登录的人数。** 6 条 I/O 线程，几十人的企业陆续上线基本无感；几千人集中在
   上班点登录才有必要。
2. **能否接受风险。** 这是三步里唯一动并发模型的，出错方式（用后释放、乱序、退出时崩）
   比前两步隐蔽得多，且不易靠单测覆盖全。

**结论：暂不实施**，等有了真实用户规模的数据再重新评估。

#### 一个成本低得多的中间选项

只把"每次新建连接"改成每条 I/O 线程持有一条常驻连接（thread_local）。**不解决阻塞**，
但省掉每次建连接的开销，改动小、风险低，MySQL 下收益更明显。若哪天觉得第三步太重，
可以先走这一步。

## 5. 实施顺序：先跑通测试，再改代码

每一步都按同一个节奏走（开发约定文档「测试规范」第 1 条：不确定的行为先测后改）：

1. **先补正确性用例，并确认它们在<u>改动前</u>就能通过** —— 这一步是把"现在的正确行为"
   钉死，之后的改动才有参照物。
2. **再改代码**，重跑正确性用例，必须全绿。
3. **最后跑 CVB 计时用例**，确认曲线确实掰平了。

第一步要补的正确性用例（暂定 Suite CVU，`tests/test_conversationunread.cpp`）：

| 用例 | 钉住的行为 |
| --- | --- |
| CVU1 | 未读只数**别人发的**（`f_from != 本人`），自己发的不计 |
| CVU2 | 未读只数**已读位点之后**的（`f_msgid > f_readmsgid`） |
| CVU3 | 本人已删除的消息不计入未读（`t_message_deleted`） |
| CVU4 | 全部已读时未读为 0 |
| CVU5 | 单聊与群聊两条路的口径一致 |
| CVU6 | **未读超过上限时返回上限值**（改动后的新行为，改动前预期失败） |

CVU1~CVU5 必须在动代码之前就通过；CVU6 是这次要引入的新行为，改完才会绿。

第二步补的是"批量查与逐会话查结果完全一致"的用例：同一份数据，两条路各跑一遍，
逐字段比对。第三步补的是"查询期间连接断开不崩、不泄漏"的用例。

### 计时用例怎么跑

CVB 套**不进默认测试集**（真建库灌几十万行，一次几十秒）：三个用例都挂了
`doctest::skip()`，默认只列名不执行。跑它必须**同时**给上 `--no-skip` 与名字过滤 ——
doctest 的名字过滤<u>不会</u>解除 skip 标记，只给 `--test-case` 是跑不起来的：

```
flamingoserver\windowsproj\x64\Debug\Tests.exe --no-skip --test-case="CVB*"
```

数字用 `MESSAGE` 输出（doctest 无论成败都打印）。用例只断言「跑完了、条数对得上」，
不断言具体快慢 —— 写死时间阈值必然变成一条时不时误报的用例。

## 6. 分期

| 期 | 状态 | 内容 | 实际效果 |
| --- | --- | --- | --- |
| 一 | **已完成** | 未读数封顶 + 补 `idx_to_msgid` 索引 | 掰平了「越用越慢」那条曲线 |
| 二 | **已完成** | 逐会话查改批量查 | 群会话侧压下大半；单聊侧几乎没动，原因见下 |
| 三 | **暂缓** | 挪出网络 I/O 线程 | 不实施，理由见第三步末尾 |

三期各自独立可提交，做完一期用 CVB 套复测一次。

## 7. 前两期的最终数字

| 场景 | 原始 | 一期后 | 二期后 |
| --- | --- | --- | --- |
| 50 群 × 每群 5000 条 | 2058 ms | 68 ms | **68 ms** |
| 200 个群 × 每群 200 条 | 656 ms | 346 ms | **256 ms** |
| 300 个单聊 × 每个 50 条 | 358 ms | 328 ms | **301 ms** |

**单聊侧几乎没被二期改善**，是设计使然而非疏漏：单聊那条路里取最后一条消息的详情原本
只占一半开销，另一半是**逐会话的未读数查询** —— 那条按方案是<u>特意保留</u>的（封顶后已是
固定小开销，硬要合并得为每个会话拼各自的已读位点阈值，SQL 变得难读难维护）。故剩下的
线性增长来自"每个会话一条未读查询"这个结构本身，三期也不会让它变快，只会让它不再拖住
同线程上的其他人。

## 9. MySQL 后端的实测（2026-08-12）

### 9.1 怎么测的

默认的 `flamingo_tests` 目标<u>连不上 MySQL</u> —— 它特意定义了 `FLAMINGO_NO_MYSQL`，
`DbFactory` 里根本没编 MySQL 分支（`CMakeLists.txt` 那段注释写明了）。故新增两样：

- **`tests/test_dbbackend.{h,cpp}`** —— 后端切换。默认 SQLite；设 `FLAMINGO_TEST_MYSQL=1`
  时跑 MySQL，连接参数取自 `FLAMINGO_TEST_MYSQL_HOST/USER/PWD`（缺省值与
  `etc/chatserver.conf` 那组一致）。建库两边都<u>走产品自己那条路</u>：SQLite 用
  `CSqliteManager::init`，MySQL 先 DROP 整个测试库再用 `CMysqlManager::init` 建库建表 ——
  这样"新建库的表结构对不对（索引在不在）"也一并被测到。
- **`flamingo_tests_mysql` 构建目标** —— 同一套用例，不定义 `FLAMINGO_NO_MYSQL`，
  链上 `mysqlapi` 与 MariaDB 连接器（`mariadbclient`）。仅在 `WITH_MYSQL=ON` 时生成。

```
cmake -S . -B build-mysql -DWITH_MYSQL=ON && make -C build-mysql -j$(nproc)
FLAMINGO_TEST_MYSQL=1 ./build-mysql/flamingo_tests_mysql --test-case="CVU*,CVE*"
FLAMINGO_TEST_MYSQL=1 ./build-mysql/flamingo_tests_mysql --no-skip --test-case="CVB2*"
```

顺带修了测试代码的一处可移植性问题：辅助函数原先用 `INSERT OR REPLACE INTO`
（SQLite 专有），MySQL 不认；改成两边都支持的 `REPLACE INTO`。

### 9.2 结果

**正确性**：CVU（未读口径）与 CVE（会话摘要）两套用例在真实 MySQL 上全绿，产出与 SQLite 完全一致。封顶 SQL
`SELECT COUNT(*) FROM (SELECT 1 ... LIMIT 101) t` 在 MySQL 8.0.46 上正常执行。

**性能**（50 群 × 每群 5000 条 = 25 万消息，群聊段）：

| 后端 | 改造前 | 改造后 |
| --- | --- | --- |
| SQLite | 2058 ms | **68 ms** |
| MySQL | — | **303 ms** |

MySQL 比 SQLite 慢属正常：每条查询都要过一次本地 TCP，而 SQLite 是进程内函数调用。

单独量过封顶那一项（一个积压 5102 条的群，数一次未读）：未封顶 15.58 ms → 封顶 3.00 ms，
快 5 倍，且开销从"与积压量成正比"变成固定值。

### 9.3 一个必须记下的弯路：结论一度反了

中途曾判定"**MySQL 不需要 `idx_to_msgid`**"，理由是 InnoDB 的二级索引叶子节点自带主键值，
既有的 `idx_to_from (f_to, f_from)` 实际等价于 `(f_to, f_from, f_msgid)`。当时还据此把索引从
`table_mysql.sql` 与 `MysqlManager.cpp` 里删掉、把它改成了 SQLite 专有。

**这个结论是错的**，随后在 C++ 路径上实测推翻（583 ms → 303 ms），改动已全部撤回。

错因不在测量本身，而在**拿旧查询形状的结论套了新代码**：当时用命令行模拟的是第二步
重构<u>之前</u>的形状（逐会话 `ORDER BY f_msgid DESC LIMIT 1`），那种形状 MySQL 靠
`idx_to_from` 隐含的主键列确实够用，加索引反而略慢——那次测量是准的，只是不适用于
现在的代码。第二步之后查询已变成 `GROUP BY f_to` 取 `MAX(f_msgid)`，要的是按
`(f_to, f_msgid)` 逐组直接跳到最大值，`idx_to_from` 帮不上（第二列是 `f_from`，
同一个会话内 msgid 是散的）。

**教训：换了查询写法就要重新测，别拿旧形状的结论套新代码。**
