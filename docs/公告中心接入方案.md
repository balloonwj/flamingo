## 1. 背景与目标

企业管理控制台 flamingoAdmin 已经有完整的「公告中心」：管理员能新建公告、选择投放目标（全部企业 / 指定企业 / 指定部门 / 指定员工）、立即发布或定时发布、置顶、撤回。服务端也已经把这些公告存进了数据库。

但这些公告**发出去之后没有任何人能收到**——PC 客户端没有接收公告的任何代码。管理员在控制台上看到的「已读进度」永远是 0，因为读回执表从建好那天起就没有一行数据。

本方案要做的就是把这条链路的最后一段接上：让 PC 客户端主面板的「公告中心」成为平台公告的收件箱，用户能看到发给自己的公告、点开阅读，阅读行为回流到服务端，管理员在控制台看得到真实的已读进度。

最终形态：主面板 Banner 底部那个铃铛按钮有未读公告时显示角标与「你有 N 条新公告」，点击打开公告中心窗口；窗口里按时间倒序列出发给本人的全部公告（置顶的排在最前），未读的高亮，点开即标记已读并上报服务端；公告在本地落库，换到离线状态也能回看历史。

整条链路分三段，**两头是通的，中间断了一大截**。

- `flamingoAdmin/Screens/AnnouncementsScreen.{h,cpp}` —— 公告中心界面（页头 + 左栏公告列表与筛选 + 右栏预览），已实现。

- `flamingoAdmin/AdminFrame.cpp:1566-1590`、`:2247`、`:3820` —— 这些接口都已经在发真实 HTTP 请求并处理应答。

**一处文档与代码不一致（需要留意，不属本方案改动范围）：** `flamingoAdmin/README.md` 写着「当前阶段数据全部 mock」，`AnnouncementsScreen.h` 的文件头也写「数据取自 Mock/DataStore」。实际情况是 `AdminFrame` 用 HTTP 拉到真实数据后写进 `DataStore`，界面再从 `DataStore` 读（`AnnouncementsScreen.cpp:132`、`:163`、`:188`、`:424`）——`DataStore` 现在是一层内存缓存，不再是假数据源。这两处注释已经过时。

### 2.2 服务端存储与管理侧 —— 表、业务类、HTTP 路由全部就位

三张表在 `flamingoserver/table_mysql.sql` 里都建好了：

| 表 | 位置 | 用途 |
| --- | --- | --- |
| `t_announcement` | `table_mysql.sql:255` | 公告主体。含 `f_audience_type`（0 全部企业 / 1 指定企业 / 2 指定部门 / 3 指定员工 / 4 平台内部）、`f_severity`、`f_pinned`、`f_scheduled`、`f_status`（0 草稿 / 1 已发布 / 2 已撤回） |
| `t_announcement_target` | `table_mysql.sql:277` | 投放目标。受众为指定企业 / 部门 / 员工时，一条公告对应多行 |
| `t_announcement_read` | `table_mysql.sql:288` | 已读回执，唯一键 `(f_announcement_id, f_user_id)` |

`AnnouncementManager`（`chatserversrc/AnnouncementManager.{h,cpp}`）提供了 `listAnnouncements` / `getAnnouncement` / `saveAnnouncement` / `sendAnnouncement` / `deleteAnnouncement` / `recallAnnouncement` / `setPinned` / `publishDueScheduled` 八个方法。

七个 Admin HTTP 路由全部接上：`HttpSession.cpp:280-292`。

定时发布有后台驱动：`main.cpp:301` 注册了周期任务调用 `publishDueScheduled()`，把到点的定时公告自动转为「已发布」。

### 2.3 服务端投递侧 —— 完全空白，这是本方案的核心缺口

- **没有「这个用户能看到哪些公告」的查询。** `AnnouncementManager` 全部八个方法都是管理侧视角（按状态分页列全部公告），没有任何一个按 userid 做受众匹配。
- **`t_announcement_read` 从建表起就没有任何代码写过它。** 全仓库检索 `t_announcement_read` 只在 `table_mysql.sql` 里出现。因此 `computeAudienceTotal` 算出来的应送达人数有值，但已读人数恒为 0。
- **公告发布后不通知任何在线 IM 客户端。** `sendAnnouncement()` 与 `publishDueScheduled()` 都只改数据库状态，不接触 `ChatServer` 的在线会话。
- **IM 协议里没有公告相关的任何报文。** 客户端与服务端两份 `Protocol.h` 的 `msg_type` 枚举里都没有公告类命令。

### 2.4 IM 客户端 —— 按钮画好了，但既没有数据也点不动

- **「公告中心」按钮已经存在。** `MainPanelHeader.cpp:553-562`：Banner 底部一行，左边是半透明黑圆角铃铛盒（`:417`），右边是文字。文字逻辑是未读数大于 0 时显示「你有 N 条新消息」，否则显示「公告中心」。
- **但它显示的数字恒为 0。** `MainPanelHeader::SetUnreadTotal()` 全项目**无人调用**，`m_unreadTotal` 初始化为 0（`MainPanelHeader.cpp:180`）之后再没被改过，所以真实登录后这行永远显示「公告中心」四个字、没有角标。
- **而且它点不动。** `MainPanelHeader::OnLButtonUp` 只分派头像 / 昵称 / 签名三块命中区，头文件注释明写「状态胶囊 / 通知盒 / 空白渐变区 → 不触发」（`MainPanelHeader.h:132` 附近）。
- **系统菜单里的「公告与通知」是个占位。** `MainPanelSystemMenu.h:35` 定义了 `kSysMenuAnnounce`，点击后弹「该功能正在开发中。」（`BalloonMainPanel.cpp:5047`）。

### 2.5 已经具备的基础

- **本地库的写法有两个现成样板。** `UI/BalloonHistory/V2MsgStore`（历史消息，`ChatLog\msgv2.db`）与 `UI/BalloonHistory/FileLocalStore`（文件落点，`ChatLog\filelocal.db`）。约定是**每个用途一个独立 `.db` 文件**，都放在当前账号个人目录的 `ChatLog\` 下，登录后由主面板 `Open`、账号切换时改开新库。公告库照此新建 `announce.db` 即可。

## 3. 总体设计

```
  ┌──────────────────┐   HTTP /admin/announcement/*.do   ┌──────────────────┐
  │  flamingoAdmin   │ ────────── 已实现 ──────────────▶ │   chatserver     │
  │   公告中心       │                                    │ AnnouncementMgr  │
  └──────────────────┘                                    │  + 三张表        │
                                                          └────────┬─────────┘
                                                                   │
                                        ★ 本方案新增：受众匹配 + 投递 + 已读回流
                                                                   │
                                                          ┌────────▼─────────┐
                                                          │  IM 长连接协议   │
                                                          │  2101 / 2102 /   │
                                                          │  2103            │
                                                          └────────┬─────────┘
                                                                   │
  ┌──────────────────────────────────────────────────────┬─────────▼─────────┐
  │  flamingoclient 主面板                                │  AnnounceStore    │
  │  Header 铃铛按钮（角标）→ 公告中心窗口                 │  announce.db      │
  └──────────────────────────────────────────────────────┴───────────────────┘
```

设计上的三条原则：

1. **公告不是聊天消息。** 不进 `t_chatmsg`、不进会话列表（消息 Tab）、不占会话未读数。它自成一路，入口只有 Header 上的公告中心按钮。这样既不污染既有的会话体系，将来要往公告中心里加别的通知类型也有地方放。
2. **服务端只认「已发布且受众命中」。** 草稿（`f_status=0`）、已撤回（`f_status=2`）、以及受众类型为「平台内部」（`f_audience_type=4`）的公告一律不投给 IM 用户。最后这条尤其要注意——平台内部公告是给运营看的，漏投出去是事故。
3. **客户端本地留全量历史。** 公告落 `announce.db`，离线也能回看。服务端只负责「给我发过哪些」，不承担客户端的历史存储。

## 4. 服务端设计

### 4.1 受众匹配规则

新增 `AnnouncementManager::getAnnouncementsForUser(int32_t userid, ...)`，按下表决定一条已发布公告是否投给某用户：

| `f_audience_type` | 含义 | 匹配条件 |
| --- | --- | --- |
| 0 | 全部企业 | 无条件命中所有 IM 用户 |
| 1 | 指定企业 | 用户所属企业 id 在 `t_announcement_target`（`f_target_type=1`）里 |
| 2 | 指定部门 | 用户所属部门 id 在 `t_announcement_target`（`f_target_type=2`）里 |
| 3 | 指定员工 | 用户 userid 在 `t_announcement_target`（`f_target_type=3`）里 |
| 4 | 平台内部 | **一律不投**给 IM 用户 |

关于类型 2「指定部门」是否要向下级部门递归，**据推测**多数场景下管理员选中一个部门是希望连同下属部门一起收到，但这一点在 `docs/Admin控制台接口文档.md` 与 `ComposeModal` 的实现里都没有明确规定。**这是待确认事项，见第 9 节**——在确认之前按「只匹配精确部门、不递归」实现，因为它是可逆的保守选择（漏投比误投容易补救）。

### 4.2 新增三条 IM 协议

协议号建议新开 **2100-2199「平台公告」**段（客户端与服务端两份 `Protocol.h` 同步添加）。选新段而不是塞进 1900「收藏与其它」，是因为公告是独立的一类业务，将来公告中心扩展到别的通知类型时还要在同段里加号。

> 协议号的最终取值需要确认，见第 9 节。以下按 2101/2102/2103 撰写。

**2101 `cmd_get_announcements` —— 拉取发给我的公告**

```jsonc
// 请求
{ "sinceid": 0, "limit": 50 }
// sinceid：本端已有的最大公告 id，0 表示全量拉取；服务端只返回 id 大于它的
// limit：单次上限，服务端另有硬上限（建议 100）兜底

// 应答
{ "code": 0, "msg": "ok", "hasmore": false,
  "announcements": [
    { "announcementid": 10023, "title": "系统维护通知",
      "body": "...", "severity": 1, "sendername": "平台运营",
      "pinned": false, "senttime": 1754300000000, "read": false }
  ] }
```

时间统一用 Unix 毫秒（与 v2 其余报文一致），服务端负责把表里的 `datetime` 转过来。

**2102 `cmd_mark_announcement_read` —— 上报已读**

```jsonc
// 请求
{ "announcementid": 10023 }
// 应答
{ "code": 0, "msg": "ok" }
```

服务端写 `t_announcement_read`。该表有唯一键 `(f_announcement_id, f_user_id)`，重复上报用 `INSERT IGNORE` 吞掉即可，不算错误。

**2103 `cmd_announcement_notify` —— 推送（服务端 → 客户端）**

```jsonc
{ "changetype": 1, "announcement": { /* 同 2101 的条目结构 */ } }
// changetype：1=新发布 2=已撤回（撤回时 announcement 只带 announcementid）
```

### 4.3 推送时机

两处发布出口都要挂钩推送，**一处都不能漏**：

1. `AnnouncementManager::sendAnnouncement()` —— 管理员点「立即发布」。
2. `AnnouncementManager::publishDueScheduled()` —— 后台定时器把到点的定时公告转为已发布（`main.cpp:301` 每周期调用）。这一处最容易漏，因为它是批量的、没有请求上下文。

撤回同理：`recallAnnouncement()` 成功后推 `changetype=2`，客户端本地删除该条。

推送的实现方式参照 `ChatSession::sendToUser()`（`ChatSession.cpp:1337`）——遍历在线会话按 userid 匹配。但公告的受众可能是「全部企业」，逐个用户算受众再逐个推会很重。**据推测**更合理的做法是反过来：遍历一遍在线会话，对每个在线用户跑一次受众匹配，命中就推。**这一点需要在实现前写个压测确认**（在线用户上万时这一遍遍历的耗时），不能凭推测直接定；在确认之前，先按「遍历在线会话 + 逐个匹配」实现，并在关键路径打 `LOGI` 记录本次推送耗时与命中数。

离线用户不需要补推——他们下次登录时客户端会发 2101 拉取。

### 4.4 已读回流对 Admin 的影响

`t_announcement_read` 一旦有数据，Admin 公告中心的「已读进度」就自动有了真实数字：`computeAudienceTotal` 算应送达总数，已读数由 `AnnouncementManager` 按 `t_announcement_read` 计数（列表查询与 `getAnnouncement` 里的 `readCount`）。

## 5. 客户端设计

### 5.1 net 层：新增 `AnnounceProtocolClient.{h,cpp}`

放在 `flamingoclient/Source/net/`，照 `FavoriteProtocolClient` 的结构写：

- 编码：`BuildGetAnnouncementsRequest(sinceId, limit)`、`BuildMarkReadRequest(announcementId)`

纯函数、不碰 socket，这样能直接进 Catch2 测试工程。

### 5.2 四层窗口消息管线

新增三条消息号，**每条都要接满四层**，漏掉第三层不会报错、只会静默失效（症状是日志里收到了帧、界面纹丝不动）：

| 层 | 文件 | 要做的事 |
| --- | --- | --- |
| 1 | `Source/Session/UserSessionData.h` | 定义 `FMG_MSG_V2_ANNOUNCEMENTS` / `FMG_MSG_V2_ANNOUNCEMENT_NOTIFY` / `FMG_MSG_V2_ANN_MARK_READ_RESULT`，注明 lParam 的堆对象类型与由谁 delete |
| 2 | `Source/net/IUSocket.cpp` 的 `HandleV2Frame` | 加三个 `case`，解析后 `PostMessage` 给代理窗 |
| 3 | **`Source/App/FlamingoClient.cpp` 代理窗口转发 switch** | ★ 最容易漏的一层。不在 switch 里的消息落进 `default` 被直接丢掉，堆对象顺带泄漏 |
| 4 | 主面板 `CBalloonMainPanel` 的消息映射与处理函数 | 代理窗转来的消息在这里处理（起草时这一层是 `CMainDlg`，再由它转交主面板；`CMainDlg` 已于 2026-08-19 删除） |

照抄模板：`FMG_MSG_V2_MESSAGE_RECALLED`。

### 5.3 本地库：新增 `UI/BalloonHistory/AnnounceStore.{h,cpp}`

（起草时位于 `Source/BalloonHistory/`，2026-08-18 目录重排后移入 `Source/UI/BalloonHistory/`。）

与 `FileLocalStore` 同构：单例、内部 `sqlite3*` + `std::mutex`、`Open(dbPathUtf16)` 幂等且支持账号切换重开。库文件 `<个人目录>\ChatLog\announce.db`。

表结构：

```sql
CREATE TABLE IF NOT EXISTS t_announce (
    f_announcement_id INTEGER PRIMARY KEY,  -- 公告业务 id，服务端全局唯一
    f_title           TEXT NOT NULL,
    f_body            TEXT,
    f_severity        INTEGER NOT NULL DEFAULT 0,
    f_sender_name     TEXT,
    f_pinned          INTEGER NOT NULL DEFAULT 0,
    f_sent_time       INTEGER NOT NULL DEFAULT 0,  -- Unix 毫秒
    f_read            INTEGER NOT NULL DEFAULT 0,  -- 0 未读 1 已读
    f_recalled        INTEGER NOT NULL DEFAULT 0   -- 1 = 服务端已撤回，本地保留但不显示
);
```

方法：`Upsert(item)`、`MarkRead(id)`、`MarkRecalled(id)`、`QueryAll(out)`、`GetMaxId()`（供 2101 的 `sinceid` 增量拉取）、`GetUnreadCount()`。

**注意 `V2MsgStore` 踩过的坑：** 建表语句是 `CREATE TABLE IF NOT EXISTS`，库文件已存在时它整条跳过，**后加的列永远不会生效**。`V2MsgStore.cpp` 为此有一套 `kSchemaColumns` + `EnsureColumnsLocked()` 的补列机制（这是客户端本地库的做法，与服务端 2026-10-09 删除的启动补列无关）。`AnnounceStore` 从第一版就要把这套机制带上，别等到加列时才发现。

## 8. 风险与注意事项

1. **平台内部公告漏投是事故。** `f_audience_type=4` 的过滤要在服务端查询的最内层做（SQL 的 WHERE 里），不要只在应用层判断，避免将来加了别的调用路径时绕过去。
2. **推送遍历的性能没有实测数据。** 第 4.3 节的做法是推测，实现时必须打日志记录耗时与命中数，在线用户规模上来后回看这个数字。
3. **定时发布那条推送出口极易漏。** `publishDueScheduled()` 是批量的、无请求上下文，写代码时容易只顾着 `sendAnnouncement()`。
4. **客户端建表的补列机制第一版就要带上**（见 5.3），否则将来加字段时老用户的库不会升级。
5. **Header 的会话未读接口不要挪用**（见 5.4），它与公告未读语义不同。

**过程中发现并处理的三个问题：**

1. **不能在 SQL 里用 `UNIX_TIMESTAMP()`。** 本机 chatserver 跑的是 SQLite，而 `sqliteapi/SqliteFunctions.cpp` 只注册了 NOW / CURDATE / LAST_INSERT_ID / FROM_UNIXTIME / GREATEST / CONCAT / SUBSTRING 七个 MySQL 兼容函数，没有 `UNIX_TIMESTAMP`，写了会让 SQLite 侧整条查询失败。改为按字符串读出 `f_sent_time` 后在 C++ 侧转换，实现为 `AnnouncementProtocol::dateTimeToMs`，配 4 个测试用例（含时区无关的往返验证）。

2. **`publishDueScheduled` 原来是一条 UPDATE，说不出改了哪几条。** 推送需要具体的公告ID，故改为「先 SELECT 出到点的ID，再按ID列表 UPDATE」。这样两条语句处理的集合严格一致，顺带避免了「某条公告的定时时间恰好落在两条语句之间」导致的漏推。

3. **撤回的推送顺序有坑。** 受众筛选只认「已发布」状态的公告，而撤回会把状态改成「已撤回」——先撤回再筛受众的话一个都筛不到，撤回通知就发不出去。故把「筛受众 → 撤回 → 推送」编排成 `ChatServer::recallAnnouncementAndNotify` 一个方法，由它保证顺序，并在撤回失败时不推送。

**新增文件**：

**表结构**：`t_announce`，以 `announcementid` 作主键（服务端全局分配、单调递增，天然去重，也正好用作增量拉取的游标）。方法：`Upsert` / `MarkRead` / `MarkRecalled` / `QueryAll` / `GetMaxId` / `GetUnreadCount`。

**实现上有三处是刻意为之，都配了测试：**

1. **不能用 `INSERT OR REPLACE`。** 那是整行替换，撞主键时会把 `read` / `recalled` 一并冲成默认值。同一条公告重复落库是常态（登录时全量拉一次、之后推送又来一次），用整行替换的话「用户读过的公告下次登录又变回未读」。改用显式 UPSERT，冲突时只更新内容类字段。对应用例 ANS3。

2. **已读只进不退。** `read` 一列取本地值与服务端下发值的较大者：在别的设备上读过时服务端下发 `read=1`，本地要跟上；而本地已读、服务端因为上报还没到而仍下发 0 时，不能把本地的已读抹掉。对应用例 ANS4。

3. **补列机制从第一版就带上。** 建表语句是 `CREATE TABLE IF NOT EXISTS`，库文件已存在时它整条跳过，后加的列永远不会自己出现，随后所有带新列的 SQL 都会报 no such column。`V2MsgStore` 是踩过这个坑才补的机制，本库直接照搬。对应用例 ANS11 —— 该用例手工造一个只有三列的旧库文件，再用正式的 `Open` 打开，验证缺列被 `ALTER` 补上且旧数据还在。

**主面板接线**：

- 新增 `EnsureAnnounceStoreOpen()`（惰性打开 + 账号切换切库）与 `RequestAnnouncements()`（取本地最大公告ID作增量游标后发请求）。
- `OnAnnouncementsArrived` 逐条落库；`hasmore` 为 true 时以**本批**最大公告ID作新游标续拉。这里刻意不用 `store.GetMaxId()`：两者通常相同，但万一本地库里已存着更大的ID（推送先于拉取到达），拿库里的最大值当游标会把本批与那个ID之间的公告整段跳过。另外本批为空时不再续拉，否则服务端说「还有更多」却一条都不给时会死循环。
- `OnAnnouncementNotify` 按 changetype 分流：新发布整条落库，撤回只打标记（本地那行留着，供「用户正开着这一条」时给出正确提示，而不是让它凭空消失）。
- 登录成功处改调主面板的 `RequestAnnouncements()`，增量游标要从主面板持有的本地库取（当时在 `MainDlg`，现在在会话控制器 `MainPanelSessionController.cpp`）。

**验证结果（据实证）：**

### S6 收尾回填（2026-08-05）

**新增目录 `flamingoclient/Source/BalloonAnnounce/`**（2026-08-18 目录重排后为 `Source/UI/BalloonAnnounce/`），公告中心的界面代码集中在此（本地库仍在 `UI/BalloonHistory/`，与其它本地库放一起）：

**两处形态决策与用户确认过（2026-08-05）：**

1. **列表行走「子类化扩展」这一档。** `DuiListBox` 是单列纯文本列表，装不下「标题 + 发布者·时间 + 未读点」这样的两行富行；`DuiButton` 继承 `DuiControl` 而非布局容器，塞不了子控件。故新写 `AnnounceRow` 子类化 `DuiHBox`，只覆写 `OnPaint`，不改 balloonui。**没有**把它与 `HistoryRow` 抽公共基类——两者共同部分只有「铺一层底色」几行，各自差异（那边悬停显示操作按钮 + 双击定位，这边选中态 + 级别色条 + 未读点）都不小，抽取的收益不抵动存量代码的回归风险。
2. **窗口为左右双栏**（左列表 + 右详情，820×560，最小 640×420），与 flamingoAdmin 公告中心的形制呼应。

**一个已知的坑照搬了历史窗的解法**：行的悬停与单击都<u>由窗口按几何位置驱动</u>，不靠 `OnMouseEnter` / `OnLButtonUp` 虚函数——`DuiHost::TrackHover` 只把事件发给<u>最深</u>的那个控件，鼠标停在行内的标题 Label 上时行容器永远收不到。窗口旁听 `WM_MOUSEMOVE` / `WM_MOUSELEAVE` / `WM_LBUTTONUP` 三条消息，处理完一律置 `bHandled=FALSE`（不消费，否则整个界面的鼠标交互都会失灵）。

**行 id 的边界按历史窗的教训写死**：`RowIndexFromCtrlId` 判定用 `基址 <= id < 基址 + 本段容量`，不拿下一段基址当上界；用例 ANB4 专门钉住这条边界（历史窗那边正是这个写法出过事）。

**主面板接线**：`OpenAnnounceBox` 改为真正打开窗口；收到新公告 / 撤回推送、以及拉取落库之后，除刷 Banner 角标外还调 `m_announceBoxWindow.RefreshIfOpen()`，窗口开着时即时反映变化。

### S6 实测反馈修复（2026-08-05）

用户实测提了四个问题，逐一处理如下。

**① 公告详情只看得到标题、看不到正文。** 根因：`DuiLabel` 的 `OnPaint` / `MeasureHeight` 看的是 `m_wordWrap` 这个<u>标志位</u>，只在 `SetTextAlign` 里给 `DT_WORDBREAK` 是**不生效**的，必须显式调 `SetWordWrap(true)`——正文因此只画得出第一行，看着就像"只有标题没有内容"。

顺带把滚动范围也补上了：正文区改为**不用** `auto-content-height`（内容是个 `Weight(1)` 的多行 Label，自动模式问不出它折行后的真实高度），改由窗口的 `SyncDetailBodyHeight()` 按视口实际宽度调 `MeasureHeight` 算好再 `SetContentHeight`，与主面板 `SyncPaneContentHeight` 同套路。建窗后、每次局部刷新后、以及 `WM_SIZE` 后各调一次；`WM_SIZE` 那次要**投递延迟消息**再算——控件重排发生在 `WM_SIZE` 继续传递之后，就地算会拿到旧的控件矩形。算宽度时还要扣掉滚动条占的那一条，否则高度偏小、长公告末尾会被截掉。

**② 列表不响应鼠标滚轮。** 根因是 balloonui 的一个结构性行为：`DuiHost::OnMouseWheel` 只把滚轮投给**最深命中控件**，该控件返回 false 就直接放弃（`SetMsgHandled(FALSE)`），**不向上冒泡**。公告行铺满了整个列表视口，滚轮总是落在行或行内的 Label 上，于是列表滚不动。解法与主面板 `MainPanelTreeView` 一致——在控件自己的 `OnMouseWheel` 里调 `balloonmain::ForwardWheelToScrollView` 上抛：

- `AnnounceRow` 覆写 `OnMouseWheel`（管左栏列表）；
- 新增 `AnnounceWheelLabel`（`DuiLabel` 子类，只覆写这一个虚函数），右栏正文用它，否则长公告同样滚不动。

**③ 新公告没有桌面弹窗。** 确认原先确实没有——S4 的 `OnAnnouncementNotify` 只落库 + 刷角标。新增 `AnnouncePopupWindow`：收到新发布推送时在桌面**右下角**弹一个置顶提示（级别徽章 + 标题 + 正文 + 发布者·时间 + 「知道了」「查看全部」）。几个要点：

- **没有复用群公告的 `CBalloonAnnouncePopupDlg`**：那个是<u>居中</u>弹在主面板上，且接口绑死了群（groupId / 群名 / 「查看全部」跳该群聊天窗的公告 Tab）。本窗要求右下角落点、字段与去处都不同，改造它会牵动已在使用的群公告行为。两者骨架写法保持一致，日后若出现第三种公告提示再考虑抽公共部分。
- 落点按**鼠标所在显示器**的 `rcWork`（已排除任务栏）右下角反推，天然落在可见区内，满足开发约定文档 UI 约定第 3 条；窗口比工作区还大时退到左上角，保证标题栏可见、关得掉。
- `SW_SHOWNOACTIVATE` + `HWND_TOPMOST`：置顶但不抢前台焦点，不打断用户正在做的事。
- 关闭只隐藏不销毁，骨架留着，下一条公告直接换文本再显示。同一时刻只有一个实例，上一条没关就来新的即就地替换（弹一摞窗口比漏掉一条更糟，与群公告弹窗同策略）。
- 「查看全部」经新增的 `FMG_MSG_OPEN_ANNOUNCE_BOX` 请主面板打开公告中心（当时取 `WM_USER + 552`，2026-08-16 消息号整改时改为 `WM_USER + 4540`，见 `docs/客户端窗口消息号段规约与整改方案.md` 第 5 节第 4 步）。

**④ 系统菜单「公告与通知」点击无效（弹"开发中"）。** 改为调 `OpenAnnounceBox()`，与 Banner 底部那一行指向同一个窗口，不各开一个。

**时间格式化抽成共用**：原先窗口内部的 `FormatSentTime` 提升为 `balloonannounce::FormatAnnounceTime`（放 `AnnounceBoxLayout`），公告中心列表与新公告提示窗共用，避免同一条公告在两处显示的时间口径不一致。
