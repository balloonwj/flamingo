# v2 协议加密方案

> 作者：balloonwj@qq.com　起草日期：2026-08-12
> 用途：记录客户端与服务端之间通信加密的整体设计、libsodium 的具体用法、帧格式变更、密钥管理、配置项与构建集成。开发阶段实施，不考虑与旧客户端的兼容。

---

## 1. 背景与现状

改造前的实测结论：

- **压缩有**：包体 ≥ 256 字节走 zlib，帧头置 `frame_flag_compressed`（`Protocol.h` 的 `COMPRESS_THRESHOLD`、`frame_flag_compressed`）。
- **加密没有**：帧头虽然预留了 `frame_flag_encrypted = 0x02`，但注释写着「本期保留不实现」，全仓库无人置位或处理。
- **TLS 也没有**：服务端 `net/`、`chatserversrc/`、`fileserversrc/` 里没有任何 TLS 实现。客户端的 `m_tls` 字段与 `flamingo.ini` 里的 `tls=` 只是空挂的脚手架，从未被读取使用。
- **口令不是明文过网**，客户端上送的是 SHA-256（`IUSocket.cpp` 的 `Login`），但该值**可直接重放登录**，等价于口令本身。

所以现状是：任何能在链路上抓包的人，可以看到全部聊天内容、通讯录、文件内容，并能重放登录凭据。

---

## 2. 路线选择：应用层帧体加密

两条路可走，选后者：

| | 传输层 TLS | 应用层帧体加密（本方案） |
| --- | --- | --- |
| 密码学实现 | 交给成熟库，最省心 | 用 libsodium 的高层 API，仍不自己实现算法 |
| 证书体系 | **必须有**，自建 IM 多为自签名，客户端要配信任链 | 不需要，改为在客户端预置服务端公钥 |
| 改动范围 | 服务端 `TcpConnection` 层 + 客户端 socket 层 | 帧编解码层，位置更集中 |
| 与既有设计的关系 | 与帧头预留的加密位无关 | 正是帧头注释里预留的那条路 |

决定性理由是**证书运维**：自签名证书的分发、过期、更换在自建部署里是长期负担，而预置一个 32 字节公钥可以直接写进本来就要分发的 `flamingo.ini`。

**必须说清的前提**：本方案的抗中间人能力，**完全取决于客户端是否预置并校验了服务端公钥**。不校验的话，加密只防被动窃听，防不住中间人——攻击者可两头各握一次手，中间全程解密。因此「预置公钥」不是可选项。

## 3. libsodium 用法详解

本节是给不熟悉 libsodium 的人看的。所有数字都是在本仓库 `third-party/libsodium-1.0.22-RELEASE` 上**实测**得到的，不是抄文档。

### 3.1 为什么用它，以及绝对不做什么

**绝不自己实现算法，也不用低层 API 自行拼装**（选模式、选填充、选 IV 那种）。这类代码翻车时**不报错、功能照常跑**——加密看着在工作，实际可能被轻易破解，而且没有任何测试会告诉你。libsodium 的高层 API 的设计目标就是「不给你用错的机会」：不暴露模式选择，nonce 由库自己管，认证失败一律返回非零。

### 3.2 初始化

```cpp
#include <sodium.h>

if (sodium_init() < 0) {
    // 初始化失败，此时任何加密函数都不可用，必须终止相关流程
}
```

- 返回 `0` 成功、`1` 表示之前已初始化过（也算成功）、`-1` 失败。
- **必须在使用任何其它 sodium 函数之前调用一次**，且应当在创建工作线程之前调用。
- 多次调用是安全的，所以可以在服务端 `main` 与客户端启动处各调一次，不必费心去做「只调一次」的协调。

### 3.3 三组原语，各管一件事

| 用途 | 原语 | 关键函数 |
| --- | --- | --- |
| 服务端身份（防中间人） | Ed25519 签名 | `crypto_sign_*` |
| 协商本次连接的会话密钥 | X25519 密钥交换 | `crypto_kx_*` |
| 加密每一帧的包体 | XChaCha20-Poly1305 流加密 | `crypto_secretstream_xchacha20poly1305_*` |

实测尺寸（`sizeof` 与常量值）：

```
Ed25519    公钥 32   私钥 64   种子 32   签名 64      字节
X25519     公钥 32   私钥 32   会话密钥 32           字节
secretstream  流头 24   每帧固定开销 17              字节
```

### 3.4 身份密钥：Ed25519

服务端的长期身份。**私钥只存在服务端**，公钥分发给所有客户端。

```cpp
unsigned char pk[crypto_sign_PUBLICKEYBYTES];   // 32
unsigned char sk[crypto_sign_SECRETKEYBYTES];   // 64
unsigned char seed[crypto_sign_SEEDBYTES];      // 32

// 首次生成：随机种子 -> 确定性推出密钥对
randombytes_buf(seed, sizeof seed);
crypto_sign_seed_keypair(pk, sk, seed);

// 之后每次启动：从文件读回 seed，重新推出同一对密钥
crypto_sign_seed_keypair(pk, sk, seed);
```

**只需持久化 32 字节的 seed**，公私钥都能从它确定性地推出来，不必存 64 字节私钥。

签名与验签（分离签名，签名不与消息拼在一起）：

```cpp
// 服务端签
unsigned char sig[crypto_sign_BYTES];           // 64
unsigned long long siglen = 0;
crypto_sign_detached(sig, &siglen, msg, msglen, sk);

// 客户端验；返回 0 才算通过，非 0 一律视为握手失败
if (crypto_sign_verify_detached(sig, msg, msglen, pinnedServerPk) != 0) {
    // 中间人、或连错了服务器，必须断开
}
```

实测：换一把不相干的公钥去验，`crypto_sign_verify_detached` 返回非 0——**中间人正是在这一步被挡住**。

### 3.5 密钥交换：X25519（crypto_kx）

每条连接各生成一次性密钥对，用完即弃。

```cpp
unsigned char pk[crypto_kx_PUBLICKEYBYTES];     // 32
unsigned char sk[crypto_kx_SECRETKEYBYTES];     // 32
crypto_kx_keypair(pk, sk);
```

双方各自导出**两把**会话密钥，收发各一把：

```cpp
// 客户端：参数顺序是 (rx, tx, 自己的公钥, 自己的私钥, 对方公钥)
unsigned char rx[crypto_kx_SESSIONKEYBYTES], tx[crypto_kx_SESSIONKEYBYTES];   // 各 32
if (crypto_kx_client_session_keys(rx, tx, myPk, mySk, peerPk) != 0) {
    // 对方公钥非法（如低阶点），握手失败
}

// 服务端：函数名不同，参数顺序相同
crypto_kx_server_session_keys(rx, tx, myPk, mySk, peerPk);
```

**关键约定**：客户端的 `tx` 与服务端的 `rx` 是同一把密钥（客户端→服务端方向），反之亦然。实测已验证两侧导出的字节完全一致。

**必须一边用 client 版、一边用 server 版**，两边都调 client 版会导出对不上的密钥。

### 3.6 帧体加密：secretstream

这是本方案选它而不选普通 AEAD 的关键原因：**nonce 由库内部自增管理，调用方碰不到**。手工管 nonce 是 AEAD 用错的最大来源（重用一次 nonce 就可能泄露明文）。

它还天然提供**顺序保证**：消息被重排、重放、截断，解密都会失败。

发送方（每个方向一个 state）：

```cpp
crypto_secretstream_xchacha20poly1305_state st;
unsigned char header[crypto_secretstream_xchacha20poly1305_HEADERBYTES];   // 24

// 初始化，产出 24 字节流头，必须发给对端
crypto_secretstream_xchacha20poly1305_init_push(&st, header, key);

// 逐帧加密；ad 是「附加认证数据」，参与认证但不被加密
unsigned long long clen = 0;
crypto_secretstream_xchacha20poly1305_push(
    &st, cipher, &clen, plain, plainlen, ad, adlen,
    crypto_secretstream_xchacha20poly1305_TAG_MESSAGE);
// clen == plainlen + crypto_secretstream_xchacha20poly1305_ABYTES(17)
```

接收方：

```cpp
crypto_secretstream_xchacha20poly1305_state st;
if (crypto_secretstream_xchacha20poly1305_init_pull(&st, peerHeader, key) != 0) {
    // 流头非法
}

unsigned long long plen = 0;
unsigned char tag = 0;
if (crypto_secretstream_xchacha20poly1305_pull(
        &st, plain, &plen, &tag, cipher, clen, ad, adlen) != 0) {
    // 认证失败：被篡改、乱序、重放、或密钥不对。必须断开连接，不能重试
}
```

**两条使用纪律**：

1. **state 是有状态的，且不是线程安全的。** 同一方向的发送必须串行，否则内部计数器错乱。实现里给每个方向的 state 各加一把锁。
2. **解密失败不可恢复。** 一旦某帧认证失败，该方向的流就废了，只能断连重连——不要跳过这一帧继续解下一帧。

### 3.7 其它会用到的工具函数

```cpp
randombytes_buf(buf, len);                 // 密码学安全随机数，用于生成种子
sodium_memzero(buf, len);                  // 擦除内存里的密钥，编译器不会优化掉
sodium_memcmp(a, b, len);                  // 常数时间比较，防时序侧信道

// 二进制 <-> 文本，配置文件与 JSON 里传密钥用
sodium_bin2base64(out, outlen, bin, binlen, sodium_base64_VARIANT_ORIGINAL);
sodium_base642bin(bin, binmax, b64, b64len, NULL, &binlen, NULL,
                  sodium_base64_VARIANT_ORIGINAL);
sodium_bin2hex(hex, hexmax, bin, binlen);
```

`flamingo.ini` **必须保持纯 ASCII**（见文件头注释），base64 与 hex 都满足。

## 4. 握手设计

连接建立后、任何业务帧之前，走三帧握手，全部使用 `cmd_handshake`（1001，协议里早已预留）。**握手帧本身是明文**——此时还没有密钥。

```
客户端                                                    服务端
  |                                                          |
  |-- 帧1  cmd_handshake  {ver, cpk, cnonce}  ------------->|
  |                                     生成临时密钥对、导出会话密钥
  |                                     用身份私钥对握手记录签名
  |<-- 帧2  cmd_handshake  {code, spk, snonce, sig, shdr} ---|
  |                                                          |
  验证 sig（用预置的服务端公钥）                              |
  导出会话密钥、初始化自己的发送流                             |
  |-- 帧3  cmd_handshake  {chdr}  -------------------------->|
  |                                                          |
  |============ 之后所有帧的包体均加密 ====================>|
```

**帧 1**（客户端 → 服务端）

```json
{"ver":1, "cpk":"<base64 32B 客户端临时公钥>", "cnonce":"<base64 16B 随机数>"}
```

**帧 2**（服务端 → 客户端）

```json
{"code":0, "spk":"<base64 32B>", "snonce":"<base64 16B>",
 "sig":"<base64 64B>", "shdr":"<base64 24B 服务端发送流的流头>"}
```

签名覆盖的握手记录（按顺序拼接的原始字节，不是 base64 文本）：

```
transcript = ver(1字节) || cpk(32) || cnonce(16) || spk(32) || snonce(16) || shdr(24)
```

把 `shdr` 也纳入签名，是为了防止有人替换流头；把两个随机数纳入，是为了让每次握手的记录都不同。

**帧 3**（客户端 → 服务端）

```json
{"chdr":"<base64 24B 客户端发送流的流头>"}
```

客户端必须先收到帧 2 才能导出密钥、才能初始化自己的发送流，所以流头只能在第三帧发，握手无法压缩成两帧。

握手失败（验签不过、字段缺失、base64 非法、公钥非法）时：**双方都直接断开连接并记日志，不重试、不降级为明文**。

## 5. 帧格式变更

帧头 24 字节的结构**不变**，只是两个字段的语义要精确化，并新启用一个标志位。

### 5.1 处理顺序：先压缩、后加密

```
发送： 明文包体 → (长度 ≥ 256 则 zlib 压缩) → secretstream 加密 → 上线
接收： 线上数据 → secretstream 解密 → (若置了压缩位则 zlib 解压) → 明文包体
```

**顺序不能反**。密文是高熵数据、压不动，先加密再压缩等于白压。这个顺序两端任何一处写反，表现都是解不出的乱码，所以在两边代码里都要注释写死。

### 5.2 字段语义

| 字段 | 含义 |
| --- | --- |
| `flags` | 可同时置 `frame_flag_compressed(0x01)` 与 `frame_flag_encrypted(0x02)` |
| `bodylen` | **线上实际字节数**，即最终密文长度 |
| `originlen` | **最原始的明文长度**（压缩前、加密前） |

未压缩且未加密时，`originlen == bodylen`，与改造前一致。加密后 `bodylen = 压缩后长度 + 17`。

### 5.3 附加认证数据绑定帧头字段

每帧加解密时都要传一份「附加认证数据」（AD）——它参与认证但不被加密。把帧头的关键字段纳进来之后，攻击者改动其中任何一个，接收方解密都会失败：无法把一帧改投成另一个 `cmd`、无法替换序列号、无法伪造长度。

AD 由 `buildFrameAd()` 按固定布局拼出，共 16 字节，全部大端序：

```
cmd(2) | flags(1) | 固定 0(1) | seq(4) | bodylen(4) | originlen(4)
```

**这里不直接取帧头的原始字节**，而是按上述布局重新拼一遍，原因有二：一是发送侧的帧头由 `FrameCodec` 内部生成、外部拿不到，取原始字节就得改动那个已有测试覆盖的模块；二是这样两端都不依赖帧头的内存布局，日后帧头增删保留字段也不会牵动加密。

`magic` / `version` 是常量、`headercrc` 是派生值，不纳入不影响安全性。

实测已验证：改动 AD 里任意一个比特，`crypto_secretstream_..._pull` 返回非 0。

## 6. 密钥管理

**服务端身份密钥**

- 首次启动时生成 32 字节种子，写入 `etc/server_key`（文本，hex 编码），文件权限设为仅属主可读写（0600）。
- 之后每次启动读回种子推出密钥对。
- 同时把公钥写到 `etc/server_key.pub`（base64），并在日志里打出**指纹**（公钥前 8 字节 hex）便于核对。
- **私钥、种子、会话密钥一律不得进日志**，只允许打指纹。

**客户端预置公钥**

`flamingo.ini` 的 `[server]` 段新增：

```ini
serverpubkey=<base64 32 字节服务端公钥>
```

未配置时：若服务端要求加密，则握手必然失败、客户端报「未配置服务端公钥」并拒绝连接。**不做「首次连接自动信任」**——那在首次连接时仍有中间人窗口，且开发期每次换服务端密钥都要清缓存，反而添乱。

**密钥更换**：删掉 `etc/server_key` 重启即生成新的，再把新公钥分发给客户端。三个服务（chat / file / img）**必须共用同一份身份密钥文件**，否则客户端要配三个公钥。

## 7. 配置项

`chatserver.conf` / `fileserver.conf` / `imgserver.conf` 各加两项：

```ini
#encryption: 0=关闭（明文，仅用于抓包排查）  1=开启（默认）
encryption=1

#身份密钥文件路径。相对路径按「实际加载的那个配置文件所在目录」解析（通常就是 etc/）。
serverkeyfile=server_key
```

`serverkeyfile` 的相对路径解析规则与 `logfiledir`、`dbpath` **不同**，后两者按可执行文件所在目录解析。这个差别是刻意的：`logfiledir` 与 `dbpath` 是各服务自己的产出目录，而身份密钥要求三个服务共用同一份，而三个服务的 `.conf` 本来就在同一个 `etc/` 目录里，按配置文件定位天然就落到同一个文件上，不需要额外约定。若按可执行文件目录解析，Windows 下可执行文件在 `windowsproj\x64\<配置>\`、Linux 下在 `build-linux/`，各自会算出一个并不存在的子目录。

`encryption` 这一项**缺失时按开启处理**。安全开关的默认值必须偏保守，否则有人漏配一行就在不知情的情况下裸奔。

`encryption=1` 时，未完成握手的连接**只允许收 `cmd_handshake`**，其它 cmd 一律拒绝并断开，日志记明原因。握手完成之后反过来，**只接受密文帧**，收到明文业务帧同样拒绝并断开，不允许明文与密文混发。

实现上这段启动逻辑三个服务共用一份，在 `utils/ServerConfigLoader.h` 的 `InitProtocolEncryption()`，各服务的 `main.cpp` 只调用它并在失败时终止启动。**开着加密却拿不到密钥时必须让启动失败**，不能退回明文继续跑——那会让管理员以为链路已加密。

## 8. 构建集成

libsodium 已放在 `third-party/libsodium-1.0.22-RELEASE/`（源码包，自带 MSVC 工程）。

服务端不直接链接这里的编译产物：编好的头文件与静态库随仓库提交在 `flamingoserver/deps/libsodium/`（`include/`、`lib/x64/<配置>/libsodium.lib`、`lib/linux/libsodium.a`），来源与重编方法见该目录的 `README.txt`。下面的 Windows 步骤是客户端各工程的接法。

**Windows**：用它自带的解决方案编静态库

```
third-party\libsodium-1.0.22-RELEASE\builds\msvc\vs2022\libsodium.sln
配置 StaticDebug / StaticRelease，平台 x64 与 Win32
产物：bin\<平台>\<配置>\v143\static\libsodium.lib
```

**运行库必须一致**：libsodium 的 `StaticDebug` 用 `/MTd`。客户端本来就是 `/MTd`；服务端四个工程原先没显式设置、走默认 `/MDd`，已于 2026-08-12 统一改为 `/MTd`（Debug）与 `/MT`（Release），顺带去掉了对 VC++ 运行库 DLL 的依赖。CRT 不一致会报 `LNK4098`。

各工程需要加：

- 附加包含目录：`third-party\libsodium-1.0.22-RELEASE\src\libsodium\include`
- 附加库目录：`third-party\libsodium-1.0.22-RELEASE\bin\<平台>\<配置>\v143\static`
- 附加依赖项：`libsodium.lib`
- 预处理器定义：`SODIUM_STATIC`（静态链接时必须定义，否则符号按 DLL 导入解析）

**Linux**：`CMakeLists.txt` 按完整路径链接 `deps/libsodium/lib/linux/libsodium.a`，不写库名，避免链接器在系统目录里找到另一份 libsodium。

## 9. 客户端接入

### 9.1 客户端有多条独立链路，不是一条

服务端的发送只有一个出口（`TcpSession::send`），接起来很轻松；客户端不是这样，它同时维护多条到服务端的连接，各有各的收发实现。方案实施时有主连接、文件传输、图片传输、中转通道四条，之后各功能新增的连接也都走同一套三帧握手与帧体加密（客户端经 `net/HandshakeRunner` 的 `performClientHandshake()` 握手，没有配置 `serverpubkey` 时走明文，见 9.6）：

| 链路 | 端口 | 客户端实现 | 服务端会话类 |
| --- | --- | --- | --- |
| chatserver 主连接 | 20000 | `net/IUSocket.cpp` | `chatserversrc/ChatSession` |
| 文件传输（共享连接） | 20001 | `net/FileTransfer.cpp`、`net/FileStreamTransfer.cpp` | `fileserversrc/FileSession` |

以下几种不走三帧握手：

- **P2P 直连（UDP）**：两端之间端到端加密。每个 P2P 会话两端各生成一个临时 X25519 密钥对，公钥经 chatserver 的 2303 交换，按角色导出收、发两把密钥；每个报文用 ChaCha20-Poly1305（IETF）加密认证，报文头作为附加数据参与认证，接收方向带重放窗口（`flamingoclient/FlamingoP2P/Core/P2PCrypto.h`）。信任 chatserver 转交的对方公钥，网络上的第三方与中转服务器都读不到内容。
- **P2P 地址探测（imgserver 的 UDP 20004 / 20005）**：兼容 RFC 5389 的 Binding 请求与应答，明文，只携带地址，不承载业务内容（`flamingoclient/FlamingoP2P/Ice/P2PStunClient.cpp`、`flamingoserver/imgserversrc/P2PAddressProbe.cpp`）。
- **单聊密聊**：消息走主连接（帧体照常加密），另在两端之间端到端加密（X25519 与 XChaCha20-Poly1305），服务端只转发它解不开的密文，见 `docs/密聊方案.md`。

**每一条都要接**，漏掉任何一条，那条链路上的内容仍是明文，而且由于服务端在握手完成前会拒收业务帧，那条链路会直接连不上。

有两处容易被漏掉。其一是 `net/FileServerConn.h`：它自带 socket、不走 `CIUSocket::ConnectToFileServer`，群文件并发池与升级包下载都用它，且按其注释是「可以在未登录时使用」。其二是中转链路在客户端有两份互相独立的实现（远程桌面一份、音视频一份），而服务端是同一个 `RelaySession`。

**自动升级的两段都在覆盖范围内**：检查更新（`cmd_check_update`）走主连接，`CheckUpdateSync` 内部先调 `Connect()`，握手在那里完成、与登录无关；下载升级包走 `net/FileServerConn`。`FlamingoUpdater` 只解压 zip、不联网，不涉及。

由此带来一个必须记住的后果：**升级通道自身被加密之后，加密相关的改动无法再靠自动升级修复**。不会握手的客户端连不上服务端，也就下载不到新版本。本期处于开发阶段、不考虑存量旧客户端，故不做处理；正式发布之后若要再动握手或密钥格式，必须先想清楚存量客户端怎么升上来（可选办法：服务端对下载升级包这一个 cmd 放行明文，并靠升级包签名而非传输加密来防篡改）。

### 9.2 握手放在 Connect 内部，且在"已连接"标志置真之前

对每条链路，三帧握手都在该链路的连接函数内部同步走完，成功之后才把"已连接"标志置真、才算连接可用；握手失败等同于连接失败，走各自既有的连接失败路径。

主连接把握手放在这个位置有一条实证依据：`IsClosed()` 的实现就是 `return !m_bConnected`（`net/IUSocket.cpp:1158`），而收取线程循环顶部是 `if (IsClosed()) { ::Sleep(200); continue; }`（`net/IUSocket.cpp:1273`），`Connect()` 的两条成功路径都在最末一行才 `m_bConnected = true`（`net/IUSocket.cpp:535` 与 `:562`）。也就是说标志置真之前收取线程一直睡着，同步收 ServerHello 不会和它抢数据。**握手一旦挪到 `Connect()` 外面（例如放进 `Login()`），就会与收取线程产生竞争。**

放在 `Connect()` 里还有一个好处：`Login`、`Register`、`CheckUpdateSync`、`Reconnect` 全都要先调它，接一处即全覆盖，不会漏掉某条入口。

### 9.3 握手流程只留一份：net/HandshakeRunner

各条链路的收发方式各不相同（主连接走 `CIUSocket::SendData`，`FileServerConn` 自带 socket 裸收发，中转通道连上后还会切回阻塞模式），但**三帧握手的流程对每条链路完全相同**。这份流程收在 `flamingoclient/Source/net/HandshakeRunner.h` 的 `performClientHandshake()` 里，各链路只提供一个实现 `IHandshakeChannel` 的薄适配器（两个方法：发满 N 字节、收满 N 字节）。

这不只是省代码。实施中出过一次教训：产品代码与联调测试各写了一份握手流程，**两份都踩了同一个坑**——`net::encodeFrame` 是<u>追加</u>语义（为的是支持把多帧攒在一起批量发出），复用同一个缓冲会把第 3 帧拼在第 1 帧后面一起发出去。服务端于是连着收到两个 ClientHello，第二个正好撞在「等客户端流头」的状态上，报的错却是「字段 chdr 缺失」，离真正的原因很远。流程只留一份之后，联调测试验的就是产品代码本身，这类「测试和产品各错各的」不会再发生。

**握手三帧里第 3 帧必须绕开发送漏斗**，这是「所有帧都走漏斗」那条规则的唯一例外：`buildClientStreamHeader()` 一返回，客户端的握手状态就已是「完成」，再走漏斗会把这一帧自己也加密；而服务端正是靠这一帧才能初始化接收流，那时它还解不开任何密文。

### 9.4 先收敛建帧与解帧的漏斗，再挂加解密

改造前，客户端的建帧与解帧是散开的。以主连接为例，建帧散在 `Login`、`Register`、`CheckUpdateSync`、`EnqueueFrame` 四处，解帧散在异步的 `DecodePackages` 与同步的 `RecvOneFrame` 两处。

**必须先把它们各自收敛成一个函数，再在那一个函数里挂加解密**，不允许在四五个地方分别改。漏掉一处的后果是明文与密文混发，服务端收到会直接断开连接，而使用者看到的现象只是"登录偶尔失败"，很难往加密上想。

收敛这一步是纯重构，线上字节一个都不变，应当**单独成一步并单独验证**，这样后面万一出问题，能一眼分清是重构引入的还是加密引入的。

### 9.5 有并发发送方的链路：加密必须在发送锁之内

中转通道（远程桌面、音视频）有多条业务线程往同一条连接上发帧——远程桌面是被控端的推流线程与控制端的 UI 线程，音视频更直接，音频采集线程与视频采集线程会同时发。这两处原本的写法都是**锁外组帧、锁内写 socket**，加密引入之后这个顺序<u>必须改</u>。

原因是流加密按调用顺序推进内部计数器。若在锁外加密、锁内发送，两条线程产出的密文写到 socket 的先后就可能与加密的先后相反，接收方按流顺序解密必然失败并断开连接。`FrameCipher` 内部虽然给每个方向各有一把锁，但那只保证单次加密是原子的，**保证不了加密顺序等于上线顺序**。

因此这两处都改成了「加密 + 套帧头 + 写 socket」整体在发送锁内完成。远程桌面为此把分片切分与套帧头拆成两步（新增只产包体的 `relayframing::BuildEngineBodies`），切分仍可在锁外做——它与顺序无关。

**新增有并发发送方的链路时，这一条要照做。** 服务端的 `RelaySession` 同理，它也加了发送锁，因为一条中转连接上有两个写入方：本会话回的应答，以及配对端 I/O 线程转发来的数据帧。

### 9.6 客户端不设独立的加密开关

客户端只看 `flamingo.ini` 里有没有配 `serverpubkey`：配了就握手加密，没配就走明文。

不设开关是刻意的。若客户端也有一个开关，它与服务端的 `encryption` 配反时（一边开一边关）连接会失败，而失败原因要同时看两边配置才能判断。只看有没有公钥，就与服务端的开关天然配成一对：服务端关了加密而客户端配了公钥，服务端会明确拒绝并记录原因；服务端开着而客户端没配公钥，服务端记录的是 `recv business frame before handshake completed`。两种情形的日志都指向确定的原因。

## 10. 中转通道：服务端解密后重新加密

远程桌面与音视频的中转通道要单独说明，因为它与另外三条链路的结构不同。

`RelaySession` 原本是**字节级透传**：`onData` 把整帧原始字节（连帧头一起）原样转发给配对端，不解析包体；配套的 `RelayHub` 只保存 `TcpConnection` 的弱引用。加密引入之后"原样转发"不再成立，因为两条连接各有各的会话密钥。

**采用的做法**是：relay 连接照常做客户端与服务端之间的三帧握手，服务端转发时先用本端密钥解密、再用配对端的密钥重新加密后发出。相应地 `RelayHub` 改为保存 `RelaySession` 的弱引用、`getPeer` 返回对端会话——`RelayServer` 本来就用 `std::list<std::shared_ptr<RelaySession>>` 持有全部会话，所以弱引用是安全的。

这样各条链路保持同一套机制，客户端直接复用 `ClientHandshake`，握手帧里的 relay 令牌也一并受到保护。代价是 imgserver 每个屏幕帧多做两次对称加密，以及服务端能看到明文的屏幕内容。

**曾考虑但未采用的做法**是让两端客户端做端到端加密、密钥由 chatserver 随 relay 令牌下发，imgserver 保持透传。它的优点是服务端看不到屏幕内容，但 relay 握手帧里的令牌仍是明文，中间人抓到就能抢先冒充一端接入；而且它要改动 chatserver 的令牌下发协议与 `docs/协议设计-v2.md`。企业版是客户自行部署的服务器，"服务端看不到内容"不属于本期要防的威胁，故不采用。

## 13. 测试

### 13.1 单元测试（各自那一半）

客户端在 `Source/Tests/FrameCryptoTests.cpp`：握手状态机的时序约束、验签能否挡住中间人、帧体加解密往返一致、篡改后必须失败、公钥文本解析与指纹。服务端在 `tests/` 下同类覆盖。

**这些测试证明不了两端能互通**——它们各自只验证自己那一半自洽。而互通失败的典型原因（握手记录拼接顺序不同、附加认证数据的字节布局差一位、base64 变体不一致）恰恰是各自测试测不出来的。

### 13.2 跨实现联调（`Source/Tests/` 下的 `HandshakeLiveTests.cpp` 与 `RelayForwardLiveTests.cpp`）

两份镜像实现在同一个进程里链接不到一起（同名 namespace 下有同名的 `FrameCipher`、`buildFrameAd`，会重复定义），所以只能走真实 socket。这组用例带 `[.live]` 标签，常规测试会跳过，要跑就显式指定：`FlamingoUnit.exe "[live]"`（只跑中转那五条用 `"[relay]"`）。

建连、按帧收发、走三帧握手这套脚手架收在 `Source/Tests/LiveTestConn.h`，两个测试文件共用，端口与身份公钥常量也在那里。

跑之前起三个独立实例（端口错开，避免与开发中正在用的撞上）：chatserver 20100、fileserver 20101、imgserver 20102 加中转 20103，`encryption=1`，`serverkeyfile` 都指向真正在用的那份密钥，客户端那侧的公钥常量填对应的 `server_key.pub`。

覆盖的十三条：

| 用例 | 验的是什么 |
| --- | --- |
| HSLIVE1 | 客户端侧走完三帧握手 |
| HSLIVE2 | chatserver 上加密业务帧双向可解 |
| HSLIVE3 | chatserver 上未握手发业务帧被拒 |
| HSLIVE4 | 换一把公钥验签必然失败 |
| HSLIVE5 | fileserver 上握手与加密帧双向可解 |
| HSLIVE6 | fileserver 上未握手发业务帧被拒 |
| HSLIVE7 | 中转通道握手与加密报到帧可解 |
| HSLIVE8 | 中转通道上未握手发报到帧被拒 |
| RELAY1 | 一对同 sessionid、角色相反的令牌，两端各自握手并报到成功 |
| RELAY2 | A 端发的加密帧，B 端解出的明文与 A 发送时逐字节相同；且**两端密文不相同** |
| RELAY3 | 反方向 B→A 同样成立（两个方向各有一套流密钥，只验一个方向漏得过去） |
| RELAY4 | 压缩标志与 originlen 经服务端转发后原样保留 |
| RELAY5 | 音视频那一档（`cmd_av_relay_*`）同样能配对并双向转发 |

RELAY2 里「两端密文不相同」那条断言是刻意加的：服务端若哪天退回字节透传，功能看起来照常，唯有这条会失败。测试载荷用了覆盖全部 256 种字节取值的数据（含 `0x00`），防的是某处把包体当 C 字符串处理。

中转令牌是把服务端的 `flamingoserver/utils/RelayToken.cpp` 直接编进测试工程签出来的，不是在测试里另写一份同样算法——那样测的就成了测试自己的实现，令牌格式日后改动时两边会各错各的。

**有一条经验值得单独记下来。** HSLIVE1 这类「客户端侧走完三帧」的用例<u>证明不了两端真的握上手了</u>：第 3 帧没有应答，客户端把它发出去就自认为完成，服务端认不认这一帧在那里根本看不出来。实施中就出过——第 3 帧因为缓冲区复用被拼在了 ClientHello 后面，服务端一路报错，那条用例却照样全绿。**真正的判据只有一个：发一帧加密的业务帧并收到加密的应答。** 服务端解不开就不会回，客户端解不开就断言失败。写这类联调用例时，必须有这样一条往返断言，否则整组测试可能是自欺欺人的。

### 13.3 性能实测（`Source/Tests/CryptoBenchTests.cpp`）

方案立项时写过一句「加解密开销可以忽略」，当时是<u>推测</u>，估的量级是每秒 1 GB 以上。实测下来**这个推测偏高了一倍以上**，结论方向虽然对，但数字不能照抄。

测的是 XChaCha20-Poly1305 一次加密加一次解密的往返，附加认证数据取与真实帧一致的 16 字节。用例带 `[.bench]` 标签，常规测试跳过，跑法：`FlamingoUnit.exe "[bench]"`。

本机（x64）实测：

| 单帧大小 | Debug 往返吞吐 | Release 往返吞吐 |
| --- | --- | --- |
| 512 B（聊天消息一档） | 44.6 MB/s | 239.2 MB/s |
| 100 KB（典型 1080p 屏幕帧） | 82.7 MB/s | 391.1 MB/s |
| 512 KB（中转分片上限） | 82.0 MB/s | 386.5 MB/s |

**Debug 比 Release 慢约 4.7 倍**，因为它链的是未优化的 libsodium。下面按 Release 折算，1080p、30 fps、每帧 100 KB：

| 角色 | 每帧运算次数 | 每秒耗时 | 占单核 |
| --- | --- | --- | --- |
| 客户端（发送端加密 / 接收端解密各一次） | 1 | 3.75 ms | 0.375% |
| 中转服务端（解密 + 重新加密） | 2 | 7.49 ms | 0.749% |

**结论：开销确实可以忽略**，但依据是这组数字而不是当初的估计。一帧屏幕数据在整条链路上一共过四次运算（发送端加密、服务端解密、服务端重新加密、接收端解密），分摊在三个进程上。中转服务端按每路会话 0.75% 单核计，同时跑 20 路远程桌面也只占 15% 的一个核，而且服务端本就是多线程的。

小包那一档的绝对耗时更值得看：512 字节的往返只要 2 微秒，对聊天消息这种量级完全不构成负担。

## 14. 不在本方案范围内

- **flamingoAdmin ↔ 服务端的 HTTP 接口**：`HttpClient` 已支持 `useTls`（`WINHTTP_FLAG_SECURE`），但服务端那个 HTTP 端口是纯明文实现。要加密需另架反向代理终结 TLS，另立一期。（flamingoAdmin 的 `FlamingoLink` 长连接走本方案的三帧握手与帧体加密，见 `flamingoAdmin/FlamingoLink/Net/LinkConnection.cpp`。）
- **帧头本身不加密**：`cmd`、包长、序列号等元数据仍可见，能看出「谁在什么时候发了一条消息」，但看不到内容。这是应用层加密的固有代价。
- **服务端之间**（chatserver ↔ fileserver 等）的内部通信不在本期。（chatserver 主动连 imgserver 中转端口的云端录制控制连接例外，它走本方案的三帧握手与帧体加密，见 9.1。）
