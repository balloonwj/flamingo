# 单聊发送文件夹方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-08-13
> 用途：记录给 flamingoclient 单聊接入「发送文件夹」的整体方案、协议设计、多通道并行传输设计与开发步骤。后续每步开工前据此细化、收尾后回填实际结果。

## 1. 背景与目标

现在单聊只能一个一个地发文件（`msgtype=3` 的文件消息），要把一整个目录发给同事，只能先压缩成一个压缩包。本方案给单聊补上「发送文件夹」：选中本地一个目录，连同它的子目录结构一起发给对方。

与发送单个文件相比，文件夹传输有四点本质差异，方案的全部复杂度都由它们衍生：

1. **必须先获得对方同意**，同意之后才开始传输——一个目录可能有几万个文件、几十 GB，不能像发一条文件消息那样先塞给对方。
2. **任一环节出错，整个文件夹即视为失败**，并且失败原因要让双方都看到。
3. **支持重试与断点续传**，但**仅在本次登录期间有效**。
4. **服务端记动作、不记内容**：文件夹里的文件不在服务端留任何记录（不写 `t_file`、不落磁盘、不进消息表），历史消息面板里也不提供重新下载；但一次传输结束后，会在双方的单聊会话里留下一条只写"发生过这次传输"及其结局的记录条。

第 4 条决定了实现路径：不能走现有的「上传到 fileserver、发一条文件消息、对方按 fileid 下载」那条链路，因为那条链路必然在 `t_file` 表留下文件元数据、在服务器磁盘留下文件内容（见 3.3）。文件夹传输改为**双方各建连接、由服务器在内存里转发**，字节不落盘、不入库，会话随退出登录消失。

第 4 条里"留一条记录条"这半句是 **2026-08-14 需求方追加的**。原先的口径是"文件夹与其中的文件都不在服务端留记录"，实测后需求方提出：传完之后聊天记录里空空如也，事后想不起来给谁发过哪个文件夹、传成功没有，故要求聊天记录里能看到发过什么文件夹。取舍是只加"动作"这一层——记文件夹名、目录数 / 文件数 / 总字节数与结局，仍不记文件清单与文件内容，故"字节不落盘、不入库"这条不变式没有被打破，也不因此多出重新下载的能力。落地细节见 5.5 与 `docs/协议设计-v2.md` 12.8。

## 2. 已确认的产品选择

以下选择均已与需求方确认，是本方案的前提，实现时不得擅自变更。

| 事项 | 结论 |
| --- | --- |
| 传输通道 | 由 **fileserver** 承载（保持"文件传输归文件服务器"的语义），**不新开监听端口**，在现有端口上按帧 cmd 分流 |
| 并行方式 | **一条控制通道 + N 条数据通道**；一期只做**文件级并行**，单个大文件不切段 |
| 通道条数 | 数据通道**默认 4 条**（每端连 5 条、服务端每次传输 10 条），由服务端配置项决定并下发，**硬上限 8**；另设服务端同时进行的文件夹传输会话数上限 |
| 征求同意 | 接收方在**会话内的气泡**上看到「接收 / 另存为 / 拒绝」，不弹独立授权窗。「接收」直接落到本机默认的接收目录、不打断用户，「另存为」才弹选目录框由用户挑位置。2026-08-14 实测反馈后由原先的「接收 / 拒绝」两个按钮拆成三个 —— 大多数时候用户并不在意存到哪里，每次都弹一个选目录框是多余的一步 |
| 失败语义 | 任一错误即整个文件夹失败，**双方都收到同一条失败原因** |
| 服务端记录 | **记动作、不记内容**：一次传输走到终态后在双方单聊会话里留一条 `msgtype=18` 的记录条（文件夹名 / 目录数 / 文件数 / 总字节数 / 结局），文件清单与文件内容一概不记、也不提供从历史重新下载。六种终态（被拒绝、应答前撤回、对方离线、邀请超时、失败、完成）一视同仁，**一次尝试走到任何终态都留且只留一条**。记录由**服务端**生成而非客户端补发。2026-08-14 实测反馈后由原先的「文件夹与其中的文件都不在服务端留记录」调整至此 —— 传完之后聊天记录里空空如也，事后想不起来给谁发过哪个文件夹 |
| 记录粒度 | **每次尝试各留一条**：一笔传输先失败、又在保留期内重试成功时，聊天记录里依次出现"传输失败"与"传输完成"两条，过程完整可见；连续重试多次就留多条。实现上会话表记一个从 1 起算的尝试序号，记录条的幂等键含它。2026-08-14 需求方在「每笔只留一条、以最先到达的终态为准」与本方案之间选定了本方案 —— 前者会让重试成功的一笔在聊天记录里一直显示为失败 |
| 重试 | **不做自动重连**；由用户手动点「重试」；失败会话保留 **10 分钟**，期内重试直接断点续传、不再征求接收方同意；超过 10 分钟只能重新发送并从零开始 |
| 重名 | 接收端目标位置已有同名文件夹时**自动改名新建**（`xxx(2)`）；重试续传时复用上次那个目录，不再改名新建 |
| 并发 | **每个用户同时最多 5 笔**文件夹传输（发送与接收各算一笔），阈值放服务端配置项 `foldermaxperuser`，**服务端是权威方**；整台服务器的会话总数另有上限。客户端另有一道同口径的本地闸门，阈值放客户端配置项 `foldermaxconcurrent`（`flamingoclient/Bin/config/flamingo.ini` 的 `[app]` 段，默认 5），作用是在用户点下去之前就给出提示，而不是等服务端拒绝。2026-08-14 实测反馈后由原先的「本机全局同时只跑一个」放宽至此 |
| 邀请超时 | 邀请无应答 **30 分钟**后自动作废，阈值放服务端配置项 `folderinvitetimeout`；发送方随时可以主动撤回，不必等超时。2026-08-14 实测反馈后由原先的 60 秒放宽至此 —— 接收方常常只是暂时离开座位 |
| 规模上限 | **文件数与总大小都限**，阈值放服务端配置项，由服务端校验，客户端不硬编码 |
| 工具栏图标 | 候选 **B：文件夹 + 夹内向上箭头**（四个候选的对比图见 `snapshots/folder-button-icon-candidates.png`） |
| 附带修复 | `FileServer::onDisconnected` 删错会话的既有缺陷本次一并修掉（见第 10 节） |

## 3. 现状盘点（据实证）

### 3.1 征求同意的握手有两套现成范式

远程桌面（`cmd_rd_invite` 1710 ~ `cmd_rd_relay_info` 1716，见 `flamingoserver/chatserversrc/Protocol.h:197-204`）与音视频通话都已经完整走过一遍「发起邀请 → 对方应答 → 签发中转令牌 → 双方连中转通道 → 状态推送收尾」。服务端的会话表在 `chatserversrc/RemoteDesktopManager.h`：内存里的 `sessionid → 会话` 映射，带创建时间供超时清理，**不查库、不落库**。文件夹传输的信令层照此复制即可。

### 3.2 中转层是通用的，多角色共存

imgserver 的 `RelaySession` 按令牌里的 `sessionid` 与 `role` 把两条连接配对，收到数据帧就转发给配对端，服务端不解析内容（`flamingoserver/imgserversrc/RelaySession.h:6-13`）。远程桌面与音视频已经是共用它的两套，令牌角色 `role_controller / role_controlled / role_caller / role_callee` 四个值并存（`flamingoserver/utils/RelayToken.h:47-54`）。中转单帧上限 2 MiB，远程桌面按 512 KiB 分片（`flamingoclient/Source/RemoteDesktop/RdRelayFraming.h:11`）。

### 3.3 走 fileserver 现有上传下载链路会留记录

每次 `cmd_request_upload` 都会在 `t_file` 表登记一行文件元数据（文件名、扩展名、大小、MD5、上传者），磁盘文件以 MD5 命名故内容天然去重（`flamingoserver/table.sql:552-568`）。这正是本功能要避免的"服务端记录"，故不能复用这条链路。

### 3.4 fileserver 的连接本来就是按 cmd 分发的

`FileSession::processFrame` 是一个 switch，目前只有 `cmd_file_upload` 与 `cmd_file_download` 两个分支（`flamingoserver/fileserversrc/FileSession.cpp:243-252`）；会话自身已有"当前处于什么传输模式"的概念，枚举 `transfer_mode` 现在是空闲 / 上传中 / 下载中三个值（`fileserversrc/FileSession.h:45-50`）。协议加密的三帧握手在业务分发之前统一做掉（`FileSession.cpp:180-235`）。这三点合起来意味着：中转能力可以作为第三种模式接进现有连接，**不必新开端口，也不必重写握手**。

另外 fileserver 起了 6 个 I/O 工作线程（`fileserversrc/FileServer.cpp:12`、`:25`），多条中转连接会落到不同线程上，转发与重新加密是真并行。fileserver 侧没有空闲连接超时踢下线的逻辑（`fileserversrc/` 内无相关代码），故控制通道长时间无数据也不会被服务端主动断开。

### 3.5 客户端已有"每笔传输各建一条 fileserver 连接"的先例

群文件并发池里每笔上传 / 下载各自新建一条独立的 fileserver 连接（`flamingoclient/Source/net/FileTransfer.h` 中的 `FileServerConn` 与并发池说明），连接、加密握手、阻塞收发这套代码可直接复用来建多条中转通道。

### 3.6 Windows 上服务端的连接数有硬上限（决定通道条数的关键约束）

`EventLoop` 在 Windows 分支创建的是 `SelectPoller`（`flamingoserver/net/EventLoop.cpp:48`；Linux 走 `EPollPoller`，见 `:52`），而 `SelectPoller::poll` 用 `fd_set` + `FD_SET` 收集待查连接（`net/SelectPoller.cpp:41-60`）。全仓库没有任何地方重定义 `FD_SETSIZE`（全文搜索无结果），故在 Windows 上取 winsock 的默认值 64：**每个 I/O 线程最多盯 64 条连接**，fileserver 有 6 个 I/O 线程，整个进程约 384 条封顶。

危险之处在于失败方式：winsock 的 `FD_SET` 在超出 `FD_SETSIZE` 时是**静默丢弃**，连接照样 accept 成功但永远收不到可读事件，表现为传输凭空卡住、日志里毫无线索。因此多通道方案必须自己在上层设闸——服务端同时进行的文件夹传输会话数超过配置上限时，直接拒绝新会话并回明确的错误码，绝不能让连接连上之后静默卡死。Linux 上走 epoll 没有这个限制，但闸门照设，两个平台行为一致。

### 3.7 字节级续传的既有做法可以照搬语义

现有上传的每片回执都回带服务端权威的 `nextoffset`，服务端对 `.part` 临时文件做续传（`flamingoserver/fileserversrc/FileSession.cpp:325`、`:391-401`）。文件夹传输沿用同一语义，区别只是权威位点由**接收端**给出，而不是服务器。

## 4. 总体设计

### 4.1 拓扑

```
发送端                         chatserver                        接收端
  │  1810 邀请 ─────────────────►│                                  │
  │                              │─── 1811 邀请推送 ───────────────►│
  │                              │◄── 1812 同意 / 拒绝 ─────────────│
  │◄── 1816 中转参数(含 lanes) ──│─── 1816 中转参数 ───────────────►│
  │                                                                 │
  │        fileserver 现有监听端口（不新开端口）                     │
  │  lane0 控制通道 ═══════════[内存转发]═══════════════════════════ │
  │  lane1 数据通道 ═══════════[内存转发]═══════════════════════════ │
  │  lane2 数据通道 ═══════════[内存转发]═══════════════════════════ │
  │  ...                                                            │
  │                              │                                  │
  │  1814 结束(带 errcode) ─────►│─── 1815 状态推送 ───────────────►│
```

信令走 chatserver 主连接；字节走 fileserver，服务端只在内存里解密→重新加密→转发，不写盘、不入库。

### 4.2 通道分工

- **lane 0 是控制通道**：清单、目录创建回执、中止（含失败原因）、完成、重试同步。
- **lane 1..N 是数据通道**：只走文件字节。

把控制单独拉出来的理由：数据通道随时可能被一个大文件的字节流占满，而"某个文件写盘失败、整个文件夹中止"这条消息必须立刻送达对端；挤在同一条通道里，中止通知就得排在若干兆字节的数据之后。

数据通道数 N 由服务端配置项 `folderlanes` 决定（默认 4），经 `cmd_folder_relay_info` 下发，客户端不自行决定；**硬上限 8**，配置值越界时按 8 截断并记一条日志，中转握手里 `lane` 序号越界的连接直接拒绝。

这个默认值是这样定下来的：一次传输在服务端占用 `2 × (N + 1)` 条连接（双方各一套），N 取 4 即每次 10 条。收益上，多通道主要解决高时延链路上单条 TCP 跑不满带宽、以及大量小文件时每个文件一次往返的等待，这两项在 2~4 条之间提升最明显，再往上收益迅速变平，而接收端并行写多个文件在机械硬盘上会退化成随机写、反而更慢。约束上，Windows 的 select 上限（见 3.6）决定了连接不能随便挥霍。两头一夹，默认 4、上限 8。

同时进行的文件夹传输会话数由配置项 `foldermaxsessions` 封顶（Windows 建议 24，Linux 建议 128），超出时 `cmd_folder_invite` 直接返回"服务器繁忙"错误码。

### 4.3 文件如何分派到多条通道

发送端把清单里的文件排成一个待传队列，每条数据通道一个工作线程：取队首未传文件 → 在本通道上把它整个传完 → 再取下一个。不预先按大小分组，谁先传完谁先接下一个，天然负载均衡。

多通道能提速的三处：单条 TCP 在有时延、有丢包的链路上跑不满带宽，多条能占满；大量小文件时"一个文件一次往返"的等待可以在通道间重叠，不再串行累加；服务端的转发与重新加密分摊到不同 I/O 线程并行完成。

一期不做单个大文件切段并行，代价是"尾巴上只剩一个大文件时只有一条通道在干活"。实测下来若这一段拖慢明显，二期再补（见第 13 节）。

## 5. 协议设计

### 5.1 信令（chatserver 主连接，取 1800 段空闲号 1810~1817）

| cmd | 枚举名 | 方向与内容 |
| --- | --- | --- |
| 1810 | `cmd_folder_invite` | 发送方→服务器：`{peerid, foldername, totaldirs, totalfiles, totalsize}`；应答 `{code, msg, sessionid}`，因超限被拒时附 `maxfiles / maxsize` 供客户端提示 |
| 1811 | `cmd_folder_invite_notify` | 推送给接收方：`{sessionid, from, fromname, foldername, totaldirs, totalfiles, totalsize}` |
| 1812 | `cmd_folder_response` | 接收方→服务器：`{sessionid, accept}`，1 同意 / 0 拒绝 |
| 1813 | `cmd_folder_cancel` | 发送方在对方应答前取消：`{sessionid}` |
| 1814 | `cmd_folder_close` | 任一端结束本次传输：`{sessionid, result, errcode, errmsg}` |
| 1815 | `cmd_folder_state_notify` | 推送状态变更：`{sessionid, state, errcode, errmsg}`，覆盖响铃 / 拒绝 / 取消 / 对方离线 / 超时 / 失败 / 完成 |
| 1816 | `cmd_folder_relay_info` | 同意后下发给双方：`{sessionid, relayip, relayport, token, role, lanes}`。地址字段沿用远程桌面与通话推送的既有名字 `relayip` / `relayport`（见 `flamingoclient/Source/net/RemoteDesktopProtocolClient.cpp:127`），客户端解析代码因而可以复用 |
| 1817 | `cmd_folder_retry` | 期内重试：`{sessionid}`；服务端校验会话未过期、双方仍在线后重新签发令牌并再下发一次 1816 |

### 5.2 中转（fileserver 现有监听端口）

| cmd | 枚举名 | 说明 |
| --- | --- | --- |
| 1857 | `cmd_folder_relay_hello` | 连上后首帧报到，包体 `{token, lane}`；服务端验签、验角色、按 `(sessionid, lane)` 配对 |
| 1858 | `cmd_folder_relay_data` | 中转数据帧，包体为下一节的应用帧；服务端不解析，解密后用配对端密钥重新加密转发 |

令牌沿用 `utils/RelayToken`，新增两个角色常量：`role_folder_sender = 5`、`role_folder_receiver = 6`，续接现有的 1~4。**每端只签一枚令牌**，客户端拿它建 N+1 条连接，各连接在 hello 帧里报自己的 `lane` 序号；同一个 `(sessionid, lane, role)` 重复报到、`lane` 越界都直接拒绝。

### 5.3 通道内的应用帧

包体首字节为帧类型，与远程桌面的引擎帧同构。分片 512 KiB（与远程桌面同口径，中转单帧上限 2 MiB）。

| 帧类型 | 方向 | 内容 |
| --- | --- | --- |
| `ft_manifest` | 发→收 | 目录清单（相对路径列表，含空目录）+ 文件清单（相对路径、字节数） |
| `ft_manifest_ack` | 收→发 | **接收端把目录结构全部建好之后才回**，带每个文件的续传起点（首次全 0） |
| `ft_file_begin` | 发→收 | `{index, size, md5, offset}` |
| `ft_file_chunk` | 发→收 | `{index, offset}` + 二进制 |
| `ft_chunk_ack` | 收→发 | `{index, nextoffset}`，既是流控也是权威续传位点 |
| `ft_file_end` | 发→收 | `{index}`，标记该文件字节发完 |
| `ft_file_result` | 收→发 | `{index, code, msg}`，落盘与 MD5 校验结果 |
| `ft_abort` | 双向 | `{errcode, errmsg}`，任一端出错即发 |
| `ft_complete` | 发→收 | 全部文件传完 |

流控：每条数据通道各自维护窗口，在途分片不超过 4 片（512 KiB × 4 = 2 MiB），收到回执才继续。

### 5.4 错误码

在 600 文件域内取空号新增一组（具体数值落地时按 `Protocol.h` 现状顺排），至少覆盖：对方拒绝、对方离线、邀请超时、超出文件数上限、超出总大小上限、接收端建目录失败、接收端磁盘空间不足、写盘失败、读源文件失败、内容校验不符、中转通道断开、用户取消、会话已过期不可重试。

失败原因走两条路送达，保证双方都能看到：中转通道还活着时经 `ft_abort` 直达对端；通道已断则经 `cmd_folder_close` → 服务端 → `cmd_folder_state_notify` 兜底。

### 5.5 传输记录条（`message_type_folder` = 18）

一次传输走到终态后，服务端在**发送方与接收方之间的单聊会话**里落一条消息，`ctype` 为 1（单聊）、`msgtype` 为新增的 `message_type_folder`（18）、`from` 取文件夹发送方、`to` 取接收方（两端渲染出来的左右位置因而与传输方向一致）。`content` 只有七个字段：

```json
{ "sessionid": "…", "foldername": "…", "totaldirs": 12, "totalfiles": 128, "totalsize": 2576980378, "result": 8, "errcode": 0 }
```

`result` 取 `folder_transfer_state` 的终态值（3 已拒绝 / 4 应答前撤回 / 5 对方离线 / 6 邀请超时 / 7 失败 / 8 完成），`errcode` 仅 `result` 为 7 时填有意义的值（取 `error_code_folder_*`），其余结局恒为 0。**没有**文件清单、相对路径与 MD5，故这条记录不构成"服务端保存了文件夹内容"，也不因此多出重新下载的能力。字段表与边界情形见 `docs/协议设计-v2.md` 12.8。

**由服务端生成，不由客户端发。** 服务端是唯一知道全部终态的一方：邀请超时是服务端定时器判定的、对方离线是服务端发现的，这两种结局下发送方客户端可能根本不在线，交给客户端补记必然漏。

**双方都要收到。** 服务端生成的消息没有"发送方的发送回执"这一说，故发送方与接收方各收到一帧 `cmd_message_notify`，两帧的差别只在会话 id（各自视角下的会话 id 都是对端 userid）。会话列表的摘要与未读不另走一套 —— 会话集合、最后一条消息与未读数都由 `t_chatmsg` 派生（`MessageManager::getConversationBriefs`），记录一入库即自然生效。

**一次尝试一条记录。** 留记录的粒度是一次尝试，不是一次会话。会话表为每笔传输记一个从 1 起算的**尝试序号**（`FolderTransferSessionInfo::attemptSeq`）：建会话时为 1，此后每受理一次 `cmd_folder_retry`（`canRetry` 通过、真正要重新签发令牌）加一，加一与"会话置回传输中"在同一个临界区内完成（`FolderTransferManager::beginRetryAttempt`）。序号本身不进 `content`，只进幂等键。

**幂等。** 由两道防线保证，去重粒度都是「会话 id + 尝试序号」。

**第一道（主防线）是服务端的原子终结判定** `FolderTransferManager::finishAttempt`：「本次尝试是否已经终结过」的判断与「标记为已终结」在会话表那把互斥量的同一个临界区内一次做完，只有第一个调用方拿到放行，负责推 1815 与落记录；后到的一律被挡下、安静返回并记一条日志。会话的终态也由它在同一个临界区内置上，故「进入终态」这件事同样只发生一次。

**第二道是 `clientmsgid` 幂等键**：取由会话 id 与尝试序号一起派生的固定串 `"folder-" + sessionid + "-" + 尝试序号`，落库前先按「发送方 userid + `clientmsgid`」查一次（与 `cmd_send_message` 的重发去重是同一个键），已有记录就跳过。它挡的是日后新增的、绕开第一道防线的调用路径，以及进程重启前后的重复落库。

于是两个层面各自成立：**同一次尝试之内**只落一条（正常收尾时双方各发一帧 `cmd_folder_close`，无论先后到达还是同时落在两个工作线程上，都只有一个能通过终结判定），**不同次尝试之间**互不去重（序号既进了终结判定的粒度、也进了幂等键，后一次的记录不会被前一次那条挡住）。

**第一道防线是 2026-08-16 补的**，此前只有 `clientmsgid` 那一道。缺陷的表现是同一次传输在双方聊天记录里出现两条一模一样的记录条：一次传输结束时双方各发一帧 `cmd_folder_close`，两帧落在两个不同的 I/O 工作线程上，而「先按 `clientmsgid` 查一次、没有就落库」这种先查后写不是原子的，两个线程都查到"还没写过"，于是各插一条。2026-08-14 的实测日志里两条 `folder transfer record saved ... attempt: 1` 相隔 7 毫秒、分属线程 2668 与 18668，会话终态也被置了两次（`state: 2 -> 7` 之后又一次 `state: 7 -> 7`），跟着向对端多推了一帧 1815。修法是把判定与标记收进 `FolderTransferManager` 已有的那把互斥量 —— 会话状态与尝试序号本就归它维护，不在 `ChatSession` 里另加锁。

序号加一必须赶在签发令牌之前：从那一刻起会话进入新一次尝试，此后即便令牌签发失败、这次尝试当场以失败告终，它也确实是一次独立的尝试，理应留下自己那条记录。反过来，重试因"接收端已离线"被拒时序号<u>不</u>加 —— 那次重试根本没开始，它命中的是上一次失败那条记录的幂等键，不会多留一条。

## 6. 服务端设计

### 6.1 chatserver

新增两个文件，均为纯逻辑、不查库、可单测：

- `chatserversrc/FolderTransferManager.{h,cpp}` —— 内存会话表（`sessionid → 会话信息`）、状态流转、超时清理、令牌签发、10 分钟重试窗口的过期判定，以及尝试序号的维护（`beginRetryAttempt`）。仿 `RemoteDesktopManager`。
- `chatserversrc/FolderTransferProtocol.{h,cpp}` —— 8 个信令的请求解析与应答构造。仿 `RemoteDesktopProtocol`。

`ChatSession` 增加 8 个 cmd 的分发与处理函数；`Protocol.h` 增加 cmd 枚举、状态枚举、错误码，以及记录条的内容类型 `message_type_folder = 18`；`RelayToken.h` 增加两个角色常量。

规模上限在 `cmd_folder_invite` 处校验：文件数超过 `foldermaxfiles`、总大小超过 `foldermaxsize` 一律拒绝，应答里带回上限值。

**终态收口。** 「向相关方推一帧 `cmd_folder_state_notify`」与「在双方会话里留一条记录条」这两件事绑在 `ChatSession::finishFolderTransferSession` 一个函数里，六条终态分支（1812 拒绝、1813 撤回、1814 结束、1817 重试时对端已离线、连接断开时的收尾、主循环定时器判定的邀请超时）一律经由它，不得自己另写一份推送。理由是日后新增一条终态分支时极容易漏掉留记录，而漏掉的表现只是"聊天记录里少了一条"，不报错、不崩溃，几乎测不出来。

该函数一进来就调 `FolderTransferManager::finishAttempt` 这道**原子终结闸门**（见 5.5 的"幂等"），拿到 `true` 才继续推送与留记录，返回值原样回给调用方（`main.cpp` 的超时清理路径据它决定要不要记那条超时日志）。这也意味着**调用方不必、也不应在闸门之外自己置终态**：`onFolderClose` 的失败分支原先在调用之前先 `setState(folder_state_failed)`，现已删去，那一步并进了闸门内部。

该函数写成**静态方法**，是因为主循环那条邀请超时清理路径（`main.cpp` 的 `ReapFolderTransferSessionsTick`）没有 `ChatSession` 可用 —— 超时的判定与任何一条客户端连接都无关，发起邀请的那一端完全可能早已断开。函数体内只用到 `ChatServer`（推送）与 `MessageManager`（落库）两个单例，不依赖任何会话状态。记录条 `content` 的构造与解析（`buildRecordContent` / `parseRecordContent`）以及幂等键的拼法（`buildRecordClientMsgId`）放在纯逻辑的 `FolderTransferProtocol` 里，可单测；尝试序号由 `FolderTransferManager` 随会话一起维护，`ChatSession` 只从会话快照里取用，不自己计数。

### 6.2 fileserver

- `FileSession` 的 `transfer_mode` 增加 `mode_folder_relay`，`processFrame` 增加两个 case。
- 中转逻辑抽成 `fileserversrc/FolderRelayEndpoint.{h,cpp}`（持有配对表指针、sessionid、lane、role，负责登记、找对端、转发），`FileSession` 里只有几行转调，避免它膨胀成两套业务。

- **模式互斥必须显式判**：中转模式的连接不再接受 `cmd_file_upload` / `cmd_file_download`，已进入上传 / 下载模式的连接也不接受中转握手。否则可以拿一条中转连接去调文件接口，绕过上传下载令牌里的场景校验。

### 6.3 新增配置项

`etc/chatserver.conf`：

| 配置项 | 含义 | 建议默认值 |
| --- | --- | --- |
| `foldermaxfiles` | 单次文件夹传输的文件数上限 | 10000 |
| `foldermaxsize` | 单次文件夹传输的总字节数上限 | 53687091200（50 GiB） |
| `folderlanes` | 数据通道条数（不含控制通道），硬上限 8，越界按 8 截断 | 4 |
| `foldermaxsessions` | 整台服务器同时进行的文件夹传输会话数上限，超出时拒绝新会话（错误码 619） | Windows 24 / Linux 128 |
| `foldermaxperuser` | 每个用户同时可参与的传输笔数，发送与接收各算一笔；失败待重试的会话在保留期内仍占名额。任一方满额时拒绝新邀请（错误码 620） | 5 |
| `folderinvitetimeout` | 邀请无应答的超时毫秒数（1800000 = 30 分钟） | 1800000 |
| `folderretrywindow` | 失败会话的保留毫秒数（期内可重试续传） | 600000 |

两道并发闸门是相互独立的，估算 `foldermaxsessions` 时要按 `foldermaxperuser` 算：一笔传输在服务端占用 `2 × (folderlanes + 1)` 条连接，默认配置下每笔 10 条，单个用户满额（5 笔）即 50 条。两道闸门同时到顶时，`cmd_folder_invite` 先报每用户上限的 620 而不是服务器繁忙的 619 —— 前者对用户更有指导性（等自己那几笔里有一笔传完即可），后者只能干等。

`etc/fileserver.conf`：新增 `relaytokenkey`，须与 chatserver 的同名配置一致（不新增端口，但中转令牌要用这把密钥验签）。

## 7. 客户端设计

### 7.1 模块划分

新增目录 `flamingoclient/Source/FolderTransfer/`：

| 文件 | 职责 |
| --- | --- |
| `FolderManifest.{h,cpp}` | 扫描本地目录树生成清单，相对路径规范化与合法性校验，统计目录数 / 文件数 / 总字节数 |
| `FolderRelayFraming.{h,cpp}` | 5.3 那套应用帧的编解码（纯函数，可单测），仿 `RdRelayFraming` |
| `FolderRelayClient.{h,cpp}` | 一条到 fileserver 的中转连接：连接、加密握手、hello 报到、收发线程 |
| `FolderSendSession.{h,cpp}` | 发送端状态机：扫描 → 邀请 → 等同意 → 建 N+1 条通道 → 发清单 → 等目录就绪 → 多通道并行传 → 收尾 |
| `FolderRecvSession.{h,cpp}` | 接收端状态机：选保存位置 → 建目录树 → 回执 → 收片写盘 → 校验 → 收尾 |
| `FolderTransferManager.{h,cpp}` | 单例，按会话 id 管理**多笔**并存的文件夹传输，管理会话生命周期与向 UI 回投消息 |

信令的 JSON 编解码放 `Source/net/FolderProtocolClient.{h,cpp}`，仿 `net/RemoteDesktopProtocolClient`。

`FolderTransferManager` 内部分成两层，界线与本目录其余模块一致：

- **会话表 `FolderSessionRegistry`（纯逻辑，可单测）** —— 一笔传输一条 `FolderSessionRecord`，各自持有角色、会话 id、对端 userid、清单 / 接收进度、待应答邀请与失败时刻。名额闸门（占名额的记录数是否已达上限）、失败记录的保留期判定、待应答邀请的取出、按会话 id 与本地占位 id 的路由都收在这一层，不碰网络、磁盘与窗口。用例见 `Source/Tests/FolderTransferManagerTests.cpp`（Suite FTM）。
- **管理器本体** —— 互斥量、扫描线程、状态机与回调适配器的生命周期、信令收发。记录里的运行期对象一律「锁内摘下、锁外停掉」，且状态机先于回调适配器销毁。

并发笔数上限来自客户端配置项 `foldermaxconcurrent`（`Bin/config/flamingo.ini` 的 `[app]` 段，默认 5、合法区间 1~16），登录成功后由 `CMainDlg` 调 `FolderTransferManager::LoadConfig()` 读入；缺失或取值非法时回落默认值 5 并记一条日志。**客户端这道闸门只为即时提示**，服务端的 `foldermaxperuser` 才是权威判定，故客户端不得用它去推断服务端会不会放行。

一笔失败之后，**名额立刻放开**（用户可以马上另发一笔），而这条记录的清单 / 会话 id / 接收进度照旧留满 10 分钟保留期供重试续传 —— 这两件事在客户端是分开的。服务端的 `foldermaxperuser` 口径不同（失败待重试的会话在保留期内仍占名额），差异只会导致"客户端放行、服务端回 620"，界面按服务端的错误码提示即可。

发送侧的 1810 应答**包体**里没有任何可对回发起方的字段（既无本地占位 id 也无对端 userid），多笔并发时靠 **v2 帧头的 `seq`** 配对：`CIUSocket::SendFolderInvite` 返回本次请求所用的帧 seq，管理器把「seq → 本地占位 id」记进会话表，`CIUSocket::HandleV2Frame` 的 1810 分支把 seq 作为 `FMG_MSG_V2_FOLDER_INVITE_ACK` 的 `wParam` 投上来，`CMainDlg` 透传给 `FolderTransferManager::OnInviteAck`，按 seq 精确命中；命中不了就记一条英文告警并忽略，绝不猜。这与 `net/FileTransfer` 的上传 / 下载信令按 seq 找等待槽是同一套做法（`CIUSocket::RequestUpload` / `RequestDownload`）。

之所以不按「先发先答」的顺序配对：那要依赖"同一条连接上应答顺序等于请求顺序"这个前提，它现在成立（`ChatSession::onFolderInvite` 全程无异步数据库操作、就地回包，`flamingoserver/chatserversrc/ChatSession.cpp:3271`），但哪天有人在这个处理函数里加一次异步查库，前提就悄悄不成立了，而症状是"会话 id 绑到了别人的气泡上"，极难查。

「发出邀请」与「按 seq 登记」在同一个临界区内完成，否则应答可能早于登记到达、被当成对不上而忽略。用户在应答到达前取消了某一笔时，记录删掉而登记项保留，应答按 seq 命中登记项、却查不到记录，客户端据此替它发一条 `cmd_folder_cancel` 把服务端刚建好的会话撤掉。

  - **「接收」不弹选目录框**，直接落到本机默认的接收目录 `<数据根目录>Users\<登录账号>\ChatFolder\<文件夹名>`。这条路径与聊天文件缓存的 `ChatFile\`、图片缓存的 `ChatImage\` 同级，由 `net::UserCacheDir`（`Source/net/UserCachePath.h`）统一拼出，账号取自 `net::CurrentUserAccount()`；`Users`、`Users\<账号>`、`ChatFolder` 三级由聊天窗在应答之前逐级创建（`CreateDirectoryW` 只建最后一级，故要逐级调用），建不出来时弹框告知并提示改用「另存为」，不静默失败。根目录重名仍由接收端状态机自动改名（`xxx(2)` / `xxx(3)`……，见 `FolderRecvSession::PrepareRootDirectory`），界面这一层不处理重名。
  - **「另存为」才弹选目录框**，由用户挑落地位置；选定之后的流程与「接收」完全一致，两者在 `CBalloonChatWindow::AcceptFolderInvite` 汇合，差别只有"父目录从哪来"这一步。
  - 三个按钮排在**同一行**内，按各自文字宽度从左往右顺排，故气泡高度只与"有没有按钮"有关、与按钮个数无关（见 `ChatBubble.cpp` 的 `FolderBubbleHeight`）。按钮数上限常量 `kMaxChatFolderActions` 为 3，它同时是气泡里几个按钮数组的长度，与逐状态实测出的最大值由单元测试 CFOLD15 钉死。
- **本地气泡**：传输**进行中**的这些气泡（邀请、进度、接收 / 另存为 / 拒绝按钮）不发 `cmd_send_message`、不进服务端消息表，退出登录后不再出现。传输走到终态后，服务端会另推一条 `msgtype=18` 的记录条（见 5.5），它才是留在聊天记录里的那一条；两者是"进行中的临时气泡"与"事后的历史记录"的关系，不冲突。历史记录里仍不提供重新下载。
- 窗口消息按既有惯例新增 `FMG_MSG_V2_FOLDER_*` 系列，注意主窗、代理窗、聊天窗各层都要接上。

### 7.3 线程模型

每条通道一个收发线程，与群文件并发池的做法一致；UI 线程只负责发起与显示，全部结果经窗口消息回投。发送端的文件读取、接收端的写盘与增量 MD5 都在各自通道线程上完成，不同文件不同句柄，彼此不加锁。

### 7.4 传输记录条（`msgtype=18`）的客户端接入

5.5 那条服务端生成的记录条，在客户端要落到三个地方：聊天窗的气泡、消息记录窗的一行、会话列表的一行摘要。落地方式如下（2026-08-14 实现）。

**协议镜像与解析。** `Source/net/Protocol.h` 的 `enum message_type` 增加 `message_type_folder = 18`，与服务端逐值一致。`content` 的构造与解析放在 `Source/net/FolderProtocolClient`（与服务端 `FolderTransferProtocol` 的 `buildRecordContent` / `parseRecordContent` 互为镜像，不放 `MessageProtocolClient` —— 那边只负责消息报文的外层，字段口径归文件夹这一摊自己管）：

| 名字 | 说明 |
| --- | --- |
| `struct net::FolderRecordContent` | 七个字段：`m_sessionId` / `m_folderName` / `m_totalDirs` / `m_totalFiles` / `m_totalSize` / `m_result` / `m_errCode` |
| `static std::string FolderProtocolClient::buildRecordContent(const FolderRecordContent&)` | 客户端不发这条消息，构造侧存在的理由是"落进本地历史库"与"让构造—解析能在单测里往返比对" |
| `static bool FolderProtocolClient::parseRecordContent(const std::string&, FolderRecordContent&)` | 会话 id 非空、结局须为终态、三项统计须为非负 JSON 整数，否则返回 false |
| `static bool FolderProtocolClient::isTerminalState(int)` | 3~8 为终态，响铃中与传输中不是 |

「`errcode` 仅失败态有意义」这条不变式在构造与解析两侧各归一一次：结局不是 `folder_state_failed` 时一律把它抹成 0。`MessageProtocolClient::parseMessageNotify` 对 `msgtype=18` 转调 `parseRecordContent`，结果填进 `MessageNotify` 新增的 `m_folderXxx` 系列字段。

**气泡就地接管。** 传输进行中，聊天窗里已经有一条本地文件夹气泡（带进度与按钮）。记录条到达时（实时推送或翻历史）走 `CBalloonChatWindow::OnFolderRecord`：按 `sessionid` 找到那条**尚未被任何记录接管过**的本地气泡，就地填上 `msgid` 与服务端时间戳、按 `result` 切到对应终态；找不到就正常追加一条新的记录气泡。

命中判据收在 `ChatMessageList.cpp` 的 `IsLiveFolderBubble` 一处：`FolderSessionId() == sessionId && Msgid() == 0`。`GetFolderMessage` / `SetFolderMessage` 都按它定位，因而**已经带着 msgid 的气泡不会再被接管**。之所以要加 `msgid` 这一半：一次传输可能留下多条记录（见下），不加的话第二条记录会把第一条那个已经定格的气泡再改一遍。

**一次传输可能留下多条记录，这是预期行为。** 服务端的幂等键是「会话 id + 尝试序号」，每次尝试各落一条：先失败落一条 `result=7`，10 分钟保留期内重试成功再落一条 `result=8`。于是用户点「重试」时，客户端先经 `ChatMessageList::ReviveFolderMessage` 把那条气泡身上的 `msgid` 清掉、放回"活的本地气泡"状态，本次尝试结束时到达的新记录才接管得了它。结果是：**实时看到的是一条随状态变化的气泡；重开窗口从历史加载时，会看到这一笔的每次尝试各一条记录**。这不是重复消息，不要去"修"。

结局到气泡状态的映射抽成纯函数 `balloonchatwnd::FolderStateFromRecord(result, errCode)`（`ChatFolderStateModel`）：3~6 与 8 是恒等映射，失败态再按错误码分成「已取消」`kFolderUserCanceled`、「已过保留期」`kFolderExpired`、「传输失败」`kFolderFailed` 三档 —— 与实时路径的 `ApplyFolderFailure` 判的是同一件事，抽出来由两处共用，免得同一次传输"实时看到的"与"翻历史看到的"说法不一样。

**本地路径存在哪。** 记录条**不含任何路径**（服务端也不记），故「打开文件夹」要靠本机自己记一份：新增 `Source/BalloonHistory/FolderLocalStore.{h,cpp}`（单例 `CFolderLocalStore`，仿同目录的 `FileLocalStore`），库文件 `<个人目录>\ChatLog\folderlocal.db`、按账号隔离，由 `CBalloonMainPanel::EnsureMsgStoreOpen` 与另两个库一起打开。表 `t_folder_local(sessionid TEXT PRIMARY KEY, localroot TEXT, updatetime INTEGER)`，**键是会话 id 而不是 msgid** —— 会话 id 在传输一开始就有，而 msgid 要等传输走到终态才存在；同一会话的多条记录本地根目录也是同一个。写入两处：`OnFolderBound` 拿到真会话 id 时记发送端的源目录，`OnFolderResult` 记两端的最终根目录（接收端含重名自动改名之后的名字）。

**换一台机器只显示记录、不给「打开文件夹」**，这是预期行为：那台机器上从来没有过这个目录。

**历史消息窗口。** 记录条进本地消息库走既有的"收到消息就 upsert"链路，`V2MsgStore` 的建表与 upsert SQL 一行没动。改的是展示这几处：

- `V2MsgQuery.cpp`：`BuildSearchText` 对 `msgtype=18` 返回文件夹名（用户回头找的就是"那个叫 xxx 的文件夹"）；`BuildContentJson` 把七个字段原样写进 `content.folder` 子对象，字段名转调 `buildRecordContent`，不另抄一份。
- `HistoryView.{h,cpp}`：`PreviewFromContent` 给出 `[文件夹] 名字`；`ParseContentBrief` 多取四项（`m_folderSessionId` / `m_folderName` / `m_folderTotalFiles` / `m_folderTotalSize` / `m_folderResult`）；新增纯函数 `FolderResultText`（六种终态的中文文案）与 `BuildFolderRowText`（拼成 `[文件夹] 项目资料 · 128 个文件 · 2.4 GB · 已完成`）。
- `HistoryRowMenu.{h,cpp}`：新增 `IsHistoryRowFolderType` 与菜单项 `kHistoryRowMenuOpenFolderRoot`（「打开文件夹」）。它与文件行的「打开所在文件夹」不是一回事，故另开一个 id：前者打开目录本身，后者打开父目录并选中文件。**不给「下载」「另存为」** —— 服务端没存内容，那些项点下去必然无效。
- `BalloonHistoryWindow.cpp`：行文字用 `BuildFolderRowText`；`ResolveRowLocalFile` 增加文件夹分支（按会话 id 查 `CFolderLocalStore`，再用新增的 `DirectoryExistsOnDisk` 确认目录还在）；菜单命令分发增加打开目录那一支。

**类型筛选胶囊没有新增「文件夹」一档**，理由有三：胶囊行是单选、且现有七枚一律按"两字"等宽排（`kChipW = 56`），加一枚三字胶囊要动整行布局；记录条一次传输才一条、频次极低；它已经能经「全部」浏览、并按文件夹名被关键字搜到。因此 `TypeFilterToSqlFragment` 一行未改，单测 V2Q17 顺带守住"别有人把 18 顺手塞进「文件」那一档"（那会让文件筛选里冒出一堆下载不了的行）。

**会话列表摘要。** 复用邀请阶段那份 `balloonmain::BuildFolderInviteDigest`，显示为 `[文件夹] xxx`，与文件消息的 `[文件]` 同体例；`digestForMsgType` 另加一档 `message_type_folder → "[文件夹]"` 作为拿不到文件夹名时的类型占位。邀请阶段 `BumpConversation` 的消息类型也从 `message_type_file` 改成 `message_type_folder`，免得同一次传输在会话列表上先是文件、后变成文件夹。

**顺带修掉的一处路由缺陷。** 记录条由服务端生成、**向双方各推一帧**，发送方那一帧的 `from` 就是他自己。而 `CBalloonMainPanel::OnRecvChatMessage` 的单聊分支一直用 `from` 当会话对端，那一帧因而会被归进"自己和自己"的会话里，聊天窗与会话列表都找不到它。现在改成：`from` 等于本端 userid 且 `cid` 有效时取 `cid`（协议约定 `cid` 恒为收件方视角下的对端 userid），落库与窗口路由共用同一个值。

**用例。** `FolderProtocolClientTests.cpp` FPC19~FPC26（六种终态往返、`errcode` 归一、字段缺失 / 类型不对 / 越界安全失败、50 GiB 与 int64 上限不丢精度、字段名与服务端逐字对应）；`FolderLocalStoreTests.cpp` Suite FLR1~FLR7（登记 / 覆盖 / 未命中 / 多会话互不覆盖 / 参数非法 / 删除幂等 / 库未打开）；`V2MsgQueryTests.cpp` V2Q12~V2Q17；`HistoryViewTests.cpp` V2V-FOLDER1~7；`ChatFolderStateModelTests.cpp` CFOLD16~CFOLD19；`HistoryRowMenuTests.cpp` HRM13~HRM15；`MessageProtocolTests.cpp` MP-FOLDER1~5。

## 8. 关键流程

### 8.1 正常传输

1. 发送方选中目录，客户端扫描生成清单（目录数 / 文件数 / 总字节数）。
2. 发 `cmd_folder_invite`；服务端校验规模上限、对方在线、双方各自的并发笔数均未达 `foldermaxperuser`，建会话并推 `cmd_folder_invite_notify`。
3. 接收方在气泡上作出应答，两条路都发 `cmd_folder_response(accept=1)`，区别只在落地位置从哪来：点「接收」直接用本机默认的接收目录 `<数据根目录>Users\<登录账号>\ChatFolder\`（不存在则逐级创建，创建失败时提示改用「另存为」）；点「另存为」则先弹出"选择保存位置"，由用户挑一个目录。
4. 服务端给双方各签一枚令牌，下发 `cmd_folder_relay_info`（含 `lanes`）。
5. 双方各建 1 条控制通道 + N 条数据通道，用同一枚令牌、各报自己的 lane。
6. 发送端在控制通道发 `ft_manifest`。
7. **接收端先建目录**：在选定位置建根目录（重名自动改名），再按目录清单逐级建完全部子目录（含空目录），全部成功后回 `ft_manifest_ack` 并带上每个文件的续传起点。
8. 发送端这才开始传字节：各数据通道各取一个文件，边读边发，接收端边收边写 `.part` 并增量算 MD5。
9. 每个文件传完，接收端校验大小与 MD5，通过则去掉 `.part` 后缀，回 `ft_file_result`。
10. 全部文件完成后发送端发 `ft_complete`，双方发 `cmd_folder_close(result=成功)`，气泡转完成态。

先建目录再传文件，把"没有写权限、路径过长、磁盘只读、空间不足"这类环境问题挡在传字节之前，出问题时一个字节都还没浪费。

### 8.2 失败

任一端在任一步出错：立即停止本端全部通道 → 在控制通道发 `ft_abort(errcode, errmsg)` → 发 `cmd_folder_close(result=失败, errcode, errmsg)`。服务端把会话置失败态、保留 10 分钟，并向对端推 `cmd_folder_state_notify`（控制通道已断时的兜底）。双方气泡显示同一条失败原因。已落盘的部分保留在接收端，供重试续传。

**不做自动重连**：网络抖动导致通道断开，同样按失败处理并如实告知双方，由用户决定是否重试。

### 8.3 重试与续传

用户在失败气泡上点「重试」→ 发 `cmd_folder_retry(sessionid)` → 服务端校验会话未过期（10 分钟内）且双方仍在线 → 重签令牌、再下发一次 `cmd_folder_relay_info` → 双方重建通道 → 接收端**复用上次那个目录**，在 `ft_manifest_ack` 里回带各文件的续传位点（已完成的文件跳过，传了一半的从 `.part` 长度接着传）→ 断点续传。全程不再打扰接收方，接收方看到气泡从失败变回传输中，随时可以点取消。

超过 10 分钟：服务端销毁会话，接收端清除内存里的续传状态，发送端的「重试」按钮置灰并提示"已超时，请重新发送"。此时只能重新发起一次完整传输，重新征求同意、从零开始。任一方退出登录同样立即作废。

### 8.4 取消

- 发送方在对方应答前取消：`cmd_folder_cancel`。
- 任一方在传输中取消：等同于一次失败，错误码为"用户取消"，双方气泡显示已取消。

## 9. 边界与安全

- **路径校验**：清单里的相对路径必须拒绝 `..`、绝对路径、盘符前缀、非法字符与 Windows 保留名（`CON` / `PRN` 等）。否则对端可以借相对路径把文件写到接收方选定目录之外。校验在接收端建目录前做，发送端生成清单时也做一遍。
- **长路径**：接收端拼出的完整路径可能超过 260，用 `\\?\` 前缀处理；仍处理不了的判失败并明确报"路径过长"。
- **重名**：根目录重名自动改名 `xxx(2)`、`xxx(3)`；重试时复用会话里记下的目录路径，不再改名新建。
- **规模上限**：服务端权威校验，客户端按应答里带回的上限值提示，不硬编码。
- **并发**：每个用户同时最多参与 `foldermaxperuser` 笔文件夹传输（默认 5 笔，发、收各算一笔，失败待重试的会话在保留期内仍占名额）；名额已满时再发起，提示"同时进行的文件夹传输已达上限（最多 N 笔），请等其中一笔结束后再试"。服务端权威校验（`FolderTransferManager::checkInvite` 对发送方与接收方各判一次），整台服务器的会话总数另有 `foldermaxsessions` 一道闸门，两道同时到顶时先报每用户上限。
- **客户端的本地闸门**：客户端另有一道同口径的判定，阈值取自配置项 `foldermaxconcurrent`（`flamingoclient/Bin/config/flamingo.ini` 的 `[app]` 段，默认 5、合法区间 1~16，缺失或非法时回落 5）。它的作用只有一个 —— 在用户点「发送文件夹」、或收到别人的邀请时就地给出提示，免得白选一次目录、或让对方干等到邀请超时；名额满时收到的邀请直接回一个拒绝，不挂在那里。**它不是权威判定**：客户端的笔数与服务端的 `foldermaxperuser` 各配各的，两者不一致时以服务端应答为准（错误码 620），故客户端不得据本地闸门推断服务端会不会放行，规模上限那类阈值更是一律用服务端回带的数值提示、不硬编码。
- **失败之后名额立刻放开（客户端）**：客户端一笔失败即释放名额，而清单 / 会话 id / 接收进度照旧留满 10 分钟保留期供重试；服务端口径不同（保留期内仍占名额）。差异只会表现为"客户端放行、服务端回 620"，界面按服务端错误码提示即可。
- **掉线收尾要逐笔处理**：一个用户可能同时参与多笔传输，故连接断开 / 退出登录时必须查出他参与的**全部**会话并逐笔收尾（`FolderTransferManager::findSessionsByUser` + `ChatSession::cleanupFolderTransferOnOffline`）。只处理其中一笔的话，其余几笔的对端会一直干等到邀请超时（默认 30 分钟）才知道这一方已经离线。
- **模式互斥**：见 6.2。
- **令牌**：一枚令牌开多条连接是安全的（令牌里已绑定 sessionid / uid / peeruid），但必须限制 lane 上限，防止拿一枚令牌开出几百条连接。

## 10. 附带修复：`FileServer::onDisconnected` 删错会话

`FileServer::onDisconnected`（`flamingoserver/fileserversrc/FileServer.cpp:56-72`）在连接断开时遍历会话表，但循环体里没有把 `conn` 与会话持有的连接做比对，而是直接删掉列表里的**第一个**会话。也就是说任何一条连接断开，被移除的都是最早建立的那条会话。

对照可知这是抄漏：`ChatServer::onDisconnected`（`chatserversrc/ChatServer.cpp:98`）与 `RelayServer::onDisconnected`（`imgserversrc/RelayServer.cpp:66`）都先用 `getConnectionPtr() == conn` 匹配再删；`FileServer.cpp` 把判空那半段原样抄了过去，真正做匹配的那半段没抄。

影响面：`FileServer` 是 fileserver 与 imgserver 共用的（`imgserversrc/main.cpp:14`、`:144`），故两个服务各有一份这个缺陷；修一次两边同时受益。现在不易察觉是因为文件连接多为"连上、传完、断开"的短连接，删错往往正好赶上别的连接也快结束；而多通道文件夹传输一次就有 5 条以上连接同时挂着，任一条断开都可能误删仍在传输的会话对象。

修法：补上按连接指针匹配那一句，与另外两处保持一致，并补一个能复现删错的用例。

4. fileserver：`FolderRelayHub` + `FolderRelayEndpoint` + `FileSession` 接入 + 模式互斥 + 单测。
5. 客户端纯逻辑层：`FolderManifest`（含路径安全）+ `FolderRelayFraming` + 单测。
6. 客户端通道层：`FolderRelayClient`，跑通多条通道的建立、握手与空帧对发。
7. 接收端状态机：建目录 → 回执 → 收片写盘 → 校验。
8. 发送端状态机：扫描 → 邀请 → 等同意 → 多通道并行传 → 收尾。
9. 界面：工具栏入口与图标、文件夹气泡、进度、失败原因、重试与过期置灰。
10. 重试与续传打通，两账号真机联调与验收。

## 12. 测试用例

### 12.1 客户端纯逻辑（FlamingoUnit / Catch2）

- 清单生成：空目录纳入、深层嵌套、超长路径、中文与特殊字符文件名、统计值（目录数 / 文件数 / 总字节数）正确。
- 路径安全：`..`、绝对路径、盘符前缀、保留名、非法字符一律拒绝。
- 应用帧编解码：各帧类型往返一致；超出中转上限的包体被拒绝；截断 / 畸形包体不崩溃。
- 续传位点计算：已完成文件跳过、半成品从 `.part` 长度续、全新文件从 0 开始。
- 发送端与接收端状态机的迁移表：正常路径、失败路径、取消路径、过期路径。
- 会话表与并发闸门（Suite FTM，`Source/Tests/FolderTransferManagerTests.cpp`）：配置项缺失 / 非数字 / 负数 / 超硬上限时回落默认的 5 笔；未满不拦、满了才拦；任一笔结束后名额立刻释放；失败后名额立刻释放而重试记录与清单仍在；保留期边界（差 1 毫秒可重试、正好到期不可）；超期记录被清理而未超期的不动；同一对端的多条待应答邀请全部按序取出、已应答与已作废的不再取出；按会话 id 与本地占位 id 两种方式路由；1810 应答按帧 seq 配对（乱序到达仍各归各笔、同一条应答重复到达不会二次命中、被取消的那一笔的应答不误伤别人、陌生 seq 一律不命中）。

### 12.2 服务端（现有 tests/）

- 会话建、查、删与超时清理；10 分钟重试窗口的边界（第 9 分 59 秒可重试、第 10 分 01 秒不可）。
- 非参与方拿别人 sessionid 发 `cmd_folder_retry` 被拒。
- 令牌签发：两端角色相反、uid 与 peeruid 对调、过期判定。
- 配对表：`(sessionid, lane)` 正确配对；同一 `(sessionid, lane, role)` 重复报到被拒；lane 越界被拒；任一 lane 断开连带关闭本会话全部 lane。
- 文件传输模式与中转模式互斥。
- 规模上限校验：文件数超限、总大小超限分别返回对应错误码与上限值。
- `FileServer::onDisconnected` 在多连接下删对会话。
- 传输记录条（Suite FTP，`tests/test_foldertransferprotocol.cpp` 的 FTP21~FTP28、FTP26B）：`content` 的构造与解析往返一致、七个字段齐全且不含文件清单；六种终态各自的取值都能往返；"`errcode` 仅失败态非零"这条不变式在构造时被归一、在解析时被校验；幂等键 `"folder-" + sessionid + "-" + 尝试序号` 的拼法，同一会话同一序号恒相同、不同序号必不同；`isTerminalState` 认 3~8 而拒绝响铃中与传输中；大整数（50 GiB、int64 上限）与中文目录名不丢失。
- 尝试序号（Suite FTM，`tests/test_foldertransfermanager.cpp` 的 FTM18）：新建会话的序号是 1；`setState` 这类非重试路径不改它；每调一次 `beginRetryAttempt` 加一并把会话置回传输中、刷新状态时间而不动创建时间；反查路径拿到的序号与直接查会话一致；会话不存在时不受理且出参置 0；会话销毁后重建又从 1 起算。
- 原子终结判定（Suite FTM，FTM19~FTM22）：8 条线程在自旋栅栏上等齐后同时对同一个会话的同一次尝试调 `finishAttempt`，连做 200 轮，每一轮都必须恰好只有一个拿到 `true`（这一条就是"聊天记录里出现两条重复记录"的复现用例，改动前 200 轮里有几十轮会出现多个终结者、单轮最多 7 个）；顺序调用时第一次 `true`、其后一律 `false`，且被去重的调用不改会话状态；终结 → 重试（序号加一）→ 再终结时第二次仍拿到 `true`，而上一次尝试那条迟到的终结判定被挡下；会话不存在（邀请超时那条路径上会话已被 `tick` 移出会话表）时照常受理、重复的仍被挡下；传入过程态一律不受理且不占名额；登记项在会话销毁后再保留 `kFinishedAttemptRetentionMs` 才由 `tick` 回收，会话仍在表里的登记项不受该保留期约束。

### 12.3 两账号真机联调验收

- 正常传一个多层目录（含空目录、中文名、超长名、单个大文件、上万个小文件）。
- 传输中拔网线：双方是否在合理时间内都显示同一条失败原因。
- 期内点重试：是否续传而非重传，接收方是否未被再次询问。
- 超过 10 分钟：重试按钮是否置灰并给出正确提示。
- 接收端磁盘写满、目标目录只读、目标位置已有同名文件夹。
- 接收方中途取消、发送方中途取消、对方退出登录。
- 超出文件数与总大小上限时的提示文案是否用的是服务端下发的数值。
- 同时跑满 5 笔（发、收混合）之后再发起，是否被本地闸门拦下并提示"已达上限（最多 5 笔）"；把客户端的 `foldermaxconcurrent` 配得比服务端的 `foldermaxperuser` 大时，多出来的那一笔是否如实显示服务端回的 620。
- 同一个人先后发来两个文件夹、两个人同时发来邀请：会话窗里是否两条邀请气泡都在，接收、拒绝、进度是否各归各条互不串。
- 传输记录条：六种终态各走一遍（拒绝、应答前撤回、响铃中对方退出登录、邀请超时、传输中失败、传完），双方的聊天记录里是否**各留下一条且只有一条**，正文里的文件夹名与规模统计是否与实际相符；重新登录后翻历史这条记录是否还在；接收方的会话列表摘要与未读是否照常更新。
- 传输记录条的幂等：正常传完时双方各发一帧 `cmd_folder_close`，聊天记录里是否只多出一条而不是两条。
- 传输记录条的尝试粒度：传输中断一次、在 10 分钟保留期内点「重试」并让它传完，双方聊天记录里是否依次留下"传输失败"与"传输完成"两条；连续失败重试多次时是否每次各留一条、条数与实际尝试次数相符。
- 重试因接收方已退出登录而被拒时，聊天记录里是否**不会**多出一条（那次重试没有真正开始）。

## 13. 未定与后续

- **单个大文件切段并行**：一期不做。若实测"尾巴上只剩一个大文件"拖慢明显，二期再把大文件按字节区间切段分给空闲通道，届时续传位点要从"每个文件一个"改成"每段各一个"，接收端还要处理同一文件多句柄按偏移写。
- **小文件打包**：大量小文件时可把小于 64 KiB 的文件在同一通道上打包成一帧连续发送，减少往返。跑通后按实测决定是否加。
- **群聊发送文件夹**：本期只做单聊。群聊要面对"多个接收方各自同意、各自进度"，是另一套设计，暂不展开。
- **重试成功后合并那几条记录**：现在每次尝试各留一条，一笔反复重试的传输会在聊天记录里留下一串"传输失败 / 传输失败 / 传输完成"。这是需求方 2026-08-14 选定的口径（过程完整可见），暂不改。若日后觉得重试多次时这一串太吵，可再评估"折叠成一条并显示尝试次数"的展示方案 —— 那是客户端渲染层的事，不必动协议：记录条里已有 `sessionid`，同一 `sessionid` 的多条本就可以在界面上归成一组。
