# PC 客户端图片文字识别方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-05
> 用途：记录 PC 客户端（`flamingoclient/`）「识别图片中的文字」功能的需求结论、现状盘点、第 0 期实测数据、总体设计、接口约定、测试用例与分期开发步骤。后续每步开工前据此细化、收尾后回填实际结果。

## 1. 背景与目标

用户在聊天里收到的截图、照片里常有需要摘抄的文字（错误信息、会议通知、表格里的数字）。本方案让客户端把图片里的文字识别出来，用户可以在结果窗口里修改、复制。识别全部在本机完成，图片不上传，服务端与协议都不改。

识别引擎以独立工程 `flamingoclient/FlamingoOcr/` 交付，产物为 `FlamingoOcr.dll`。三条设计目标：

1. **不引入重的第三方库。** 第一个引擎用 Windows 10 起自带的 `Windows.Media.Ocr`，体积为零。
2. **引擎可以替换。** exe 与 DLL 之间只有一张 C 函数表，任何实现了同一接口的同名 DLL 放进安装目录即可替换，exe 不用改；以后效果不够时可换成 PaddleOCR 之类的引擎。
3. **DLL 不存在或加载失败时，主程序照常运行**，只是识别入口不出现。

不在本方案范围内：手写体与竖排文字、服务端识别、Android 客户端、flamingoAdmin、识别结果的翻译。

### 1.1 术语

| 用语 | 含义 |
| --- | --- |
| 引擎 | 实际做识别的组件。第一个引擎是 `Windows.Media.Ocr`，封装在 `FlamingoOcr.dll` 里 |
| 识别语言 | 引擎按哪种语言识别，用 BCP-47 代码表示，如 `zh-Hans-CN`。Windows 引擎的识别语言随系统语言组件安装 |
| 行、词 | 识别结果的两级结构。每一级都带文字与矩形，矩形用输入图片的像素坐标 |
| 预加载 | 程序启动阶段（`CAppShell::Startup`）在后台线程加载 DLL、初始化并查询可用性，结果缓存到进程退出 |
| 可用性 | DLL 加载成功后，引擎报告的「能不能识别」：可用、系统不支持、没有识别语言、引擎初始化失败 |
| 拼行整理 | 按词框之间的间距重新拼出一行文字，去掉引擎在汉字之间插入的空格（第 4.3 节） |

## 3. 现状盘点（据实证）

### 3.1 客户端最低支持 Windows 7

`Source/stdafx.h:14-15` 定义 `WINVER` 与 `_WIN32_WINNT` 为 `0x0601`；`FlamingoMedia`、`FlamingoFileShare`、`FlamingoP2P` 的 `stdafx.h` 同样如此。`Windows.Media.Ocr` 是 Windows 10 起才有的 WinRT 接口，所以 `FlamingoOcr.dll` 不得静态导入任何 WinRT 函数，否则在 Win7 上连 DLL 都加载不了。

### 3.2 WinRT 运行时取用的现成写法

`FlamingoMedia/Share/WgcWindowCapturer.cpp` 已经在用同样的办法调 `Windows.Graphics.Capture`：

- 文件头（1~15 行）说明：只用 C++11 语法，经 WRL 的 `ComPtr` 调 ABI 接口；本翻译单元不包含 `stdafx.h`，自己把系统版本宏定到 Win10，只为让 WinRT 头文件声明出所需类型；
- `struct WinRtApi`（63 行起）在运行时从 `combase.dll` 取 `RoGetActivationFactory`（79 行）与 `WindowsCreateStringReference`，取不到就判定为不支持。

本方案的 Windows 引擎照搬这一写法。

### 3.3 现有插件 DLL 的两种接口惯例

| 形式 | 代表 | 特点 |
| --- | --- | --- |
| C++ 接口对象 + 工厂函数，版本号必须一致 | `FlamingoFileShare/FileShareApi.h`、FlamingoMedia | exe 与 DLL 必须一起发布，换一个别人编译的 DLL 就用不了 |
| C 函数表，`m_cbSize` 只追加 | `FlamingoLang/FlamingoLangApi.h`（`LangApi::m_cbSize` 在 91 行，`kLangApiMinSize` 在 137 行） | 新 exe 配旧 DLL、旧 exe 配新 DLL 都能用，任何编译器都能实现 |

引擎要能替换，选第二种。

### 3.4 通用加载器

`Source/App/PluginModuleLoader.h` 分两层：`CPluginLibrary`（52 行起，`Load` 在 72 行）只管 `LoadLibraryExW` / `GetProcAddress` / `FreeLibrary` 与加载结果码；模板外壳 `CPluginModuleLoader<TModule>` 假定工厂函数接收接口版本号、返回模块对象，与 C 函数表的形态不同。本方案复用 `CPluginLibrary`，不用模板外壳。

### 3.5 三个入口的现状

| 入口 | 位置 | 现状 |
| --- | --- | --- |
| 聊天图片右键菜单 | `Source/UI/BalloonChatWnd/ChatMessageMenu.h` | 纯模型 + 单测（ChatImageMenuTests）。菜单项标识最后一个是 `kChatMsgMenuResendVoice = 13`（55 行）；`kChatMsgMenuSaveImageAs = 2`（44 行）只在图片就绪时出现 |
| 看图窗工具栏 | `Source/UI/BalloonImageViewer/ImageViewerToolbar.h` | 自绘控件，按钮种类 `ToolbarItemKind`，最后一个是 `kTbCopyImage`（42 行）；按钮编排有纯数据查询供单测使用 |
| 截图工具栏 | `FlamingoScreenshot/Capture/ScreenshotToolbar.h`（2026-10-07 前在 `Source/UI/BalloonScreenshot/`） | 自绘深色工具栏，图标种类 `ToolIconKind`，最后一个是 `kIconCancel`（41 行） |

看图窗的 `ImageCanvas` 用 `Gdiplus::Bitmap` 持有解码后的图片（`ImageCanvas.h:158`），exe 侧解码沿用 GDI+。

### 3.6 窗口私有消息号

`WM_APP + 0xF0` 已被 `FlamingoMedia/Record/RecordMessages.h:27` 的 `kMsgRecordManagerDeferred` 占用。本方案取 `WM_APP + 0xF8`，以 `[msgid]` 用例为准。

## 4. 第 0 期实测结果（2026-10-05）

环境：Windows 10 19045，已装识别语言 `en-US` 与 `zh-Hans-CN`，`OcrEngine::MaxImageDimension` 为 10000。试验脚本、样本与结果页当时放在本机临时目录，未入库。

### 4.1 样本与准确率

五张合成图（文字由脚本画上，有完整的标准答案）与四张 `design/` 下的真实截图和照片（标准答案是对照图片手抄的主要文字）。准确率 = 1 − 编辑距离 ÷ 标准答案字数，比较前去掉空格、统一全角半角。据实证（第 0 期试验脚本的输出）：

| 样本 | 原图行高 px | 原图 | 放大 2 倍 | 放大 3 倍 | 自动选择 |
| --- | --- | --- | --- | --- | --- |
| S1 文档段落（宋体 14px） | 14.0 | 88.9% | **94.9%** | 94.4% | ×2 |
| S2 表格（雅黑 13px） | 10.0 | 72.9% | 85.3% | **86.4%** | ×3 |
| S3 中英混排技术文字（14px） | 12.0 | 83.8% | **89.6%** | 89.2% | ×2 |
| S4 彩色横幅（大字白字） | 34.0 | **60.9%** | 58.7% | 58.7% | 原图 |
| S5 模拟手机拍纸质文档 | 25.0 | **93.8%** | 93.8% | 93.8% | 原图 |
| R1 单聊窗截图 | 12.0 | 55.6% | **74.6%** | 71.0% | ×2 |
| R2 消息记录窗截图 | 12.0 | 75.3% | **83.2%** | 78.9% | ×2 |
| R3 系统设置窗截图 | 11.5 | 31.8% | 58.8% | **64.7%** | ×3 |
| R4 手机拍屏幕的照片（4032×3024） | 49.0 | **79.8%** | 71.9% | 超上限 | 原图 |
| 平均 | | 71.4% | | | 80.9% |

结论：

1. **清晰的整段中文基本可用**（S1、S5 约 94%）。
2. **小字必须先放大。** 第 4.2 节的规则在九张图上选中的都是准确率最高的倍数。
3. **弱项**：彩色、渐变背景上的浅色字（S4 标题几乎全错，R1 顶部渐变上的白字同样）；灰色小字常被漏掉；英文与数字有固定混淆，连字符读成 `·`（`2021·03·15`）、`IM` 读成 `lM`、字母中间的 `0`、`1` 读成 `O`、`I`。这些是引擎本身的局限，预处理救不回来（第 4.4 节），要改善只能换引擎。
4. **R3 对话框背后那一片模糊文字，没有被误读出任何一行。**
5. **英文引擎**读英文更准（S3 的英文行完全正确），但读不出中文。

### 4.2 放大规则

先按原图识别一遍，取含汉字的行的行高中位数（没有含汉字的行时取全部行）：不低于 20px 不放大，12~20px 放大 2 倍，低于 12px 放大 3 倍；放大后最长边超过 10000 时降一档。原图最长边超过 10000 时先等比缩小。

### 4.3 拼行整理

引擎在每个汉字之间都插空格，数字有时被拆开（`1 0 月`）。整理规则：同一行的词按横坐标排序，两个汉字（含全角标点）之间不加空格；汉字与非汉字之间，间距超过行高的 0.25 倍才加空格；非汉字之间超过 0.35 倍才加。两个阈值是在九张图上网格搜索得出的，可能偏向这批样本。据实证，整理后保留空格比较时的平均准确率从 42.2% 提到 78.9%。

### 4.4 试过但不采用的预处理

在自动选出的倍数上对照（据实证，第 0 期试验脚本的输出）：只放大 81.1%，转灰度并拉伸对比度 79.2%，再加锐化 75.6%，「正色识别一遍、反色再识别一遍、把反色里新出现的行补进来」只多 0.2 个百分点，S4 的白字仍认不出。另外，同样放大 3 倍，GDI+ 高质量插值比 PIL 双三次插值略好（S1 为 94.9% 对 91.9%）。

### 4.5 耗时

只计 `RecognizeAsync` 本身：普通截图 40~400 ms；R4 原图 1.1 s、放大 2 倍 3.9 s。同一张图多次运行有一两倍的波动。两遍识别时第一遍是原图，小图的第一遍只要几十毫秒。

## 5. 总体结构

### 5.1 模块划分

```
Flamingo.exe                                          FlamingoOcr.dll（可替换）
├─ Feature/Ocr/OcrModuleHost   预加载、状态、缓存 ───► FlamingoOcr_GetApi → OcrApi 函数表（OcrApiTable）
├─ Feature/Ocr/OcrRecognizer   后台识别线程 ─────────► m_recognize / m_freeResult
├─ Feature/Ocr/OcrPrompt       不可用原因 → 提示框      ├─ Core/   结果组装、经宿主写日志
├─ Feature/Ocr/OcrLauncher     入口的发起调度（纯逻辑）  └─ WinOcr/ WinRT 取用、可用性、语言选择、
├─ UI/BalloonOcr/OcrEntry      发起实现：前置判断 + 打开结果窗口      放大规则、GDI+ 缩放、拼行整理、识别
├─ UI/BalloonOcr/OcrResultWindow / OcrResultLayout 结果窗口
└─ 三个入口（聊天菜单、看图窗、截图工具栏）→ ocr::LaunchOcrForFile / LaunchOcrForImage
```

DLL 没有界面、不依赖 balloonui、不做多语言；日志经宿主传入的回调写进客户端日志。

入口为什么不直接调结果窗口：入口所在的 `ChatBubble.cpp`、`ImageCanvas.cpp` 等也编进了 FlamingoUnit，而结果窗口只在 exe 里。入口只调 `Feature/Ocr/OcrLauncher`（纯逻辑），exe 在启动阶段（`CAppShell::Startup`）经 `balloonocr::RegisterOcrLaunchers()` 把真正的实现注册进去；单元测试则注册假的实现，检查入口传来的路径与旋转方向（OCRH9）。

### 5.2 状态与入口显隐

`OcrModuleHost` 的状态只会单向变化：

| 状态 | 何时进入 | 入口 | 点击后 |
| --- | --- | --- | --- |
| 未开始 / 加载中 | 进程启动 / 预加载线程已启动 | 不显示 | — |
| 不可用 | DLL 不存在、加载失败、不是本模块、函数表过旧、`m_init` 失败 | 不显示 | — |
| 可用，引擎可用 | 查询结果为 `ocr_available` | 显示 | 打开结果窗口并开始识别 |
| 可用，系统不支持 | `ocr_os_unsupported`（如 Win7） | 显示 | 提示「当前系统不支持文字识别，需要 Windows 10 或更高版本」 |
| 可用，没有识别语言 | `ocr_no_language` | 显示 | 提示「系统未安装文字识别所需的语言组件」，带「打开系统设置」按钮 |
| 可用，引擎初始化失败 | `ocr_engine_failed` | 显示 | 提示「文字识别引擎无法启动」，具体原因写日志 |

「不可用」只尝试一次，之后不再重试；日志里记一条英文原因（`CPluginLibrary::DescribeResult`）。看图窗与截图工具栏在创建时取一次状态决定有没有识别按钮；预加载在后台线程上很快完成（联调实测 16 ms，第 11 节），赶在它之前打开的窗口这一次没有按钮。2026-10-07 起预加载与结果窗口的接线由登录成功后提前到程序启动阶段（`CAppShell::Startup`），未登录时截图也能识别文字（`docs/截图独立模块方案.md` 3.7 节）。

### 5.3 线程模型

| 线程 | 做什么 |
| --- | --- |
| 预加载线程（一次性） | `CoInitializeEx(MTA)` → 加载 DLL → `m_init` → `m_queryAvailability` → 取识别语言列表 → 把结果交回 `OcrModuleHost`（加锁） → 退出 |
| 识别线程（常驻，按需创建） | `CoInitializeEx(MTA)`；从队列取任务：GDI+ 解码 → `m_recognize` → 拷贝结果 → `m_freeResult` → 投递给结果窗口。宿主保证同一时刻只有一个 `m_recognize` 调用，替换引擎时不必考虑并发 |
| 界面线程 | 只读缓存的状态，从不等待 DLL |

- 结果窗口私有消息 `WM_APP + 0xF8`，`lParam` 为堆上的结果对象。窗口已关闭导致 `PostMessage` 失败时，由识别线程释放该对象。
- 同一个结果窗口发起新识别时，先置位上一个任务的取消标志。
- DLL **加载后不卸载**（与 FlamingoLang 相同），避免卸载正在运行识别的代码。进程退出时识别线程若仍在运行，不等待它。

## 6. 接口约定（`FlamingoOcr/FlamingoOcrApi.h`，1a 定稿）

exe、Windows 引擎 DLL 以及以后的替换引擎共用这一个头文件。下面是起草时的版本，**以头文件为准**；1a 定稿时的改动：取消标志的类型写成 `volatile long*`（不再依赖 `windows.h` 的 `LONG`，替换引擎的实现方更省事）；`m_scale100` 改名为 `m_scalePercent`；增加了 `kOcrHostInfoMinSize`、`kOcrAvailabilityInfoMinSize`、`kOcrImageMinSize` 三个最小结构大小，DLL 据此拒绝过小的结构；`OcrWord`、`OcrLine`、`OcrRect` 以数组出现，声明为大小永久固定，需要扩展时在 `OcrResult` 末尾追加新的并列数组。

```cpp
#define FLAMINGO_OCR_DLL_NAME    L"FlamingoOcr.dll"     //与 Flamingo.exe 放在同一目录
#define FLAMINGO_OCR_ENTRY_NAME  "FlamingoOcr_GetApi"   //由 .def 固定，32 位与 64 位相同

namespace flamingoocr {

//引擎可用性
enum OcrAvailability
{
    ocr_available      = 0,   //可以识别
    ocr_os_unsupported = 1,   //操作系统不支持（如 Win7 上没有 Windows.Media.Ocr）
    ocr_no_language    = 2,   //引擎在，但没有任何可用的识别语言
    ocr_engine_failed  = 3,   //引擎初始化失败（模型文件缺失等），详情已写日志
};

//m_recognize 的返回值
enum OcrResultCode
{
    ocr_ok                   = 0,   //成功（识别出 0 行也算成功）
    ocr_bad_argument         = 1,   //参数非法：图像为空、宽高为 0、行跨度不足、出参为 NULL
    ocr_unavailable          = 2,   //引擎不可用（可用性不是 ocr_available）
    ocr_language_unsupported = 3,   //指定的识别语言不在可用列表里
    ocr_cancelled            = 4,   //宿主置位了取消标志
    ocr_engine_error         = 5,   //引擎内部错误，详情已写日志
    ocr_out_of_memory        = 6,   //内存不足
};

struct OcrHostInfo        //宿主交给 DLL 的信息（m_cbSize 由宿主填）
{
    uint32_t m_cbSize;
    void (__cdecl* m_log)(int level, const char* text);   //写日志，text 为 ASCII 英文
    const wchar_t* m_uiLanguage;                          //当前界面语言，如 L"zh-CN"，用于选默认识别语言
};

struct OcrAvailabilityInfo   //m_queryAvailability 的出参（m_cbSize 由宿主填）
{
    uint32_t m_cbSize;
    int      m_availability;          //取值见 OcrAvailability
    const wchar_t* m_settingsUri;     //可选：「打开系统设置」的地址，如 L"ms-settings:regionlanguage"；没有时为 NULL
};

struct OcrImage   //输入图像：32 位 BGRA，自上而下
{
    uint32_t m_cbSize;
    uint32_t m_width;                 //宽，像素
    uint32_t m_height;                //高，像素
    uint32_t m_stride;                //每行字节数，不小于 m_width * 4
    const uint8_t* m_pixels;          //像素数据，归宿主所有，只在本次调用期间有效
};

struct OcrRect { float m_x; float m_y; float m_w; float m_h; };   //输入图像的像素坐标

struct OcrWord { const wchar_t* m_text; OcrRect m_rect; };
struct OcrLine { const wchar_t* m_text; OcrRect m_rect; uint32_t m_wordCount; const OcrWord* m_words; };

struct OcrResult   //识别结果，整块归 DLL 所有，经 m_freeResult 释放
{
    uint32_t m_cbSize;
    uint32_t m_lineCount;
    const OcrLine* m_lines;           //按阅读顺序排列；m_text 已做拼行整理
    const wchar_t* m_languageTag;     //实际使用的识别语言
    float    m_textAngle;             //引擎估计的文字倾斜角（度），估计不出时为 0
    uint32_t m_scale100;              //实际放大倍数 ×100（100 表示未放大），写日志用
};

struct OcrApi
{
    uint32_t m_cbSize;                                                   //DLL 编译时的结构大小，只在末尾追加
    int  (__cdecl* m_init)(const OcrHostInfo* host);                     //初始化，返回 0 表示成功；只调用一次
    const wchar_t* (__cdecl* m_getEngineName)();                         //如 L"Windows.Media.Ocr"，写日志用
    const wchar_t* (__cdecl* m_getEngineVersion)();
    int  (__cdecl* m_queryAvailability)(OcrAvailabilityInfo* out);
    uint32_t (__cdecl* m_getLanguageCount)();
    const wchar_t* (__cdecl* m_getLanguageTag)(uint32_t index);          //BCP-47 代码
    const wchar_t* (__cdecl* m_getLanguageName)(uint32_t index);         //显示名，由引擎按系统语言给出
    const wchar_t* (__cdecl* m_getDefaultLanguage)();                    //按 m_uiLanguage 选出的默认识别语言
    int  (__cdecl* m_recognize)(const OcrImage* image, const wchar_t* languageTag,   //NULL 表示默认语言
                                volatile LONG* cancelFlag,               //宿主置 1 请求取消，可为 NULL
                                OcrResult** result);                     //成功时置为结果，失败时置为 NULL
    void (__cdecl* m_freeResult)(OcrResult* result);                     //传 NULL 是安全的
};

} // namespace flamingoocr

typedef const flamingoocr::OcrApi* (__cdecl* FlamingoOcrGetApiFn)();     //永不返回 NULL
```

约定：

- **兼容规则**：所有带 `m_cbSize` 的结构只在末尾追加字段，不修改、不删除、不重排；宿主用某个字段之前先按 `m_cbSize` 判断对方是否提供了它。宿主可用的最小函数表到 `m_freeResult` 为止（`kOcrApiMinSize`）。
- **内存**：两边都静态链接 CRT、各有独立的堆。DLL 返回的结果整块归 DLL 所有，只能经 `m_freeResult` 释放；DLL 返回的其它字符串在 DLL 卸载之前一直有效（宿主加载后不卸载）；宿主传入的指针只在本次调用期间有效。
- **异常**：每个导出函数都在边界上捕获全部 C++ 异常并转成返回码，异常不越过模块边界。
- **线程**：`m_init`、`m_queryAvailability` 与语言查询在预加载线程上调用；`m_recognize` 在识别线程上调用，宿主保证同一时刻最多一个；`m_log` 可以在任意线程回调。

### 6.1 替换引擎须知

替换用的 DLL 须满足：文件名为 `FlamingoOcr.dll`；导出 `FlamingoOcr_GetApi` 并按上面的约定填表；位数与 exe 相同（64 位 exe 配 64 位 DLL，否则加载失败、入口隐藏）；自带的模型等文件按 DLL 自身所在目录定位（`GetModuleFileNameW` 取自身句柄），不依赖当前目录；预处理与拼行整理由引擎自己负责，交出的行文字已经是给用户看的样子。

## 7. Windows 引擎的实现要点

- **WinRT 取用**：照搬第 3.2 节，运行时从 `combase.dll` 取 `RoGetActivationFactory`、`WindowsCreateStringReference`、`WindowsGetStringRawBuffer`、`WindowsDeleteString`；任一取不到即报告 `ocr_os_unsupported`。WinRT 相关代码集中在 `WinOcr/` 下几个不用预编译头的翻译单元里，自己把系统版本宏定到 Win10。
- **可用性**：`OcrEngine` 的激活工厂取不到 → `ocr_os_unsupported`；`AvailableRecognizerLanguages` 为空 → `ocr_no_language`，`m_settingsUri` 给 `ms-settings:regionlanguage`。
- **默认识别语言**：界面语言 `zh-CN` → `zh-Hans`，`zh-TW` → `zh-Hant`，`en-US` → `en`，`ja-JP` → `ja`，`ko-KR` → `ko`，按前缀匹配可用列表；匹配不到时用 `TryCreateFromUserProfileLanguages`。
- **输入图像**：先复制一份并把透明背景铺成白色（`FlattenOnWhite`，透明 PNG 上的深色字不会变成黑底黑字）。`ISoftwareBitmapFactory::CreateWithAlpha`（BGRA8、预乘 Alpha）建 `SoftwareBitmap`，`LockBuffer` 取 `IMemoryBufferByteAccess` 按行拷入像素。放大与缩小用 GDI+ 高质量双三次插值（`WinOcr/OcrBitmapScaler`），在 DLL 内部完成；GDI+ 在 `m_init` 时启动，不在 `DllMain` 里。
- **等待识别完成**：`RecognizeAsync` 返回 `IAsyncOperation<OcrResult*>`；**每 5 ms 轮询一次 `IAsyncInfo::get_Status`**，同时检查取消标志，置位时调 `IAsyncInfo::Cancel` 并返回 `ocr_cancelled`；一遍超过 60 秒按超时处理。起草时打算注册完成回调，实现时改为轮询：取消之后回调仍可能晚到，届时等待它的对象可能已经析构，轮询没有这个问题（写法与 `WgcWindowCapturer` 轮询取帧相同）。
- **不跨线程缓存 WinRT 对象**：初始化只保存语言列表等普通数据，每次识别重新取工厂、创建引擎；每个方法自己调一次 `CoInitializeEx`（多线程套间），调用线程已初始化过 COM 时照常工作。
- **两遍识别**：第一遍识别原图（最长边超过 10000 时先缩小），按第 4.2 节的规则决定是否放大再识别第二遍，坐标除以倍数换算回原图。实现时补充一条：**第一遍一行都没识别出来时，放大 2 倍再试一次**（小字图在原尺寸下可能什么都读不到）；第二遍失败或一行都没读出而第一遍有结果时，保留第一遍。
- **拼行整理**：第 4.3 节的规则与阈值，实现为不依赖 WinRT 的纯函数，配单测。
- **日志**：英文，记录引擎名与版本、可用性、语言列表、图像尺寸、放大倍数、两遍各自的耗时、行数，失败时的 HRESULT。**不记录识别出的文字**，以免截图里的敏感内容落进日志。

## 8. exe 侧设计

### 8.1 `Feature/Ocr/OcrModuleHost`

- `StartPreload(dllPath, uiLanguage)`：程序启动时由 `CAppShell::Startup` 调用（2026-10-07 起），立即返回；只第一次调用有效，再调不会重复加载。DLL 路径为 exe 所在目录下的 `FlamingoOcr.dll`，界面语言取 `i18n::GetLanguage()`。
- `GetState()`：返回第 5.2 节的状态，界面线程随时可调，不阻塞。
- `CanShowEntry()`：状态为「可用」（任一引擎可用性）时返回 true。入口实际调用的是 `ocr::IsOcrEntryVisible()`，它还要求发起实现已注册。
- 测试用：`StartPreloadWithProvider(provider, ...)` 用函数表来源代替 DLL 加载（起草时叫 `AttachApiForTest`，改成来源函数后预加载线程的行为也能一并测到）；`WaitForPreload(timeout)` 等待预加载结束。

### 8.2 `Feature/Ocr/OcrRecognizer`

- 任务来源有两种：图片文件路径（聊天图片、看图窗，看图窗另带当前旋转角度），或内存中的 32 位位图（截图选区）。
- GDI+ 解码为 `PixelFormat32bppARGB` 后按行拷成 BGRA；GIF 取当前帧。
- 识别结果拷成 exe 自己的结构（`std::wstring` 与矩形），随后立即 `m_freeResult`。

### 8.3 结果窗口 `UI/BalloonOcr/OcrResultWindow`（按推荐取值实现，2026-10-05）

- `DuiFrameWindow`，只用 balloonui 现成控件，未改 balloonui。控件树单独放在 `OcrResultLayout`（与接龙窗口同一写法），布局单测不建窗口也能排版。
- 版式自上而下：「识别语言」小标题 + 下拉框（`DuiComboBox`，列出可用识别语言，默认选中引擎给的默认语言）+ 右侧状态文字；可编辑、可选取的识别结果（`DuiRichEdit`，多行、自动换行，内容多时出现悬浮滚动条，识别错的字可以就地改）；底部右侧「重新识别」「复制全部」（`DuiButton`）。

- 进程内只有一个窗口：已打开时再从别处打开，取消上一次识别、换成新图片，窗口留在用户放的位置；不设 owner，聊天窗或看图窗关闭时它照常保留。换识别语言即重新识别；迟到的旧任务结果按任务号丢弃。

- 原图上画行框、点框选中对应文字等增强，未做，视需要再做。

## 9. 工程与构建

- `FlamingoOcr.vcxproj`：`Debug|Win32`、`Release|Win32`、`Debug|x64`、`Release|x64` 四个配置，都定义 `WIN32`、使用静态 CRT（`/MTd`、`/MT`）、加 `/utf-8`；`OutDir` 与 `FlamingoLang.vcxproj`（85~103 行）一致，`Debug|x64` 输出到 `flamingoclient/Debug/`。
- `.def` 固定导出名；exe 不链接 DLL 的导入库。
- 登记进 `FlamingoClient.sln`。与其它插件 DLL 一样不设生成顺序依赖（`Flamingo` 工程在解决方案里只依赖 balloonui_static）。
- DLL 源文件与 `FlamingoOcr/Tests/` 下的用例直接编进 `FlamingoUnit`；新增文件后运行 `python flamingoclient/tools/gen_vcxproj_filters.py`，它已登记 `FlamingoOcr.vcxproj`，DLL 自身的 `.filters` 也由它生成。
- 工程文件与 props 里一律用相对路径（2026-10-05 用户定的原则）。
- `.gitignore` 已加入 DLL 的四个中间目录；编译出的 DLL 与 pdb 由「PC 客户端的四个输出目录」一节统一忽略。
- **发布**：更新包由发布者把要覆盖的文件手工打成 zip（`docs/客户端自动更新方案.md` 7.1 节「发布一个新版本的完整流程」及其中的「打包规则」：每次都要放进安装根目录下全部的 `.exe` 与 `Flamingo*.dll` 插件，只有字幕模型 `FlamingoCaptionModel.dll` 在没有变化时可以不放），仓库里没有列 DLL 清单的打包脚本。发布带识别功能的版本时，要把 `FlamingoOcr.dll` 一并放进包里；漏放时客户端照常运行，只是没有识别入口。

## 12. 风险

1. **识别效果有上限。** 第 4.1 节的弱项（彩色背景上的浅色字、灰色小字、英文数字混淆）是引擎本身的局限。对策是可替换的 DLL 接口：效果不够时换引擎，exe 不用改。
2. **进程内运行。** DLL 与 exe 在同一个进程里，加载失败、接口不对、引擎报错都能妥善处理，但引擎内部崩溃会带着主程序一起退出。Windows 引擎据推测不会有这个问题；以后接入来源不明的第三方引擎时，如需完全隔离，要改成独立进程。
3. **识别语言组件。** 英文版 Windows 的用户需要自己安装中文识别组件，入口会提示并带「打开系统设置」按钮。
4. **阈值可能偏向样本。** 放大规则与拼行阈值只在九张图上调过，上线后按反馈再调。

## 14. 系统菜单入口与「打开图片」（2026-10-05）

### 14.1 需求与决定

用户要求在主面板系统菜单里也加一个「图片文字识别」，打开后可以选一张本地图片识别。2026-10-05 用户选定的做法：

- 点菜单项**先打开识别窗口**，窗口里还没有图片，状态行显示「请打开一张图片」；用户在窗口里点「打开图片」选图后开始识别。
- 「打开图片」按钮放在结果窗口左下角，**从任何入口打开的结果窗口都有**：从聊天图片、看图窗、截图进来的窗口也可以换一张图接着识别。

### 14.2 改动

- **菜单项**：`MainPanelSystemMenu` 新增命令 `kSysMenuOcr = 18`；`BuildSystemMenuModel` 末尾新增参数 `withOcr`（默认 false），为真时在「消息与工具」组里紧跟「备忘与提醒」插入「图片文字识别」。图标 `kIconOcr = 37`（`MainPanelIcons`，四角取景框加一个「T」，与看图窗、截图操作栏的识别图标同一画法）。
- **可见性**：主面板按 `ocr::IsOcrEntryVisible()` 传 `withOcr`，与其它三个入口规则相同 —— 识别模块加载失败或 DLL 不存在时整项不出现；系统不支持、没有识别语言时照常出现，点了弹提示（第 8.4 节）。
- **打开窗口**：`CBalloonMainPanel` 收到 `kSysMenuOcr` 时调用 `balloonocr::LaunchOcrWindow(m_hWnd)`（`UI/BalloonOcr/OcrEntry`）：先过与其它入口相同的前置判断，通过后调用 `COcrResultWindow::OpenEmpty` 打开没有图片的窗口，居中摆在主面板上。窗口已经开着时直接提到前台，不清掉已有结果。
- **「打开图片」按钮**：`OcrResultLayout` 新增控件 `kOcrIdOpen = 107`，宽 96，在底部按钮行最左边（「重新识别」「复制全部」仍靠右）。`COcrResultWindow::ChooseImageFile` 用 `CFileDialog` 选文件，过滤串用 `filedlg::MakeFilter` 拼「图片文件」（`filedlg::kImagePatterns`）与「所有文件」；选好后按文件路径识别，走的是聊天图片入口同一条路径（`OcrRequest::m_filePath`），旋转角度取 0。
- **没有图片时的状态**：新增 `OcrRecognizer` 的 `HasImageSource(request)`，请求里既没有文件路径、也没有像素时返回 false。`StartRecognition` 遇到这种请求时不发起识别，状态行显示 `OcrNoImageText()`（「请打开一张图片」），「重新识别」不可用；`CancelRunning` 也按它决定「重新识别」是否恢复可用。
- **界面文字**：新增「图片文字识别」「打开图片」「请打开一张图片」三条，已跑 `i18n_extract.py`，四种语言的译文已补齐、标「待审校」。
