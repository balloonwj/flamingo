# PC 客户端多语言方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-03
> 用途：记录 PC 客户端（`flamingoclient/`）支持简体中文、繁体中文、英文、日文、韩文五种界面语言的需求结论、现状盘点、总体设计、分期开发步骤与测试用例。后续每步开工前据此细化、收尾后回填实际结果。
> 体例沿用 `docs/文件共享方案.md`：结论一律标注来源，「据实证」必附文件:行号或命令输出，「据推测」表示尚未验证。

---

## 1. 背景与目标

客户端界面目前只有简体中文。本方案让客户端支持五种界面语言：简体中文（zh-CN）、繁体中文（zh-TW）、英文（en-US）、日文（ja-JP）、韩文（ko-KR）。

翻译数据以独立工程 `flamingoclient/FlamingoLang/` 交付，产物为 `FlamingoLang.dll`，由主程序在启动时按需加载。三条设计目标：

1. **DLL 不存在时，行为与外观与现在完全一样**，界面为简体中文，也不出现语言选项。
2. **对以后新增的界面保持兼容。** 新界面的文字即使还没有译文，也只是显示中文，不会出现空白或乱码；新代码忘记标记翻译时，单元测试要能当场发现。
3. **exe 与语言包可以各自升级。** 旧语言包配新 exe，新增的文字显示中文；新语言包配旧 exe，多出来的条目被忽略。

不在本方案范围内：flamingoAdmin、Android 客户端、服务端日志与管理端接口。

### 1.1 术语

| 用语 | 含义 |
| --- | --- |
| 原文 | 代码里写的简体中文文字。它同时是查找译文的键 |
| 译文 | 语言包里某条原文在某种语言下的文字 |
| 上下文 | 同一条原文在不同场合需要不同译法时附加的区分标记，对应 gettext 的 `msgctxt` |
| 语言包 | `FlamingoLang.dll`，内含繁中、英、日、韩四种语言的译文与推荐字体 |
| 伪语言 | 语言包里一种不对用户开放的测试语言，把每条原文加括号并拉长，用来发现漏标记与被截断的文字 |

## 3. 现状盘点

### 3.1 界面文字的数量与分布

用脚本粗略统计（排除注释、日志、单测与 Mock / Stress / DebugEntry 数据文件），据实证：

| 范围 | 带中文的字面量（处） |
| --- | --- |
| 主程序 `Source/` | 约 2340 |
| `FlamingoMedia/` | 约 440 |
| `FlamingoFileShare/` | 约 250 |
| `FlamingoUpdater/` | 83 |
| balloonui 库 | 12 |

- 去重后约 2050 条、1.6 万个汉字，分布在约 400 个文件里。
- 集中定义在 `Source/App/UIText.h` 的只有 20 来条，其余直接写在各窗口代码与内嵌 XML 里。
- 189 条带 `%d`、`%s` 等格式占位符；另有 20 处左右把几段中文拼接成一句（如 `name + _T("的…")`）。
- 按 `==`、`!=`、`Compare`、`Find` 搜索，没有拿中文字面量做比较或查找的逻辑代码（0 处），翻译不会改变程序行为。
- 其中混有一部分不是界面文字、而是没走 `LOG_` 宏的中文诊断信息，例如 FlamingoMedia 枚举设备时的 `原生[%lu]：fourcc=...`、`设备[%u]：%s`。这类按日志规范改成英文，不进翻译表；第 2、3 期改造时逐个甄别。

### 3.2 界面的搭建方式

- 主要窗口的客户区由内嵌 XML 经 balloonui 的 `DuiXmlBuilder` 构建，例如登录窗 `Source/UI/BalloonAuth/BalloonLoginLayout.cpp` 的 `kLoginBodyXml`。文字写在 `text`、`placeholder` 等属性里。
- `DuiXmlBuilder` 提供 `Parse`（XML → 节点树）与 `Build`（节点树 → 控件）两步接口，以及 `FromString`、`FromFrameXml` 两个一步到位的入口（`third-party/balloonui/balloonui/DuiXmlBuilder.h`），据实证。客户端可以在交给它之前替换文字属性，不必修改 balloonui。
- 其余文字由代码直接 `SetText`、`DrawText`、`MessageBox` 写出；含 `MessageBox` 一类调用的文件有 32 个、共 160 处。
- `Source/flamingo.rc` 里的菜单与字符串表是早年遗留：代码里没有任何 `LoadMenu`、`LoadString` 调用（`grep` 结果为空），本方案不处理。

### 3.3 balloonui 内置的中文

只有 12 条，全部是输入框右键菜单的命令文字，据实证：

- `Controls/Input/EditContextMenu.h:137-143`（`EditContextCommandLabel`：剪切、复制、粘贴、全选）；
- `Controls/Input/RichEditContextMenu.h:118-139`（`DuiRichEditMenuCommandLabel`：撤销、重做、剪切、复制、粘贴、粘贴为纯文本、删除、全选）。

其中富文本框的菜单已允许调用方传入文字（`MakeDuiRichEditMenuItem` 的 `szText` 参数，传空指针时才取内置文字），普通输入框的菜单没有这样的入口。

### 3.4 字体

- 客户端有 50 多个文件写死了「微软雅黑」或 `Microsoft YaHei`（含注释，69 行）。
- balloonui 的 `DuiTheme` 提供 `SetDefaultFontFace` / `GetDefaultFontFace`（`DuiTheme.h:110-111`），但 `DuiEdit.cpp`、`DuiResMgr.cpp`、`DuiAvatar.cpp` 另外写死了 `Microsoft YaHei`（第 3 期 3d 已改为取 `DuiTheme` 的默认字体）。
- `ChatBubble.cpp`、`ImageViewerToolbar.cpp`、`BalloonModifyAvatarDlg.cpp`、`MainPanelAvatar.cpp` 用 GDI+ 绘制文字；balloonui 中 `DuiToast.cpp` 也是。

## 4. 总体结构

```
Flamingo.exe ──启动时──> Common/I18n ──LoadLibrary──> FlamingoLang.dll（可选）
    │                        │                           └ 繁中 / 英 / 日 / 韩 的 .po 与推荐字体
    │                        └ TR / TRC / TRF / TranslateXml
    ├─ 宿主接口提供翻译函数 ──> FlamingoMedia.dll、FlamingoFileShare.dll
    └─ 命令行 --lang ──> FlamingoUpdater.exe ──复制到 %TEMP% 后自行加载──> FlamingoLang.dll
```

- **`FlamingoLang` 工程**：不含界面，不依赖 balloonui，只装译文数据与查找代码。简体中文就是代码里的原文，不放进 DLL。
- **主程序的 `Source/Common/I18n/` 模块**：启动时加载 DLL、确定当前语言、提供查找接口。DLL 不存在、加载失败、函数表不合要求、或配置的语言在 DLL 里没有，一律退回简体中文，并写一条英文日志说明原因。
- **FlamingoMedia 与 FlamingoFileShare** 不自己加载语言包。exe 在 `IMediaHost`、`IFileShareHost` 里新增翻译函数与取界面字体的函数（与现有的 `Log` 一样经宿主调用），两边的 `kApiVersion` 各加 1。整个进程只有一份语言状态。
- **FlamingoUpdater** 是独立进程。exe 启动它时在命令行加 `--lang <代码>`；它把语言包复制到 `%TEMP%\FlamingoLang_updater_<进程号>.dll` 再加载，上次运行留下的复制品启动时清理（第 11 节 3c）。原因：升级包里如果带有新的 `FlamingoLang.dll`，更新器自己占用着安装目录里的这个文件会导致覆盖失败。

## 5. 文字的标记与查找

### 5.1 写法

```cpp
pLabel->SetText(TR(L"记住密码"));                                  // 普通文字
menu.AddItem(TRC(L"群成员菜单", L"移出"));                          // 同一原文需要不同译法时附加上下文
CString s = TRF(L"已选择 {0} 个联系人，共 {1} 个", n, total);       // 带参数的整句模板
```

- `TR(原文)`：返回当前语言的译文；查不到时返回原文本身。目标 1、2 都由这条规则保证，不需要额外分支。
- `TRC(上下文, 原文)`：带上下文的查找。上下文只用于区分，不显示。
- `TRF(模板, 参数...)`：先查模板的译文，再把 `{0}`、`{1}` 替换为参数。参数支持整数与字符串，用 C++11 变参模板实现。
- `TR_NOOP(原文)`：原样返回原文，不做翻译，只供提取脚本收录。用于静态字符串表（见第 5.6 节）与运行期拼接的 XML 片段（见第 5.3 节）。
- 返回的指针指向语言包内存或原文字面量，在进程生命周期内一直有效（语言包加载后不卸载）。

### 5.2 为什么占位符改成编号形式

英、日、韩的语序与中文不同，译者需要调整参数的位置。`CString::Format` 与 `printf` 系列不支持带序号的参数，所以 189 条格式串在改造时统一改成 `{n}`。拼接句同样改写成整句模板，例如 `name + _T("的群")` 改为 `TRF(L"{0}的群", name)`。

### 5.3 内嵌 XML

不逐条改写 XML。新增 `i18n::TranslateXml(xml)`：在交给 `DuiXmlBuilder::FromString` / `FromFrameXml` 之前，**在字符串层面**把 `text`、`placeholder`、`title`、`tooltip` 四个属性的值替换为译文，其余字节原样保留。译文写回前把 `&`、`<`、`>`、`"`、`'` 转义，与 `DuiXmlBuilder` 解码属性值时认的五种转义一致（`DuiXmlBuilder.cpp` 的 `DecodeAttrEntities`）。各窗口只需在调用处多包一层。选字符串层面而不是节点树层面，是因为 `FromFrameXml` 没有节点树层面的入口，字符串替换能统一覆盖两种入口。

只翻译这四个属性的原因：其它属性里也可能出现中文，但那是用户数据，例如通讯录头像的占位姓氏 `name="江"`（`ContactLayout.cpp:1732`）。

**运行期拼接的 XML**（如 `BalloonMainLayout.cpp` 的 `xml += u8"搜索联系人、群、消息、文件…";`）：拼接用的中文片段用只做标记、不做翻译的 `TR_NOOP(...)` 包起来，供提取脚本收录；整段拼好后照样经过 `TranslateXml`。

#### 5.3.1 0b 步原型验证结果（2026-10-03）

原型验证程序链接 balloonui 的 x64 Debug 静态库，用真正的 `DuiXmlBuilder::Parse` 解析替换前后的 XML 并逐节点比对，据实证：

1. 生产代码中全部 9 段内嵌 XML（7 个文件）共 75 个含中文的文字属性（`text` 71、`placeholder` 4），用伪翻译替换后全部命中；替换前后标签、属性集合、层级完全相同，只有这 75 个值发生变化，且恰好是期望的译文。
2. 译文含 `&`、`"`、`<`、`>`、`'` 时，单引号与双引号两种写法下解析出的值都与译文逐字节相同。
3. 注释中的属性、`name` 等非白名单属性、空值、不含中文的值（如 `text="1:1"`）均不变。
4. 耗时：最大的一段（群聊窗布局，6189 字节）Release 0.15 毫秒、Debug 1.9 毫秒，只在建窗时执行一次，可以接受。

### 5.4 不翻译的内容

- 聊天内容、联系人 / 部门 / 群名称等用户数据，包括服务端自动生成的群名（已经是数据，用户可改）。
- 日志：已经约定为英文（开发约定文档代码规范第 15 条）。
- 部署方在 `flamingo.ini` 配置的品牌文字 `apptitle`、`slogan`、`copyrighttext`。但**未配置时使用的内置标语与版权行要翻译**，「关于 {0}」「退出 {0}」这类改为模板。
- 联系人按拼音排序与拼音搜索，与界面语言无关，不改。

### 5.5 查找性能

自绘控件每次重绘都会调用 `TR`。0b 步用生产代码中 2009 条真实的中文字面量建表实测，每次查找的平均耗时，据实证：

| 查找方式 | Debug（/MTd /Od） | Release（/MT /O2） |
| --- | --- | --- |
| 先用字面量构造 `std::wstring`，再查 `unordered_map` | 3.9 微秒 | 0.54 微秒 |
| 直接对 `wchar_t*` 算 64 位 FNV-1a 哈希查索引，命中后 `wcscmp` 校验，不分配内存 | 1.2 微秒 | 0.25 微秒 |
| 在上一种前面加一层按字面量地址的缓存 | 1.15 微秒 | 0.04 微秒 |

2009 条原文的 64 位哈希没有冲突，但实现上仍须处理冲突（同一哈希挂多条、逐条比对）。

**结论**：采用第二种。即使一次重绘查找 100 条文字，Debug 下也只多 0.12 毫秒；地址缓存在 Debug 下几乎没有收益，暂不做。

### 5.6 静态字符串表与初始化顺序

文件作用域的静态字符串表（如菜单项名称数组）在 `main` 之前完成初始化，早于语言包加载。若在那里直接调 `TR`，得到的永远是中文。规则：静态表里一律用 `TR_NOOP` 标记，到使用处再调 `TR`。`I18n` 模块在 Debug 构建下检测「初始化之前就被调用的 `TR`」，并写一条警告日志带上原文，便于定位。

## 6. 语言包 DLL

### 6.1 翻译源文件

- 采用标准 gettext `.po` 格式，每种语言一个：`FlamingoLang/lang/zh-TW.po`、`en-US.po`、`ja-JP.po`、`ko-KR.po`，UTF-8 无 BOM。好比对、好合并，译者也能用 Poedit 等通用工具。
- `.po` 原样作为 `RCDATA` 资源编进 DLL；运行时只解析当前选中的那一种语言。修改译文只需重新编译 DLL。
- 机器起草、尚未经母语者审校的条目，用译者注释 `#. 待审校` 标记（不用 gettext 的 `fuzzy` 标记，因为按 gettext 惯例带 `fuzzy` 的条目不生效）。

### 6.2 导出接口

DLL 只导出一个 C 函数 `FlamingoLang_GetApi()`，返回一张函数表，全部使用 C 类型，不跨 DLL 边界传递 C++ 对象：

| 函数 | 作用 |
| --- | --- |
| 取语言数与第 i 种语言的信息 | 语言代码、本族语名称（繁體中文、English、日本語、한국어）、推荐界面字体 |
| 选定语言 | 解析该语言的 `.po`，失败时返回错误 |
| 按上下文与原文查找 | 返回 UTF-16 译文指针，查不到返回 NULL；内存归 DLL 所有 |
| 取语言包版本 | 写日志、排查问题用 |

函数表**只在末尾追加，不修改已有字段**，首字段为 `cbSize`，exe 按大小判断哪些函数可用。这一点与 FlamingoMedia、FlamingoFileShare「双方版本号必须完全相同」的规则不同，是有意为之：语言包要能单独替换，严格匹配版本会让「旧语言包配新 exe」直接失效，违背目标 3。

### 6.3 工程配置

与 `FlamingoP2P` 一样：四种配置都定义 `WIN32`、使用静态 CRT；四种配置的输出目录与 exe 相同（`Debug|x64` 为 `flamingoclient/Debug/`），与 exe 并列。加载复用 `Source/App/PluginModuleLoader.h` 的 `CPluginLibrary`（按完整路径、`LOAD_WITH_ALTERED_SEARCH_PATH` 加载并取导出函数）。

### 6.4 提取脚本

`flamingoclient/tools/i18n_extract.py`：扫描源码里的 `TR`、`TRC`、`TRF` 与内嵌 XML 的文字属性，更新各个 `.po`。新出现的原文追加为待翻译条目，代码里已不存在的条目标为作废（`#~`），条目按源文件排序以保证差异稳定。支持 `--check`，只比较不写入，用法与 `gen_vcxproj_filters.py` 一致。

## 7. 语言的选择、保存与生效

### 7.1 保存位置

`flamingo.ini` 的 `[ui] language=<语言代码>`，按机器保存。不按账号保存的原因：登录窗出现时还不知道是哪个账号。

没有这一项时表示「跟随系统」，每次启动按 Windows 显示语言（`GetUserDefaultUILanguage`）决定：

| Windows 显示语言 | 界面语言 |
| --- | --- |
| 中文（台湾、香港、澳门） | zh-TW |
| 英文（任何地区） | en-US |
| 日文 | ja-JP |
| 韩文 | ko-KR |
| 其它，包括简体中文 | zh-CN |

用户在界面上明确选过语言之后才写入这一项。

### 7.2 入口

- **设置窗「通用」页**：一个「语言 / Language」下拉框，各语言用本族语名称显示，第一项为「跟随系统」。

## 8. 专项处理

### 8.1 时间与日期

「昨天 14:05」「星期一」「上午」等文字分布在 `ChatTimeSeparator.cpp`、`HistoryView.cpp`、主面板列表项等处，改为模板；星期名、月份名也作为翻译条目。统一使用 24 小时制，不引入完整的区域格式库。`HistoryView.cpp` 里一类返回窄字符（UTF-8）字符串的地方，在 2d 步统一改为宽字符或提供 UTF-8 版本的查找函数。

### 8.2 复数

第一版不做复数规则。英文译文用不区分单复数的写法（如 `Files: 2`）。

### 8.3 文件大小、数字

文件大小沿用「KB / MB / GB」与阿拉伯数字，不随语言变化。

### 8.4 菜单助记符

带 `(&T)` 一类助记符的文字，译文自行决定助记符位置（如英文 `Cu&t`）；`[langpack]` 用例检查原文有助记符时译文也有。

### 8.5 界面字体

每种语言给一串候选字体，启动时取第一个已安装的：

| 语言 | 候选字体（按优先顺序） |
| --- | --- |
| zh-CN | Microsoft YaHei |
| zh-TW | Microsoft JhengHei → PMingLiU → Microsoft YaHei |
| ja-JP | Yu Gothic UI → Meiryo UI → Meiryo → MS UI Gothic → Microsoft YaHei |
| ko-KR | Malgun Gothic → Gulim → Microsoft YaHei |
| en-US | Segoe UI → Microsoft YaHei |

做法：候选列表由语言包提供（简体中文时用内置的微软雅黑）；启动时用 `EnumFontFamiliesExW` 挑出第一个已安装的字体，调用 `DuiTheme::SetDefaultFontFace`；客户端里写死的字体名改为 `i18n::GetUiFontFace()`，它只返回已安装的字体。用户为聊天内容自选的字体属于用户设置，不受影响。

#### 8.5.1 0a 步实测结果（2026-10-03）

实测截图 `snapshots/i18n-font-test.png`、`snapshots/i18n-han-glyphs.png`。本机 Windows 10，120 DPI，界面语言 zh-CN（`GetUserDefaultUILanguage` = 0x0804）。据实证：

1. **雅黑本身没有韩文字形**（`GetGlyphIndicesW` 统计：韩文样例 15 个字全缺），但 GDI `DrawText`、GDI+ 按字体名建字体、GDI+ 由 HFONT 转换三种画法都能补上，没有出现方框。原先「GDI+ 未必能补上」的推测不成立。系统字体链接表里雅黑之后依次挂着 Segoe UI、SimSun、Microsoft JhengHei、Meiryo、Malgun Gothic、Yu Gothic UI。
2. **区域字形差异确实存在。** 「冷」「角」「骨」「直」等字，雅黑与正黑体是中文写法，Yu Gothic UI 与 Malgun Gothic 是日韩写法（见 `i18n-han-glyphs.png`）。日文界面沿用雅黑，日本用户看到的是中文字形。
3. **字体未安装时，GDI+ 按字体名建的字体什么也画不出来**（本机没有 Meiryo UI，图中那一块中间一列整列空白），由 HFONT 转换的那一列排版错乱。所以必须用候选列表、只用已安装的字体。客户端最低支持 Windows 7（`WINVER 0x0601`），据推测 Yu Gothic UI 从 Windows 8.1 起才自带，候选列表里排在其后的 Meiryo UI 用于这种情况。
4. **行高差别很小**：15 像素字号下，雅黑、Yu Gothic UI、Malgun Gothic、Segoe UI 的行高都是 20 像素，正黑体 19 像素。换字体不会让固定行高的控件裁字。
5. **正黑体经字体链接补出的韩文明显偏小**（`i18n-font-test.png` 中 Microsoft JhengHei 一块的 GDI 列）。影响繁中界面下的韩文昵称等用户数据，程度较轻，暂不处理。
6. **英文用 Segoe UI 比雅黑窄约一成**（「Remember password」雅黑 155 像素、Segoe UI 140 像素），行高相同。

#### 8.5.2 译文宽度实测

14 条典型界面文字，用草拟的译文、各语言推荐字体在 15 像素字号下测宽（`DrawText` + `DT_CALCRECT`，与 `DuiLabel` 的测量方式相同），与简体中文（雅黑）相比，据实证：

| 语言 | 平均倍数 | 最大倍数（条目） |
| --- | --- | --- |
| zh-TW | 1.02 | 1.33（群管理 → 群組管理） |
| en-US（雅黑） | 2.01 | 3.24（群管理 → Group management） |
| ja-JP | 1.42 | 2.09（忘记密码？ → パスワードをお忘れですか？） |
| ko-KR | 1.35 | 2.16（忘记密码？ → 비밀번호를 잊으셨나요?） |

英文改用 Segoe UI 后约再窄一成。排版改造（4e 步）以英文为准，日韩通常也能容纳。

### 8.6 balloonui 拟改内容（3d 步给出具体代码，经用户批准后才改）

1. **新增全局文字转换回调。** 新增一个小头文件，提供 `SetTextResolver()`（登记回调）与 `ResolveText()`（转换）；未登记回调时原样返回。`EditContextCommandLabel` 与 `DuiRichEditMenuCommandLabel` 的返回值经它转换。不改的话，非中文界面里普通输入框的右键菜单仍是中文。
2. **默认字体统一取自 `DuiTheme`。** `DuiEdit.cpp:68`、`DuiResMgr.cpp:104`、`DuiAvatar.cpp:379` 改为读取 `DuiTheme` 的默认字体。`DuiTheme` 的默认值仍是微软雅黑，flamingoAdmin 与 DuiGallery 的行为不变。

用户已于 2026-10-04 批准，实施见第 11 节 3d。

## 9. 服务端下发文字的结构化（第 5 期）

- **系统消息**：保留现有的 `text` 字段不变，另加两个字段：`tipkind`（提示类型，如 `member_leave`、`owner_transfer`、`announcement_publish`、`group_welcome`、`relay_join` 等）与 `tipargs`（参数对象，如 `{"from":"张三","to":"李四"}`）。新客户端认得 `tipkind` 时用本地模板生成文字；认不出的类型、以及库里原有的消息，仍显示 `text`。

- **兼容性**：老客户端忽略新字段，显示不变。库里已存的历史系统消息仍为中文，不做迁移。
- **不改的部分**：自动群名、群发助手会话名属于数据，保持服务端生成的中文。
- 协议变更同步写入 `docs/协议设计-v2.md`，服务端补 doctest 用例。

## 12. 风险

1. **英文排版是工作量最大的部分。** 据实证（第 8.5.2 节），14 条典型文字的英文译文平均比中文宽 2.0 倍、最多 3.2 倍；界面代码里有 114 处 `fixedWidth`，按钮、页签、列表右侧时间列都可能被撑破。能改成按内容测量宽度的就改，改不了的加省略号与悬停提示。
2. **翻译质量。** 机器起草的英、日、韩译文必须经母语者审校，界面用语尤其讲究习惯说法。
3. **与并行项目冲突。** 第 2 期要改约 400 个文件，而屏幕共享、文件共享、消息提醒模式、聊天记录管理器等项目都有未提交的改动。第 2 期按模块推进，尽量等对应模块的改动提交之后再动。
4. **插件接口版本。** 第 3 期 FlamingoMedia、FlamingoFileShare 的 `kApiVersion` 加 1 后，exe 与这两个 DLL 必须一起发布（现有规则本来如此）。
