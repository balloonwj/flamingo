# 客户端窗口消息号段规约与整改方案

> 客户端用一大批 `FMG_MSG_*` 自定义窗口消息在网络层、代理窗、主窗口、主面板与各子窗口
> 之间传递事件。这些号是逐个手工分配的，已经撞过多次。本文给出号段规约与整改结果。
>
> 初稿写于 2026-08-14（当时方案尚未实施，号段布局为 1000–2999 那一套）。
> **2026-08-16 按最终决定实施完毕并据实测数据重写本文**：号段改为 4000–4999，
> 守卫测试、`CustomMsgDef.h` 清理、聊天窗私有消息迁移、四处撞号消除、闸门收窄
> 均已完成。文中「已完成」标注的部分是实测结果，不是计划。

---

## 1. 背景：撞号已经发生了多次

整改前的实测数据（2026-08-16 扫描 `#define NAME WM_USER + n` 与
`static const UINT kName = WM_USER + n` 两种写法得出）：

| 文件 | 条数 | 取值范围（相对 `WM_USER`） |
| --- | --- | --- |
| `Source/UserSessionData.h` | 168（含 `FMG_MSG_FIRST` / `FMG_MSG_LAST` 两个哨兵，实际消息 166 条） | 1 – 620 |
| `Source/CustomMsgDef.h` | 41 | 1 – 41 |
| `Source/BalloonChatWnd/BalloonChatWindow.h` | 5 | 1537 – 1541（写成 `WM_USER + 0x601` 这种十六进制） |
| `Source/BalloonChatWnd/BalloonGroupChatWindow.h` | 7 | 1537 – 1543 |

其中有四类问题。

### 1.1 `UserSessionData.h` 内部 4 处撞号

| 数值 | 撞在一起的两条消息 | 当时为什么没有出事 |
| --- | --- | --- |
| `WM_USER + 472` | `FMG_MSG_V2_USERINFO_CHANGED` / `FMG_MSG_OPEN_GROUP_MANAGE` | 前者经代理窗转 `CMainDlg`，后者由群聊窗直投主面板 |
| `WM_USER + 474` | `FMG_MSG_V2_IMAGE_DOWNLOAD_RESULT` / `FMG_MSG_REFRESH_SELF_HEADER` | 同上 |
| `WM_USER + 477` | `FMG_MSG_V2_FILE_SEND_PROGRESS` / `FMG_MSG_OPEN_HISTORY` | 同上 |
| `WM_USER + 552` | `FMG_MSG_V2_SET_REMARK_RESULT` / `FMG_MSG_OPEN_ANNOUNCE_BOX` | 同上 |

四对的形态完全一致：

- 一条是**网络层的应答或推送**，由 `IUSocket` / `ImageTransfer` / `FileTransfer` 投给
  代理窗，经 `CFlamingoClient::ProxyWndProc` 转发给 `CMainDlg`；
- 另一条是**某个窗口请主面板代办的事**，直接 `PostMessage` 到 `m_hostPanel`，由
  `CBalloonMainPanel` 自己的消息映射处理。

也就是说，四处撞号都只是因为「收件窗口恰好不同」而侥幸无害。**这个安全性依赖的是一条
没有任何东西强制的不变量**：这条消息只会投给那一个窗口。谁哪天把其中一条改走另一个
窗口、或者给另一个窗口也登记一次同名处理，立刻就是一次静默失效 —— 不报错、不崩溃、
日志里什么都没有，只能靠人偶然发现。

这类故障本仓库已经吃过亏：2026-08-12 修掉的 `FMG_MSG_LINK_OPTION_CHANGED` 与
`FMG_MSG_CONV_MARK_READ` 同占 `WM_USER + 497`，那一次是真的重叠在同一个窗口上，表现为
某个功能点了完全没反应。

### 1.2 `CustomMsgDef.h` 文件内部自己重号

`WM_TRAYICON_NOTIFY`（文件开头）与 `WM_CLOSE_MSGLOGDLG`（文件末尾）都取 `WM_USER + 1`。
前者由 `MainDlg.h` 的 `MESSAGE_HANDLER_EX` 处理托盘图标通知，后者全仓库零引用。
**同一文件内撞号比跨文件更危险** —— 同文件的消息往往投给同一个窗口。

### 1.3 `CustomMsgDef.h` 里有 5 条零引用的死定义

`WM_DEL_MSG_SENDER`、`WM_SETDLGINITFOCUS`、`WM_SHOW_USERINFODLG`、
`WM_CLOSE_USERINFODLG`、`WM_CLOSE_MSGLOGDLG`。对应界面早已改由 v2 那套窗口实现，
全仓库既没有投递点也没有处理点。

### 1.4 两个聊天窗彼此完全重号

`kRelayoutMsg` / `kSendOnEnterMsg` / `kOpenSendMenuMsg` / `kDoScreenshotMsg` 等在
`BalloonChatWindow.h` 与 `BalloonGroupChatWindow.h` 里取同一批值（`WM_USER + 0x601` 起）。
它们是**窗口投给自己**的消息，各发各的窗口所以无害，但占着公共的 `WM_USER` 段。

## 2. 一个大幅降低改号风险的事实

**全仓库没有任何地方绕过符号名直接写消息数值。** 实测：`grep -rn "WM_USER\s*+\s*[0-9]"`
在客户端自有代码里除上述四个定义文件外零命中（只有 `Source/wtl10.1/` 那套 WTL 库头文件
用裸数字定义标准控件消息，与本仓库的消息号无关）。

因此**改号只需改 `#define` 那一行**，投递点与处理点都用符号名、自动跟着走。真正需要
当心的只有两类改动：删除死定义（要确认真的没人引用）、挪去 `WM_APP` 段（要确认对应
窗口的消息映射与投递点都在同一个窗口内自洽）。

## 3. 核心判断：只划号段解决不了问题

`UserSessionData.h` 里本来就写着提醒新增消息要注意号段的注释，照样撞了多次。**靠人
自觉是靠不住的**，尤其是这类「撞了也不报错」的问题。

因此本方案是**规约 + 守卫两件一起做，且守卫优先**：先让机器能在测试里发现撞号，再谈
号段怎么划、存量怎么搬。

## 4. 号段规约（最终版）

### 4.1 划分维度：按收件方划，不按功能划

撞号**只有在同一个窗口的消息映射里才真正致命**，因此能杜绝事故的划分维度是「谁收」。
功能作为号段内部的二级划分。

### 4.2 号段布局

`WM_USER` 为 `0x0400`（1024），应用可用范围上到 `0x7FFF`（32767），空间充裕。
下表数值均相对 `WM_USER`。

| 段 | 范围 | 收件方 | 内部二级划分 |
| --- | --- | --- | --- |
| **A 网络应答与推送** | 4000 – 4499 | 代理窗 → `CMainDlg` | 每档 100，与 v2 协议 cmd 分组同序（见 4.3） |
| **B 窗口 → 主面板** | 4500 – 4799 | `CBalloonMainPanel` | 按发起窗口分档（见 4.4） |
| **C 主面板 → 子窗口** | 4800 – 4999 | 各具体子窗口 | 按目标窗口分档 |
| **D 窗口投给自己** | 不占本段 | 窗口自身 | 一律走 `WM_APP + n` |

起点定在 4000 而不是更小的数，是为了与存量号段（50 – 620）之间留出明显的空白带 ——
一眼就能看出某个号是整改后按规约取的，还是历史遗留的。

### 4.3 A 段与协议 cmd 号段对齐

| A 段档位 | 对应协议分组 |
| --- | --- |
| 4000 – 4099 | 账号与会话 |
| 4100 – 4199 | 个人资料 |
| 4200 – 4299 | 联系人 |
| 4300 – 4399 | 群组 |
| 4400 – 4499 | 消息与会话列表 |

档位顺序与 `flamingoserver/chatserversrc/Protocol.h` 的 `enum cmd_type` 分组一致
（1000 账号 / 1100 资料 / 1200 联系人 / 1300 群 / 1400 与 1500 消息）。远程桌面、
文件传输、通话、平台公告等分组暂未在 A 段开档，将来需要时按同样口径往后排。

### 4.4 B 段内部分档

| B 段档位 | 发起窗口 |
| --- | --- |
| 4500 起 | 聊天窗 / 群聊窗（`CBalloonChatWindow`、`CBalloonGroupChatWindow`） |
| 4520 起 | 个人资料、系统设置一类的对话框 |
| 4540 起 | 公告提示窗、消息盒子一类的浮窗 |

### 4.5 D 段走 WM_APP 是既有做法，不是新规定

窗口投给自己的消息（去抖、延后一拍这类）本来就不该占公共号段。整改前已有先例：
`WM_APP_REMOVE_ACCOUNT`（`BalloonAuth/BalloonLoginDlg.h`）、
`WM_CONTACT_REMARK_COMMIT`（`BalloonContact/BalloonContactWindow.h`）。
两处的注释都写明了理由：这类消息不经代理窗、不受 `FMG_MSG_FIRST` / `FMG_MSG_LAST`
闸门约束，另起一段最省心。

**目前 `WM_APP` 段已占用的偏移**（新增时避开）：

| 偏移 | 占用者 |
| --- | --- |
| `1` – `3` | `BalloonLoginDlg`、`RdViewerWindow`、`BalloonCallDlg` |
| `0x21`、`0x22` | `BalloonGroupInfoDlg`、`BalloonContactWindow`、`BalloonNetSettingsWindow` |
| `0x31`、`0x32` | `BalloonRegisterWindow` |
| `0x40` – `0x44` | `BalloonChatWindow`（2026-08-16 迁入） |
| `0x50` – `0x56` | `BalloonGroupChatWindow`（2026-08-16 迁入） |
| `0x120` | balloonui `DuiHost::kMsgRelayout` |
| `0x137` – `0x13A` | `BalloonHistoryWindow`、`BalloonAnnounceBoxWindow` |

## 5. 整改执行情况

### 第 1 步：加自动化守卫 —— **已完成**

新增 `Source/Tests/MessageIdRegistryTests.cpp`（Catch2，标签 `[msgid]`，已登记进
`Source/Tests/FlamingoUnit.vcxproj`；该工程没有 `.filters` 文件，无需同步）。

用例在**运行期**解析上述四个头文件（靠 `__FILE__` 推出源码目录，工程为该文件单独加了
`/FC` 让 `__FILE__` 展开成绝对路径；另有一条从测试 exe 位置向上回溯的退路），断言：

- 四个头文件都读得到、都解析得出定义（**读不到直接判失败，不跳过** —— 静默跳过等于
  守卫失效，那正是本次要根治的问题类型）；
- 同一头文件内部不得有两条消息取同一个号；
- 跨头文件取同号必须列入白名单并写明理由；
- `UserSessionData.h` 的消息号都落在 `FMG_MSG_FIRST` / `FMG_MSG_LAST` 闸门区间内；
- `CustomMsgDef.h` 的消息号都落在闸门区间**之外**。

解析器同时认 `WM_USER` 与 `WM_APP` 两种基址，也认 `#define` 与类内 `static const UINT`
两种写法，比较时用加上基址后的绝对值。

**守卫确实能复现撞号的证据**：把两张豁免表临时清空后重新编译运行，`[msgid]` 一组由
「4 用例 342 断言全过」变成「2 用例失败、10 条断言失败」，逐条报出的正是第 1 节列的
5 处文件内撞号与 5 处跨文件撞号。

### 第 2 步：清理 `CustomMsgDef.h` —— **已完成**

复核 5 条定义确实零引用（`.h` / `.cpp` / `.rc` / `.vcxproj` 等全扫，排除构建中间目录；
唯一的其它命中是 Visual Studio 的 `Browse.VC.db` 智能感知缓存，属生成文件）后删除。
`WM_CLOSE_MSGLOGDLG` 一删，文件内那处 `WM_USER + 1` 重号随之消失。剩余 36 条号值无重复。
原处留了一段注释写明删掉的是哪五条、为什么删。同时给该文件补了文件头注释。

### 第 3 步：聊天窗的窗口私有消息挪去 `WM_APP` 段 —— **已完成**

两个聊天窗共 12 条 `WM_USER + 0x60x` 改成 `WM_APP + n`，取值段互不相同：

| 窗口 | 新取值段 | 条数 |
| --- | --- | --- |
| `BalloonChatWindow` | `WM_APP + 0x40` – `0x44` | 5 |
| `BalloonGroupChatWindow` | `WM_APP + 0x50` – `0x56` | 7 |

之所以不用更靠前的 `0x10` / `0x20`：`0x21` / `0x22` 已被另外三个窗口占用，`0x40` / `0x50`
是当前完全空着的两段。改动只落在两个头文件的常量定义上 —— 所有 `MESSAGE_HANDLER` 与
`PostMessage` 调用点都用符号名，自动跟着走；已逐条复核这 12 条消息的投递点全部是
`::PostMessage(m_hWnd, ...)`（窗口投给自己）或由装在自己输入框上的键盘钩子投回自己。

### 第 4 步：消除 `UserSessionData.h` 的 4 处撞号 —— **已完成**

一律**搬走「窗口→主面板」那一条、保留网络应答那一条**（前者不经代理窗，影响面最小）：

| 消息 | 原号 | 新号 | 发起窗口 |
| --- | --- | --- | --- |
| `FMG_MSG_OPEN_HISTORY` | `WM_USER + 477` | `WM_USER + 4500` | 聊天窗 / 群聊窗 |
| `FMG_MSG_OPEN_GROUP_MANAGE` | `WM_USER + 472` | `WM_USER + 4501` | 群聊窗 |
| `FMG_MSG_REFRESH_SELF_HEADER` | `WM_USER + 474` | `WM_USER + 4520` | 个人信息对话框 |
| `FMG_MSG_OPEN_ANNOUNCE_BOX` | `WM_USER + 552` | `WM_USER + 4540` | 新公告提示窗 |

每条都核对了四处：`#define`、投递点、代理窗 `case`、目标窗口的 `MESSAGE_HANDLER`。
这四条**不经代理窗**，因此代理窗那一层本来就没有对应的 `case`，无需改动；处理器全部
在 `BalloonMain/BalloonMainPanel.h` 的消息映射里。

### 第 5 步：收窄闸门 + 写进开发约定文档 —— **已完成**

- `FMG_MSG_FIRST` 由 `WM_USER + 1` 抬到 `WM_USER + 50`。现存 `FMG_MSG_*` 的最小值正是
  `FMG_MSG_NET_ERROR`（`WM_USER + 50`），抬到 50 把 `CustomMsgDef.h` 那批 v1 消息
  （`WM_USER + 1` – `41`）整段排除在代理窗收件范围之外。
- `FMG_MSG_LAST` 由 `WM_USER + 620` 抬到 `WM_USER + 4999`，一次性覆盖 A / B / C 三段，
  免得每加一条消息都要动它。闸门放宽本身无风险：`switch` 里没有匹配 `case` 的消息一律
  走 `default` → `DefWindowProc`，与被闸门挡掉的效果相同。
- 闸门判定在 `Source/FlamingoClient.cpp` 的 `CFlamingoClient::ProxyWndProc` 开头。
- 号段规约写进开发约定文档的「UI 约定」第 6 条。

因为 `FMG_MSG_FIRST` 抬到 50 之后与 `FMG_MSG_NET_ERROR` 同值，守卫用例把
`FMG_MSG_FIRST` / `FMG_MSG_LAST` 当作**哨兵**处理：不参与重号判定，只用来划定
合法区间。

### 第 6 步：清空守卫的豁免名单 —— **已完成**

两张表都只剩结束标记行。留结束标记是因为 C++ 不允许零长度数组，同时也给将来需要
临时豁免时保留了表结构。

### 第 7 步（原方案的「存量迁移」）：**明确不做**

**不把存量 166 条 `FMG_MSG_*` 整体改号。** 其中 4 条已在第 4 步搬进 B 段，剩下
**162 条仍留在历史号段（`WM_USER + 50` – `620`）**，长期如此。

理由：任何一处遗漏都是「编译得过、运行时静默失效」，风险与收益不成比例；而有了第 1 步
的守卫，留在旧号也不会再撞。今后的口径是**新增消息一律按第 4 节的号段取号，存量不动**。

## 6. 今后新增消息的做法

1. 先判断收件方，按 4.2 选段：网络应答与推送进 A 段，窗口请主面板代办进 B 段，
   主面板通知子窗口进 C 段，窗口投给自己走 `WM_APP`。
2. 在段内按 4.3 / 4.4 的档位取一个空号，在 `#define` 后面写清楚 `wParam` / `lParam`
   的含义与堆对象的释放责任。
3. **接满四层**：`#define`、投递点、代理窗 `case`（仅经代理窗中转的消息需要）、目标
   窗口的 `MESSAGE_HANDLER`。漏掉任何一层都不会有编译错误，只会静默失效。
4. 跑一次 `FlamingoUnit.exe "[msgid]"`。
5. 作废某个号时，在原处留一行注释写明它原来是什么，**不要复用**。

## 7. 附：本文数据的复现方法

文中的条数、范围与撞号清单由脚本扫描 `#define NAME WM_USER + n` 与
`static const UINT kName = WM_USER + n` 两种写法得出。复现时注意三点：

- `FMG_MSG_FIRST` 与 `FMG_MSG_LAST` 本身也匹配该模式，统计时应作为哨兵排除；
- 这些头文件是 UTF-8 无 BOM，按 GBK 读会得到乱码的消息名；
- 整改后聊天窗那两个头文件里已经没有 `WM_USER` 系定义了，只扫 `WM_USER` 会得到空结果，
  须同时认 `WM_APP`。

最省事的复现方式是直接跑守卫用例：`FlamingoUnit.exe "[msgid]"`。
