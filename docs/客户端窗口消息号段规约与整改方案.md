# 客户端窗口消息号段规约与整改方案

> 客户端用一大批 `FMG_MSG_*` 自定义窗口消息在网络层、代理窗、主窗口、主面板与各子窗口
> 之间传递事件。这些号是逐个手工分配的，已经撞了四次。本文给出号段规约与分步整改办法。
>
> 本文写于 2026-08-14，所列代码位置与统计数据均由脚本扫描实测得出，**方案尚未实施**。

---

## 1. 背景：撞号已经发生了四次

`flamingoclient/Source/UserSessionData.h` 里现有 **168 条** `FMG_MSG_*` 定义，实际只占用
**164 个数值** —— 差值就是撞号。逐个列出：

| 数值 | 撞在一起的两条消息 | 当前为什么没有出事 |
| --- | --- | --- |
| `WM_USER + 472` | `FMG_MSG_V2_USERINFO_CHANGED` / `FMG_MSG_OPEN_GROUP_MANAGE` | 前者经代理窗转 `CMainDlg`，后者由群聊窗直投主面板 |
| `WM_USER + 474` | `FMG_MSG_V2_IMAGE_DOWNLOAD_RESULT` / `FMG_MSG_REFRESH_SELF_HEADER` | 同上 |
| `WM_USER + 477` | `FMG_MSG_V2_FILE_SEND_PROGRESS` / `FMG_MSG_OPEN_HISTORY` | 同上 |
| `WM_USER + 552` | `FMG_MSG_V2_SET_REMARK_RESULT` / `FMG_MSG_OPEN_ANNOUNCE_BOX` | 同上 |

四对的形态完全一致：

- 一条是**网络层的应答或推送**，由 `IUSocket` / `ImageTransfer` / `FileTransfer` 投给
  代理窗，经 `CFlamingoClient::ProxyWndProc` 转发给 `CMainDlg`；
- 另一条是**某个窗口请主面板代办的事**，直接 `PostMessage` 到 `m_hostPanel`，由
  `CBalloonMainPanel` 自己的消息映射处理。

也就是说，四处撞号都只是因为"收件窗口恰好不同"而侥幸无害。**这个安全性依赖的是一条
没有任何东西强制的不变量**：这条消息只会投给那一个窗口。谁哪天把其中一条改走另一个
窗口、或者给另一个窗口也登记一次同名处理，立刻就是一次静默失效 —— 不报错、不崩溃、
日志里什么都没有，只能靠人偶然发现。

这类故障本仓库已经吃过一次亏：2026-08-12 修掉的 `FMG_MSG_LINK_OPTION_CHANGED` 与
`FMG_MSG_CONV_MARK_READ` 同占 `WM_USER + 497`，那一次是真的重叠在同一个窗口上，表现为
某个功能点了完全没反应。

## 2. 现状：号段是完全交错的

按收件方统计现有消息（脚本扫描 `MainDlg.h` / `BalloonMain/BalloonMainPanel.h` 里的
消息映射得出，含少量注释提及造成的误差，量级可信）：

| 收件方 | 条数 | 数值范围 |
| --- | --- | --- |
| 代理窗 → `CMainDlg` | 约 111 | 50 – 590 |
| `CBalloonMainPanel` | 约 17 | 453 – 562 |
| 其它窗口 / 未在这两处登记 | 约 31 | 120 – 556 |

两大类的取值范围**你中有我、完全交错**。撞号是这种交错的必然结果，不是偶然 —— 只要
新增消息时"顺手取下一个没人用的号"，早晚会与另一类撞上。

另有两点需要一并处理：

1. **存在第二套并行的消息命名空间。** `flamingoclient/Source/CustomMsgDef.h` 里还有
   41 条 v1 遗留消息，占 `WM_USER + 1` 到 `WM_USER + 41`。
2. **代理窗的收件闸门边界画错了。** `FMG_MSG_FIRST` 取 `WM_USER + 1`、`FMG_MSG_LAST`
   取 `WM_USER + 620`，这个区间把上面那 41 条 v1 消息整个罩了进去。目前无害（那些
   消息不投给代理窗），但闸门守的范围与它实际该守的东西并不对应。

## 3. 核心判断：只划号段解决不了问题

`UserSessionData.h` 文件里本来就写着提醒新增消息要注意号段的注释，照样撞了四次。**靠人
自觉是靠不住的**，尤其是这类"撞了也不报错"的问题。

因此本方案是**规约 + 守卫两件一起做，且守卫优先**：先让机器能在构建期发现撞号，再谈
号段怎么划、存量怎么搬。守卫一旦到位，后面每一步都可以从容做，出错也会被立刻拦下。

## 4. 分步整改

### 第一步：加自动化守卫（优先做，单独就能封住问题）

在 `FlamingoUnit` 测试工程里加一条测试，解析 `UserSessionData.h` 与 `CustomMsgDef.h`，
断言三件事：

- 所有消息号**互不重复**；
- 每条消息落在它所属号段的范围内（号段定义见第 5 节）；
- A 段（网络应答与推送）的消息号都落在代理窗闸门区间内。

现存的 4 处撞号先进豁免名单，避免一上来整片飘红；第二步做完即清空该名单。

这一条单独就把问题封住了：此后任何人新增撞号的消息，测试立刻失败并指出与谁撞了。

### 第二步：消除现存 4 处撞号

只需改动 4 个数值，改动面很小。但**每搬一条都必须同时改四个地方**：

1. `UserSessionData.h` 里的 `#define`；
2. 投递点（`PostMessage` / `SendMessage` 的调用处）；
3. 代理窗 `CFlamingoClient::ProxyWndProc` 里的 `case`（仅 A 段消息有这一层）；
4. 目标窗口消息映射里的 `MESSAGE_HANDLER` / `MESSAGE_HANDLER_EX`。

**漏掉任何一处都不会有编译错误，只会静默失效。** 这正是本仓库既有约定"客户端窗口消息
要接满四层"的由来。改完清空第一步的豁免名单。

### 第三步：确立号段规约并写进开发约定文档

规约见第 5 节。同时把代理窗闸门收窄到只覆盖 A 段 —— 它本来就只该守那批经它转发的
消息。

### 第四步：存量迁移（可选，分批，随时可停）

**不建议一次性把 168 条全部改号。** 任何一处遗漏都是"编译得过、运行时静默失效"，风险
与收益不成比例。务实的做法是：

- 新增消息一律按新号段分配；
- 存量按功能域分批搬迁，每批搬完跑一次回归；
- 不着急的批次可以长期留在旧号上 —— 有了第一步的守卫，留在旧号也不会再撞。

## 5. 号段规约

### 5.1 划分维度：按收件方划，不按功能划

撞号**只有在同一个窗口的消息映射里才真正致命**，因此能杜绝事故的划分维度是"谁收"。
功能作为号段内部的二级划分。

### 5.2 号段布局

`WM_USER` 为 `0x0400`（1024），应用可用范围上到 `0x7FFF`（32767），空间充裕，因此号段
可以划得宽松、留足余量。下表数值均相对 `WM_USER`。

| 段 | 范围 | 收件方 | 内部二级划分 |
| --- | --- | --- | --- |
| **A 网络应答与推送** | 1000 – 2999 | 代理窗 → `CMainDlg` | 与 v2 协议 cmd 分组对齐（见 5.3） |
| **B 窗口 → 主面板** | 3000 – 3499 | `CBalloonMainPanel` | 按发起窗口分档 |
| **C 主面板 → 子窗口** | 3500 – 3999 | 各具体子窗口 | 按目标窗口分档 |
| **D 窗口投给自己** | 不占本段 | 窗口自身 | 一律走 `WM_APP + n` |

### 5.3 A 段与协议 cmd 号段对齐

A 段内部按 v2 协议 `enum cmd_type` 的分组同序排布：

| A 段档位 | 对应协议分组 |
| --- | --- |
| 1000 – 1099 | 账号与会话 |
| 1100 – 1199 | 个人资料 |
| 1200 – 1299 | 联系人 |
| 1300 – 1399 | 群组 |
| 1400 – 1599 | 消息与会话列表 |
| 1700 – 1799 | 远程桌面 |
| 1800 – 1899 | 文件与文件夹传输 |
| 1900 – 1999 | 音视频通话、客户端升级 |
| 2100 – 2199 | 平台公告 |

这样看到 `WM_USER + 1217` 就知道它是联系人段某条命令的应答，认知成本为零，也不必再去
翻表确认某个号属于哪个功能。

### 5.4 D 段走 WM_APP 是既有做法，不是新规定

窗口投给自己的消息（去抖、延后一拍这类）本来就不该占公共号段。本仓库已有先例：

- `WM_APP_REMOVE_ACCOUNT`（`BalloonAuth/BalloonLoginDlg.h`）
- `WM_CONTACT_REMARK_COMMIT`（`BalloonContact/BalloonContactWindow.h`）

两处的注释都写明了理由：这类消息不经代理窗、不受 `FMG_MSG_FIRST` / `FMG_MSG_LAST` 闸门
约束，另起一段最省心，也不会与那批撞号。规约只是把这条既有做法明确下来。

## 6. 实施顺序建议

第一步到第三步都是小改动，可以连着做完；第四步随时可停。

1. 加守卫测试（含存量豁免名单）
2. 消除 4 处撞号，清空豁免名单
3. 号段规约写进开发约定文档，代理窗闸门收窄到 A 段
4. 新增消息按新段分配；存量分批搬迁（可长期搁置）

## 7. 附：本文数据的复现方法

文中的条数、范围与撞号清单由脚本扫描 `#define FMG_MSG_xxx WM_USER + n` 得出。复现时
注意两点：`FMG_MSG_FIRST` 与 `FMG_MSG_LAST` 本身也匹配该模式，统计时应排除；
`UserSessionData.h` 是 UTF-8 文件，按 GBK 读会得到乱码的消息名。
