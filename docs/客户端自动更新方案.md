# 客户端自动更新方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-08-11
> 用途：记录把 PC 客户端的自动更新从 v1 时代遗留的那套死链路，重做成 v2 协议下一个正常业务的方案、分期路线与开发步骤。含 `FlamingoUpdater` 更新器的完整重写设计。后续每步开工前据此细化、收尾后回填实际结果。
> 体例沿用 `docs/群公告接入方案.md`：结论一律标注来源，「据实证」必附文件:行号，「据推测」表示尚未验证。

---

## 1. 背景与目标

本方案的目标：

- 把检查更新做成 v2 协议下的一个普通业务，走 chatserver 的正常信令通道，升级包走 fileserver 的正常下载通道，不再有任何独立于 v2 之外的私有机制。
- 检查更新与下载升级包**都要能在未登录状态下完成**，否则"版本过低被拒绝登录"的用户将无路可走。
- 更新器 `FlamingoUpdater` 完整重写，去掉历史遗留依赖，并补上现在完全没有的失败回滚与日志。
- 升级失败时客户端必须还能启动。这是硬要求，宁可升级不成功，不可把客户端弄成半个程序。

## 3. 总体设计

### 3.1 数据流

```
        ┌─────────────────────────────────────────────┐
        │ 发布侧：打包 zip → 放进升级包目录 →          │
        │ 控制台扫描并发布（版本表插一行）             │
        └─────────────────────────────────────────────┘
                              │
   ① cmd_check_update(1905)   │  ② 应答带 版本 / 说明 / MD5 / 大小
      {platform, version}     ▼     / downloadtoken / fileserver 地址
   客户端 ───────────────► chatserver
        │
        │ ③ 用 ② 里的令牌直连 fileserver，
        │    FileStreamTransfer::downloadFile 分片下载 + 校验 MD5
        ▼
   <程序目录>/update/Flamingo-<版本号>.zip
        │
        │ ④ 拉起 FlamingoUpdater.exe，主进程退出
        ▼
   FlamingoUpdater：等主进程退出 → 备份 → 解压覆盖 → 成功则重启主程序
                                      └ 失败则回滚并提示
```

### 3.2 三个关键设计决策

**决策一：1905 的应答直接带下载令牌，不返回 `fileid` 让客户端再走一次 1802。**

`docs/协议设计-v2.md` 10.12 的草案是返回 `fileid`，客户端据此再申请下载。本方案改为在检查更新的应答里直接下发令牌，理由有两条：

- 省一次往返。
- 更重要的是，`cmd_request_download(1802)` 是登录后才放行的命令（见决策二），而检查更新必须在未登录时可用。既然 chatserver 自己持有 `filetokenkey`，直接签一枚令牌没有任何障碍。

`docs/协议设计-v2.md` 的 10.12 节已按本方案改写。

**决策二：`cmd_check_update` 必须放进登录前的白名单。**

`ChatSession.cpp:290-330` 的分发逻辑是：登录前只放行登录、心跳、注销、注册、短信验证码、重置密码（以及按本决策加入的 1905），其它命令一律记日志并断开连接。如果不放行 1905，那么一个版本过低、被 `error_code_version_too_old` 拒绝登录的客户端，将既无法登录也无法检查更新，只能靠用户自己去官网下载，自动更新形同虚设。

未登录时签发的令牌，其载荷里的 `uid` 字段填 0。令牌本身有 HMAC 签名与过期时间（`utils/FileToken.h:9-13`），不会因为 uid 为 0 而降低安全性；升级包对所有人都是同一份公开内容，也不存在越权问题。

**决策三：升级包用整包覆盖的单个 zip，不做分包增量。**

老流程是"版本清单 + 多个分包 zip + 按文件时间戳逐项跳过"的模型。整包的代价是包体更大，换来的是逻辑简单、可整体校验 MD5、可整体回滚。考虑到本项目的发版频率，这个交换是划算的。将来若包体大到不可接受，再在此基础上加差分包，届时协议里的 `packagetype` 字段可以扩展（本期先不加，留待需要时再说，避免过早设计）。

## 4. 服务端改动

### 4.1 新增 `t_client_version` 表

放数据库而不是放配置文件，理由是企业版最终一定要在控制台上发版；表结构先立住，可以免掉一次数据迁移。

按仓库约定，改的是 `flamingoserver/table_mysql.sql`（权威源），改完跑 `flamingoserver/tools/gen_table_sqlite.py` 重新生成 `table_sqlite.sql` 与 `sqliteapi/SqliteSchema.cpp`，这两个是生成物，绝不手改。

字段设计见[附录 B](#附录-b表结构)。取数规则：按 `f_platform` 过滤，在 `f_enabled = 1` 的记录里取 `f_publish_time` 最大的一条作为当前最新版本。

同时要在 `mysqlmgr/MysqlManager.cpp` 里登记这张表，启动时由 `ensureTable` 在表不存在时建表。2026-10-09 起已有的表不再自动补列，表结构有变化时须手工修改已有的库。

### 4.2 新增 `chatserversrc/UpdateProtocol.{h,cpp}`

与 `LoginProtocol` 同构：请求解析、应答组装做成纯逻辑静态方法，放进 `flamingoserver/tests` 单测；`ChatSession::onCheckUpdate` 只负责查表、签令牌、调组包。

请求与应答的 JSON 见[附录 A](#附录-a协议报文)。

### 4.3 把 1905 加进登录前白名单

在 `ChatSession.cpp:292-321` 那一组 `case` 里增加 `cmd_check_update`，与 `cmd_register` / `cmd_send_sms_code` / `cmd_reset_password` 并列。登录后收到 1905 也要能正常处理（同一个处理函数，只是签令牌时 uid 填真实 userid）。

### 4.4 新增文件场景 `file_scene_update = 5`

- `chatserversrc/Protocol.h:1062` 起的 `enum file_scene` 增加一项，按仓库规范逐条写中文注释。
- `utils/FileToken.cpp:160` 的 `isFileScene` 把它算进 fileserver 一侧（不是 imgserver）。

fileserver 那道场景门禁**不需要另外改**：`fileserversrc/FileSession.cpp:77` 的 `isSceneAllowedOnServer` 只是按服务器种类委托给 `FileToken::isImageScene` / `isFileScene`（`:79-82`），改了后者它自动跟随。**据实证**，全仓 `isFileScene` 在产品代码里只有这一个调用点（其余是 `tests/test_filetoken.cpp` 与 `tests/test_filestoremanager.cpp` 里的测试引用），所以这次扩展没有其它影响面。

> **部署注意：`fileserver` 与 `imgserver` 必须跟 `chatserver` 一起重新编译发布。** `isFileScene` 是编进这两个进程各自的二进制里的，光换 chatserver 不换 fileserver，新签出的升级包令牌会被 fileserver 以 `error_code_permission_denied`（"scene not allowed on this server"）挡掉。**据实证**，S1 联调时正是踩到这个：沙箱里用的是 8 月 3 日的旧 `fileserver.exe`，下载第一次就被拒，换成当天重编的二进制后立刻通过。

### 4.5 最低版本号改为从表读

原先 `ChatSession.cpp` 里的硬编码常量 `MIN_CLIENT_VERSION` 改为读版本表的 `f_min_version`，这样"登录拦截"与"强制升级"是同一份配置驱动的，不会出现两边打架。读不到记录时退回编译期兜底常量 `MIN_CLIENT_VERSION_FALLBACK`（`ChatSession.cpp:117`）。

### 4.6 强制升级开关 `f_forced`

`t_client_version` 增加一列 `f_forced`（0 否 / 1 是），控制台发布版本时可直接勾选。

之所以不复用 `f_min_version` 来表达"必须升级"：那一列是**版本门槛**，语义是"低于它的
客户端连登录都不放行"，把它抬高到当前版本会连带影响别的判断，也没法表达"这个版本必须装，
但旧版本仍可登录"。两者相互独立，`cmd_check_update` 里**任一命中即下发 `forced = true`**：

```cpp
const bool forced = (info.forced != 0)
                 || !LoginProtocol::isVersionAtLeast(req.version, info.minVersion);
```

改 `table_mysql.sql` 之后按仓库约定重跑了 `tools/gen_table_sqlite.py`（`table_sqlite.sql` 与
`sqliteapi/SqliteSchema.cpp` 是生成物），并在 `mysqlmgr/MysqlManager.cpp` 里登记该列。
2026-10-09 起启动时不再给已有的表补列，已有的库加列须手工执行 SQL。

> 读取端有个容易踩的地方：`ClientVersionManager::readRecord` 是**按下标**读列的，而
> `f_forced` 插在 `f_enabled` 之前，故其后各列下标整体后移一位。列清单常量
> `CLIENT_VERSION_COLUMNS` 与该函数必须同步改，改一处漏一处会读串列且不报错。
> 落地后用控制台接口做过一次写入-读回验证，各字段未错位。

## 5. 客户端改动

### 5.1 版本号收口到一处

新增 `Source/ClientVersion.h`，定义版本号与 build 号常量，`net/IUSocket.cpp` 的 `kClientVersionV2` 与 `UI/BalloonMain/AboutDlgModel.h` 都改成引用它。

`flamingo.rc` 的版本资源也一并收口：资源脚本本身没法引用 C++ 常量，但可以 `#include` 同一个头文件——`ClientVersion.h` 里额外给出逗号形式的 `FLAMINGO_CLIENT_VERSION_RC`（供 `FILEVERSION` / `PRODUCTVERSION`）与字符串形式的 `FLAMINGO_CLIENT_VERSION_RC_STR`（供 `VALUE "FileVersion"` / `VALUE "ProductVersion"`），`flamingo.rc` 顶部的生成区与 `TEXTINCLUDE 2` 块里各加一行 `#include "ClientVersion.h"`（后者是为了资源编辑器重新生成 `.rc` 时不把前者弄丢）。**发版时只改 `ClientVersion.h` 一个文件即可，exe 文件属性会跟着变。**

这里有个坑值得记一笔：`ClientVersion.h` <u>必须保持 CRLF 换行</u>。`rc.exe` 只把 CRLF 当换行，纯 LF 的头文件在它眼里是一整行，于是第一个 `//` 注释就把后面所有 `#define` 一路吞到文件末尾，宏一个都定义不了，报 `error RC2104: undefined keyword or key name: FLAMINGO_CLIENT_VERSION_RC`；而同一个文件 `cl.exe` 编译毫无问题（cl.exe 认 LF），很容易往错误方向排查。该约束已写进 `ClientVersion.h` 的文件头注释。

### 5.2 新增 `net/UpdateProtocolClient.{h,cpp}`

按 `net/` 目录现有惯例（参照 `FileProtocolClient`）写 1905 的请求组包与应答解析，做成无状态静态方法，配单测。

版本号比较也放这里做成纯函数。服务端 `LoginProtocol::isVersionAtLeast`（`LoginProtocol.cpp:125`）有现成实现，测试用例在 `tests/test_loginprotocol.cpp:93-99`，客户端照抄一份即可（两端不共享代码，这是本仓库既有的做法）。

### 5.3 新增 `Source/Feature/Update/UpdateManager.{h,cpp}`

（起草时位于 `Source/Update/`，2026-08-18 目录重排后移入 `Source/Feature/Update/`。）一条串行工作线程，跑完整流程：

1. 发 1905，等应答（沿用 `CIUSocket::HandleV2Frame` 按 seq 转交等待槽的既有机制，与 `FileTransfer` 同构）。
2. 应答说有更新，就起一条独立的 fileserver 连接（复用 `FileServerConn` 那种 `IFileFrameChannel` 实现）。
3. 调 `FileStreamTransfer::downloadFile` 下载到 `<程序目录>\update\Flamingo-<版本号>.zip`。MD5 校验与原子落地它内部已经做了，不需要重复实现。
4. 回投进度与结果消息给 UI。
5. 用户确认后拉起 `FlamingoUpdater.exe`，然后主进程退出。

**注意**：新增的 `FMG_MSG_*` 窗口消息要把四层都接上，实践中最容易漏掉代理窗那一层，症状是网络层明明跑完了、界面却一动不动。

#### 5.4.1 纯逻辑层 `Source/Feature/Update/UpdateViewModel.{h,cpp}`

（起草时位于 `Source/Update/`，2026-08-18 目录重排后移入 `Source/Feature/Update/`。）窗口只负责"把状态摆出来"，**决定摆成什么样的逻辑全部抽成纯函数**放在这里，不依赖
HWND / balloonui / 业务对象，可被 `FlamingoUnit` 直接断言。做法与既有的
`UI/BalloonMain/AboutDlgModel.h` 一致。三组函数：

```cpp
namespace update {

//升级窗的四种形态
enum UpdateViewKind
{
    update_view_has_update = 0,   //有可用新版本，可下载（非强制）
    update_view_forced     = 1,   //有可用新版本且强制升级
    update_view_latest     = 2,   //已是最新版本
    update_view_failed     = 3,   //检查失败（超时 / 没连上 / 服务端报错）
};

//升级窗要呈现的完整状态；窗口按它摆控件，不自己做判断
struct UpdateViewState
{
    UpdateViewKind kind;             //形态
    bool           showLaterButton;  //是否显示「稍后」按钮
    bool           closable;         //窗口是否允许关闭
    bool           canDownload;      //是否给「立即更新」入口
    std::wstring   title;            //标题文案
    std::wstring   versionLine;      //版本行文案（无更新 / 失败时为空）
};

//由一次检查更新的结果推出升级窗该显示什么
UpdateViewState BuildUpdateViewState(const UpdateTaskResult& r);

//下载进度百分比（0~100）
int ComputeDownloadPercent(long long received, long long total);

//这次检查结果是否应当拦住登录
bool ShouldBlockLogin(const UpdateTaskResult& r);

} // namespace update
```

三个要点，都是容易写错、故意用测试钉住的地方：

- `BuildUpdateViewState` 对「服务端说有更新、但包信息不全」（`HasUsableUpdate()` 为
  false，即缺令牌 / MD5 / 大小）一律按**无更新**处理，不给下载入口 —— 下了也校验不过。
- `ComputeDownloadPercent` 的 `total` 为 0 时返回 0 而不是除零崩掉；`received` 大于
  `total`（异常）钳到 100；中间量用 64 位算，3 GiB 级别的包 `received * 100` 在 32 位下
  会溢出。
- `ShouldBlockLogin` 只在**强制升级**时返回 true。检查失败 / 超时一律放行 —— 不能因为
  检查更新这条链路挂了就把人挡在门外。

#### 5.4.2 线程与进度回传

`UpdateManager` 跑在自己的工作线程上，**绝不能直接碰控件**。做法是窗口把自己的 `HWND`
交给 `UpdateManager`，工作线程用 `PostMessage` 把进度与结果抛回 UI 线程：

| 消息 | 编号 | 载荷 |
| --- | --- | --- |
| `FMG_MSG_UPDATE_PROGRESS` | `WM_USER + 556` | `lParam` = 堆上的 `update::UpdateProgressInfo*`，UI 线程处理后 `delete` |
| `FMG_MSG_UPDATE_RESULT` | `WM_USER + 557` | `lParam` = 堆上的 `update::UpdateTaskResult*`，同上 |

（定义在 `Session/UserSessionData.h`。）载荷走"堆上结构体指针 + UI 线程
delete"这一既有约定（与 `FMG_MSG_V2_*` 那批一致），**不要**把 `int64` 塞进
`wParam` / `lParam` —— Win32 配置下这两个参数是 32 位的，大于 4 GiB 的包会被截断，而本
仓库四个配置都要能编。

`UpdateManager` 内部实现一个 `net::IDownloadProgressSink`（接口见
`net/ImageDownloadDriver.h`），在 `onProgress(received, total)` 里发上面那条进度消息；
`DoDownload` 把它（`DownloadProgressRelay`）传给 `FileStreamTransfer::downloadFile`。

> 这两条消息**不走主面板代理**。升级窗是独立顶层窗口，`UpdateManager` 直接
> `PostMessage` 到它的 `HWND` 即可，不必像其它 `FMG_MSG_*` 那样在主面板 / 代理窗里
> 逐层转发 —— 那条路子漏一层的典型症状是"网络通了但界面不动"。

### 5.5 三个触发点

| 触发点 | 行为 |
| --- | --- |
| 登录窗点击登录 | 先检查再登录。查出可用新版本就弹升级窗并<u>拦住登录</u>；点「稍后」关掉升级窗后自动继续那次登录 |
| 关于页"检查更新"按钮 | 接上真实逻辑（`UI/BalloonMain/BalloonAboutDlg.cpp` 的 `kIdCheckUpdate`）。无更新时仍提示"当前已是最新版本" |
| 登录被拒且错误码为 `error_code_version_too_old` | 直接进升级流程，不让用户卡在登录窗反复重试 |

三个触发点的差别只在**谁来发起**与**发起后怎么处置结果**，检查与下载这条链路是同一条
（`UpdateManager::CheckAndDownload`），不各写一份：

- **检查时机在 2026-08-12 实测后前移**。原设计是"登录成功后静默检查"，实测下来体验不对：
  用户点了登录，主面板已经出来了，升级窗才盖在上面弹出来 —— 该拦的没拦住。现在改成
  <u>点击登录时先查</u>：登录按钮变成「正在检查更新...」并禁用，查完再决定登不登。
  查出可用新版本就弹升级窗、**不登录**；用户点「稍后」关掉升级窗时，升级窗给登录窗投一条
  `FMG_MSG_UPDATE_LOGIN_CONTINUE`，那次登录随即继续。已是最新 / 检查失败一律照常登录。

  强制升级正是靠这条链路生效的：强制时升级窗关不掉，那条"继续登录"的消息就永远发不出去，
  登录也就一直进行不下去 —— 不需要在登录路径上另写一段拦截判断。

  整个进程只查一次（`m_preLoginUpdateChecked`）。否则用户点过「稍后」再点登录会被反复拦住，
  永远进不去。

- 检查更新走的是服务端的登录前白名单，但仍需要一条已建立的连接才能把帧发出去。建连由
  工作线程里的 `CIUSocket::CheckUpdateSync` 自己完成，不在 UI 线程上提前 `Connect()`
  （同步建连在服务器没起来时会让界面卡住约 4 秒，2026-08-14 实测）；连不上时照常放行登录。
- **关于页按钮**投递的是"只查不下"的任务（`CheckAndDownload(false)`），先把结果告诉用户，
  用户点「立即更新」才真下 —— 用户主动点「检查更新」时不该背着他下几十兆的包。
- **登录被拒**这条走的是 `cmd_login` 应答里的 `error_code_version_too_old`：登录窗收到该
  错误码后不停在"密码错误"那类提示上，直接拉起升级窗并按强制形态呈现。

原先的 `#ifndef _DEBUG` 编译期开关已去掉，Debug 构建同样检查更新；登录成功后的静默检查要不要顺带下载，由运行目录 `config/flamingo.ini` 的 `[app] autodownloadupdate` 控制。注意该 ini 必须保持纯 ASCII。

### 5.5.1 实测后的四项调整（2026-08-12）

第一轮真机联调暴露出四个问题，均已修复：

| # | 问题 | 处理 |
| --- | --- | --- |
| 1 | 登录时有升级提示却仍然登了进去 | 检查时机前移到"点击登录时"，见上文 |
| 2 | 强制升级只能靠 `minversion` 间接表达 | 版本表加 `f_forced` 列，控制台发布时可直接勾选，见 [4.6](#46-强制升级开关-f_forced) |
| 3 | 点「立即重启并安装」弹出旧的退出提示框 | 见下 |
| 4 | 升级窗标题栏没有图标、标题是「软件更新」 | 加 app 图标（16×16 合成到标题栏底色），标题改为「FlamingoIM升级提醒」 |

第二轮实测又暴露出两个问题，一并记在这里。

**升级窗必须相对被挡窗口模态。** 第一版把登录拦住的做法是"整个进程只检查一次"
（`m_preLoginUpdateChecked`），但升级窗是非模态的 —— 用户再点一次登录按钮就会跳过检查
直接登进去，闸门形同虚设。现在改为登记被挡窗口并 `EnableWindow(FALSE)`：

| 场景 | 被挡的窗口 | 关闭升级窗后 |
| --- | --- | --- |
| 点击登录时查出可用新版本 | 登录窗 | 恢复可用，并续上那次被拦下的登录 |
| 登录后查出<u>强制</u>升级 | 主面板 | 恢复可用（没有待续的登录） |
| 登录后查出非强制升级 | 不挡 | —— 那只是个提示，不该妨碍人干活 |

强制升级时升级窗关不掉，被挡窗口也就一直处于禁用状态，这正是"不升级就不能用"要的效果。
代价是用户没有任何正常退出途径，所以强制形态下「稍后」按钮位置换成「**退出程序**」——
要拦的是"不升级还接着用"，不是"不让人走"。

**登录前后的退出路径不能混用**（这条踩了一次崩溃）。点「退出程序」最初一律投
`FMG_MSG_EXIT_FOR_UPDATE` 给主窗口、由它 `CloseDialog` 收尾。登录后没问题，登录前却会崩：

```
Debug Assertion Failed!  atlwin.h:4066   Expression: ::IsWindow(this->m_hWnd)
```

原因是 `StartLogin`（当时在 `CMainDlg`，现在在会话控制器 `CSessionController`，`UI/BalloonMain/MainPanelSessionController.cpp`）里有这么一段 —— 登录窗 `DoModal` 返回非 IDOK 时会调
`CloseDialog(IDOK)`。于是收尾走了两遍：本窗口先请主窗口 `CloseDialog`，它
`PostQuitMessage` 让登录窗的模态循环退出、`DoModal` 返回 IDCANCEL，`StartLogin` 见状
又调一次 `CloseDialog`，第二次对着已经销毁的窗口调 `DestroyWindow`，触发断言。

现在按所处阶段分流（`RequestApplicationExit`）：登录前把 `WM_CLOSE` 投给登录窗，让它自己
退出模态循环，收尾由 `StartLogin` 统一做一次；登录后才投 `FMG_MSG_EXIT_FOR_UPDATE`。
「立即重启并安装」那条路同理 —— 它原先也是无条件投给主窗口，同样会在登录前崩。

**问题 3 的来龙去脉值得记一笔。** 升级窗原先用 `WM_CLOSE` 请主窗口退出，而主窗口的 `OnClose`
会先弹「退出程序还是最小化到托盘？」。用户若选「最小化」，主进程不退出，更新器按 `--pid`
等满 30 秒后放弃 —— **一个文件都没动**（安全兜底按设计生效了），但用户还以为在升级。
实测日志：

```
[21:13:15] ======== 更新器启动 ========
[21:13:45] FlamingoIM 仍在运行，升级已取消。请关闭程序后重试。
[21:31:08] ======== 更新器退出（等待主进程超时）========
```

改为专用消息 `FMG_MSG_EXIT_FOR_UPDATE`（`WM_USER + 499`），由主面板的会话控制器
（`CSessionController::OnExitForUpdate`）收到后直接退出，不再询问。

## 6. FlamingoUpdater 重写

### 6.2 依赖取舍

- **`wldef.h` / `wlconfig.h`：整个删除。** 新程序不再读 `update.version` 清单，所有配置从命令行进来，`wl_config` 失去存在意义。
- **`unzip.cpp` / `comutil`：删除，改用仓库里已有的 zlib 1.2.11。** **据实证**，`flamingoclient/Source/third-party/zlib1.2.11/` 是完整的 zlib 源码，主工程已经在编译它（`Source/Flamingo.vcxproj:1465` 起）。只做解压的话需要其中 6 个 `.c`：`adler32`、`crc32`、`inffast`、`inflate`、`inftrees`、`zutil`。zip 的容器格式（中央目录 + 本地文件头 + raw deflate 数据）自己写，约两百行，逻辑直白且好单测。这样既不引入新的第三方库，也不用继续背那 4236 行老代码。
- **`_bstr_t`：删除**，全程宽字符，不再有 ANSI 转换环节。

### 6.3 文件结构

```
FlamingoUpdater/
  Main.cpp                入口：解析参数 → 等待主进程退出 → 解压 → 重启
  CommandLine.{h,cpp}     命令行解析（纯逻辑，可单测）
  ZipReader.{h,cpp}       中央目录解析与条目定位（纯逻辑、零依赖，可单测）
  ZipInflate.{h,cpp}      调 zlib 解压单个条目 + CRC 校验
  ZipPathSafety.{h,cpp}   zip 内路径的安全校验与归一化（纯逻辑，可单测）
  Installer.{h,cpp}       备份 / 覆盖 / 回滚
  UpdateLog.{h,cpp}       写 update/update.log
```

> 落地时把原计划的 `ZipReader` 一拆为二：容器格式解析留在 `ZipReader`，真正调 zlib 的
> inflate 挪到 `ZipInflate`。这样 `ZipReader` 不依赖任何第三方库，可以直接编进
> `FlamingoUnit` 测试工程；否则测试工程要连带链上 zlib 才能跑几个解析用例。

### 6.4 命令行契约

```
FlamingoUpdater.exe --zip "<升级包绝对路径>" --target "<安装目录>" --exec "<要重启的exe>" --pid <主进程PID> [--silent]
```

用 `CommandLineToArgvW` 解析，带空格的路径不会出问题。

老版本是遍历进程列表按名字找 `Flamingo.exe`，多开或者改个名就失灵，新版改成按 PID 等待。

### 6.5 执行流程

1. 打开日志文件 `update/update.log`。
2. `OpenProcess(SYNCHRONIZE, ...)` 加 `WaitForSingleObject` 等主进程退出，超时（建议 30 秒）就提示用户手动关闭后重试并退出，**绝不调 `TerminateProcess`**。老版本只等 5 秒，且超时后照样往下走，主进程还没退出就开始覆盖文件，必然失败。
3. 遍历中央目录跑两遍：第一遍只校验（路径安全、目标文件可写、磁盘空间是否够），全部通过才进第二遍真正落盘。
4. 覆盖之前，把每个将被替换的旧文件移动到 `update/backup/<版本号>/`；任何一步失败就按备份回滚。老版本没有任何回滚，中途失败客户端就变成半个程序。
5. 全部成功后删除备份、写日志、启动主程序、退出。

### 6.6 必须处理好的三个细节

**路径穿越。** zip 条目名里出现 `..`、绝对路径、盘符、`\\?\` 前缀的一律拒绝。老代码把安装目录与条目名直接拼起来就写，一个构造过的包能写到系统上任意位置。这条要有单测覆盖。

**条目名编码。** 按 zip 规范，通用位标记 bit 11 置位时条目名是 UTF-8，否则是本地代码页，转宽字符时分别用 `CP_UTF8` 与 `CP_ACP`。打包侧统一带 UTF-8 标记就不会出现中文文件名乱码。

**提权带来的权限继承。** 装在 `Program Files` 下必须要管理员权限。这里有个不容易想到的坑：如果 FlamingoUpdater 自己是被提权拉起来的，它最后用 `CreateProcess` 启动的 Flamingo.exe 会继承管理员令牌，之后这个客户端将收不到从资源管理器拖进来的文件，日常用管理员权限跑 IM 本身也不合适。**据推测**（这是 Windows 完整性级别的通用行为，尚未在本项目实测），解决办法是最后一步不直接 `CreateProcess`，而是借 explorer.exe 的令牌以普通用户身份启动。**这一条必须单独安排一次验证，确认之后再定实现方式，不得凭推测直接写代码。**

### 6.7 工程配置

- 去掉 `comsuppw.lib`，加入 zlib 那 6 个 `.c` 与包含目录。
- 补上 x64 配置，并把 `FlamingoClient.sln` 里那四行映射从 `Debug|Win32` / `Release|Win32` 改成真正的 x64。改之前主程序是 64 位、更新器却是 32 位。
- 字符集保持 Unicode，源码统一用宽字符 API。
- CRT 用静态版（Debug `/MTd`、Release `/MT`），与主程序和各插件 DLL 一致（2026-10-08 起；此前是动态 CRT，在没装 VC++ 运行库的机器上启动不了，见 7.1 末尾）。本工程的源码（含 zlib）全部直接编译进来，不链接外部静态库，不存在 CRT 不匹配的问题。

落地结果（2026-08-12 实测）：四个配置全部编过，产物架构核对为 x64。输出目录按主客户端
的规矩排布 —— 与 `Flamingo.exe` 同处，四个配置分别落在 `flamingoclient/Debug/`、`Release/`、
`Debug_Win32/`、`Release_Win32/`（2026-10-09 起的目录布局），中间目录也按配置分开，避免同名产物与 obj 互相覆盖。另外去掉了工程里遗留的
`_USE_32BIT_TIME_T`（x64 下无效），并统一加上 `/utf-8` —— 新源码带中文注释且是 UTF-8
无 BOM，不加这个开关 MSVC 会按 GBK 读，一个被误解的字节就能让 `//` 注释吞掉下一行代码。

## 7. 发布流程与控制台版本管理

发版由 flamingoAdmin 完成，**不手工改数据库**。升级包本身由运维放到服务器的升级包目录里，控制台不负责上传——这样控制台侧没有大文件传输，服务端也不必为此扩容 HTTP 请求体上限（`HttpSession.cpp:61` 的 `MAX_HTTP_BODY_LENGTH` 是 1 MiB，`:159` 超限直接拒，整包 POST 本就不可能）。

### 7.1 发布一个新版本的完整流程

1. 按下面「打包规则」把文件按相对安装根目录的路径打成一个 zip。打包时统一带 UTF-8 文件名标记，中文文件名才不会乱码。
2. 把 zip 丢进服务器的升级包目录。**文件名随便起**，用 `Flamingo-3.3.0.zip` 这种人能看懂的名字即可，不需要改名，也不需要自己算 MD5。
3. 打开 flamingoAdmin 的「客户端版本」页，点「扫描」，从列出的候选包里选中刚放进去的那个。MD5 与字节数由服务端算好带出来。
4. 填版本号、最低版本、更新说明。
5. 存成草稿核对无误后再发布；也可以直接发布。

#### 打包规则（2026-10-08 更正）

**更新器的行为（据实证，`FlamingoUpdater/Installer.cpp`）：** 只覆盖或新增包里有的文件，缺的目录自动创建；包里没有的文件原样保留，**从不删除**。所以「放进包里」等于「用包里的版本替换」，「不放」等于「保留用户机器上现有的那一份」。

**每次都必须放进包里的：**

- 安装根目录下的全部 `.exe` 与 `.dll`：`Flamingo.exe`、`FlamingoUpdater.exe`，以及全部 `Flamingo*.dll` 插件（例外只有下面的字幕模型）。**不能只放改过的那几个。** 原因：FlamingoMedia、FlamingoP2P、FlamingoFileShare、FlamingoLock、FlamingoCaption、FlamingoSecretChat、FlamingoScreenshot、FlamingoThreadGroup、FlamingoBot 这 9 个插件都要求接口版本（各自 `*Api.h` 里的 `kApiVersion`）与主程序**完全一致**，参数结构体的大小（`m_cbSize`）也要相等。包里只有新的 `Flamingo.exe` 时，它加载到用户机器上的旧 DLL 会因版本不符而加载失败，对应功能的入口直接隐藏，**不报错、不提示**，极难发现。FlamingoLang、FlamingoOcr、FlamingoMarkdown 按 `m_cbSize` 向后兼容，新旧混用不会加载失败，但同样一并放进去，省得逐个判断。
- 资源目录：目前是 `Face/`、`Image/`、`Sound/`（合计约 1 MiB）。

**可以不放的：**

- **字幕模型 `FlamingoCaptionModel.dll`**：模型与 `FlamingoCaption/Engine/CaptionModelRes.h` 里的资源编号都没有变化时，可以不放，用户机器上现有的那份照常可用。它是纯数据 DLL，没有接口版本。这一项影响很大：按 2026-10-08 的 Debug|x64 产物估算，完整包压缩后约 152 MiB，其中模型一个就占约 124 MiB（解压后约 162 MiB，模型数据几乎不能压缩），不放它包体约 28 MiB（Release|x64 产物约 18 MiB）。不放模型的包装上之后，用户机器上原有的模型文件原样保留（2026-10-09 实测，修改时间精确到毫秒都没变，见第 9 节第二轮验证）。

**绝对不能放进包里的：**

- `config/`：`config/flamingo.ini` 里既有部署方配置的服务器地址、产品名称，也有用户在程序里改过的设置（`[ui] language` 界面语言、`[screenshot]` 截图热键等）。放进包里会把这些全部改回包里那一份。新版本需要的新配置项必须在代码里有缺省值，不能靠升级包去改 ini。
- 运行期数据：`Users/`（各账号的聊天记录库与设置）、`Logs/`、`log/`、`update/`（下载的升级包与更新器日志，更新器自己也在这里放备份）。
- 编译中间产物：`.pdb`、`.ilk`、`.lib`、`.exp`。
- 开发机运行目录里的私有副本与测试产物：`Flamingo_xxx.exe`、`FlamingoMedia_xxx.dll` 之类改了名的副本，以及 `Tests/` 子目录（单元测试程序）。

**架构与配置：**

- 发布用 `Release|x64` 的产物，即 `flamingoclient/Release/`。这个目录本身就带全套资源（`Face/`、`Image/`、`Sound/` 与 `config/`，与 `flamingoclient/Debug/` 里的一份内容相同，都入库），打包时资源也从这里取。Debug 版（`flamingoclient/Debug/`）不要发出去。
- 检查更新只上报平台 `platform=1`（PC），**服务端不区分 32 位与 64 位**，所有 PC 客户端拿到的是同一个包。因此同一时间只能为一种架构发版，目前只发 x64。

**大小上限：** 更新器把整包一次性读进内存，上限 500 MiB（`Installer.cpp` 的 `kMaxPackageBytes`），超过直接拒绝安装。

**已经装出去的老更新器：** 客户端启动的是安装目录里**现有的** `FlamingoUpdater.exe`，不是升级包里的新版本。2026-10-08 之前编出来的更新器使用动态 CRT（Release 依赖 `VCRUNTIME140.dll` 等，Debug 依赖只有装了 Visual Studio 才有的调试运行库），在没有这些运行库的机器上启动不了；当天起改为静态 CRT，与主程序和各插件一致。这类老安装只能手工装一次新版本（或先装 VC++ 运行库）。

### 7.2 升级包目录与聊天文件目录分开

新增配置项 `updatecachedir`，**同时出现在 `fileserver.conf` 与 `chatserver.conf`，且必须指向同一个目录**：

- fileserver 从它取包（读）。
- chatserver 从它做扫描，供控制台列候选包（**只读，不写文件**）。

fileserver 按场景选目录：`ResolveDownloadPath(scene, md5, ...)`（`fileserversrc/UpdatePackageIndex.h`）在 `scene == file_scene_update` 时经升级包索引（7.3）反查实际文件，其余场景仍是原来的 `filecachedir` 加 MD5（实现时代替了原计划的 `baseDirForScene`，见第 9 节 A1）。imgserver 复用同一份代码，但 scene=5 会先被 `isSceneAllowedOnServer` 挡掉，给它传空目录即可。

**相对路径的基准两边不一样，这是最容易搞错的地方。据实证**：

| 配置项 | 所在服务 | 相对基准 | 依据 |
| --- | --- | --- | --- |
| `dbpath` | chatserver | **可执行文件所在目录** | `chatserversrc/main.cpp:548-549` 显式调 `apppath::ResolveAgainstDirectory(GetExecutableDirectory(), ...)` |
| `filecachedir` | fileserver | **进程工作目录** | `fileserversrc/main.cpp:98`、`:137` 直接把配置值交给 `FileManager::init`，没有做任何解析 |

`updatecachedir` **统一按可执行文件所在目录解析**（与 `dbpath` 一致），避免再多一种基准。Windows 下两个 exe 都在 `windowsproj/x64/<配置>/`，实际位置就是 `flamingoserver/windowsproj/x64/<配置>/updatecache/`。

### 7.3 fileserver 怎么按 MD5 找到一个人命名的文件

fileserver 对聊天文件是拿令牌里的 MD5 当文件名去开文件的（`filecachedir` 加 MD5），而运维手工放进去的包叫 `Flamingo-3.3.0.zip`，两者对不上。解决办法是给 fileserver 加一份 **`UpdatePackageIndex`（MD5 → 实际文件路径）**：

- 启动时扫一遍升级包目录，逐个算 MD5 建映射。升级包目录里本来就只有几个文件，这点开销可以接受。
- 下载时按令牌里的 MD5 查映射；**查不到就重扫一次再判失败**，这样刚放进去的新包不必重启服务也能被找到。
- 映射按「路径 + 大小 + 修改时间」做失效判断，避免每次都重算 MD5。

两个被否掉的替代方案，记下来免得日后重复讨论：

- **要求运维按 MD5 重命名后再放**：fileserver 零改动，但把"算 MD5 再改名"这件机械活推给了人，正是本次要消除的东西。
- **把文件名塞进令牌**：令牌载荷是 `type|scene|md5|size|uid|expire` 的竖线分隔六段（`utils/FileToken.h:10`），文件名里出现竖线就会把载荷切错，而且要同时改动签发与校验两侧。

### 7.4 控制台的「客户端版本」页

**入口与权限。** `Screen` 枚举加一项，侧栏加一个「客户端版本」，**仅平台超管可见可用**（`admin.enterpriseid == 0`）；企业级管理员调这组接口一律拒绝——客户端版本是平台级资产，不属于任何一家企业。全部写接口沿用既有机制自动写 `t_admin_audit_log`。

**界面。** 一个版本列表加一个「新建版本」按钮。列表列出版本号、平台、最低版本、包大小、发布时间、状态（当前生效 / 已发布 / 草稿）与操作。新建弹窗是纯表单：点「扫描」列出升级包目录里的候选包 → 选一个 → 填版本号、最低版本、更新说明 → 存草稿或直接发布。**没有上传，也就没有进度条。**

**控制台侧的落地情况（A3）：** `Util/AdminApi` 加了六对 `MakeXxxRequest` / `ParseXxxResponse` 与 `FormatPackageSize`；`Screens/ClientVersionsScreen` 是列表页（页头两个按钮是真实 `DuiButton`，表格与行内操作自绘，与 `AuditScreen` 同构）；`Screens/ClientVersionModal` 是新建弹窗（候选包自绘列表 + 三个 `DuiEdit` + 存草稿 / 直接发布）。侧栏入口按 `AdminSession::IsPlatformAdmin()` 决定加不加。

> **自绘控件的 `OnLButtonUp` 千万不要先转交基类。** **据实证**，`DuiControl::OnLButtonUp` 对落在自己矩形内的<u>任何</u>点击都 `NotifyParent(DUIN_CLICK)` 并返回 true（`third-party/balloonui/balloonui/DuiControl.cpp:288-296`）。列表页与弹窗最初都写成"先调基类、返回 true 就不再往下走"，结果自绘的行内操作按钮与候选包行<u>全部点不动</u>，而且因为基类发的是一条不带动作的空通知，表现为"点了完全没反应、也不报错"，极难从现象反推原因。工程里既有的 `AuditScreen` / `GroupModal` 都是直接做自己的命中判定、不调基类——子控件的点击由宿主经 `HitTest` 直接派发给它们本身，根本不经过父控件这个函数。新写自绘控件时照抄它们的形态即可。

> **踩到一次控件 ID 撞号。** 新界面的 ID 最初编在 400 起，而 400-405 早已归平台设置界面（`kIdSettings*`）—— 这正是 `UiIds.h` 里那条既有注释警告过的同一类问题。所幸 `switch` 的 `case` 重复在编译期就报了错；若两个 ID 分处不同 `switch`，它会变成"点了另一个界面的按钮"这种极难查的运行期故障。新 ID 已挪到 430 / 440 段，并把这次的教训补进了注释。

### 7.6 撤回与重新发布

- **撤回**：把该行 `f_enabled` 置 0。此后取到的是其余已发布记录里发布时间最新的那条；若一条都不剩，客户端得到"无更新"。
- **把旧版本重新顶成当前生效**：对那一行先「撤回」再「发布」。发布会把 `f_publish_time` 刷成当前时间，于是它立刻成为取数规则下的"最新发布"。取数规则按发布时间而非版本号，就是为了让这一步不需要改动历史数据。

> 控制台早先有一个「回滚」按钮（对应 `republish.do` 接口），与「发布」在数据层是同一个动作，
> 只是审计日志的 action 名不同。**2026-08-13 按用户要求整个去掉**：那个叫法容易让人以为它能把
> <u>已经升级完的客户端</u>降回旧版本，而它实际上只影响尚未升级的客户端 —— 已装上新版的用户
> 不会被降回去，因为客户端只在"服务端版本比自己新"时才提示升级。真要把已升级的用户拉回来，
> 得把旧版本重新打一个更高的版本号发出去。能力上没有损失：撤回 + 发布两步完全等价。

> **发布时间必须取真毫秒。** `f_publish_time` 是"哪条记录更新"的唯一判据，而服务端各处惯用的 `time(NULL) * 1000` 只有秒级精度。**据实证**，A2 联调时正是踩到这个：同一秒内先发布 3.4.0、再把 3.3.0 重新发布一次，两条记录拿到一模一样的发布时间，随后按 `f_id DESC` 兜底选中了后插入的 3.4.0，**这一步静默失效**且没有任何报错。现改用 `Timestamp::now().microSecondsSinceEpoch() / 1000`（`base/Timestamp.cpp:58-61` 的 `Timestamp::now` 走 `chrono::system_clock`，两个平台都是微秒精度）。残留的理论边界是"同一毫秒内连发两次"，经 HTTP 调用不可能达到，且结果仍是确定的。

### 7.7 应急手段

控制台不可用时仍可直接改库应急，但**不作为常规手段**。本机没有 `sqlite3` 命令行，用 Python 的 `sqlite3` 模块操作，输出中文前先 `sys.stdout.reconfigure(encoding='utf-8')`。chatserver 开着时读写仍然安全（库是 WAL 模式），但**要复制库文件必须用 `Connection.backup()` 做在线备份，不能直接拷文件**。

改用 MySQL 部署时，表结构、取数规则、上述所有填法完全一致。

## 附录 A：协议报文

### A.1 `cmd_check_update`（1905）请求

```json
{
  "platform": 1,
  "version": "3.2.1"
}
```

- `platform`：客户端平台，1 为 Windows PC，2 为 Android（预留）。
- `version`：客户端当前版本号，取自 `ClientVersion.h`。

### A.2 有更新时的应答

```json
{
  "code": 0, "msg": "ok",
  "hasupdate": true,
  "latestversion": "3.3.0",
  "minversion": "3.1.0",
  "forced": false,
  "releasenote": "新增群接龙；修复若干问题",
  "md5": "9f2c8ab1...",
  "size": 38219776,
  "packagename": "Flamingo-3.3.0.zip",
  "downloadtoken": "2|5|9f2c8ab1...|38219776|0|1723363200000.a1b2c3...",
  "server": { "host": "file.flamingo.io", "port": 20001, "tls": false }
}
```

- `forced`：客户端当前版本低于 `minversion` 时为 true，界面上不给"稍后"选项。
- `md5` / `size`：直接喂给 `FileStreamTransfer::downloadFile` 作校验。
- `downloadtoken`：chatserver 现签的下载令牌，类型为下载、场景为 `file_scene_update`；未登录时载荷里的 uid 为 0。
- `server`：字段结构与 `cmd_request_download` 应答一致，客户端解析代码可以复用。

### A.3 无更新时的应答

```json
{ "code": 0, "msg": "ok", "hasupdate": false }
```
