# 客户端自动更新方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-08-11
> 用途：记录把 PC 客户端的自动更新从 v1 时代遗留的那套死链路，重做成 v2 协议下一个正常业务的方案、分期路线与开发步骤。含 `iUpdateAuto` 更新器的完整重写设计。后续每步开工前据此细化、收尾后回填实际结果。
> 体例沿用 `docs/群公告接入方案.md`：结论一律标注来源，「据实证」必附文件:行号，「据推测」表示尚未验证。

---

## 1. 背景与目标

PC 客户端从 v1 时代就带着一套自动更新代码，至今仍在工程里编译，登录时也仍在调用，但整条链路在 v2 改造之后已经不可能跑通了（证据见第 2 节）。与此同时，v2 协议早就给检查更新留好了命令号，客户端的分片下载栈也已经完整可用，"关于"页的检查更新按钮也画好了，缺的只是把这几段接起来，外加一个能用的更新器。

本方案的目标：

- 把检查更新做成 v2 协议下的一个普通业务，走 chatserver 的正常信令通道，升级包走 fileserver 的正常下载通道，不再有任何独立于 v2 之外的私有机制。
- 检查更新与下载升级包**都要能在未登录状态下完成**，否则"版本过低被拒绝登录"的用户将无路可走。
- 更新器 `iUpdateAuto` 完整重写，去掉历史遗留依赖，并补上现在完全没有的失败回滚与日志。
- 升级失败时客户端必须还能启动。这是硬要求，宁可升级不成功，不可把客户端弄成半个程序。

## 2. 现状盘点（据实证，均已核对代码位置）

### 2.1 老链路由三部分组成，且仍在编译

| 组成 | 位置 | 职责 |
| --- | --- | --- |
| 检查入口 | `BalloonLoginDlg.cpp:509-511`（`#ifndef _DEBUG` 包着 `DetectNewVersion()`），实现在 `BalloonLoginDlg.cpp:731-754` | 点登录按钮时触发，Release 构建才走 |
| 版本比对 | `Updater.cpp:19-88` | 下载 `update.version` 清单，与本地 `update2.version` 做字符串比较 |
| 下载与解压 | `UpdateDlg.cpp` 整个文件 | SkinLib 老皮肤库的对话框，逐个下载分包 zip，再调 `Unzip()`（`:243-365`）拉起 `iUpdateAuto.exe` |

两个 `.cpp` 都还挂在主工程里编译（`Flamingo.vcxproj:329-330`）。`Bin/update/update2.version` 也还留着，是那套清单格式的残留。

### 2.2 这条链路已经跑不通

**据实证**，有两处硬性阻断：

1. **协议对不上。** 老的下载走 `CFileTaskThread::DownloadFile`，收的是 v1 的 `msg_type_download_resp`（`FileTaskThread.cpp:538`）。而现在的 fileserver 只认 `cmd_file_upload(1851)` 与 `cmd_file_download(1852)` 两个命令，收到其它任何 cmd 一律记错误日志并关闭连接（`fileserversrc/FileSession.cpp:186-201`）。
2. **寻址方式对不上。** 老流程按文件名下载（`Updater.cpp:36` 传的就是字符串 `"update2.version"`）。而 v2 的 fileserver 把文件按内容 MD5 命名存放在 `filecache` 目录下（`FileSession.cpp:451` 的 `path = m_strFileBaseDir + md5`），并且下载必须携带 chatserver 签发的下载令牌（`FileSession.cpp:426-434` 校验，失败直接回错）。"按文件名取 update.version"这条路径在新服务端根本不存在。

结论：这套代码不是"有 bug 待修"，而是整体作废，本方案直接删除而非改造。

### 2.3 协议位子留好了，服务端一行实现都没有

- `cmd_check_update = 1905` 在两端的 `Protocol.h:221`（服务端 `flamingoserver/chatserversrc/Protocol.h`）与 `Protocol.h:220`（客户端 `flamingoclient/Source/net/Protocol.h`）都已定义。
- `error_code_version_too_old = 4` 同样两端都有（服务端 `Protocol.h:249`）。
- 登录时已经在校验版本：`ChatSession.cpp:525` 调 `LoginProtocol::isVersionAtLeast(req.clientversion, MIN_CLIENT_VERSION)`，不达标就回这个错误码。最低版本是硬编码常量 `MIN_CLIENT_VERSION = "3.0.0"`（`ChatSession.cpp:70`）。
- `docs/协议设计-v2.md` 的 10.12 节写了应答草案。

但**据实证**，全仓 grep `cmd_check_update` 只命中两端 `Protocol.h` 各一行声明，chatserver 里没有任何处理器，客户端也没有任何调用。

### 2.4 可以直接复用的现成能力

v2 的客户端文件下载栈是完整的，本方案不需要写任何新的传输代码：

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| 申请下载令牌 | `net/FileProtocolClient.h:145-157` | `cmd_request_download(1802)` 的组包解包 |
| 流式分片下载 | `net/FileStreamTransfer.h:103-124` 的 `downloadFile` | 已含分片请求、增量算 MD5、校验后原子 rename，全程只占一个分片内存 |
| 独立连接通道 | `net/FileTransfer.h:63-65` 的 `FileServerConn` | 群文件并发池用的 `IFileFrameChannel` 实现，自带 socket，不占主连接 |
| 服务端签发令牌 | `utils/FileToken.h`，`ChatSession::onRequestDownload`（`ChatSession.cpp:4936`） | chatserver 持有 `filetokenkey`（`etc/chatserver.conf:63`），可自行签发下载令牌 |
| 进度条控件 | `balloonui/Controls/Feedback/DuiProgressBar.h` | 升级窗直接用，不需要改 balloonui |

### 2.5 版本号有三处，且互相不一致

**据实证**：

| 位置 | 当前值 | 用途 |
| --- | --- | --- |
| `net/IUSocket.cpp:40` 的 `kClientVersionV2` | `"3.2.1"` | 登录请求里报给服务端的版本号 |

### 2.6 关于页有按钮，但是假的

## 3. 总体设计

### 3.1 数据流

```
        ┌─────────────────────────────────────────────┐
        │ 发布侧：打包 zip → 算 MD5 → 按 MD5 名放进    │
        │ fileserver 的 filecache → 版本表插一行       │
        └─────────────────────────────────────────────┘
                              │
   ① cmd_check_update(1905)   │  ② 应答带 版本 / 说明 / MD5 / 大小
      {platform, version}     ▼     / downloadtoken / fileserver 地址
   客户端 ───────────────► chatserver
        │
        │ ③ 用 ② 里的令牌直连 fileserver，
        │    FileStreamTransfer::downloadFile 分片下载 + 校验 MD5
        ▼
   Bin/update/Flamingo-<版本号>.zip
        │
        │ ④ 拉起 iUpdateAuto.exe，主进程退出
        ▼
   iUpdateAuto：等主进程退出 → 备份 → 解压覆盖 → 成功则重启主程序
                                      └ 失败则回滚并提示
```

### 3.2 三个关键设计决策

**决策一：1905 的应答直接带下载令牌，不返回 `fileid` 让客户端再走一次 1802。**

`docs/协议设计-v2.md` 10.12 的草案是返回 `fileid`，客户端据此再申请下载。本方案改为在检查更新的应答里直接下发令牌，理由有两条：

- 省一次往返。
- 更重要的是，`cmd_request_download(1802)` 是登录后才放行的命令（见决策二），而检查更新必须在未登录时可用。既然 chatserver 自己持有 `filetokenkey`，直接签一枚令牌没有任何障碍。

代价是 `docs/协议设计-v2.md` 的 10.12 节要同步改写，本方案落地时一并更新。

**决策二：`cmd_check_update` 必须放进登录前的白名单。**

现在 `ChatSession.cpp:217-224` 的分发逻辑是：登录前只放行登录、心跳、注册、短信验证码、重置密码，其它命令一律记日志并断开连接。如果不放行 1905，那么一个版本过低、被 `error_code_version_too_old` 拒绝登录的客户端，将既无法登录也无法检查更新，只能靠用户自己去官网下载，自动更新形同虚设。

未登录时签发的令牌，其载荷里的 `uid` 字段填 0。令牌本身有 HMAC 签名与过期时间（`utils/FileToken.h:9-13`），不会因为 uid 为 0 而降低安全性；升级包对所有人都是同一份公开内容，也不存在越权问题。

**决策三：升级包用整包覆盖的单个 zip，不做分包增量。**

老流程是"版本清单 + 多个分包 zip + 按文件时间戳逐项跳过"的模型。整包的代价是包体更大，换来的是逻辑简单、可整体校验 MD5、可整体回滚。考虑到本项目的发版频率，这个交换是划算的。将来若包体大到不可接受，再在此基础上加差分包，届时协议里的 `packagetype` 字段可以扩展（本期先不加，留待需要时再说，避免过早设计）。

## 4. 服务端改动

### 4.1 新增 `t_client_version` 表

放数据库而不是放配置文件，理由是企业版最终一定要在控制台上发版；表结构先立住，可以免掉一次数据迁移。

按仓库约定，改的是 `flamingoserver/table.sql`（权威源），改完跑 `flamingoserver/tools/gen_table_sqlite.py` 重新生成 `table_sqlite.sql` 与 `sqliteapi/SqliteSchema.cpp`，这两个是生成物，绝不手改。

字段设计见[附录 B](#附录-b表结构)。取数规则：按 `f_platform` 过滤，在 `f_enabled = 1` 的记录里取 `f_publish_time` 最大的一条作为当前最新版本。

同时要在 `mysqlmgr/MysqlManager.cpp` 里登记这张表，让 `_CheckTable` 的建表与补列机制覆盖它——这样老库升级不需要手工执行 SQL。

### 4.2 新增 `chatserversrc/UpdateProtocol.{h,cpp}`

与 `LoginProtocol` 同构：请求解析、应答组装做成纯逻辑静态方法，放进 `flamingoserver/tests` 单测；`ChatSession::onCheckUpdate` 只负责查表、签令牌、调组包。

请求与应答的 JSON 见[附录 A](#附录-a协议报文)。

### 4.3 把 1905 加进登录前白名单

在 `ChatSession.cpp:200-215` 那一组 `case` 里增加 `cmd_check_update`，与 `cmd_register` / `cmd_send_sms_code` / `cmd_reset_password` 并列。登录后收到 1905 也要能正常处理（同一个处理函数，只是签令牌时 uid 填真实 userid）。

### 4.4 新增文件场景 `file_scene_update = 5`

- `chatserversrc/Protocol.h:426-432` 的 `enum file_scene` 增加一项，按仓库规范逐条写中文注释。
- `utils/FileToken.cpp:160` 的 `isFileScene` 把它算进 fileserver 一侧（不是 imgserver）。

fileserver 那道场景门禁**不需要另外改**：`fileserversrc/FileSession.cpp:71` 的 `isSceneAllowedOnServer` 只是按服务器种类委托给 `FileToken::isImageScene` / `isFileScene`（`:74-76`），改了后者它自动跟随。**据实证**，全仓 `isFileScene` 只有这一个调用点加一处测试引用（`tests/test_filetoken.cpp:142,151`），所以这次扩展没有其它影响面。

> **部署注意：`fileserver` 与 `imgserver` 必须跟 `chatserver` 一起重新编译发布。** `isFileScene` 是编进这两个进程各自的二进制里的，光换 chatserver 不换 fileserver，新签出的升级包令牌会被 fileserver 以 `error_code_permission_denied`（"scene not allowed on this server"）挡掉。**据实证**，S1 联调时正是踩到这个：沙箱里用的是 8 月 3 日的旧 `fileserver.exe`，下载第一次就被拒，换成当天重编的二进制后立刻通过。

### 4.5 最低版本号改为从表读

`ChatSession.cpp:70` 的硬编码常量 `MIN_CLIENT_VERSION` 改为读版本表的 `f_min_version`，这样"登录拦截"与"强制升级"是同一份配置驱动的，不会出现两边打架。读不到记录时退回一个编译期兜底常量，保持现有行为。

## 5. 客户端改动

### 5.1 版本号收口到一处

新增 `Source/ClientVersion.h`，定义版本号与 build 号常量，`net/IUSocket.cpp:40` 与 `BalloonMain/AboutDlgModel.h:40` 都改成引用它。

`flamingo.rc` 的版本资源也一并收口：资源脚本本身没法引用 C++ 常量，但可以 `#include` 同一个头文件——`ClientVersion.h` 里额外给出逗号形式的 `FLAMINGO_CLIENT_VERSION_RC`（供 `FILEVERSION` / `PRODUCTVERSION`）与字符串形式的 `FLAMINGO_CLIENT_VERSION_RC_STR`（供 `VALUE "FileVersion"` / `VALUE "ProductVersion"`），`flamingo.rc` 顶部的生成区与 `TEXTINCLUDE 2` 块里各加一行 `#include "ClientVersion.h"`（后者是为了资源编辑器重新生成 `.rc` 时不把前者弄丢）。**发版时只改 `ClientVersion.h` 一个文件即可，exe 文件属性会跟着变。**

这里有个坑值得记一笔：`ClientVersion.h` <u>必须保持 CRLF 换行</u>。`rc.exe` 只把 CRLF 当换行，纯 LF 的头文件在它眼里是一整行，于是第一个 `//` 注释就把后面所有 `#define` 一路吞到文件末尾，宏一个都定义不了，报 `error RC2104: undefined keyword or key name: FLAMINGO_CLIENT_VERSION_RC`；而同一个文件 `cl.exe` 编译毫无问题（cl.exe 认 LF），很容易往错误方向排查。该约束已写进 `ClientVersion.h` 的文件头注释。

### 5.2 新增 `net/UpdateProtocolClient.{h,cpp}`

按 `net/` 目录现有惯例（参照 `FileProtocolClient`）写 1905 的请求组包与应答解析，做成无状态静态方法，配单测。

版本号比较也放这里做成纯函数。服务端 `LoginProtocol::isVersionAtLeast`（`LoginProtocol.cpp:111`）有现成实现，测试用例在 `tests/test_loginprotocol.cpp:93-99`，客户端照抄一份即可（两端不共享代码，这是本仓库既有的做法）。

### 5.3 新增 `Source/Update/UpdateManager.{h,cpp}`

一条串行工作线程，跑完整流程：

1. 发 1905，等应答（沿用 `CIUSocket::HandleV2Frame` 按 seq 转交等待槽的既有机制，与 `FileTransfer` 同构）。
2. 应答说有更新，就起一条独立的 fileserver 连接（复用 `FileServerConn` 那种 `IFileFrameChannel` 实现）。
3. 调 `FileStreamTransfer::downloadFile` 下载到 `Bin/update/Flamingo-<版本号>.zip`。MD5 校验与原子落地它内部已经做了，不需要重复实现。
4. 回投进度与结果消息给 UI。
5. 用户确认后拉起 `iUpdateAuto.exe`，然后主进程退出。

**注意**：新增的 `FMG_MSG_*` 窗口消息要把四层都接上，实践中最容易漏掉代理窗那一层，症状是网络层明明跑完了、界面却一动不动。

### 5.4 升级窗用 balloonui 重写

新建 `Source/BalloonUpdate/BalloonUpdateWindow.{h,cpp}`，`DuiFrameWindow` 子类。老的
`CUpdateDlg` 用的是 SkinLib 老皮肤库，随老代码一起删除（见 [5.6](#56-老代码清理)）。

**控件全部是 balloonui 现成件，不需要改 balloonui 库**：

只会让他卡在登录窗反复重试。

#### 5.4.1 纯逻辑层 `Source/Update/UpdateViewModel.{h,cpp}`

窗口只负责"把状态摆出来"，**决定摆成什么样的逻辑全部抽成纯函数**放在这里，不依赖
HWND / balloonui / 业务对象，可被 `FlamingoUnit` 直接断言。做法与既有的
`BalloonMain/AboutDlgModel.h` 一致。三组函数：

```cpp
namespace update {

//升级窗的四种形态
enum UpdateViewKind
{
    update_view_has_update = 0,   //有可用新版本，可下载（非强制）
    update_view_forced     = 1,   //有可用新版本且强制升级
    update_view_latest     = 2,   //已是最新版本
    update_view_failed     = 3,   //检查失败（超时 / 没连上 / 服务端报错）
};

//升级窗要呈现的完整状态；窗口按它摆控件，不自己做判断
struct UpdateViewState
{
    UpdateViewKind kind;             //形态
    bool           showLaterButton;  //是否显示「稍后」按钮
    bool           closable;         //窗口是否允许关闭
    bool           canDownload;      //是否给「立即更新」入口
    std::wstring   title;            //标题文案
    std::wstring   versionLine;      //版本行文案（无更新 / 失败时为空）
};

//由一次检查更新的结果推出升级窗该显示什么
UpdateViewState BuildUpdateViewState(const UpdateTaskResult& r);

//下载进度百分比（0~100）
int ComputeDownloadPercent(long long received, long long total);

//这次检查结果是否应当拦住登录
bool ShouldBlockLogin(const UpdateTaskResult& r);

} // namespace update
```

三个要点，都是容易写错、故意用测试钉住的地方：

- `BuildUpdateViewState` 对「服务端说有更新、但包信息不全」（`HasUsableUpdate()` 为
  false，即缺令牌 / MD5 / 大小）一律按**无更新**处理，不给下载入口 —— 下了也校验不过。
- `ComputeDownloadPercent` 的 `total` 为 0 时返回 0 而不是除零崩掉；`received` 大于
  `total`（异常）钳到 100；中间量用 64 位算，3 GiB 级别的包 `received * 100` 在 32 位下
  会溢出。
- `ShouldBlockLogin` 只在**强制升级**时返回 true。检查失败 / 超时一律放行 —— 不能因为
  检查更新这条链路挂了就把人挡在门外。

#### 5.4.2 线程与进度回传

`UpdateManager` 跑在自己的工作线程上，**绝不能直接碰控件**。做法是窗口把自己的 `HWND`
交给 `UpdateManager`，工作线程用 `PostMessage` 把进度与结果抛回 UI 线程：

| 消息 | 编号 | 载荷 |
| --- | --- | --- |
| `FMG_MSG_UPDATE_PROGRESS` | `WM_USER + 570` | `lParam` = 堆上的 `update::UpdateProgressInfo*`，UI 线程处理后 `delete` |
| `FMG_MSG_UPDATE_RESULT` | `WM_USER + 571` | `lParam` = 堆上的 `update::UpdateTaskResult*`，同上 |

编号接在现有最大号 `WM_USER + 560` 之后取，留出空档。载荷走"堆上结构体指针 + UI 线程
delete"这一既有约定（与 `FMG_MSG_V2_*` 那批一致），**不要**把 `int64` 塞进
`wParam` / `lParam` —— Win32 配置下这两个参数是 32 位的，大于 4 GiB 的包会被截断，而本
仓库四个配置都要能编。

`UpdateManager` 内部实现一个 `net::IDownloadProgressSink`（接口见
`net/ImageDownloadDriver.h`），在 `onProgress(received, total)` 里发上面那条进度消息；
现在 `DoDownload` 给 `FileStreamTransfer::downloadFile` 传的 `nullptr` 换成它。

> 这两条消息**不走主面板代理**。升级窗是独立顶层窗口，`UpdateManager` 直接
> `PostMessage` 到它的 `HWND` 即可，不必像其它 `FMG_MSG_*` 那样在主面板 / 代理窗里
> 逐层转发 —— 那条路子漏一层的典型症状是"网络通了但界面不动"。

### 5.5 三个触发点

| 触发点 | 行为 |

## 6. iUpdateAuto 重写

### 6.1 澄清：它没有依赖 MFC

**据实证**，`iUpdateAuto.vcxproj` 里没有 `UseOfMfc` 设置，源码也没有 include 任何 `afx*`。它实际背着的历史包袱是另外三样：

1. **`wldef.h` / `wlconfig.h`** —— 一份从某个股票行情软件搬来的"winlinux 兼容层"头文件，里面是行情码表 `tagStockIndex`、数据库连接结构 `tagUDBConnInfo`、Level2 报价字段这类与本项目毫不相干的定义，足有六百多行。真正用到的只有几十行的 `wl_config` 文本读取类和一个 `__string_search__` 宏。
2. **`unzip.cpp` / `unzip.h`** —— 4236 行的 Wischik 版 unzip，内嵌了一份 zlib 的 inflate 实现。
3. **`_bstr_t` 与 `comsuppw.lib`**（`iUpdateAuto.cpp:2,5`）—— 仅仅是为了把宽字符路径转成 ANSI 喂给 `OpenZip`。

要砍的是这三样，结果与"去掉历史依赖重写"这个目标一致。

### 6.2 依赖取舍

- **`wldef.h` / `wlconfig.h`：整个删除。** 新程序不再读 `update.version` 清单，所有配置从命令行进来，`wl_config` 失去存在意义。
- **`unzip.cpp` / `comutil`：删除，改用仓库里已有的 zlib 1.2.11。** **据实证**，`flamingoclient/Source/zlib1.2.11/` 是完整的 zlib 源码，主工程已经在编译它（`Flamingo.vcxproj:959` 起）。只做解压的话需要其中 6 个 `.c`：`adler32`、`crc32`、`inffast`、`inflate`、`inftrees`、`zutil`。zip 的容器格式（中央目录 + 本地文件头 + raw deflate 数据）自己写，约两百行，逻辑直白且好单测。这样既不引入新的第三方库，也不用继续背那 4236 行老代码。
- **`_bstr_t`：删除**，全程宽字符，不再有 ANSI 转换环节。

### 6.3 文件结构

```
iAutoUpdate/
  Main.cpp                入口：解析参数 → 等待主进程退出 → 解压 → 重启
  CommandLine.{h,cpp}     命令行解析（纯逻辑，可单测）
  ZipReader.{h,cpp}       中央目录解析与条目定位（纯逻辑、零依赖，可单测）
  ZipInflate.{h,cpp}      调 zlib 解压单个条目 + CRC 校验
  ZipPathSafety.{h,cpp}   zip 内路径的安全校验与归一化（纯逻辑，可单测）
  Installer.{h,cpp}       备份 / 覆盖 / 回滚
  UpdateLog.{h,cpp}       写 update/update.log
```

> 落地时把原计划的 `ZipReader` 一拆为二：容器格式解析留在 `ZipReader`，真正调 zlib 的
> inflate 挪到 `ZipInflate`。这样 `ZipReader` 不依赖任何第三方库，可以直接编进
> `FlamingoUnit` 测试工程；否则测试工程要连带链上 zlib 才能跑几个解析用例。

### 6.4 命令行契约

```
iUpdateAuto.exe --zip "<升级包绝对路径>" --target "<安装目录>" --exec "<要重启的exe>" --pid <主进程PID> [--silent]
```

用 `CommandLineToArgvW` 解析，带空格的路径不会出问题。

老版本是遍历进程列表按名字找 `Flamingo.exe`（`iUpdateAuto.cpp:193-215`），多开或者改个名就失灵，新版改成按 PID 等待。

### 6.5 执行流程

1. 打开日志文件 `update/update.log`。
2. `OpenProcess(SYNCHRONIZE, ...)` 加 `WaitForSingleObject` 等主进程退出，超时（建议 30 秒）就提示用户手动关闭后重试并退出，**绝不调 `TerminateProcess`**。老版本只等 5 秒，且超时后照样往下走（`iUpdateAuto.cpp:212-215`），主进程还没退出就开始覆盖文件，必然失败。
3. 遍历中央目录跑两遍：第一遍只校验（路径安全、目标文件可写、磁盘空间是否够），全部通过才进第二遍真正落盘。
4. 覆盖之前，把每个将被替换的旧文件移动到 `update/backup/<版本号>/`；任何一步失败就按备份回滚。老版本没有任何回滚，中途失败客户端就变成半个程序（`iUpdateAuto.cpp:128-134` 是解压失败只把 `errorUpdate` 置位、继续解下一个）。
5. 全部成功后删除备份、写日志、启动主程序、退出。

### 6.6 必须处理好的四个细节

**路径穿越。** zip 条目名里出现 `..`、绝对路径、盘符、`\\?\` 前缀的一律拒绝。老代码是 `wsprintf(fullpath, TEXT("%s%s"), __main_home__, ze.name)` 拼出来就写（`iUpdateAuto.cpp:120`），一个构造过的包能写到系统上任意位置。这条要有单测覆盖。

**条目名编码。** 按 zip 规范，通用位标记 bit 11 置位时条目名是 UTF-8，否则是本地代码页，转宽字符时分别用 `CP_UTF8` 与 `CP_ACP`。打包侧统一带 UTF-8 标记就不会出现中文文件名乱码。

**提权带来的权限继承。** 装在 `Program Files` 下必须要管理员权限。这里有个不容易想到的坑：如果 iUpdateAuto 自己是被提权拉起来的，它最后用 `CreateProcess` 启动的 Flamingo.exe 会继承管理员令牌，之后这个客户端将收不到从资源管理器拖进来的文件，日常用管理员权限跑 IM 本身也不合适。**据推测**（这是 Windows 完整性级别的通用行为，尚未在本项目实测），解决办法是最后一步不直接 `CreateProcess`，而是借 explorer.exe 的令牌以普通用户身份启动。**这一条必须单独安排一次验证，确认之后再定实现方式，不得凭推测直接写代码。**

**老的提权分支有 bug，顺手清掉。** `UpdateDlg.cpp:280` 的注释写"Vista 以下不存在管理员权限运行程序的方式"，条件却写成 `if (!IsWindowsXPOrGreater())`，与注释对不上。重写时这个分支整个删除，统一走 `ShellExecuteEx` 的 `runas`。

### 6.7 工程配置

- 去掉 `comsuppw.lib`，加入 zlib 那 6 个 `.c` 与包含目录。
- 补上 x64 配置，并把 `FlamingoClient.sln` 里那四行映射从 `Debug|Win32` / `Release|Win32` 改成真正的 x64。改之前主程序是 64 位、更新器却是 32 位。
- 字符集保持 Unicode，源码统一用宽字符 API。

落地结果（2026-08-12 实测）：四个配置全部编过，产物架构核对为 x64。输出目录按主客户端
的规矩排布 —— `Debug|x64` 落在 `Bin\`（与 `Flamingo.exe` 同处），其余三个各有独立目录，
中间目录也按配置分开，避免同名产物与 obj 互相覆盖。另外去掉了工程里遗留的
`_USE_32BIT_TIME_T`（x64 下无效），并统一加上 `/utf-8` —— 新源码带中文注释且是 UTF-8
无 BOM，不加这个开关 MSVC 会按 GBK 读，一个被误解的字节就能让 `//` 注释吞掉下一行代码。

## 7. 发布流程与控制台版本管理

发版由 flamingoAdmin 完成，**不手工改数据库**。升级包本身由运维放到服务器的升级包目录里，控制台不负责上传——这样控制台侧没有大文件传输，服务端也不必为此扩容 HTTP 请求体上限（`HttpSession.cpp:32` 的 `MAX_HTTP_BODY_LENGTH` 是 1 MiB，`:132` 超限直接拒，整包 POST 本就不可能）。

### 7.1 发布一个新版本的完整流程

1. 把需要覆盖的文件按相对安装根目录的路径打成一个 zip（`Flamingo.exe`、`Skins/xxx.png` 之类）。打包时统一带 UTF-8 文件名标记，中文文件名才不会乱码。
2. 把 zip 丢进服务器的升级包目录。**文件名随便起**，用 `Flamingo-3.3.0.zip` 这种人能看懂的名字即可，不需要改名，也不需要自己算 MD5。
3. 打开 flamingoAdmin 的「客户端版本」页，点「扫描」，从列出的候选包里选中刚放进去的那个。MD5 与字节数由服务端算好带出来。
4. 填版本号、最低版本、更新说明。
5. 存成草稿核对无误后再发布；也可以直接发布。

### 7.2 升级包目录与聊天文件目录分开

新增配置项 `updatecachedir`，**同时出现在 `fileserver.conf` 与 `chatserver.conf`，且必须指向同一个目录**：

- fileserver 从它取包（读）。
- chatserver 从它做扫描，供控制台列候选包（**只读，不写文件**）。

fileserver 按场景选目录：抽一个 `baseDirForScene(scene)` 纯函数，`scene == file_scene_update` 时返回升级包目录，其余场景仍返回原来的 `filecachedir`。imgserver 复用同一份代码，但 scene=5 会先被 `isSceneAllowedOnServer` 挡掉，给它传空目录即可。

**相对路径的基准两边不一样，这是最容易搞错的地方。据实证**：

| 配置项 | 所在服务 | 相对基准 | 依据 |
| --- | --- | --- | --- |
| `dbpath` | chatserver | **可执行文件所在目录** | `chatserversrc/main.cpp:198-199` 显式调 `apppath::ResolveAgainstDirectory(GetExecutableDirectory(), ...)` |
| `filecachedir` | fileserver | **进程工作目录** | `fileserversrc/main.cpp:104-105` 直接把配置值交给 `FileManager::init`，没有做任何解析 |

`updatecachedir` 建议**统一按可执行文件所在目录解析**（与 `dbpath` 一致），避免再多一种基准。在本机当前跑法下（两个 exe 都在 `windowsproj/`）实际位置就是 `flamingoserver/windowsproj/updatecache/`。

### 7.3 fileserver 怎么按 MD5 找到一个人命名的文件

fileserver 现在是拿令牌里的 MD5 当文件名去开文件的（`FileSession.cpp:451` 的 `m_strFileBaseDir + md5`），而运维手工放进去的包叫 `Flamingo-3.3.0.zip`，两者对不上。解决办法是给 fileserver 加一份 **`UpdatePackageIndex`（MD5 → 实际文件路径）**：

- 启动时扫一遍升级包目录，逐个算 MD5 建映射。升级包目录里本来就只有几个文件，这点开销可以接受。
- 下载时按令牌里的 MD5 查映射；**查不到就重扫一次再判失败**，这样刚放进去的新包不必重启服务也能被找到。
- 映射按「路径 + 大小 + 修改时间」做失效判断，避免每次都重算 MD5。

两个被否掉的替代方案，记下来免得日后重复讨论：

- **要求运维按 MD5 重命名后再放**：fileserver 零改动，但把"算 MD5 再改名"这件机械活推给了人，正是本次要消除的东西。
- **把文件名塞进令牌**：令牌载荷是 `type|scene|md5|size|uid|expire` 的竖线分隔六段（`utils/FileToken.h:10`），文件名里出现竖线就会把载荷切错，而且要同时改动签发与校验两侧。

### 7.4 控制台的「客户端版本」页

**入口与权限。** `Screen` 枚举加一项，侧栏加一个「客户端版本」，**仅平台超管可见可用**（`admin.enterpriseid == 0`）；企业级管理员调这组接口一律拒绝——客户端版本是平台级资产，不属于任何一家企业。全部写接口沿用既有机制自动写 `t_admin_audit_log`。

**界面。** 一个版本列表加一个「新建版本」按钮。列表列出版本号、平台、最低版本、包大小、发布时间、状态（当前生效 / 已发布 / 草稿）与操作。新建弹窗是纯表单：点「扫描」列出升级包目录里的候选包 → 选一个 → 填版本号、最低版本、更新说明 → 存草稿或直接发布。**没有上传，也就没有进度条。**

**控制台侧的落地情况（A3）：** `Util/AdminApi` 加了六对 `MakeXxxRequest` / `ParseXxxResponse` 与 `FormatPackageSize`；`Screens/ClientVersionsScreen` 是列表页（页头两个按钮是真实 `DuiButton`，表格与行内操作自绘，与 `AuditScreen` 同构）；`Screens/ClientVersionModal` 是新建弹窗（候选包自绘列表 + 三个 `DuiEditHost` + 存草稿 / 直接发布）。侧栏入口按 `AdminSession::IsPlatformAdmin()` 决定加不加。

> **自绘控件的 `OnLButtonUp` 千万不要先转交基类。** **据实证**，`DuiControl::OnLButtonUp` 对落在自己矩形内的<u>任何</u>点击都 `NotifyParent(DUIN_CLICK)` 并返回 true（`balloonui/DuiControl.cpp:268-276`）。列表页与弹窗最初都写成"先调基类、返回 true 就不再往下走"，结果自绘的行内操作按钮与候选包行<u>全部点不动</u>，而且因为基类发的是一条不带动作的空通知，表现为"点了完全没反应、也不报错"，极难从现象反推原因。工程里既有的 `AuditScreen` / `GroupModal` 都是直接做自己的命中判定、不调基类——子控件的点击由宿主经 `HitTest` 直接派发给它们本身，根本不经过父控件这个函数。新写自绘控件时照抄它们的形态即可。

> **踩到一次控件 ID 撞号。** 新界面的 ID 最初编在 400 起，而 400-405 早已归平台设置界面（`kIdSettings*`）—— 这正是 `UiIds.h` 里那条既有注释警告过的同一类问题。所幸 `switch` 的 `case` 重复在编译期就报了错；若两个 ID 分处不同 `switch`，它会变成"点了另一个界面的按钮"这种极难查的运行期故障。新 ID 已挪到 430 / 440 段，并把这次的教训补进了注释。

| `POST /admin/clientversion/update.do` | 修改更新说明 / 最低版本 |
| `POST /admin/clientversion/setenabled.do` | 发布 / 撤回 |
| `POST /admin/clientversion/republish.do` | 回滚：把该行 `f_publish_time` 刷成当前时间，使其立即成为"最新发布" |

**暂不提供删除接口。** 版本记录留着是回滚的依据，删掉反而麻烦；要让某个版本停止下发，用「撤回」即可。

**一道最便宜的防呆：** 扫描时检查文件头是不是 `PK`，不是 zip 的直接标成不可用，挡掉"放错文件"这类低级错误。真正"解压得开"的校验要等 S4 写完 zip 解析后才能做，本期不做。

### 7.5 各字段怎么填

| 字段 | 填法 |
| --- | --- |
| `f_platform` | PC 填 1（取值见 `enum platform_type`） |
| `f_version` | 新版本号，**必须与客户端 `ClientVersion.h` 里的值对得上**，否则升级完还会提示有新版本 |
| `f_min_version` | 低于它的客户端会被拒绝登录、并在检查更新时被判为强制升级。不想强制就填一个足够低的值 |
| `f_release_note` | 更新说明，展示在升级窗里，可含中文与标点 |
| `f_package_md5` / `f_package_size` | 由扫描接口算出，控制台自动填入，**不需要人工输入** |
| `f_package_name` | 候选包的原始文件名，仅用于界面显示与本地落地命名 |
| `f_enabled` | 0 草稿、1 已发布 |
| `f_publish_time` | Unix 毫秒。**取数按这一列最大的一条**，不是按版本号大小 |
| `f_creator_adminid` / `f_create_time` | 由服务端在 create.do 里自动填，供列表页展示与审计追溯 |

### 7.6 撤回与回滚

- **撤回**：把该行 `f_enabled` 置 0。此后取到的是其余已发布记录里发布时间最新的那条；若一条都不剩，客户端得到"无更新"。
- **回滚到旧版本**：不要删数据，对旧版本那一行调 `republish.do`，把它的发布时间刷成当前即可，它立刻变成"最新发布"。取数规则按发布时间而非版本号，就是为了让这一步不需要改动历史数据。

> **发布时间必须取真毫秒。** `f_publish_time` 是"哪条记录更新"的唯一判据，而服务端各处惯用的 `time(NULL) * 1000` 只有秒级精度。**据实证**，A2 联调时正是踩到这个：同一秒内先发布 3.4.0、再回滚到 3.3.0，两条记录拿到一模一样的发布时间，随后按 `f_id DESC` 兜底选中了后插入的 3.4.0，**回滚静默失效**且没有任何报错。现改用 `Timestamp::now().microSecondsSinceEpoch() / 1000`（`base/Timestamp.cpp:73` 走 `chrono::system_clock`，两个平台都是微秒精度）。残留的理论边界是"同一毫秒内连发两次"，经 HTTP 调用不可能达到，且结果仍是确定的。

### 7.7 应急手段

控制台不可用时仍可直接改库应急，但**不作为常规手段**。本机没有 `sqlite3` 命令行，用 Python 的 `sqlite3` 模块操作，输出中文前先 `sys.stdout.reconfigure(encoding='utf-8')`。chatserver 开着时读写仍然安全（库是 WAL 模式），但**要复制库文件必须用 `Connection.backup()` 做在线备份，不能直接拷文件**。

改用 MySQL 部署时，表结构、取数规则、上述所有填法完全一致。

## 附录 A：协议报文

### A.1 `cmd_check_update`（1905）请求

```json
{
  "platform": 1,
  "version": "3.2.1"
}
```

- `platform`：客户端平台，1 为 Windows PC，2 为 Android（预留）。
- `version`：客户端当前版本号，取自 `ClientVersion.h`。

### A.2 有更新时的应答

```json
{
  "code": 0, "msg": "ok",
  "hasupdate": true,
  "latestversion": "3.3.0",
  "minversion": "3.1.0",
  "forced": false,
  "releasenote": "新增群接龙；修复若干问题",
  "md5": "9f2c8ab1...",
  "size": 38219776,
  "packagename": "Flamingo-3.3.0.zip",
  "downloadtoken": "2|5|9f2c8ab1...|38219776|0|1723363200000.a1b2c3...",
  "server": { "host": "file.flamingo.io", "port": 20001, "tls": false }
}
```

- `forced`：客户端当前版本低于 `minversion` 时为 true，界面上不给"稍后"选项。
- `md5` / `size`：直接喂给 `FileStreamTransfer::downloadFile` 作校验。
- `downloadtoken`：chatserver 现签的下载令牌，类型为下载、场景为 `file_scene_update`；未登录时载荷里的 uid 为 0。
- `server`：字段结构与 `cmd_request_download` 应答一致，客户端解析代码可以复用。

### A.3 无更新时的应答

```json
{ "code": 0, "msg": "ok", "hasupdate": false }
```

> 本节确定后，`docs/协议设计-v2.md` 的 10.12 节须同步改写——原草案返回的是 `fileid`，与本方案不同。

## 附录 B：表结构

以下为拟加进 `flamingoserver/table.sql` 的定义。**据实证**，该文件的既有风格是不带反引号的裸标识符、列名与类型按列对齐、每张表前用 `//` 写中文说明（见 `table.sql:539-546` 的 `t_group_file`），下面按同一风格书写。

改完须跑 `flamingoserver/tools/gen_table_sqlite.py` 重新生成 `table_sqlite.sql` 与 `sqliteapi/SqliteSchema.cpp`，这两个是生成物，绝不手改。

```sql
//客户端版本发布记录表（v2 自动更新功能）：一行 = 某平台的一次版本发布。
//取数规则为「按 f_platform 过滤，在 f_enabled=1 的记录里取 f_publish_time 最大的一条」，
//故 idx_platform_enabled 覆盖这两列；历史发布记录保留不删，便于回溯与回滚到旧版本。
//f_package_md5 既是升级包的内容校验值，也是它在 fileserver filecache 目录下的文件名。
CREATE TABLE IF NOT EXISTS  t_client_version  (
         f_id            int(11)       NOT NULL AUTO_INCREMENT COMMENT '自增主键',
         f_platform      int(4)        NOT NULL DEFAULT 1 COMMENT '客户端平台:1 Windows PC 2 Android(预留)',
         f_version       varchar(32)   NOT NULL DEFAULT '' COMMENT '本条记录发布的版本号,形如3.3.0',
         f_min_version   varchar(32)   NOT NULL DEFAULT '' COMMENT '允许登录的最低版本号,低于它的客户端被拒绝登录并强制升级',
         f_release_note  varchar(2048) NOT NULL DEFAULT '' COMMENT '更新说明,展示在升级窗里',
         f_package_md5   varchar(32)   NOT NULL DEFAULT '' COMMENT '升级包内容MD5(小写十六进制32位),同时是它在filecache里的文件名',
         f_package_size  bigint(20)    NOT NULL DEFAULT 0 COMMENT '升级包字节数',
         f_package_name  varchar(255)  NOT NULL DEFAULT '' COMMENT '升级包原始文件名,仅用于界面显示与本地落地命名',
         f_enabled       int(4)        NOT NULL DEFAULT 0 COMMENT '是否已发布:0草稿不下发 1已发布',
         f_publish_time  bigint(20)    NOT NULL DEFAULT 0 COMMENT '发布时间(Unix毫秒)',
         PRIMARY KEY ( f_id ),
         KEY  idx_platform_enabled  ( f_platform, f_enabled )
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

同一套字段还要在 `mysqlmgr/MysqlManager.cpp` 里登记一份（写法见 `MysqlManager.cpp:72-79` 的 `t_contact_remark`），这样 `_CheckTable` 的建表与补列机制才会覆盖它，老库升级不需要手工执行 SQL。两处定义须逐字对齐。
