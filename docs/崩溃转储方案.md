# PC 客户端崩溃转储方案

> 作者：balloonwj@qq.com　起草日期：2026-08-12
> 用途：记录 PC 客户端崩溃时如何产出转储文件（.dmp）—— 进程内与系统级两条路径各自覆盖什么、为什么两条都要、以及配置与排查方法。

---

## 1. 背景：一条路径盖不全

客户端原本只有<u>进程内</u>一条路径：`Source/App/Crash.cpp` 里一个全局对象在启动时调
`SetUnhandledExceptionFilter`，崩溃时在本进程内用 `MiniDumpWriteDump` 写盘。

这条路径的前提是「崩溃之后本进程还能执行代码」。多数崩溃（空指针、非法访问 `0xC0000005`
那一类）确实如此，历史转储也证明它在工作。但有一整类崩溃它<u>接不住</u>：

**栈保护失败（`__fastfail`）**。栈上的 /GS cookie 被覆盖时，CRT 走 `__report_gsfailure`
→ `__fastfail(FAST_FAIL_STACK_COOKIE_CHECK_FAILURE)`，产生 `0xC0000409`。它的设计前提恰恰
相反 —— **栈已经不可信，此刻再执行任何用户态代码都不安全**，于是绕过整个异常分发链，
直接由内核终止进程。注册过的 unhandled exception filter 根本没有机会运行。

2026-08-12 客户端退出时崩溃（"Stack around the variable 'dlgMain' was corrupted" /
`FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`）就属于这一类：崩了两次，运行目录的 `Users\` 下一个新的
`.dmp` 都没有。

---

## 2. 实测证据

用一个只做 `__fastfail` 的十几行测试程序（里面注册了与 `Crash.cpp` 同款的过滤器）实测：

| 验证项 | 结果 |
| --- | --- |
| 进程内 `SetUnhandledExceptionFilter` 能否接住 `__fastfail` | **不能**。过滤器里写标记文件的代码一次都没跑到 |
| 系统的 WER 是否把它当崩溃处理 | **是**。应用程序错误事件（ID 1000），exception code `0xc0000409` |
| 开启 LocalDumps 后是否真的写出转储 | **是**。`fastfail_test.exe.20088.dmp`，8.1 MB |
| 该转储是否可用 | **可用**。cdb 打开后异常地址、异常码、子码、调用栈齐全 |

最后一项的输出：

```
ExceptionAddress: fastfail_test!main+0x3c
ExceptionCode: c0000409 (Security check failure or stack buffer overrun)
Subcode: 0x2 FAST_FAIL_STACK_COOKIE_CHECK_FAILURE
栈：fastfail_test!main+0x3c -> invoke_main -> __scrt_common_main_seh
```

也就是说，同样的崩溃发生在客户端上时，转储里会直接给出**是哪个函数的栈被破坏了**——
这正是只靠事后推理拿不到的东西。

---

## 3. 方案：两条路径并存，各管一段

| 崩溃类型 | 由谁产出转储 | 落盘位置 |
| --- | --- | --- |
| 普通异常（空指针 / 非法访问 / 除零等） | 进程内 `Crash.cpp` 的过滤器 | `<exe 所在目录>\Users\dump\` |
| `__fastfail`（栈 cookie 被覆盖）、栈溢出等进程内接不住的 | 系统的 WER LocalDumps | `<exe 所在目录>\Users\dump\` |

两者<u>不会重复产出</u>：`Crash.cpp` 的过滤器最后返回 `EXCEPTION_EXECUTE_HANDLER`，
意为「我已处理，不再向下传递」，所以普通崩溃 WER 根本看不到；而 `__fastfail` 那条路
过滤器压根跑不到，只剩 WER。两者的产物落在同一个目录，排查时不必分头去找。

> 若日后希望普通崩溃也同时留一份 WER 转储，把过滤器的返回值改成
> `EXCEPTION_CONTINUE_SEARCH` 即可（先写自己的，再交给 WER）。

## 4. WER LocalDumps 的配置与自动写入

### 4.1 配置内容

```
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\Flamingo.exe
    DumpFolder   REG_EXPAND_SZ   <exe 所在目录>\Users\dump
    DumpType     REG_DWORD       2      （2 = 完整转储，带堆内存）
    DumpCount    REG_DWORD       10     （超过后自动删最旧的）
```

按 exe 名开子键，只对 `Flamingo.exe` 生效，不影响机器上其它程序。该配置<u>只能写在
HKLM</u>，没有当前用户级的等价项，因此**需要管理员权限**。

### 4.2 由客户端自行写入，且只在已提权时写

不引入安装程序、也不要求用户手工配注册表。做法是：

**客户端启动时检测自身是否以管理员权限运行 —— 是则写入这份配置，否则静默跳过。**

- 检测用 `GetTokenInformation(..., TokenElevation, ...)`，不弹任何提示、不主动请求提权。
- 写入是<u>幂等</u>的：已存在就更新，值没变时也不额外做什么。
- 配置是机器级且长期有效，所以**一生只需成功写入一次**。用户哪天恰好以管理员身份运行过
  一次客户端，之后即便一直以普通权限运行，WER 兜底也一直生效。
- 未提权时不报错、不提示、不打断启动，只记一条日志说明「未提权，跳过 WER 配置」。这条
  路径失败并不影响主流程：进程内那条转储路径照常工作，只是 `__fastfail` 那类崩溃拿不到
  转储而已。

之所以不主动弹 UAC 请求提权：为了写一个诊断配置去打断用户启动流程、还留下一个提权进程，
代价明显大于收益；而愿意配的用户以管理员身份启动一次即可。

## 5. 转储文件的落盘位置与命名

### 5.1 目录统一为 `<exe 所在目录>\Users\dump\`

改版前进程内那条路径写在 exe 所在目录的 `Users\`，与账号配置文件混在一处。现统一收到
`<exe 所在目录>\Users\dump\`（`Crash.cpp` 的 `kDumpSubDir`），与 WER 的产物同处一地。目录不存在时由写入方创建。

### 5.2 文件名补零成定长

改版前的格式是 `%d%d%d%02d%02d%02d.dmp`，年月日<u>没有补零</u>，于是 8 月 5 日是
`202685133729.dmp`、12 月 5 日是 `2026125133729.dmp` —— 长度不一致，字典序排出来也是错的，
在文件管理器里按名称排序无法得到时间顺序。

现改为 **`Flamingo_YYYYMMDD_HHMMSS.dmp`**（例：`Flamingo_20260805_133729.dmp`）：定长、
可排序、且与 WER 产出的 `Flamingo.exe.<pid>.dmp` 一眼可区分是哪条路径写的。

## 7. 排查时的注意事项

- **挂着调试器时 WER 不介入。** 调试器优先拿到异常，进程终止不再上报 WER，因此在 cdb / VS
  下复现崩溃是<u>不会</u>产生 WER 转储的。要拿 WER 转储就正常运行、别挂调试器；
  要实时看现场就挂调试器、别指望转储。两者二选一。
- **`/RTC1` 的运行时检查对话框不是崩溃。** Debug 版里 "Debug Error! Stack around the
  variable 'xxx' was corrupted" 是 CRT 在程序还活着时弹的报告框，不走异常路径，两条转储
  路径都不会触发。要抓这种情形得靠调试器（弹框时点【重试】进入调试器）。
- **完整转储体积较大**（实测 8 MB 量级，客户端会更大），`DumpCount=10` 是上限保护；磁盘紧张
  时可把 `DumpType` 调成 1（小转储），但栈破坏类问题常需要看堆与相邻内存，能留完整的尽量留。
- **取消配置**：删掉 `LocalDumps\Flamingo.exe` 子键即可，客户端下次以管理员身份启动会再写回去。

## 8. 已知边界

- 本方案只覆盖 PC 客户端。服务端（`chatserver` / `fileserver` / `imgserver`）崩溃走的是各自的
  机制，不在本文范围内。
- WER 可能被企业组策略关闭。真被关掉时事件日志照记、转储不写；判断方法是按第 2 节的办法跑一次
  测试程序，看目标目录有没有出文件。
