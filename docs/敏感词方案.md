## 1. 背景与目标

现有的敏感词功能是**群级**的：每个群的群主或管理员在群管理窗口「群权限」页打开过滤开关、在「管理词库」二级页维护本群词库，服务端只在开启了过滤的群里、只对文字消息做子串匹配，命中回 `error_code_sensitive_word`（507）。它有三个根本问题：

1. **管理分散。** 企业要统一管控用语，只能挨个群去配，单聊则完全没有过滤。
2. **覆盖面窄。** 只查群聊的文字消息与转发到群的文字；单聊、群发助手、转发到单聊、昵称、群名、文件名等一概不查。
3. **被拦下之后发送者几乎察觉不到。** 气泡照常显示，看起来像发成功了（详见 3.4）。

本方案把词库改为**按企业统一配置**：由各企业的管理员在 flamingoAdmin 里维护本企业的词库，服务端用发送者所属企业的词库检查一切由用户提交、别人能看到的文字，单聊与群聊一视同仁；PC 客户端把被拦下的消息清楚地标为发送失败。原有的群级敏感词整体删除。

### 1.1 术语

| 用语 | 含义 |
| --- | --- |
| 词库 | 某个企业的全部敏感词。每个企业一份，互不影响 |
| 词条 | 词库里的一条记录：原文、分类、备注 |
| 归一化 | 匹配之前对文字做的统一处理：统一大小写与全半角，去掉空白、标点符号与表情标记（规则见 4.2）。词条与待检查的文字都要先归一化 |
| 命中 | 归一化后的待检查文字里包含某个归一化后的词条 |
| 拦截 | 命中后服务端拒绝这次请求：不落库、不推送，回一个错误码 |
| 拦截记录 | 每次拦截在服务端留下的一条记录，供管理员在 flamingoAdmin 里查看 |
| 检查点 | 服务端在某个命令的处理函数里调用词库检查的位置 |
| 提交者 | 发起这次请求的用户。检查一律用提交者所属企业的词库 |

## 2. 已确认的产品选择

以下选择均已在 2026-10-02 与需求方逐条确认，是本方案的前提，实现时不得擅自变更。

### 2.1 词库归属与维护

- 词库**按企业划分**，每个企业一份；**没有**对所有企业共同生效的平台级词库。
- 企业管理员只能维护本企业的词库；平台超级管理员可以选择任一企业代为维护。
- 词库**只保存在服务端**，不下发到任何客户端。
- 原有的**群级敏感词整体删除**：群权限页的过滤开关、「管理词库」页、协议 1321 / 1322、`t_group.f_sensitive_on` 列与 `t_group_sensitive_word` 表。旧的群词库数据**不迁移**到企业词库。

### 2.2 拦截方式与适用范围

- **只在服务端拦截**，客户端不做预检。
- 单聊、群聊**统一生效**。
- 一律按**提交者所属企业**的词库检查，与接收方属于哪个企业、群主属于哪个企业无关。
- 管理员在 flamingoAdmin 里录入的内容（员工姓名、部门名、平台公告、服务号名称等）**不检查**。
- 命中后**不告诉**提交者命中了哪个词，只提示「包含敏感词」。理由与「词库不下发」一致：告诉了就能一个词一个词地试出整个词库。

### 2.3 检查范围

| 类别 | 检查的文字 |
| --- | --- |
| 文字消息 | 文字消息正文；群发助手发出的消息 |
| 引用 | 引用块里的文字快照（客户端自己填的，必须查） |
| 转发 | 逐条转发的文字、合并转发记录里的全部文字（含嵌套的合并记录）、合并转发的记录标题；转发到单聊与转发到群都查 |
| 卡片消息 | 投票、接龙、待办卡片里用户填写的文字；参与接龙时填写的文字 |
| 文件名 | 文件消息的文件名；申请上传文件时的文件名；单聊发送文件夹时的文件夹名 |
| 个人资料 | 昵称、个性签名、地址、邮箱；自助注册时填写的昵称 |
| 群资料 | 建群时的群名；群名称、群简介、入群欢迎语；群公告的标题与正文 |
| 群内其它文字 | 群名片；加群申请的验证消息；管理员禁言时填写的原因 |

**不检查**的内容：

- 只有本人可见的文字：联系人备注、联系人标签。
- 文件夹里各个文件的文件名：它们由两个客户端经 fileserver 中转直接传递，服务端不解析（见 3.6），无从检查。
- 图片：没有用户输入的文字。
- 管理员在 flamingoAdmin 里录入的内容（见 2.2）。
- **已经存在的内容不回溯**：新加的词只对之后提交的内容生效，已有的昵称、群名、历史消息不受影响。

### 2.4 匹配规则

- 不区分大小写，不区分全角与半角（「ABC」「ａｂｃ」视为相同）。
- **忽略空白、标点符号和表情**：「a b c」「a*b*c」、字间夹一个表情，都算命中「abc」。
- 归一化之后做子串匹配。
- 已知代价：会多一些误拦。例如词条「敏感」，在「过敏，感冒了」里也会命中，因为逗号被忽略后两个字连在了一起。需求方已接受。

### 2.5 被拦下之后的表现（PC 客户端）

- **发送消息被拦**：气泡保留在聊天窗里并标为发送失败——气泡旁一个红色感叹号，气泡下方一行灰字「消息包含敏感词，未能发出」；**不弹框**。右键菜单提供「重新编辑」与「删除」。「重新编辑」把原文放回输入框：输入框为空时直接填入，不为空时插入到光标处，已输入的内容不动。
- 失败的气泡只存在于当前窗口，不写入本地消息库，关闭聊天窗后不再出现；会话列表的预览也不显示被拦下的内容。
- **其它操作被拦**（改资料、建群、改群资料、发群公告、设群名片、加群申请、禁言、发文件夹、转发、发文件）：沿用各自现有的失败提示路径，把文案改成「包含敏感词」的专门说法。
- **Android 客户端本次不改。** 服务端拦截对 Android 同样生效，只是 Android 上的失败提示不够友好。

### 2.6 管理端功能（flamingoAdmin）

- 词库列表：分页、按关键字搜索、按分类筛选。
- 逐条添加、编辑、删除。
- 批量导入（粘贴多行，或导入一个文本文件）与导出（文本文件）。
- 企业级总开关：一键暂停 / 恢复本企业的过滤，不必清空词库。
- 拦截记录：分页查看，可按时间、发送者、来源、分类筛选；**不提供导出**。
- 词条分类与备注。

### 2.7 分类

固定六类，做成协议里的枚举：**违法违规、色情低俗、攻击辱骂、商业机密、广告引流、其他**。添加时不选分类的词归入「其他」。

### 2.8 上限

- 每个词最长 **32 个字符**（按字符数计，不按字节）。
- 每个企业最多 **10000 条**。

### 2.9 拦截记录

- 记录：时间、提交者、来源、会话（单聊对象或群）、命中的词条与分类、内容摘要。
- 内容摘要只保存命中位置前后各 **20 个字**，不保存整条内容。
- 保留 **180 天**，服务端定时清理过期记录。

## 3. 现状盘点（据实证）

### 3.2 单聊、群发助手与转发到单聊都不检查

- 单聊发送（`ChatSession::onSendMessage` 的单聊分支）没有任何词库检查。
- 群发助手 `onMassSend` 经 `deliverConversationMessage` 直接落库，既不查词库、也不查禁言。PC 客户端没有群发入口（`cmd_mass_send` 只在 `flamingoclient/Source/net/Protocol.h` 有定义）。
- 转发只在目标是群时检查（`ChatSession::onForwardMessage`），转发到单聊不查；合并转发的记录标题（`MessageProtocol.cpp` 解析）也不查。
- 卡片消息（投票 / 接龙 / 待办，msgtype 10 / 11 / 12）不查；`onJoinRelay` 的接龙文字不查。

### 3.3 发送被拒的应答不带 clientmsgid

- `MessageProtocol::buildSimpleResponse` 只输出 `code` 与 `msg`。
- 普通群发的禁言（经 `checkGroupSpeakAllowed`）、「仅管理员可 @全体」、命中敏感词三种拒绝都用它回包。
- 而 `buildSendMessageResponse` 会带 `clientmsgid`，「内容过长」这一种拒绝已经在用它。
- 客户端解析发送回执时，失败应答也会读取 `clientmsgid`（`flamingoclient/Source/net/MessageProtocolClient.cpp`），所以服务端补上这个字段即可，客户端解析不用改。

### 3.4 客户端被拦下之后的表现

以群聊为例（单聊同理）：

1. 群聊窗先把消息作为气泡显示出来（`BalloonGroupChatWindow.cpp`），清空输入框，并通知主面板把会话冒泡到顶部、预览换成这句话。
2. 拒绝应答不带 `clientmsgid`（3.3），客户端无从知道被拒的是哪一条。
3. 主面板只弹一个框（`BalloonMainPanel.cpp`），弹框挂在主面板上，文案是通用的「消息发送失败（错误码 507）」——`SendFailureText`（`ChatSendLimit.cpp`）只给「内容过长」写了专门文案。
4. 气泡一直留着，与发送成功的消息没有区别：文字气泡没有「发送失败」状态，只有图片有（`ChatMessageList.h` 的 `MarkImageUploadFailed`）。会话预览也停在这句被拒的话上。

会话冒泡共 6 处，都在发送当时发出：单聊窗的文字、图片、文件、窗口抖动（`BalloonChatWindow.cpp`），群聊窗的文字、图片（`BalloonGroupChatWindow.cpp`）。

本地消息库只写入服务端推送或同步下来、带 msgid 的消息（`BalloonMainPanel.cpp`），被拦下的消息不会进消息记录。

### 3.5 提交者所属企业

- 会话对象上没有缓存企业 id：`OnlineUserInfo`（`ChatSession.h`）只有 userid、用户名、昵称、密码、客户端类型与状态；登录时算出的企业 id 只存在局部变量里（`ChatSession.cpp`）。
- `DepartmentManager::getUserEnterpriseId`（`DepartmentManager.cpp:265-304`）先查一份带互斥锁的内存缓存，未命中才查 `t_user`，结果大于 0 时写入缓存。首次之后每次调用只是一次加锁的 map 查找，可以直接在检查点里调用。

### 3.6 文件名与文件夹名

- fileserver 从头到尾看不到文件名：上传凭证里只有类型、场景、md5、大小与 uid（`ChatSession::onRequestUpload` 签发），`FileSession.cpp` 只读凭证与偏移。
- chatserver 两次看到文件名：申请上传 `cmd_request_upload` 1801（`FileProtocol.cpp:82`，秒传命中时在 `onRequestUpload` 里提前返回），以及发送文件消息时的 `content.name`。
- 文件夹名在 `cmd_folder_invite` 1810 的 `foldername` 里（`FolderTransferProtocol.cpp`，处理函数 `ChatSession::onFolderInvite`）；文件夹里的各个文件名走中转帧，fileserver 不解析（`FileSession.cpp`）。

### 3.7 服务端没有现成的 UTF-8 解码与多模式匹配工具

- `utils/StringUtil.h:19-26` 只有 split / cut / replace / trim。
- 仅有的 UTF-8 处理都是按字节、各文件私有的（`GroupProtocol.cpp` 的 `utf8CharCount`、`MessageProtocol.cpp` 的 `normalizeForwardTitle` 等）；没有 Aho-Corasick 之类的多模式匹配实现。
- 表情在文字里编码为 `/f["数字"]`（`flamingoclient/Source/UI/BalloonChat/BalloonChatMsgFormat.cpp:187`）。用户输入的 `/` 若恰好构成一个合法标记的开头，会被转义成 `//f["`（`EscapeTextForSend`，同文件 `155-173`），其余的 `//`（如网址）不是转义。

### 3.8 管理后台

- flamingoAdmin 通过 HTTP 调 chatserver 的 `/admin/*.do`，`HttpSession::processAdminRequest` 按完整 URL 分发；业务逻辑放在 `chatserversrc` 下的 `XxxManager` 单例里。
- 企业范围：请求带 `enterpriseid`，企业管理员一律被改写为本企业（`HttpSession.cpp`）；写操作要查目标行所属企业，不符回 116。
- 分页：`page`（从 1 起）+ `pagesize`，应答 `{"code":0,"msg":"ok","total":N,"list":[...]}`。
- 审计：`AdminManager::writeAudit(actorId, actorName, ip, enterpriseId, action, target, severity, detail)`（`AdminManager.h:224`），动作命名为「模块.动词」，普通写操作 severity 取 1、删除取 2。
- 错误码在 `chatserversrc/AdminApiCodes.h`，下一个空号是 **120**；`HttpSession` 及其调用的 manager **不得包含** `Protocol.h`（两份 `error_code` 枚举冲突）。
- 导出：服务端生成 CSV、设行数上限（`ADMIN_AUDIT_EXPORT_MAX`，`AdminManager.h:22`），客户端 `AdminFrame::SaveCsvToFile` 写盘（3c 起改为 `SaveTextToFile`）。它的成功提示固定为「企业列表已导出」。
- flamingoAdmin 里**没有任何读取文本文件的代码**；列表页**都没有**企业选择器，最接近的先例是 `PresentComposeModal`（`AdminFrame.cpp`）拉取企业列表。

### 3.9 客户端其它失败提示的现状

| 场景 | 现有处理 | 位置 |
| --- | --- | --- |
| 个人资料保存失败 | 从快照回退、弹「保存资料失败，请稍后重试。」 | `CBalloonMainPanel::OnUpdateProfileResult`（按资料窗就地编辑的提交队列回滚并提示） |
| 个性签名修改失败 | 回退、弹「修改个性签名失败，请稍后重试。」 | `BalloonMainPanel.cpp` |
| 建群失败 | 弹「创建群聊失败（错误码 N）。」 | `CreateGroupDlg.cpp` |
| 群管理各项操作失败 | `DescribeGroupOpFailure` 按错误码给文案，没有对应条目时附上服务端原文 | `GroupManageMapping.cpp` |
| 转发失败 | `ForwardErrorText` 对 507 已有文案「内容包含该群设置的敏感词」 | `ForwardDispatcher.cpp` |
| 发文件时申请上传被拒 | 把错误码交给聊天窗，文件气泡标为失败，不显示原因 | `FileTransfer.cpp` |

## 4. 总体设计

### 4.1 结构

```
flamingoAdmin ──HTTP /admin/sensitive/*.do──▶ HttpSession ─┐
                                                           ▼
                                               SensitiveWordManager（单例）
                                               ├─ 词库增删改查、导入导出
                                               ├─ 按企业缓存匹配器（只读快照）
                                               ├─ 写拦截记录、定时清理
                                               └─ SensitiveWordMatcher（纯函数：归一化 + 匹配）
                                                           ▲
PC 客户端 / Android ──TCP──▶ ChatSession 各检查点 ─────────┘
                                │ 命中：回各自的错误码，不落库、不推送
                                ▼
                     t_sensitive_word　t_sensitive_hit_log　t_enterprise.f_sensitive_on
```

### 4.2 归一化规则

对一段 UTF-8 文字依次处理，得到一串 Unicode 码点；同时记下每个保留下来的码点在原文中是第几个字符，供截取内容摘要用。

1. **按 UTF-8 解码**。非法字节序列逐字节跳过，不中断、不报错。
2. **去掉表情标记**：`/f["数字"]` 整体去掉；被转义的 `//f["` 按字面文字处理（还原为 `/f["`，再交给第 5 步）。
3. **全角转半角**：U+FF01–U+FF5E 映射到 U+0021–U+007E；全角空格 U+3000 视为空白。
4. **统一大小写**：ASCII 大写字母转小写（全角字母经第 3 步后同样适用）。
5. **去掉忽略字符**：
   - 空白：ASCII 空白与控制字符、U+00A0、U+2000–U+200F、U+2028–U+202F、U+205F、U+3000、U+FEFF；
   - ASCII 中字母与数字以外的全部可见字符；
   - 通用标点 U+2010–U+2027、U+2030–U+205E；
   - CJK 符号和标点 U+3001–U+303F；
   - 全角标点（第 3 步映射后已成为 ASCII 标点，由上一条覆盖）、竖排与小写变体 U+FE10–U+FE1F、U+FE30–U+FE6F、半角标点 U+FF61–U+FF65；
   - 各类符号与表情：U+2100–U+2BFF、U+1F000–U+1FAFF，以及变体选择符 U+FE00–U+FE0F、零宽连接符 U+200D。

   其余字符（汉字、字母、数字、假名、谚文等）原样保留。具体码点区间以单元测试为准，实施时可以调整，但调整后词条要整体重建（见 4.4）。

词条用**同一套规则**归一化。归一化后为空的词（例如整个词只有符号）不允许入库。

### 4.3 匹配引擎：`SensitiveWordMatcher`

- 新文件 `flamingoserver/chatserversrc/SensitiveWordMatcher.{h,cpp}`，只依赖标准库，便于单元测试。
- 用归一化后的全部词条构建 **Aho-Corasick 自动机**，对待检查文字只扫描一遍就能找出命中。转移表用一张以「(节点号, 码点)」为键的 `std::unordered_map`，加上失败指针数组与输出链。
- 接口：
  - `static void Normalize(const std::string& utf8, std::vector<uint32_t>& codepoints, std::vector<uint32_t>* origCharIndex)`；
  - `bool Build(const std::vector<SensitiveWordEntry>& words)`；
  - `bool Match(const std::string& utf8, SensitiveHit* hit) const`——返回第一个命中的词条 id、分类，以及命中位置在原文中的字符区间；
  - `static std::string MakeSnippet(const std::string& utf8, uint32_t beginChar, uint32_t endChar, uint32_t contextChars)`——截取命中位置前后各 `contextChars` 个字符，两端被截断时加省略号。
- 规模估计（据推测；SW-M10 的实测耗时见第 9 节 1a）：10000 条、每条 32 字时，自动机最多约 32 万个节点。按每条转移约 40 字节计，最坏约十几 MB；常见词表的词短、前缀重合多，实际会小一个数量级。匹配耗时与文字长度成正比，与词条数无关，256 KiB 上限的消息也只扫描一遍。

### 4.4 词库缓存：`SensitiveWordManager`

- 新文件 `flamingoserver/chatserversrc/SensitiveWordManager.{h,cpp}`，`Singleton<SensitiveWordManager>`，在 `main.cpp` 里与其它 manager 一起初始化。
- 缓存结构：`std::map<int64_t, std::shared_ptr<const EnterpriseWordSet>> m_cache` 加一把互斥锁。`EnterpriseWordSet` 包含企业总开关与构建好的 `SensitiveWordMatcher`，构建后只读。
- 检查流程：在锁内取出该企业的 `shared_ptr` 副本，随即释放锁，在锁外匹配。多个检查点、多个事件循环线程可以并发读取同一份快照。
- 首次用到某企业时在锁外查库、构建，构建完再加锁放入缓存。两个线程同时构建同一企业时以后放入的为准，结果相同，无害。
- 管理端每次写入（增删改、导入、开关）在数据库写成功后**丢弃**该企业的缓存，下一次检查时重新构建，因此改动立即生效。

### 4.5 统一检查入口

`ChatSession` 新增一个私有方法，所有检查点都调用它：

```cpp
/**
 *  按提交者所属企业的词库检查一组文字，任意一段命中即返回 true。
 *  命中时写一条拦截记录、记一条 LOGI；调用方负责按各自命令的格式回错误码。
 *    source： 来源，取值见 sensitive_hit_source
 *    ctype：  会话类型，单聊 1、群聊 2；与会话无关的检查（改资料等）传 0
 *    cid：    会话 id，单聊为对方 userid，群聊为群 id；ctype 为 0 时传 0
 *    texts：  待检查的文字（UTF-8），空串跳过
 */
bool hitSensitive(int source, int ctype, int64_t cid, const std::vector<std::string>& texts);
```

日志只记词条 id、分类与来源，不记命中的原文与内容摘要（这两项只进拦截记录表），日志用英文。

### 4.6 各命令用各自号段的错误码

`docs/协议设计-v2.md` 第 8.1 节规定：新错误码落在对应功能段的末尾；语义横跨两段的，按它在哪个业务的应答里下发归段。因此「包含敏感词」按命令所属的业务分成四个码：消息段沿用 507，资料段新增 109，群组段新增 312，文件段新增 621（取值见 5.3）。

## 5. 协议设计

### 5.1 退役与删除

- `cmd_get_sensitive_words` = 1321、`cmd_operate_sensitive_word` = 1322 退役，**两份** `Protocol.h` 同时删除，原位留一行「已作废、禁止复用」的注释（参照 `Protocol.h` 里 1214 的写法）。`docs/协议设计-v2.md` 第 7.4 节补一条退役说明。
- 服务端的 `enum sensitive_word_operation` 一并删除（客户端没有这份枚举）。
- 群资料 JSON（1303 / 1318 / 1320 的群对象）不再输出 `sensitiveon`；`cmd_update_group_info` 1311 不再识别 `sensitiveon`，旧客户端带上来时直接忽略。

### 5.2 `cmd_send_message` 的失败应答带回 clientmsgid

所有拒绝分支（不是群成员、群不存在、禁言、@全体被拒、包含敏感词、内容过长、落库失败等）一律改用 `buildSendMessageResponse`：

```json
{ "code": 507, "msg": "message contains sensitive word", "clientmsgid": "9f1c…", "msgid": "0", "timestamp": 0 }
```

旧客户端只读 `code`，不受影响。`docs/协议设计-v2.md` 的 1503 一节同步更新。

#### 6.3.1 从一条消息里取出待检查的文字

`MessageProtocol` 新增 `collectSensitiveTexts(int msgtype, const std::string& content, const std::string& quote, std::vector<std::string>& out)`，内部把原先的 `collectTextsFromContent` 扩充为同一套规则；原先的 `collectForwardTexts` 删除，转发改为对实际要新建的内容调用 `collectSensitiveTexts`（2a 实施时确定）：

- 引用：`quote.digest`（发送请求的引用快照，以及转发源消息内嵌的引用）；
- 文件消息（3）：`content.name`；

- 合并记录（15）：标题与全部子消息，递归；

### 6.5 定时清理拦截记录

照 `PublishDueAnnouncementsTick` 的写法，新增一个具名的静态函数，在 manager 初始化之后用 `g_mainLoop.runEvery` 每小时执行一次（间隔常量以微秒为单位）。它调用 `SensitiveWordManager::purgeHitsBefore(HitRetentionCutoff(now))`，删除 `f_create_time` 早于「当前时刻往前 180 天」的记录。启动后先立即执行一次。日志：启动时那一次无论删没删都记一行，之后每小时只在确实删了记录时才记（2d 实施时与用户确认）。

### 6.6 删除企业时一并清理

### 8.3 失败状态的气泡

- `ChatMessage` 新增两个字段：`sendFailed`（是否发送失败）与 `failReason`（失败原因，界面显示用）。
- `ChatMessageList` 新增 `bool MarkSendFailed(const std::string& clientMsgId, const CString& reason)`：按 clientMsgId 找到本端发出、尚未回填 msgid 的那一行，置失败状态，重新计算行高并重绘；找不到时返回 false。适用于文字、文件、卡片等各类气泡；图片沿用现有的 `MarkImageUploadFailed` 破图样式，另外加上原因行。
- 绘制（`ChatBubble`）：本端的气泡靠右，在气泡左侧垂直居中画一个红色圆形感叹号（颜色取现有的 `kImagePlaceholderCaptionRed`）；气泡下方右对齐一行灰色小字显示 `failReason`。
- 失败行的 msgid 为 0，现有逻辑已经保证它没有已读回执、不能撤回 / 转发 / 引用 / Pin，「删除」直接从列表移除（`ChatMessageList.cpp`）。
- 文件发送失败（`OnFileSendResult`）目前只有成功与否两种结果，扩充为带上错误码，以便显示「文件名包含敏感词」。

### 8.4 重新编辑

- 右键菜单（`ChatMessageMenu`）新增「重新编辑」，只对**发送失败的文字气泡**显示。
- 点击后把原文放回输入框：输入框为空时直接填入；不为空时插入到当前光标处，已有内容不动。表情按 `ParseSendBody` 还原成输入框里的表情图片；群聊里的 @ 片段按气泡上记录的 `ats` 重新登记为待发的 @ 候选，发送时照常重扫。

- 失败的气泡保留，用户可以自行删除。

### 8.5 会话冒泡改到发送成功之后

现在 6 处冒泡（3.4）都在发送当时发出，被拦下的消息会成为会话预览。改为：各发送点不再自己冒泡；单聊窗与群聊窗的 `OnSendChatAckBackfill`（回填 msgid 的地方）在找到那一行之后，按该行的消息类型与内容发出冒泡。发送失败的消息不会冒泡，预览也就不会出现被拦下的内容，不需要回退。

代价：会话移到顶部的时机推迟到回执到达，正常网络下只差几十毫秒。

窗口抖动、文件、图片走的都是 `cmd_send_message`，同样经过回填，一并迁移。

- **flamingoAdmin**：删除 `ActionTable::SetRowCount`（绕开代码）。企业管理页实机核对时又查出一个问题：`EnterprisesScreen::HitTestActionDotsAt` 把「操作」列算到表格右边界，滚动条叠在这一段上，按下滚动条会被 `AdminFrame::OnLButtonDown` 当成点了三个点，弹出行菜单并拦下这次按下，滚动条无法点击与拖动。以前滚动条矩形为空，这个问题没有暴露出来。现在命中测试先排除表格的子控件（滚动条）。企业表格类定义在 `EnterprisesScreen.cpp` 的匿名命名空间里，该文件也不在测试工程中，所以这一处没有单测，用实机前后对比验证：修复前点滚动条的空白处会弹出行菜单、滚动条不动；修复后点空白处翻一页，拖动滑块可拖到底，点三个点仍弹出行菜单。企业管理页的表头与数据行都按固定列宽从左排，出现滚动条不会错位，不需要 `SetTrailingInset`。flamingoAdmin 测试通过 1082、失败 0（AT-3 不再依赖绕开代码，仍然通过）。截图在 `snapshots/bug60-enterprise-scrollbar.png`、`bug60-enterprise-drag.png`。

### 10.4 双账号联调验收

1. 管理员给企业加词「测试敏感」；用户 A 在单聊、群聊各发一条含该词的消息：A 端气泡标红、显示原因，B 端收不到；会话预览不变。
2. A 发「测 试 敏 感」「ＴＥＳＴ」类变体（先加英文词「test」）：同样被拦。
3. A 点「重新编辑」，删掉敏感词后重发：发送成功。
4. A 转发一条加词之前发出、含该词的消息到单聊与群：都被拦。
5. A 改昵称、签名、群名称、群公告、群名片：都被拦，提示正确，界面回退到修改前。
6. A 发送文件名含该词的文件、文件夹：被拦。
7. 管理员关闭总开关：上述操作都能成功；重新打开：立即恢复拦截。
8. 管理员在 flamingoAdmin 拦截记录里能看到以上每一次拦截，来源、会话、摘要正确。
9. 管理员删除该词：立即可以发送。
10. 平台超级管理员切换企业：只看到所选企业的词库与记录。

## 11. 未定与后续

- **繁简转换、拼音与谐音、形近字**：本方案不处理，「敏感」与「敏 感」能拦，「敏gan」拦不住。

- **重新编辑不恢复引用**（8.4）：如有需要，可在 `ChatMessage` 上保存完整的引用信息后再支持。
- **服务端 HTTP 请求体大小上限**为 1 MiB（`HttpSession.cpp` 的 `MAX_HTTP_BODY_LENGTH`），大于 1000 行一批的导入请求体（约 100 KB），每批行数不用调小。
