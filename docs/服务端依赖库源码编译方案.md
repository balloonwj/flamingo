# 服务端依赖库源码编译方案（MariaDB 连接器、zlib 1.3.2、只保留 x64）

2026-10-09 起草。起因：清理 `flamingoserver/` 时，用户要求把 `mariadb-connector-c-3.4.9` 的源码放进服务端工程、以源码方式编译进程序，不再使用 `deps/mariadb-connector/` 下预编译的静态库；讨论中又定下服务端只保留 x64 的 Debug / Release、服务端 zlib 升级到 1.3.2。

## 1. 现状（2026-10-09 核实）

- **只有 chatserver 用到 MySQL 客户端库。**
  - Windows：`windowsproj/chatserver.vcxproj` 中从 `..\deps\mariadb-connector\lib\$(Platform)\$(Configuration)` 链接 `mariadbclient.lib`，另带 `ws2_32 shlwapi crypt32 bcrypt secur32`。`Tests.vcxproj` 四个配置都定义了 `FLAMINGO_NO_MYSQL`，不链接它。
  - Linux：`CMakeLists.txt` 按完整路径链接 `deps/mariadb-connector/lib/linux/libmariadbclient.a`，外加 `ssl crypto dl`；用到它的目标是 `chatserver` 与 `flamingo_tests_mysql`，`WITH_MYSQL=OFF` 时两者都不链接。
- **代码里只有两个文件引用连接器头文件**：`mysqlapi/DatabaseMysql.h`（`<mysql/mysql.h>`、`<mysql/errmsg.h>`）、`mysqlapi/MysqlQueryResult.h`（`<mysql/mysql.h>`）。
- **预编译库的编译参数**见 `deps/mariadb-connector/README.txt` 与同目录 `build/` 下的两个脚本：Windows 用 SChannel、Linux 用 OpenSSL 作 TLS 后端；`CLIENT_PLUGIN_CACHING_SHA2_PASSWORD / SHA256_PASSWORD / DIALOG / MYSQL_CLEAR_PASSWORD` 全部 `STATIC`；`WITH_EXTERNAL_ZLIB=OFF`（用连接器自带的 zlib）；`WITH_UNIT_TESTS / WITH_CURL / WITH_MYSQLCOMPAT=OFF`。源码 `flamingoserver/mariadb-connector-c-3.4.9` 是官方发布包、未做改动（`deps/mariadb-connector/README.txt:8`），目前被 `.gitignore` 忽略、没有入库。
- **上游 CMake 在配置阶段生成三个文件**，只把 `.c` 加进工程无法编译：`include/ma_config.h`（平台探测结果）、`include/mariadb_version.h`（公共头文件，含版本号、默认字符集、插件目录）、`libmariadb/ma_client_plugin.c`（静态插件登记表）。见上游 `CMakeLists.txt:390-395`、`libmariadb/CMakeLists.txt` 中 `CONFIGURE_FILE(... ma_client_plugin.c.in ...)`。
- **上游假设自己是顶层工程**：要求 CMake ≥ 3.12（上游 `CMakeLists.txt:5`，而我们的 `CMakeLists.txt` 写的是 2.6）；在非 Windows 平台无条件引入 `mariadb_config/` 与 `man/`（上游 `CMakeLists.txt:446-447`、`463-464`）；使用自带 zlib 时引入 `external/zlib`（`:238`），并以 `${CMAKE_SOURCE_DIR}/external/zlib` 作为头文件目录（`libmariadb/CMakeLists.txt:380`），作为子目录引入时这个路径会指向不存在的 `flamingoserver/external/zlib`。WSL 上的 CMake 为 3.28.3。
- **zlib 有两份。** chatserver / fileserver / imgserver / 测试程序都直接编译 `zlib1.2.11/` 的源文件；连接器自带的 `external/zlib` 版本号为 1.3.1（`external/zlib/zlib.h:40`），但它**不是官方原版**：带有 `adler32_simd.c`、`crc32_simd.c`、`inffast_chunk.c`、`chunkcopy.h` 等加速补丁，也没有 `zconf.h`。据推测，现在链接时实际使用的是我们的 1.2.11：静态库中的成员只在符号尚未定义时才会被链接器取出，而 zlib 的符号已由各程序自己的目标文件定义。
- **`zlib1.2.11` 这个目录名写死在多处**：`net/FramePayload.cpp:8`、`chatserversrc/ChatSession.cpp:16`、`tests/test_framecompress.cpp`（均为 `#include "../zlib1.2.11/ZlibUtil.h"`），四个 vcxproj 与其 `.filters`，`CMakeLists.txt` 的 `zlib_srcs`，`windowsproj/tools/regen_filters.ps1`。目录里除 zlib 本身外还有我们自己的 `ZlibUtil.cpp/.h` 与 `文件概览.txt`。
- **Windows 服务端维护三个配置** `Debug|Win32`、`Debug|x64`、`Release|x64`（开发约定文档），`deps/libsodium` 与 `deps/mariadb-connector` 各有一份 `lib/Win32`。

## 2. 已定的决定（2026-10-09 与用户逐项确认）

| 问题 | 决定 |
| --- | --- |
| 连接器以什么方式进入程序 | 源码随仓库提交，编译时从源码编出，不再使用预编译库 |
| 需要哪些平台与配置 | Windows 与 Linux 都只要 x64 的 Debug 与 Release。**整个服务端**去掉 32 位：解决方案与四个工程删除 `Debug|Win32`、`Release|Win32`，删除 `deps/*/lib/Win32` |
| Windows 侧的编译方式 | 独立的静态库工程 `windowsproj/mariadbclient.vcxproj`，加入 `FlamingoServer.sln`，chatserver 以工程引用方式链接 |
| Linux 侧的编译方式 | `add_subdirectory` 引入上游 CMake，由它在配置阶段现场生成文件 |
| zlib | 服务端 zlib 升级到官方 1.3.2，整个程序（含连接器）共用这一份；连接器不再编译自带的 zlib。起初定的是 1.3.1（与连接器自带的版本一致），实施时发现官网当前版本已是 1.3.2（2026-02-17 发布），而连接器改用我们的 zlib 后不必再与它一致，经用户确认改为 1.3.2 |
| 守卫用例 | ZLB1、MDB1～MDB3（见第 6 节），全部加上；现有 `test_framecompress` 作为 zlib 升级的回归测试 |

- 上游目录删掉 `unittest/`、`benchmark/`、`docs/`、`external/`（不再使用自带 zlib）以及 CI 脚本，其余保留：Linux 侧由上游 CMake 现场配置，`mariadb_config/`、`man/`、`cmake/`、`win-iconv/` 等都要在。`gen_config.ps1` 需要完整的上游源码时，使用官方发布包（仓库外的临时目录），不依赖裁剪后的入库副本。
- Linux 不需要预生成文件，所以 `config/` 下只有 `x64` 一份。Debug 与 Release 共用，因为这三个文件只与平台、架构有关。

## 4. 编译方式

### 4.1 Windows

- `mariadbclient.vcxproj`：纯 C 静态库，只有 `Debug|x64`、`Release|x64` 两个配置；静态 CRT（`/MTd`、`/MT`）、定义 `WIN32`、传 `/utf-8`，与其余服务端工程一致。
- 源文件清单与宏以 `gen_config.ps1` 运行上游 CMake 时记录下来的为准（上游生成的 vcxproj 中 `mariadbclient` 目标的源文件与 `PreprocessorDefinitions`），预计包括 `LIBMARIADB`、`THREAD`、`HAVE_COMPRESS`、`HAVE_SCHANNEL`、`HAVE_TLS`、`HAVE_WINCRYPT`、`SIZEOF_CHARP=8` 等。这些宏与上游的内部头文件目录只作用于本工程，上游代码的告警也只在本工程内屏蔽。
- 头文件目录指向 `zlib1.3.2/`，本工程不编译任何 zlib 源文件；链接 chatserver 时由 chatserver 自己编译的 zlib 提供实现。
- `chatserver.vcxproj` 改为 `ProjectReference` 引用它，删除 `deps\mariadb-connector` 的库目录与 `mariadbclient.lib`；系统库保持不变。`Tests.vcxproj` 也引用它，只为守卫用例，`FLAMINGO_NO_MYSQL` 保持不变。

### 4.2 Linux

- `cmake_minimum_required` 提到 3.12。
- zlib 做成静态库目标（源文件为 `zlib1.3.2/` 下的 zlib 本体），三个服务与测试程序改为链接它；`gz*` 需要的 `HAVE_UNISTD_H` 照旧只加在 zlib 源文件上（`CMakeLists.txt:209-215`）。
- 在 `add_subdirectory` 之前，按现在编译脚本的参数设置上游的缓存变量，但 `WITH_EXTERNAL_ZLIB=ON`，并预先设好 `ZLIB_FOUND=TRUE`、`ZLIB_INCLUDE_DIR`（`zlib1.3.2/`）、`ZLIB_LIBRARY` 与 `ZLIB_LIBRARIES`（都设为上面的 zlib 目标）。上游的写法是 `IF(NOT ZLIB_FOUND) FIND_PACKAGE(ZLIB REQUIRED)`（上游 `CMakeLists.txt:230-233`），预设之后不会调用 FindZLIB，也就不会去系统里找 zlib；第 2 步在 Windows 上用同样的预设运行过上游 CMake，日志中 `SYSTEM_LIBS` 的最后一项正是预设的 zlib 目标名。
- `add_subdirectory(mariadb-connector-c-3.4.9 EXCLUDE_FROM_ALL)`，只编译 `mariadbclient` 目标，不编译动态库与 `mariadb_config`。`chatserver`、`flamingo_tests_mysql` 改为链接该目标；我们的代码需要的头文件目录为上游 `include/` 与上游构建目录下生成的 `include/`。
- 编译机需要 OpenSSL 头文件（`libssl-dev` / `openssl-devel`）。现在链接时已经需要 `-lssl -lcrypto`，实际上这个包本来就要装。

### 4.3 两处头文件引用

`<mysql/mysql.h>`、`<mysql/errmsg.h>` 改为 `<mysql.h>`、`<errmsg.h>`：上游源码树中这两个文件位于 `include/` 根下。

## 6. 守卫用例

都不需要 MySQL 服务器。Windows 放在 `Tests.exe`，Linux 放在 `flamingo_tests_mysql`（ZLB1 两个测试程序都放）。

| 编号 | 内容 |
| --- | --- |
| ZLB1 | `zlibVersion()` 返回 `"1.3.2"`，且与头文件中的 `ZLIB_VERSION` 一致 |
| MDB1 | `mysql_get_client_version()` 等于 30409，确认链接的是源码编出的 3.4.9 |
| MDB2 | `mysql_init` 之后，`mysql_client_find_plugin` 能找到 `caching_sha2_password`、`sha256_password`、`mysql_native_password`、`dialog`、`mysql_clear_password`，不依赖从磁盘加载插件 |
| MDB3 | `mariadb_get_infov(..., MARIADB_TLS_LIBRARY, ...)` 报告的 TLS 后端：Windows 为 SChannel，Linux 为 OpenSSL |

## 7. 风险与注意

- 升级连接器版本时：Windows 要重跑 `gen_config.ps1`，并对照新旧源文件清单更新 `mariadbclient.vcxproj`；Linux 由上游 CMake 自动处理。
- 上游作为子目录引入时可能还有其它「假设自己是顶层工程」的写法，第 5 步逐项排查，处理方式限于在我们自己的 CMakeLists 里设置，不修改上游文件。
- 部署机若是 CentOS 7 一类的老系统，默认 CMake 低于 3.12，需要另装 `cmake3`。
- 连接器的许可证是 LGPL 2.1。现在已经是静态链接，改为源码编译后义务不变，`COPYING.LIB` 随源码保留。
- 客户端 `flamingoclient` 也带有一份 zlib 1.2.11，不在本方案范围内。

## 11. 设计

### 11.1 目录布局

```
flamingoserver/
  libsodium-1.0.22/     取自 ../third-party/libsodium-1.0.22-RELEASE（官方发布包，未改动），裁剪后入库：
                        保留 configure、build-aux/、src/、各级 Makefile.in 与 *.pc.in、LICENSE 等 configure 需要的文件
  openssl-3.5.9/        官方发布包裁剪后入库（约 33 MB）：test/、fuzz/、doc/、demos/ 只保留各级 build.info
                        （Configure 无条件读取它们，整目录删除时 Configure 报 fuzz/build.info 不存在）；
                        apps/ 下 11 个含私钥的演示文件（*.pem）也不入库：GitHub 的推送保护会拦截含私钥的提交，
                        而构建脚本不引用它们（我们只编库，不编命令行工具）
```

部署时往往只拷 `flamingoserver/`（用户的机器就是 `/opt/flamingoserver`），所以源码必须放在服务端目录里，不能引用 `../third-party`。两份上游源码都不修改任何文件。

### 11.2 编译方式

- **在 cmake 配置阶段编译，不用 ExternalProject。** 连接器在配置阶段就要用到 OpenSSL：`IF (NOT OPENSSL_FOUND) FIND_PACKAGE(OpenSSL)`，并检查 `${OPENSSL_INCLUDE_DIR}/openssl/evp.h`、用头文件做 `TRY_RUN`（上游 `CMakeLists.txt:305-336`）。在配置阶段用 `execute_process` 依次运行 configure、`make -j<CPU 核数>`、`make install` 装到构建目录下，之后 `find_package(OpenSSL)` 与连接器的检查都照常进行；并行度由 CMake 自己取，与用户敲的是 `make` 还是 `make -j` 无关。
- **只编一次。** 安装目录里放一个记录版本号与编译参数的标记文件，两者都没变时直接跳过；换版本、改参数或删掉构建目录后重编。失败时 `message(FATAL_ERROR)` 给出日志路径与最后几行。
- 构建目录在 `${PROJECT_BINARY_DIR}/deps-build/`、安装目录在 `${PROJECT_BINARY_DIR}/deps-install/`。用户在 `flamingoserver/` 里直接 `cmake .` 时它们会出现在源码目录中，`.gitignore` 忽略这两个目录。
- **libsodium**：`sh configure --enable-static --disable-shared --with-pic --disable-dependency-tracking`（仓库里的 configure 权限位是 644，用 `sh` 调用；它调用 config.guess 等辅助脚本时都经过 `$SHELL`）。Linux 的头文件目录与静态库都改用安装目录里的，`deps/libsodium/include` 只留给 Windows。
- **OpenSSL**：`perl Configure no-shared no-tests no-docs --prefix=<安装目录> --libdir=lib --openssldir=<安装目录>/ssl`，目标平台由 Configure 自动识别（不写死 `linux-x86_64`，aarch64 也能用），`make build_libs` 加 `make install_dev`。`make install_dev` 只装头文件、库与 pkgconfig 文件，不会创建 `<安装目录>/ssl`（第 4 步实测），所以编进库里的 OPENSSLDIR 是一个不存在的目录，运行时不会读取系统里别的版本的 `openssl.cnf`（CentOS 7 的是 1.0.2 的配置）。然后把 `OPENSSL_INCLUDE_DIR`、`OPENSSL_SSL_LIBRARY`、`OPENSSL_CRYPTO_LIBRARY` 设成安装目录里的文件，再调用 `find_package(OpenSSL)`，这一段移到 `WITH_MYSQL` 一段之前，连接器继承 `OPENSSL_FOUND` 后不再自己查找。
- **`WITH_SYSTEM_OPENSSL=ON`**：保持现在的行为：`find_package(OpenSSL QUIET)`，找到就启用 https，找不到时只支持 http。之前用自带 OpenSSL 配置过的构建目录，缓存里指向 `deps-install` 的三个路径先清掉再查找。
- **Perl 检查**（只在使用自带 OpenSSL 时）：`find_package(Perl)`，再用 `perl -M<模块> -e 1` 逐个检查所需模块，缺失时报错，列出缺的模块，并给出各发行版的安装命令。模块清单为实测结果（2026-10-12，在只装最基本 Perl 的容器里让 Configure 逐个报缺）：`FindBin`、`lib`、`IPC::Cmd`、`File::Compare`、`File::Copy`、`Time::Piece`。CentOS 7 只装 `perl` 时缺 `IPC::Cmd`、`Time::Piece`，`yum install perl perl-IPC-Cmd perl-Time-Piece` 后齐全；Rocky 8 只装 `perl-interpreter` 时缺 `IPC::Cmd`、`Time::Piece`，Rocky 9 缺全部六个，两者 `dnf install perl`（完整的 perl 元包）后都齐全，Rocky 9 上没有 `perl-core` 这个包；Ubuntu 24.04 的 `perl` 包本身就齐全。

### 11.3 HttpsClient 的根证书

自带的 OpenSSL 只会去 openssldir 找根证书，所以使用自带 OpenSSL 时（CMake 定义 `FLAMINGO_BUNDLED_OPENSSL`），`startTls` 在 `SSL_CTX_set_default_verify_paths` 之后，如果环境变量 `SSL_CERT_FILE`、`SSL_CERT_DIR` 都没设，就按下面的顺序探测系统证书包，用第一个存在的调用 `SSL_CTX_load_verify_locations`；结果只在第一次时写一条日志（找到的路径，或一个都没找到的警告）。

```
/etc/ssl/certs/ca-certificates.crt                    Debian、Ubuntu
/etc/pki/tls/certs/ca-bundle.crt                      RHEL、CentOS、Fedora、Rocky
/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem     RHEL 7 及以上的原始位置
/etc/ssl/ca-bundle.pem                                openSUSE
/etc/pki/tls/cacert.pem                               OpenELEC
/etc/ssl/cert.pem                                     Alpine
```

探测本身写成不依赖 OpenSSL 的纯函数（新文件 `utils/CaBundleLocator.h/.cpp`，判断文件是否存在的函数由调用方传入），便于单元测试。使用系统 OpenSSL 时不做探测，行为与现在相同。

## 14. 风险与注意

- OpenSSL 的安全更新从此由我们负责：出安全公告时升级 `openssl-3.5.9/`（换目录名与 CMakeLists 里的版本号）并重新部署。升级时照第 11.1 节裁剪，并删掉含私钥的演示文件（`grep -rlE "BEGIN ([A-Z0-9]+ )?PRIVATE KEY"` 找出来），否则推送会被 GitHub 拦下。需要跟随发行版补丁的部署方用 `-DWITH_SYSTEM_OPENSSL=ON`。
- 仓库增加约 40 MB（OpenSSL）与约 3 MB（libsodium）源码。
- 全新构建目录第一次 cmake 要多花约 40 秒（8 核），单核机器约 3 分钟。
- OpenSSL 3.x 的许可证为 Apache 2.0，libsodium 为 ISC，静态链接都没有额外义务，两份源码里的许可证文件保留。
