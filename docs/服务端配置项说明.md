# 服务端配置项说明

本文逐项说明 `flamingoserver/etc/` 下三个配置文件的含义。文件由 `base/ConfigFileReader` 解析，
格式为最简单的 `key=value`，每行一项。

## 通用约定

- **`#` 在一行中的任何位置都会开始注释**，其后内容一律被丢弃。因此 **value 中不能出现 `#`**：
  写 `password=abc#123` 实际取到的是 `abc`，而且不会有任何报错，属于最难排查的一类问题。
- **解析器不做编码转换，值按文件里的字节原样使用。** 仓库自带的三个配置文件以 UTF-8（不带 BOM）保存，
  注释里有中文。值里要写中文时（如 `defaultenterprise`、`defaultadminname`），文件必须保持 UTF-8；
  用 GBK 一类的编码保存，中文会以乱码写进数据库。
- **必填项只有下面几项**，缺失时服务拒绝启动，并一次列出全部缺失的配置项
  （`serverconfig::CRequiredConfig`，见 `flamingoserver/utils/ServerConfigLoader.h`）：

  | 配置文件 | 必填项 |
  | :--- | :--- |
  | chatserver.conf | `logfiledir`、`logfilename`、`listenip`、`listenport`、`monitorlistenip`、`monitorlistenport`、`monitortoken`、`httplistenport` |
  | fileserver.conf | `logfiledir`、`logfilename`、`filecachedir`、`filetokenkey`、`listenip`、`listenport` |
  | imgserver.conf | `logfiledir`、`logfilename`、`imgcachedir`、`filetokenkey`、`listenip`、`listenport` |

  其余配置项不在启动时统一检查：多数缺失时取内置默认值，少数（对外地址、令牌密钥等）缺失时
  依赖它的功能不可用，后文各节分别注明。另外，数据库初始化失败（例如 `dbtype=mysql` 时连接参数不对）时，
  服务记一条 FATAL 日志后主动结束（`base/AsyncLog` 的 FATAL 级别会让进程退出）。
  下表这几项，以及后文各节注明缺失时默认值的配置项，可以安全地不写：

  | 配置项 | 缺失时的行为 |
  | :--- | :--- |
  | `dbtype` | 按 `mysql` 处理，保证改造前的旧配置文件仍可用 |
  | `dbpath` | 取内置默认值 `data/flamingo.db` |
  | `defaultadminenable` | 视为启用，只有显式写 `0` 才关闭 |
  | `defaultadminemail` | 取内置默认值 `admin@flamingo.com` |
  | `defaultadminpassword` | 取内置默认值 `admin123` |
  | `defaultadminname` | 取内置默认值“超级管理员” |
  | `iothreadnum` | 取内置默认值（chatserver 与 fileserver / imgserver 均为 `6`） |
  | `monitoriothreadnum` | 取内置默认值 `1` |
  | `httpiothreadnum` | 取内置默认值 `4` |
  | `relayiothreadnum` | 取内置默认值 `4` |

  下文各表中的“配置文件中的值”一列，是仓库自带配置文件里的现值，**不代表省略该项也能得到同样的结果**。

- 相对路径的基准按配置项而不同：`dbpath`、`logfiledir`、`updatecachedir`、`cloudrecorddir` 以可执行文件所在目录为基准；
  `serverkeyfile` 以实际加载的那个配置文件所在目录为基准（见「协议加密」一节）；`filecachedir`、`imgcachedir`
  **以进程工作目录为基准**，所以启动服务时工作目录必须是 `flamingoserver/`。

## chatserver.conf

### 监听地址

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `listenip` | `0.0.0.0` | 客户端连接的监听地址，`0.0.0.0` 表示监听所有网卡 |
| `listenport` | `20000` | 客户端连接的监听端口，PC 端与安卓端都连这个端口 |
| `monitorlistenip` | `0.0.0.0` | 监控端口的监听地址 |
| `monitorlistenport` | `18889` | 监控端口，可用 `nc` / `telnet` 连接查看服务器实时状态 |
| `monitortoken` | `123` | 监控端口的访问口令，**部署前请修改** |
| `httplistenip` | `0.0.0.0` | **当前不生效**：代码不读取这一项，HTTP 端口实际监听在 `monitorlistenip` 上（见下文） |
| `httplistenport` | `12345` | HTTP 端口，企业管理控制台的接口与机器人的 Webhook（`/bot/webhook.do`）走这里 |

除 `httplistenip` 外，本节各项都是必填项。

> **`httplistenip` 的现状**：`chatserversrc/main.cpp` 初始化 `HttpServer` 时传入的是 `monitorlistenip`，
> 不是 `httplistenip`；代码注释说明这是既有行为，改动会影响现网部署的监听地址，须先与使用方确认，故照原样保留。
> 因此 HTTP 端口与监控端口总是监听在同一个地址上，要改 HTTP 端口的监听地址只能改 `monitorlistenip`，
> 而它同时决定监控端口的监听地址。

### 管理控制台长连接

flamingoAdmin 的 `FlamingoLink.dll` 用来实时查看企业在线用户的长连接端口（`docs/FlamingoLink方案.md`）。
三项**都可以省略**；加密沿用下文「协议加密」一节的 `encryption` 与 `serverkeyfile`，端口号与服务端公钥由
`/admin/login.do` 下发给控制台。部署在 NAT 或云安全组之后时，要放通这个 TCP 端口。

| 配置项 | 配置文件中的值 | 缺失时 | 说明 |
| :--- | :--- | :--- | :--- |
| `adminlinklistenip` | `0.0.0.0` | `0.0.0.0` | 监听地址，可只填内网地址 |
| `adminlinklistenport` | `20006` | 不开启 | 监听端口。缺失、为 0 或超出 1～65535 时不开启，`login.do` 回 `linkport=0`，控制台的「在线用户」页提示服务器未开启 |
| `adminlinkiothreadnum` | `1` | `1` | 该端口的 I/O 工作线程数，取值规则见文末一节 |

### 网络 I/O 工作线程数

客户端、监控、HTTP 三个监听端口各配一项（管理控制台长连接端口的 `adminlinkiothreadnum` 见上一节），单位：条线程。服务把这个数交给 `TcpServer`，由它建出同样条数的
I/O 工作线程（`EventLoopThreadPool`），该端口上所有连接的收发都摊在这些线程上。

**这一组可以整项省略**，省略时按下表的默认值运行 —— 默认值就是本组配置项引入之前
写死在代码里的那几个数，因此老配置文件不改也能启动，行为完全不变。

| 配置项 | 配置文件中的值 | 缺失时的默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `iothreadnum` | `6` | `6` | 客户端连接（`listenport`）所用的 I/O 工作线程数 |
| `monitoriothreadnum` | `1` | `1` | 监控端口（`monitorlistenport`）所用的 I/O 工作线程数。该端口同时只有零星几条 telnet 连接，一条线程足够 |
| `httpiothreadnum` | `4` | `4` | HTTP 端口（`httplistenport`）所用的 I/O 工作线程数。默认值 `4` 取自 `TcpServer::start` 声明里的默认参数 —— 本配置项引入之前这里调的正是不带参数的 `start()` |

取值规则对下面 fileserver.conf、imgserver.conf 里的同类配置项同样适用，见本文末尾的
「网络 I/O 工作线程数的取值规则」一节。

### 日志

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `logfiledir` | `logs/` | 日志目录，相对路径以 chatserver 可执行文件所在目录为基准，不存在时自动创建 |
| `logfilename` | `chatserver` | 日志文件名前缀，实际文件名会附加启动时间与进程号 |
| `logbinarypackage` | `0` | 是否把收发的二进制包体也写进日志。`1` 打开，仅用于排查协议问题，日志量很大 |

### 数据库

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `dbtype` | `sqlite` | 使用哪种数据库后端，取 `mysql` 或 `sqlite`。该项缺失时按 `mysql` 处理，保证旧配置文件仍可用 |
| `dbconnpool` | `1` | 是否启用数据库连接池，`1` 启用、`0` 关闭；缺失或为空时按启用处理。启用后用完的连接暂存起来供下一次访问直接使用，两种后端的空闲连接都在 10 分钟没有被使用后关闭；MySQL 的空闲连接另外定期 ping 保活 |

`dbtype=mysql` 时生效：

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `dbserver` | `127.0.0.1` | 数据库服务器地址 |
| `dbuser` | `root` | 登录用户名 |
| `dbpassword` | `123456` | 登录密码，**部署前请修改**；注意不能含 `#` |
| `dbname` | `flamingo` | 库名，不存在时首次启动会自动创建 |

`dbtype=sqlite` 时生效：

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `dbpath` | `data/flamingo.db` | 数据库文件路径 |

`dbpath` 的相对路径**以 chatserver 可执行文件所在目录为基准，而不是进程工作目录**。
这样无论从哪个目录启动服务，打开的都是同一个库；此前以工作目录为基准时，换一种启动方式
就会打开另一个库，现象看起来像是数据全部丢失。绝对路径（`X:\...`、`/var/...`、UNC 路径）
按原样使用。文件与其父目录会在首次运行时逐级自动创建。

> 若编译时使用了 `cmake -DWITH_MYSQL=OFF`，产出的二进制只支持 `sqlite`，此时 `dbtype`
> 必须为 `sqlite`。

### 默认超级管理员

chatserver 启动时会检查 `t_admin` 表中是否存在平台超级管理员（`f_enterprise_id = 0` 的记录）。
若不存在，则按以下配置创建一个，使全新部署的数据库也有账号可以登录管理控制台。
若已存在则既不创建也不覆盖 —— 在控制台里改过的密码不会被重启还原。

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `defaultadminenable` | `1` | `1` 表示超管不存在时自动创建，`0` 表示完全不碰数据库 |
| `defaultadminemail` | `admin@flamingo.com` | 该账号的登录邮箱 |
| `defaultadminpassword` | `admin123` | 该账号的初始口令 |
| `defaultadminname` | 未填（该行被注释掉） | 该账号的显示名，缺失时取内置默认值「超级管理员」。要填中文显示名，配置文件须以 UTF-8 保存 |

> **安全提示：** 上述默认口令在源码仓库中是公开的，任何正式部署前都必须修改，
> 或直接把 `defaultadminenable` 置为 `0`。另外该口令中**不能包含 `#`** —— 否则会被截断，
> 账号将以截断后的短口令创建，用完整口令反而登录不上。

### 默认企业

| 配置项 | 配置文件中的值 | 缺失时 | 说明 |
| :--- | :--- | :--- | :--- |
| `defaultenterprise` | `FlamingoIM.org` | `FlamingoIM.org` | 默认企业的全称。chatserver 每次启动时保证库里有这家企业：不存在时建出来（状态为活跃）并建好公司根部门；已存在时不改它的状态，只在缺少根部门时补建。值为空白时同样取 `FlamingoIM.org`，首尾空白会被去掉 |

PC 客户端注册窗「公司名称」的默认项取自客户端 `config/flamingo.ini` 的 `[ui] defaultcompany`，两边须配成同一个值，
否则用户不改默认名直接注册时会提示公司不存在；服务端不检查两边是否一致。可以写中文，此时本文件须保存为 UTF-8。
改名不会改动已建出的企业：原来那家企业仍然保留，启动时会按新名称再建一家。

### 文件与图片服务

| 配置项 | 配置文件中的值 | 说明 |
| :--- | :--- | :--- |
| `filetokenkey` | `flamingo-file-token-secret` | 文件上传下载令牌的 HMAC 密钥，**必须与 fileserver.conf、imgserver.conf 中的同名项一致**。缺失时文件功能不可用，云端录制也不启用（启动日志记 `cloud record disabled: filetokenkey not configured`） |
| `relaytokenkey` | `flamingo-relay-token-secret` | 全部中转令牌的 HMAC 密钥：imgserver 中转端口上的远程桌面、一对一音视频、屏幕共享、群通话、P2P 回落中转与云端录制控制连接，以及 fileserver 上的单聊文件夹传输与文件共享。**必须与 imgserver.conf、fileserver.conf 中的同名项一致**。缺失时这些中转功能不可用 |
| `fileserverhost` | `127.0.0.1` | 告知客户端 fileserver 的地址（单聊文件夹传输、文件共享的中转，客户端自动更新下载升级包）。**填写客户端可达的地址**，跨机器部署时不能保留 `127.0.0.1` 等本机回环地址 |
| `fileserverport` | `20001` | 同上，端口 |
| `imgserverhost` | `127.0.0.1` | 告知客户端去哪里上传下载图片与头像，同样须为客户端可达地址 |
| `imgserverport` | `20002` | 同上，端口 |
| `relayport` | `20003` | imgserver 中转端口（远程桌面、一对一音视频、屏幕共享、群通话、P2P 回落中转共用），须与 imgserver.conf 的 `relaylistenport` 一致；主机地址复用 `imgserverhost` |
| `cloudrecordhost` | 未填（该行被注释掉） | 云端录制控制连接要连的 imgserver 地址，缺失或为空时取 `imgserverhost`。chatserver 用 `relayport` 与 `relaytokenkey` 主动连 imgserver 的中转端口建控制连接，并按 imgserver 的身份签名完成加密握手（要求两边用同一份 `server_key`）；两台服务之间走内网时在这里另填内网地址。见 `docs/屏幕共享与录制方案.md` 12.6 |

> 除 `cloudrecordhost` 外，这几项是 chatserver **告诉客户端**去连哪里，不是自己监听的地址。跨机器部署时若仍填
> `127.0.0.1`，其他机器上的客户端会去连它自己那台电脑：远程桌面、一对一音视频、屏幕共享、群通话、单聊文件夹传输、
> 文件共享的中转全部连不上，P2P 地址探测失效，客户端自动更新下载升级包、云端录像的上传下载也会失败。例如屏幕共享
> 开始约 5 秒后提示「与屏幕共享服务的连接已断开，共享已结束。」（2026-10-12 实际遇到）。聊天里的图片和文件不受影响，
> 它们按客户端 `flamingo.ini` 里的地址连接。
>
> chatserver 启动时按**实际下发**的地址逐项检查（2026-10-14 起）：中转（`imgserverhost` + `relayport`）、P2P 地址探测
> （`p2pprobehost`，不配时按 `imgserverhost`）、云端录像传输（`imgserverhost` + `imgserverport`）、升级包下载与文件夹传输、
> 文件共享（`fileserverhost` + `fileserverport`）。地址是回环地址（`127.0.0.0/8`、`localhost`、`::1`）或未指定地址
> （`0.0.0.0`、`::`）时，每个配置项记一条 WARN 并列出受影响的功能（`config item imgserverhost=127.0.0.1 is reachable
> from this machine only, so clients on other machines cannot use ...`）；端口为 0、没有下发的功能不检查。判定见
> `utils/ConfigHostCheck.h`。三个服务部署在同一台机器上时，建议同时填
> `cloudrecordhost=127.0.0.1`，使 chatserver 到 imgserver 的云端录制控制连接留在本机，不经过公网地址。

### 远程桌面、通话、屏幕共享与群通话

下面几项**配置文件里没有写，代码会读取**（`chatserversrc/main.cpp`），缺失时按默认值运行；取值不合法时按各行所写处理。

| 配置项 | 缺失时的默认值 | 说明 |
| :--- | :--- | :--- |
| `rdofflinegracems` | `30000` | 远程桌面一方掉线后等待它回来的宽限期，单位：毫秒；不大于 0 时取默认值 |
| `callofflinegracems` | `30000` | 一对一通话一方掉线后等待它回来的宽限期，单位：毫秒；不大于 0 时取默认值 |
| `screensharemaxmembers` | `50` | 屏幕共享房间的人数上限（含发起人），单位：人；小于 2 或大于 254 时取默认值 |
| `screensharemaxcameras` | `9` | 屏幕共享房间里同时开摄像头的人数上限；小于 1 时取默认值，大于人数上限时取人数上限 |
| `screensharehostgracems` | `30000` | 屏幕共享发起人掉线后房间保留的宽限期，单位：毫秒；不大于 0 时取默认值 |
| `screensharemaxsharers` | `4` | 同时共享屏幕的人数上限（含主持人）；小于 1 或大于人数上限时取默认值（不超过人数上限） |
| `groupcallmaxmembers` | `16` | 群通话的人数上限（振铃中与已加入合计），单位：人；小于 2 或大于 254 时取默认值 |
| `groupcallmaxcameras` | `9` | 群通话里同时开摄像头的人数上限；小于 1 时取默认值，大于人数上限时取人数上限 |
| `groupcallofflinegracems` | `30000` | 群通话已加入的人掉线后等待他回来的宽限期，单位：毫秒；不大于 0 时取默认值 |

这几项的中转地址、令牌密钥都复用上一节的 `imgserverhost`、`relayport`、`relaytokenkey`。

### 单聊文件夹传输

单聊里把一整个目录发给对方（`cmd_folder_*` 1810~1817）用到的一组上限与超时。协议契约见
`docs/协议设计-v2.md` 的「文件夹传输协议（单聊）」一章，整体方案见 `docs/单聊文件夹传输方案.md`。

**这一组都可以整项省略**（与 chatserver.conf 里多数非必填项一样），省略时按下表的默认值运行，老配置文件不改也能启动。

| 配置项 | 配置文件中的值 | 缺失时的默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `foldermaxfiles` | `10000` | `10000` | 单次传输的文件数上限，单位：个。超限时 `cmd_folder_invite` 返回 `609` 并**回带本值**，客户端照它提示，不得硬编码 |
| `foldermaxsize` | `53687091200` | `53687091200` | 单次传输的总字节数上限，单位：字节（`53687091200` = 50 GiB）。超限时返回 `610` 并回带本值 |
| `folderlanes` | `4` | `4` | 数据通道条数，单位：条，**不含 lane 0 那条控制通道**；经 `cmd_folder_relay_info` 下发，客户端据此共建 `folderlanes + 1` 条连接。**硬上限 8**，写大了按 8 截断并记一条告警日志；写成 0 或负数按默认值 |
| `foldermaxsessions` | `24` | `24` | 整台服务器同时进行的文件夹传输会话数上限，单位：个。达到上限后新邀请返回 `619`。**Windows 建议 24，Linux 建议 128** |
| `foldermaxperuser` | `5` | `5` | 每个用户同时可参与的文件夹传输笔数，单位：笔。**发送与接收各算一笔**（发出 3 个文件夹、同时接收 2 个文件夹即已满额）；失败待重试的会话在 `folderretrywindow` 保留期内仍占名额。邀请的任一方满额时返回 `620` |
| `folderinvitetimeout` | `1800000` | `1800000` | 邀请发出后等待接收方应答的超时，单位：毫秒（`1800000` = 30 分钟）。超时后服务端结束会话并向双方推一帧「已超时」。取 30 分钟是因为接收方常常只是暂时离开座位；发送方随时可以主动撤回（`cmd_folder_cancel`），不必等超时 |
| `folderretrywindow` | `600000` | `600000` | 传输失败后会话的保留时长，单位：毫秒（`600000` = 10 分钟）。期内发送方点「重试」即断点续传、不再打扰接收方；期满会话销毁，只能重新发起 |

关于这几项，有四点容易被忽略：

- **中转地址与端口不在这里另配。** 文件夹的文件字节走 fileserver **现有的**监听端口（不新开端口），
  chatserver 下发给客户端的就是上面的 `fileserverhost` / `fileserverport` —— 与 `cmd_request_upload`
  应答里告诉客户端去哪里收发文件的是同一份配置。中转令牌的 HMAC 密钥同理复用 `relaytokenkey`。
  因此 **`fileserver.conf` 也要配上与 chatserver 一致的 `relaytokenkey`**：令牌由 chatserver 签发、
  由 fileserver 本地验签。
- **`foldermaxsessions` 是一道必需的闸门，不是可有可无的限流。** Windows 上 `EventLoop` 用的是
  `SelectPoller`，每个 I/O 线程最多盯 `FD_SETSIZE`（默认 64）条连接，超出时 winsock 的 `FD_SET`
  会**静默丢弃**——连接照样 accept 成功却永远收不到可读事件，表现为传输凭空卡住且日志里毫无线索。
  上层设闸就是为了在这之前先把新会话明确拒掉。Linux 走 epoll 没有这个限制，但闸门照设，两个平台行为一致。
- **`foldermaxsessions` 与 `foldermaxperuser` 是两道相互独立的闸门，估算前者时要按后者算。**
  一笔传输在服务端占用 `2 × (folderlanes + 1)` 条连接，默认配置下即每笔 10 条；单个用户满额
  （5 笔）时就是 50 条。因此 `foldermaxsessions=24` 在最坏情况下只够 5 个用户各自满额。
  调大 `foldermaxperuser` 时要连带复核 `foldermaxsessions` 与部署平台的连接数余量。
  两道闸门同时到顶时，`cmd_folder_invite` 先报每用户上限的 `620` 而不是服务器繁忙的 `619` ——
  前者对用户更有指导性（等自己那几笔里有一笔传完即可），后者只能干等。
- **`folderlanes` 的默认值 4 是两头夹出来的。** 一次传输在服务端占用 `2 × (folderlanes + 1)` 条连接
  （双方各一套）；多通道的收益在 2~4 条之间提升最明显，再往上迅速变平，而接收端并行写多个文件
  在机械硬盘上反而会退化成随机写。

| `encryption`、`serverkeyfile` | `1`、`server_key` | 协议加密，三个配置文件共有，见下文「协议加密」一节 |

本表中 `listenip`、`listenport`、`imgcachedir`、`logfiledir`、`logfilename`、`filetokenkey` 为必填项。

> `iothreadnum` 与 `relayiothreadnum` 相互独立，各管各的端口。`iothreadnum` 与 fileserver.conf 里的同名项也是各读各的，
> 见上一节的说明。

## 协议加密（三个配置文件共有）

chatserver.conf、fileserver.conf、imgserver.conf 各有这两项，由三个服务共用的 `serverconfig::InitProtocolEncryption`
（`utils/ServerConfigLoader.cpp`）读取。设计见 `docs/协议加密方案.md`。

| 配置项 | 配置文件中的值 | 缺失时 | 说明 |
| :--- | :--- | :--- | :--- |
| `encryption` | `1` | 按 `1` 处理 | `1` 表示三帧握手之后每个帧体都加密，`0` 表示明文（仅用于抓包排查）。缺失时按开启处理：安全开关往安全的方向失败，免得少写一行就把链路降成明文 |
| `serverkeyfile` | `server_key` | `server_key` | 服务端长期 Ed25519 身份密钥种子文件的路径。相对路径以**实际加载的那个配置文件所在目录**为基准（通常就是 `etc/`），与 `logfiledir`、`dbpath` 不同。文件不存在时首次启动自动创建，同时在旁边生成 `<serverkeyfile>.pub`（base64 公钥），把它填进客户端 `config/flamingo.ini` 的 `serverpubkey` |

- **三个服务必须指向同一个密钥文件**，否则客户端要为每个服务各配一把公钥；chatserver 连 imgserver 的云端录制控制连接也按这份密钥验签。
- 开着加密却加载不了密钥时，服务启动失败，不会退回明文继续运行。
- 种子文件是服务端的私有身份，不要提交进版本库；删掉它会让服务在下次启动时生成新的身份，所有客户端都得换用新公钥。

## 跨文件必须保持一致的项

改动其中任何一项时，三个文件都要同步修改，否则相关功能会以“令牌校验失败”或“连接不上”的形式失效：

| 项目 | 涉及文件 |
| :--- | :--- |
| `filetokenkey` | chatserver.conf、fileserver.conf、imgserver.conf |
| `relaytokenkey` | chatserver.conf、imgserver.conf（远程桌面、音视频、屏幕共享、群通话、P2P 回落中转与云端录制控制连接）、fileserver.conf（单聊文件夹传输与文件共享中转） |
| 文件服务端口 | chatserver.conf 的 `fileserverport` ↔ fileserver.conf 的 `listenport` |
| 图片服务端口 | chatserver.conf 的 `imgserverport` ↔ imgserver.conf 的 `listenport` |
| 中转端口 | chatserver.conf 的 `relayport` ↔ imgserver.conf 的 `relaylistenport` |
| P2P 地址探测端口 | chatserver.conf 的 `p2pprobeport1` / `p2pprobeport2` ↔ imgserver.conf 的同名项 |
| 客户端升级包目录 | chatserver.conf 与 fileserver.conf 的 `updatecachedir` 指向同一个目录 |
| 身份密钥文件 | 三个文件的 `serverkeyfile` 指向同一个文件 |

## 网络 I/O 工作线程数的取值规则

三个文件里共七项 —— chatserver.conf 的 `iothreadnum` / `monitoriothreadnum` /
`httpiothreadnum` / `adminlinkiothreadnum`，fileserver.conf 的 `iothreadnum`，imgserver.conf 的 `iothreadnum` /
`relayiothreadnum`。七项都经 `serverconfig::ReadIoThreadCountConfig` 读取，共用同一段取值判定（`serverconfig::ResolveIoThreadCount`，
见 `flamingoserver/utils/ServerConfigLoader.h`），规则如下：

- **合法取值是 1 到 256 之间的十进制整数**，此时原样采用。
- **取值非法时回落到该项的默认值**，并在日志里记一条告警，告警中同时写出**配置的值**与
  **实际采用的值**。非法包括这几种：整项缺失或写成 `key=`、不是十进制整数（如 `abc`、
  `4x`、`1.5`、`0x10`）、`0`、负数、大于 `256`。
- **是回落到默认值，不是截断到边界。** 写 `1000` 得到的是默认值而不是 `256`。这样设计是
  因为截断之后实际生效的线程数与配置文件里写的对不上，而排查问题的人手上往往只有配置文件，
  据此会得出错误的结论；回落再配上那条告警日志，「配的值没被采用」这件事才看得见。
- **上界 `256` 的依据。** Windows 上 `EventLoop` 用的是 `SelectPoller`，`select` 每条线程
  最多盯 `FD_SETSIZE`（winsock 下默认 64）条连接，线程数超过几十条之后再往上加已无实际
  意义，只是白白多出线程栈与调度开销。定这个上界主要是挡住「把端口号或字节数误填进线程数」
  这类笔误 —— 那类值动辄上万，真按它建线程会让服务在启动阶段就耗光资源。

告警日志的形态（`key` 与各数值随配置项不同而变）：

```
config item iothreadnum is invalid, configured value: "0", reason: value is out of the valid range, valid range: [1, 256], falling back to the default: 6 io thread(s).
```

取值合法时同样有一条日志，便于确认服务实际起了几条线程：

```
config item iothreadnum: using 12 io thread(s) from the config file.
```

相关单元测试：`flamingoserver/tests/test_iothreadcount.cpp`（Suite `IOT`）。
