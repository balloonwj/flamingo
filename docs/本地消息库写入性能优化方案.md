# 本地消息库写入性能优化方案

> 客户端把聊天消息存进本地 SQLite 库（`msgv2.db`）时，每条都要等磁盘确认一次，
> 100 条要花 0.6～1 秒，而这段时间全压在界面线程上。本文记录实测数据、根因，
> 以及两种改法的取舍。

2026-08-12

---

## 1. 问题从哪来

排查「登录后有大量离线消息时界面会不会卡」时顺出来的。先澄清一个前提：

**服务端不会在登录时把离线消息推给客户端。** 消息发出时就无条件落进服务端的
`t_chatmsg`（`chatserversrc/ChatSession.cpp:1888`），对端在线才推
`cmd_message_notify`，离线就留在库里（同文件 1902 行的注释写明了这条约定）。服务端
没有「离线消息队列」这类内存结构（见 `chatserversrc/MessageManager.h:6`），所以
chatserver 重启也不会丢。客户端登录后只拉一次会话列表（`cmd_sync_conversations`），
真正的消息体要等用户**打开某个会话**时才按会话拉，一次最多 100 条（服务端
`SYNC_MESSAGES_DEFAULT_LIMIT=20`、`SYNC_MESSAGES_MAX_LIMIT=100`）。

所以「登录瞬间被大量消息压垮」不成立，**但「打开一个积压了上百条未读的会话时界面
僵住」是真的**，下面的数据能证明。

---

## 2. 实测数据

用例：`flamingoclient/Source/Tests/MsgStoreWriteBenchTests.cpp`，落 100 条中等长度的
文本消息，只计落库那一段（不含建库建表）。测试机为固态盘，机械盘只会更慢。

| 组 | 配置 | 第一轮 | 第二轮 | 第三轮 |
| --- | --- | --- | --- | --- |
| **A** | **现状**：`CV2MsgStore::Upsert` 逐条，默认配置、无事务 | **1055 ms** | **651 ms** | **612 ms** |
| B | 裸 sqlite 复刻同一条 SQL，配置同 A（用来印证 A 可信） | 929 ms | 601 ms | 602 ms |
| C | 默认配置 + 整批一个事务 | 23.6 ms | 12.0 ms | 14.2 ms |
| D | WAL + `synchronous=NORMAL`，无事务 | 34.6 ms | 11.8 ms | 13.5 ms |
| E | WAL + `synchronous=NORMAL` + 整批一个事务 | 19.0 ms | 5.7 ms | 5.7 ms |

第一轮整体偏高是冷启动（文件系统缓存未热），后两轮为稳态。

**换算成单条**：现状每条 6～10 毫秒，正是一次 fsync 的典型开销；WAL 下每条降到
0.12～0.35 毫秒。

B 与 A 相差 5%～14%，说明裸 sqlite 的复刻可信，C/D/E 的对比数字站得住。多出来的那点
是 `CV2MsgStore` 的互斥锁与记录拷贝，不是主要矛盾。

---

## 3. 根因

两条，各自独立：

1. **每条 INSERT 都是一次独立事务。** `CV2MsgStore::Upsert`
   （`BalloonHistory/V2MsgStore.cpp:221`）是「prepare → bind → step → finalize」一条一条
   来的，调用方的循环外面没有事务包裹。SQLite 在没有显式事务时会给每条语句<u>隐式</u>
   开一个事务并提交，提交就要落盘。

2. **落盘方式取的是最保守的一档。** `CV2MsgStore::Open`（同文件 108 行）只有
   `sqlite3_open16` 加建表 SQL，<u>没有设置任何 PRAGMA</u>，于是走 SQLite 默认的
   `journal_mode=DELETE` + `synchronous=FULL`：改数据前先把原页抄进回滚日志文件，
   改完删掉，且每次提交都等磁盘确认。一次写要动三个文件、等一次 fsync。

---

## 4. 写入点盘查

本地库的写入调用一共五处，全部在 `CBalloonMainPanel` 里、全部由窗口消息触发，
也就是**全在界面线程上**（`CV2MsgStore` 里那把互斥锁是兜底，不是因为真有并发写）：

| 位置 | 函数 | 形态 | 事务能否救 |
| --- | --- | --- | --- |
| `BalloonMainPanel.cpp:4023` | `OnSyncMessagesArrived` | 一批最多 100 条 | 能，正是它 |
| `BalloonMainPanel.cpp:3717` | `OnPinnedMessagesArrived` | 一批，条数看 Pin 数量 | 能 |
| `BalloonMainPanel.cpp:2646` | `OnRecvChatMessage` | **单条**（实时推送） | **不能** |
| `BalloonMainPanel.cpp:4349` | `OnMessageRecalled` → `MarkRecalled` | 单条 | 不能 |
| `BalloonMainPanel.cpp:3608` | `OnMessagePinned` → `SetPinned` | 单条 | 不能 |

**这张表带出一个关键结论：事务只解决批量场景。** 实时收到一条新消息时只有一次写，
事务包一条和不包没有区别，仍然是 6～10 毫秒的界面线程开销。群聊高峰期消息一条接一条
地来，这个开销就一直存在——那种场景**只有 WAL 能救**（每条从 6～10 毫秒降到
0.12～0.35 毫秒，约 30～50 倍）。

## 5. 改法一：批量落库包进一个事务

### 设计

不在调用方直接写 `BEGIN` / `COMMIT` 的裸 SQL —— 本地库的所有 SQL 都收在
`CV2MsgStore` 里，调用方不碰 SQL 语句，这条边界不该为了这次优化破掉。故在
`CV2MsgStore` 上新增一对方法，并配一个 RAII 守卫：

- `bool BeginBatch()` —— 开一个显式事务。已经在事务里时直接返回 true（幂等，
  见下面「重入」一条）。
- `void EndBatch(bool commit)` —— 提交或回滚。
- `class CV2MsgStore::BatchGuard` —— 构造时 `BeginBatch`、析构时提交。调用方只需要在
  循环前声明一个局部变量，中途 `return` 或抛异常也不会把事务悬着。

### 要处理的三种边界

1. **开事务失败**：`BEGIN` 执行不成功时**照常往下写**，只是退回逐条落盘的老行为。
   落库比快更重要，不能因为开不了事务就把消息丢了。

2. **重入**：五个写入点都在界面线程上、互不嵌套，正常不会重入。但为了防止日后有人在
   批量循环里间接调到另一个批量落库，`BeginBatch` 记一个计数，非最外层的调用直接返回
   成功、也不重复提交——SQLite 不支持嵌套事务，重复 `BEGIN` 会直接报错。

3. **中途某条写失败**：不回滚整批。这些消息彼此独立，一条内容异常不该让另外 99 条也
   进不去；失败那条记日志即可。

### 改动清单

| 文件 | 改动 |
| --- | --- |
| `BalloonHistory/V2MsgStore.h` / `.cpp` | 新增 `BeginBatch` / `EndBatch` / `BatchGuard` |
| `BalloonMain/BalloonMainPanel.cpp:4007` | `OnSyncMessagesArrived` 的循环前放一个 `BatchGuard` |
| `BalloonMain/BalloonMainPanel.cpp:3704` | `OnPinnedMessagesArrived` 同上 |

### 收益与风险

收益：批量落库从 0.6～1 秒降到 12～24 毫秒（约 45 倍）。

风险基本为零，而且**比现在更安全**：现在写到第 50 条时程序崩溃，库里会留下前 50 条的
半截状态；包进事务后只有「全进」或「全不进」两种结果。落盘的严格程度一点没动。

## 6. 改法二：WAL + `synchronous=NORMAL`

### 做什么

在 `CV2MsgStore::Open` 里建表之前执行两句设置：日志方式改成 WAL（新数据追加写进
一个日志文件、攒够了再合并回主库，不必每次都动三个文件），落盘严格程度降一档
（写完交给操作系统安排刷盘，不死等磁盘确认）。

`journal_mode` 是写进数据库文件本身的，设一次长期有效，存量库下次打开自动转换。

### 收益

- 批量场景：与事务叠加后 5.7 毫秒（约 110 倍），且三轮里最稳。
- **单条推送场景：只有它能救**，每条 6～10 毫秒 → 0.12～0.35 毫秒。这是事务覆盖不到的
  那一半，见第 4 节。

### 代价与风险

1. **突然断电 / 操作系统蓝屏时，最后几条刚写的消息可能没落到盘上。** 要区分清楚：
   **程序自身崩溃或被强制结束进程不会丢**（内容已交给操作系统），只有整机掉电才会。
   而且丢的是最后几条，不会损坏数据库。

   这个风险在本场景里很轻：**本地库只是缓存，服务端才是消息的正主**（见第 1 节）。
   最坏情况是断电重开后那几条重新从服务端同步下来。

2. **数据库目录下会多出 `-wal` 与 `-shm` 两个文件。** 关库时会合并回主库。备份 / 清理
   用户数据的地方要连它们一起处理，只拷主库文件可能丢掉最后一部分。

3. **WAL 不能用在网络盘上。** 本地库放在用户个人目录的 `ChatLog` 子目录下，正常是本机
   路径；但公司若启用了漫游配置文件（个人目录映射到服务器），就可能踩到。
   <u>此项未实测</u>。故实现上必须做到：设置失败时记一条日志、退回默认方式继续跑，
   绝不能因为设不上 WAL 就打不开消息记录。

## 7. 验证方式

基准用例已就位：`Source/Tests/MsgStoreWriteBenchTests.cpp`，标签 `[.][msgstorebench]`。

标签以 `.` 开头是 Catch2 的隐藏标签约定，**默认不参与全量回归**——它真刷盘、耗时随
机器负载波动，混进常规用例里既拖慢又会看起来忽快忽慢。要跑就显式指定：

```
Bin\Tests\Win32\Debug\FlamingoUnit.exe "[msgstorebench]"
```

数字用 `WARN` 输出（Catch2 的 `INFO` 只在断言失败时才打印）。用例只断言「跑完了」，
不断言具体快慢——写死阈值必然变成一条时不时误报的用例。

改完之后重跑一次，A 组的数字应当落到 C 组（只做事务）或 E 组（两个都做）的量级。

## 8. 分期与取舍

| 期 | 内容 | 理由 |
| --- | --- | --- |
| 一 | 改法一（事务） | 收益最大的一步，零安全折衷，不引入新文件 |
| 二 | 改法二（WAL） | 覆盖单条推送那一半场景；需先确认网络盘的情况 |

两期互不依赖，可分别提交。

先前只做第一期的建议，是在还没盘查全部写入点时给的；盘查之后发现**实时收消息那条路
只有第二期能救**（第 4 节），故第二期不是可有可无的锦上添花。是否连做，取决于对
「群聊高峰期每条消息 6～10 毫秒界面开销」的容忍度。
