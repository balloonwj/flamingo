# 消息改写离线同步方案

balloonwj@qq.com　2026-10-08

本文解决的问题是：服务端改写了一条已经发出去的消息（公告卡片被删、通话结束、屏幕共享改标题、帖子被编辑或删除……）之后，当时不在线的成员登录时收不到这次改写，本地聊天记录里一直是旧样子。帖子群卡片的删除已经用 2716（`cmd_thread_check_cards`）单独补上，本方案把它推广成对所有改写都适用的办法。

状态：已实施（2026-10-08）。第 5 节的五个取舍与第 6 节的测试用例均已由用户确认（全部采用推荐项），各步结果见第 7 节。

---

## 1. 现状（据实证）

### 1.1 服务端改写消息只有一个入口

服务端改写 `t_chatmsg.f_content` 一律经由 `MessageManager::updateMessageContent(msgid, storedContent)`（`chatserversrc/MessageManager.cpp:1076`），它同时更新 `f_search_text`，不改 `f_msgtype`。除此之外只有撤回（`recallMessage`，`MessageManager.cpp:1047`，只改 `f_recalled` / `f_recalled_by`）和 `f_search_text` 的存量回填会写这张表，没有删除行的语句（删除消息是本人视角，记在 `t_message_deleted` 等表里，不动 `t_chatmsg`）。

调用 `updateMessageContent` 的地方共六处：

| 编号 | 卡片 | 改写位置 | 改成什么 | 给在线成员的推送 |
| --- | --- | --- | --- | --- |
| A | 群公告卡片（msgtype 22） | `ChatSession::rewriteAnnouncementCardAsDeleted`（`ChatSession.cpp:6749`） | 去掉正文，`deleted:true` | 1326 `cmd_group_announcement_notify` |
| B | 单聊通话卡片（msgtype 16，kind `call`） | `CallCardWriter::finishCard`（`CallCardWriter.cpp:71`）；拒接、取消、挂断，以及**对方离线时的超时回收**（`main.cpp:150`、`:1057`） | 加上结局、结束时间、时长 | 1717 `cmd_call_card_notify` |
| C | 群通话卡片（msgtype 16，kind `groupcall`） | `GroupCallService::finishRoom`（`GroupCallService.cpp:729`） | 加上结束时间、时长 | 1750 `cmd_groupcall_status_notify` |
| D | 屏幕共享卡片（msgtype 19） | `ScreenShareService.cpp` 的 `handleSetInfo`（`:1009`） | 换成新标题、新描述 | 1734 `cmd_screenshare_info_notify` |
| E | 帖子卡片（msgtype 25）被编辑 | `ChatSessionThread.cpp:578` | 新标题、新摘要 | **没有卡片推送**，只有帖子群窗口用的 2720 |
| F | 帖子 / 评论 / 补充卡片（msgtype 25 / 26）被删除 | `rewriteThreadCardDeleted`（`ChatSessionThread.cpp:1388`） | 去掉标题摘要，`deleted:1` | 2721 `cmd_thread_cards_notify`；离线由 2716 补 |

投票、接龙、待办、文件共享、入群邀请这几种卡片的状态不存在 `f_content` 里，服务端在返回消息时现查现拼（`ChatSession::augmentCardRecord`，`ChatSession.cpp:9292`），离线成员拉到消息时自然是最新状态，不在本方案范围内。

### 1.2 离线成员为什么收不到

- `t_chatmsg` 没有修改时间或版本号一类的列（`table_mysql.sql` 的 t_chatmsg 定义），服务端无从回答「自某时起哪些消息被改过」。
- 客户端登录后只拉会话列表（1501，摘要取的是当前行，所以会话列表里的摘要是新的）；打开聊天窗口时拉最新一页（1502，before 模式），消息记录窗按需回补。拉到的每一页用 `UpsertBatch` 整行覆盖本地库。所以**被改写的消息只有恰好落在某次重新拉取的页里才会更新**；更早的消息，本地库里永远是旧的。
- B 类里「对方离线时超时回收」这一种，改写发生时必然有人不在线。

### 1.3 在线推送路径上的两个附带问题

- B、C、D 三类的客户端处理最终调用 `CV2MsgStore::UpdateContent`（`UPDATE t_msg SET content=?`），**不更新 `raw` 与 `search_text` 两列**：本地搜索仍按旧标题命中，按 `raw` 重建消息的地方拿到的也是旧内容。
- E 类在线时也不推卡片，群聊记录里的帖子卡片要等下次重新拉取才会变。

### 1.4 撤回有同样的缺口

离线期间被撤回的消息，本地库只在收到 1509 推送时改 `recalled`（`V2MsgStore.cpp:168`），否则同样要等重新拉取那一页。撤回通常发生在刚发出的消息上，多数落在打开窗口时拉的最新一页里，所以实际很少暴露；但群主、管理员撤回较早的群消息时会遇到。

## 2. 两种做法

### 做法一（推荐）：给消息加「改写序号」，登录后按序号拉取被改写过的消息

- 服务端：`t_chatmsg` 加一列 `f_rev`。每次 `updateMessageContent` 与撤回（见 5.2）给这条消息分配一个**全局递增**的序号写进这一列。新增命令 1526 `cmd_sync_rewritten_messages`：客户端带上「我已同步到的序号」，服务端返回本人可见、序号更大的消息（完整消息体，与 1502 的条目同形），按序号升序分页。
- 客户端：每个账号在本地库里记一个水位（已同步到的最大序号）。登录拿到会话列表之后发一次 1526，一页一页拉完；每条消息**只在本地库里已有这一行时**用 `UpsertBatch` 覆盖（content、raw、search_text、recalled 一起更新），本地没有的行跳过；拉完把水位推到应答里的最大序号，再刷新受影响的已打开窗口。

优点：
- 与卡片类型无关。以后新增任何一种会被改写的卡片，只要走 `updateMessageContent`，离线同步自动就有，客户端不用改。
- 每次登录只传「上次以来被改过」的那几条，通常是个位数。
- 走的是与 1502 相同的整行覆盖，顺带修好 1.3 第一条：离线期间的 B / C / D 改写落库时 raw 与 search_text 也是新的。在线时收到推送、只更新了 content 的那些行，下次登录时也会因为序号大于水位被重新覆盖一遍。

代价：
- 服务端改表（加列、加索引）、加一条命令；客户端加一条命令和一个水位。
- 通话卡片每次通话都会改写一次，序号增长较快；但每次登录只拉增量，影响的只是查询条数，不影响正确性。
- 第一次使用时（水位为 0）会把本人可见范围内历来所有被改写过的消息都拉一遍，见 3.4。

### 做法二：把 2716 推广到所有卡片类型

客户端在本地库里按类型挑出「还可能被改写」的卡片（公告未删除、通话没有结局、群通话没有结束时间、屏幕共享、帖子），把它们的 msgid 分批发给服务端；服务端逐条比较，把内容变了的返回。

缺点：
- 客户端要按卡片类型维护「什么样子算终态、不会再变」的规则。屏幕共享卡片与帖子卡片**没有终态**（随时可能改标题、被编辑），每次登录都要把本地所有这类卡片发一遍。
- 每新增一种会被改写的卡片，都要同时改服务端返回规则和客户端挑选规则，漏改一处就静默失效，正是离线成员收不到改写这一类问题的来源。
- 撤回无法用同一套机制覆盖。

**推荐做法一。** 下文按做法一展开。

## 3. 做法一的设计

### 3.1 服务端存储

- `table_mysql.sql` 的 `t_chatmsg` 加列 `f_rev bigint(20) NOT NULL DEFAULT 0 COMMENT '改写序号:0表示从未被改写;每次改写内容或撤回时取全局递增的新值'`，加索引 `KEY idx_rev (f_rev)`。重新运行 `tools/gen_table_sqlite.py` 生成 SQLite 那两份文件。
- 存量库：2026-10-09 起启动时不再给已有的表补列（见 `docs/SQLite本地数据库模式方案.md` 第 12 节），已有的库须手工加列与索引。
- 序号的分配：`MessageManager` 启动时读一次 `SELECT MAX(f_rev) FROM t_chatmsg` 作为起点，之后在内存里加锁递增；改写时把新序号与新内容放进**同一条** `UPDATE`，撤回时与 `f_recalled` 放进同一条 `UPDATE`（`recallMessage`，`MessageManager.cpp:1047`）。`f_search_text` 的存量回填不分配序号。服务端是单进程，不需要数据库序列。

### 3.2 新命令 1526 `cmd_sync_rewritten_messages`

请求：

```json
{ "since": "1234", "limit": 200 }
```

- `since`：客户端已同步到的序号，首次为 `"0"`。按协议对 64 位值的约定以字符串编码；缺省、不是字符串或为负时按 0 处理。
- `limit`：本页最多几条，上限 200（常量 `REWRITTEN_SYNC_LIMIT_MAX`）；缺省或不大于 0 时取 200（与 1502 缺省取默认值的做法一致），超过时截到 200。

应答：

```json
{
  "code": 0,
  "items": [ { "ctype": 2, "cid": "268435457", "msgid": "88231", "...": "与 1502 应答 messages[] 的条目同形", "rev": "1301" } ],
  "rev": "1301",
  "more": true,
  "currev": "5120"
}
```

- `items`：按 `f_rev` 升序。每条与 1502 的消息条目字段完全相同（客户端直接复用解析与落库代码），另加字符串编码的 `rev`。
- `rev`：本页最后一条的序号，客户端下一页以它为 `since`；本页为空时等于请求的 `since`。
- `more`：后面还有没有。
- `currev`：服务端当前的最大序号，用于 3.4 的首次同步优化。

可见范围（据实证，与全局搜索 `MessageManager::globalSearchConversations` 的条件相同）：单聊取 `f_from` 或 `f_to` 是本人的；群聊取本人**当前**所在的群，每个群按 `GroupProtocol::computeHistoryBound` 算出的入群时间下界、「同步最近 N 条」的 msgid 下界过滤（`ChatSession::onGlobalSearch` 构造 `GroupSearchScope` 的做法）；再加上 `visibleToUserClause(userid)`（本人删除、清空过的消息以及 `f_audience` 受限且本人不在名单里的消息都不返回）。

条目的加工与 1502 相同（`ChatSession::onSyncMessages`）：投票、接龙、待办、文件共享、入群邀请卡片经 `augmentCardRecord` 合并当前状态；本人发出的文件消息补上 `fileackstate`；条目由 `messageBodyValue` 生成，`cid` 取本人视角（群聊为群 id，单聊为对方 userid）。

按体积截断：一页里有几条长消息时应答可能超过客户端的单帧上限，与 1502 一样受 `RESPONSE_MESSAGES_BUDGET_BYTES` 约束。现成的 `trimMessagesToBudget` 只接受一个统一的 `cid`，1526 一页里有多个会话，因此另写一个按条累计体积的组装函数：从序号小的一端起逐条加入，超出预算就停，`rev` 取最后加入的那一条，`more` 置为 true。这样被截掉的都是序号大的那一端，下一页从 `rev` 接着取，不会漏。一条消息本身就超过预算时仍单独放进一页（与 1502 的处理一致），避免卡在同一个序号上。

### 3.3 客户端

- 水位存在本账号的 `msgv2.db` 里（键值表 `t_sync_meta`，键名 `rewritten_rev`；没有用 `t_fts_meta`，理由见第 7 节 2b），与本地库同生共死：本地库被删掉重建时水位自然归零。
- 触发时机：登录成功时（含断线重连）由 `MainPanelSessionController` 调 `OnRewrittenSyncLoginSucceeded` 开始一轮（不挂在「会话列表到达」上，理由见第 7 节 2c）。
- 应用：每页逐条判断本地库有没有这一行，有就加进一批交给 `UpsertBatch`，没有就跳过；整页处理完再推进水位。中途断线时水位停在上一页，下次从那里继续。
- 刷新界面：受影响的会话若开着聊天窗口或消息记录窗，按会话刷新一次（复用现有「重新从本地库加载」的入口，实现时确认每类窗口用哪个）；会话列表摘要已由 1501 保证是新的，不用处理。
- 纯逻辑放进一个独立的小模块（「这一页里哪些条目要落库、水位推到多少」），便于单测。

### 3.4 第一次同步

升级后第一次登录时水位为 0，服务端会把本人可见范围内历来被改写过的消息都返回（一页 200 条，通话多的用户可能有几十页）。两种情况：
- 本地库是空的（新装、换电脑）：没有一行需要更新，客户端直接把水位设成 `currev`，不必一页页拉。
- 本地库里有存量记录：照常一页页拉完。这是一次性的，之后每次登录只拉增量。

存量的改写在加列之前发生，`f_rev` 都是 0，**不会**被这次同步补上；只有加列之后的改写会同步（用户已确认接受，见 5.4）。

## 5. 已确认的取舍（2026-10-08，用户逐项确认，全部采用推荐项）

5.1 **采用做法一（改写序号）。**

5.2 **撤回也分配改写序号。** `recallMessage` 的那条 `UPDATE` 里多写一列；1526 返回的整行带 `recalled`，客户端落库时一起更新，不用另做处理。离线期间较早的消息被撤回（群主、管理员撤回别人的旧消息）的问题顺带解决。

5.3 **帖子被编辑时也给在线成员推 2721。** 服务端改写卡片后补一次推送；客户端处理 2721 的 `ApplyThreadCardToStore`（`Source/Feature/ThreadGroup/ThreadCardSync.cpp:102`）按收到的卡片内容整体替换，不只认「已删除」，客户端不用改（据实证，读代码）。

5.4 **加列之前已经发生的改写不补同步。** 存量消息的 `f_rev` 为 0，服务端不知道它们以前有没有被改过；从升级那一刻起生效。

5.5 **客户端停用 2716，服务端保留。** 1526 联调通过后，客户端删除 `CheckThreadCardsOnce`、`LoadLiveThreadCardIds` 等只为 2716 服务的代码，登录时不再发整批 msgid；服务端 2716 的处理与用例保留，以后需要按 msgid 核对时还能再用。帖子群是本分支新做的功能，据推测还没有发布过，加列之前的帖子删除只存在于开发与测试环境，停用 2716 后这些不再补同步。

## 6. 测试用例（2026-10-08 用户已确认）

服务端（doctest，`flamingoserver/tests/test_rewrittensync.cpp`，用 SQLite 测试库）：

- **RW1** 新消息的 `f_rev` 为 0；`updateMessageContent` 之后变为大于 0，两次改写同一条消息，第二次的序号更大。
- **RW2** 两条不同消息先后改写，序号严格递增；服务端重启（重新读 `MAX(f_rev)`）后再改写，序号接着增长、不与旧值重复。
- **RW3** 撤回分配序号，撤回后经 1526 取出的条目 `recalled` 为 1；只更新 `f_search_text` 的存量回填**不**分配序号。
- **RW4** 1526 请求解析：缺 `since`、`since` 不是字符串或为负时按 0 处理；`limit` 缺省或不大于 0 时取 200，超过 200 时截到 200（实现时与 1502 的缺省规则对齐，原写法为「超出 1 ~ 200 时截到边界」）。
- **RW5** 只返回 `f_rev > since` 的消息，按序号升序；`limit` 生效，`more` 与 `rev` 正确；空页时 `rev` 等于 `since`、`more` 为 false。
- **RW6** 可见范围：单聊只返回本人是收发一方的；群聊只返回本人当前所在群的；退群之后不再返回那个群的改写；`f_audience` 为 1 且本人不在名单里的不返回。
- **RW7** 条目字段与 1502 的消息条目逐字段一致（同一条消息分别经 1502 与 1526 取出，比较 JSON），另带 `rev`。
- **RW8** `currev` 等于当前最大序号。
- **RW9** 编辑帖子：卡片被改写并分配序号，同时向群成员推 2721，推送里的卡片是新标题、新摘要（放在 `tests/test_threadgroup.cpp`，与 TG15 / TG16 同处）。

客户端（Catch2，标签 `[rewrittensync]`）：

- **RWC1** 请求编码：`since`、`limit` 正确写入。
- **RWC2** 应答解析：条目复用 1502 的解析，`rev`、`more`、`currev` 正确；缺字段时取安全的默认值。
- **RWC3** 应用一页：本地已有的行被整行覆盖（content、raw、search_text、recalled 都更新），本地没有的行不插入。
- **RWC4** 水位：整页处理完才推进到 `rev`；处理中途失败（模拟落库失败）时水位不动。
- **RWC5** 首次同步：水位为 0 且本地库为空时直接设成 `currev`，不发后续页；本地库非空时照常逐页拉取。
- **RWC6** 水位按账号隔离：A 账号的水位不影响 B 账号。
- **RWC7** 登录后、断线重连后各触发一次；`more` 为 true 时接着发下一页，为 false 时停止。
- **RWC8** 受影响的会话开着窗口时触发刷新，没开的不触发；一页里同一会话多条只刷新一次。
