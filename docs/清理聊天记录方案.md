# 清理聊天记录方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-09-30
> 用途：记录「按时间范围清理聊天记录」「消息记录窗删除单条消息」「消息记录窗看到服务端全部历史」三项功能的整体方案与开发步骤；2026-10-02 补充的「按会话清空聊天记录」见第 16 节。后续每步开工前据此细化测试用例、收尾后回填实际结果。

## 1. 需求

1. 系统设置 → 聊天页新增「清理聊天记录」按钮，按时间范围清理。时间范围既有预设档位，也能自定义到日期与时、分。
2. 清理同时作用于本机与服务端，按本人视角软删除，对方不受影响。
3. 消息记录窗的右键菜单新增「删除」，删除单条消息。
4. 消息记录窗能看到服务端上的全部历史：翻到本地最早一页时，继续向服务端拉取更早的消息。
5. 聊天窗现有的「删除」菜单项（目前只从界面移除这一行，见 `ChatMessageMenu.h` 的 `kChatMsgMenuDelete`）改为与消息记录窗相同的真删除。

以下口径均已与用户逐条确认，实现时不再另行请示：

| 决策点 | 取值 | 详见 |
| --- | --- | --- |
| 清理范围 | 本机 + 服务端 | §3、§5 |
| 服务端存储方式 | 每次清理只记一条时间区间，不逐条展开；清理完成后不显示具体条数 | §5 |
| 区间的语义 | 本人在该时间段内的全部单聊与群聊消息都隐藏，包括以后新加入的群在该时间段内的历史 | §3 |
| 本地对账删除 | 采用：服务端在某段 msgid 范围内没有返回的消息，本地同步删除 | §7.3 |
| `t_chatmsg.f_create_time` 索引 | 不加（改为区间记录后不再需要） | §5 |
| 聊天窗「删除」 | 改为真删除，单条与多选都改 | §10 |
| 预设档位 | 全部 / 最近 1 天 / 最近 7 天 / 最近 30 天 / 7 天以前 / 30 天以前 / 3 个月以前 / 半年以前 / 1 年以前 / 自定义 | §11 |
| 同步应答回带 `beforemsgid` | 采用 | §4 |
| 登录后清空覆盖区间 | 采用 | §7.4 |
| 导出范围 | 只导出已加载到本地、且在覆盖区间内的记录 | §9.3 |
| 没有覆盖区间时的显示 | 照旧显示全部本地记录，区间建立后再收窄（断网时仍能翻本地记录） | §9.2 |

## 2. 调查结论

以下各条均有代码依据（行号为 2026-09-30 的状态）。

1. **只删本地会被服务端数据重新填回来。** 打开消息记录窗时，`CBalloonMainPanel::OpenHistory` 向服务端回填本会话最新 100 条并写入本地库；打开聊天窗时，历史消息直接从服务端拉取（`BalloonChatWindow.cpp`），同步回来的消息同样写入本地库。
2. **服务端已有本人视角的软删除，只缺按时间范围批量删除。** `cmd_delete_message`（1512）按单条 msgid 写入 `t_message_deleted`。同步、搜索、会话列表预览、未读数、Pin 列表都经 `MessageManager.cpp` 的 `visibleToUserClause`（原名 `notDeletedClause`）或 Pin 查询里的同类条件（`MessagePinManager.cpp` 的 `buildPinnedWhere`）过滤。
5. **本地库在时间上有断层。** Pin 列表会把任意久远的消息写进本地库（服务端最多返回 200 条、不限时间），聊天窗往上翻页、实时推送也都写入本地库。因此不能用"本地最早一条"作为向服务端继续拉取的锚点。
6. **服务端数据库操作在网络 I/O 线程上同步执行**（`MessageManager.h` 里会话未读数上限的注释记有实测：数未读一次两秒多，期间占着 I/O 线程）。逐条展开写入删除记录，数量大时会卡住同一 I/O 线程上的其他用户。
7. **客户端本地库在 UI 线程上同步读写**（`UI/BalloonHistory/V2MsgStore.h`），当时只有 `(ctype,cid,timestamp)` 与 `(ctype,cid,msgtype)` 两个索引，"所有会话里某时间段"的删除只能全表扫描。
8. **消息记录窗已有右键菜单**，菜单项由纯函数 `BuildHistoryRowMenuModel`（`HistoryRowMenu.h/.cpp`）生成，有 HRM 组单测；时间筛选已用「年 / 月 / 日」下拉框实现自定义日期（`BalloonHistoryWindow.cpp` 的 `DateToUnixMs`）。
9. **服务端支持同一用户在不同客户端类型上同时登录**；`ChatSession::sendToUser` 会推给本人全部会话，包括发起请求的这一台。
10. **服务端消息时间精度只到秒**（写入时取 `time(NULL)*1000`）。

## 3. 语义说明

- **对方不受影响。** 删除只作用于删除者本人：服务端过滤条件按请求者的 userid 查，消息本体仍在 `t_chatmsg`。B 看与 A 的聊天记录不变，群内其他成员也不受影响。
- **删除不等于撤回。** 要让对方也看不到，只能用撤回。
- **删掉的内容可能以新消息的形式回来。** 对方引用或转发那条消息给本人时，本人会看到其中的内容。Pin 是会话内共享的状态：本人删掉一条被钉住的消息后，本人的 Pin 列表里不再有它，对方仍显示已钉住。
- **会话可能从列表中消失。** 某个会话的消息被全部清空后，该会话不再出现在会话列表里（被置顶的群除外），这是服务端现有行为。
- **请求发出那一秒内到达的消息不会被清理。** 服务端消息时间精度只到秒，为了绝不误删之后到达的新消息，区间终点截断在服务端当前这一秒开始之前（§5.1）。
- **本地已下载的图片与文件不删除。** 它们属于缓存，由「存储 → 清理本地缓存」负责。

## 5. 服务端

### 5.1 纯函数（新文件 `chatserversrc/MessageDeleteRange.h/.cpp`）

- `NormalizeDeleteRange`：校验请求区间（开始不为负、截断后结束不早于开始），并把终点截断到"服务端当前这一秒开始前 1 毫秒"。这样即便客户端时钟偏快，之后到达的新消息也不会落进区间。
- `MergeDeleteRanges`：把新区间与本人已有区间合并，重叠或首尾相接（前一段结束 + 1 = 后一段开始）的合并成一段，结果按开始时间排序。

### 5.2 新表 `t_message_deleted_range`

| 列 | 含义 |
| --- | --- |
| `f_userid` | 执行清理的用户 |
| `f_begin_time` | 区间开始，Unix 毫秒（含） |
| `f_end_time` | 区间结束，Unix 毫秒（含） |
| `f_update_time` | 本行写入时间，Unix 毫秒，供排查 |

主键 `(f_userid, f_begin_time)`。写进 `table_mysql.sql` 后用 `tools/gen_table_sqlite.py` 重新生成 `table_sqlite.sql` 与 `sqliteapi/SqliteSchema.cpp`；在 `MysqlManager` 里登记表结构，启动时自动建表，不需要迁移脚本。列名刻意不用 `f_create_time`，避免读取过滤的相关子查询里与 `t_chatmsg.f_create_time` 同名混淆。

### 5.3 写入与读取

- `MessageManager::addDeletedRange(userid, begin, end)`：在一个事务里读出本人已有区间，经 `MergeDeleteRanges` 合并后整体写回。写入量与被清理的消息条数无关。
- 读取过滤：`visibleToUserClause`（原名 `notDeletedClause`）与 Pin 查询里的同类条件各加一项"消息时间不在本人任一已删区间内"。同步、搜索、会话列表预览、未读数、Pin 列表随之生效。

### 5.4 处理函数与推送

- 新增 `ChatSession::onDeleteMessagesByTime`：解析 → `NormalizeDeleteRange` → `addDeletedRange` → 回应答 → `sendToUser` 推送区间形式的 1522。
- `ChatSession::onDeleteMessage`：成功后推送单条形式的 1522。
- 两者都以英文日志记下 userid、区间或 msgid、耗时。
- 1502 应答构造函数回带 `beforemsgid`。

### 5.5 工程

服务端新文件存成带 BOM 的 UTF-8，同时加进 `CMakeLists.txt` 与 `windowsproj/` 下对应 vcxproj 两份源文件清单。

## 7. 客户端本地库

### 7.1 删除接口（`CV2MsgStore`）

- `DeleteMessages(ctype, cid, msgids)`：按 msgid 删除。
- `DeleteByTimeRangeBatch(begin, end, batchSize)`：一次最多删 batchSize 行，返回实际删除行数；调用方逐批投递消息反复调用，直到返回 0。每批 2000 行（以基准测试结果为准，§12）。

### 7.2 覆盖区间

新表 `t_cover(ctype, cid, lo_msgid, hi_msgid, reached_oldest)`，每个会话一行，含义是"服务端上 msgid 落在 [lo, hi] 里的消息，本地一条不缺"；`reached_oldest` 表示已经拉到服务端最早的一条。更新规则写成纯函数（新文件 `UI/BalloonHistory/HistoryCoverage.h/.cpp`），全部做单测：

- **一页同步应答覆盖的范围**：下界是这页最早的一条（服务端表示没有更多时为 0，即已到最早）；上界是这页最新的一条（从最新开始拉时）或"请求锚点 − 1"（往前翻页时）。
- **从最新开始拉的应答**：与已有区间接得上就合并；接不上（中间可能有断层）就以这一页为准重新起算。
- **往前翻页的应答**：只有接得上才扩展已有区间，接不上的忽略。
- 所有同步应答（无论由聊天窗还是消息记录窗发起）都参与计算，靠 1502 应答回带的 `beforemsgid` 区分是哪一种。

### 7.3 对账

一页同步应答覆盖的范围内，本地有、服务端没返回的行，视为已在别处删除，本地同步删除。例外：从最新开始拉却一条都没返回时不对账，以免误删对账期间刚到达的新消息。服务端的同步结果包含已撤回的消息，所以撤回的消息不会被误删。

### 7.4 登录后清空覆盖区间

离线设备收不到 1522，它之前验证为"完整"的区间里可能已有被删掉的行。每次登录成功后清空所有会话的覆盖区间记录；本地的行保留（用于去重与 Pin），重新验证之前不显示。代价：登录后往前翻历史时重新从服务端下载，每次 100 条。

## 8. 收到删除推送（1522）之后

- **单条形式**：本地库删行；已打开的对应聊天窗移除气泡（新增 `ChatMessageList::RemoveMessagesByMsgid`，全部移除后只重排一次）；刷新消息记录窗；调 `CIUSocket::RequestConversations()` 重新拉会话列表，由服务端算出新的预览。
- **区间形式**：本地库分批删除；删完后已打开的聊天窗整体重新加载最新一页（等同于重新打开窗口）；刷新消息记录窗；重新拉会话列表。
- **应答**（1512、1521）只负责提示结果：失败时由主面板弹出原因；1521 的结果经系统设置对话框转交清理对话框。

## 9. 消息记录窗

### 9.1 右键「删除」

- 只对有 msgid 的消息显示，放在菜单末尾，前面有分隔线（在 `BuildHistoryRowMenuModel` 里加项，命令 id 接着现有的 11 往后排）。
- 点击后先确认：「删除后本机和你的其他设备都不再显示这条消息，对方不受影响。」确认后发 1512，界面等 1522 到达后更新。

### 9.2 按覆盖区间分页

- 总条数与页数只按覆盖区间内的本地行计算，断层以下的旧行暂不显示。Pin 分类不受限制（它是服务端单独给的全集）。还没有覆盖区间时（刚升级、刚登录、或断网时回填到不了），照旧显示全部本地记录，回填到达、区间建立之后再收窄到区间内。（2026-09-30 与用户确认改为此口径；原定的"没有区间就不显示、等回填到达"会让断网时消息记录窗一直是空的。）
- 翻到最后一页、而覆盖区间还没到最早时，以区间下界为锚点向服务端拉更早的 100 条，底部显示「正在加载更早的消息…」。
- 有类型或关键字筛选时连续拉取，直到筛选结果多出一页或已到最早，每次点击最多 5 轮。
- 时间筛选（如「近 7 天」）的下界已在覆盖区间之内时，不再向服务端拉取。

### 9.3 导出

导出只导出已加载到本地、且在覆盖区间内的记录，不自动拉取服务端全部历史；需要导出全部时，先翻到末页。

## 10. 聊天窗「删除」改为真删除

- 单条删除与多选删除都改为发 1512；多选时每条发一个请求（1512 一次只收一个 msgid）。
- 删除前的确认文案与消息记录窗相同；气泡在 1522 到达后移除，不再由界面直接移除。
- 聊天列表通知所在窗口的消息按开发约定文档「UI 约定」第 6 条走 D 段（`WM_APP + n`），取未被占用的偏移，并把新占用的偏移补进开发约定文档的已占用列表。

## 11. 系统设置与清理对话框

### 11.1 聊天页

新增一行「清理聊天记录」，副标题「按时间范围删除本机和服务器上的记录，对方不受影响」，右侧按钮「清理…」；原来的最后一行「自动识别链接」改为带分隔线。

### 11.2 对话框 `CBalloonChatCleanDlg`

由系统设置对话框按值持有，结构照搬「清理本地缓存」对话框（`BalloonCacheCleanDlg`），全部使用 balloonui 现成控件，不改 balloonui。

```
清理聊天记录
┌──────────────────────────────────────────────┐
│ 时间范围   [ 30 天以前的记录              ▼ ] │
│                                              │
│ 开始  [2018▼]年[01▼]月[01▼]日 [00▼]:[00▼]      │
│ 结束  [2026▼]年[08▼]月[31▼]日 [21▼]:[45▼]      │
│                                              │
│ 将删除 2018-01-01 00:00 至 2026-08-31 21:45     │
│ 之间的全部单聊和群聊记录，本机与服务器同时删除，   │
│ 对方不受影响，删除后无法恢复。                    │
│                              [ 取消 ] [ 清理 ] │
└──────────────────────────────────────────────┘
```

- 时间范围下拉框列出 §1 的 10 个档位。
- 开始、结束各一组「年 / 月 / 日 / 时 / 分」下拉框，年份从 2018 年起（与消息记录窗一致）；月份或年份变化时「日」的选项随之调整。
- 选中预设会自动填好时间；用户手动改了任一时间，档位切到「自定义」。`DuiComboBox` 在程序赋值时也会发 `DUIN_VALUECHANGED`，须用标志位区分"程序填入"与"用户修改"。
- 说明文字随时间范围实时更新。

### 11.3 流程

点「清理」后先弹确认框 → 发 1521，按钮变为「清理中…」并置灰 → 成功时提示「已清理 X 至 Y 的聊天记录」并关闭 → 失败或 15 秒没有应答时按钮恢复可用并说明原因。未连接服务器时「清理」按钮置灰。

### 11.4 纯函数（新文件 `UI/BalloonSettings/ChatCleanRange.h/.cpp`）

档位到时间区间的换算（按本地时区）、年月日时分到毫秒的换算、各月天数、合法性校验（开始早于结束、结束不晚于当前时刻）、说明文字的生成，全部做单测。

## 12. 性能

| 位置 | 做法 | 验证 |
| --- | --- | --- |
| 服务端写入 | 每次清理只写一条区间，与消息条数无关 | 基准测试 MDB1：10 万条消息，对比"逐条写入删除记录"与"写一条区间"的清理耗时 |
| 服务端读取 | 过滤条件多一个区间判断，每个用户的区间只有几行 | MDB1 同时测清理后同步一页、拉一次会话列表的耗时 |
| 客户端本地删除 | 每批 2000 行，逐批投递 | 基准测试：本地库 10 万条，单批最长耗时目标不超过 50 毫秒 |
| 已打开的聊天窗 | 区间清理后整页重新加载，不逐个移除气泡 | — |
| 对账 | 每次最多涉及一页 100 条 | — |

基准测试挂 `doctest::skip()` 或 Catch2 的 `[.]` 标签，默认不执行；实测数字回填到 §14。

## 16. 按会话清空聊天记录（2026-10-02）

起因是主面板群列表右键「清空聊天记录」没有接入，点了只弹「该功能正在开发中」。用户逐项确定的口径：

- **本人视角清空、多端同步**：只对本人隐藏该会话目前为止的全部消息，本人登录的其他设备同步清空，对方与其他群成员不受影响；之后到达的新消息照常可见。
- 群聊之外，**单聊也要能清空**。
- 清空后**会话从最近会话列表移除**；之后再来新消息时会话重新出现。
- 入口：群列表右键、联系人右键、会话右键各一项；单聊窗与群聊窗头部**在「…」按钮左边单独加一个按钮**（扫帚图标），不放进「…」里。「…」按钮本身目前点了没有反应，记入 `bugs.md` BUG-50。
  - **2026-10-03 调整（用户要求）**：聊天窗头部的扫帚按钮去掉，改放到消息记录窗：底部「导出」左边一个「清空聊天记录」按钮（用户选定的位置），行右键菜单最末（「删除」之后）一项同名的菜单项，清空的都是消息记录窗当前查看的会话。主面板的三处右键入口不变。底部一行因此在窗口变窄时多一级隐藏：依次隐藏左侧信息、首页与末页、「跳至 _ 页」（与用户确认）。清空失败的提示弹在发起的消息记录窗上（`ChooseClearFailureOwner`）。
