# 「特别关注」接入方案与开发计划

> 被特别关注的联系人上下线时，右下角弹一个置顶小窗提示。入口放在联系人右键菜单
> 与最近会话列表右键菜单，**仅对联系人有效**（群、群成员都不参与）。
>
> 本文写于 2026-08-12，所列代码位置均已核对。

---

## 1. 背景与目标

企业版里同事很多，真正需要盯着"他在不在"的只有少数几个人 —— 直属领导、正在协作的
对接人、随时可能来活的甲方接口人。目前客户端能看到的只有联系人树上那个静态的状态点，
想知道某人什么时候上线，只能自己反复去看。

目标：把这少数几个人标记出来，他们上线 / 下线时主动弹一个提示，不必盯着列表。

**不在本期范围内**：给被标记的人做可视标记（星标 / 单独分区）、按标记做消息优先提醒、
标记群或群成员。

---

## 2. 命名约定：代码里叫 `Starred`

界面文案一律是「特别关注」，**代码标识符一律用 `Starred`**（`StarredModel` /
`IsStarred` / `SetStarred` / `cmd_set_starred` / `t_starred`）。

为什么不用直译的 `Focus`：`focus` 在本仓库已经明确表示**键盘 / 输入焦点** ——
聊天窗刚加的 Ctrl+C 路由就有 `m_focusArea` / `CHAT_FOCUS_INPUT`（`CustomMsgDef.h`）。
同一个词在同一个模块里担两种含义，读代码的人每次都要停下来分辨。

其余候选词与落选理由（2026-08-12 与用户对齐）：

| 候选 | 落选理由 |
| --- | --- |
| `Watch` | 已被占用：`IsUserWatchingChatWindow` / `bWatching` 表示"用户正盯着这个聊天窗"，与本功能撞义 |
| `Vip` | 仓库零占用、也够短，但 VIP 容易让人联想到"付费等级"，企业版里尤其不该有这个联想 |
| `SpecialCare` | 最贴中文，但谓词读着别扭（`IsCared` / `SetCared`），而谓词恰是出现频率最高的形态 |
| `PresenceAlert` | 把"标记这个人"与"提醒方式"绑死，日后要扩展就名不副实 |

`Star` 作为标识符在客户端源码里**零占用**（此前 grep 命中的 189 处全是 `Start` 的误伤）。

与已有的「收藏」（代码里是 `Favorite`）是**两个独立标记**：收藏是常用入口的书签，
特别关注是要盯上下线的人，两者互不影响、可同时存在。

## 3. 现状盘点（据实证，均已核对代码位置）

### 3.1 上下线推送：按企业广播给全体在线用户

`ChatServer::broadcastToEnterprise`（`chatserversrc/ChatServer.cpp:325-355`）取当前在线
会话快照，逐个判 `getUserEnterpriseId(...) == enterpriseId` 后下发，并跳过发起者自己。
三个触发点：

| 触发 | 位置 |
| --- | --- |
| 登录成功 | `chatserversrc/ChatSession.cpp:693` |
| 主动改状态 | `chatserversrc/ChatSession.cpp:1362` |
| 连接断开（补一条离线通知） | `chatserversrc/ChatServer.cpp:154` |

对本功能有三个直接影响：

1. **范围够用，不必改服务端推送逻辑。** 既然是按企业全员广播，标星一个从没聊过的
   同事照样收得到他的上下线。若当初是"只推给有会话关系的人"，本功能就得先扩推送范围。
2. **离线期间的上下线收不到，也不补发。** 推送不落库。这是**有意接受**的：特别关注的
   价值在实时性，登录后再补一堆"两小时前张三上线过"没有意义。写在这里以免日后被当成 bug。
3. 登录时**别人的**状态是随通讯录应答一次性给的（`cmd_get_contacts` 里每个联系人自带
   `presence`），不是靠一堆推送，所以不存在"登录推送风暴"。但仍需静默期，理由见 §7.3。

### 3.2 客户端已有上下线判定的纯函数

`balloonmain::IsBuddyJustCameOnline(oldPresence, newPresence)`（`BalloonMain/NotificationSound.h:68`）
——"由不可见态（离线 / 隐身）跳变为可见在线态（在线 / 离开 / 忙碌）"，现在用来放上线提示音，
挂在 `CBalloonMainPanel::OnPresenceChanged`（`BalloonMain/BalloonMainPanel.cpp:6903`，处理 1109 推送）里。
**挂钩点与口径都是现成的**，下线只需补一个对称判定。

### 3.3 「收藏」是可以逐字照抄的参照物

收藏是"每账号一份、服务端存"的联系人标记，全套都在：

| 层 | 文件 |
| --- | --- |
| 建表 | `flamingoserver/table.sql:412` 的 `t_favorite` |
| 服务端管理器 | `chatserversrc/FavoriteManager.{h,cpp}` |
| 服务端报文 | `chatserversrc/FavoriteProtocol.{h,cpp}` |
| 随通讯录下发 | `chatserversrc/ContactsProtocol.cpp` |
| 客户端报文 | `Source/net/FavoriteProtocolClient.h` |
| 客户端模型 | `Source/BalloonMain/FavoritesModel.{h,cpp}` |
| 服务端测试 | `flamingoserver/tests/test_favoriteprotocol.cpp` |
| 方案文档 | `docs/收藏接入方案.md` |

本方案的服务端与协议部分**整体照它的形状做**，不另起炉灶。

### 3.4 右键菜单两处都有纯函数模型层

`BuildContactMenuModel`（`BalloonMain/MainPanelContactMenu.h`）与 `BuildConversationMenuModel`
（`BalloonMain/MainPanelConversationMenu.h`）都是纯函数 + 有单测。加一项 = 加一个 id +
一行文案。文案随状态取反的先例有「添加到收藏 / 取消收藏」「消息免打扰 / 取消免打扰」。

### 3.5 公告弹窗正是要的那种置顶窗

`CAnnouncePopupWindow`（`Source/BalloonAnnounce/AnnouncePopupWindow.cpp`）已经做到：

- 贴**工作区**右下角（`rcWork`，排除任务栏），按鼠标所在显示器定位，多显示器安全（`:210-244`）；
- `HWND_TOPMOST` 置顶（`:202`）；
- `SW_SHOWNOACTIVATE` 不抢前台焦点（`:200`）。

两点不同需注意：它是主面板持有的**单实例**成员（`BalloonMainPanel.h:1627`），且**没有自动关闭**
（靠用户点关闭）。特别关注的弹窗要能自动消失、且要能装多条，故**另建一个窗口类**，
但把"贴右下角"那段几何抽成共用函数，不写两份。

## 4. 数据库设计

### 4.1 新建 `t_starred`

```sql
//特别关注表：记录"某用户特别关注了哪些联系人"。被关注者上下线时，关注方的客户端
//会在右下角弹提示。键的形态与 t_favorite 一致（userid + 对象id），但<u>不带 ctype</u>
//——特别关注只对联系人有效，群与群成员都不参与，多一列 ctype 只会让人误以为群也能标。
//之所以不复用 t_favorite 加一列：收藏与特别关注是两件事（书签 vs 盯上下线），
//一个对象可以只收藏不关注、也可以只关注不收藏，挤在一张表里两个语义会互相牵制。
CREATE TABLE IF NOT EXISTS  t_starred  (
         f_userid       bigint(20) NOT NULL COMMENT '关注方userid（名单的归属者）',
         f_target       bigint(20) NOT NULL COMMENT '被关注的联系人userid',
         f_create_time  bigint(20) NOT NULL DEFAULT 0 COMMENT '标记时间,Unix毫秒;列表按本列倒序,最近标记的排最前',
         PRIMARY KEY ( f_userid, f_target ),
         INDEX idx_starred_user ( f_userid )
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

### 4.2 三处建表定义都要改，漏一处就有一套库跑不起来

| 文件 | 改什么 |
| --- | --- |
| `flamingoserver/table.sql` | MySQL 建表语句（**唯一手写的一份**） |
| `flamingoserver/table_sqlite.sql` | 由脚本生成 |
| `flamingoserver/sqliteapi/SqliteSchema.cpp` | 由脚本生成（内嵌建表语句 + 表名清单 + 列清单三处） |

后两者**不得手改**：改完 `table.sql` 后跑 `python tools/gen_table_sqlite.py` 重新生成
（见开发约定文档「Protocol & data references」）。当前部署跑的是 SQLite
（`flamingoserver/etc/chatserver.conf` 的 `dbtype=sqlite`），这一步不能漏。

## 5. 协议设计

### 5.1 `cmd_get_contacts`(1201) 应答里增加 `starred` 数组

与既有的 `favorites` 并列，装被特别关注的联系人 userid：

```json
"starred": ["5081", "5099"]
```

只装联系人，故是**扁平的字符串数组**，不像 `favorites` 那样带 `ctype`。64 位 ID 以字符串
编码进 JSON，沿用本协议既有约定。按 `f_create_time` 倒序。

老客户端读到多出来的字段会忽略，不影响兼容。

### 5.2 新增 `cmd_set_starred = 1216`

1200 段现状：1201~1209 已用，1210~1212 已废弃留空不复用，1213 已用，1214 废弃，
1215 已用（`cmd_set_favorite`），**1216 空闲**。

```
请求  {"target":"5081", "starred":1}
应答  {"code":0, "msg":"ok", "target":"5081", "starred":1}
```

`starred` 取 1 标记 / 0 取消，一条命令兼管两个方向，与 `cmd_set_blacklist`(1213)、
`cmd_set_favorite`(1215) 的既有写法一致。应答回带 `target` / `starred`，便于客户端在
多条请求并发时对上号。

### 5.3 服务端校验与新增错误码

| 校验 | 不通过时 |
| --- | --- |
| `target` 为正、`starred` 为 0/1 | `error_code_bad_request`(3) |
| `target` 须是**同企业成员**（与收藏对联系人的校验同口径） | `error_code_not_friend` |
| `target` 不能是自己 | `error_code_bad_request`(3) |
| 关注总数上限 50 人 | 新增 `error_code_starred_limit` |

上限取 50：特别关注的意义就是"少数几个人"，几百人等于没关注；同时防刷表。该常量在
服务端定义为具名 `constexpr`，不得写成裸数字。

### 5.4 多端同步

本期**不做**推送。A 设备标记后，B 设备在下次拉通讯录（重登 / 重连）时同步 —— 与收藏
当初的处置一致。

## 6. 服务端行为

新增 `StarredManager`（`chatserversrc/StarredManager.{h,cpp}`）与
`StarredProtocol`（`chatserversrc/StarredProtocol.{h,cpp}`），形状照抄 Favorite 那一对：

| 函数 | 职责 |
| --- | --- |
| `getStarred(userid, out)` | 取某用户的关注名单（拉通讯录时用） |
| `setStarred(userid, target, starred, outCode)` | 加 / 删一条，含上限与同企业校验 |
| `countStarred(userid)` | 上限判定用 |
| `removeStarredForAll(target)` | 某用户被删号 / 移出企业时，把别人对他的关注一并清掉 |

`ContactsProtocol` 组装 1201 应答时，多查一次关注名单并塞进 `starred` 字段。

**关键：本功能不需要改推送逻辑。** 谁该收到上下线，服务端照旧按企业广播；
"要不要弹窗"完全是客户端按自己的关注名单决定的。服务端不知道、也不必知道谁关注了谁。

## 7. 客户端设计

### 7.1 数据层 `StarredModel`（纯逻辑，可单测）

`Source/BalloonMain/StarredModel.{h,cpp}`，照 `FavoritesModel` 的样子：持有当前账号的
关注集合（`std::set<int64_t>`），回答 `IsStarred(userid)`，供两处右键菜单取反文案。
不碰窗口、不碰网络，两个工程共用（主工程里标 `PrecompiledHeader=NotUsing`）。

数据来源是 1201 应答里的 `starred` 数组；改动经 `cmd_set_starred` 提交，服务端应答
成功后再改内存（失败则不改，避免界面与服务端不一致）。

### 7.2 入口：五处右键菜单

| 位置 | 菜单模型 | 新增项 |
| --- | --- | --- |
| 主面板联系人列表 | `BuildContactMenuModel` | `kContactMenuStarred = 13` |
| 主面板最近会话列表 | `BuildConversationMenuModel` | `kConvMenuStarred = 11` |
| 群聊窗右侧成员列表 | `BuildMentionMenuModel` | `kMentionMenuStarred` |
| 群聊窗气泡里的 @某人 片段 | 同上（共用） | 同上（共用） |
| 群聊窗气泡的**发送者头像** | 同上（共用） | 同上（共用） |

文案一律「特别关注 / 取消特别关注」，随当前状态取反。

**仅对联系人有效**落在模型层：会话菜单按 `ctype` 判断，群会话**不出现**该项 ——
与「查看资料 / 查看群资料」按 ctype 分叉是同一处地方。群成员本身是同企业的人，
可以标记；标记的是**那个人**，不是群。

后三处能一起拿下，是因为群成员列表行与气泡里的 @片段**本来就共用同一套菜单模型**
`BuildMentionMenuModel`（`BalloonChatWnd/GroupMentionMenu.h`，见 `GroupMemberItem.cpp:180`
与 `ChatBubble::TryPopupMentionMenu`）—— 往那一份里加一项，两处同时就有了。
菜单模型需要多收一个"该 uid 当前是否已被标记"的入参，用来取反文案；已有的
`stillInGroup` / `myNetRole` / `targetNetRole` 就是同样的用法。

**气泡头像的右键**是这次新增的落点，此前头像上右键弹的是气泡自己的菜单（复制 /
引用回复 / 撤回那套）。做法：

- 头像矩形**不存成员**，而是按与绘制完全相同的公式**按需重算**（新增
  `RECT AvatarRectInHost() const`，没有头像的行返回空矩形）。原因：文字气泡走渲染缓存
  （`IsRenderCacheable()` 为真），而缓存的前提正是"绘制时不记录任何宿主坐标系命中
  矩形"——图片 / 文件行之所以不可缓存就是因为要记 `m_imageRect` / `m_fileBtnRect`。
  若为头像也存一份矩形，所有文字气泡都会退出缓存。仓库里已有同样手法的先例：
  `TextOriginInHost`。
- 命中头像时弹成员菜单（与 @片段同一套），否则照旧弹气泡菜单。实际的判定顺序是
  链接 → @片段 → 头像 → 气泡菜单：前两者都在正文区里、与头像区不重叠，谁先判都
  一样，按这个顺序写只是为了不动已有那两段的相对次序。
- **只在群聊上下文生效**：单聊窗的气泡头像不弹这个菜单（那套菜单里的「@TA」
  「设为管理员」在单聊里没有意义）。判据取 `senderName` 非空 —— 只有群聊才填它
  （与绘制时 `showSender` 同一口径）。单聊的联系人在主面板两处菜单里已经能标。
- **自己发的那条也不弹**：右键点自己的头像本就不是个有意义的动作，与 @ 到自己时
  只留「查看资料」是同一个道理，但这里连菜单都不必出。
- 头像代表谁取 `ChatMessage::senderUserId`（`ChatMockData.h:158`）；为 0（mock / 未知）
  时不弹。
- @片段与头像两个入口的"建菜单 → 弹出 → 投递选中项"抽成了 `ChatBubble::PopupMemberMenu`，
  两处共用 —— 两份菜单本来就该逐字一样，各建一份迟早走样。

菜单模型多收的那个"是否已标记"入参，值从哪来：关注名单只有主面板那一份，气泡与成员
行都不认识它，故沿用仓库里已有的**查询钩子**路子（与 `SetMemberInGroupQuery` /
`SetMemberRoleQuery` 完全同形）：`ChatMessageList::SetStarredQuery` 与
`GroupMemberItem::SetStarredQuery`，都由群聊窗在建控件时装上，钩子内部经
`FMG_MSG_QUERY_STARRED` 同步问主面板。用钩子而不是往行里存一个 `bool`，是因为关注
状态可能在别处（主面板的两处菜单）被改掉，而成员侧栏并不会因此重建，存下来的那份会过期。

### 7.3 上下线检测与抑制

在 `CBalloonMainPanel::OnPresenceChanged` 里，紧挨现有的上线提示音那一段，加一段判定：

```
被关注(userid) 且 (刚上线 或 刚下线) 且 未被抑制  →  请求弹窗
```

- **上线**：复用 `IsBuddyJustCameOnline`（不可见 → 可见）。
- **下线**：新增对称的 `IsBuddyJustWentOffline`（可见 → 不可见，即离线 / 隐身），
  与前者放在同一个文件里，共用同一套 presence 取值口径。
- **在线↔离开↔忙 之间的来回切换不提示** —— 对方锁个屏就弹一次，一上午能弹十几次。

抑制策略（缺了任何一条都会变成骚扰）：

| 抑制 | 理由 |
| --- | --- |
| 登录后 `kStarredSilenceMs`（默认 10 秒）内不弹 | 通讯录还没拉回来时，`OnPresenceChanged` 对查不到的人**一律按离线**处理（那段代码的注释写明了），此时收到的推送会被误判成"上线" |
| 本人处于「勿扰」时不弹 | 用户选了勿扰就是不想被浮窗打断 |
| 自己（多设备回声）不弹 | 现有代码已按 selfId 排除，沿用 |

落地时这三条的实现细节：

- 五条判定收在 `CBalloonMainPanel::MaybeShowStarredPresencePopup` 一个函数里（不在名单、
  是自己、不是上下线跳变、静默期内、勿扰），`OnPresenceChanged` 只调它一行。
- **静默期的起点**：主面板是登录成功之后才创建的，故构造函数里就是"刚登录"这一刻。
  断线重连（`ApplyConnectionState` 由非在线态回到 `kConnUiOnline`）时重新起一个静默期
  —— 重连后服务端会把在线的同事重推一遍，与刚登录是同一个局面。断线时顺带把已经弹着
  的提示收掉，那批状态是断线前的旧账。
  比较写成 `(int)(GetTickCount() - 截止时刻) < 0` 而不是直接比大小，`GetTickCount`
  约 49.7 天回绕一次，直接比会在回绕那一刻判反。
- **「勿扰」在本客户端里就是用户自己选的在线状态 `presence_busy`**（状态菜单里的那一项），
  不是某个配置开关 —— `CUserConfig::IsEnableMute()` 是"关闭所有声音"，是另一回事。
  读的是 `MainPanelHeader::GetPresence()`，它存的是"用户自己选的状态"、不受掉线影响，
  拿连接态去判会在断线重连时误伤。

### 7.4 弹窗 `CStarredPopupWindow`

新建 `Source/BalloonMain/StarredPopupWindow.{h,cpp}`，外观与定位跟公告弹窗一致，
但有三点不同：

- **能装多条**：同一时刻多人上下线时**合并成一个弹窗、逐行列出**（"张三 已上线"
  "李四 已离线"），而不是弹一串窗口 —— 早高峰会变成弹窗轰炸。新事件追加进去并
  **重置计时**。超过 `kStarredPopupMaxRows`（默认 5 行）时，多出来的收敛成
  "等 N 人"一行。
- **自动消失**：`kStarredPopupAutoCloseMs`（默认 6 秒）后淡出；鼠标悬停其上时暂停计时
  （用户正在看，别抽走）。
- **点某一行打开与那个人的单聊**：经主面板既有的打开会话入口，弹窗自己不碰业务。

"贴工作区右下角"的几何从 `AnnouncePopupWindow` 抽成共用纯函数（放
`BalloonMain/CornerPopupPlacement.h`），两个弹窗共用一份，符合开发约定文档 UI 约定
第 3 条（弹层必须整体落在工作区内）。

落地时的几点：

- **行怎么排是纯函数**：`BuildStarredPopupRows`（`BalloonMain/StarredPopupModel.h`）——
  去重、封顶、「等 N 人」、顺序四条规则都在这里，窗口只管把结果喂给控件。因此这部分
  有单测（`Tests/StarredPopupTests.cpp` 的 SPM 组），不必靠人工去点。
  去重规则里有一条容易漏：**同一个人反复变化只留最后一次的状态，但位置留在他第一次
  出现的地方** —— 位置跟着最后一次跑的话，用户眼看着行在列表里跳来跳去。
- **行控件直接用 balloonui 的 `DuiListBox`**（开发约定文档 UI 约定第 2 条）：悬停高亮、
  单击选中、内容多了自动出滚动条它都自带，不必手写自绘列表。每行的 `lParam` 存该行
  对应的 userid，点行时按它开单聊；汇总行存 0，点它不开窗。
- **悬停暂停**靠 `TrackMouseEvent(TME_LEAVE)`：进入窗口时停掉计时器并登记一次离开
  追踪，收到 `WM_MOUSELEAVE` 后<u>从头</u>重新计时（不是接着剩下的那点时间——用户刚看过
  一眼，该给足一整轮）。这个追踪是一次性的，每次进入都要重新登记，漏了就再也收不到
  离开通知、窗口会一直挂着不走。
- 窗口高度按行数算，`SetMinSize` + `ResizeClient` 一起改 —— 只有一条提示时不该留一大片空白。
