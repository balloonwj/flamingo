# 界面自动化验证原理

> 作者：balloonwj@qq.com　日期：2026-10-05
> 用途：说明联调时「自动操作真实客户端界面并核对结果」这套做法的原理、具体步骤、各种情况下的表现与局限，
> 供以后写新的联调脚本、或判断一项核对结论可不可信时参考。
> 文中的脚本以音视频通话联调环境 `tmp/gc_live/` 为例（`gw.ps1`、`menu.ps1`、`pincheck.ps1`），该目录现已删除；
> 现存的同原理脚本是各联调环境里的 `ui.ps1`（如 `tmp/bot/live/ui.ps1`，主要动作与 `gw.ps1` 相同）。
> 文中的窗口尺寸与坐标是 2026-10-05 的实测值；2026-10-06 起一对一通话窗默认宽由 720 改为 776（`CallingLayout.h` 的 `kCallDlgWidth`），
> 照做时要重新截图取坐标。

---

## 1. 一句话原理

不动真实的鼠标和键盘，而是**直接往目标窗口的消息队列里投递 Windows 消息**（鼠标按下、抬起、字符、按键、
系统命令，以及客户端自己定义的消息）；再**让窗口把自己画进一张内存位图**来截图，结合窗口状态、客户端日志、
文件系统等多方面的证据判断结果对不对。

客户端收到这些消息后，走的是与真人操作完全相同的界面代码（见第 7 节），所以它验证的是真实的界面逻辑；
但它绕开了 Windows 的真实输入通道，凡是依赖「真实光标在哪里、哪个窗口在前台」的行为都验证不准（见第 11 节）。

## 2. 为什么不用真实鼠标键盘，也不用 UI Automation

| 做法 | 问题 |
| --- | --- |
| `SendInput` / `SetCursorPos` 模拟真实鼠标键盘 | 会抢走用户正在用的鼠标和焦点，目标窗口必须在前台、不能被遮挡；共用桌面上会直接干扰用户与其它会话 |
| UI Automation、`FindWindowEx` 按控件查找 | 客户端界面由 balloonui 自绘：整个窗口只有一个 HWND，按钮、输入框都不是子窗口，没有句柄，也不暴露自动化接口，按控件名查不到 |
| `SendKeys` 发字母 | 桌面默认开着中文输入法，字母会被输入法拿去组拼音，输入框里什么都没有（2026-10-01 实测） |

投递消息的做法不移动用户的鼠标、不改变前台窗口，目标窗口被遮挡也照样能操作，所以整个核对过程可以放在用户看不见的
隐藏桌面上进行（见第 12 节）。

操作窗口的脚本是 PowerShell 5.1，内嵌一段用 `Add-Type` 编译的 C#，通过 `DllImport` 调用 `user32.dll`。
PowerShell 5.1 按 ANSI 读 `.ps1`，所以脚本里只写 ASCII，不拿中文窗口标题去匹配窗口。

## 4. 第一步：找到目标窗口

### 4.1 先找进程

三个测试客户端的可执行文件都叫 `Flamingo.exe`，按文件名分不出 A、B、C。`gw.ps1` 用
`Get-CimInstance Win32_Process` 取出所有 `Flamingo.exe`，再按**完整路径**（如 `tmp\gc_live\clientA\Flamingo.exe`）
挑出目标进程，得到进程号。

### 4.2 再列窗口

调用 `EnumWindows` 枚举桌面上全部顶层窗口，对每个窗口用 `GetWindowThreadProcessId` 取所属进程号，只保留
属于目标进程、并且 `IsWindowVisible` 为真的窗口，逐个打印：

```
pid=16280
74123694  __DuiHost__  600,231 720x569  client=720x569  [语音通话]
15008430  __DuiHost__  631,182 658x667  client=658x667  [韩晓燕888（小燕消息xx）]
10947710  __DuiHost__  791,152 338x727  client=338x727  [FlamingoIM]
```

各列依次是窗口句柄、窗口类名、屏幕位置与尺寸、客户区尺寸、标题。

- **按尺寸和类名认窗口**比按标题可靠：标题经控制台代码页输出时常是乱码，脚本又不能写中文。
  例如 720×569 的是一对一通话窗，420×200 的是右下角来电窗，338×727 的是主面板。
- 常见的窗口类：`__DuiHost__`（balloonui 的普通窗口）、`__DuiMenuPopup__`（balloonui 的弹出菜单）、
  `__DuiComboBoxPopup__`（下拉框的浮层）、`#32768`（系统原生弹出菜单）、`#32770`（系统消息框）。
- 句柄每次打开窗口都会变，每一步操作前都要重新列一次，不能沿用上一个窗口的句柄。

## 5. 第二步：确定要点的坐标

### 5.1 坐标系

投递鼠标消息用的是**客户区坐标**（相对窗口客户区左上角）。客户端的窗口多数是 `DuiFrameWindow`，它在
`WM_NCCALCSIZE` 里去掉了系统非客户区，客户区就是整个窗口，所以截图里看到的坐标可以直接用。

脚本启动时调用 `SetProcessDPIAware()`，让本进程拿到的都是**物理像素**：截图的像素坐标、`GetWindowRect`
的结果与投递的坐标属于同一个坐标系。不调用的话，在 125% 缩放下脚本看到的是缩小过的逻辑坐标，会点偏
（2026-10-02 用逻辑坐标点到过相邻的菜单项）。

### 5.2 怎么知道按钮在哪里

按钮没有句柄，没法查询它的位置，只能用下面几种办法：

1. **截图后看图读坐标**（最常用）：先按句柄截一张窗口图，人工判断按钮在图上的位置，例如单聊窗右上角的电话
   图标约在 (428, 62)。截图与点击同为物理像素，读出来的坐标直接用。
2. **按布局常量推算**：例如通话窗宽 720，「挂断」按钮宽 88、距右边 24，底部栏从 y = 44 + 405 开始、高 120，
   按钮在底部栏里竖直居中，于是中心约在 (651, 509)。布局单测里用的就是这些常量。（这是 2026-10-05 的尺寸；现在通话窗宽 776，
   「挂断」是直径 56 的圆形图标按钮，见 `CallingLayout.h`、`CallButtonArt.h`。）
3. **拿不准时先问窗口**：贴着窗口右缘的控件，最外侧几个像素会被 `DuiFrameWindow` 判成缩放边框，点在那里只会
   拖动边框。可以先向窗口发 `WM_NCHITTEST`，返回 1（`HTCLIENT`）才说明这个点属于客户区。

重新编译、换了布局之后，旧坐标可能点到别的控件上（2026-10-02 曾因此点中了「禁止机器休眠」），所以每次点之前
都先截图核对。

## 6. 第三步：投递消息

### 6.1 消息一览

| 动作 | 投递的消息 | wParam | lParam |
| --- | --- | --- | --- |
| 单击 | `WM_MOUSEMOVE`(0x200) → `WM_LBUTTONDOWN`(0x201) → `WM_LBUTTONUP`(0x202)，间隔 60 / 40 毫秒 | 按下时为 1（`MK_LBUTTON`），其余为 0 | 坐标：低 16 位是 x，高 16 位是 y |
| 双击 | 单击之后再发 `WM_LBUTTONDBLCLK`(0x203) 与 `WM_LBUTTONUP` | 同上 | 同上 |
| 右键 | `WM_RBUTTONDOWN`(0x204) → `WM_RBUTTONUP`(0x205)；隐藏桌面上要用 `SendNotifyMessage` 发送，不能用 `PostMessage` 投递（见第 12 节） | 按下时为 2（`MK_RBUTTON`） | 同上 |
| 拖动 | 按下 → 分 12 步 `WM_MOUSEMOVE`（wParam = `MK_LBUTTON`）→ 抬起 | 同上 | 每一步的坐标 |
| 打字 | 每个字符一条 `WM_CHAR`(0x102)，间隔 30 毫秒；中文用 `PostMessageW` 按码位发 | 字符码 | 1（重复次数） |
| 按键 | `WM_KEYDOWN`(0x100) → `WM_KEYUP`(0x101) | 虚拟键码，如 Esc 为 0x1B | 按下为 1；抬起为 0xC0000001（第 30、31 位表示「之前按着、现在抬起」） |
| 最大化 / 最小化 / 还原 | `WM_SYSCOMMAND`(0x112) | `SC_MAXIMIZE` 0xF030 / `SC_MINIMIZE` 0xF020 / `SC_RESTORE` 0xF120 | 0 |
| 关闭窗口 | `WM_CLOSE`(0x10) | 0 | 0 |
| 程序内部操作 | 客户端自定义的 `WM_USER + n` 消息（见 6.2） | 按消息约定 | 按消息约定 |

单击前先发一次 `WM_MOUSEMOVE`，让控件先进入悬停状态，再按下、抬起，顺序与真人操作相同。
几十毫秒的间隔是为了让客户端的 UI 线程有机会按顺序处理完每条消息，避免多条消息挤在一起时出现意外的合并。

删除输入框里的字符不能发 `WM_CHAR` 0x08，要发 `WM_KEYDOWN` 的 `VK_BACK`（2026-10-03 实测）。

### 6.2 直接调用客户端内部的消息

有些操作靠点界面要绕好几步，不如直接给主面板投递客户端内部本来就有的消息，例如：

- `FMG_MSG_OPEN_CHAT`（`WM_USER + 454` = 0x5C6，wParam 为对方 userid）：打开与某人的单聊窗；
- `FMG_MSG_OPEN_GROUP_ANNOUNCE`（`WM_USER + 539` = 0x61B，wParam 为群号）：打开该群的群聊窗并切到「公告」页签。

这些消息定义在 `Source/Session/UserSessionData.h`，产品代码里本来就有窗口在发，借用它们不会走出产品正常的执行路径。
`lParam` 指向堆对象的消息不能这样投递（脚本给不出有效的指针）。

### 6.3 投递是异步的

`PostMessage` 只是把消息放进队列就返回，不等处理完成。所以每次投递之后要留出等待时间（几百毫秒到几秒），
再用第 8 节的办法检查结果；脚本输出的 `clicked … at …` 只说明消息投出去了，不说明点中了。

## 7. 客户端怎样处理投递来的点击

以单击一个 balloonui 按钮为例（代码在 `third-party/balloonui/balloonui/`）：

1. `DuiHost` 的消息映射收到 `WM_LBUTTONDOWN`，进入 `DuiHost::OnLButtonDown`（`DuiHost.cpp:951`）。
2. `HitTopMost(pt)` 调用根控件的 `HitTest`，按坐标在控件树里找到最上层的控件；控件可获得焦点时顺便设为焦点控件。
3. 交给该控件的 `OnLButtonDown`：按钮记下「已按下」，并捕获鼠标。
4. `WM_LBUTTONUP` 到达后交给 `DuiButton::OnLButtonUp`（`DuiButton.cpp:875`）：只有按钮**可用**、**之前被按下**、
   **抬起点仍在按钮矩形内**三个条件同时满足，才 `NotifyParent(DUIN_CLICK)`。
5. 宿主窗口在 `OnDuiNotify` 里按 `code == DUIN_CLICK` 与 `ctrlId` 分发，执行这个按钮的功能。

这条路径与真人点击完全相同，因此：

- 按钮被禁用时，投递的点击同样不起作用（2026-10-05 核对群通话全员静音时，点变灰的「打开麦克风」没有反应，
  正是第 4 步的判断在起作用）；
- 按下与抬起的坐标必须落在同一个按钮里，否则不算一次点击。

与真人点击不同的地方在于：真实输入时系统会先发 `WM_NCHITTEST`、`WM_SETCURSOR`、`WM_MOUSEACTIVATE` 等消息，
并可能激活窗口、把它提到前台；投递消息没有这些前置步骤，窗口不会被激活。

## 8. 第四步：取证

### 8.1 截图

`gw.ps1 -Action shot` 按窗口矩形建一张 32 位位图，调用 `PrintWindow(h, hdc, 2)`。参数 2 是
`PW_RENDERFULLCONTENT`：请窗口把自己的完整内容（包括经桌面窗口管理器合成的部分）画进这张位图，
而不是从屏幕上拷贝像素。所以窗口被遮挡、不在前台时也能截全。

截图只针对显示测试账号数据的窗口。另外几个动作用来少存内容：

| 动作 | 用途 |
| --- | --- |
| `crop` / `band` / `strip` | 只保存窗口里的一块矩形、一段行或顶部几行（例如只要按钮行，不要中间可能有真实内容的区域） |
| `tiny` | 保存缩小到 1/10 的图：看得出布局，看不清任何内容 |
| `stats` | 不保存图片，只在内存里统计某种颜色的像素占比和平均亮度。用于含真实摄像头画面的窗口，例如判断「画面区不再是黑的」 |

截图先放在联调环境的 `shots/` 下；要给人看的再复制到仓库根目录的 `snapshots/`。

### 8.2 窗口状态

`pincheck.ps1` 读取：

- `GetWindowLong(h, GWL_EXSTYLE)` 的 `WS_EX_TOPMOST`（0x8）：是否置顶；
- `IsIconic` / `IsZoomed`：是否最小化、最大化；
- `GetWindowRect`：位置与尺寸，用来核对「接通后窗口没有移动、没有改变大小」这类要求。

### 8.3 其它证据

- **窗口清单的变化**：点了「呼叫」之后多出一个 720×569 的窗口，对方进程多出一个 420×200 的来电窗。
- **客户端日志**（`clientX/Logs/*.log`）：例如 `Call dialog open (calling)`、`StartLoopSound … call_outgoing.wav`、
  `voice record: resumed at 16970 ms`。声音能不能听到，界面上看不出来，只能看日志里有没有开始播放，
  真正「听没听到」要请用户确认。
- **服务端日志**：请求的 `cmd` 与 `body` 能看出客户端实际发了什么。
- **文件系统**：例如暂停中试听的临时文件 `rec_<id>_paused.ogg` 有没有生成、继续录音后有没有被删除。

任何一项结论都尽量由两种以上的证据互相印证，只看截图容易把「旧画面」或「点到了别处」误判成成功。

## 9. 窗口被遮挡等情况的影响

| 情况 | 投递的点击、按键 | 截图 | 说明 |
| --- | --- | --- | --- |
| 被别的窗口遮挡 | 不受影响 | 不受影响 | 消息直接进目标窗口的队列；`PrintWindow` 让窗口自己重画 |
| 不在前台、没有焦点 | 不受影响 | 不受影响 | `WM_CHAR` 照常进入输入框 |
| 完全挪到屏幕外 | 照常生效 | **可能是旧画面** | 2026-10-02 实测：完全在屏幕外的窗口收不到 `WM_PAINT`，截图前要挪回屏幕内（不激活、不改 Z 序），等约 0.5 秒再截 |
| 最小化 | 据推测不起作用 | 截不到 | 最小化后窗口尺寸为 0，`PrintWindow` 没有内容可画；命中测试也找不到控件（据推测，未专门验证），要先还原 |
| 同一位置叠着多个窗口 | 不受影响 | 不受影响 | 按句柄投递和截图，不按屏幕位置，所以不会落到上面那个窗口里。用屏幕坐标、先把窗口提到前台的旧脚本会点错 |
| 用 Direct3D 等硬件加速绘制的内容 | — | 据推测可能是黑块 | 客户端的视频画面用 GDI 绘制，不受影响 |

## 10. 特殊界面元素

### 10.1 balloonui 弹出菜单（`__DuiMenuPopup__`）

- **用投递消息打开的菜单约一秒就会自己关掉**（据推测与属主窗口不在前台有关）。分成「先打开、再截图」两条命令时
  菜单已经没了，而且每启动一次 PowerShell 脚本光编译 `Add-Type` 就要近一秒。所以 `menu.ps1` 把多个步骤放在
  一个进程里执行，步骤之间用分号隔开：

  ```
  menu.ps1 -Who A -Steps "open:14222068,587,609;wait:600;grab:top;shot:top,menu.png"
  menu.ps1 -Who A -Steps "open:14222068,587,609;wait:600;grab:top;click:top,40,17"
  ```

  `open` 点击打开菜单的按钮，`grab` 记下该进程最新出现的可见菜单窗口，`shot` / `click` 对记下的菜单窗口
  截图或点击（菜单内的客户区坐标）。
- **弹出位置**：按钮下拉菜单按按钮的矩形定位（如群通话的「成员管理」菜单向上弹在按钮上方），不受影响；
  右键菜单按 `GetCursorPos` 弹在**用户真实鼠标所在的位置**，投递的悬停会被真实鼠标覆盖，子菜单常常打不开，
  也会打扰用户（2026-10-03 实测）。这类菜单尽量改用按键选择，或换一个不经菜单的入口。
- **残留的菜单**：真人点菜单外面时菜单会先关闭，投递消息不会产生这种点击。如果脚本结束时菜单还开着，
  要给菜单窗口投递 `WM_KEYDOWN` 的 Esc 把它关掉（2026-10-05 核对后就遇到过一次）。
  上一个菜单还开着时不要再投递右键，会出现菜单嵌套。

### 10.2 其它浮层与系统窗口

- **系统原生菜单 `#32768`**（如聊天气泡、群成员的右键菜单）：给菜单窗口投递若干次「下」键再回车来选项；
  不要先把属主窗口提到前台，否则菜单立即关闭。
- **下拉框浮层 `__DuiComboBoxPopup__`**：列表画在浮层的子窗口里，点击要投递给子窗口，投给顶层浮层不会选中。
- **系统消息框 `#32770`**：给它发 `WM_COMMAND`（是 = 6、否 = 7、确定 = 1、取消 = 2）。只有「确定」按钮的消息框
  发 1 不生效，要发 `WM_CLOSE`。
- **无边框窗口的空白处**：在 `DuiFrameWindow` 非控件区域投递 `WM_LBUTTONDOWN` 会触发窗口拖动，窗口会按真实光标
  的位置被挪走，之后的截图坐标要重新取。

## 11. 这种做法验证不了、或验证不准的东西

| 类别 | 原因 | 替代办法 |
| --- | --- | --- |
| 悬停效果、悬停提示 | `DuiHost` 用 `TrackMouseEvent` 按真实光标检测鼠标离开；真实光标不在窗口里时系统随即发 `WM_MOUSELEAVE`，投递的悬停态马上被清掉，提示气泡也弹不出来 | 单测在内存位图上逐像素检查；实机效果请用户自己看 |
| 依赖真实光标、键盘状态的代码 | `GetCursorPos`、`GetAsyncKeyState` 读到的是用户真实的鼠标和键盘 | 改从入口消息或单测验证 |
| 焦点、前台窗口 | 这台机器的输入法工具条注入在客户端 UI 线程里，只投递消息时线程的活动窗口长期是它 | 在产品代码里把 `SetForegroundWindow` 的结果写进日志取证 |
| 系统层面的交互 | 拖到屏幕边缘自动贴边、Win+方向键、点任务栏按钮等经过系统输入处理 | 请用户手动操作 |
| 空闲相关的功能 | 投递消息不会重置系统空闲计时，测试客户端开着超过 5 分钟会被切成「离开」 | 核对结果时把这种状态变化排除在外 |
| 声音 | 界面上看不出声音 | 看日志确认开始播放；听没听到请用户确认（2026-10-05 回铃音就是这样确认的） |
| 时间很短的动画 | 两次脚本调用之间至少隔近一秒 | 在同一个进程里完成「投递 → 截图」 |

所以这种做法适合核对**界面逻辑与状态切换**：按钮点下去走了哪条代码、窗口尺寸与状态对不对、显示的文字对不对。
手感类的效果（悬停、拖动是否顺手、动画是否流畅）仍要人来试。

## 12. 隐藏桌面与可见桌面的规矩

### 12.1 联调一律放在命名的隐藏桌面上

测试客户端与操作它们的脚本都运行在一个**命名的隐藏桌面**上，不占用用户正在用的可见桌面。

原理：同一个窗口站（`WinSta0`）里可以有多个桌面，显示在屏幕上、接收真实键盘鼠标输入的只是其中一个。用
`CreateDesktop` 建一个有名字的桌面，在 `CreateProcess` 的 `STARTUPINFO.lpDesktop` 里填上这个名字，新进程的窗口就建在
那个桌面上：不出现在用户的屏幕和任务栏上，置顶的通话窗也盖不住用户的窗口；用户在自己的桌面上点来点去，也不会让
测试窗口失去焦点，投递的 `WM_CHAR` 能真正进到输入框里。2026-10-08 测试客户端曾放在可见桌面上（窗口挪到屏幕外），
新打开的群聊窗在用户屏幕上闪了一下，挪到屏幕外的窗口也会在用户点别处时失去焦点，投递的字符进不了输入框，此后改为隐藏桌面。

`EnumWindows` 只列出调用者所在桌面的窗口，所以列窗口、截图、投递消息的脚本本身也要在这个隐藏桌面上启动。

### 12.2 隐藏桌面上要始终保留一个常驻进程

桌面只在还有进程打开着它时存在：最后一个进程退出、桌面句柄都关闭后，系统就销毁这个桌面。如果此时恰好在往这个桌面上
启动新进程，新进程还没连上桌面，桌面就已被销毁，新进程随之失败：只有 1 个线程、不写日志、不出窗口，过一会儿自行退出
（2026-10-08 管理控制台与客户端都遇到过；客户端自动更新联调时，更新器拉起新客户端后立即退出，也是这个原因，见
`docs/客户端自动更新方案.md` 第 9 节）。所以先在隐藏桌面上放一个只做长时间等待的常驻进程，再启动测试客户端；
联调结束时关掉测试客户端与常驻进程，桌面随之消失。

### 12.3 右键用 `SendNotifyMessage` 发送

从另一个进程用 `PostMessage` 投递给隐藏桌面上窗口的 `WM_RBUTTONDOWN` 到不了控件：控件的 `OnRButtonDown` 没有日志，
右键菜单也不出现；投递的左键点击则正常（2026-10-08 实测，帖子群的 @ 菜单与主面板群列表的右键菜单都是如此，刚启动的
客户端也一样）。把同样的移动与按下改用 `SendNotifyMessage` 发送后菜单正常弹出；`SendNotifyMessage` 不等对方处理完就
返回，脚本不会被弹出的菜单卡住。在隐藏桌面上看不到右键菜单时，先检查是不是用了 `PostMessage`，不要当成产品缺陷去查。
`TrackPopupMenu` 弹出的系统菜单，给它的属主窗口投递 `WM_CANCELMODE`（0x1F）即可关掉。

### 12.4 其它规矩

- 只操作隔离联调环境里的测试账号和测试服务端，不碰用户自己在用的客户端。
- 桌面隔离不隔离声音与设备：提示音照样从扬声器放出来，录语音消息照样用真实的麦克风。要放声音、开摄像头、录音时先向用户说明。
- 录下的语音核对完直接放弃，不发送，不留文件；含真实摄像头画面的窗口不存图。
- 动手前看看有没有别的会话也在做界面操作，约好谁先用，用完通知对方。
- 核对时打开的菜单、窗口用完要关掉；联调结束后关掉测试客户端与常驻进程，联调环境是否保留问一下用户。

### 12.5 必须在可见桌面上做的核对

锁屏、截图界面这类会盖住整个桌面、拦截键盘或抓取真实屏幕内容的功能，以及防截图这类必须在真实桌面上采集的测试，
没法放进隐藏桌面。这类核对事先征得用户同意，或由用户本人操作。用户明确把屏幕让出来时（例如帮助文档的截图要带上
弹出菜单与窗口阴影），也可以在可见桌面上进行，但只限那一项任务，做完回到隐藏桌面。
