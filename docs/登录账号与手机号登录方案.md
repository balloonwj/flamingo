# 登录账号与手机号登录方案

> 作者：balloonwj@qq.com　起草日期：2026-10-06
> 用途：记录四件相关的事的需求结论、现状盘点、设计、分期与测试用例：一是新账号改为「前缀 + 8 位随机数字」，不再暴露注册先后；二是管理后台给企业设置账号前缀；三是账号与手机号都能登录（为此手机号要全局唯一、管理后台新建与编辑员工时必填）；四是修复管理后台编辑员工时同一企业第二名没填工号的员工保存失败的问题，并补齐测试数据的手机号。后续每步开工前据此细化、收尾后回填实际结果。
> 体例沿用 `docs/联系人资料字段扩充方案.md`：结论一律标注来源，「据实证」必附文件:行号或命令输出，「据推测」表示尚未验证。

## 1. 需求与已定决定（2026-10-06 与用户确认）

| 事项 | 决定 |
| --- | --- |
| 新账号格式 | 默认 `EMP` + 8 位随机数字（如 `EMP48203917`）；企业在管理后台设了账号前缀时，用「前缀 + 8 位随机数字」（如 `HW.48203917`）。自助注册与管理员新建员工两条路径都按此生成 |
| 前缀规则 | 只能由英文字母（含拼音）和点号「.」组成（用户确定）；按推荐取值：长度 1～10 个字符、至少含一个字母、保存时统一转成大写；不设时用默认的 `EMP` |
| 已有账号 | 不迁移：`EMP5313`、`MY0001` 这类账号保持不变，免得大家记住的账号失效；改前缀只影响之后新建的账号 |
| 登录方式 | 账号与手机号都能登录，客户端仍只有一个输入框（占位文字改为「账号 / 手机号」）；账号不区分大小写（按推荐取值，与数据库对账号的比较规则一致） |
| 手机号 | 全局唯一。管理后台新建、编辑员工时手机号必填、格式为 11 位以 1 开头的数字、不能与其他账号重复；自助注册在服务端补上同样的格式校验 |
| 编辑员工的工号 | 管理后台编辑员工时工号为空写 NULL；工号与本企业其他人重复时给明确的错误码，与新建员工一致 |
| 测试数据 | 开发库里没有手机号的用户补成 `138` + 8 位用户 ID（如用户 5001 补成 `13800005001`），保证不重复、好记；`testdata.sql` 同步补上，`tools/gen_testdata.py` 改为按用户 ID 生成 |

## 2. 现状（据实证）

- **账号生成**：两条建号路径都用 `MakeEmployeeAccount(userId)` 拼成 `EMP` + 用户 ID（`chatserversrc/AccountName.cpp:12`）。自助注册经 `RegisterService` → `UserManager::addUser`，`username` 留空时由它生成（`UserManager.cpp`）；管理员新建员工在 `EmployeeManager::createEmployee`（`EmployeeManager.cpp`）。用户 ID 由 `allocUserId` 取「库里最大值 + 1」（`UserManager.cpp`），所以账号连续：开发库里客户端注册出的账号是 `EMP5313`、`EMP5314`、`EMP5315`……（只读查询 `build-linux/data/flamingo.db`）。自助注册不填工号（`f_employee_no` 为 NULL）；`MY0001` 这批账号来自 `testdata.sql`，工号与账号相同。
- **编辑员工的工号**：`updateEmployee` 把工号按字符串写入 `f_employee_no = '%s'`（`EmployeeManager.cpp`），没填时写成空串；`createEmployee` 没填时写 NULL。`t_user` 有唯一索引 `uk_ent_employee_no (f_enterprise_id, f_employee_no)`（`table_mysql.sql:34`）。
- **登录**：`ChatSession::onLogin` 只调 `UserManager::getUserInfoByUsername`（`ChatSession.cpp`），后者在内存缓存里做区分大小写的精确比较（`UserManager.cpp`）；而库里 `f_username` 在 SQLite 上是 `COLLATE NOCASE`、在 MySQL 上是不区分大小写的 `utf8_general_ci`（`tools/gen_table_sqlite.py` 的 `NOCASE_COLUMNS`）。查不到返回 `error_code_not_registered`（102），客户端提示「该账号未注册。」（`App/UIText.h:33`）。
- **手机号唯一性**：只有自助注册查重（`RegisterService.cpp`，经 `getUserInfoByPhone` 扫缓存）；服务端注册不校验格式，格式只在客户端查（`RegisterModel.h:53`）。管理后台新建、编辑员工时手机号可空、不查重（`EmployeeManager.cpp` 的 `createEmployee` / `updateEmployee` 只是原样写入）；库上没有手机号的唯一索引。
- **企业设置**：`t_enterprise` 没有账号前缀列（`table_mysql.sql:155-177`）；`/admin/enterprise/update.do` 只有平台超管能调，按「全量覆盖」写 `f_name / f_short_name / f_industry / f_region / f_plan`（`HttpSession::onAdminEnterpriseUpdate`、`EnterpriseManager::updateEnterprise`）。
- **测试数据**：5 个开发库里有 4 个有数据（`build-linux/data`、`flamingoserver/data`、`windowsproj/data`、`windowsproj/x64/Debug/data` 下的 `flamingo.db`），每个库 320～322 个用户里有 316 个没有手机号；`testdata.sql` 插入用户时不带 `f_phonenumber`，且已没有生成脚本，平时直接维护（`tools/import_testdata_sqlite.py` 把它导入 SQLite）；`tools/gen_testdata.py` 随机生成手机号，可能重复。
- **客户端登录框**：账号框只检查非空（`BalloonLoginLayout.h`），占位文字是「账号」（`BalloonLoginLayout.cpp`），对输入的字符与长度没有限制。

## 3. 服务端

### 3.1 编辑员工的工号

`updateEmployee` 与 `createEmployee` 一致：工号为空写 NULL；工号非空时先查本企业有没有别人用着（排除自己），有则返回与新建相同的「工号已存在」错误码，不再落到 `db execute error`。

### 3.2 企业账号前缀

- `t_enterprise` 加 `f_account_prefix varchar(16) DEFAULT NULL COMMENT '新建账号的前缀：英文字母与点号，大写保存；为空时用 EMP'`，按惯例改 `table_mysql.sql`、重新生成 SQLite 架构、`MysqlManager.cpp` 列清单加一行。
- `EnterpriseInfo` 加 `accountPrefix`；企业详情、列表的 JSON 加 `accountprefix`。
- `/admin/enterprise/update.do` 新增可选字段 `accountprefix`：**带了才改**（老版本控制台不带这个字段，不能因此把前缀清空），空串表示清除。校验与规整用纯函数 `NormalizeAccountPrefix`（`AccountName.h`）：去掉首尾空白、长度 1～10、只含字母与点号、至少一个字母，转大写；不合格返回新的管理端错误码「账号前缀不合法」。
- 权限沿用 `update.do` 现有的「只允许平台超管」，不新开企业管理员入口（见第 4 节）。
- 新建企业接口 `create.do` 暂不带前缀：企业建好后在企业设置里设置。

### 3.3 随机账号

- `AccountName.h` 新增纯函数 `MakeRandomAccount(prefix, number)`：`prefix` 为空时用 `EMP`，`number` 取 10000000～99999999，拼成 `前缀 + 8 位数字`。
- `UserManager` 新增 `allocRandomAccount(prefix)`：用进程内的随机数发生器（`std::mt19937`，以 `std::random_device` 播种）抽号，在用户缓存里按不区分大小写查重，撞号重抽，最多 20 次；仍然撞号（理论上不会发生）时返回空串、建号失败。
- 两条建号路径都改用它：自助注册在 `ChatSession.cpp` 的 `createUser` 里按企业取前缀（`EnterpriseManager::getAccountPrefix`）、抽好账号后再交给 `addUser`；管理员新建员工在 `createEmployee` 里同样取前缀。`addUser` 收到空账号时也改为抽 `EMP` + 8 位随机数字，作为其他调用方的兜底。`MakeEmployeeAccount` 不再用于建号（保留给存量逻辑与单测）。
- 并发：查重与写库之间不加全局锁。两个请求恰好抽中同一个号的概率极低，万一发生，库上的 `uk_f_username` 让后到的那次写库失败、按建号失败返回，用户重试即可。

### 3.4 账号与手机号登录

- `UserManager::getUserInfoByUsername` 改为不区分大小写（与库的比较规则一致）。
- `onLogin`：先按账号查；查不到、且输入是 11 位以 1 开头的数字时，再按手机号查。查找顺序收在 `UserManager::findLoginUser`，「像不像手机号」直接用下一条的 `IsValidPhoneNumber`，没有另写判定函数。按手机号匹配上时记一条 `login matched by phone` 日志，都查不到时记 `login rejected: no account or phone matches`。协议不变，老客户端输入手机号也能登录。
- 手机号格式校验收成一个纯函数 `IsValidPhoneNumber`（11 位、以 1 开头、全是数字），注册、管理后台新建与编辑员工共用。
- `getUserInfoByPhone` 只匹配普通用户（排除群账号与空号码）。

### 3.5 管理后台新建、编辑员工

- 手机号必填、格式合法、不能与其他账号重复（编辑时排除自己）；不合格分别返回新的管理端错误码「手机号不能为空 / 格式不正确」「手机号已被其他账号使用」。
- 新建员工的账号按第 3.3 节生成。

## 4. 管理后台 flamingoAdmin

现状（据实证）：

- 企业设置窗口 `Screens/EnterpriseSettingsModal`（从企业详情页的「企业设置」按钮与企业列表的行菜单打开，都经 `AdminFrame::OpenEnterpriseSettings`）：表单是两列三行，第三行右列空着（`EnterpriseSettingsModal::LayoutFormControls`）；保存经 `adminapi::MakeEnterpriseUpdateRequest`（`Util/AdminApi.cpp`）调 `update.do`。从详情页保存后 `AdminFrame::OnEnterpriseUpdated` 不更新 `DataStore` 里的企业记录，再打开设置窗口显示的仍是旧值。
- 企业数据结构 `Enterprise`（`Mock/MockData.h`），由 `EnterpriseFromJson`（`Util/AdminApi.cpp`）从列表与详情应答解析。
- 员工：新建在 `Screens/NodeModal`（手机号占位文字「手机号（可选）」），编辑在 `Screens/EmployeeEditDialog`（标签「手机号」不带星号）；两处本地只校验姓名与邮箱。
- 服务端错误码到提示文字只有一张表 `DescribeAdminError`（`Util/AdminApi.cpp`），新建与编辑员工、修改企业的失败都经它变成提示，窗口保持打开。表里没有 101（工号已存在）、102（员工不存在）、119（企业全称已被占用），这几种失败现在显示为「操作失败（错误码 N）」。

改法：

- **企业设置窗口**：第三行右列加「账号前缀」输入框（控件 id 取 397），填入时按企业现有前缀，占位文字「不填时为 EMP，如 HW.」，规则写进字段标签「账号前缀（字母与点号，只影响新账号）」，不另加说明行（加一行会改变表单高度），输入框最多 10 个字符。保存时本地先用纯函数 `adminapi::NormalizeAccountPrefix`（与服务端同一套规则）校验，不合格给出提示、不发请求；`MakeEnterpriseUpdateRequest` 加参数 `accountprefix`。表单行数不变，窗口高度与现有布局单测（ESS1～ESS5）不受影响。
- **企业数据**：`Enterprise` 加 `m_accountPrefix`，`EnterpriseFromJson` 读 `accountprefix`；企业详情页头部的信息行显示当前前缀。顺带修正保存后 `DataStore` 里的企业记录不更新的问题。
- **员工手机号**：新建与编辑窗口的手机号都改为必填（标签「手机号 *」，占位文字「11 位手机号，可用于登录」），本地用 `adminapi::IsValidPhoneNumber` 校验格式；为空或格式不对时提示「请填写正确的手机号（11 位，以 1 开头）」、不发请求。
- **错误提示**：`DescribeAdminError` 补上 101「工号已被本企业其他员工使用」、102「员工不存在，可能已被删除」、119「企业全称已被其他企业使用」，以及新的 150「请填写正确的手机号（11 位，以 1 开头）」、151「该手机号已被其他账号使用」、152「账号前缀只能由字母和点号组成，1～10 个字符」。
- **权限**：`update.do` 目前只允许平台超管调用（`HttpSession.cpp:940-944`），企业设置窗口也只在平台超管能进入的企业页面里，账号前缀沿用这一权限，不新开企业管理员入口。

## 5. PC 客户端

- 登录框占位文字「账号」改为「账号 / 手机号」；账号为空时的提示「请输入账号！」改为「请输入账号或手机号！」；登录失败「该账号未注册。」改为「该账号或手机号未注册。」。
- 记住的登录名就是用户输入的那一个（账号或手机号），自动登录照常可用；主面板与资料里显示的账号取登录应答里的 `username`，不受影响。本地数据目录 `Users\<账号>\` 按登录应答里的 `username` 建（`CFlamingoClient::OnLoginResult` 把它写进本人资料，`FlamingoClient.cpp:769`），同一个人用手机号与账号登录用的是同一个目录。
- **联调中发现的问题（据实证，2026-10-06 用界面实际登录复现）**：历史账号列表 `LoginAccountList.dat` 以输入的原文为键，而登录后本人资料里的账号已换成 `username`，有三处拿后者去查列表，用手机号或大小写不同的账号登录时查不到：
  - 退出登录与被踢下线（`CSessionController::ReturnToLoginWindow`）清不掉「自动登录」。实测日志 `ClearAutoLoginFlag: account is not in the history list, skipped. account=FL.43350744`，列表里那条手机号记录的自动登录标志仍为 1，下次启动照样自动登录；退出后登录窗预填的也是 `username`，认不出这条记录（不显示姓名与头像），再登录一次会多出一条同一个人的记录。
  - 断线重连回「密码错误」时忘不掉已存的密码（`ForgetSavedPasswordForCurrentAccount`）。
  - 登录窗删除账号并勾选「同时删除本地聊天记录」时，按输入的原文拼目录（`Users\<手机号>\`），目录不存在就当作已删干净，真正的聊天记录留在原处。
- **修法（2026-10-06 与用户确认：下拉列表仍记输入的手机号）**：
  - 历史记录 `LOGIN_ACCOUNT_INFO` 新增 `szAccountName`（服务端返回的规范账号），按现有办法用第三个尾块（魔数 `FLA3`）落盘，老文件读不到时为空、按原文处理；登录成功后由会话控制器 `SetAccountName` 写入。
  - 新增两个纯函数（`Session/LoginAccountList.h`）：`PickLoginAccountListKey` 取本次登录在列表里的键（输入的原文，取不到时退回规范账号）；`LoginAccountDataName` 取一条记录的本地数据目录名（规范账号，为空时退回原文）。
  - 退出登录 / 被踢下线清自动登录、回填登录窗，以及密码错误忘掉密码，都改用输入的原文；登录窗删除本地数据按 `LoginAccountDataName` 定位目录。
  - 断线重连仍发 `username`（服务端照常认），不受影响。
- 新文字按多语言约定包进 `TR` 并补四种语言译文。

## 9. 风险与不做的

- **用户 ID 仍然连续**：它出现在协议报文里（界面上看不到），懂行的人抓包仍能看出先后。改用户 ID 的分配方式牵涉群号边界（`0x0FFFFFFF`）与大量存量数据，本次不做。
- **大小写**：账号改为不区分大小写后，若库里已有只差大小写的两个账号，登录取先找到的那一个。数据库上的唯一索引本来就不区分大小写，按理不会有这种数据。
- **手机号唯一性只在应用层保证**：库上不加唯一索引（存量数据里可能有空串与重复，加索引会让老库启动失败）；本次补测试数据时一并核对没有重复。
