# 群公告接入方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-08-03
> 用途：记录把「群公告」从现在的一个自由文本字段，做成设计稿要求的「多条公告 + 发布人 + 优先级 + 撤回 + 全员通知」完整功能的方案、分期路线与开发步骤。后续每步开工前据此细化、收尾后回填实际结果。
> 体例沿用 `docs/群管理接入方案.md`：结论一律标注来源，「据实证」必附文件:行号，「据推测」表示尚未验证。

## 1. 背景与目标

设计稿里群公告是一个独立功能，横跨三处界面：

- `design/群管理7.png` —— 群管理窗左侧导航有独立的「群公告」分组与页面，页内是「发布新公告」表单（优先级三选一 + 标题 + 正文 + 清空 / 发布）与「历史公告 · N 条」列表（每条可「重新发布」「撤回」）。
- `design/群公告.png` —— 群聊窗右侧边栏「公告」Tab，按条分页浏览（`‹ 1/2 ›` + 圆点指示器），卡片显示标题、正文、发布人头像与昵称、发布时间。
- `design/群公告.png` 头部 —— 群名右下方一行 `📌 v3.2 版本即将发布，全员准备。`，即最新一条公告的标题摘要。

而现在服务端只有一个 `varchar(1024)` 的自由文本字段，客户端能真正编辑它的地方只有群管理窗「基本信息」页里那个多行输入框。**两者差着一整个数据模型**：设计稿要的是「一个群有多条公告，每条有标题、优先级、发布人、发布时间、可撤回」，现状是「一个群有一段话」。

本方案的目标是把这个差补齐，并且做到：老客户端与现有的三处只读展示（群资料对话框、会话列表、旧接口）**完全不用改也能继续正常显示最新公告**。

## 2. 现状盘点（据实证，均已核对代码位置）

### 2.1 服务端：一个群一段话，没有发布人也没有时间

`table.sql:397` 的 `t_group.f_announcement` 是 `varchar(1024) NOT NULL DEFAULT '' COMMENT '群公告'`，整张表里与公告相关的就这一列 —— 没有发布人、没有发布时间、没有历史。

改公告走的是通用的改群资料通道：`ChatSession::onUpdateGroupInfo`（`ChatSession.cpp:3106`）校验 `myrole < group_role_admin` 拒绝（`:3127-3133`），`GroupManager::updateGroupInfo` 在 `req.has_announcement` 时拼一条 `f_announcement = '...'` 的 SET 片段（`GroupManager.cpp:505-506`），成功后向全体成员推 `cmd_group_info_changed_notify`（`:3145-3156`）。

**没有**：公告变更时在群里发系统消息，也**没有**任何"通知全员"的动作 —— 只有那条群资料变更推送。

### 2.2 客户端：四处涉及公告，真正能用的只有一处

| 位置 | 状态 | 证据 |
| --- | --- | --- |

### 2.3 已经具备的基础

- **服务端能自动加列**：`CMysqlManager::_CheckTable` 会对已登记但表里没有的列执行 `ALTER TABLE ... ADD COLUMN`，用的是 `STableField` 的完整定义串（带 `NOT NULL` 与 `DEFAULT`），老库升级后已有行直接拿到默认值（`MysqlManager.cpp:447-475` 是 `t_group` 的登记，七列群管理新字段就是这样加上去的）。**新增列与新建表都不需要手工 SQL。**
- **服务端生成系统消息有现成范例**：`ChatSession::sendGroupWelcomeMessage`（`ChatSession.cpp:3254-3300`）用 `message_type_system` + `kSystemMessageSenderId` 往群里插了一条入群欢迎语，连"给服务器生成的消息编一个不会与客户端撞车的 clientMsgId"这种细节都有现成写法（`:3293`）。公告的系统提示照抄即可。
- **客户端有居中系统提示行**：`ChatBubble` 支持把一行就地变成居中的系统提示（`ChatBubble.h:146`、`ChatBubble.cpp:1025`），单聊窗的"对方向你发送了窗口抖动"就是这么显示的（`BalloonChatWindow.h:144`）。
- **优先级 chip 有现成做法**：群文件面板的分类筛选 chips 就是一排 `buttonType="push"` 的 `DuiButton`（`GroupChatWindowLayout.cpp:553-557`），公告的「通知 / 重要 / 紧急」三选一可以照搬，不必自绘。
- **群管理窗的页面 / 导航 / 角色门控是数据驱动的**：加一页只要在 `GmPageId` 加一个 id、`BuildNav` 加一项、`BuildPage` 加一个分支、`IsPageVisibleForRole` 加一条规则（`GroupManageLayout.h:26-39`、`GroupManageLayout.cpp:1179-1233`、`GroupManageMapping.cpp:391-425`）。

## 3. 三个岔路口与选择

### 3.1 多条公告：新建表，`f_announcement` 降级为"最新公告快照"

设计稿要的是多条（`群管理7.png` 的"历史公告 · 2 条"、`群公告.png` 的 `1/2` 翻页），单条字段撑不住。

**选择**：新建 `t_group_announcement` 表存全部公告；`t_group` 保留 `f_announcement` 并**改由服务端自动维护** —— 每次发布 / 撤回后同步刷成"当前最新已发布公告的正文"，另加三列存该公告的 id、标题与发布时间。

这样做的好处是所有现存的只读展示（群资料对话框、1303、1318）**一行都不用改**就能继续显示最新公告，老客户端也不受影响；要历史、要发布人、要撤回的新界面才走新协议。

**代价**：`f_announcement` 从"用户直接编辑的字段"变成"派生字段"，群管理窗「基本信息」页那个输入框必须撤掉（见 §3.3），否则两条写入路径会互相打架。

### 3.2 通知全员：推送 + 群内系统消息 + 弹窗，三件事分开

`群管理7.png` 页顶那句"发布后所有成员将收到弹窗通知，并可在公告管理器中再次查看"要求发布后主动触达每个成员。拆成三件独立的事：

1. **推送 `cmd_group_announcement_notify`**（新增）—— 已打开的群聊窗 / 群管理窗据此实时刷新，不需要重拉。
2. **群内系统消息** —— 服务端插一条 `message_type_system`：`「张三」发布了群公告：v3.2 版本即将发布`。它会进历史消息、进会话预览，用户即使当时不在线，之后进群也看得到。
3. **客户端弹窗** —— 收到推送且该公告没弹过时弹一次。**必须按公告 id 去重并本地持久化**，否则每次重连收到推送都弹，会变成骚扰。

第 2、3 件是可选的，可以放到二期；第 1 件是必需的。

### 3.3 「基本信息」页那个公告输入框怎么办

**选择**：撤掉，并在原位放一行只读的最新公告摘要 +「去群公告页管理」的跳转按钮。

理由：留着它就有两条语义不同的写入路径（一条改自由文本、一条发带标题的公告），先后顺序不同结果就不同，是必然要还的债。撤掉之后 `SaveBasicInfo` 里公告那一段（`GroupManageWindowData.cpp:700-710`）一并删掉。

> 这一条会让「基本信息」页的保存按钮只剩"群名称 + 群简介"两项可改，属于预期内的收敛。

## 4. 数据库设计

### 4.1 新建 `t_group_announcement`

```sql
//群公告表（v2 群公告功能）：一行 = 某群的一条公告。撤回是软删（f_status=2），
//历史照旧保留，群管理页的「历史公告」列表按 f_publish_time 倒序展示。
CREATE TABLE IF NOT EXISTS t_group_announcement (
    f_id           bigint(20)     NOT NULL AUTO_INCREMENT COMMENT '公告ID',
    f_groupid      bigint(20)     NOT NULL COMMENT '所属群ID',
    f_title        varchar(128)   NOT NULL DEFAULT '' COMMENT '公告标题(必填)',
    f_content      varchar(2048)  NOT NULL DEFAULT '' COMMENT '公告正文',
    f_severity     int(2)         NOT NULL DEFAULT 0 COMMENT '优先级:0通知 1重要 2紧急',
    f_publisher    bigint(20)     NOT NULL DEFAULT 0 COMMENT '发布人userid',
    f_publish_time bigint(20)     NOT NULL DEFAULT 0 COMMENT '发布时间(Unix毫秒)',
    f_status       int(2)         NOT NULL DEFAULT 1 COMMENT '状态:1已发布 2已撤回',
    PRIMARY KEY ( f_id ),
    KEY idx_group_status ( f_groupid, f_status )
) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

同时在 `MysqlManager.cpp` 的表登记里追加一份（照 `t_group_sensitive_word` 的写法），老库首次启动即自动建表。

### 4.2 `t_group` 新增三列

| 列 | 定义 | 用途 |
| --- | --- | --- |
| `f_announce_id` | `bigint(20) NOT NULL DEFAULT 0` | 最新已发布公告的 `f_id`；0=本群没有公告 |
| `f_announce_title` | `varchar(128) NOT NULL DEFAULT ''` | 最新公告标题。群聊窗头部 `📌` 摘要行显示的就是它，冗余一份省掉一次连表 |
| `f_announce_time` | `bigint(20) NOT NULL DEFAULT 0` | 最新公告发布时间(Unix毫秒) |

`f_announcement`（既有列）语义收窄为"最新已发布公告的正文"，由服务端维护，不再由客户端直接写。

老库由 `_CheckTable` 自动加列，默认值即"本群还没有公告"，与新建群一致，读取处无需兜底。

## 5. 协议设计

在 `Protocol.h`（客户端 `net/Protocol.h:122-143`、服务端 `chatserversrc/Protocol.h`）的群协议段尾部追加四条。1301~1322 已用满，**1323 起为空号**（据实证：两份 `Protocol.h` 的群段最大值都是 1322）。

| 协议号 | 名称 | 方向 | 权限 |
| --- | --- | --- | --- |
| 1323 | `cmd_get_group_announcements` | 请求 / 应答 | 全体群成员 |
| 1324 | `cmd_publish_group_announcement` | 请求 / 应答 | 群主 + 管理员 |
| 1325 | `cmd_revoke_group_announcement` | 请求 / 应答 | 群主 + 管理员 |
| 1326 | `cmd_group_announcement_notify` | 服务端推送 | —— |

### 5.1 1323 拉公告列表

```jsonc
// 请求
{"groupid":"10000000001", "offset":0, "count":20, "includerevoked":0}
// includerevoked: 0=只回已发布(群聊窗边栏用) 1=连撤回的一起回(群管理页的历史列表用)

// 应答
{"code":0, "msg":"ok", "groupid":"10000000001", "total":2,
 "announcements":[
   {"id":"12", "title":"v3.2 发布周五上线", "content":"...",
    "severity":1, "publisher":"100023", "publishername":"林知夏",
    "publishtime":1785000000000, "status":1}
 ]}
```

`publishername` 由服务端查 `UserManager` 填好再下发 —— 发布人可能已退群，客户端的成员列表里未必找得到他。

### 5.2 1324 发布公告 / 重新发布

```jsonc
// 新发布
{"groupid":"10000000001", "title":"...", "content":"...", "severity":0}
// 重新发布（把某条历史公告以当前时间重新发一遍；服务端读旧内容新建一条，历史保留）
{"groupid":"10000000001", "id":"12"}

// 应答
{"code":0, "msg":"ok", "id":"15"}
```

校验：`title` 去空白后非空、字符数 ≤ 128；`content` 字符数 ≤ 2048；`severity` ∈ {0,1,2}，越界按 0 处理。任一不过回 `error_code_bad_request`。

### 5.3 1325 撤回公告

```jsonc
{"groupid":"10000000001", "id":"12"}
{"code":0, "msg":"ok"}
```

群主与管理员都可撤回**任意一条**（依 `群管理7.png` 的管理员视图里每条都有撤回按钮）。撤回已撤回的按成功返回（幂等）。

### 5.4 1326 公告变更推送

```jsonc
{"groupid":"10000000001", "changetype":1,
 "announcement":{"id":"15", "title":"...", "content":"...", "severity":0,
                 "publisher":"100023", "publishername":"林知夏",
                 "publishtime":1785000000000, "status":1}}
// changetype: 1=新发布(客户端据此弹窗) 2=已撤回(客户端据此从列表摘掉)
```

推送体里带完整公告，客户端不必再拉一次就能刷新边栏与弹窗。

### 5.5 新增错误码

| 错误码 | 含义 |
| --- | --- |
| `error_code_announcement_not_exist` | 公告不存在或不属于本群（撤回 / 重新发布时） |

其余复用现有的 `error_code_not_group_admin`(303)、`error_code_group_not_exist`、`error_code_bad_request`。

## 6. 服务端行为

### 6.1 发布（1324）

1. 校验群存在、发起人 `role >= group_role_admin`，否则 `error_code_not_group_admin`。
2. 写 `t_group_announcement` 一行，`f_status=1`、`f_publish_time=` 当前 Unix 毫秒。
3. **同步 `t_group` 的四列**：`f_announce_id` / `f_announce_title` / `f_announce_time` / `f_announcement`（正文）。
4. 回应答，随后向全体成员推 1326（`changetype=1`），并推一条 1318 —— 因为 `t_group` 变了，已有的群资料展示处（群资料对话框、会话列表）靠这条刷新。
5. 往群里插一条 `message_type_system` 消息：`「<发布人昵称>」发布了群公告：<标题>`，做法照抄 `sendGroupWelcomeMessage`。

### 6.2 撤回（1325）

1. 同样的权限校验；公告不存在或 `f_groupid` 对不上回 `error_code_announcement_not_exist`。
2. 置 `f_status=2`。
3. **若撤回的正好是 `t_group.f_announce_id` 那条**，回填上一条仍为已发布的公告（`ORDER BY f_publish_time DESC LIMIT 1`）到那四列；一条都没有了就清空（id=0、标题与正文置空）。
4. 回应答，推 1326（`changetype=2`）；第 3 步动了 `t_group` 时一并推 1318。

### 6.3 拉列表（1323）

只校验"发起人是本群成员"（`getMemberRole >= 0`）。`includerevoked=0` 时 `WHERE f_groupid=? AND f_status=1`，按 `f_publish_time DESC` 排序、`LIMIT offset,count`；`total` 用同条件的 `COUNT(*)`。

### 6.4 权限矩阵

| 操作 | 群主 | 管理员 | 普通成员 |
| --- | --- | --- | --- |
| 查看公告（1323、边栏、头部摘要） | ✓ | ✓ | ✓ |
| 发布 / 重新发布（1324） | ✓ | ✓ | ✗ |
| 撤回（1325） | ✓ | ✓ | ✗ |
| 进群管理窗「群公告」页 | ✓ | ✓ | ✗（普通成员在群聊窗边栏看） |

## 7. 客户端改造

### 7.1 群管理窗新增「群公告」页

- `GroupManageLayout.h` 的 `GmPageId` 加 `kPageAnnouncement = 1008`；`GmEditId` / `GmCtrlId` 加标题框、正文框、三个优先级 chip、清空、发布，以及历史列表逐行的「重新发布」「撤回」两组 id 基址（照现有 `kIdApprovalAcceptBase` 那样每段留 50 个）。
- `BuildNav` 里在「成员」组之后、「设置」组之前插入一个新分组标题「群公告」与一个导航项，徽章数 = 已发布公告条数（对齐 `群管理7.png` / `群管理8.png` 的导航结构）。
- `IsPageVisibleForRole` 加一条：`kPageAnnouncement` → 群主与管理员可见。
- 页面内容全部用 balloonui 现成控件搭：`DuiVBox` / `DuiHBox` / `DuiLabel` / `DuiEditHost`（标题单行、正文多行）/ `DuiButton`（优先级 chip 用 push 变体，与群文件分类 chips 同款）/ `DuiScrollView`（历史列表）。**按开发约定文档的 UI 约定，不新写自绘控件**；唯一可能需要子类化的是历史公告条目那张卡（圆角浅底 + 左侧铃铛图标），优先看能否用 `DuiVBox` + 背景色 + `DuiImage` 拼出来。
- 数据落点照现有套路：模型加 `std::vector<GroupAnnouncement> m_announcements`，映射函数 `ApplyGroupAnnouncements` 放进 `GroupManageMapping.cpp`（纯函数、可单测）。

### 7.2 群聊窗右侧边栏「公告」Tab

- 布局 XML 加第三个内容容器 `kGIdNoticePanel = 570`（成员 550 / 群文件 551 之后），内含：顶部「群公告 · N 条」+ `‹ x/y ›` 翻页 + 圆点指示器，中间一张公告卡片（标题 / 正文 / 分隔线 / 发布人头像 + 昵称 + 时间），对照 `design/群公告.png`。
- `SwitchSideTab`（`BalloonGroupChatWindow.cpp:2705-2790`）现在硬编码了"成员 / 群文件"两个面板的显隐与 `ForceLayout`，要改成三个。**这里有个已知的 balloonui 布局坑**：切可见性后子控件会停在 `{0,0,0,0}`，必须拿槽位矩形对新显示的容器 `ForceLayout` —— 现有代码已经这么处理了，照着扩一路即可。
- 首次切到公告 Tab 时发 1323 拉一次（`includerevoked=0`），拉完渲染；之后靠 1326 推送增量更新。做法与群文件 Tab 的 `m_fileLoaded / m_fileLoading` 一致。

### 7.3 群聊窗头部 `📌` 摘要行

- 布局 XML 头部左侧的 `<control weight="1"/>` 占位（`GroupChatWindowLayout.cpp:92-94`）换成 `<group-headerinfo id="506" weight="1"/>`。

## 10. 实施回填（2026-08-03）

A1~A6 六步已全部落地，编译与单元测试通过。与本方案原稿的出入、以及实施中补上的细节记在这里。

### 10.1 与原稿一致的部分

数据库、协议号（1323~1326）、服务端行为（发布后推 1326 + 1318 + 插一条系统消息；撤回后回填快照）、权限矩阵、§3 的三个取舍都按原稿实现，没有改动。

### 10.2 实施中补上的细节

1. **`t_group` 加的是三列而不是原稿说的"另加三列 + 复用 f_announcement"里含糊的部分**：最终是 `f_announce_id` / `f_announce_title` / `f_announce_time` 三列新增，`f_announcement` 语义收窄为"最新已发布公告的**正文**"。头部 `📌` 摘要行显示的是 `f_announce_title`（标题），群资料对话框那个浅橙框显示的仍是 `f_announcement`（正文）—— 两处要的粒度本来就不同。

2. **长度校验按字符而不是字节**。`varchar(128)` 在 MySQL utf8 下是 128 个**字符**，按字节校验会让纯中文标题写十几个字就被拒。`GroupProtocol.cpp` 里加了 `utf8CharCount`，用例 `parsePublishAnnouncementRequest 长度按字符计` 锁住了这条。

3. **`error_code` 取 310 而不是接着 309 往下**。群组段的 307 / 308 各被两个错误码占着（`error_code_cannot_operate_owner` 与 `error_code_join_need_approval` 都是 307，`error_code_sensitive_word` 与 `error_code_join_req_not_exist` 都是 308）—— 这是既有问题，改动会影响现网客户端对错误码的判断，故本次<u>没有动它</u>，只是新号避开了这一段。

4. **`FMG_MSG_LAST` 从 535 抬到 539**。它是 socket 线程投给代理窗口的消息号段闸门，超出范围的消息在 `ProxyWndProc` 里会被直接丢弃、连 `switch` 都进不去。新增的三个消息号（537 公告列表应答 / 538 公告变更推送 / 539 提示窗→主面板"查看全部"）都在它之内。

5. **公告面板复用 balloonui、没有新写自绘控件**。公告卡是普通 `<vbox>`，圆角浅底与各行字号 / 换行由 `ConfigureNoticePanelDefaults` 用 `DuiVBox` / `DuiLabel` 现成的 setter 配置 —— XML builder 的通用属性只认 `id` 与 `padding` / `gap`，配色字号走不了 XML。群管理页那边只加了一个 `GmIcon`（画本目录矢量图标集的小控件，与同文件里的 `GmText` / `GmSectionHeader` 同类），理由写在类注释里。

6. **弹窗去重的判定抽成了纯函数**（`BalloonGroupManage/AnnouncePopupPolicy`）。拒绝弹窗有四条理由：公告ID非正、不是"新发布"、发布人就是自己、公告ID不大于上次弹过的。最后一条同时挡住"断线重连后重复推来的同一条"与"推送乱序时补到的更旧的一条"。记账落在 `<账号>.cfg` 的 `[GroupAnnouncePopped]` 小节，键是群ID、值是最后弹过的公告ID —— 用 INI 而不是内存，重启客户端后不会把开机前那条再弹一遍。

## 11. 变更：删除取代撤回、列表分页（2026-08-03）

起因是两个问题：公告攒多了怎么展示；以及需要删除功能。经与用户确认后做了下面这轮改动，**本节的结论覆盖前文中与"撤回"「软删」有关的一切描述**（§3.1 的 `f_status`、§5.1 的 `includerevoked`、§5.3 的撤回、§6.2 的回填逻辑）。

### 11.1 删除取代撤回，软删机制整个拆掉

不再有"撤回"这个动作，也不再有"已撤回"这个状态。删除就是真删：`DELETE FROM t_group_announcement`，那一条从库里、从所有人的列表里一起消失，不可恢复。

拆掉的东西：`t_group_announcement.f_status` 列、`group_announcement_status` 枚举（两端）、`includerevoked` 请求字段、应答与推送里的 `status` 字段、界面模型的 `AnnounceStatus` 与"已撤回"显示分支。留着它们只会让后来读代码的人以为还有软删这条路。

`cmd_revoke_group_announcement`(1325) 更名为 `cmd_delete_group_announcement`，协议号不变；推送的 `changetype=2` 从"已撤回"改为"已删除"。索引由 `idx_group_status(f_groupid, f_status)` 换成 `idx_group_time(f_groupid, f_publish_time)` —— 查询条件里不再有状态，排序键才是该建索引的地方。

**权限**：群主与管理员都能删，且可删任意一条（与发布、与原先的撤回同一口径）。界面上删除按钮用危险色，点击必过一道确认，提示语里明说"彻底消失、无法恢复"。

> 存量库里已经建出来的 `f_status` 列不会被自动删除（SQLite 的补列机制只加不删，MySQL 侧同理）。这不影响运行 —— 代码不再读写它，`INSERT` 不带这一列时由列默认值兜住。新建的库则没有这一列。

### 11.2 群管理窗「历史公告」改为分页

原先是把拉回来的公告全部铺成卡片（每条约 84px），且客户端写死 `offset=0, count=100` —— 超过 100 条的根本拿不到，而 100 条会在控件树里建出 8400px 的内容、每次发布 / 删除还要整页重建。

现在每页 8 条（`kAnnouncePageSize`），底部一行「共 N 条 · 第 x/y 页」加 ‹ › 翻页，与群文件面板同一套交互。翻页即向服务端要那一页（`offset = page * 8`），本地只留当前这一页。

几处配套：
- 左侧导航「群公告」的计数徽章改用服务端给的 `total`，不再数本地列表（本地只有一页）；
- 逐条按钮的 ctrl id 段随之收窄（一页至多 8 条，每段留 20 个），`kIdAnnounceRepublishBase` / `kIdAnnounceDeleteBase`；
- 页号越界时夹回最后一页 —— 典型场景是停在最后一页、把那页唯一一条删掉，不夹的话界面会显示"第 5/4 页"加一片空白；
- 新公告发布后回到第一页（它排最前），删除后留在原页（免得刚删一条就被弹回第一页）。

### 11.3 群聊窗公告边栏改为按需拉单条

边栏本来就是一次只看一条、靠 ‹ x/y › 翻，所以不必把整份列表拉回来。现在改成 `offset=当前下标, count=1`：翻到哪条要哪条，`total` 从应答里取。这样公告有几千条也不受服务端单页上限影响，本地也只留手上这一条。

代价是每翻一页一个来回，但公告是低频浏览，不值得为它加一层本地缓存。翻页请求在途时再点翻页会被 `m_noticeLoading` 挡掉；1326 推送到达时会清掉这个标志再重拉 —— 在途那次拿回的是旧数据，本来就该被覆盖。

### 11.4 测试结果

服务端 277 用例 / 1838 断言全绿；客户端公告相关 32 用例 / 226 断言全绿（含新增的分页边界与页号夹取用例）。`Flamingo.vcxproj` 编译通过。

> 本轮收尾时 `chatserver.vcxproj` 编不过，原因在 `MessageManager.cpp` 与 `MessageProtocol.cpp` 的并行改动（数据库抽象层与文件回执状态，与公告无关），需待那边落定后再整体编译并重启服务端验证。
