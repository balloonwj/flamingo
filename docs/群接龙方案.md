# 群接龙接入方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-02
> 用途：记录给 PC 客户端群聊增加「接龙」功能的整体方案、分期路线与开发步骤。后续每步开工前据此细化、收尾后回填实际结果。

---

## 1. 背景与目标

群里经常需要收集每个人的一条信息：团建报名、订餐、值班登记、资料提交确认。现在只能每人在群里回一句，再由组织者从聊天记录里逐条摘出来统计，人一多就容易漏。本方案给群聊加一张「接龙」卡片：发起人写好标题和格式说明，群成员各自填写一条，所有人看到的是同一份按顺序排列的名单，组织者可以一键复制整份结果。

最终形态：在群聊窗头部那一排图标里点「发起接龙」，填写标题、说明、截止时间后发出一张卡片；群成员点卡片打开详情窗，提交、修改或撤回本人那一条；每次变化都会在群里留下一行系统提示，所有打开着的卡片实时刷新；发起人、群主、管理员可以提前结束接龙。

以下口径均已与用户逐条确认（2026-10-02），实现时不再另行请示：

| 决策点 | 取值 | 详见 |
| --- | --- | --- |
| 适用会话 | 只做群聊；协议允许单聊卡片，但入口只放在群聊窗 | §3.1 |
| 参与后群里是否出现新内容 | 刷新原卡片，**并且**发一条系统提示 | §3.4 |
| 哪些操作发系统提示 | 参与、修改、撤回本人那条都发；提前结束也发 | §3.4 |
| 截止时间 | **必填**，发起时自定义年月日时分秒，不能早于当前时间 + 5 分钟，到点后不再接受参与（2026-10-03 起；此前是几档预设、可以不限） | §3.5 |
| 提前结束 | 支持，发起人、群主、管理员可操作 | §3.5 |
| 到截止时间是否发提示 | **不发**，各端按时间自行显示「已截止」，服务端不加定时任务 | §3.5 |
| 发起入口 | 群聊窗头部那一排图标里单独加一个接龙按钮，在「文件共享」右边（2026-10-03 起；此前在输入框工具栏「+」左边） | §6.7 |
| 被禁言成员 | 不能发起，也不能参与、修改、撤回；判断规则与发消息相同 | §3.6 |
| 发起人的第一条 | 发起窗口里可选填写，留空就只发卡片 | §3.1 |
| 转发 | 不能单条转发；合并转发时这一条只显示「[接龙] 标题」摘要 | §3.7 |
| 长度上限 | 标题 50 字、说明 200 字、每条接龙 100 字（按字符计，一个汉字算一个） | §4.8 |
| 本地搜索范围 | 只搜标题和说明，接龙条目不进搜索文本 | §6.3 |
| 每张接龙的人数上限 | **200 人**（2026-10-02 1d 开工时发现推送整份名单可能超过客户端 1 MiB 单帧上限后确认）。满员后新人参与回 509，已参与的人修改、撤回不受影响；推送仍发完整名单；判断不加锁，两人同时抢最后一个名额时偶尔多出一两条 | §4.8 |
| 卡片撤回、群解散后的接龙数据 | **保留不删**（2026-10-02 1f 开工时确认），与消息本身的审计保留口径一致；已撤回的卡片下发时不再合并名单与投票结果 | §5.4 |
| 接龙文本中间的换行 | **拒绝**，返回 3（请求非法）；首尾的换行与其它空白一起去掉 | §4.2 |
| 敏感词检查 | **本方案不实现**。参与接龙的文字与卡片里的标题、说明，统一由 `docs/敏感词方案.md` 第 2 期按企业级词库检查（2026-10-02 1a 实施时发现两份方案重叠后确认） | §5.3 |

## 2. 现状盘点（据实证，均已核对代码位置）

本节记的是 2026-10-02 开工前的现状，「约第 N 行」与「当前占到」一类的说法只对当时的代码成立；其中的缺口此后都已按第 7 节处理。

### 2.1 协议已经预留了接龙

- `flamingoserver/chatserversrc/Protocol.h` 已定义 `cmd_join_relay = 1603`、`cmd_relay_changed_notify = 1604`、`message_type_relay = 11`；客户端 `flamingoclient/Source/net/Protocol.h` 与之一致。
- `docs/协议设计-v2.md` 的 §10.4 内容表把接龙卡片的 `content` 定为 `{ "title", "note", "items": [ { "userid", "text" } ] }`；§10.22 描述了 1603 / 1604 的报文与"每人一条接龙，重复参与即更新本人那条"的语义。

### 2.2 服务端已有的实现

- `ChatSession::onJoinRelay` 解析请求、取卡片消息、校验消息类型与会话成员身份，然后调用 `CardManager::upsertInteraction` 写入 `t_card_interaction`，应答 `{code, msg}`，再向全群推送 1604。
- `cmd_sync_messages` 下发卡片消息时调用 `CardProtocol::augmentCardContent`，把当前接龙列表合并进 `content` 的 `items`（`ChatSession.cpp` 约第 2421–2425 行），客户端打开会话即可看到最新列表。
- 会话摘要 `MessageProtocol` 里接龙已有占位「[接龙]」。
- 纯逻辑在 `CardProtocol`，已有 doctest 用例 K1–K9（`flamingoserver/tests/test_cardprotocol.cpp`）。

### 2.3 服务端的缺口

1. **修改本人那条会改变名次**（1a 已修复）。UPSERT 冲突时连 `f_create_time` 一起刷新，而列表按 `f_create_time` 升序排列。
2. **撤回后的卡片仍可参与；参与不检查禁言、不限长度、不过敏感词**。1a 修复了撤回、禁言与长度三项；敏感词一项划归 `docs/敏感词方案.md`，现已实现：参与接龙的文字按提交者所属企业的词库检查（`ChatSession::onJoinRelay`，与本人已提交的相同时不查，命中回 507，拦截来源 4）。
3. **发卡片时不校验 `content`。** 标题可以为空；客户端还可以在 `content` 里自带 `items`，同步时会被 `augmentCardContent` 覆盖，但实时推送 `cmd_message_notify` 会把它原样转发给全群。
4. **标题与说明不过敏感词。** 这一项划归 `docs/敏感词方案.md`，现已实现：`cmd_send_message` 对全部消息类型按 `MessageProtocol::collectSensitiveTexts` 取文字检查（单聊、群聊发送与群发助手都查，命中回 507），接龙卡片取 `content.title` 与 `content.note`，投票卡片取标题与各选项，待办卡片取标题（敏感词方案 §6.3、§6.3.1）。本方案不另做处理。
5. **没有撤回本人那条、截止、提前结束三种能力。**
6. **1604 推送不带 `ctype` / `cid`。** 客户端收到后无法直接定位到对应的群窗口。
7. **没有任何清理。** 全仓读写 `t_card_interaction` 的只有 `CardManager` 和同步时的合并两处，卡片撤回、群解散后这张表里的数据一直留着。

### 2.4 客户端现状

客户端只有命令号与消息类型的枚举，其余全部没有接入：

- 实时收到的接龙卡片被直接丢弃：`BalloonGroupChatWindow.cpp` 约第 3451–3457 行对 `m_text` 为空的非文本消息记一条「暂不渲染」日志后返回。
- 历史消息里，接龙卡片按 `digestForMsgType` 的默认值渲染成一个写着「[消息]」的文字气泡。
- 本地库 `BuildContentJson` 对接龙这类类型只存 `{}`（`V2MsgQuery.cpp` 约第 245 行），原始 JSON 存在 `raw` 列。
- `IUSocket::HandleV2Frame` 没有 1601–1606 的分支，这些帧进入 `default` 只记一条日志（`IUSocket.cpp` 约第 3341 行）。

## 3. 交互设计

### 3.1 发起

- 群聊窗头部点接龙按钮，打开「发起接龙」窗口。它是群聊窗的模态窗口（2026-10-03 起）：以群聊窗为所有者，打开期间群聊窗不可操作，关闭后恢复；一个群聊窗同时只开一个。接龙详情窗同样是打开它的群聊窗的模态窗口。
- 窗口内容：标题（必填，最多 50 字）、说明 / 格式示例（选填，多行，最多 200 字）、截止时间（必填，年月日时分秒六个微调框，见 §3.5）、「我的接龙」（选填，最多 100 字），以及「发起」「取消」两个按钮。
- 点「发起」后，客户端以 `cmd_send_message`（`msgtype = 11`）发出卡片。若「我的接龙」不为空，在收到发送回执、拿到卡片 msgid 之后自动补发一次 `cmd_join_relay`，发起人因此排在第 1 位，群里随即出现一条「参与了接龙」的系统提示。
- 被禁言时，服务端按发消息的规则拒绝（错误码 306），发起窗口提示原因并保持打开，已填写的内容不丢。

### 3.2 卡片

卡片作为一条普通聊天气泡显示在消息列表里，自上而下依次是：

1. 标题，单行，超长以省略号结尾；
2. 说明，最多两行；
3. 前若干条接龙，每行是「序号. 名字　内容」，条数在 3a 步骤里按截图确定；
4. 状态行：「共 N 人参与」，有截止时间时追加「截止 10-03 18:00」，已结束显示「已结束」，已过截止时间显示「已截止」；
5. 底部按钮：未参与时为「参与接龙」，已参与时为「修改我的」；已结束、已截止、本人被禁言时不显示按钮。

点击卡片任意位置打开详情窗；点按钮同样打开详情窗，并把焦点放到本人那条的输入框上。

### 3.3 详情窗

- 每张卡片最多一个详情窗，由主面板按卡片 msgid 管理，推送到达时据此刷新。
- 内容：标题、说明、状态行、完整的接龙列表（`DuiScrollView`，序号按服务端返回顺序编号），底部是本人那条的输入框与「提交」/「修改」按钮、「撤回我的」按钮，以及「复制为文本」按钮。
- 发起人、群主、管理员在接龙进行中时额外看到「结束接龙」按钮，点击后先弹确认。
- 本人被禁言时，输入框与提交按钮置灰，旁边说明「你已被禁言，不能参与接龙」。
- 已结束或已截止时，隐藏底部的输入区域，只保留「复制为文本」。按开发约定文档 UI 约定第 5 条，显隐变化后要对父容器调用 `ForceLayout`。
- 「复制为文本」的格式：

  ```
  接龙：周五团建报名
  格式：姓名+是否带家属
  1. 张三　本人+1
  2. 李四　不带
  （共 2 人，截至 10-02 15:30）
  ```

### 3.4 系统提示

每次参与、修改、撤回本人那条，以及提前结束，服务端都在群里发一条系统提示（`msgtype = 17`），客户端渲染为居中的灰色提示行。系统消息不计未读（沿用现有规则）。

| 操作 | 提示文字 |
| --- | --- |
| 首次参与 | 「张三」参与了接龙「周五团建报名」 |
| 修改本人那条 | 「张三」修改了在接龙「周五团建报名」中的内容 |
| 撤回本人那条 | 「张三」撤回了在接龙「周五团建报名」中的内容 |
| 提前结束 | 「李四」结束了接龙「周五团建报名」，共 12 人参与 |

提示里不带接龙文本本身，避免把超长内容或敏感内容再复制一遍。昵称为空时写成「有成员……」，标题为空（只有旧数据会出现）时省略标题。只有群卡片发提示，单聊卡片不发。提示的 `content` 追加 `cardmsgid` 字段（§4.6），客户端据此让提示行可以点击，点击后打开对应卡片的详情窗；卡片已撤回时点击无反应。

### 3.5 截止与提前结束

- 截止时间必须设置（2026-10-03 起）：在发起窗口里填年、月、日、时、分、秒，初始值为当前时间加 1 小时、秒为 0；不能早于当前时间 + 5 分钟，客户端按本机时间、服务端按它的时间各查一次，服务端不满足时回 510。卡片与详情窗里仍只显示到分钟。此前的预设档位（不限、今天 18:00、明天 18:00、3 天后、7 天后）已删除，之前发出的不限截止时间的卡片照常显示为不限。
- 截止时间写在卡片 `content` 的 `deadline` 里，发出后不能修改。服务端每次处理参与请求时按当前时间判断是否已截止；客户端显示时按本机时间判断，以服务端的拒绝为准。到截止时间不发系统提示，服务端不加定时任务。
- 提前结束写入新表 `t_card_state`（§5.1），结束后不能重新开放。

### 3.6 权限与限制

- 只有卡片所在群的成员能参与、修改、撤回、结束；退群后即失去这些权限，但其已提交的条目保留，名字按通讯录显示。
- 被禁言（个人禁言，或仅通知模式（原称全员禁言）时的普通成员）不能发起，也不能参与、修改、撤回本人那条，判断复用 `checkGroupSpeakAllowed`。结束接龙是管理动作，不受禁言限制。
- 卡片被撤回后，所有交互都返回「卡片不存在」（503）。
- 每人只有一条；修改保持原名次；撤回后再参与，排到列表末尾。
- 已参与的人再次提交一模一样的内容（如双击提交）时直接回成功，不写库、不推送、不发提示（2026-10-02 用户确认）。

### 3.7 转发、引用、复制与摘要

- 右键菜单不显示「转发」。多选后选择「逐条转发」时，接龙卡片被跳过并提示一句；选择「合并转发」时允许，聊天记录里这一条只显示「[接龙] 标题」，不能点开参与。服务端在逐条转发里同样跳过 `msgtype = 11` 的源消息、其余照常转发（与跳过已撤回的源消息同一做法），一条不剩时回 503。
- 允许引用回复，引用摘要为「[接龙] 标题」。
- 右键「复制」与详情窗的「复制为文本」输出同一份文本。
- 所有摘要统一为「[接龙] 标题」：会话列表（服务端 `buildMessageDigest` 一并改）、托盘提醒、消息记录窗、引用、合并转发里的子消息、导出。

## 4. 协议设计

所有改动都是追加字段或追加命令，已有字段的含义不变。

### 4.1 卡片 `content`（`msgtype = 11`）

客户端发送：

```json
{ "title": "周五团建报名", "note": "格式：姓名+是否带家属", "deadline": 1759485600000 }
```

- `title`：必填，去掉首尾空白后不能为空，中间不能含回车或换行（2026-10-02 用户确认：拒绝），最多 50 字。
- `note`：选填，最多 200 字。
- `deadline`：截止时间，Unix 毫秒，必填，不能早于服务端当前时间 + 5 分钟（`RELAY_DEADLINE_MIN_LEAD_MS`），否则回 510 `error_code_relay_deadline_invalid`（2026-10-03 起；此前 0 或缺省表示不限，只要求晚于当前时间）。

服务端只保存这三个字段，客户端自带的其它字段一律丢弃。下发时（同步与实时推送）合并当前状态：

```json
{
  "title": "周五团建报名", "note": "格式：姓名+是否带家属", "deadline": 1759485600000,
  "items": [ { "userid": "100008", "text": "本人+1" } ],
  "state": 0, "closedby": "0", "closetime": 0
}
```

`state` 取值新增枚举 `relay_state`：

| 值 | 含义 |
| ---: | --- |
| 0 | 进行中 |
| 1 | 已被提前结束，`closedby` / `closetime` 记录操作者与时间 |
| 2 | 已过截止时间（由服务端在下发时按当前时间算出，不落库） |

### 4.2 `cmd_join_relay`（1603，变更）

请求不变：`{ "ctype": 2, "cid": "600001", "msgid": "9007199254741011", "text": "本人+1" }`。

- `text` 先去掉首尾空白（半角空格、制表符、回车、换行、全角空格），去完后不能为空，中间不能含回车或换行（2026-10-02 用户确认：拒绝而不是替换），最多 100 字。
- 应答追加 `ctype` / `cid` / `msgid`，使客户端不必按 seq 对应请求：`{ "code": 0, "msg": "ok", "ctype": 2, "cid": "600001", "msgid": "9007199254741011" }`。
- 本人已有一条时为修改，保持原名次；没有时为首次参与，排到末尾。

### 4.3 `cmd_withdraw_relay`（1607，新增）

撤回本人那条。请求 `{ "ctype": 2, "cid": "600001", "msgid": "..." }`，应答格式同 1603。本人没有参与时直接返回成功，不推送、不发提示。

### 4.4 `cmd_close_relay`（1608，新增）

提前结束接龙。请求与应答格式同 1607。只有发起人、群主、管理员可以操作，其他人返回 6（无权限）。已结束或已截止时返回 508。

### 4.5 `cmd_relay_changed_notify`（1604，追加字段）

```json
{ "ctype": 2, "cid": "600001", "msgid": "9007199254741011",
  "items": [ { "userid": "100008", "text": "本人+1" } ],
  "state": 0, "closedby": "0", "closetime": 0 }
```

参与、修改、撤回、提前结束之后都推送这一帧，推送对象为全体群成员，操作者本人也会收到。

### 4.6 系统提示 `content` 追加 `cardmsgid`

```json
{ "text": "「张三」参与了接龙「周五团建报名」", "cardmsgid": "9007199254741011" }
```

不认识这个字段的客户端照常把它当文本提示显示。

### 4.7 错误码

| 情况 | 错误码 |
| --- | --- |
| 接龙已被提前结束或已过截止时间 | **508 `error_code_card_closed`（新增，消息段）** |
| 卡片不存在或已撤回 | 503 `error_code_message_not_exist` |
| 标题、说明、接龙文本超出长度上限 | 505 `error_code_msg_too_large` |
| 标题或接龙文本为空、接龙文本中间含换行 | 3 `error_code_bad_request` |
| 截止时间没有设置，或早于服务端当前时间 + 5 分钟（2026-10-03 起） | 510 `error_code_relay_deadline_invalid` |
| 被禁言 | 306 `error_code_member_muted` |
| 命中敏感词（由敏感词方案在 1503 / 1603 里返回，本方案不实现） | 507 `error_code_sensitive_word` |
| 接龙人数已满（新人参与） | **509 `error_code_card_full`（新增，消息段）** |
| 结束接龙但不是发起人、群主或管理员 | 6 `error_code_permission_denied` |

### 4.8 长度上限

服务端与客户端各定义一组同值常量，单位是 Unicode 字符数（UTF-8 按码点计数）：

| 常量 | 取值 |
| --- | ---: |
| `RELAY_TITLE_MAX_CHARS` | 50 |
| `RELAY_NOTE_MAX_CHARS` | 200 |
| `RELAY_TEXT_MAX_CHARS` | 100 |

100 个汉字按 UTF-8 最多 300 字节，远小于 `t_card_interaction.f_data` 的 `varchar(1024)`。客户端在输入框上就限制长度，服务端再校验一次。

## 5. 服务端

### 5.1 数据库

- **修名次问题**：`CardManager::upsertInteraction` 冲突时只更新 `f_data`，保留首次参与的 `f_create_time`。投票、待办共用这个函数，二者都不依赖这个时间的刷新（投票只统计票数；待办取消勾选走 `removeInteraction`，重新勾选是新插入的一行）。
- **新建 `t_card_state`**：一行表示一张卡片的结束状态，投票以后要支持提前结束也可以复用。

  | 列 | 类型 | 含义 |
  | --- | --- | --- |
  | `f_msgid` | bigint，主键 | 卡片所在消息 id |
  | `f_closed` | int | 1 表示已被提前结束 |
  | `f_closer` | bigint | 操作者 userid |
  | `f_close_time` | bigint | 结束时间，Unix 毫秒 |

- 改 `table_mysql.sql` 后运行 `tools/gen_table_sqlite.py` 重新生成 `table_sqlite.sql` 与 `sqliteapi/SqliteSchema.cpp`，不手改生成结果。

### 5.2 `CardProtocol` 扩展（纯逻辑，进 doctest）

- `normalizeRelayContent`：校验并规范化发卡片时的 `content`，返回错误码。
- `parseRelayTargetRequest`：解析 1607 / 1608 共用的 `{ctype, cid, msgid}`。
- `parseJoinRelayRequest` 增加长度与空白校验。
- `buildRelayChangedNotify` 增加 `ctype` / `cid` / `state` / `closedby` / `closetime`。
- `buildRelayOpResponse`：带 `ctype` / `cid` / `msgid` 的应答。
- `augmentCardContent` 对接龙额外合并 `state` 等字段，需要传入结束状态与当前时间。
- `buildRelayTip`：按操作类型生成 §3.4 的提示文字。
- `utf8CharCount`：按码点计数，若 `utils/StringUtil` 里已有同类函数则直接复用。

### 5.3 `ChatSession`

- `onSendMessage` 的群聊分支：`msgtype = 11` 时调用 `normalizeRelayContent`，存规范化之后的 `content`。标题与说明的敏感词检查由敏感词方案在同一分支里统一加上。
- `onJoinRelay`：补撤回检查、禁言检查（`checkGroupSpeakAllowed`）、截止与结束检查；区分首次参与与修改，以便生成对应的提示。接龙文字的敏感词检查由敏感词方案加在这个函数里（其 §6.3「参与接龙」检查点）。
- 新增 `onWithdrawRelay`、`onCloseRelay`。
- `sendGroupSystemMessage` 增加一个可选参数 `cardMsgId`，非 0 时把它写进 `content`。
- 逐条转发（`cmd_forward_message`，merge=0）跳过 `msgtype = 11` 的源消息（`CardProtocol::canForwardSeparately`），全部被跳过时回 503。
- `buildMessageDigest` 对接龙返回「[接龙] 标题」。
- 投票、待办的处理函数一并补上撤回检查（1a 已完成）。

### 5.4 清理

卡片撤回、群解散后 `t_card_interaction` 与 `t_card_state` 里的数据**保留不删**（2026-10-02 1f 开工时用户确认）：服务端从不物理删除 `t_chatmsg` 的消息，撤回只置 `f_recalled`，解散群也保留群消息供企业审计追溯；接龙名单是用户写的内容，按同一口径保留。Pin 之所以清理，是因为它只是展示状态。

保留下来的数据不会再被操作到：撤回的卡片在 `checkCardTarget` 处被拒，解散后原成员不再是群成员、在 `canAccessCard` 处被拒；每张最多 200 行，体量有限。下发时已撤回的卡片不再合并名单与投票结果（`CardProtocol::shouldAugmentCard`），省掉查库，也不把名单随撤回的卡片发出去。

核对过程中还发现一个与接龙无关的既有问题：撤回的消息原文仍会随同步、Pin 列表、搜索下发，已记为 `bugs.md` BUG-58。

### 5.5 关键路径日志

发卡片被拒（原因）、参与 / 修改 / 撤回 / 结束成功与被拒（原因、msgid、userid），全部用英文 `LOGI` / `LOGE` 输出。

### 1a 实施记录（2026-10-02）

- **名次**：`CardManager::upsertInteraction` 冲突时只覆盖 `f_data`；`getCardInteractions` 的排序补上 `f_id ASC`，同一毫秒参与的两人读回的先后固定。KM1 在修复前失败（读回顺序为 A、C、B，B 的时间被刷新），修复后通过。

### 1b 实施记录（2026-10-02）

- **规范化**：`CardProtocol::normalizeRelayContent(content, nowMs, out)` 只输出 `title`、`note`、`deadline` 三个字段；去首尾空白的逻辑从 `normalizeRelayText` 抽成文件内的 `trimRelayBlank`，三处共用。截止时间只接受 JSON 整数，超出 int64 范围的无符号整数也拒绝，避免 jsoncpp 的 `asInt64` 抛异常。
