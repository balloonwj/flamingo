## 1. 背景与目标

群管理窗口（`flamingoclient/Source/UI/BalloonGroupManage/`）的界面已按 `design/群管理1.png ~ 7.png` 画完，但数据全部是本地假数据。与此同时服务端已经实现了完整的群组能力，客户端只用上了其中一小部分。本方案要做的是把两边接通。

接通过程中发现界面设计稿比服务端能力宽——有一批控件在数据库里根本没有对应字段。经与用户确认，**这些缺口由扩服务端补齐**，而不是把控件藏掉。因此本方案同时覆盖服务端的数据、协议与行为扩展。

最终形态：群管理窗口六个页面全部使用真实数据，群主与管理员能在其中完成成员管理、加群审批、禁言管理、群资料修改、群权限设置与解散转让，且任何一端的改动都能通过推送实时反映到其它端。

## 2. 现状盘点（据实证，均已核对代码位置）

### 2.1 服务端 20 条群协议全部实现，客户端只接了 6 条

`chatserversrc/Protocol.h` 定义了 `cmd_create_group`(1301) 到 `cmd_get_user_groups`(1320) 共 20 条群组协议，`ChatSession.cpp` 全部登记了分发入口并有完整实现。

客户端 `net/IUSocket.cpp` 里只出现了 6 条：1301 建群、1303 群资料、1304 群成员、1309 退群、1315 改本人群名片、1320 我的群列表。

**没接的 14 条**：1302 解散群、1305 邀请入群、1306 申请加群、1307 加群申请推送、1308 审批加群、1310 移出成员、1311 改群资料、1312 设管理员、1313 禁言成员、1314 仅通知模式（原称全员禁言）、1316 转让群主、1317 成员变动推送、1318 群资料变更推送、1319 待审批列表。

### 2.2 群管理窗口是纯假数据

`BalloonGroupManageWindow.cpp` 直接调 `FillMockData(m_model)`；`BalloonGroupManageWindow.h` 的注释写明"本轮只做群主全功能视图、数据为本地假数据，接入 v2 群管理协议与管理员受限视图留待后续"。

界面骨架是齐的：`GroupManageLayout.h` 定义了 6 个页面 id、4 个输入框 id、19 个按钮/开关/下拉 id 以及 4 组逐行按钮的 id 基址。

### 2.3 成员卡片没有任何操作入口

`GroupManageLayout.cpp` 的成员卡是"头像 + 昵称/职务 + 角色徽章"，既没有按钮也没有右键处理。移出成员、设管理员、禁言这三个操作虽然协议齐备，界面上却无处可点。

### 2.4 服务端缺失的字段

`table_mysql.sql:392-416` 的 `t_group` 只有 groupid / name / facetype / customface / announcement / ownerid / join_mode / mute_all / create_time 九列；`t_group_member` 只有 groupid / userid / role / card / muted / join_time 六列。

界面上以下内容在服务端**无对应字段**：

| 界面元素 | 所在页 | 现状 |
| --- | --- | --- |
| 群简介 | 基本信息 | `t_group` 无此列 |
| 谁能 @ 全体成员 | 群权限 | 无 |
| 新成员查看历史消息 | 群权限 | 无 |
| 成员邀请好友加群 | 群权限 | 无 |
| 入群欢迎语 | 群权限 | 无 |
| 禁言原因 | 禁言管理 | `t_group_member` 无此列 |

`UpdateGroupInfoRequest`（`GroupProtocol.h`）只支持 name / facetype / customface / announcement / joinmode / muteall 六项。

## 3. 数据库设计

### 3.1 `t_group` 新增六列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_intro` | `varchar(512)` | `''` | 群简介 |
| `f_at_all_scope` | `int(2)` | `0` | 谁能 @ 全体：0 仅群主和管理员，1 所有人 |
| `f_new_see_history` | `int(2)` | `1` | 新成员可否查看入群前的历史消息：0 否 1 是 |
| `f_member_invite` | `int(2)` | `0` | 普通成员邀请好友是否免审批：0 否（转为待审批申请）1 是（直接入群） |
| `f_welcome_on` | `int(2)` | `0` | 入群欢迎语开关 |
| `f_welcome_text` | `varchar(256)` | `''` | 入群欢迎语正文 |

### 3.2 `t_group_member` 新增两列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_mute_until` | `bigint(20)` | `0` | 禁言到期时间（Unix 毫秒）。`f_muted=1` 且本列为 0 表示**永久禁言** |
| `f_mute_reason` | `varchar(128)` | `''` | 禁言原因 |

**为什么不把 `f_muted` 直接换成 `f_mute_until`**：保留 `f_muted` 作为"是否处于禁言态"的标志、`f_mute_until` 作为到期时间。老库加列后已有行的 `f_mute_until` 取默认值 0，而 0 的语义正是"永久禁言"——与升级前 `f_muted=1` 的表现完全一致，老数据零迁移。若改成单列表达，老数据就得写脚本迁移。

**到期处理采用惰性判断，不引定时任务**：读取成员禁言态时用 `now` 与 `f_mute_until` 比对得出实际状态；发言校验时若发现已过期，顺手把 `f_muted` 置 0 并推一条成员变动通知。定时任务会引入一个新的后台线程与它自己的一整套问题（漏跑、重复跑、与请求并发写同一行），而惰性判断在本场景下没有任何功能损失——没人读到的过期禁言，过不过期都不影响任何行为。

### 3.3 `t_group_join_request` 新增两列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_source` | `int(2)` | `1` | 申请来源：0 好友邀请 1 群搜索 2 扫码加群 |
| `f_recommender` | `bigint(20)` | `0` | 推荐人 userid，0 表示无 |

取值与客户端 `GroupManageModel.h:54-59` 的 `JoinSource` 枚举对齐。

## 4. 协议设计

### 4.1 扩展既有报文

**`GroupRecord`** 增加 `intro` / `atallscope` / `newseehistory` / `memberinvite` / `welcomeon` / `welcometext` 六个字段，随之影响 `buildGroupInfoResponse`、`buildUserGroupsResponse`、`buildGroupInfoChangedNotify` 三个构造器的输出。

**`UpdateGroupInfoRequest`** 按既有 `has_*` 模式增加同名的六组可选项。

**`GroupMemberRecord`** 增加 `muteuntil` / `mutereason`，随之影响 `buildGroupMembersResponse`。

**`GroupJoinRequestRecord`** 增加 `source` / `recommender`，随之影响 `buildGetJoinRequestsResponse` 与 `buildJoinGroupRequestNotify`。

**`cmd_mute_member` 请求**从 `{groupid, userid, muted}` 扩为 `{groupid, userid, muted, duration, reason}`：

- `duration`：禁言时长，单位**秒**，可选，缺省 0。`muted=1` 且 `duration=0` 表示永久禁言；`duration>0` 时服务端算出 `f_mute_until = now + duration*1000`。
- `reason`：禁言原因，可选，缺省空串。
- `muted=0`（解禁）时忽略这两个字段，并把 `f_mute_until` 与 `f_mute_reason` 一并清空。

由于两个新字段都是可选的，老客户端发来的三字段请求仍然合法，解析出 `duration=0` 即永久禁言，与扩展前行为一致。

### 4.3 新增错误码

`error_code` 目前群组段用到 306，往后取：

| 值 | 名称 | 含义 |
| --- | --- | --- |
| 307 | `error_code_cannot_operate_owner` | 不能对群主执行该操作（踢/禁言/降级） |
| 507 | `error_code_sensitive_word` | 消息内容包含敏感词，已拒绝发送（2026-10-02 起由企业级词库判定，见 `docs/敏感词方案.md`） |
| 309 | `error_code_at_all_denied` | 无权 @ 全体成员 |

`error_code_sensitive_word` 原先取 308，与 `error_code_join_req_not_exist` 撞号，且它的语义是"一次发消息被拒绝"、本就该归消息段，2026-08-16 改为 **507**。号段规约见 `docs/协议设计-v2.md` 第 8.1 节。

### 4.4 权限矩阵

服务端对每个操作的角色校验（客户端据同一张表做界面门控，两边必须一致；**服务端校验是权威，客户端门控只是不让用户白点**）：

| 操作 | 群主 | 管理员 | 成员 | 附加约束 |
| --- | --- | --- | --- | --- |
| 改群资料 / 权限（1311） | ✓ | ✓ | ✗ | |
| 邀请入群（1305） | ✓ | ✓ | 视 `f_member_invite` | 关闭时成员的邀请转为待审批申请 |
| 移出成员（1310） | ✓ | ✓ | ✗ | 管理员不能移出管理员；任何人不能移出群主 |
| 设 / 撤管理员（1312） | ✓ | ✗ | ✗ | |
| 禁言 / 解禁（1313） | ✓ | ✓ | ✗ | 管理员不能禁言管理员；任何人不能禁言群主 |
| 仅通知模式（1314） | ✓ | ✓ | ✗ | 仅通知模式期间管理员及以上仍可发言 |
| 审批加群（1308、1319） | ✓ | ✓ | ✗ | |
| 转让群主（1316） | ✓ | ✗ | ✗ | 目标须为本群成员且不是自己 |
| 解散群（1302） | ✓ | ✗ | ✗ | |

## 5. 服务端行为

### 5.1 禁言校验改为按到期时间判断

`ChatSession::sendGroupMessage` 现在的判断是：

```cpp
if (mymuted != 0 || (group.muteall != 0 && myrole < group_role_admin))
```

改造为：先取回 `f_muted` 与 `f_mute_until`，若 `f_muted != 0` 且 `f_mute_until != 0` 且 `f_mute_until <= now`，视为已到期——把 `f_muted` 置 0、清空 `f_mute_until` 与 `f_mute_reason`、推一条 `cmd_group_member_changed_notify`（changetype 为成员禁言状态变更），然后按未禁言放行。

同一套"取实际禁言态"的逻辑在 `cmd_get_group_members` 组装应答时也要用到（否则界面会把已过期的禁言仍显示为禁言中），故抽成 `GroupManager` 的一个方法，两处共用。

### 5.3 @全体权限校验

`sendGroupMessage` 中若 `req.mentionall` 为真、且 `f_at_all_scope == 0`、且发送者 `myrole < group_role_admin`，以 `error_code_at_all_denied` 拒绝。

### 5.4 入群欢迎语

成员成功加入后（`cmd_invite_to_group`、`cmd_join_group_request` 直接入群、`cmd_handle_join_group` 审批通过，共三处入口），若群 `f_welcome_on` 为真且 `f_welcome_text` 非空，以 `message_type_system` 生成一条群消息落库并推送。发送者 userid 取 0 表示系统。

三处入口共用一个 `sendGroupWelcomeMessage(groupid, newMemberIds)` 私有方法，避免抄三遍。

### 5.5 新成员查看历史消息

群 `f_new_see_history` 为 0 时，成员拉取群历史消息要以其 `f_join_time` 为下界过滤。落点在群历史查询处（开工时定位 `MessageManager` 里对应的群历史 SQL），加一个"该成员入群时间"的时间下界条件。

### 5.6 成员邀请好友加群

`onInviteToGroup` 现在只校验"邀请人须为群成员"。改为：邀请人是群主或管理员则直接拉人；是普通成员时，若 `f_member_invite` 为 1 直接拉人，为 0 则把每个被邀请人转写成一条 `t_group_join_request`（`f_source` 记为好友邀请、`f_recommender` 记为邀请人），并推 `cmd_join_group_request_notify` 给群主与管理员。

## 6. 客户端数据流

```
打开群管理窗口
  └─ SetGroupContext(groupid, ...)  → CreateAndShow
       └─ 并发拉三份数据
            1303 cmd_get_group_info          → 群资料 + 本人角色
            1304 cmd_get_group_members       → 成员列表（含禁言态与到期时间）
            1319 cmd_get_group_join_requests → 待审批申请（仅群主/管理员拉）
       └─ 三份应答各自到达时写入 GroupManageModel，重建当前页

用户操作
  └─ 发对应请求（1302/1305/1308/1310/1311/1312/1313/1314/1316）
       └─ 应答 code != 0 → 弹提示，界面回退到操作前状态
       └─ 应答 code == 0 → 不直接改界面，等 1317/1318 推送统一刷新
                            （本端也会收到自己触发的推送）

推送到达
  ├─ 1317 cmd_group_member_changed_notify → 按 changetype 增/删/改成员，重建成员页与禁言页
  └─ 1318 cmd_group_info_changed_notify   → 改群资料，刷新 Header、基本信息页、群权限页
                                            changetype=2（已解散）→ 关窗并提示
```

**为什么成功应答不直接改界面**：服务端在每次成功的写操作后都会向全体成员推送变更，本端也在推送范围内。若应答与推送各改一次，同一次操作会重排两遍界面；且推送里带的是服务端的权威结果，比客户端自己猜的更准。**唯一的例外是需要立刻给用户反馈的失败路径**——失败没有推送，只能靠应答。

## 7. 界面与交互

### 7.1 成员卡右键菜单

在成员卡上右键弹出，落点经 `ClampPopupMenuToWorkArea` 夹取。菜单项：

```
发消息
查看资料
────────────
设为管理员 / 撤销管理员
禁言 / 解除禁言
────────────
移出本群
```

可用项按**登录者角色 × 目标成员角色**计算，与 §4.4 的权限矩阵一致。这段判定抽成纯函数 `BuildMemberMenuModel(myRole, targetRole, targetMuted, isSelf)` 单独测试——角色门控是最容易写错、又最难靠手点覆盖全的地方。

对自己右键时只显示"查看资料"（不能给自己发消息、也不能自己禁言自己）。

### 7.2 禁言时长的输入

点"禁言"后需要选时长。用一个小的二级菜单（10 分钟 / 1 小时 / 12 小时 / 1 天 / 永久）而不是弹对话框——禁言是个高频轻操作，弹窗太重。禁言原因本轮不在右键流程里填，留给禁言管理页的"添加禁言成员"走完整对话框。

### 7.3 选人对话框

从 `CreateGroupDlg` 抽出共用组件，三处复用：

| 调用处 | 候选来源 | 选择语义 |
| --- | --- | --- |
| 邀请成员（1305） | 通讯录（企业组织架构），**排除已在群内的** | 多选 |
| 添加禁言成员（1313） | 本群成员，**排除群主与自己** | 多选，另需时长与原因 |
| 转让群主（1316） | 本群成员，**排除自己** | 单选 |

组件需支持配置候选来源、排除集合、单选/多选，以及底部附加区（禁言那处要放时长与原因）。

### 7.4 角色门控

本人是普通成员时不应该能打开群管理窗口的多数页面。按角色决定左侧导航显示哪些项：

| 页面 | 群主 | 管理员 | 成员 |
| --- | --- | --- | --- |
| 成员管理 | ✓ | ✓ | ✓（只读，无右键管理项） |
| 加群审批 | ✓ | ✓ | ✗ |
| 禁言管理 | ✓ | ✓ | ✗ |
| 基本信息 | ✓ | ✓ | ✓（只读） |
| 群权限 | ✓ | ✓ | ✗ |
| 危险区域 | ✓ | ✗ | ✗ |

## 8. 分期

**第一期（服务端）**：数据层加列、协议层扩字段与新报文、五项新行为。做完后服务端能力完整，用现有测试与手工请求即可验证，不依赖客户端。

**第二期（客户端读）**：协议层接通、群管理窗口各页改用真实数据、按角色门控。做完后窗口能正确显示一个真实群的全部信息，但还不能改。

**第三期（客户端写）**：成员卡右键菜单、各页按钮接线、选人对话框、1317/1318 推送刷新。做完后闭环。

分期的依据是**每期结束时都有一个可验证的完整状态**，而不是按文件切。

## 13. 补做：群权限五项接线（2026-08-01）

### 13.1 群权限页五项接线

下表的控件（两个下拉与三个开关）现在拨动即生效，各自独立发一条 `cmd_update_group_info`。

**为什么逐项发、而不是攒一个"保存"按钮**：这一页设计上就没有保存按钮，交互预期是拨完立刻生效。逐项发还顺带避免了多端同时编辑时的互相覆盖 —— 请求里只带改动的那一项，别人刚改的其它项不会被本端的旧值盖掉。

映射关系（下拉项下标与服务端枚举同序，故直接透传）：

| 控件 | 协议字段 | 取值 |
| --- | --- | --- |
| 加群方式 | `joinmode` | 0 自由 / 1 需审批 / 2 禁止 |
| 谁能 @ 全体成员 | `atallscope` | 0 仅群主和管理员 / 1 所有人 |
| 新成员查看历史消息 | `newseehistory` | 0 / 1 |
| 成员邀请好友加群 | `memberinvite` | 0 / 1 |
| 入群欢迎语 | `welcomeon` | 0 / 1 |

**一处刻意的额外行为**：开启"入群欢迎语"时若正文还是空的，请求里会顺带带一句默认欢迎语。服务端那边"开关开着但正文为空"等于不发，用户拨了开关却什么都没发生，会以为功能坏了。正文的编辑入口尚未提供，见 §12 第 4 条。

### 13.3 验证

- 界面行为一如既往**未经实机验证**。

## 14. 「全员禁言」改名为「仅通知模式」（2026-10-06 起草）

12 项新功能的第一批之一（同批另见 `docs/撤回后重新编辑方案.md`、`docs/快捷回复方案.md`、`docs/备忘与提醒方案.md` §8）。功能本身不变：开启后只有群主和管理员能发言（`GroupPermission.h:145-156`）。本节把它在所有用户可见处改叫「仅通知模式」，并补上普通成员一侧原本缺失的提示。

### 14.1 已定事项

| 事项 | 结论 | 来源 |
| --- | --- | --- |
| 名称 | 「全员禁言」统一改叫「仅通知模式」；协议字段 `muteall`、表列 `f_muteall`、代码标识符都不改 | 用户确认 |
| 说明 | 群管理窗的开关单独成一行：标题「仅通知模式」，下方灰字「开启后，仅群主和管理员可以发言，其他成员只能查看消息」，标题另挂 tooltip 写同样的说明 | 用户确认（文字或 tooltip） |
| 普通成员的群聊窗 | 开启期间，输入框与工具栏换成一行灰字「本群为仅通知模式，仅群主和管理员可以发言」，开关变化时实时切换；群主、管理员不受影响；本人角色未取到时按可以发言处理，以服务端判断为准 | 用户确认 |
| 群里的系统提示 | 开启、关闭时服务端在群里写一条系统提示，全体成员可见：「张三 开启了仅通知模式，仅群主和管理员可以发言」「张三 关闭了仅通知模式」 | 用户确认 |

| 发送被拒的提示 | 服务端仍回 306（与单人禁言共用）。客户端已知本群开启了仅通知模式、且本人是普通成员时，提示改为「本群为仅通知模式，仅群主和管理员可以发言」，否则仍为「你已被禁言，消息未能发出」；顺带修正发文件被拒时只显示「文件发送失败（错误码 306）」的问题 | 默认 |

### 14.2 现状（据实证）

- **客户端界面上只有一处**：群管理窗禁言页标题行右侧的开关标签 `TR(L"全员禁言")`（`flamingoclient/Source/UI/BalloonGroupManage/GroupManageLayout.cpp`），标签宽固定 72 像素，开关是 `DuiSwitch`，id `kIdSwitchMuteAll = 2121`（`GroupManageLayout.h:80`）。「仅通知模式」五个字约 70 像素，英文译文放不下，所以要改成单独一行。同文件已有「标题 + 灰色说明 + 开关」的行写法（`MakePermRow`）。群管理窗还没有用过 tooltip，写法参照 `BalloonGroupChatWindow.cpp`。
- **没有系统提示**：服务端 `onMuteAll`（`flamingoserver/chatserversrc/ChatSession.cpp`）只回应答并推 1318 群资料变更，客户端收到成功应答后不做任何事（`GroupManageWindowData.cpp`）。群系统提示已有结构化字段 `tipkind` / `tipargs`（`Protocol.h`），老客户端显示服务端拼好的 `text`。
- **群聊窗不知道开关状态**：群聊窗不记录 `muteall`（`BalloonGroupChatWindow.cpp`），但群资料应答与 1318 推送里都带有 `muteall`（客户端 `net/GroupProtocolClient.h`）。
- **主面板的群列表**：服务端 1320 应答其实已经带 `muteall`（群资料、1320、1318 三处共用 `fillGroupValue`，`flamingoserver/chatserversrc/GroupProtocol.cpp`），只是客户端的 `UserGroupItem`（`net/GroupProtocolClient.h`）没有解析这个字段。
- **发送被拒**：单人禁言与全员禁言都回 306（`ChatSession.cpp`），客户端提示在 `ChatSendLimit.cpp`、`ForwardDispatcher.cpp`、`ChatRelayCard.cpp`、`RelayDetailModel.cpp`、`RelayComposeModel.cpp`；文件发送的提示函数不处理 306（`ChatSendLimit.cpp`）。
- **翻译**：四个 `.po` 里 `msgid "全员禁言"` 已有译文；改原文后旧条目会作为 `#~` 作废条目保留，新原文的四种译文要手工补（`tools/i18n_extract.py`）。
- **flamingoAdmin** 里没有「全员禁言」字样，不用改。

### 14.3 设计

**服务端**

- `Protocol.h` 新增两种系统提示：`kSystemTipMuteAllOn = "muteall_on"`、`kSystemTipMuteAllOff = "muteall_off"`，参数 `{ operator: 操作人昵称, operatorid: 操作人 userid }`，昵称取不到时不写 `operator`；客户端据 `operatorid` 判断操作人是不是本人，是本人时写「你开启了……」。`text` 写好中文供老客户端显示。
- `onMuteAll` 在状态真正发生变化（0 变 1 或 1 变 0）后写这条系统提示；重复设置同一个值不写。
- 协议文档补上两种提示。1320 应答本来就带 `muteall`，服务端不用改。

**客户端**

- 群管理窗：禁言页把开关从标题行挪成独立一行（标题、灰色说明、开关），标题挂 tooltip。
- 系统提示：按 `tipkind` 用 `TRF8` 模板生成文字，与 `member_join` 等同一处处理。
- 群聊窗：记录群资料里的 `muteall`，打开窗口时与收到 1318 推送时更新；本人是普通成员且开关为开时，隐藏输入框与工具栏，显示灰字提示行；切换后按开发约定文档 UI 约定 5 对父容器 `ForceLayout`。判断规则放进纯函数（输入 `muteall` 与本人角色，输出是否可以发言），便于单测。
- 发送被拒的提示：`SendFailureText` 增加「本群是否为仅通知模式」参数，文件发送的提示也处理 306。
- 主面板：解析 1320 的 `muteall` 并存进群条目，收到 1318 时更新；「群聊」列表与会话列表的群名后画灰色小标签「仅通知」，悬停提示说明。
- 翻译：运行 `i18n_extract.py`，四种语言补译文（英文 Notice-only mode、日文 お知らせ専用モード、韩文 공지 전용 모드、繁体 僅通知模式，界面上的短标签另译）。
