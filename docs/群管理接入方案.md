# 群管理接入方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-07-31
> 用途：记录把 `flamingoclient` 的群管理窗口从假数据接到真实协议、并补齐服务端缺失能力的整体方案、分期路线与开发步骤。后续每步开工前据此细化、收尾后回填实际结果。

---

## 1. 背景与目标

群管理窗口（`flamingoclient/Source/BalloonGroupManage/`）的界面已按 `design/群管理1.png ~ 7.png` 画完，但数据全部是本地假数据。与此同时服务端已经实现了完整的群组能力，客户端只用上了其中一小部分。本方案要做的是把两边接通。

接通过程中发现界面设计稿比服务端能力宽——有一批控件在数据库里根本没有对应字段。经与用户确认，**这些缺口由扩服务端补齐**，而不是把控件藏掉。因此本方案同时覆盖服务端的数据、协议与行为扩展。

最终形态：群管理窗口六个页面全部使用真实数据，群主与管理员能在其中完成成员管理、加群审批、禁言管理、群资料修改、群权限设置与解散转让，且任何一端的改动都能通过推送实时反映到其它端。

### 2.5 已经具备的基础

- **系统提示消息类型已存在**：`Protocol.h:369` 的 `message_type_system = 17`，注释即写"入群欢迎、撤回提示等，服务器生成"。入群欢迎语有现成载体。
- **@全体的字段已在收发链路里**：`ChatSession::sendGroupMessage` 收到的 `SendMessageRequest` 已带 `mentions` / `mentionall`（见 `MessageProtocol::buildStoredContent` 调用处），加权限校验有落点。
- **禁言校验只有一处**：`ChatSession.cpp:1770-1776`，改造干净。
- **数据库能自动加列**：`CMysqlManager::_CheckTable` 会对已登记但表里没有的列执行 `alter table X add column`。拼进 ALTER 的是 `STableField` 的**第二个**字段 `m_strType`（`MysqlManager.cpp:722-723`），也就是那一整串完整定义，**带 NOT NULL 与 DEFAULT**，MySQL 会用默认值填满已有行 —— 老库升级后每行都拿到与新建时一致的初值，读取处无需 `IFNULL` 兜底。
  > 起草本方案时这一条我写反了（以为 ALTER 只用裸类型、补出来的列可为 NULL），`MysqlManager.cpp` 里 `f_deleted_msgid` 旁边那条注释也是按错误前提写的，已一并改正。`MessageManager` 读 `f_deleted_msgid` 时套的 `IFNULL(...,-1)` 因此是多余的 —— 不影响正确性，只是那条兜底分支永远走不到。
- **选人 UI 有现成的**：`BalloonMain/CreateGroupDlg` 已有一套"左侧可勾选成员列表 + 右侧已选 chip 区 + 底部计数"，可抽成共用组件。
- **菜单夹取有现成的**：`BalloonMain/PopupMenuPlacement.h` 的 `ClampPopupMenuToWorkArea`，按开发约定文档的约定所有弹出菜单必须走它。

## 3. 数据库设计

### 3.1 `t_group` 新增七列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_intro` | `varchar(512)` | `''` | 群简介 |
| `f_at_all_scope` | `int(2)` | `0` | 谁能 @ 全体：0 仅群主和管理员，1 所有人 |
| `f_new_see_history` | `int(2)` | `1` | 新成员可否查看入群前的历史消息：0 否 1 是 |
| `f_member_invite` | `int(2)` | `0` | 普通成员邀请好友是否免审批：0 否（转为待审批申请）1 是（直接入群） |
| `f_welcome_on` | `int(2)` | `0` | 入群欢迎语开关 |
| `f_welcome_text` | `varchar(256)` | `''` | 入群欢迎语正文 |
| `f_sensitive_on` | `int(2)` | `0` | 消息敏感词过滤开关 |

### 3.2 `t_group_member` 新增两列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_mute_until` | `bigint(20)` | `0` | 禁言到期时间（Unix 毫秒）。`f_muted=1` 且本列为 0 表示**永久禁言** |
| `f_mute_reason` | `varchar(128)` | `''` | 禁言原因 |

**为什么不把 `f_muted` 直接换成 `f_mute_until`**：保留 `f_muted` 作为"是否处于禁言态"的标志、`f_mute_until` 作为到期时间。老库自动加列后 `f_mute_until` 被默认值填成 0，而 0 的语义正是"永久禁言"——与升级前 `f_muted=1` 的表现完全一致，老数据零迁移。若改成单列表达，老数据就得写脚本迁移。

**到期处理采用惰性判断，不引定时任务**：读取成员禁言态时用 `now` 与 `f_mute_until` 比对得出实际状态；发言校验时若发现已过期，顺手把 `f_muted` 置 0 并推一条成员变动通知。定时任务会引入一个新的后台线程与它自己的一整套问题（漏跑、重复跑、与请求并发写同一行），而惰性判断在本场景下没有任何功能损失——没人读到的过期禁言，过不过期都不影响任何行为。

### 3.3 `t_group_join_request` 新增两列

| 列名 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `f_source` | `int(2)` | `1` | 申请来源：0 好友邀请 1 群搜索 2 扫码加群 |
| `f_recommender` | `bigint(20)` | `0` | 推荐人 userid，0 表示无 |

取值与客户端 `GroupManageModel.h:50-55` 的 `JoinSource` 枚举对齐。

### 3.4 新建 `t_group_sensitive_word`

```sql
CREATE TABLE IF NOT EXISTS t_group_sensitive_word (
    f_id          bigint(20)  NOT NULL AUTO_INCREMENT COMMENT '词条ID',
    f_groupid     bigint(20)  NOT NULL COMMENT '所属群ID',
    f_word        varchar(64) NOT NULL COMMENT '敏感词',
    f_create_time bigint(20)  NOT NULL DEFAULT 0 COMMENT '添加时间(Unix毫秒)',
    PRIMARY KEY (f_id),
    KEY idx_group (f_groupid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

每条词一行、按群隔离。命中判定为**子串匹配、不区分大小写**，不做分词——群级词库量小，简单直白即可。

## 4. 协议设计

### 4.1 扩展既有报文

**`GroupRecord`** 增加 `intro` / `atallscope` / `newseehistory` / `memberinvite` / `welcomeon` / `welcometext` / `sensitiveon` 七个字段，随之影响 `buildGroupInfoResponse`、`buildUserGroupsResponse`、`buildGroupInfoChangedNotify` 三个构造器的输出。

**`UpdateGroupInfoRequest`** 按既有 `has_*` 模式增加同名的七组可选项。

**`GroupMemberRecord`** 增加 `muteuntil` / `mutereason`，随之影响 `buildGroupMembersResponse`。

**`GroupJoinRequestRecord`** 增加 `source` / `recommender`，随之影响 `buildGetJoinRequestsResponse` 与 `buildJoinGroupRequestNotify`。

**`cmd_mute_member` 请求**从 `{groupid, userid, muted}` 扩为 `{groupid, userid, muted, duration, reason}`：

- `duration`：禁言时长，单位**秒**，可选，缺省 0。`muted=1` 且 `duration=0` 表示永久禁言；`duration>0` 时服务端算出 `f_mute_until = now + duration*1000`。
- `reason`：禁言原因，可选，缺省空串。
- `muted=0`（解禁）时忽略这两个字段，并把 `f_mute_until` 与 `f_mute_reason` 一并清空。

由于两个新字段都是可选的，老客户端发来的三字段请求仍然合法，解析出 `duration=0` 即永久禁言，与扩展前行为一致。

### 4.2 新增敏感词库协议

`Protocol.h` 的 1300 段目前用到 1320，取后续两个号：

| 号 | 名称 | 用途 |
| --- | --- | --- |
| 1321 | `cmd_get_sensitive_words` | 拉取本群敏感词库 |
| 1322 | `cmd_operate_sensitive_word` | 敏感词增 / 删 |

请求与应答：

```
1321 请求 { "groupid": "..." }
1321 应答 { "code":0, "msg":"ok", "groupid":"...",
            "words":[ {"id":"...","word":"...","timestamp":123} ] }

1322 请求 { "groupid":"...", "operation":1, "word":"..." }      // operation: 1 新增
           { "groupid":"...", "operation":2, "id":"..." }        // operation: 2 删除
1322 应答 { "code":0, "msg":"ok" }
```

`operation` 取值另立枚举 `sensitive_word_operation`，与既有 `department_operation_type` 同风格。（原先此处举的例子是 `team_operation`，该枚举随 QQ 式好友分组一并取消，已于 2026-08-03 从 `Protocol.h` 删除。）

### 4.3 新增错误码

`error_code` 目前群组段用到 306，往后取：

| 值 | 名称 | 含义 |
| --- | --- | --- |
| 307 | `error_code_cannot_operate_owner` | 不能对群主执行该操作（踢/禁言/降级） |
| 308 | `error_code_sensitive_word` | 消息命中群敏感词，已拒绝发送 |
| 309 | `error_code_at_all_denied` | 无权 @ 全体成员 |

### 4.4 权限矩阵

服务端对每个操作的角色校验（客户端据同一张表做界面门控，两边必须一致；**服务端校验是权威，客户端门控只是不让用户白点**）：

| 操作 | 群主 | 管理员 | 成员 | 附加约束 |
| --- | --- | --- | --- | --- |
| 改群资料 / 权限（1311） | ✓ | ✓ | ✗ | |
| 邀请入群（1305） | ✓ | ✓ | 视 `f_member_invite` | 关闭时成员的邀请转为待审批申请 |
| 移出成员（1310） | ✓ | ✓ | ✗ | 管理员不能移出管理员；任何人不能移出群主 |
| 设 / 撤管理员（1312） | ✓ | ✗ | ✗ | |
| 禁言 / 解禁（1313） | ✓ | ✓ | ✗ | 管理员不能禁言管理员；任何人不能禁言群主 |
| 全员禁言（1314） | ✓ | ✓ | ✗ | 全员禁言期间管理员及以上仍可发言 |
| 审批加群（1308、1319） | ✓ | ✓ | ✗ | |
| 转让群主（1316） | ✓ | ✗ | ✗ | 目标须为本群成员且不是自己 |
| 解散群（1302） | ✓ | ✗ | ✗ | |
| 敏感词库（1321、1322） | ✓ | ✓ | ✗ | |

## 5. 服务端行为

### 5.1 禁言校验改为按到期时间判断

`ChatSession::sendGroupMessage` 现在的判断是：

```cpp
if (mymuted != 0 || (group.muteall != 0 && myrole < group_role_admin))
```

改造为：先取回 `f_muted` 与 `f_mute_until`，若 `f_muted != 0` 且 `f_mute_until != 0` 且 `f_mute_until <= now`，视为已到期——把 `f_muted` 置 0、清空 `f_mute_until` 与 `f_mute_reason`、推一条 `cmd_group_member_changed_notify`（changetype 为成员禁言状态变更），然后按未禁言放行。

同一套"取实际禁言态"的逻辑在 `cmd_get_group_members` 组装应答时也要用到（否则界面会把已过期的禁言仍显示为禁言中），故抽成 `GroupManager` 的一个方法，两处共用。

### 5.2 敏感词过滤

群开启 `f_sensitive_on` 时，`sendGroupMessage` 在落库前对文本类消息（`message_type_text`）的正文做子串匹配，命中即以 `error_code_sensitive_word` 拒绝并记 `LOGI`。非文本消息不过滤。

词库按群缓存在 `GroupManager` 内存里，随 1322 的增删失效重载——每条消息都查一次库不可接受。

### 5.3 @全体权限校验

`sendGroupMessage` 中若 `req.mentionall` 为真、且 `f_at_all_scope == 0`、且发送者 `myrole < group_role_admin`，以 `error_code_at_all_denied` 拒绝。

### 5.4 入群欢迎语

成员成功加入后（`cmd_invite_to_group`、`cmd_join_group_request` 直接入群、`cmd_handle_join_group` 审批通过，共三处入口），若群 `f_welcome_on` 为真且 `f_welcome_text` 非空，以 `message_type_system` 生成一条群消息落库并推送。发送者 userid 取 0 表示系统。

三处入口共用一个 `sendGroupWelcomeMessage(groupid, newMemberIds)` 私有方法，避免抄三遍。

### 5.5 新成员查看历史消息

群 `f_new_see_history` 为 0 时，成员拉取群历史消息要以其 `f_join_time` 为下界过滤。落点在群历史查询处（开工时定位 `MessageManager` 里对应的群历史 SQL），加一个"该成员入群时间"的时间下界条件。

### 5.6 成员邀请好友加群

`onInviteToGroup` 现在只校验"邀请人须为群成员"。改为：邀请人是群主或管理员则直接拉人；是普通成员时，若 `f_member_invite` 为 1 直接拉人，为 0 则把每个被邀请人转写成一条 `t_group_join_request`（`f_source` 记为好友邀请、`f_recommender` 记为邀请人），并推 `cmd_join_group_request_notify` 给群主与管理员。

## 6. 客户端数据流

```
打开群管理窗口
  └─ SetGroupContext(groupid, ...)  → CreateAndShow
       └─ 并发拉三份数据
            1303 cmd_get_group_info          → 群资料 + 本人角色
            1304 cmd_get_group_members       → 成员列表（含禁言态与到期时间）
            1319 cmd_get_group_join_requests → 待审批申请（仅群主/管理员拉）
            1321 cmd_get_sensitive_words     → 敏感词库（进「管理词库」时按需拉）
       └─ 三份应答各自到达时写入 GroupManageModel，重建当前页

用户操作
  └─ 发对应请求（1302/1305/1308/1310/1311/1312/1313/1314/1316/1322）
       └─ 应答 code != 0 → 弹提示，界面回退到操作前状态
       └─ 应答 code == 0 → 不直接改界面，等 1317/1318 推送统一刷新
                            （本端也会收到自己触发的推送）

推送到达
  ├─ 1317 cmd_group_member_changed_notify → 按 changetype 增/删/改成员，重建成员页与禁言页
  └─ 1318 cmd_group_info_changed_notify   → 改群资料，刷新 Header、基本信息页、群权限页
                                            changetype=2（已解散）→ 关窗并提示
```

**为什么成功应答不直接改界面**：服务端在每次成功的写操作后都会向全体成员推送变更，本端也在推送范围内。若应答与推送各改一次，同一次操作会重排两遍界面；且推送里带的是服务端的权威结果，比客户端自己猜的更准。**唯一的例外是需要立刻给用户反馈的失败路径**——失败没有推送，只能靠应答。

## 7. 界面与交互

### 7.1 成员卡右键菜单

在成员卡上右键弹出，落点经 `ClampPopupMenuToWorkArea` 夹取。菜单项：

```
发消息
查看资料
────────────
设为管理员 / 撤销管理员
禁言 / 解除禁言
────────────
移出本群
```

可用项按**登录者角色 × 目标成员角色**计算，与 §4.4 的权限矩阵一致。这段判定抽成纯函数 `BuildMemberMenuModel(myRole, targetRole, targetMuted, isSelf)` 单独测试——角色门控是最容易写错、又最难靠手点覆盖全的地方。

对自己右键时只显示"查看资料"（不能给自己发消息、也不能自己禁言自己）。

### 7.2 禁言时长的输入

点"禁言"后需要选时长。用一个小的二级菜单（10 分钟 / 1 小时 / 12 小时 / 1 天 / 永久）而不是弹对话框——禁言是个高频轻操作，弹窗太重。禁言原因本轮不在右键流程里填，留给禁言管理页的"添加禁言成员"走完整对话框。

### 7.3 选人对话框

从 `CreateGroupDlg` 抽出共用组件，三处复用：

| 调用处 | 候选来源 | 选择语义 |
| --- | --- | --- |
| 邀请成员（1305） | 好友列表 + 组织架构，**排除已在群内的** | 多选 |
| 添加禁言成员（1313） | 本群成员，**排除群主与自己** | 多选，另需时长与原因 |
| 转让群主（1316） | 本群成员，**排除自己** | 单选 |

**实现期的四个决定**

- **`MessageManager` 不认识群设置**，只认一个时间下界参数。把"是否该限制、限到什么时候"留在会话层，避免消息模块反向依赖群模块。
- **群主与管理员不受"新成员看历史"限制**。这项设置是拿来防新人翻旧账的，管理者需要看全量记录才能处理纠纷。
- **抽了两个小函数消灭重复**：`MessageProtocol::extractText`（敏感词过滤与会话摘要都要取消息正文）和 `MessageProtocol::buildTextContent`（服务器生成文本消息用，免得会话层为拼一个 `{"text":...}` 直接依赖 jsoncpp）。另外把"推给群主与管理员"的循环抽成了 `notifyGroupAdmins`，与既有的 `notifyGroupMembers` 配套。
- **敏感词库的读也要管理员权限**：词库内容本身算群管理信息，让普通成员看到等于把过滤规则直接告诉想绕过它的人。

**踩到的坑**：`ChatSession.h` 原先不认识 `GroupRecord`（它在 `GroupProtocol.h` 里，而该头没被 `ChatSession.h` 引入），加了前置声明；`ChatSession.cpp` 没有引入 `<sstream>` 与 jsoncpp，改用 `std::to_string` 拼接、并把 JSON 构造收进 `MessageProtocol`。

## 11. 待确认与风险

1. **老客户端与新服务端的兼容**：新增字段全部可选、新增列全部有默认值，老客户端不受影响。反向（新客户端连老服务端）不做保证——本项目客户端与服务端同版本发布。

2. **敏感词的匹配口径**：本方案取子串匹配、不区分大小写、不分词。这对中文够用，但会有"误伤"（词出现在无害的更长词里）。若实际使用中误伤明显，再考虑加词边界规则，届时改的是 `GroupManager` 里一个函数，不影响协议。

3. **禁言到期的惰性判断有一个可见后果**：若一个被禁言成员到期后一直不发言，他在成员列表里仍显示为"禁言中"，直到有人拉一次成员列表（拉取时也会走同一套到期判定并纠正显示）。这不影响他实际能否发言。

4. **`f_new_see_history` 的落点尚未定位**：群历史消息查询的具体 SQL 位置要在 S3 开工时确认，可能涉及 `MessageManager` 里不止一处查询。

5. **群头像**：基本信息页有"更换头像"按钮，服务端 `f_facetype` / `f_customface` 是有的，但自定义群头像要走文件服务器上传，链路比本方案其余部分都长。**本方案不含群头像上传**，该按钮留到后续单独一轮。

## 13. 补做：群权限六项接线 + 管理词库界面（2026-08-01）

### 13.1 群权限页六项接线

八个控件（两个下拉 + 六个开关中的四个属于本次范围，另两个是加群方式与@全体范围）现在拨动即生效，各自独立发一条 `cmd_update_group_info`。

**为什么逐项发、而不是攒一个"保存"按钮**：这一页设计上就没有保存按钮，交互预期是拨完立刻生效。逐项发还顺带避免了多端同时编辑时的互相覆盖 —— 请求里只带改动的那一项，别人刚改的其它项不会被本端的旧值盖掉。

映射关系（下拉项下标与服务端枚举同序，故直接透传）：

| 控件 | 协议字段 | 取值 |
| --- | --- | --- |
| 加群方式 | `joinmode` | 0 自由 / 1 需审批 / 2 禁止 |
| 谁能 @ 全体成员 | `atallscope` | 0 仅群主和管理员 / 1 所有人 |
| 新成员查看历史消息 | `newseehistory` | 0 / 1 |
| 成员邀请好友加群 | `memberinvite` | 0 / 1 |
| 入群欢迎语 | `welcomeon` | 0 / 1 |
| 消息敏感词过滤 | `sensitiveon` | 0 / 1 |

**一处刻意的额外行为**：开启"入群欢迎语"时若正文还是空的，请求里会顺带带一句默认欢迎语。服务端那边"开关开着但正文为空"等于不发，用户拨了开关却什么都没发生，会以为功能坏了。正文的编辑入口尚未提供，见 §12 第 4 条。

### 13.2 管理词库二级界面

从群权限页「管理词库」按钮进入，页面 id 取 `kPageSensitive = 1007`。

**为什么做成页面而不是独立对话框**：群管理窗已经有一整套"页面"机制（`BuildPage` 分发、`SwitchToPage` 切换、按角色门控），做成页面能整个复用；独立对话框要新写一个 `DuiFrameWindow` 子类、自己处理创建/销毁/居中/消息路由，为一个列表加输入框不值当。

**为什么不进左侧导航**：它属于"消息敏感词过滤"这一项的细节。放进导航会让六项主功能变成七项，层级也不对 —— 导航里的是并列的六个管理面，词库是其中一项的下钻。页面左上角有「‹ 返回」回到群权限页。

界面构成：返回按钮 + 标题、一行匹配规则说明、"输入框 + 添加"行、词条列表（每条含词、添加时间、删除按钮）。

**三个状态分开处理**：`m_sensitiveWordsLoaded` 区分"还没拉回来"（显示"正在加载词库…"）与"拉过了但确实没有词"（显示"还没有敏感词。在上面的输入框里添加第一个。"）。两者混成一句话的话，加载慢时用户会以为词全没了。

**敏感词的增删不在推送范围内**。词库既不是群资料（1318）也不是成员变动（1317），服务端不会推。故 `OnGroupOpResult` 里为 `cmd_operate_sensitive_word` 开了一个例外：成功应答直接触发重拉。这是"成功应答不改界面、一律等推送"这条规则唯一的例外，代码里注明了原因。

删除是个例外中的例外：本地先摘掉那一行再发请求（否则点了删除要等一个来回才消失，手感很差），应答回来后重拉对齐；失败时重拉会把它带回来。

新增前会在本地查一遍重复 —— 服务端也会静默忽略重复词，但提前挡掉能立刻给反馈，而不是点了半天没动静。
