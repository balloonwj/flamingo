# 群语音 / 群视频通话方案

> 作者：balloonwj@qq.com　起草日期：2026-10-04
> 用途：给 flamingoclient 增加群语音、群视频通话的整体方案、协议要点、分期与进度记录。协议细节以
> `docs/协议设计-v2.md` 第 21 节为准，本文只写设计思路与取舍。

---

## 1. 背景与目标

群聊窗口的「语音通话」「视频通话」两个按钮一直只弹「群聊暂不支持」（`BalloonGroupChatWindow.cpp`）。
本项目让群成员在群里发起多人语音、多人视频通话：发起人选人振铃，其余群成员看到横幅后可以自己加入；
通话中每个人随时开关自己的麦克风与摄像头。

## 2. 已定决策

2026-10-04 与用户逐项确认：

| # | 决策项 | 结论 |
| ---: | --- | --- |
| 1 | 发起方式 | **选人振铃**：发起人从群成员里勾选要叫的人，只有被选中的人收到来电振铃；其余群成员在群聊窗顶部看到横幅，可以自己加入 |
| 2 | 结束规则 | **保留到所有人都离开**：最后一个已加入的人离开时通话结束；只剩一人时房间照常保留 |
| 3 | 人数上限 | 默认 **16 人**（含发起人），同时开摄像头最多 **9 路**；两个数都是 `chatserver.conf` 的可选配置项 |
| 4 | 服务端结构 | 新写一套群通话信令（GroupCall 四件套），**不改造**屏幕共享已有的代码；imgserver 复用屏幕共享的房间中转 |
| 5 | 与屏幕共享的关系 | 第 1~6 期里群通话与屏幕共享互斥；「群通话中共享屏幕」留到第 7 期（可选） |
| 6 | 从横幅 / 卡片主动加入群视频通话时的摄像头 | **默认关闭**，进来后自己打开（2026-10-05 联调后确认）；接听邀请时仍按媒体类型，群视频默认打开 |

由此推导出的其余约定（未单独征询，按惯例处理）：

- 群语音与群视频是**同一种房间**，`media` 只决定发起时各人摄像头的默认开关；通话中不需要「切换媒体」协商。
- **一个群同时只有一场群通话**。已有通话时再发起，服务端回 722 并带上那一场的房间号，客户端直接改为加入。
- **一个人同时只能在一处**：一对一通话（含响铃）、屏幕共享房间、群通话房间（含振铃中）三者互斥。
- 被邀请人所有在线的设备都振铃；在其中一台接听或拒绝后，其它设备的振铃随房间状态推送自动收起。
- 通话记录用一直定义着、从未使用的 `message_type_rtc`（16）：发起时服务端在群里写一张通话卡片，结束时改写成
  「已结束 · 时长」。卡片的进行状态以查询结果为准，内容里有时长就显示已结束。

## 3. 现状盘点（据实证）

| 现有能力 | 位置 | 对群通话 |
| --- | --- | --- |
| 一对一通话 `CallManager`（1701~1709） | `chatserversrc/CallManager.h`（`CallSessionInfo`） | 会话结构只有主叫、被叫，sessionid 按两人拼成，不能扩展 |
| imgserver 一对一中转 `RelayHub` | `imgserversrc/RelayHub.cpp:14-23` | 写死「最多两端」，不能用 |
| imgserver 房间中转（1859 / 1860） | `RelayRoomHub.h`、`ScreenShareRoomRelay.cpp`、`RoomForwardPolicy.h` | 座位 0~254、帧头带「轨道 + 发送者座位」、慢接收端丢帧、新人加入请求关键帧；**直接复用** |
| 房间中转客户端 `ShareRelayClient` | `FlamingoMedia/Share/ShareRelayClient.h` | 握手、报到、收发 1860，与房间种类无关；**直接复用** |
| 房间语音 `ShareAudioSession` | `FlamingoMedia/Share/ShareAudioSession.h` | 每人一路 Opus（48 kHz、20 ms），多路混音、回声消除、说话人检测；**直接复用** |
| 摄像头收发 `ShareCameraSender` / `ShareCameraReceiver` | `FlamingoMedia/Share/` | 640×360、15 fps、400 kbps，每座位一个解码器、最多 9 路；**直接复用** |
| 企业功能开关 `FeatureSwitchManager` | `chatserversrc/FeatureSwitchManager.cpp`（`KnownFeature` 表） | 新增一行 `groupcall.enabled` |
| 信令白名单 | `flamingoclient/Source/net/MediaSignalPolicy.cpp` | 只放行 1701~1716、1720~1734，要加群通话号段 |

容量参考：屏幕共享 1 人推流 + 30 人观看、2 Mbps 时中转出口约 61.8 Mbps，Debug 版 imgserver 占一个核的 15%
（`docs/屏幕共享与录制方案.md` 第 3c 步的压测）。

带宽估算（据推测，按现有参数计算，未实测）：16 人全开麦克风时每人下行约 15 × 28 kbps ≈ 420 kbps，第 5 期打开
Opus DTX 后只剩正在说话的几路；视频最坏情况每人下行 8 × 400 kbps ≈ 3.2 Mbps，中转出口约 51 Mbps（第 5 期按人数降码率后
9 路全开时为 8 × 200 kbps ≈ 1.6 Mbps）。

## 4. 协议要点

完整定义见 `docs/协议设计-v2.md` 第 21 节，这里只列结构。

- 信令 1740~1751（chatserver）：发起 1740、邀请推送 1741、加入 1742、拒绝 1743、离开 1744、房间状态推送 1745、
  中转参数推送 1746、追加邀请 1747、成员媒体 1748、查询 1749、群内状态推送 1750、管理操作 1751（第 6 期）。
- 媒体：复用 1859 / 1860 房间中转，令牌角色新增 `role_groupcall_member`（13），sessionid 为房间号（`gc-` 开头），
  `peeruid` 承载座位号（1~254）。群通话房间只接受摄像头（2）、麦克风（3）、控制（6）三种轨道。
- 错误码 721~728（700 段音视频域）。
- 卡片：`message_type_rtc`，content 带 `kind:"groupcall"`。

## 5. 服务端设计

### 5.1 chatserver：GroupCall 四件套

照屏幕共享的结构拆成四个模块。原计划的 `GroupCallRules`（被邀请人筛选、通知对象等纯函数）实现时并进了
`GroupCallService`：服务把群成员查询、在线推送、忙线判断、消息落库都经 `IGroupCallEnv` 接口取得，单测里换成假环境，
规则部分随服务一起测，不必再拆一个模块。

| 模块 | 职责 | 单测套件 |
| --- | --- | --- |
| `GroupCallManager` | 房间表（房间号 → 房间、群号 → 房间号、用户 → 房间号），成员状态（振铃中 / 已加入）、座位分配、摄像头上限、振铃超时、掉线宽限、令牌签发 | GCM |
| `GroupCallProtocol` | 1740~1751 的 JSON 编解码，卡片 content 的构造与结束改写 | GCP |
| `GroupCallService` | 每个请求、登录 / 下线、定时扫描的业务规则：被邀请人筛选（去重、去掉自己、非群成员、忙线、离线）、权限、互斥、通知对象；输出「发给谁、发什么」的列表，不直接碰网络 | GCS |
| `GroupCallServerEnv` | `IGroupCallEnv` 的真实实现：群成员与角色、在线会话、一对一通话与屏幕共享的忙线、企业开关、卡片落库与改写、推送 | （联调验证） |

关键规则：

- 发起人自动加入（座位最小的空闲号）；被邀请人进入「振铃中」状态，不占座位，接听时才分配座位。
- 振铃中的人也算在房间里：再收到别的邀请、一对一来电时按「忙」处理。
- 振铃 45 秒无应答、拒绝、离线：从房间里移除，向房间成员与他本人推 1745。
- 已加入的人最后一条连接断开：标记离线，宽限 30 秒（`groupcallofflinegracems`）；期内重新登录推 1745 并补发 1746，超时按离开处理。
- 已加入人数降到 0 时房间结束：向群成员与仍在振铃的人推 1750（`active` 为 0），改写卡片。
- 互斥判断：一对一通话邀请、屏幕共享发起 / 加入经 `GroupCallService::isUserInGroupCall` 判断是否已在群通话里；群通话一侧经
  `IGroupCallEnv::isBusyOutsideGroupCall` 判断是否在一对一通话或屏幕共享里。

### 5.2 imgserver：房间中转只改三处

1. `RelayToken::role_groupcall_member = 13`；`RelayRoomHubT::join` 接纳它（座位 1~254），并要求同一房间里的角色同属一类
   （屏幕共享的 7 / 8 与群通话的 13 不能混在一个房间里）。
2. `RelaySession::onRoomHello` 接纳角色 13；一对一报到（`RelayHelloPolicy::isAcceptedPairRole`）拒绝角色 13。
3. `RelaySession::onRoomData`：群通话连接发来的屏幕（1）、电脑声音（4）、标注（5）轨道直接丢弃；控制帧中的「订阅」（第 5 期）
   由服务端消费、不转发。

## 6. 客户端设计

### 6.1 FlamingoMedia.dll 新增 `GroupCall/`

| 类 | 职责 |
| --- | --- |
| `GroupCallProtocolClient` | 1740~1751 的 JSON 编解码与房间快照（`GroupCallState`：成员、谁在振铃、谁开着摄像头），纯逻辑，配单测 |
| `GroupCallLayout` | 宫格排布的纯函数（人数 → 行列、格子排序、订阅哪些座位、摄像头码率档位）与窗口文字，配单测 |
| `GroupCallMediaSession` | 一条房间中转连接（`ShareRelayClient`）+ 分片重组 + 房间语音（`ShareAudioSession`，打开 DTX）+ 摄像头收发 + 订阅控制帧；收到的包体按轨道分发 |
| `GroupCallController` | 消息窗口 + 状态机：发起、来电、加入、离开、快照处理、铃声、管理操作、向宿主报告群通话状态 |
| `GroupCallIncomingDlg` | 右下角来电窗：「某某邀请你加入群语音通话」、群名、已在通话中的人数、拒绝 / 接听 |
| `GroupCallWindow` | 通话主窗口：宫格画面 / 头像、说话高亮、底部小条、按钮（麦克风、摄像头、邀请成员、挂断）、成员右键菜单（静音、移出） |
| `GroupCallMessages` | 控制器消息窗口的私有消息号 `WM_APP + 0xC0~0xC4` |

原计划的 `GroupCallModel` 没有单独成类：房间快照就是 `GroupCallState`，宫格的输入由 `GroupCallLayout` 的纯函数算出。

宫格规则：1 人整幅；2 人左右两格；3~4 人 2×2；5~6 人 3×2；7~9 人 3×3；超过 9 人时宫格只放 9 人（开着摄像头的优先），
其余人以头像小条列在底部。

### 6.2 插件接口（不升版本号）

- `IMediaModule`：`StartGroupCall(groupId, groupName, media, invitees, count)`、`JoinGroupCall(groupId, groupName, roomId)`、
  `QueryGroupCall(groupId)`、`InviteToGroupCall(groupId, userIds, count)`。
- `IMediaHost`：`OnGroupCallStatus(groupId, roomId, active, media, count, initiatorId, startTime)`（刷新横幅与卡片）、
  `OnGroupCallCardChanged(groupId, msgId, contentJson)`（通话结束后服务端改写了卡片）、
  `RequestGroupCallInvitees(groupId, excludeIds, excludeCount)`（通话窗点「邀请成员」，由 exe 弹选人框）、
  `GetGroupMemberRole(groupId, userId)`（决定显不显示静音、移出）。

### 6.3 exe 侧

- `MediaSignalPolicy` 白名单加 1740~1751。
- `Feature/GroupCall/`：`CGroupCallHub`（群聊窗与主面板经它调模块）与 `GroupCallStatusCache`（各群的群通话状态，登出清空）。
- 群聊窗：语音 / 视频按钮 → 选人框（`CCreateGroupDlg` 的 `kPurposeGroupCall`，追加邀请用 `kPurposeGroupCallInvite`）→
  `StartGroupCall`；本群已有群通话时直接加入；群通话横幅（`kGIdGroupCallBanner`）；打开时查询。
- 消息列表：`message_type_rtc` 的群通话卡片复用屏幕共享卡片的气泡（`screenShareIsGroupCall`，解析与状态在
  `ChatGroupCallCard`）：标题按媒体类型、发起人、状态（进行中人数 / 已结束 · 时长）、「加入」按钮。本地库的 content 列存
  `groupcall` 子对象，结束后由主面板改写。
- 企业开关 `groupcall` 为 0 时隐藏两个按钮（登录应答与 1013 推送）；flamingoAdmin 的企业设置弹窗与平台设置页各有一个开关面板。

实机联调（2026-10-05，用户同意后在共用桌面上做）：隔离服务端，三个客户端 A（群主）、B、C；PostMessage 驱动、
按窗口句柄截图，截图在 `snapshots/gc_*.png`。A 用真实的麦克风与扬声器，
B、C 设 `FLAMINGO_GROUPCALL_NO_DEVICES=2`（Debug 版：不开声音设备、摄像头照常），三人都设 `FLAMINGO_SHARE_FAKE_CAMERA=1`
（模拟摄像头），避免同一台机器上三个客户端的扬声器与麦克风互相回授。走通的场景：

- 群聊窗「视频通话」→ 选人框 → 发起；不在线的成员没有振铃（`offline=1`）；B、C 右下角来电窗接听，三路画面互通；
- 群聊窗横幅与卡片的人数随加入、离开实时变化；订阅的座位数随人数变化；第三路摄像头加入后本人码率 400 → 300 kbps，
  有人离开后回到 400 kbps；
- 群主静音某人、全员静音（2026-10-05 起是房间状态，见 `docs/音视频通话优化方案.md` 第 9 项）、移出某人（被移出的人收到提示）；通话窗「邀请成员」只列不在通话里的人；拒绝邀请；
  从群聊窗横幅自己加入；发起人先离开后通话保留在其余两人之间；最后一人离开后通话结束，三个客户端的卡片都改写成
  「通话已结束 · 时长」、本地库命中改写；重开群聊窗时历史卡片仍显示已结束；会话列表摘要「[群语音通话]」；
- 语音通话中途打开摄像头，对方宫格里这个人挪到前面并出现画面。

联调中有一次 C 关掉「你已被移出群通话」提示框时群聊窗被打开，服务端没有推送、按同样步骤没能复现，
据推测是有人手动点了 C 的托盘或会话列表，记为未复现。

第 5 期两项补充说明：

- **DTX**：只在群通话的麦克风轨打开（`GroupCallMediaSession` 启动语音前调 `ShareAudioSession::SetDtx(true)`）。静音时编码器
  产出 1~2 字节的包，音频引擎不再交给上层，接收端该路没有新数据时混音按静音处理。一对一通话、屏幕共享、语音消息不受影响。
- **码率自适应**：没有做按丢包反馈的闭环调节，而是按房间里开着摄像头的人数分档（1~2 路 400 kbps、3~4 路 300 kbps、
  5 路及以上 200 kbps，`GroupCallCameraBitrateFor`），9 路全开时每人下行约 8 × 200 kbps ≈ 1.6 Mbps（据推测，未实测）。
  通话窗每次刷新时按当前人数重算，变化时在下一帧编码前交给编码器。

## 8. 风险

- 全部流量走 TCP 中转，网络差的成员会被服务端丢视频帧（关键帧照发），音频不丢。
- 每人收 N−1 路 Opus，人数多时下行上升；第 5 期的 DTX 是主要缓解手段。
- 静音由客户端配合执行（与屏幕共享相同），中转不拦截被静音者的声音帧。

> 认知诚实声明：第 3 节均已核对代码位置（据实证）；带宽数字是按现有编码参数计算的推测值，第 3e、4 期联调时实测。
