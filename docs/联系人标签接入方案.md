# 「联系人标签」接入方案与开发计划

> 在联系人资料对话框里给同事贴短词标签（「设计」「外包」「三期项目」之类），
> 用来补足组织架构表达不了的那部分关系。标签是**单向**的：只影响贴标签的人自己看到的
> 内容，被贴的人既看不到也不受影响。
>
> 本文写于 2026-08-13，所列代码位置均已核对。

---

## 1. 背景与目标

企业版的通讯录直接来自组织架构（`t_department` / `t_department_member`），一家公司里
所有同事互相可见。这带来一个新问题：通讯录很长，而部门与职务是公司统一定义的，
表达的是「这个人在公司里是什么角色」，**表达不了「这个人跟我是什么关系」**。

现有的联系人备注名（`cmd_set_friend_remark`，1209）已经是私人视角的信息，但它是
**单值**的 —— 一个人只能有一个备注名，写了「设计组组长」就写不下「三期项目对接人」。
用户真正需要的是可以并列的若干个短词。

目标：让每个人能给通讯录里的同事贴任意几个短标签，标签只属于贴的人自己，
在联系人资料对话框里增删改，随通讯录一起读回来。

**不在本期范围内**：按标签筛选联系人（表结构为此留了余地，界面本期不做）、
标签的颜色与图标、给群或群成员贴标签、多端实时同步。

## 3. 数据模型与表结构

### 3.1 新建 `t_contact_tag`，一行一个标签

```sql
//联系人标签表：一行表示"f_userid 给 f_target_userid 贴了一个标签 f_tag"。
//标签是单向的（口径同 t_contact_remark）：只影响 f_userid 这一侧的显示，
//被贴标签的人看不到、也不受影响，同一个人在不同同事那里可以有完全不同的标签。
//一行一个标签而不是把整串标签打包进一列，理由见 docs/联系人标签接入方案.md 的决策记录。
CREATE TABLE IF NOT EXISTS  t_contact_tag  (
         f_userid         bigint(20)  NOT NULL COMMENT '标签归属用户userid(贴标签的人)',
         f_target_userid  bigint(20)  NOT NULL COMMENT '被贴标签的联系人userid',
         f_tag            varchar(16) NOT NULL COMMENT '标签文本,最长16字符(按字符计,非字节)',
         f_order          int(4)      NOT NULL DEFAULT 0 COMMENT '同一联系人下的展示次序,从0起递增',
         f_update_time    bigint(20)  NOT NULL DEFAULT 0 COMMENT '最近一次写入时间(Unix毫秒)',
         PRIMARY KEY ( f_userid, f_target_userid, f_tag ),
         //按标签反查人用："我贴了'外包'标签的都有谁"。主键的最左前缀只覆盖
         //(f_userid) 与 (f_userid, f_target_userid)，覆盖不到"跳过 target 直接按 tag 查"，
         //故单独建这一条。本期界面不做筛选，索引先留着，避免日后加筛选时要改表。
         KEY  idx_contact_tag_tag  ( f_userid, f_tag )
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

**不再单独给 `f_userid` 建索引**：主键 `(f_userid, f_target_userid, f_tag)` 的最左前缀
已经能服务「取某人给某个联系人贴的全部标签」与「取某人贴过的全部标签」两种查询。
`t_contact_remark` 里那条 `KEY idx_user (f_userid)` 与它的主键前缀重复，是历史写法，
新表不照抄。

### 3.2 `f_order` 的语义

`f_order` 记录标签在界面上的先后次序，从 0 起连续递增，取值范围是 `[0, 9]`（受
每个联系人 10 个标签的上限约束）。它不参与主键，只用于读取时排序：
`ORDER BY f_order ASC`。整份覆盖写入时按请求里的数组下标重新赋值，因此这一列
永远与用户在界面上看到的顺序一致，不会出现空洞。

### 3.3 三处建表定义都要改，漏一处就有一套库跑不起来

| 文件 | 改什么 |
| --- | --- |
| `flamingoserver/table.sql` | MySQL 建表语句（**唯一手写的一份**） |
| `flamingoserver/table_sqlite.sql` | 由脚本生成 |
| `flamingoserver/sqliteapi/SqliteSchema.cpp` | 由脚本生成（内嵌建表语句 + 表名清单 + 列清单三处） |

后两者**不得手改**：改完 `table.sql` 后执行 `python tools/gen_table_sqlite.py`
重新生成（见开发约定文档「Protocol & data references」）。当前部署跑的是 SQLite
（`flamingoserver/etc/chatserver.conf` 的 `dbtype=sqlite`），这一步不能漏。

### 3.4 `f_tag` 必须登记进 `NOCASE_COLUMNS`，否则两个后端行为不一致

生成脚本 `flamingoserver/tools/gen_table_sqlite.py:43` 有一张 `NOCASE_COLUMNS` 表，
列在里面的文本列会在 SQLite 侧显式加 `COLLATE NOCASE`。原因是两个后端的默认行为相反：

- MySQL 侧建表带 `DEFAULT CHARSET=utf8`，默认排序规则 `utf8_general_ci` **不区分大小写**；
- SQLite 的文本比较默认 `BINARY`，**区分大小写**。

标签要做不区分大小写的去重（见 §5.3），而去重最终是靠主键 `(f_userid,
f_target_userid, f_tag)` 的唯一性兜底的。若不登记，同一份请求在 MySQL 上
`Design` 与 `design` 会因主键冲突只落一行、在 SQLite 上却会落两行 —— 同一套代码
在两种部署下得到不同结果，且只有换库时才暴露。

因此本功能必须同时改脚本：

```python
NOCASE_COLUMNS = set([
    ('t_user', 'f_username'),
    ('t_user', 'f_mail'),
    ('t_admin', 'f_email'),
    ('t_enterprise', 'f_name'),
    ('t_contact_tag', 'f_tag'),   #标签按不区分大小写去重，两个后端须一致
])
```

改完脚本后要**重新生成**一次 SQLite 那两份文件，生成物里应能看到
`f_tag varchar(16) COLLATE NOCASE NOT NULL`。

### 3.5 长度上限按字符计，不按字节

`varchar(16)` 在 MySQL 的 utf8 字符集下是 **16 个字符**（一个汉字算一个），
SQLite 则根本不约束长度。因此服务端的长度校验**必须自己按 UTF-8 码点数**判定，
不能用 `std::string::size()`（那是字节数，16 个汉字是 48 字节，会被误判为超长）。
这是本功能最容易写错的一处。

## 4. 协议设计

### 4.1 新增 `cmd_set_contact_tags = 1217`

1200 段现状（核对 `chatserversrc/Protocol.h:103-120`）：

| 状态 | 编号 |
| --- | --- |
| 在用 | 1201、1202、1209、1213、1215、1216 |
| 作废、不得复用 | 1203–1208、1210、1211、1212、1214 |
| 空闲 | **1217 起** |

1216（`cmd_set_starred`）是当前段内最大的在用编号，故本功能取 **1217**。

### 4.2 请求与应答

**设置某个联系人的标签** `cmd_set_contact_tags`（1217）：

→ 请求：

```json
{
  "userid": "100009",
  "tags": ["设计", "三期项目", "外包"]
}
```

← 成功应答：

```json
{
  "code": 0, "msg": "ok",
  "userid": "100009",
  "tags": ["设计", "三期项目", "外包"]
}
```

← 失败应答（以标签条数超限为例）：

```json
{
  "code": 211, "msg": "tag count limit exceeded",
  "userid": "100009",
  "tags": ["设计", "三期项目"]
}
```

字段说明：

- `userid`：被贴标签的联系人 userid。字段名与 `cmd_set_friend_remark`（1209）一致
  而不用 `cmd_set_starred` 的 `target` —— 标签与备注名是同一类数据、落在同一种表
  形态上，两条命令的请求字段应当叫同一个名字。
- `tags`：**该联系人在本人视角下的完整标签列表**，不是增量。空数组 `[]` 表示清空。
- 应答里的 `tags` 是**服务端归一并落库之后的最终结果**（归一规则见 §5.3），
  不是把请求原样回带。客户端拿它覆盖本地那一份，界面就与服务端一致了。
- **失败时 `tags` 回带的是服务端当前实际存着的列表**，客户端据此把界面对回真值。
  这一条是有意为之：用户在界面上已经改了（乐观更新），请求失败若不告诉客户端
  真实状态，界面会一直显示一份服务端并不认可的内容。

### 4.3 `cmd_get_contacts`（1201）应答里增加 `tags`

在 `contacts[]` 的每个元素上加一个 `tags` 数组，与 `remark` 并列：

```json
"contacts": [
  { "userid": "100009", "username": "10010002", "nickname": "江屿白",
    "presence": 1, "clienttype": 1,
    "remark": "设计组组长",
    "tags": ["设计", "三期项目"] }
]
```

- **一律写出，不做「空则省略字段」的优化。** 没有标签时写 `[]`。这与同一段代码里
  `remark` 的既有处置一致（`chatserversrc/ContactsProtocol.cpp:74-77` 的注释写明了
  同样的理由）：客户端只需要一条解析路径，`tags` 有无与「标签被清空」在显示上
  本就是同一种效果，不必用字段有无来区分。
- 顺序按 `f_order` 升序，与用户在界面上看到的顺序一致。
- **不新增读取命令。** 标签只在联系人资料对话框里显示，而打开该对话框的前提是
  通讯录已经拉到，因此随 1201 一起下发就够了，再加一条「拉某人的标签」是多余往返。
- 老客户端读到多出来的字段会忽略，不影响兼容。

### 4.4 新增错误码 `error_code_tag_limit = 211`

联系人域 200–299 的现状（核对 `chatserversrc/Protocol.h:294-304`）：200、202、204、
209、210 在用，201、203、205、206、207、208 作废留空，**211 空闲**。

### 4.5 本期不新增主动推送

A 设备改了标签，B 设备要到下次拉通讯录（重新登录 / 断线重连）时才看到，
与备注名、收藏、特别关注当初的处置一致。

> **将来若要做多端同步，不得借用 `cmd_user_info_changed_notify`（1108）。**
> 那条推送的语义是「某个联系人的资料变了」，推送的内容是**所有人共享**的信息
> （昵称、头像、签名等），收到的人都会据此刷新自己看到的那个联系人。
> 标签只属于一个人，塞进这条推送会让所有收到的人都误以为该联系人资料发生了变更，
> 进而刷出错误的内容。正确的做法是另开一条只发给标签归属者其他在线设备的推送，
> 取 1200 段的下一个空闲编号。

## 5. 限制与校验

### 5.1 两个上限

| 上限 | 取值 | 依据 |
| --- | --- | --- |
| 单个标签长度 | 16 字符 | 见下方推导 |
| 每个联系人的标签数 | 10 个 | 配合「标签区封顶 3 行、超出用滚动容器」 |

**16 字符是按界面宽度算出来的**，不是随手取的整数：

- 胶囊的理想宽度公式在 `Source/BalloonContact/TagChip.cpp:129-134`：
  `左内边距 10 + 文字宽 + 文字与「×」间距 4 + 「×」字形宽 12 + 右内边距 10`，
  即 **36 像素 + 文字宽**。
- 标签区可用宽度是 **380 像素**：对话框客户区宽 420
  （`Source/BalloonContact/BalloonContactWindow.cpp:45`），根容器左右内边距各 20
  （`ContactLayout.cpp` 内嵌 XML 的 `padding="20,18,20,18"`）。
- 胶囊字号 12 像素，一个汉字约占 12 像素宽。32 个汉字的胶囊约
  `36 + 32 × 12 = 420` 像素，**比整行可用宽度还宽**，必然被省略号截断，等于用户
  打了字却看不到。16 个汉字约 `36 + 16 × 12 = 228` 像素，占一行的六成，稳妥。

两个上限都必须在服务端定义为具名 `constexpr` 常量并注释出处，不得写成裸数字
（开发约定文档代码规范第 2 条）。客户端的输入框同时用 `SetMaxLength(16)` 从源头限制，
与备注名行 `SetMaxLength(32)` 的既有写法一致
（`BalloonContactWindow.cpp:203`）。

### 5.2 校验清单

| 校验项 | 不通过时返回 |
| --- | --- |
| `userid` 缺失、非数字或不为正 | `error_code_bad_request`(3) |
| `tags` 缺失或不是 JSON 数组 | `error_code_bad_request`(3) |
| 数组元素不是字符串 | `error_code_bad_request`(3) |
| 单个标签归一后超过 16 字符 | `error_code_bad_request`(3) |
| 目标用户不存在 | `error_code_not_found`(7) |
| 目标用户不在同一企业 | `error_code_not_friend`(202) |
| 归一后条数超过 10 | `error_code_tag_limit`(211) |

**单条超长为什么不给专门的错误码**：正常路径下客户端已经用输入框的最大长度
从源头挡住了，服务端这道校验是兜底，用户在界面上撞不到它，给它一个专码
客户端也没有对应的提示文案可写。而**条数达到上限是用户正常操作会真实撞上的**
情况（贴到第 11 个），界面要给一句明确的「最多只能贴 10 个标签」，
值得一个专码来区分。

### 5.3 服务端归一规则

服务端收到 `tags` 后，按下列顺序处理，**处理完的结果既是落库的内容、也是应答
回带的内容**：

1. 逐条去掉首尾空白字符；
2. 丢弃处理后为空串的项；
3. **不区分大小写去重**，保留首次出现的那一条，并保留它的原始大小写
   （用户输入 `Design` 就存 `Design`，后面再来一个 `design` 直接丢掉）；
4. 保持请求里的先后次序，按下标依次写入 `f_order`（0、1、2……）。

去重保留「首次出现者的原始大小写」而不是统一转成小写：标签是给人看的文字，
用户特意打的大写不该被系统改掉。

### 5.4 清空不受条数上限约束

`tags` 为空数组时**跳过条数校验**直接放行。若不放行，历史上因上限调整或数据
迁移而超过 10 条的用户会陷入「加不了也删不掉」的状态 —— 想删就得提交一份新列表，
而任何一份超过 10 条的列表都会被上限挡回去。

由此带来一个需要知道的边界：存量 12 条的用户**不能只删一条变成 11 条**
（仍然超限、仍被拒绝），只能一次删到 10 条以内，或者直接清空重来。这是可以接受的，
因为超限状态本身只可能来自上限调整或人工改库，不是正常路径。

### 5.5 整份覆盖的写入方式

一次请求就是一次完整替换，服务端在同一个事务里做两步：删掉
`(f_userid, f_target_userid)` 下的全部现有行，再按归一后的列表逐条插入。
不做「算差集、只改变化的那几行」的优化 —— 单个联系人的标签最多 10 行，
差集算法带来的复杂度远大于它省下的那点写入量。

## 6. 服务端设计

新增 `ContactTagManager`（`chatserversrc/ContactTagManager.{h,cpp}`），形状照
`ContactRemarkManager` 那一对：

| 函数 | 职责 |
| --- | --- |
| `getTags(userid, targetUserId, out)` | 取某人给某个联系人贴的标签，按 `f_order` 升序 |
| `getTagsBatch(userid, out)` | 取某人贴过的全部标签，按被贴人分组；组装 1201 应答时一次查完 |
| `setTags(userid, targetUserId, tags, now, outErrorCode)` | 整份覆盖，含归一、校验与事务 |
| `removeTagsForAll(targetUserId)` | 某用户被删号 / 移出企业时，把别人给他贴的标签一并清掉 |

报文的解析与组装放在 `ContactTagProtocol.{h,cpp}`，与 `FavoriteProtocol` /
`StarredProtocol` 同形，保持「管理器管数据、Protocol 管 JSON」的分层。

`ChatSession` 里加一个 `case cmd_set_contact_tags` 分支转到 `onSetContactTags`，
按开发约定文档代码规范第 9 条在 `case` 上一行写中文注释。

**组装 1201 应答时要用批量查询。** `ContactsProtocol.cpp` 现在对备注名走的是
`getRemarks(userid, out)` 一次取回全部再按 userid 查表填字段，标签照同样的做法用
`getTagsBatch`。若改成对每个联系人查一次，一家几百人的企业拉一次通讯录就是几百次
查询，登录会明显变慢。

关键路径要打英文日志（开发约定文档代码规范第 15 条、测试规范第 3 条）：收到请求时
记 `userid` / 目标 / 标签条数，归一后条数与请求条数不一致时记一条，落库失败时记错误。

## 7. 客户端设计

### 7.1 交互设计

| 动作 | 行为 |
| --- | --- |
| 点胶囊的**文字区** | 就地把这枚胶囊换成编辑框，光标落在文字末尾，全选当前文字 |
| 点胶囊的**「×」** | 删除这枚标签（现有行为，不变） |
| 点「+ 添加标签」 | 在按钮位置就地插入一个空编辑框 |
| 编辑中按回车 / 编辑框失焦 | 提交 |
| 编辑中按 Esc | 取消，恢复原样 |

提交时按下列规则落地：

- **修改时把内容全删光** —— 视为**删除该标签**。用户把字全删掉再确认，意图是明确的，
  此时再弹一句「标签不能为空」是在跟用户较劲。
- **新增时输入为空或全是空格** —— 视为**取消**，不添加任何东西，也不提示。
  用户点了「+」又改主意，不该被打断。
- **新增时与已有标签重复**（不区分大小写）—— 不添加，给一句轻提示。加进去会得到
  两枚一模一样的胶囊，而服务端归一时又会把它去掉，界面与服务端立刻不一致。
- **修改成与另一条重复** —— **两条合并**为一条，即被编辑的那枚消失、原有那枚保留。
  这与服务端「保留首次出现者」的归一规则得到的是同一个结果，客户端先做一遍是为了
  让用户立刻看到最终形态，而不是提交后界面才突然少一枚。

改动一律走**乐观更新**：先改界面、再发 `cmd_set_contact_tags`，应答成功就用回带的
`tags` 覆盖本地那一份（服务端归一后可能与本地略有出入，以服务端为准），
失败则用应答回带的服务端当前列表把界面对回真值。这与备注名行的既有做法一致。

**为什么是就地编辑而不是弹一个独立窗口**：这个对话框里已经有两处就地编辑
（备注名行的 `kIdRemarkEdit`，见 `ContactLayout.h:34`），主面板的个性签名也是就地编辑。
为一个 16 字的短词单独弹一个窗口，用户要多点两次、还要在两个窗口之间挪视线，
与同一个对话框里的其它字段也不是一种手感。

### 7.2 UI 实现要点

**标签胶囊维持现有的自绘控件，只做最小扩展。** 按开发约定文档 UI 约定第 2 条，
新增控件应优先复用 balloonui；但 `TagChip` 已经存在且工作正常，本期只需给它加
「文字区可点击」这一项能力，属于「子类化 / 最小扩展」而不是新起炉灶。
需要改的地方：

- `TagChip` 现在**只在「×」热区内**冒 `DUIN_CLICK`，点文字区不发任何通知
  （`Source/BalloonContact/TagChip.h:8-10` 的注释写明了）。要新增一个自定义通知码
  表示「请求编辑本标签」，在命中文字区时冒出去。
- **自定义通知码另开取值段**，不要从 `balloonwjui::DUIN_CUSTOM + 1` 起算
  （开发约定文档 UI 约定第 4 条：`+1` 那一档已有十余个控件在用）。
- **派发时必须把 `ctrlId` 写进分支条件本身**，不能进了分支再判。这个对话框里
  还有 `DuiComboBox`（分组下拉）、`DuiEdit`（备注名编辑框）、`DuiSwitch`
  等控件，它们各自的自定义码数值与本控件重合的概率很高。写错的症状是
  **点了没反应**：不报错、不崩溃、日志里什么都没有。

**编辑框复用 balloonui 的 `DuiEdit`**，与备注名行同一套用法：`SetShowBorder(true)`、
`SetMaxLength(16)`、默认 `SetVisible(false)`
（参照 `BalloonContactWindow.cpp:198-209`）。`DuiEdit` 是无窗口控件，构造完即可使用，
不需要在宿主窗口就绪之后再补一次创建调用。编辑框的理想宽度按与胶囊相同的公式给，
换成编辑态时行高不跳。

提交与取消可以直接用它的两个通知码：单行模式下按回车冒 `DuiEdit::DUIN_EDIT_ENTER`，
按 Esc 冒 `DuiEdit::DUIN_EDIT_ESCAPE`，两者都会消费掉按键。按前面 `ctrlId` 那一条，
派发这两个通知码时同样要把 `ctrlId` 一起写进分支条件。

**胶囊的 ctrlId 编号空间够用**：`kIdTagChipBase = 1050`，第 i 枚取 `1050 + i`，
布局头文件里为它留了 `[1050, 1099]` 共 50 个号（`ContactLayout.h:45-47`），
本功能上限 10 个标签，绰绰有余。

**标签区封顶 3 行、超出用滚动容器**：按 UI 约定第 1 条与第 2 条，
这里要**复用 balloonui 的 `DuiScrollView`**，沿用它内置的自动隐藏滚动条行为，
不要为标签区手写一份自绘滚动。`ContactTagFlow` 作为 `DuiScrollView` 的内容控件放进去，
它本身的换行排布逻辑不用改。

**增删标签后要重新布局**：调用现成的 `RelayoutContactBody(root)`
（`ContactLayout.h:122`），它会对整棵客户区控件树重跑一次布局，让新塞入或删除的
胶囊立即生效。

### 7.3 数据层

`ContactModel` 已有 `TagCount()` / `Tag(index)` / `AddTag()` / `RemoveTag()`
（`ContactModel.h:126-139`），本期需要补上：

- 用一份完整列表整体替换（对应服务端应答回带的 `tags`，以及从 1201 灌入）；
- 修改指定下标的标签文本（对应就地编辑提交）；
- 判定某个文本是否与已有标签重复（不区分大小写），供 §7.1 的重复处置使用。

去重、合并、空串处置这几条规则**要放在纯函数里**，不要写在窗口的消息处理中 ——
它们是本功能最容易出错、也最值得单测的部分，混在窗口代码里就测不了。

协议收发放在 `Source/net/` 下，与 `FavoriteProtocolClient` 同形。

## 10. 决策记录

| # | 决策 | 取舍理由 |
| ---: | --- | --- |
| 1 | **标签是单向的**：一行记录的含义是「A 给 B 贴了一个标签」，只影响 A 这一侧的显示 | 与既有的联系人备注名同构。双向会让标签从「私人备忘」变成「公开评价」，用户会因此不敢用；双向还要额外定义所有权（谁能改）、删除权限与推送通道。本仓库同类数据（`t_contact_remark` / `t_starred` / `t_favorite` / `t_blacklist`）全是单向形态，不在本功能上开先例 |
| 2 | **一行一个标签**，不把整串标签打包成逗号分隔的字符串存进一列 | 打包会把「按标签筛人」这条路堵死：拼在一起的串不可索引，只能全表扫描再在内存里切串。去重与长度校验也会失去数据库这一层兜底 —— 主键的唯一性本来就能挡住重复标签 |
| 3 | **取编号 1217** | 1200 段在用的是 1201 / 1202 / 1209 / 1213 / 1215 / 1216，作废不可复用的是 1203–1208 / 1210 / 1211 / 1212 / 1214，1216 是当前最大的在用编号。特别地，1210 曾是 `cmd_set_friend_tags`，虽然语义最接近也**不能复用** —— 存量客户端仍可能发这个号 |
| 4 | **整份覆盖语义**：请求带完整列表，空数组表示清空，增改删共用一条命令 | 三种操作走同一条代码路径；不存在两个请求乱序到达导致状态错乱（后到的那份就是最终状态）；重复提交天然幂等。代价是多端并发编辑时后写覆盖先写，与备注名的处置一致，可以接受 |
| 5 | **应答回带 `userid` 与服务端归一后的最终列表**；失败时回带服务端当前实际存着的列表 | 客户端是乐观更新，多条请求在途时不带 `userid` 就分不清哪一条失败、回滚会退错人。回带归一后的列表而不是原样回带请求，是因为归一可能改变内容（去空白、去重），客户端要以服务端为准。失败时回带真实列表，客户端才有办法把界面对回去 |
| 6 | **标签随 `cmd_get_contacts`(1201) 一起下发**，在 `contacts[]` 元素上加 `tags` 数组，一律写出不做「空则省略」的优化，不新增读取命令 | 打开联系人资料对话框的前提是通讯录已经拉到，随通讯录下发就够了，再加一条读命令是多余往返。一律写出是为了让客户端只有一条解析路径 —— 与同一段代码里 `remark` 的既有处置一致 |
| 7 | **上限：单个标签 16 字符、每个联系人 10 个标签** | 16 是按界面宽度算出来的：胶囊宽度是「36 像素 + 文字宽」，标签区可用 380 像素，32 个汉字的胶囊约 420 像素、一整行都放不下，必然被省略号截断；16 字约 228 像素，稳妥。10 配合「标签区封顶 3 行、超出用滚动容器」。**清空操作不受条数上限约束**，否则存量超限的用户连删都做不了 |
| 8 | **只为条数超限新增 `error_code_tag_limit`(211)**，单条超长归到已有的 `error_code_bad_request` | 单条超长在正常路径下已被客户端输入框的最大长度从源头挡住，服务端那道校验是兜底，用户撞不到，给专码也没有对应的提示文案。条数达上限则是用户正常操作会真实撞上的情况（贴到第 11 个），界面要给一句明确提示，值得专码 |
| 9 | **本期不新增主动推送**，多端靠下次拉通讯录同步 | 与备注名、收藏、特别关注当初的处置一致。**将来要做也绝不能借用 `cmd_user_info_changed_notify`(1108)** —— 那条推送的语义是「某联系人的资料变了」，内容是所有人共享的，把只属于一个人的标签塞进去，会让所有收到推送的人都误以为该联系人资料发生了变更 |
| 10 | **修改标签用点胶囊文字就地编辑**，不弹独立窗口；修改时清空视为删除、新增时空白视为取消、重复则合并 | 与同一个对话框里备注名行的就地编辑、主面板的个性签名编辑一致。为一个 16 字的短词单独弹窗，用户要多点两次还要挪视线。三条空值 / 重复的处置都遵循「按用户明显的意图办，不要弹提示跟用户较劲」，其中「重复则合并」与服务端归一规则得到的是同一个结果 |
| 11 | **标签胶囊维持现有的自绘控件，只做最小扩展**（文字区可点击、自定义通知码另开取值段） | `TagChip` 已存在且工作正常，本期只缺「文字区可点击」这一项能力，属最小扩展而非新起炉灶。另开取值段是为了减少与同对话框内其它控件的通知码撞号；即便另开了，派发时该带的 `ctrlId` 仍然要带 |

  描述的边界状态。本期不做迁移脚本，需要时另议。
