# 「联系人标签」接入方案与开发计划

> 在联系人资料对话框里给同事贴短词标签（「设计」「外包」「三期项目」之类），
> 用来补足组织架构表达不了的那部分关系。标签是**单向**的：只影响贴标签的人自己看到的
> 内容，被贴的人既看不到也不受影响。
>
> 本文写于 2026-08-13，所列代码位置均已核对。

---

## 1. 背景与目标

企业版的通讯录直接来自组织架构（`t_department` / `t_department_member`），一家公司里
所有同事互相可见。这带来一个新问题：通讯录很长，而部门与职务是公司统一定义的，
表达的是「这个人在公司里是什么角色」，**表达不了「这个人跟我是什么关系」**。

现有的联系人备注名（`cmd_set_friend_remark`，1209）已经是私人视角的信息，但它是
**单值**的 —— 一个人只能有一个备注名，写了「设计组组长」就写不下「三期项目对接人」。
用户真正需要的是可以并列的若干个短词。

目标：让每个人能给通讯录里的同事贴任意几个短标签，标签只属于贴的人自己，
在联系人资料对话框里增删改，随通讯录一起读回来。

**不在本期范围内**：按标签筛选联系人（表结构为此留了余地，界面本期不做）、
标签的颜色与图标、给群或群成员贴标签、多端实时同步。

## 3. 数据模型与表结构

### 3.1 新建 `t_contact_tag`，一行一个标签

实际建表语句（`flamingoserver/table_mysql.sql`）：

```sql
//联系人标签表（企业版）：一行 = f_userid 给 f_target_userid 贴的一个标签（形如"设计""外包"）。
//与 t_contact_remark 完全同构，同样是<单向>的 —— 只影响"本人看对方"这一侧的显示，
//对方看不到也不受影响，故主键的第一列是 f_userid。
//一行只存<一个>标签，不把多个标签打包成逗号串：打包串既没法按标签检索，
//也会让"同一个标签重复添加"要靠字符串比对去重。
//客户端一次提交某联系人的完整标签列表，服务端整份覆盖（先删后插），空列表即清空。
CREATE TABLE IF NOT EXISTS  t_contact_tag  (
         f_userid         bigint(20) NOT NULL COMMENT '标签归属用户userid（谁贴的）',
         f_target_userid  bigint(20) NOT NULL COMMENT '被贴标签的联系人userid（贴给谁）',
         f_tag            varchar(16) NOT NULL DEFAULT '' COMMENT '标签文本，去掉首尾空白后的内容',
         f_order          int(10) NOT NULL DEFAULT 0 COMMENT '同一联系人下的显示顺序，值小者靠前，从0起算',
         f_update_time    bigint(20) NOT NULL DEFAULT 0 COMMENT '最近一次整份覆盖的时间(Unix毫秒)',
         PRIMARY KEY ( f_userid, f_target_userid, f_tag ),
         KEY  idx_user  ( f_userid )
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8
```

**索引**：与 `t_contact_remark` 同形，另建了 `KEY idx_user (f_userid)`，它与主键
`(f_userid, f_target_userid, f_tag)` 的最左前缀重复，主键本身已能服务「取某人给某个联系人
贴的全部标签」与「取某人贴过的全部标签」两种查询。没有建按标签反查的 `(f_userid, f_tag)`
索引：本期界面不做按标签筛选，日后要做时再加。

### 3.2 `f_order` 的语义

`f_order` 记录标签在界面上的先后次序，从 0 起连续递增，取值范围是 `[0, 9]`（受
每个联系人 10 个标签的上限约束）。它不参与主键，只用于读取时排序：
`ORDER BY f_order ASC`。整份覆盖写入时按请求里的数组下标重新赋值，因此这一列
永远与用户在界面上看到的顺序一致，不会出现空洞。

### 3.3 三处建表定义都要改，漏一处就有一套库跑不起来

| 文件 | 改什么 |
| --- | --- |
| `flamingoserver/table_mysql.sql` | MySQL 建表语句（**唯一手写的一份**） |
| `flamingoserver/table_sqlite.sql` | 由脚本生成 |
| `flamingoserver/sqliteapi/SqliteSchema.cpp` | 由脚本生成（内嵌建表语句 + 表名清单 + 列清单三处） |

后两者**不得手改**：改完 `table_mysql.sql` 后执行 `python tools/gen_table_sqlite.py`
重新生成（见开发约定文档「Protocol & data references」）。当前部署跑的是 SQLite
（`flamingoserver/etc/chatserver.conf` 的 `dbtype=sqlite`），这一步不能漏。

### 3.4 `f_tag` 必须登记进 `NOCASE_COLUMNS`，否则两个后端行为不一致

生成脚本 `flamingoserver/tools/gen_table_sqlite.py:43` 有一张 `NOCASE_COLUMNS` 表，
列在里面的文本列会在 SQLite 侧显式加 `COLLATE NOCASE`。原因是两个后端的默认行为相反：

- MySQL 侧建表带 `DEFAULT CHARSET=utf8`，默认排序规则 `utf8_general_ci` **不区分大小写**；
- SQLite 的文本比较默认 `BINARY`，**区分大小写**。

标签要做不区分大小写的去重（见 §5.3），而去重最终是靠主键 `(f_userid,
f_target_userid, f_tag)` 的唯一性兜底的。若不登记，同一份请求在 MySQL 上
`Design` 与 `design` 会因主键冲突只落一行、在 SQLite 上却会落两行 —— 同一套代码
在两种部署下得到不同结果，且只有换库时才暴露。

因此本功能必须同时改脚本：

```python
NOCASE_COLUMNS = set([
    ('t_user', 'f_username'),
    ('t_user', 'f_mail'),
    ('t_admin', 'f_email'),
    ('t_enterprise', 'f_name'),
    ('t_contact_tag', 'f_tag'),   #标签按不区分大小写去重，两个后端须一致
])
```

改完脚本后要**重新生成**一次 SQLite 那两份文件，生成物里应能看到
`f_tag VARCHAR(16) COLLATE NOCASE NOT NULL DEFAULT ''`。

### 3.5 长度上限：客户端按字符计，服务端按字节计

`varchar(16)` 在 MySQL 的 utf8 字符集下是 **16 个字符**（一个汉字算一个），
SQLite 则根本不约束长度。实现中两端的判定口径不同：

- **客户端按字符数**：标签输入框 `SetMaxLength(kContactTagMaxLen)`（16，
  `Source/UI/BalloonContact/ContactTagModel.h`）从源头限制，提交前 `DecideTagAdd` /
  `DecideTagEdit` 再按 16 个字符判一次超长（粘贴等路径才会走到）。
- **服务端按字节数**：服务端不解析 UTF-8，`ContactTagManager::setTags` 按
  `std::string::size()` 与 `kMaxContactTagBytes` 比较（`chatserversrc/ContactTagManager.h`，
  取 `kMaxContactTagChars`（16）× 3 = 48 字节，口径与备注名的 `kMaxContactRemarkBytes` 一致）。
  utf8 下一个汉字占 3 字节，48 字节正好是 16 个汉字，因此 16 个汉字放行、17 个汉字被拒。
- **已知的宽松之处**：纯 ASCII 标签写满 48 字节就是 48 个字符，超过列宽 `varchar(16)`，
  MySQL 侧会截断到 16 个字符（严格模式下报错）。正常路径下客户端已按 16 个字符拦住，
  只有绕过客户端的请求才会走到这里；标签的实际用法是中文短词，按字节判在实际使用中够用。

## 4. 协议设计

### 4.1 新增 `cmd_set_contact_tags = 1217`

1200 段现状（核对 `chatserversrc/Protocol.h:108-128`）：

| 状态 | 编号 |
| --- | --- |
| 在用 | 1201、1202、1209、1213、1215、1217 |
| 作废、不得复用 | 1203–1208、1210、1211、1212、1214、1216 |
| 空闲 | **1218 起** |

取号时 1216（`cmd_set_starred`）是段内最大的在用编号，故本功能取 **1217**。1216 其后随特别关注并入会话的消息提醒模式而作废，编号留空不复用。

### 4.2 请求与应答

**设置某个联系人的标签** `cmd_set_contact_tags`（1217）：

→ 请求：

```json
{
  "userid": "100009",
  "tags": ["设计", "三期项目", "外包"]
}
```

← 成功应答：

```json
{
  "code": 0, "msg": "ok",
  "userid": "100009",
  "tags": ["设计", "三期项目", "外包"]
}
```

← 失败应答（以标签条数超限为例）：

```json
{
  "code": 211, "msg": "tag count limit reached",
  "userid": "100009",
  "tags": ["设计", "三期项目"]
}
```

字段说明：

- `userid`：被贴标签的联系人 userid。字段名与 `cmd_set_friend_remark`（1209）一致
  —— 标签与备注名是同一类数据、落在同一种表形态上，两条命令的请求字段应当叫同一个名字。
- `tags`：**该联系人在本人视角下的完整标签列表**，不是增量。空数组 `[]` 表示清空。
- 应答里的 `tags` 是**服务端归一并落库之后的最终结果**（归一规则见 §5.3），
  不是把请求原样回带。客户端拿它覆盖本地那一份，界面就与服务端一致了。
- **失败时 `tags` 回带的是服务端当前实际存着的列表**，客户端据此把界面对回真值。
  这一条是有意为之：用户在界面上已经改了（乐观更新），请求失败若不告诉客户端
  真实状态，界面会一直显示一份服务端并不认可的内容。

### 4.3 `cmd_get_contacts`（1201）应答里增加 `tags`

在 `contacts[]` 的每个元素上加一个 `tags` 数组，与 `remark` 并列：

```json
"contacts": [
  { "userid": "100009", "username": "10010002", "nickname": "江屿白",
    "presence": 1, "clienttype": 1,
    "remark": "设计组组长",
    "tags": ["设计", "三期项目"] }
]
```

- **一律写出，不做「空则省略字段」的优化。** 没有标签时写 `[]`。这与同一段代码里
  `remark` 的既有处置一致（`chatserversrc/ContactsProtocol.cpp:78-81` 的注释写明了
  同样的理由）：客户端只需要一条解析路径，`tags` 有无与「标签被清空」在显示上
  本就是同一种效果，不必用字段有无来区分。
- 顺序按 `f_order` 升序，与用户在界面上看到的顺序一致。
- **不新增读取命令。** 标签只在联系人资料对话框里显示，而打开该对话框的前提是
  通讯录已经拉到，因此随 1201 一起下发就够了，再加一条「拉某人的标签」是多余往返。
- 老客户端读到多出来的字段会忽略，不影响兼容。

### 4.4 新增错误码 `error_code_tag_limit = 211`

联系人域 200–299 的现状（核对 `chatserversrc/Protocol.h:516-528`）：200、202、204、
209、210 在用，201、203、205、206、207、208 作废留空；本功能取当时空闲的 **211**。

### 4.5 本期不新增主动推送

A 设备改了标签，B 设备要到下次拉通讯录（重新登录 / 断线重连）时才看到，
与备注名、收藏、特别关注当初的处置一致。

> **将来若要做多端同步，不得借用 `cmd_user_info_changed_notify`（1108）。**
> 那条推送的语义是「某个联系人的资料变了」，推送的内容是**所有人共享**的信息
> （昵称、头像、签名等），收到的人都会据此刷新自己看到的那个联系人。
> 标签只属于一个人，塞进这条推送会让所有收到的人都误以为该联系人资料发生了变更，
> 进而刷出错误的内容。正确的做法是另开一条只发给标签归属者其他在线设备的推送，
> 取 1200 段的下一个空闲编号。

## 5. 限制与校验

### 5.1 两个上限

| 上限 | 取值 | 依据 |
| --- | --- | --- |
| 单个标签长度 | 16 个字符（客户端）；服务端按 48 字节判定（§3.5） | 见下方推导 |
| 每个联系人的标签数 | 10 个 | 配合「标签区封顶 3 行、超出用滚动容器」 |

**16 字符是按界面宽度算出来的**，不是随手取的整数：

- 胶囊的理想宽度公式在 `Source/UI/BalloonContact/TagChip.cpp:129-134`：
  `左内边距 10 + 文字宽 + 文字与「×」间距 4 + 「×」字形宽 12 + 右内边距 10`，
  即 **36 像素 + 文字宽**。
- 取值时标签区可用宽度是 **380 像素**：对话框客户区宽 420，根容器左右内边距各 20
  （`ContactLayout.cpp` 内嵌 XML 的 `padding="20,18,20,18"`）。2026-10-04 起客户区加宽为 600
  （`Source/UI/BalloonContact/ContactLayout.h` 的 `kContactBodyWidth`），可用宽度随之为 560 像素。
- 胶囊字号 12 像素，一个汉字约占 12 像素宽。32 个汉字的胶囊约
  `36 + 32 × 12 = 420` 像素，**比整行可用宽度还宽**，必然被省略号截断，等于用户
  打了字却看不到。16 个汉字约 `36 + 16 × 12 = 228` 像素，占一行的六成，稳妥。

两个上限在服务端是带注释的具名常量（`ContactTagManager.h` 的 `kMaxContactTagChars` /
`kMaxContactTagBytes` / `kMaxContactTagCount`），客户端是 `ContactTagModel.h` 的
`kContactTagMaxLen` / `kContactTagMaxCount`，不写裸数字（开发约定文档代码规范第 2 条）。
客户端标签输入浮层里的输入框用 `SetMaxLength(kContactTagMaxLen)` 从源头限制，
与备注名行 `SetMaxLength(32)` 的既有写法一致（`BalloonContactWindow.cpp`）。

### 5.2 校验清单

| 校验项 | 不通过时返回 |
| --- | --- |
| `userid` 缺失、非数字或不为正 | `error_code_bad_request`(3) |
| `tags` 缺失或不是 JSON 数组 | `error_code_bad_request`(3) |
| 数组元素不是字符串 | `error_code_bad_request`(3) |
| 目标用户是本人 | `error_code_bad_request`(3) |
| 单个标签归一后超过 48 字节（`kMaxContactTagBytes`，§3.5） | `error_code_bad_request`(3) |
| 目标用户不存在 | `error_code_not_found`(7) |
| 目标用户不在同一企业 | **未实现**。方案原定回 `error_code_not_friend`(202)，`ChatSession::onSetContactTags` 只要求目标用户存在、不校验是否同一企业（口径与备注名相同） |
| 归一后条数超过 10 | `error_code_tag_limit`(211) |

**单条超长为什么不给专门的错误码**：正常路径下客户端已经用输入框的最大长度
从源头挡住了，服务端这道校验是兜底，用户在界面上撞不到它，给它一个专码
客户端也没有对应的提示文案可写。而**条数达到上限是用户正常操作会真实撞上的**
情况（贴到第 11 个），界面要给一句明确的「最多只能贴 10 个标签」，
值得一个专码来区分。

### 5.3 服务端归一规则

服务端收到 `tags` 后，按下列顺序处理，**处理完的结果既是落库的内容、也是应答
回带的内容**：

1. 逐条去掉首尾空白字符；
2. 丢弃处理后为空串的项；
3. **不区分大小写去重**，保留首次出现的那一条，并保留它的原始大小写
   （用户输入 `Design` 就存 `Design`，后面再来一个 `design` 直接丢掉）；
4. 保持请求里的先后次序，按下标依次写入 `f_order`（0、1、2……）。

去重保留「首次出现者的原始大小写」而不是统一转成小写：标签是给人看的文字，
用户特意打的大写不该被系统改掉。

### 5.4 清空不受条数上限约束

`tags` 为空数组时**跳过条数校验**直接放行。若不放行，历史上因上限调整或数据
迁移而超过 10 条的用户会陷入「加不了也删不掉」的状态 —— 想删就得提交一份新列表，
而任何一份超过 10 条的列表都会被上限挡回去。

由此带来一个需要知道的边界：存量 12 条的用户**不能只删一条变成 11 条**
（仍然超限、仍被拒绝），只能一次删到 10 条以内，或者直接清空重来。这是可以接受的，
因为超限状态本身只可能来自上限调整或人工改库，不是正常路径。

### 5.5 整份覆盖的写入方式

一次请求就是一次完整替换，服务端在同一个事务里做两步：删掉
`(f_userid, f_target_userid)` 下的全部现有行，再按归一后的列表逐条插入。
不做「算差集、只改变化的那几行」的优化 —— 单个联系人的标签最多 10 行，
差集算法带来的复杂度远大于它省下的那点写入量。

## 7. 客户端设计

### 7.1 交互设计

| 动作 | 行为 |
| --- | --- |
| 点胶囊的**文字区** | 在这枚胶囊的位置弹出单行输入浮层（`CTagEditPopup`，见 §7.2），盖住胶囊，带入当前文字并全选 |
| 点胶囊的**「×」** | 删除这枚标签 |
| 点「+ 添加标签」 | 在按钮的位置弹出空的输入浮层。标签已满 10 个时不显示这个按钮，原位置改为一行说明文字 |
| 浮层里按回车 / 浮层失去焦点（点了别处） | 提交 |
| 浮层里按 Esc | 取消，不提交 |

提交时由纯函数 `DecideTagAdd` / `DecideTagEdit`（`Source/UI/BalloonContact/ContactTagModel.h`）
判定，资料窗按结果执行：

- **修改时把内容全删光** —— 视为**删除该标签**。用户把字全删掉再确认，意图是明确的，
  此时再弹一句「标签不能为空」是在跟用户较劲。
- **修改后与原值等价**（去首尾空白、不区分大小写后相同）—— 不改也不提交。
- **新增时输入为空或全是空格** —— 视为**取消**，不添加任何东西，也不提示。
  用户点了「+」又改主意，不该被打断。
- **新增时与已有标签重复**（不区分大小写）—— 不添加，给一句轻提示「该标签已存在」。
  加进去会得到两枚一模一样的胶囊，而服务端归一时又会把它去掉，界面与服务端立刻不一致。
- **修改成与另一枚重复** —— **两枚合并**为一枚：被编辑的那枚删除，另一枚留在原位置，
  文字改为用户这次输入的写法（保留这次输入的大小写）。合并后的列表里没有重复项，
  服务端归一不会再改动它；客户端先合并是为了让用户立刻看到最终形态，而不是提交后界面
  才突然少一枚。
- **超长** —— 提示「标签最长 16 个字符」。输入框已限长，只有粘贴等路径才会走到。

改动一律走**乐观更新**：资料窗把改好的完整列表经 `FMG_MSG_SET_CONTACT_TAGS` 交给主面板
（`CBalloonContactWindow::CommitTagList`），主面板 `SetContactTags` 处理：与通讯录缓存
逐字相同则不发请求；当前不在线则把资料窗恢复为缓存值并提示「当前网络不可用，标签未能保存。」；
否则先改缓存、刷新资料窗，再发 `cmd_set_contact_tags`。应答（`OnSetContactTagsResult`）
无论成败都用回带的 `tags` 覆盖缓存：成功时是服务端归一后的最终列表，失败时是服务端当前
实际存着的列表；失败时另给提示（211 为「标签数量已达上限，未能保存。」，其余为
「标签未能保存，请稍后重试。」）。这与备注名的既有做法一致。

**为什么用盖在胶囊上的浮层而不是独立窗口**：输入框出现在被点的胶囊（或「+ 添加标签」
按钮）原来的位置上，视觉上就是那一枚原地变成了输入框；主面板的个性签名编辑
（`UI/BalloonMain/SignatureEditPopup`）是同一做法。为一个 16 字的短词单独弹一个窗口，
用户要多点两次、还要在两个窗口之间挪视线。

### 7.2 UI 实现要点

**标签胶囊维持现有的自绘控件，只做最小扩展。** 按开发约定文档 UI 约定第 2 条，
新增控件应优先复用 balloonui；但 `TagChip` 已经存在且工作正常，只需给它加
「文字区可点击」这一项能力，属于「子类化 / 最小扩展」而不是新起炉灶：

- `TagChip` 按落点发两个不同的自定义通知码：点在「×」热区内发 `DUIN_TAGCHIP_DELETE`，
  点在文字区内发 `DUIN_TAGCHIP_EDIT`（`Source/UI/BalloonContact/TagChip.h`）。
- **自定义通知码另开取值段**，不从 `balloonwjui::DUIN_CUSTOM + 1` 起算
  （开发约定文档 UI 约定第 4 条：`+1` 那一档已有十余个控件在用）；`TagChip` 取 `DUIN_CUSTOM + 50`、`+ 51`。
- **派发时把 `ctrlId` 写进分支条件本身**（`CBalloonContactWindow::OnDuiNotify` 同时判通知码
  与 `ctrlId` 落在 `[kIdTagChipBase, kIdTagChipBase + kContactTagMaxCount)` 内），不能进了分支
  再判。这个对话框里还有 `DuiComboBox`（分组下拉）、`DuiEdit`（备注名编辑框）等控件，
  它们各自的自定义码数值与本控件重合的概率很高。写错的症状是**点了没反应**：不报错、
  不崩溃、日志里什么都没有。

**输入浮层 `CTagEditPopup`**（`Source/UI/BalloonContact/TagEditPopup.{h,cpp}`）：新增与修改
共用这一个浮层，资料窗持有一个实例（`m_tagPopup`），并用 `m_editingTagIndex` 记住这次改的是
哪一枚（新增时为 `kTagIndexNone`）。

- 子类化 balloonui 的 `DuiPopupHost`（无边框 `WS_POPUP` 浮层，自带 Esc 与失焦关闭），内容是
  一个单行 `DuiEdit`：`SetMaxLength(kContactTagMaxLen)`、`SetShowBorder(true)`、
  `SetVerticalCenter(true)`。
- `OpenAt(屏幕矩形, ...)`：浮层左上角对齐被点控件的左上角（左侧外扩 6 像素），宽取
  「控件宽 + 12」与 150 的较大值，高取控件高与 24 的较大值；带入当前文字（新增时为空串）、
  取得焦点并全选。
- 提交与取消：回车时输入框发 `DuiEdit::DUIN_EDIT_ENTER`（连同 `ctrlId` 一起判），浮层提交后
  以「程序化」原因关闭；失去焦点时 `DuiPopupHost` 以 `ReasonLostFocus` 关闭，视为提交；
  Esc 由 `DuiPopupHost` 拦下、以 `ReasonEscape` 关闭，不提交。`m_handled` 保证一次打开只提交
  一次（回车提交后浮层隐藏又会触发一次失焦）。
- 浮层只把输入框文字经 `SetCommitCallback` 注册的回调交回资料窗，不做任何判定；判定见 §7.1。
- 以 `NULL` 为所有者显示（`Show(anchor, NULL)`）：有所有者的 `WS_POPUP` 窗口 `GetParent`
  返回所有者，输入框的回车通知会被发到资料窗而不是浮层（与开发约定文档 UI 约定第 11 条
  是同一个原因）。

**胶囊的 ctrlId 编号空间够用**：`kIdTagChipBase = 1050`，第 i 枚取 `1050 + i`，
布局头文件里为它留了 `[1050, 1099]` 共 50 个号（`ContactLayout.h`），
本功能上限 10 个标签，绰绰有余。

**标签区封顶 3 行、超出用滚动容器**：复用 balloonui 的 `DuiScrollView`（UI 约定第 1、2 条），
实际是 `ContactLayout.cpp` 里的子类 `ContactTagScrollView`，只把视口底色从基类的浅灰改成
与客户区一致的白色。`ContactTagFlow` 作为它的内容控件，换行排布逻辑不变。

**增删标签后的重建与重排**（`CBalloonContactWindow::RebuildTags`）：清空流式容器，按模型重建
各枚胶囊与末尾的「+ 添加标签」按钮（满额时为说明文字）；`SyncContactTagArea` 重算标签行数
与滚动范围，`ApplyBodyHeight` 按新行数调整窗口高度并整树重排；最后对滚动视口与流式容器
依次 `ForceLayout`。后一步不能省：行数已封顶或只换了几枚胶囊时它们的矩形没变，`SetRect`
会直接返回，新内容拿不到矩形（开发约定文档 UI 约定第 12 条）。

### 7.3 数据层

## 10. 决策记录

| # | 决策 | 取舍理由 |
| ---: | --- | --- |
| 1 | **标签是单向的**：一行记录的含义是「A 给 B 贴了一个标签」，只影响 A 这一侧的显示 | 与既有的联系人备注名同构。双向会让标签从「私人备忘」变成「公开评价」，用户会因此不敢用；双向还要额外定义所有权（谁能改）、删除权限与推送通道。本仓库同类数据（`t_contact_remark` / `t_favorite` / `t_blacklist`）全是单向形态，不在本功能上开先例 |
| 2 | **一行一个标签**，不把整串标签打包成逗号分隔的字符串存进一列 | 打包会把「按标签筛人」这条路堵死：拼在一起的串不可索引，只能全表扫描再在内存里切串。去重与长度校验也会失去数据库这一层兜底 —— 主键的唯一性本来就能挡住重复标签 |
| 3 | **取编号 1217** | 取号时 1200 段在用的是 1201 / 1202 / 1209 / 1213 / 1215 / 1216，作废不可复用的是 1203–1208 / 1210 / 1211 / 1212 / 1214，1216 是当时最大的在用编号（1216 其后也已作废，编号留空不复用）。特别地，1210 曾是 `cmd_set_friend_tags`，虽然语义最接近也**不能复用** —— 存量客户端仍可能发这个号 |
| 4 | **整份覆盖语义**：请求带完整列表，空数组表示清空，增改删共用一条命令 | 三种操作走同一条代码路径；不存在两个请求乱序到达导致状态错乱（后到的那份就是最终状态）；重复提交天然幂等。代价是多端并发编辑时后写覆盖先写，与备注名的处置一致，可以接受 |
| 5 | **应答回带 `userid` 与服务端归一后的最终列表**；失败时回带服务端当前实际存着的列表 | 客户端是乐观更新，多条请求在途时不带 `userid` 就分不清哪一条失败、回滚会退错人。回带归一后的列表而不是原样回带请求，是因为归一可能改变内容（去空白、去重），客户端要以服务端为准。失败时回带真实列表，客户端才有办法把界面对回去 |
| 6 | **标签随 `cmd_get_contacts`(1201) 一起下发**，在 `contacts[]` 元素上加 `tags` 数组，一律写出不做「空则省略」的优化，不新增读取命令 | 打开联系人资料对话框的前提是通讯录已经拉到，随通讯录下发就够了，再加一条读命令是多余往返。一律写出是为了让客户端只有一条解析路径 —— 与同一段代码里 `remark` 的既有处置一致 |
| 7 | **上限：单个标签 16 字符、每个联系人 10 个标签**（服务端对单个标签按 48 字节判定，见 §3.5） | 16 是按界面宽度算出来的：胶囊宽度是「36 像素 + 文字宽」，取值时标签区可用 380 像素，32 个汉字的胶囊约 420 像素、一整行都放不下，必然被省略号截断；16 字约 228 像素，稳妥。10 配合「标签区封顶 3 行、超出用滚动容器」。**清空操作不受条数上限约束**，否则存量超限的用户连删都做不了 |
| 8 | **只为条数超限新增 `error_code_tag_limit`(211)**，单条超长归到已有的 `error_code_bad_request` | 单条超长在正常路径下已被客户端输入框的最大长度从源头挡住，服务端那道校验是兜底，用户撞不到，给专码也没有对应的提示文案。条数达上限则是用户正常操作会真实撞上的情况（贴到第 11 个），界面要给一句明确提示，值得专码 |
| 9 | **本期不新增主动推送**，多端靠下次拉通讯录同步 | 与备注名、收藏、特别关注当初的处置一致。**将来要做也绝不能借用 `cmd_user_info_changed_notify`(1108)** —— 那条推送的语义是「某联系人的资料变了」，内容是所有人共享的，把只属于一个人的标签塞进去，会让所有收到推送的人都误以为该联系人资料发生了变更 |
| 10 | **修改标签用点胶囊文字、在胶囊位置弹出输入浮层**（`CTagEditPopup`），不弹独立窗口；修改时清空视为删除、新增时空白视为取消、重复则合并 | 与主面板的个性签名编辑（`SignatureEditPopup`）同一做法，输入框出现在被点的胶囊原位置。为一个 16 字的短词单独弹窗，用户要多点两次还要挪视线。三条空值 / 重复的处置都遵循「按用户明显的意图办，不要弹提示跟用户较劲」；「重复则合并」在客户端先合并成没有重复项的列表，服务端归一不会再改动它 |
| 11 | **标签胶囊维持现有的自绘控件，只做最小扩展**（文字区可点击、自定义通知码另开取值段） | `TagChip` 已存在且工作正常，本期只缺「文字区可点击」这一项能力，属最小扩展而非新起炉灶。另开取值段是为了减少与同对话框内其它控件的通知码撞号；即便另开了，派发时该带的 `ctrlId` 仍然要带 |
