# 语音字幕方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-05
> 用途：记录 PC 客户端「语音字幕」的整体方案：录屏时把说话声识别成字幕，录完后人工修改，再生成到录制文件中；屏幕共享时把每个人的发言实时显示为字幕。内容包括已确认的决定、识别引擎评测结果、DLL 工程拆分、服务端与管理端改动和分期计划。后续每步开工前据此细化，收尾后回填实际结果。
> 与 `docs/聊天字幕模式方案.md` 无关：那个功能是把聊天消息显示成桌面歌词式的字幕（代码在 `Source/UI/BalloonSubtitle/`）。为避免混淆，本功能在代码里统一叫 caption，界面上叫「语音字幕」。

---

## 1. 需求与范围

- **录屏**：录制时（或录完后）把声音识别成带时间的字幕草稿；用户在字幕编辑器里边看视频边改文字、调时间；改好后生成带字幕的视频。
- **屏幕共享**：共享过程中，每个人可以选择为自己的发言生成字幕，房间里的其他人在观看窗里看到「某某：……」。
- **轻量**：第三方库尽量少；字幕功能做成按需加载的独立 DLL，不用时不加载、不占内存，加载失败就不开启字幕，不影响主程序。
- **不在范围内**：Android 客户端；群语音 / 群视频通话里的字幕；把字幕上传服务器；翻译字幕。识别语言只有中文与英文（受模型限制），界面语言为日文、韩文时字幕仍是中英文。

## 2. 已确认的决定

2026-10-05 与用户逐项确认：

| # | 事项 | 决定 |
| --- | --- | --- |
| 1 | 识别引擎 | **sherpa-onnx + 中英带标点流式模型**（`sherpa-onnx-x-asr-480ms-streaming-zipformer-transducer-zh-en-punct-int8-2026-06-05`）。实时字幕与录制草稿共用这一个模型，录完后的重新识别也用它。依据是用户朗读录音上的评测，见第 3 节 |
| 2 | 字幕生成到录制文件的形式 | **硬字幕版与内嵌字幕轨版分别生成**，导出时勾选（可勾一项或两项）：硬字幕版「原名-字幕.mp4」重新编码；字幕轨版「原名-字幕轨.mp4」不重新编码，只把原画面与声音原样拷贝、再加一条可开关的字幕轨。另可导出同名 `.srt`。**原文件保留** |
| 3 | 共享时由谁识别 | **每个发言人在自己电脑上识别自己的话**，识别结果以文字发给房间里的其他人 |
| 4 | 共享时字幕由谁打开 | **每个人自己决定**：各自开关「为我的发言生成字幕」，互不影响 |
| 5 | 打包方式 | 字幕功能与识别组件一起封装成 DLL，**按需加载**，不影响主程序，**加载失败则不开启字幕**。拆成两个：功能 DLL `FlamingoCaption.dll`（字幕代码、sherpa-onnx、onnxruntime）与模型资源 DLL `FlamingoCaptionModel.dll`（只含模型资源，没有代码）。改代码只需更新前者 |
| 6 | 企业级开关 | 是否开启字幕功能由 **flamingoAdmin 后台按企业配置**，**默认开启** |
| 7 | 分发 | **两个 DLL 都随安装包发**；自动更新包照常带 `FlamingoCaption.dll`，`FlamingoCaptionModel.dll` 只在换模型时才放进更新包（更新包是整包覆盖的单个 zip，见 `docs/客户端自动更新方案.md` 决策三，不这样处理每次更新都会多约 140 MB） |
| 8 | 录屏何时识别 | **两种都支持**：录制选项里勾选「生成字幕」就边录边识别，录完即可编辑；没勾的录像以及任意 MP4，都可以在字幕编辑器里事后识别 |
| 9 | 字幕编辑器的入口 | 录完提示里的「编辑字幕」，以及**录像列表**。录像列表就是另一路开发中的「录制管理」窗口（`docs/屏幕共享与录制方案.md` 11.6 节 F9，`FlamingoMedia/Record/RecordManagerWindow`），在它上面加「字幕状态」与「编辑字幕」，不另做窗口 |
| 10 | 录像列表的入口 | **录完提示**、**聊天窗录制按钮的下拉菜单**、**主面板菜单**（即 F8 已加的「录制管理」）；**托盘菜单不加** |
| 11 | 模型的加载方式（2026-10-06 确认） | **给 sherpa-onnx 打补丁，直接从模型 DLL 的内存加载**，不写缓存文件。sherpa-onnx 因此由脚本从固定版本的源码加补丁编译（见 4.2、第 13 节） |

方案作者据此定下的默认做法（用户未单独确认，有异议随时改）：

| # | 事项 | 默认做法 |
| --- | --- | --- |
| D1 | 导出窗口的勾选 | 第一次只勾硬字幕版，之后记住上次的勾选 |
| D2 | 「为我的发言生成字幕」 | 第一次默认关闭，之后记住上次的选择；每个观看者都能在自己的观看窗里隐藏字幕 |
| D3 | 录制选项「生成字幕」 | 第一次默认勾选，之后记住；「为电脑声音生成字幕」默认不勾。**2026-10-06 用户调整**：去掉「为电脑声音生成字幕」，勾了「生成字幕」就识别麦克风与电脑声音两路（见 14.12） |
| D4 | 解码方式与热词 | 用贪心解码，不依赖热词；另做「自动替换表」，把用户登记的常见误识别（如 Sclight → SQLite）自动替换（依据见 3.3） |
| D5 | 企业开关关闭时 | 隐藏全部字幕入口，正在进行的识别停止，收到的字幕帧不显示；已经打开的编辑器与正在进行的导出允许完成 |
| D6 | 功能 DLL 加载失败时 | 记一条日志，所有字幕入口不显示；观看端同样不显示别人的字幕（字幕的绘制也在功能 DLL 里），与「加载失败则不开启字幕」一致 |

## 3. 第 0 期：识别引擎评测（已完成）

评测用的是一个带界面的 Python 对比程序（实时识别页、整段对比页），没有进版本库。测试机为 i7-9750H（6 核 12 线程）。

### 3.1 候选

流式：sherpa-ncnn 中英双语小模型（2023，原方案推荐）、sherpa-onnx 流式中文小模型 CTC（2025-04）、sherpa-onnx 流式中文（2025-06）、sherpa-onnx 流式中英带标点（2026-06）。非流式：SenseVoice（2025-09）、Paraformer 中文（2025-10）、中英带标点非流式版（2026-06）、中文小模型 CTC（2025-07）、whisper.cpp base / small / large-v3-turbo。

### 3.2 用户朗读录音上的准确率（据实证）

用户朗读 `docs/SQLite本地数据库模式方案.md` 的几段，录了两段（134 秒、168 秒）。参考文本以原文为底稿，朗读时临场改读的地方以多数模型一致的结果为准，代码标识符按朗读的念法书写。错误率中文按字、英文按词计（连续的单个字母合并为一个词，如把 etc 念成 E T C）。

| 模型 | 类型 | 体积 | 第一段 | 第二段 | 第二段术语认对次数（SQLite 6 / MySQL 5 / busy timeout 1 / Manager 4 / chatserver 1） |
| --- | --- | --- | --- | --- | --- |
| **sherpa-onnx 中英带标点 2026** | 流式 | 169 MB | **3.9%** | **6.2%** | 0 / 5 / 1 / 4 / 1 |
| 中英带标点 2026 非流式版 | 非流式 | 175 MB | 4.8% | 5.3% | 0 / 5 / 1 / 4 / 1 |
| SenseVoice | 非流式 | 237 MB | 15.2% | 13.0% | 0 / 0 / 0 / 3 / 0 |
| 中文小模型 CTC 2025 | 非流式 | 63 MB | 15.4% | 15.3% | 0 / 0 / 0 / 0 / 0 |
| Paraformer 2025 | 非流式 | 238 MB | 19.1% | 18.0% | 0 / 0 / 0 / 0 / 0 |
| sherpa-ncnn 中英小模型 | 流式 | 54 MB | 21.6% | 22.3% | 0 / 0 / 0 / 0 / 0 |
| sherpa-onnx 中文 2025 | 流式 | 167 MB | 25.6% | 21.4% | 0 / 0 / 0 / 0 / 0 |
| sherpa-onnx 中文小模型 CTC | 流式 | 26 MB | 23.0% | 24.6% | 0 / 0 / 0 / 0 / 0 |

- 2026 流式模型的错误率是 sherpa-ncnn 的三分之一到五分之一，技术术语优势尤其明显。非流式版并不稳定地更好，所以不另带模型做录完后的重新识别。
- whisper.cpp 被排除：CPU 空闲时 small、turbo 的实时率分别为 2.9 与 4.1（跟不上实时）；即使是 base，在实时页里每句也要等 4～5 秒才出字（据推测因为它每次固定按 30 秒窗口计算）；turbo 在模型自带的测试音频上夹杂繁体并重复了一句。在用户录音上的测试因机器被其他编译任务占满而中止，未取得结果。

### 3.3 热词（据实证，第 0 期评测结果，原始日志未保留）

| 配置 | 第一段 | 第二段 | SQLite 认对次数 |
| --- | --- | --- | --- |
| 贪心解码 | 3.9% | 6.2% | 0/4、0/6 |
| modified_beam_search | 4.8% | 5.1% | 0/4、0/6 |
| beam + 热词，分值 1.5 | 4.5% | 5.7% | 1/4、1/6 |
| beam + 热词，分值 3.0 | 5.1% | 5.5% | 1/4、1/6 |

热词只让 SQLite 多认对 1 次，整体错误率时好时坏，所以采用贪心解码加自动替换表（第 2 节 D4）。热词要求从模型的 `bpe.model` 导出 `bpe.vocab`（已验证可行），留作以后的可选项。

### 3.4 速度与资源

- 用户实测（截图 `snapshots/shibie2.png`，1 线程）：实时率 0.377，平均占整机 CPU 2.5%，进程内存约 350 MB（含 Python 自身），**模型加载约 19 秒**。
- 对比：sherpa-ncnn 小模型 1 线程实时率 0.169、CPU 1.2%、加载 0.28 秒（`snapshots/shibie1.png`）；它开多线程反而更慢。
- 用户录音上的那轮测试期间有 6 个编译进程占满 CPU，那一轮的耗时数据作废；空闲时的完整速度复测列入第 0 期剩余项 0g。

### 3.5 截图里看到、要在产品里处理的现象

- 端点有时切在标点之前，下一条以「。」「，」开头：生成字幕条时把行首标点并回上一条。
- 一句话最长可到 20 秒、两行多：按字幕条规则（第 6.2 节）再切分。
- 模型输出可能是 `E T C` 这类逐字母的写法，替换表与查找替换要能处理。

### 4.1 FlamingoCaption.dll

- 新工程 `flamingoclient/FlamingoCaption/`，形态与 `FlamingoFileShare.dll` 相同：只导出一个工厂函数，工厂函数接收接口版本号、返回模块对象；自带一份静态链接的 balloonui；日志与界面文字经宿主接口交给 exe（`Translate` / `GetUiLanguage`，与 FlamingoMedia、FlamingoFileShare 的做法一致）。
- 四个配置都用静态运行库并定义 `WIN32`。**Debug 配置也用 `/MT`**（加 `/Od /Zi`），并链接 `balloonui_static` 的 Release 配置：官方只提供 Release 版的静态运行库静态库，`/MTd` 链接它会报 LNK2038（0a 实测，见 14.2）。
  - balloonui 的 Release 配置由工程里的 `CaptionLinkReleaseBalloonUi` 目标在链接前用 MSBuild 任务编出，再把产出的静态库加入链接输入（2026-10-09 起，由 `gen_caption_vcxproj.py` 生成）。最初用的是工程引用（`ProjectReference`）加 `SetConfiguration=Release`：单独编译本工程时有效，但通过解决方案编译时，MSBuild 按解决方案的配置给被引用工程指定配置，`SetConfiguration` 不生效，`Debug|x64` 解决方案因此链接到 balloonui 的 Debug 版，报 214 条 LNK2038 / LNK2001（2026-10-09 实测，`RuntimeLibrary` 为 `MTd_StaticDebug` 与 `MT_StaticRelease` 不匹配）。改用 MSBuild 任务后，单独编译与通过解决方案编译链接的都是同一份 Release 版静态库；Release 解决方案里这次调用与解决方案自身编译 balloonui 的全局属性相同，只编一次。库路径取自紧接着调用的 `GetTargetPath` 目标：原生 C++ 工程的 `Build` 目标不返回产物路径，第一版只调用 `Build`，取到的路径为空，balloonui 没有进入链接，报 744 条 LNK2001（2026-10-09 实测）。
  - 验证（2026-10-09 实测，脚本与日志在 `tmp/clientbuild/verify_caption.ps1`、`verify_*.log`）：解决方案的 `Debug|x64`、`Debug|Win32`、`Release|x64` 重编本工程，以及单独重编本工程，四种方式都链接成功，链接的都是对应平台的 `third-party\balloonui\Bin\Static\<平台>\Release\balloonui_static.lib`；`Release|x64` 解决方案里 balloonui 只编了一次；整个 `Debug|x64` 解决方案不再因本工程中断；修复前日志里的两条 LNK4098（默认库冲突）随之消失。在 Visual Studio 里编译据推测相同（MSBuild 任务在 IDE 内照常执行），尚未实测。
- 静态链接 sherpa-onnx（Apache-2.0）与 onnxruntime（MIT），只使用它们的 C 接口，满足本项目 C++11 的要求（这两个库自身的 C++ 标准只影响编译静态库那一步）。
- **加载时机**：exe 启动时不加载。只有企业开关为开、且用户第一次用到字幕功能时（打开字幕编辑器、勾选了「生成字幕」开始录制、打开「为我的发言生成字幕」、观看端收到第一条字幕帧）才加载。FlamingoMedia 经新增的 `IMediaHost::GetCaptionService()` 取用，触发 exe 按需加载；返回 NULL 表示不可用，调用方隐藏字幕入口。
- **卸载时机**：exe 退出时，在 FlamingoMedia 关闭之后卸载。
- 接口与 FlamingoMedia 相同，采用「版本号必须完全相同」的规则（`kApiVersion`）。

### 4.2 FlamingoCaptionModel.dll

- 纯资源 DLL：没有代码，只有 RCDATA 资源（encoder、decoder、joiner、tokens）和一个记录模型名称与版本的资源。由 `FlamingoCaption.dll` 用 `LoadLibraryExW(..., LOAD_LIBRARY_AS_DATAFILE | LOAD_LIBRARY_AS_IMAGE_RESOURCE)` 加载，`FindResource` / `LockResource` 取到模型在内存里的地址。资源所在的内存页要访问时才读进来，属于文件映射页，系统内存紧张时可以直接丢弃。
- 一个模型 DLL 供 32 位与 64 位共用：以数据文件方式加载时不区分架构，0b 实测 32 位进程读出 64 位模型 DLL 的资源，校验和完全一致（14.3）。
- encoder 以 onnxruntime 的 **ORT 格式**（预先做过 EXTENDED 级图优化）存入资源，decoder、joiner 保持 ONNX；转换在生成模型 DLL 时完成（14.3）。
- **从内存加载模型**：0b 验证了下面两种做法，用户 2026-10-06 选定第 1 种（第 2 节第 11 条）：
  1. **（选定）给 sherpa-onnx 打补丁，直接从内存加载**。sherpa-onnx 内部本来就能从内存建会话（`online-zipformer2-transducer-model.cc:84-88` 的 `InitEncoder(void* model_data, size_t len)`），但桌面版只走按路径加载，C 接口也只支持从内存读 tokens 与热词（`c-api.h:272`、`:396`）。原先设想沿用它给 Android、鸿蒙用的「资源管理器」模板（`online-recognizer.cc:225`、`:267-274`），那要在二十多个文件里补实例化；实际采用的是范围小得多的「内存文件登记表」：按名字登记一块内存，按路径加载模型的那几处先查登记表（改动清单见 14.3 第 4 条）。FlamingoCaption 用 `SherpaOnnxRegisterMemoryFile` 登记 encoder、decoder、joiner，tokens 用 `tokens_buf`，并指定 `model_type`。代价是每次升级 sherpa-onnx 都要重新合补丁。
  2. （未选）**先解压到本机缓存再按路径加载**：第一次使用时把资源写到 `%LOCALAPPDATA%` 下的缓存目录（按哈希校验，模型换版本后清理旧缓存）。不改 sherpa-onnx，代价是磁盘上多一份约 170 MB，第一次使用多等一两秒。
- 加载耗时与读文件的方式无关：0b 实测从内存加载与从磁盘按路径加载耗时相同（14.3）。缩短加载时间的办法见 5.3。

## 5. 识别服务

### 5.1 接口

`FlamingoCaption.dll` 对 FlamingoMedia 提供识别服务 `ICaptionService`：

- `Preload()`：在后台线程加载模型，立即返回；`GetState()` 查询未加载 / 加载中 / 可用 / 失败。
- `CreateStream(purpose, listener)`：建一路识别流（用途：录制麦克风、录制电脑声音、共享发言、事后识别）。多路流共用一份模型。
- `stream->PushPcm(const int16_t* mono48k, int samples, int64_t ptsMs)`：任意线程推入 48 kHz 单声道声音及其时间戳（录制时间轴或本机时钟），内部重采样到 16 kHz。模型还没加载完时先缓存（上限 60 秒），加载完后补识别，不丢声音。
- 回调（识别线程上调用，实现方自行转到 UI 线程）：`OnPartial(text)` 正在说的这句的中间结果；`OnFinal(startMs, endMs, text)` 一句定稿。
- `stream->Close()`。

### 5.2 内部

- 一条识别线程、1 个推理线程（实测 CPU 约 2.5%），线程优先级低于正常。0g 实测多线程不能加速流式识别（14.6），事后识别整段改为按静音分段、多路识别流并行。
- 端点规则沿用评测时的值：识别出字后静音 0.8 秒切句，没出字时静音 2.4 秒切，一句最长 20 秒。
- 定稿后依次做：行首标点并回上一条；按自动替换表替换；交给字幕条切分（6.2）。
- 没有任何识别流超过 5 分钟后卸载模型、释放内存（据推测常驻约 250 MB）。

### 5.3 加载慢的对策

0b 已把加载时间从约 8 秒降到约 1.9 秒（低负载；CPU 被占满时为 23 秒降到 5.3 秒），用了两项措施，都不需要改 sherpa-onnx：

- **配置里指定 `model_type = "zipformer2"`**：不指定时 sherpa-onnx 为了读模型类型会先把整个 encoder 多加载一遍（`online-transducer-model.cc:48-91`、`:164-167`）。
- **encoder 预先转成 ORT 格式**（见 4.2）。

其余做法照旧：

- **提前预加载**：打开录制选项且勾着「生成字幕」时、打开「为我的发言生成字幕」时、打开字幕编辑器或录制管理窗口时，立即调 `Preload()`。
- 加载期间界面显示「语音识别准备中」，声音照常缓存（5.1）。

## 6. 录屏字幕

### 6.1 录制时识别

- 录制选项新增「生成字幕」（默认值见 D3），勾选后识别麦克风与电脑声音两路（起初另有「为电脑声音生成字幕」，2026-10-06 按用户要求去掉，见 14.12）。企业开关关闭或功能 DLL 不可用时不显示。
- 据实证，录制的混音由写入线程按录制时间轴取出，暂停的时段不计时长（`FlamingoMedia/Record/RecordAudioMixer.h:5-6`）。在混音器取数据的地方增加分路旁路：把这一次取出的各路声音连同录制时间戳交给对应的识别流，字幕时间因此与视频严格对齐，暂停也不会错位。
- 麦克风一路的说话人记为本人；电脑声音一路记为「电脑声音」。
- 录制共享时：本人打开了「为我的发言生成字幕」就照常识别；其他人的字幕取自收到的字幕控制帧，按收到的时刻换算到录制时间轴（发送方在最终结果里带上这句的时长，接收方据此推算开始时刻）。没有开字幕的发言人没有字幕，编辑器里可以对整段做事后识别补上（不区分说话人）。
- 识别结果实时写入录像旁的草稿 `原名.mp4.caption.json`。录制管理窗口的重命名、删除要连带处理这个草稿文件（与 F9 协调）。

### 6.2 字幕数据与字幕条切分

- 每条字幕：开始、结束时刻（毫秒）、说话人、文字、来源（麦克风 / 他人 / 电脑声音 / 事后识别 / 手工添加）、是否改过。
- 草稿文件 `原名.mp4.caption.json`（UTF-8）：格式版本、对应的视频文件名与大小、字幕条列表、样式；编辑器自动保存。SRT 的导入与导出自己实现，不引入库。
- 切分规则：每行不超过约 18 个汉字（英文按宽度折算），最多 2 行，单条不超过 6 秒、不短于 0.8 秒，优先在标点处断开。数字定义为常量，第 1 期用单测固定。

### 6.3 事后识别

字幕编辑器里打开没有草稿的视频时，提供「识别字幕」：用 Media Foundation 的 Source Reader 解出声音，重采样后尽快送入识别流，显示进度，可以取消。已有草稿时提供「重新识别」（覆盖前确认）。

## 7. 字幕编辑器

- 位于 `FlamingoCaption.dll`，入口见第 2 节第 9、10 条。
- **左侧视频预览**：画面上叠加当前字幕，绘制代码与生成硬字幕用的是同一份，所见即所得；播放、暂停、跳转。播放用 Media Foundation 的 `IMFMediaEngine`（第 0 期 0e 验证能否嵌进窗口并精确跳转）。
- **下方时间轴**：每条字幕显示为一个色块，拖动两端调起止时间，拖动整块平移。
- **右侧字幕列表**：时间、说话人、文字；单击跳到该处播放，双击改文字；播放时当前条高亮跟随。
- **编辑操作**：改文字；调时间（拖动或按 0.1 秒微调）；在光标处拆分；与下一条合并；插入；删除；查找替换；整体平移时间；批量改说话人名字；撤销与重做。
- **自动替换表**：按账号保存，可在编辑器里维护；「查找替换」时可以一键把这次的替换加进表里。
- **样式**：字号、离底部的距离、描边、半透明底框、是否显示说话人前缀。描边文字沿用聊天字幕已用过的画法：`GraphicsPath::AddString` 先描边再填色（`Source/UI/BalloonSubtitle/SubtitleRenderer.cpp:6`）。
- 控件尽量用 balloonui（列表、输入框、按钮、`DuiFrameWindow`）；视频预览区与时间轴需要自绘，按 UI 约定第 2 条，开工前先把这两个控件的设计交用户确认。

## 8. 导出

导出窗口里三项可勾选（默认值见 D1），在后台线程执行，显示进度、可以取消，完成后可以「发到会话」（`IMediaHost::SendFileToConversation` / `PickConversationAndSendFile` 的同类宿主方法）。

| 输出 | 文件名 | 做法 |
| --- | --- | --- |
| 硬字幕版 | 原名-字幕.mp4 | Source Reader 解码（优先硬件）→ 逐帧在 BGRA 画面上画该时刻的字幕 → Sink Writer 重新编码 H.264（与 `FlamingoMedia/Record/RecordMp4Writer` 相同的写法，按开发约定文档的共用源文件做法编译同一份源文件）；声音优先原样拷贝 AAC，不行再解码后重新编码。码率取原文件码率并略微提高，补偿二次编码损失 |

| 外挂字幕 | 原名.srt | 直接写文件 |

## 13. 主要风险

- **静态库无法入库**：0a 实测 `onnxruntime.lib` 单个文件 x64 为 922 MB，两个架构的静态库解压后合计约 1.66 GB，超过 GitHub 单文件 100 MB 的上限，不能照服务端 `deps/` 的做法提交。改为提交构建脚本：按固定的版本标签取 sherpa-onnx 源码、打补丁、用 CMake 编出两个架构的 Release 静态库（onnxruntime 静态库由 sherpa-onnx 的 CMake 按固定 SHA256 下载），输出到不进版本库的目录；`FlamingoCaption.vcxproj` 在构建前检查静态库是否就绪，缺失时提示先运行脚本。每台开发机首次构建两个架构约需 40～50 分钟（0b 在满负载下实测 x64 1662 秒、Win32 1301 秒），需要 CMake 与外网。若以后希望静态库能直接入库，可评估 onnxruntime 只保留所需算子的精简构建。
- **加载慢**：评测时约 19 秒，0b 已降到约 1.9 秒（5.3），基本解决；预加载照做。
- **内存**：模型加载后常驻约 250 MB（据推测），靠空闲卸载控制。
- **字幕轨的播放器兼容性**：`tx3g` 字幕轨在 Windows 自带播放器里能否显示尚未验证（0d）。
- **sherpa-onnx 补丁的维护**：若采用 4.2 的第 1 种做法，每次升级都要重新合补丁；补丁与说明放在 `deps/sherpa-onnx/patches/`。
- **CPU**：共享发起人边共享边录制时，要同时运行共享编码、录制编码与识别；按目前数据识别只占 2.5%，0g 再确认。
- **与 F9 的协同**：录制管理窗口由另一路开发，字幕状态列与草稿文件的连带重命名、删除，要等 F9 完成后再接（5d）。

### 14.3 0b：从资源 DLL 加载模型与缩短加载时间（2026-10-05）

**1. 加载时间花在哪里（据实证，onnxruntime 1.30，CPU 满负载）**：decoder、joiner 各不到 0.03 秒，全部时间在 155 MB 的 encoder 上；关闭全部图优化仍需 7.5 秒、打开全部为 11.9 秒，即图优化只占约三分之一，其余是解析与初始化模型本身。另外 sherpa-onnx 在没指定 `model_type` 时会为读模型类型把 encoder 多加载一遍（5.3）。

**2. 各项措施的效果（据实证，sherpa-onnx 内置 onnxruntime 1.28.2，每格三次）**：

| encoder 形式 | 不指定类型，CPU 100% | 指定 `zipformer2`，CPU 100% | 指定 `zipformer2`，CPU 17%～60% |
| --- | --- | --- | --- |
| 原始 ONNX | 21.7～24.3 秒 | 10.1～11.2 秒 | 不指定类型时 7.9～8.2 秒 |
| 预先 EXTENDED 优化的 ONNX | 12.6～15.5 秒 | 6.1～6.7 秒 | — |
| ORT 格式（EXTENDED 优化） | 12.2～13.5 秒 | 5.2～5.5 秒 | 从磁盘 1.68～2.03 秒；**从模型 DLL 内存 1.83～1.97 秒** |

各组合识别第一段录音的错误率均为 4.2%，结果不受影响。ORT 格式文件由 onnxruntime 1.30 生成，sherpa-onnx 内置的 1.28.2 能正常加载；正式的生成脚本固定用 1.28 系列（PyPI 上没有 1.28.2，有 1.28.0）。ORT 格式保留了模型元数据（14 项），体积与原文件基本相同（156.2 MB 对 155.3 MB）。

**3. 模型资源 DLL（据实证，`restest.cpp`）**：四个文件（ORT 格式 encoder、decoder、joiner、tokens）编成纯资源 DLL，体积 170,117,120 字节，资源编译加链接 32～70 秒。以数据文件方式加载 DLL 冷启动 58 毫秒、再次 0.4 毫秒；取资源不到 1 毫秒；把 encoder 全部读一遍冷启动 1.4 秒、已在文件缓存中时 0.2 秒；写到缓存文件 0.32 秒。32 位进程能加载 64 位的模型 DLL，读出的数据完全一致。

**4. 从内存加载的补丁（据实证）**：基于 v1.13.8，改动 7 个文件（新增 `memory-file-registry.h/.cc`；修改 `file-utils.cc` 的 `FileExists`、`online-zipformer2-transducer-model.cc` 按路径加载的构造函数、`online-recognizer-impl.cc` 里为判断模型种类而按路径打开 decoder 的那一处、`c-api.h/.cc` 导出 `SherpaOnnxRegisterMemoryFile` / `SherpaOnnxUnregisterMemoryFile`、`csrc/CMakeLists.txt`），diff 共 248 行。第一次只改了模型构造函数，运行时进程以 `0xC0000409` 终止：`OnlineRecognizerImpl::Create` 按路径打开 decoder（`online-recognizer-impl.cc:106-128`），名字只是登记名、磁盘上不存在，onnxruntime 抛出的异常穿过 `extern "C"` 的 C 接口函数时触发了 `std::terminate`，补上这一处后正常。tokens 用 C 接口已有的 `tokens_buf` 传入，不需要改。

**5. 从源码构建 sherpa-onnx（据实证）**：CMake 4.2.1 加 VS 2022，需加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`；只开 C 接口，关闭语音合成、说话人分离、麦克风、websocket、示例与测试。onnxruntime 1.28.2 静态库由 sherpa-onnx 的 CMake 从 `csukuangfj/onnxruntime-libs` 下载，文件名与 SHA256 固定在 `cmake/onnxruntime-win-x64-static.cmake:23-44`。64 位首次构建 1662 秒（期间 CPU 被其他编译占满，含下载依赖），打补丁后增量重编 57 秒。链接出的测试 DLL 为 18.3 MB，与用官方预编译库链接的结果相同。

**6. 32 位（据实证）**：打过补丁的源码按 Win32 构建 1301 秒，链接出的测试 DLL 为 15.8 MB。32 位进程用同一个模型 DLL（其中的 ORT 格式 encoder 在 64 位机器上用 onnxruntime 1.30 生成）从内存加载成功，加载 2.43 秒、3.24 秒（整机负载 40%～65%），识别结果与 64 位相同，错误率 4.2%；识别 134 秒录音用 50～75 秒，慢于 64 位，与 0a 一致。

### 14.4 0c：生成硬字幕版的速度与声音直通（2026-10-06）

试验程序（没有进版本库）：Source Reader（打开高级视频处理与硬件变换）解码为 RGB32 → 在画面上画两行描边字幕（GDI+，`GraphicsPath::AddString` 先描边后填色）→ Sink Writer 以硬件变换编码 H.264（码率为原码率的 1.2 倍），声音把 Source Reader 给出的原始 AAC 样本原样交给 Sink Writer。素材是本机 Flamingo 录出的两段录像的副本（1920×1080 30 fps 16 秒；620×350 30 fps 138 秒）。测试时整机负载 27%～60%。

| 方式 | 1080p 16 秒 | 620×350 138 秒 |
| --- | --- | --- |
| 不画字，只解码再编码（对照） | 108～110 帧/秒，实时的 3.6～3.7 倍，约 6.8 个核 | — |
| 每帧重新生成文字轮廓并画在整幅画面上 | 62～67 帧/秒，2.1～2.2 倍；画字每帧 12～13 毫秒 | 98 帧/秒，3.3 倍；每帧 9.3 毫秒 |
| **文字变化时才画进缓存图层，每帧只叠加** | **98～113 帧/秒，3.3～3.8 倍**；每帧 2.8 毫秒（测试中字幕每秒换一次） | **484 帧/秒，16 倍**；每帧 1.1 毫秒 |

据实证（以上输出与对输出文件的检查）：

- **画字要用缓存图层**：每帧重画时画字是瓶颈；缓存图层后速度与不画字相当。按此推算，10 分钟 1080p 录像约 3 分钟生成完。CPU 占用约 6～7 个核，主要在软件解码与颜色转换上，导出线程用较低优先级；硬件解码（给 Source Reader 配 D3D 设备管理器）留待第 7 期评估。
- **输出文件正常**：时长 16.17 秒（原 16.21 秒），视频帧数相同（486），码率为原来的 1.2 倍（4673 对 3874 kbps）；抽出的帧上字幕正立、居中、描边清楚。
- **AAC 可以原样拷贝**：Sink Writer 接受输入、输出都是原始 AAC 类型，输出的声音包与输入逐字节相同，不经重新编码。测试中最后 2 个声音包（约 43 毫秒）丢失，原因是试验程序的读循环在视频流结束时就退出了；正式代码要等所有流都结束再收尾。
- **排版要避开画中画**：抽出的帧里，较长的一行字幕右端挨到了右下角的摄像头画中画。录制时把画中画的位置写进字幕草稿，排版时避开它；编辑器的样式里提供位置调整。

### 14.5 0d：字幕轨（2026-10-06，人工核对未完成）

试验程序没有进版本库。据实证：

- **Media Foundation 的 MP4 写入不支持字幕流**：对 MPEG-4 Sink Writer 依次以 `MFMediaType_Subtitle` 加 SRT、TTML、WebVTT、XML、ATSC、CustomUserData 六种子类型调用 `AddStream`，全部返回 `0xC00D3E98`，即 `MF_E_UNSUPPORTED_FORMAT`（SDK 10.0.26100 `mferror.h:1120-1122`，「格式能识别但不支持」）。字幕轨版因此必须自己写封装。
- **Windows 自带的 Source Reader 读不出 tx3g 字幕轨**：用 ffmpeg 7.1（取自 PyPI 的 `imageio-ffmpeg`，只在试验时使用）给录像加一条 `mov_text`（tx3g）字幕轨生成参考文件，Source Reader 只列出声音与视频两个流。据推测基于 Media Foundation 的 Windows 自带播放器也不显示这条字幕轨。
- **封装方案**：候选为 minimp4（`lieff/minimp4`，CC0，单头文件 3785 行，2026-09-25 仍有更新）。它支持声音、视频、私有数据与 PCM 四种轨道（`minimp4.h:128-134`），**不支持文字轨**，需要补上文字轨类型、handler、空媒体头与 `tx3g` 样本描述（据推测约百行）。它不写合成时间偏移，Flamingo 自己的录像不受影响：两段录像均为 H.264 Constrained Baseline，所有帧显示时间与解码时间相同，没有 B 帧；但编辑器允许打开任意 MP4，遇到带 B 帧的外来视频时要补上这部分或改为重新编码。另一候选是自己写封装，只需视频、声音、文字三个轨道。
- **本机播放器核对（2026-10-06，用户同意后由脚本启动播放器并截全屏，无法点击播放器按钮）**：QQ 影音打开参考文件时提示「字幕加载成功」，能识别内嵌字幕轨（截到的时刻没有字幕正文，未能确认画面上的显示）；Windows「电影和电视」（`Microsoft.ZuneVideo` 10.26061）正常播放但画面上没有字幕，据推测其字幕默认关闭、需手动打开；旧版 Windows Media Player 6.5 秒后仍停在「正在连接」。结论：字幕轨版只对支持内嵌字幕的播放器有用，导出时**默认不勾选**（第 2 节 D1 不变）。

### 14.6 0g：识别速度复测（2026-10-06）

补丁版 x64 测试程序识别 134 秒录音，每次运行前记录整机负载。据实证：

| 线程数 | 运行前负载 | 识别耗时 | 进程 CPU 时间 |
| --- | --- | --- | --- |
| 1 | 51% | 21.0 秒（实时率 0.16） | 22.1 秒 |
| 2 | 11% | 22.2 秒 | 84 秒 |
| 4 | 44% | 52.3 秒 | 239 秒 |
| 1 | 100%（其他会话开始编译） | 51.6 秒 | 40.4 秒 |

- 流式识别每次只送 0.2 秒声音，开多线程没有加速，CPU 用量却成倍增加，据推测是 onnxruntime 线程池的同步与空转开销。**实时识别固定用 1 个线程。**
- **事后识别整段不靠加线程加速**，改为按静音把录音切成几段，多路识别流并行（每路 1 个线程，或用 sherpa-onnx 的批量解码），第 3 期实测。
- 识别速度受整机负载影响很大（同为 1 线程，21.0 秒对 51.6 秒），产品里识别线程用低于正常的优先级，界面上的进度按实际处理量显示。

### 14.7 0e：编辑器的视频预览（2026-10-06）

试验程序（没有进版本库）：`IMFMediaEngine` 帧服务模式（D3D11 设备 + DXGI 设备管理器，输出 BGRA），不显示窗口、静音，帧用 `TransferVideoFrame` 取到纹理上。据实证：

- **打开与连续播放可用**：1080p 录像 0.5～2.3 秒打开，小录像 0.5～1.4 秒；连续播放 3 秒取到 87～90 帧（29～30 帧/秒，录像为 30 帧/秒），取帧全部成功。
- **跳转要像渲染循环那样持续查询新帧**：调用 `SetCurrentTime` 后若只等「跳转完成」事件而不查询 `OnVideoStreamTick`，事件迟迟不来，取到的是上一次跳转处的帧。持续查询后，跳转一般在 14～220 毫秒内拿到新帧，帧时间与目标一致。
- **分段式 MP4 上的跳转问题**：在 Flamingo 录像（`RecordMp4Writer` 写的分段式 MP4）上，先往回跳再跳到片尾附近（如 3.0 秒 → 0.5 秒 → 15.213 秒）时，「跳转完成」事件照常到达，却一直没有新帧；对同一位置补跳三次也无效，此后的跳转有时恢复、有时持续失败。同样的序列在两个普通 MP4（Sink Writer 写出的、ffmpeg 原样重新封装的）上全部成功，单独做其中任一步也都成功，所以问题限于分段式 MP4。
- **对策（第 6 期设计编辑器时定）**：一是录制结束时把分段式文件重新封装为普通 MP4（不重新编码，录制过程中仍为分段式，崩溃保护不变；要改录制模块，需与其开发者协调）；二是字幕编辑器打开分段式文件时，先在临时目录重新封装一份普通 MP4 用于预览，与字幕轨版导出共用重新封装的代码。
- 窗口显示：产品里把纹理交给 D3D11 交换链或 Direct2D 画到编辑器的预览区，字幕用与生成时同一份绘制代码叠在上面；具体做法第 6 期定。

- 两台机器联调（第 12 节第 8 期的验证方式）、实机录制与导出文件在播放器里的人工核对**尚未进行**。

**与原方案不同的地方**：

1. **视频预览区与时间轴是自绘控件**（`CaptionPreviewView`、`CaptionTimelineView`，都是 `DuiControl` 的子类）。第 7 节原定开工前把这两个控件的设计交用户确认；开发时按「全部做完再汇报」的要求先做了，设计记在这里供审阅：
   - 预览区只负责画编辑器交来的当前帧（`IMFMediaEngine` 的帧服务模式取帧，经 D3D11 暂存纹理拷成 BGRA，按控件大小缩放、四周补黑），再用与硬字幕相同的 `CaptionRenderer` 叠加当前字幕；字幕图层按「文字 + 尺寸 + 外观」缓存。单击切换播放与暂停。没有画面时显示一行提示。
   - 时间轴上一行是刻度，下一行把每条字幕画成色块（改过的换色，选中的加边框），红色竖线表示播放位置。点空白处跳转，点色块选中并跳到开头；拖色块平移、拖边缘改起止，松开时才交给编辑模型（可撤销）；滚轮左右滚动，Ctrl + 滚轮以鼠标位置为中心缩放；播放位置走出可见范围时自动翻页。换算与限位规则在 `CaptionTimelineMath`，单测 CAPTL1～4。
   - 其余部分（列表、输入框、按钮、各个小窗）都用 balloonui 现成控件；查找替换、平移、改说话人、外观四个小窗共用一个通用的表单对话框 `CaptionFormDialog`。
2. **分段式 MP4 的预览**：0e 发现分段式 MP4 上的跳转有问题，编辑器打开这类录像时先在后台原样转封装成临时的普通 MP4 再交给 `IMFMediaEngine`，临时文件随编辑器关闭删除。
3. **事后识别只开一路识别流**：0g 结论里写的「多路并行」没有采用。多路需要按静音切段并处理段边界的句子，收益有限；一路按排队量控制送入速度，按实时率约 0.16 估算，10 分钟的录像约 1.6 分钟识别完。
4. **观看者的字幕开关放在标题栏**：观看窗标题栏放一个「字幕」图标，点它弹出「为我的发言生成字幕」「显示字幕」两个勾选项；全屏工具条上没有加（全屏工具条的按钮按下标定位，加一项要调整所有下标），全屏时沿用已选的状态。发起人的两个开关放在控制条的「更多」菜单里。字幕组件不可用（企业关闭、DLL 缺失）时两处入口都不出现。
5. **观看端的字幕不画在画面控件里**，而是一个以观看窗为所有者窗口的分层浮层（`ShareCaptionOverlay`），盖在画面控件所占矩形的底部；它不置顶，切到别的程序时随观看窗一起被遮住。共享者本人的浮层置顶、盖在被共享的显示器或窗口上并排除在采集之外；共享的窗口最小化时不显示。观看端与共享者用同一个浮层类，绘制都走字幕模块的 `RenderOverlay`。
6. **录制共享时的字幕草稿按需建立**：收到第一句最终结果时才建草稿会话，没人开字幕的录像不留空草稿。草稿会话不开识别流（为此放开了「麦克风与电脑声音至少识别一路」的限制，CAPDLL9），本人与别人的字幕都来自房间里的实时字幕，所以本人没打开「为我的发言生成字幕」时，录像里没有本人的字幕，可在编辑器里事后识别补上。这些字幕的来源统一记为「他人」。

### 14.12 增强：录制时屏幕上的实时字幕与录制中关闭字幕（2026-10-06）

**来由**：用户实测独立录屏时「没有字幕」。据实证（客户端日志与草稿 `FlamingoRecord_20261006_150134.mp4.caption.json`），识别本身正常，草稿里已有 31 条电脑声音的字幕；只是按原方案独立录屏只写草稿、不在屏幕上显示，用户在录制过程中看不到。另外那次录制没有开麦克风（日志 `mic=0`），对着麦克风说的话不会被识别。用户随后要求：录制时在屏幕上实时显示字幕，并且录制过程中可以关闭字幕，关闭期间不生成字幕。

**做法**：

1. **字幕 DLL 交出实时结果**：字幕接口升到第 2 版（`CaptionApi.h` 的 `kApiVersion = 2`），`ICaptionRecording` 增加 `SetObserver(ICaptionRecordingObserver*)`。草稿会话的每一路识别流的中间结果与定稿（定稿时已装配进草稿）在识别线程上交给观察者，回调带上来源（麦克风 / 电脑声音）。观察者在调用时持锁，`SetObserver(NULL)` 返回之后不会再回调；`Finish`、`Cancel` 也会自动取消登记。接口版本变了，`FlamingoCaption.dll`、`FlamingoMedia.dll`、`Flamingo.exe` 须一起更新。
2. **屏幕上的显示**（`FlamingoMedia/Caption/RecordCaptionLive`）：录屏控制器开始录制时启动它并登记为观察者；识别线程交来的结果排队后投递到它的消息窗口（`WM_APP + 0xE9`），在 UI 线程上更新字幕板（`ShareCaptionBoard`，与屏幕共享相同的显示规则：同一句的中间结果不断替换，定稿保留 4 秒，最多两行），用 `CShareCaptionOverlay` 画在录制区域底部。浮层置顶、鼠标穿透，并排除在屏幕采集之外，不会被录进视频；被录的窗口最小化时隐藏，录制定时器（500 毫秒）里跟随窗口移动。句子编号与说话人标注是纯逻辑（`RecordCaptionLiveRules`）：麦克风与电脑声音同时在录时，两行分别标本人名字与「电脑声音」，只有一路在录时不标说话人。
3. **录制中关闭字幕**：录制条新增「字幕：开 / 关」（只在勾了「生成字幕」的独立录屏中出现，共享录制由共享自己的开关控制）。关闭时：屏幕上的字幕清掉并隐藏；字幕旁路（`RecordCaptionTap::SetSuspended`）改为向草稿会话送同样长度、同样时刻的静音。这样关闭前说到一半的那句照常靠端点检测定稿、保留在草稿里，关闭期间不会产生任何字幕，时间轴连续，重新打开后接着识别。据实证这种做法可行：CAPDLL3 与新增的 CAPDLL10 都是推完录音再补静音，在关闭识别流之前就收到了定稿，且之后没有新的文字。
4. **浮层排除采集失败时不显示**：`CShareCaptionOverlay` 要求排除在采集之外而 `SetWindowDisplayAffinity` 失败时，浮层不显示（字幕照常写进草稿或照常发送），免得字幕被录进视频或采集进共享画面。共享者本人的浮层同样适用。

**用例**：CAPDLL10（`[captiondll]`，观察者收到中间结果与定稿、补静音后这句定稿且之后没有新文字、取消登记后不再回调）；CAPRT5（`[captionrec]`，关闭期间送静音、时刻与长度不变、重新打开后恢复原声）；CAPRL1、CAPRL2（`[captionlive]`，句子编号、说话人标注）；RBAR5（`[recordbar]`，录制条字幕开关的显示与点击）。

**同时做的**：字幕编辑器及其导出、替换表、表单小窗的标题栏加上程序图标（编辑器同时设任务栏图标），此后新窗口默认都加，写进了开发约定文档「UI 约定」第 10 条。

**同日调整：「生成字幕」同时识别麦克风与电脑声音**。用户第二次实测仍没有字幕，据实证（日志 `flamingo.20261006160400.26216.log` 与只有 474 字节的空草稿）原因是那次没录麦克风（`mic=0`），又取消了「为电脑声音生成字幕」，没有任何一路声音在识别。先与用户商定「保留两个勾选项、只加提示」，随后用户改为：只要开启了字幕，电脑声音和麦克风的声音都识别。现在的做法：

- 录制选项去掉「为电脑声音生成字幕」（控件 id 26 作废）；`caption_pref_record_system` 与设置里的 `m_recordSystem` 不再使用，编号与字段保留，字幕接口版本不变。
- 勾了「生成字幕」时草稿会话总是建麦克风、电脑声音两路识别流，旁路两路都交；没在录的一路混音器不交声音，不占识别时间；录制中途在录制条上打开的那一路马上开始识别。两路都在录时屏幕上的两行分别标本人名字与「电脑声音」。
- 两路声音都没录时给提示，判断只有一条（`RecordCaptionHasSource`）：录制选项里「生成字幕」后面的提示文字（控件 id 28，常驻、无提示时为空，免得显隐变化后要重排）显示「没有录制声音，不会生成字幕」；录制时字幕浮窗显示「没有可识别的声音：打开麦克风或电脑声音后开始生成字幕」，打开其中一路后消失。
- 用例：CAPRL3 改为两路判断；SPW5（隐藏用例，需要建窗口）改为检查「生成字幕」勾选项与提示文字：默认勾着「录制电脑声音」时没有提示，两路都取消后出现，勾回麦克风后消失。

**浮层不显示的修复（同日）**。用户第三次实测仍看不到字幕。据实证（日志 `flamingo.20261006200414.06800.log`）：第一句字幕到达时浮层调 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 失败，错误码 8，按第 4 条的保护浮层不显示。实验的结论：

- 已带 `WS_EX_LAYERED`、用 `UpdateLayeredWindow` 绘制的窗口，设置排除一律失败（错误码 8），不论在 `UpdateLayeredWindow` 之前还是之后、显示之前还是之后；普通窗口、用 `SetLayeredWindowAttributes` 的分层窗口都能成功。
- 先在普通窗口上设好排除，再加 `WS_EX_LAYERED` 并用 `UpdateLayeredWindow` 绘制：在真实桌面上截屏（GDI，`CAPTUREBLT`），对照用的分层窗口截到 9259 / 10000 个像素，这个窗口截到 0 个，排除确实生效。

`CShareCaptionOverlay` 因此改为：先建不带 `WS_EX_LAYERED` 的窗口，需要排除时先设排除，再加 `WS_EX_LAYERED`；是否排除与所有者窗口一样在建窗时决定，变了就重建。用例 SCAPO1、SCAPO2（`[captionoverlay]`，会建窗口，在不可见桌面里跑）检查排除时浮层是置顶的分层窗口且亲和性为排除，观看者的浮层有所有者、不置顶、不排除。屏幕共享发起人的浮层原先也有同样的问题，一并修好。
