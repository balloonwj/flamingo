# 邀请入群改造方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-10-04
> 用途：记录邀请入群的三项改造（入群系统提示、邀请时选择同步的历史条数、「邀请入群需被邀请人同意」开关与入群邀请卡片）的整体方案、分期路线与开发步骤。每一步开工前据此细化测试用例并与用户确认，收尾后回填实际结果。

---

## 1. 背景与目标

现在把同事拉进群之后，群里没有任何变化：其他群友看不到有人加入，被邀请人本端的会话列表和「群聊」页也不会出现这个群，要重新登录才看得到。本方案做三件事：

1. **入群系统提示。** 有人入群时，群里插入一条系统提示，如「「张三」邀请「李四」加入了群聊」，全体成员（含新成员）都能看到；被邀请人本端随即出现这个群。
2. **邀请时选择同步的历史条数。** 邀请对话框里可以选择新成员入群后能看到多少条入群前的聊天记录，默认同步全部。
3. **邀请入群需被邀请人同意。** flamingoAdmin 的企业设置里加一个开关，默认关闭。关闭时被邀请人直接入群；开启时被邀请人在与邀请人的单聊里收到一张入群邀请卡片，点「加入群聊」后才入群。

以下口径已与用户确认（2026-10-04），前四项由用户逐项拍板，其余为方案默认值、随方案一并认可：

| 决策点 | 取值 | 详见 |
| --- | --- | --- |
| 开关开启且群设了「普通成员邀请需审批」时的顺序 | **先发卡片，后审批**。被邀请人点「加入群聊」时再判断是否需要审批，判断依据是点击那一刻邀请人的角色与群设置 | §3.4 |
| 群设了「新成员不可查看入群前的历史消息」时 | **群设置优先**。对话框里的同步选项整组置灰并说明原因；群允许看历史时，邀请人只能在此范围内收紧 | §3.2 |
| 同步选项的样式 | **三个单选项**：「全部聊天记录 / 最近 [N] 条 / 不同步」，默认选中「全部」，只有选中「最近」时可填写条数（原定的勾选框 + 条数输入在界面核对后改掉，见 §10「2c 修订」） | §3.2 |
| 入群提示的措辞 | **带邀请人，涉及本人时写「你」**；名字加书名号，与退群、转让群主的提示写法一致 | §3.1 |
| 同步条数上限 | 10000 | §4.2 |
| 历史边界对群主、管理员 | 不受限制，与现有群级开关一致（管理者需要看全量记录处理纠纷） | §5.3 |
| 历史边界的作用范围 | 拉历史、会话内搜索、全局搜索、Pin 列表；群文件不受限 | §5.3 |
| 同意开关的取值依据 | 按**被邀请人**所属企业取值，默认关闭 | §3.5 |
| 卡片放在哪里 | 邀请人与被邀请人的单聊，发送者为邀请人，由服务端生成 | §3.3 |
| 卡片上的按钮 | 只有「加入群聊」，不做「拒绝」 | §3.3 |
| 卡片有效期 | 7 天 | §3.3 |
| 卡片能否撤回、转发、引用 | 都不能。卡片由服务端生成且绑定特定的被邀请人，转发出去没有意义 | §6.4 |
| 邀请人已退群后点卡片 | 邀请失效 | §3.3 |
| Android 客户端 | 不在本方案范围内 | — |

## 2. 现状盘点（据实证，均已核对代码位置）

### 2.1 服务端没有插入任何提示

- `ChatSession::onInviteToGroup` 在 `addMembers` 成功后只向全群推送一条成员变动通知 1317，不往群里写系统消息。
- 唯一会写进群里的是入群欢迎语 `sendGroupWelcomeMessage`，但群没开欢迎语时它直接返回。
- 自由加群（`onJoinGroupRequest`）与审批通过（`onHandleJoinGroup`）同样只推 1317 与欢迎语。三处入群路径的收尾步骤（1317、自动群名、欢迎语、群备忘）各写了一份。

### 2.2 客户端收到「加入」推送基本不处理

- `CBalloonMainPanel::OnGroupMemberChanged` 只刷新已经打开的群管理窗与群聊窗成员边栏；对「本人被移出 / 退出」有处理，对「本人加入」没有。被邀请人本端的会话列表与「群聊」页都不会出现这个群。
- 但只要群里来一条消息，`BumpConversation` 就会为不认识的群新建会话行并补拉群资料。因此服务端插入系统提示后，被邀请人的会话列表会自然出现这个群，只有「群聊」页的群列表（`m_myGroups`，来自 1320）还需要补拉。

### 2.3 普通成员的邀请转为审批时，邀请人得不到任何提示

- 普通成员邀请且群设了需审批时，服务端把邀请转成加群申请后回成功应答。
- 客户端 `OnV2GroupOpResult`（`BalloonMainPanelNetHandlers.cpp`）对群管理写操作只在失败时提示，成功不改界面。邀请人看不出邀请其实在等审批。

### 2.4 历史可见范围只有一个群级开关

- `t_group.f_new_see_history` 为 0 时，普通成员只能看入群时间以后的消息，群主与管理员不受限（`ChatSession::groupHistoryMinCreateTime`，2b 起换成 `groupHistoryBound`）。
- 它作用于三处：拉历史 `onSyncMessages`、会话内搜索、全局搜索。
- Pin 列表 `onGetPinnedMessages` 只校验群成员身份，不受这个开关限制，而它的应答带完整消息体。群文件（`onGetGroupFiles`、`onSearchGroupFiles`）同样不受限。
- 截断依据是消息的 `f_create_time`，精度为秒（`now = time(NULL) * 1000`），同一秒内的多条消息无法按条数区分。

### 2.5 新成员的群未读数会把入群前的消息算进去（代码层面据实证，1b 的用例 GJ8 已证实）

- 群未读查询以 `t_conversation` 的已读位点为下界（`MessageManager.cpp`）；新成员没有这一行，`ConvState` 的已读位点默认为 0。
- 因此新成员重新登录时，入群前别人发的消息会全部算成未读（上限 `kMaxUnreadCount`）；群设为不可看历史时，这些消息新成员根本看不到，却仍被计数。

### 2.6 按企业的功能开关已有通用机制

- 设置存于 `t_system_setting`（主键 `f_enterprise_id + f_key`），现有 `fileshare.enabled`、`p2p.enabled` 两个键（`table_mysql.sql:753-763`）。
- `FeatureSwitchManager`（`chatserversrc/FeatureSwitchManager.h`）负责取值、写库与内存表；登录应答的 `features` 对象与 1013 推送把开关下发给客户端；后台接口为 `/admin/setting/get.do`、`/admin/setting/set.do`（`docs/Admin控制台接口文档.md` §12.1、§12.2）。
- flamingoAdmin 的 `EnterpriseSettingsModal` 在「功能开关」块里已有两个 `FeatureSwitchPanel`。

## 3. 交互设计

### 3.1 入群系统提示

每次有人入群，服务端在群里插入一条系统提示，全体成员（含新成员）都收到。措辞随查看的人不同：

| 场景 | 其他群友看到 | 邀请人看到 | 新成员本人看到 |
| --- | --- | --- | --- |
| 邀请一人 | 「张三」邀请「李四」加入了群聊 | 你邀请「李四」加入了群聊 | 「张三」邀请你加入了群聊 |
| 邀请多人 | 「张三」邀请「李四」、「王五」加入了群聊 | 你邀请「李四」、「王五」加入了群聊 | 「张三」邀请你和「王五」加入了群聊 |
| 邀请超过 10 人 | 「张三」邀请「李四」、「王五」……等 30 人加入了群聊 | 你邀请「李四」、「王五」……等 30 人加入了群聊 | 「张三」邀请你和「王五」……等 30 人加入了群聊 |
| 自由加群、本人申请经审批 | 「李四」加入了群聊 | — | 你加入了群聊 |

- 最多列出 10 个名字；列出的名字少于实际人数时，末尾写「等 N 人」。
- 取不到邀请人昵称时写「有人」，与发布群公告的提示一致；一个新成员昵称都取不到时写「「张三」邀请 3 位新成员加入了群聊」。
- 提示插在成员变动推送 1317 之后、入群欢迎语之前：客户端要先把新成员并进成员列表，才能对上提示里的人。
- 系统提示不计未读，这是现有口径（`MessageManager.cpp` 的会话未读查询、`ConversationsProtocolClient::shouldCountAsUnread`）；唯一的例外是新成员本人看到的入群提示计一条未读（2026-10-08 起，见 §12.8）。被邀请人本端的会话列表顶部会出现这个群，摘要为「「张三」邀请你加入了群聊」。
- 被邀请人本端收到名单里有本人的「加入」推送后，补拉一次群列表（1320），使「群聊」页立刻出现这个群。

### 3.2 邀请对话框里的同步选项

在邀请对话框（`CCreateGroupDlg` 的 `kPurposeInvite`）右栏已选成员列表下方加一组选项：

```
入群后可查看的聊天记录
(●) 全部聊天记录
( ) 最近 [ 100 ] 条           ← 只有选中「最近」时输入框可编辑
( ) 不同步，只能看到入群之后的消息
```

- 输入框只接受数字，默认 100，取值 1～10000；「最近」填 0 时提示改选「不同步」。留空或超出范围时在选项组下方提示，不发请求。
- 群设为「新成员不可查看入群前的历史消息」时，整组置灰，下方显示灰字「本群已设置为新成员不可查看入群前的聊天记录」，请求里不带这个字段。
- 同意开关开启时，在确认按钮上方加一行说明「对方同意后才会加入群聊」。
- 邀请发出后，按应答里的统计（§4.2）提示：

| 应答情况 | 提示 |
| --- | --- |
| 全部直接入群 | 不提示，群里会出现入群提示 |
| 有发出卡片的 | 已向 N 人发出入群邀请，对方同意后加入群聊 |
| 有转为审批的 | 已提交邀请，等待群主或管理员审批 |

### 3.3 入群邀请卡片（同意开关开启时）

邀请人点「邀请入群」后，服务端为每位被邀请人在**邀请人与被邀请人的单聊**里生成一张卡片，发送者为邀请人。

被邀请人一侧：

```
┌──────────────────────────────────┐
│ [群头像]  邀请你加入群聊                │
│          产品研发部周会群              │
│          32 名成员                   │
│                         [加入群聊]   │
└──────────────────────────────────┘
```

邀请人一侧显示「你邀请「李四」加入群聊」、群名、成员数和状态文字，没有按钮。卡片状态与两侧的显示：

| 状态 | 被邀请人一侧 | 邀请人一侧 |
| --- | --- | --- |
| 待加入 | 「加入群聊」按钮 | 等待对方确认 |
| 等待审批 | 已申请加入，等待群主或管理员审批 | 对方已同意，等待群主或管理员审批 |
| 已加入 | 已加入 | 对方已加入 |
| 未通过审批 | 未通过群主或管理员审批 | 未通过群主或管理员审批 |
| 已过期 | 邀请已过期 | 邀请已过期 |
| 已失效 | 邀请已失效 | 邀请已失效 |

- 有效期 7 天，从发出时算起。
- 「已失效」包括：群已解散、邀请人已退出群聊。被邀请人已经通过别的途径入群时，卡片显示「已加入」。
- 点「加入群聊」后按钮置灰，显示「正在加入…」。入群成功则打开群聊窗；转为审批则卡片变为「等待审批」；失败时弹框说明原因（已过期、已失效等），卡片同步刷新。
- 卡片状态变化推给双方的全部在线设备，任何一端操作后其余各端同步刷新。
- 重复邀请会产生多张卡片，任意一张入群成功后，其余卡片都显示「已加入」。
- 卡片是邀请人发来的普通消息（不是系统提示），被邀请人照常计未读、闪托盘，会话摘要为「[入群邀请] 群名」。

### 3.4 与群审批的衔接（先发卡片，后审批）

被邀请人点「加入群聊」时，服务端按点击那一刻的情况判断：

- 邀请人是群主或管理员，或者群设置允许普通成员直接拉人（`f_member_invite = 1`）：直接入群，卡片变为「已加入」。
- 否则转为一条加群申请：来源记为好友邀请、推荐人记为邀请人，并记下邀请 id 与同步条数；推给群主与管理员（1307），卡片变为「等待审批」。
- 审批通过：入群，入群提示里的邀请人取推荐人；卡片变为「已加入」。
- 审批拒绝：卡片变为「未通过审批」。原先拒绝时不通知申请人，对这类由卡片转来的申请，卡片状态变化就是通知。

同意开关关闭时，普通成员的邀请仍按现有逻辑转为审批（`ChatSession::onInviteToGroup`），只是加上 §3.2 的提示。

### 3.5 flamingoAdmin 的开关

- 「功能开关」里加一个 `FeatureSwitchPanel`（2026-10-08 起功能开关集中在企业详情屏的「功能开关」子 tab `FeatureSwitchesPage`，不再放在企业设置弹窗里），标题「邀请入群需被邀请人同意」，说明「开启后，被邀请人会在与邀请人的单聊里收到入群邀请卡片，点「加入群聊」后才入群；关闭时被邀请人直接入群。」默认关闭。
- 改动后服务端照常向该企业的在线用户推 1013，客户端据此调整邀请对话框的说明。
- 开关由开变关时，已经发出、仍在有效期内的卡片继续有效，点了照常入群。
- 管理员操作日志记「打开邀请入群需被邀请人同意」或「关闭邀请入群需被邀请人同意」。

## 4. 协议设计

### 4.1 系统提示 `member_join`

在 `docs/协议设计-v2.md` §20.1 的表里加一行。`content` 照旧带服务端拼好的中文 `text`，老客户端显示不变。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `inviter` | 字符串 | 邀请人昵称；没有邀请人或取不到昵称时不写 |
| `inviterid` | 字符串 | 邀请人 userid；没有邀请人（自由加群、本人申请经审批）时不写 |
| `members` | 数组 | 全部新成员，每项 `{ "userid": 字符串, "nickname": 字符串 }`；只有前 10 项带 `nickname`，取不到昵称的项也不带 |

id 一律写成字符串，与群组段其它报文一致（如 1317 的 `userids`，`GroupProtocol::buildGroupMemberChangedNotify`）。

```json
{ "text": "「张三」邀请「李四」、「王五」加入了群聊", "tipkind": "member_join",
  "tipargs": { "inviter": "张三", "inviterid": "5127",
               "members": [ { "userid": "5308", "nickname": "李四" }, { "userid": "5309", "nickname": "王五" } ] } }
```

客户端按 `inviterid` 与 `members[].userid` 判断提示是否涉及本人，再选用 §3.1 的写法。`members` 带全部新成员的 userid，是为了让排在第 10 位之后的新成员也能看到「邀请你」。

### 4.2 `cmd_invite_to_group`（1305，追加字段）

请求追加可选字段 `historylimit`：

| 取值 | 含义 |
| --- | --- |
| 缺省或 -1 | 同步全部（老客户端不带此字段，行为与现在相同） |
| 0 | 不同步入群前的消息 |
| 1～10000 | 同步入群前最近 N 条 |

其他取值回 3（请求非法）。群设为不可看历史时服务端忽略此字段（群设置优先）。

应答追加三个统计字段，老客户端忽略：

```json
{ "code": 0, "msg": "ok", "added": 1, "invited": 2, "pending": 0 }
```

| 字段 | 含义 |
| --- | --- |
| `added` | 直接入群的人数 |
| `invited` | 发出入群邀请卡片的人数（同意开关开启时） |
| `pending` | 转为加群申请、等待审批的人数（同意开关关闭、邀请人是普通成员且群需审批时） |

### 4.3 入群邀请卡片 `message_type_group_invite = 21`

由服务端生成，客户端不得自行发送、撤回、置顶、转发（这几条请求带这个类型时回 6「无权限」，与文件共享卡片、屏幕共享卡片的处理相同，判定在 `MessageProtocol::isClientOperableMsgType`）。单聊消息，`from` 为邀请人，`to` 为被邀请人。落库的 `content`：

```json
{ "inviteid": "31", "groupid": "268435463", "groupname": "产品研发部周会群", "facetype": 0, "customface": "",
  "inviterid": "5127", "inviter": "张三", "inviteeid": "5308", "invitee": "李四", "expiretime": 1760195200000 }
```

下发时（实时推送与 `cmd_sync_messages`）由服务端合并：

| 字段 | 说明 |
| --- | --- |
| `state` | 卡片状态，取值见下表 |
| `membercount` | 群当前成员数；群已解散时不写 |
| `groupname`、`facetype`、`customface` | 用群当前资料覆盖；群已解散时保留卡片里的原值 |

| `state` | 含义 | 是否落库 |
| --- | --- | --- |
| 0 | 待加入 | 是 |
| 1 | 已加入（含被邀请人已通过别的途径入群） | 是；被邀请人已在群中时也按 1 下发 |
| 2 | 等待审批 | 是 |
| 3 | 未通过审批 | 是 |
| 4 | 已过期 | 否，待加入且超过 `expiretime` 时按 4 下发 |
| 5 | 已失效（群已解散、邀请人已退群） | 否，下发时计算 |

会话列表的 `lastmsg` 带 `digestarg`（群名），客户端生成「[入群邀请] 群名」，与 §20.2 接龙、文件共享卡片的做法相同。

### 4.4 `cmd_accept_group_invite`（1327，新增）

被邀请人点「加入群聊」。请求 `{ "inviteid": "31" }`，应答：

```json
{ "code": 0, "msg": "ok", "inviteid": "31", "groupid": "268435463", "joined": 1 }
```

`joined` 为 1 表示已入群，为 0 表示已转为加群申请、等待审批（只在成功时带）。`inviteid` 回带请求里的邀请 id，失败时也带，客户端据此把那张卡片从「正在加入」恢复原状。错误码：

| code | 情况 |
| --- | --- |
| 305 | 已在群中（同时把卡片记为已加入） |
| 313 | 邀请已过期 |
| 314 | 邀请已失效：邀请不存在或不属于本人、已处理过、群已解散、邀请人已退群 |

### 4.5 `cmd_group_invite_changed_notify`（1328，新增）

卡片状态变化时推给邀请人与被邀请人的全部在线设备：

```json
{ "inviteid": "31", "msgid": "9007199254741011", "inviterid": "5127", "inviteeid": "5308", "state": 1 }
```

客户端按 `inviterid` / `inviteeid` 中不是本人的那一方定位单聊会话，再按 `msgid` 找到卡片。

### 4.6 功能开关

- 设置键 `group.inviteconfirm`，取值 `"0"` / `"1"`，内置默认值为 0（关闭）。
- 登录应答与 1013 的 `features` 对象加 `inviteconfirm`，如 `{"fileshare":1,"p2p":1,"inviteconfirm":0}`。
- 后台接口 `/admin/setting/get.do` 的 `settings` 多一项，`/admin/setting/set.do` 接受这个键。

### 4.7 错误码

| code | 名称 | 含义 |
| --- | --- | --- |
| 313 | `error_code_group_invite_expired` | 入群邀请已超过有效期 |
| 314 | `error_code_group_invite_invalid` | 入群邀请已失效（不存在或不属于本人、已处理过、群已解散、邀请人已退群） |

### 5.1 数据库

改 `table_mysql.sql` 后运行 `tools/gen_table_sqlite.py` 生成 SQLite 的两份文件，并同步 `MysqlManager` 的表定义。启动时只建出缺少的表、不给已有的表补列（2026-10-09 起），已有的库须手工加列。

| 表 | 改动 |
| --- | --- |
| `t_group_member` | 加 `f_history_from bigint NOT NULL DEFAULT 0`：本人可见的最早一条群消息 msgid，0 表示不限。入群时按同步条数算出 |
| `t_group_join_request` | 加 `f_history_limit int NOT NULL DEFAULT -1`（申请通过时按它计算历史边界）与 `f_invite_id bigint NOT NULL DEFAULT 0`（由入群邀请卡片转来时记邀请 id，审批结果据此回写卡片） |
| `t_group_invite`（新增） | 一行 = 一张入群邀请卡片：`f_id`、`f_groupid`、`f_inviter`、`f_invitee`、`f_history_limit`、`f_state`（0～3）、`f_msgid`（卡片消息 id）、`f_create_time`、`f_expire_time`、`f_handle_time`；索引 `(f_invitee, f_groupid)` |

群解散时 `t_group_invite` 的行保留，卡片下发时按群不存在计算为「已失效」。

### 5.2 入群收尾统一为一个函数

现在三条入群路径各写了一份收尾步骤，加上卡片同意后共四条。抽出 `ChatSession::completeGroupJoin`，按以下顺序执行：

1. 按同步条数计算每位新成员的历史边界（§5.3），随成员行一起写入（`addMembers` 增加参数）；
2. 把新成员在该群的已读位点设为本群当前最新一条消息（修 §2.5）；
3. 推 1317；
4. 重算自动群名；
5. 插入 `member_join` 系统提示（§4.1）；
6. 发入群欢迎语；
7. 处理群备忘的可见范围（`handleMemoMembersJoinedGroup`）。

纯逻辑（提示正文、`tipargs` 的组装、条数校验）放进 `GroupProtocol`，进 doctest。

### 5.3 历史边界

- 计算：同步全部为 0；同步 N 条取本群倒数第 N 条消息的 msgid，本群消息不足 N 条时为 0；不同步取本群当前最大 msgid + 1。msgid 全局自增，入群提示等后续消息的 msgid 必然更大，不会被截掉。
- 按 msgid 而不是按时间截断：服务端时间戳精度为秒，同一秒内的多条消息按时间无法区分条数。
- `groupHistoryMinCreateTime` 扩展为返回「时间下界 + msgid 下界」两项（实现为 `ChatSession::groupHistoryBound`，返回 `GroupHistoryBound`），群主与管理员两项都为 0；四处查询同时套用两项：拉历史、会话内搜索、全局搜索、Pin 列表（`MessagePinManager::getPinnedMessages` 增加参数）。群文件不受限。
- 群设为不可看历史时，时间下界（入群时间）已经比 msgid 下界更严格，两项同时套用即可，不需要特殊处理。

### 5.4 入群邀请卡片

- 新增 `GroupInviteManager`（`t_group_invite` 的读写，单例）与 `GroupInviteProtocol`（卡片 `content` 的组装、状态计算、1327 / 1328 报文，纯逻辑进 doctest）。
- `onInviteToGroup`：按被邀请人所属企业判断开关；开启时为每人写一行 `t_group_invite`、生成卡片消息并推给双方，应答带统计。
- `onAcceptGroupInvite`（1327）：校验后按 §3.4 直接入群（调用 `completeGroupJoin`）或转为加群申请，更新卡片状态并推 1328。
- `onHandleJoinGroup`：申请带邀请 id 时，审批结果回写卡片并推 1328。
- `augmentCardRecord` 加上卡片类型，合并 §4.3 的下发字段；会话摘要加 `digestarg`。

### 5.5 关键路径日志

入群收尾（群、人数、邀请人、各人历史边界）、卡片生成与状态变化、1327 的校验结果都打英文日志；不记群名与昵称以外的消息内容。

## 11. 第 4 期：审批只生效一次、「申请已处理」推送、退群不再插提示（2026-10-04）

### 11.1 背景

第 3 期做完后核对群聊的审批与退群流程时发现几处问题，逐条与用户核对后定下处理方式：

| # | 现象 | 决定 |
| --- | --- | --- |
| 1 | 管理员处理一条已被别人处理过的申请，服务端回 308，客户端没有对应提示，弹出「操作失败。（join request already handled）」 | 提示「该申请已被其他管理员处理。」，并重拉待审批列表（失败后本来就会重拉群数据） |
| 2 | 一位管理员处理完申请，其他群主 / 管理员不知道，审批列表与计数停在旧状态 | 新增推送 1329「申请已处理」，推给该群全体群主与管理员，开着的群管理窗重拉待审批列表 |
| 3 | 两位管理员同时处理同一条申请：「先查仍是待处理、再按 id 改状态」不是原子操作，两个请求都可能通过检查，都同意时入群收尾执行两遍（两条入群提示），一同意一拒绝时申请记录与是否在群里可能矛盾 | 先写用例复现，再改成带条件的更新，只有改到的请求继续，没改到的回 308 |
| 4 | 未开卡片开关时申请被拒绝，邀请人与申请人都收不到通知 | 保持现状 |
| 5 | 主动退群时全体成员都会看到「「某人」退出了群聊」 | 去掉这条提示：退群只推成员变动通知；已落库的旧提示照常显示 |

### 11.2 审批规则（确认后的产品流程）

- 邀请入群是否需要审批只看邀请人的角色与群设置「普通成员邀请需审批」（`f_member_invite`），不看「加群方式」：群主、管理员邀请直接入群；普通成员在需审批时，邀请转为加群申请（来源「好友邀请」、推荐人为邀请人），推 1307 给全体群主与管理员。开了卡片开关时先发卡片，被邀请人点「加入群聊」那一刻再按同样的规则判断。
- 一条申请只能被处理一次：先处理的生效，晚到或同时到达而没抢到的回 308；处理生效后推 1329 给全体群主与管理员（含处理人本人的其他设备）。
- 同意：申请人入群，走入群收尾（成员变动、入群提示、欢迎语）；拒绝：只改申请状态，不通知申请人或邀请人（开了卡片开关时卡片变为「未通过审批」）。
- 主动退群：留下的成员与退群者本人只收到成员变动通知（1317），群里不再插系统提示。

## 12. 加群链接（2026-10-07 起草并实施，12 项新功能第三批之一）

群成员可以生成一条加群链接 `flamingo://joingroup?code=XXXXXXXXXXXX`，发给同事（聊天里、邮件里、网页上都行）。同事点开后客户端弹出「加入群聊」确认，按群的加群方式处理：允许任何人加入的直接入群，需要审批的转为加群申请，禁止加入的群根本生成不了链接。同批另见 `docs/群公告接入方案.md` §14、`docs/群问答方案.md`。

### 12.1 已定事项

| 事项 | 结论 | 来源 |
| --- | --- | --- |
| 链接形式 | `flamingo://joingroup?code=` 加 12 位随机码；客户端向 Windows 注册 `flamingo:` 协议，浏览器里点也能拉起或激活客户端 | 用户确认 |
| 谁能生成 | 按现有邀请权限：任何群成员都能邀请人，所以任何群成员都能生成；群的加群方式为「禁止」时谁都不能生成（错误码 `error_code_permission_denied`） | 用户确认 |
| 有效期 | 生成时选 1 天 / 7 天 / 永久，默认 7 天 | 用户确认 |

### 12.7 修正：群管理窗切到「加群链接」页后其它页签点不动（2026-10-07 晚）

**现象**：用户实机测试时，群管理窗点过「加群链接」之后，再点左侧其它页签都没有反应。

**原因（据实证）**：当时的客户端日志里 22:13 到 22:18 之间「Group manage window UI built」出现 2413 次、「group links arrived」2393 次，约每 18 毫秒一轮。代码上是一个自己触发自己的循环：收到 1341 应答时当前页是「加群链接」页，`OnGroupLinksArrived` 调 `RefreshNavAndPage` 整体重建；`RefreshNavAndPage` 先 `InitUi`（当前页被重置为成员管理），再 `SwitchToPage` 切回原页；而 `SwitchToPage` 每次切进「加群链接」页都会再发一次 1341。界面每 18 毫秒重建一次，导航控件在鼠标按下与松开之间就被换掉，凑不成一次点击（据推测，与现象相符）；服务端也一直收到请求。

**修正**：`SwitchToPage` 增加参数 `reloadPageData`，用户点导航、从「基本信息」跳到群公告页时传 `true`；`RefreshNavAndPage` 重建后切回原页时传 `false`，不再请求。改动在 `BalloonGroupManageWindow.h/.cpp`、`GroupManageWindowData.cpp`。群管理窗不在 FlamingoUnit 里，没有单测；重新编译后用户实机核对通过，日志里整个会话只重建 15 次、收到链接列表 5 次，每次都对应一次操作或一次数据返回。

### 12.8 修正：链接申请经审批入群后，新成员没有任何提醒（2026-10-08）

**现象**：用户问「A 邀请 B 加入群 C，管理员同意之后，B 没有加入成功的通知吗？」。2026-10-07 23:08 那次实际走的是加群链接：A（5308）生成链接，B（5127）点链接申请（需审批的群转为申请，`f_source=2`、推荐人 5308），A 以管理员身份同意。

1. 入群提示是系统消息，按原口径不计未读、不闪托盘、不弹窗（B 的日志 `countUnread=0, flashTray=0, popup=0`）。链接直接入群时客户端会打开群聊窗，经审批的这条路在「已提交申请，等待审批」之后就再没有任何提醒。
2. 必读卡片被客户端丢弃，见 `docs/群公告接入方案.md` §14.6。
3. 审批通过时只有好友邀请来源取推荐人作入群提示的邀请人（`ChatSession::onHandleJoinGroup`），链接来源被跳过，提示写成「「张勇」加入了群聊」，与链接直接入群时的「A 邀请 B 加入了群聊」（§12.1）不一致。

- 服务端 `GroupProtocol::joinTipInviterForRequest(来源, 推荐人)`：好友邀请与扫码 / 链接来源取推荐人，群搜索取 0；`onHandleJoinGroup` 改为调用它。用例 GJ11。
