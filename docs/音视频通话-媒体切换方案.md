# 音视频通话：对话框合一与通话中媒体切换方案

本文承接 [音视频通话方案.md](音视频通话方案.md)（第一期：把音视频通话从零做到可用），
描述后续阶段的一项改造：**语音与视频共用同一个通话对话框，并支持通话过程中在语音与
视频之间双向切换**。

编写日期：2026-07-31

---

## 1. 目标

- 语音通话与视频通话使用同一个对话框，外观以视频对话框为基座。
- 通话接通后，任一方可以把语音通话升级为视频通话。
- 通话接通后，任一方可以把视频通话降级为语音通话。
- 切换过程中**音频链路不得中断**——用户不应听到断音。

---

## 2. 现状盘点

### 2.1 已具备的（据实证）

`BalloonCallDlg` **已经是一个类同时承载语音与视频**，并非两个对话框：

- `void SetVideoCall(bool video)` 与成员 `m_videoCall`，见 `Call/BalloonCallDlg.h:93`。
- 本地 / 远端两块 `CallVideoCanvas`，以及大小画面互换 `SwapVideoCanvas()`；类头注释
  说明了 `m_localIsBig` 翻转 + 两块控件交换已持有帧的即时互换机制。
- `m_mode` 区分三种形态，对应三个打开入口：`OpenCalling`（呼出中）/ `OpenIncoming`
  （来电）/ `OpenConnected`（已接通）。
- 摄像头不可用的兜底入口 `SetCameraUnavailable(int reason)` 已存在。

也就是说"合二为一"所需的**类结构已经就位**，本方案的工作量集中在"运行期可切换"。

### 2.2 把媒体类型钉死的三处（据实证）

**一是 UI 一次性构建。** `BuildUiOnce()` 按调用时的 `m_mode` 与 `m_videoCall` 建好控件树，
其后不再重建（方法名本身即表明这一语义）。

**二是入口分成两条独立消息。** 聊天窗的两个按钮分别投递不同消息：

| 消息 | 投递点 | 主面板处理器 |
| --- | --- | --- |
| `FMG_MSG_CALL_START_INVITE` | `BalloonChatWnd/BalloonChatWindow.cpp:842` | `BalloonMain/BalloonMainPanel.h:427` |
| `FMG_MSG_CALL_START_VIDEO_INVITE` | `BalloonChatWnd/BalloonChatWindow.cpp:857` | `BalloonMain/BalloonMainPanel.h:428` |

媒体类型在发起呼叫时就固定写进 `cmd_call_invite` 的 `media` 字段，此后无处可改。

**三是协议层完全没有切换媒体的能力。** 现有通话命令只有七条
（`flamingoserver/chatserversrc/Protocol.h:171-177`）：

```
cmd_call_invite        = 1701   //发起语音/视频通话
cmd_call_invite_notify = 1702   //推送：收到通话邀请
cmd_call_response      = 1703   //接听/拒绝通话
cmd_call_cancel        = 1704   //取消呼叫（接通前）
cmd_call_hangup        = 1705   //挂断（接通后）
cmd_call_state_notify  = 1706   //推送：通话状态变更
cmd_call_signaling     = 1707   //RTC 信令透传
```

全项目搜索 `switch_media` / `change_media` / `media_change` 均无命中。

### 2.3 一条走不通的捷径（据实证）

`cmd_call_signaling`(1707) 名字像通用透传通道，**实际不是**：服务端只在接通时用它向双方
下发中转参数（`flamingoserver/chatserversrc/ChatSession.cpp:2409-2413` 的两次 `sendToUser`），
并**没有**客户端→服务端方向的处理入口。因此无法借它捎带切换信令，必须新增命令。

### 2.4 引擎侧核实结果（据实证，2026-07-31 复核）

初稿此处是据推测，复核后**一半成立、一半推翻**，结论如下。

**成立**：`CallAudioEngine` 与 `CallVideoEngine` 确实是两个独立的类，各自有
`Start()` / `Stop()` / `IsRunning()`（`Call/CallAudioEngine.h:75,78,88`、
`Call/CallVideoEngine.h:89,92,102`），可以分别启停。第 6 节"只增删视频链路、音频原样
不动"的方向因此站得住。

**推翻**：`CallMediaSession` **目前不支持运行期切换**。

- `Start()` 把 `bool enableVideo` 作为入参（`Call/CallMediaSession.h:95-97`），视频开不开
  在会话建立时就定死，此后没有任何 `EnableVideo` / `StartVideo` 之类的接口。
- `Stop()` 是**整会话拆除**，按该头文件 25-27 行写明的顺序：关中转连接 → join 连接线程 →
  停并 join 视频解码线程 → 停两个引擎。全有或全无，无法只拆视频。
- 视频解码线程是会话级的（`VideoDecodeProc`），且该线程自带 `CoInitializeEx + MFStartup`。

**因此第 6 节的工作量比初稿设想的大**：需要给 `CallMediaSession` 新增运行期视频开关，
详见 6.1。好在改动是收敛的——只落在 `CallMediaSession` 内部，不需要重构音频引擎。

**仍未核实**：视频关闭期间收到对端视频包时能否安全丢弃，取决于 `OnRelayData` 与
`CallMediaFraming` 的分流方式，实施前须确认。

## 3. 已定决策（2026-07-31 与用户对齐）

### 3.1 语音升视频：不需要对方同意，但对方默认不开摄像头

一方发起升级即刻生效，双方界面都切到视频态，但**只有发起方自动打开摄像头**；对方摄像头
保持关闭，由其自己决定何时开启。

这样既省掉了"同意 / 拒绝"那一整套应答语义与等待中间态，又避免了未经确认就打开对方摄像头
的隐私问题。协议因此只需要一条请求 + 一条推送，见第 4 节。

由此推导出的交互模型（**会话媒体类型是服务端唯一跟踪的状态，各端摄像头开关是本地状态**）：

- **语音态**：底部有「切到视频」。点击 = 请求会话转视频，收到推送后本端开摄像头。
- **视频态**：底部有「关闭摄像头」与「切回语音」两个控件。
  - 「关闭摄像头」**只关自己的摄像头**，纯本地行为、不发请求，会话仍是视频态，对端画面
    照常，对端也仍可开自己的摄像头。
  - 「切回语音」才是请求会话降级，收到推送后双方一起回语音态、两端摄像头都关。

区分这两个控件是刻意的：只想关自己的画面，不应该连带把对方的视频也掐掉。

### 3.2 通话记录：按发起时的媒体类型记

通话结束留下的 `message_type_rtc` 记录，**以呼叫发起时的媒体类型为准**，中途切换不影响它。
因此本特性**不需要改动通话记录消息的字段与渲染**。

### 3.3 服务端与客户端同期改

服务端加切换命令的校验与双向推送，客户端同步接入。不做"先只改客户端"的拆法——那样对端
看不到你开了摄像头，阶段性成果不可用。

## 4. 协议设计

新增一对命令，编号接在现有通话命令之后：

```
cmd_call_switch_media         = 1708   //请求切换通话媒体类型
cmd_call_media_changed_notify = 1709   //推送：通话媒体类型已变更
```

`media` 字段复用现有的通话媒体类型枚举，不另立一套。

### 4.1 请求 `cmd_call_switch_media`

```json
{ "sessionid": "<会话id>", "media": 2 }
```

服务端 `CallManager` 校验顺序：

1. 会话存在，否则返回会话不存在；
2. 请求者是本次通话双方之一，否则返回无权限；
3. 会话状态为**已接通**，否则返回状态非法（响铃 / 呼出中一律拒绝，见 7.1）；
4. 目标媒体类型与当前不同，相同则幂等返回成功、不推送。

校验通过后更新会话记录的媒体类型，并向**双方**推送 `cmd_call_media_changed_notify`。

### 4.2 推送 `cmd_call_media_changed_notify`

```json
{ "sessionid": "<会话id>", "media": 2, "operator": "<发起切换者userid>" }
```

双方（含发起者本人）都收到，客户端据 `operator` 是否等于自己决定提示文案。

### 4.3 客户端处理原则

沿用撤回功能确立的模式：**发出请求后不动界面，一律等服务端推回通知才改**。这样本端与
对端看到的状态必然一致，也不会出现"本地已切换、服务端其实拒绝了"的假象。应答只用于
失败时提示原因。

> 撤回功能踩过的两个坑，本特性务必避开：
> 1. 新增 `FMG_MSG_*` 消息号必须**全文件查重**——`UserSessionData.h` 的偏移是分段编号、
>    区间重叠，同号且投给同一窗口会被消息映射里靠前的处理器抢走。
> 2. 新增从 socket 层投到 UI 的消息，除了在 `CMainDlg` 加消息映射，**还必须在
>    `CFlamingoClient::ProxyWndProc` 里加转发 case**，否则 `default` 分支直接丢弃、
>    堆对象泄漏。该文件 `UserSessionData.h:191-195` 已有醒目说明。

## 5. 客户端 UI 设计

### 5.1 从"一次性构建"改为"可重建"

把 `BuildUiOnce()` 拆成两层：

- **骨架层**（只建一次）：标题栏、置顶按钮、底部操作条容器。
- **媒体层**（可重建）：抽出 `ApplyMediaLayout(bool video)`，切换时销毁旧媒体层、构建
  新媒体层、重排。

### 5.2 统一以视频对话框为基座

语音态 = 视频态的布局，但画布区替换成**对端头像 + 昵称 + 通话计时**。这样窗口尺寸、
标题栏与底部按钮条的位置在切换前后保持稳定，**不会出现窗口跳变**。

### 5.3 底部操作条按媒体类型显隐

| 当前媒体 | 按钮 |
| --- | --- |
| 语音 | 切到视频、静音、挂断 |
| 视频 | 开启/关闭摄像头（纯本地）、切回语音（请求降级）、静音、挂断 |

视频态下「开启/关闭摄像头」与「切回语音」是**两个不同的控件**，语义区别见 3.1：前者只
影响自己的画面、不发请求；后者才请求会话降级、双方一起回语音态。按 3.1 的模型，被升级
的一方进入视频态时摄像头默认关闭，其界面上该控件呈「开启摄像头」态。

切换按钮**仅在 `m_mode` 为已接通时可用**，呼出中 / 响铃中不显示（见 7.1）。

## 6. 引擎设计

核心约束：**切换过程中音频链路不中断**。

### 6.1 给 `CallMediaSession` 新增运行期视频开关

这是本特性在引擎侧的主要工作量（原因见 2.4）。新增形如
`bool EnableVideo(bool on)` 的接口，只在 UI 线程调用，与既有 `Start` / `Stop` 的线程约定
一致：

- **开**：启动 `m_videoEngine`、拉起视频解码线程（该线程自带 `CoInitializeEx + MFStartup`）。
  中转连接 `m_relay` 与 `m_audioEngine` **原样不动**——这正是音频不中断的关键。
- **关**：先停并 join 视频解码线程（保证解码器不再被访问），再 `m_videoEngine.Stop()`，
  最后清掉显示 sink 持有的帧缓冲。顺序参照既有 `Stop()` 的拆除次序，避免并发访问。

`Start()` 的 `enableVideo` 入参保留，作为会话建立时的初值；`EnableVideo` 负责其后的变更。

### 6.2 各引擎的启停

- **语音升视频**：音频引擎与中转连接原样不动，只启动摄像头采集与视频编码、启动远端视频
  解码，把视频帧接入已有的中转通道。
- **视频降语音**：停止摄像头采集与编码、停止远端视频解码、释放画布持有的帧缓冲；音频
  链路继续运行。

摄像头不可用时走既有的 `SetCameraUnavailable(int reason)` 兜底：**保持在语音态并提示，
不得让整通通话中断**。

> 本节建立在 2.4 的推测之上，实施前须先读 `CallMediaSession` / `CallAudioEngine` /
> `CallVideoEngine` 的实现确认音视频链路确实可以独立启停。

## 7. 边界与异常

### 7.1 仅接通态可切换

呼叫建立过程中（呼出中、响铃中）不允许切换。客户端不显示切换按钮，服务端同时校验并
拒绝，两侧都设防。

### 7.2 双方同时请求

以服务端串行处理为准：先到的生效，后到的返回当前状态（而非报错），客户端据推送对齐。

### 7.3 切换超时

请求发出后启动超时计时（建议与呼叫超时同量级），超时未收到推送则回落到原媒体类型并
提示，不能让 UI 卡在中间态。

### 7.4 切换期间对方挂断

挂断优先：收到挂断推送即结束通话，丢弃尚未完成的切换请求。

## 8. 测试用例

### 8.1 可自动化（纯逻辑）

**客户端 `CallProtocolClient`（Catch2）**

- 构造 `cmd_call_switch_media` 请求：`sessionid` / `media` 字段完整，`sessionid` 为空或
  `media` 非法时拒绝构造。
- 解析应答：成功码与各类失败码（会话不存在 / 无权限 / 状态非法）可区分。
- 解析 `cmd_call_media_changed_notify`：取出 `sessionid` / `media` / `operator`；畸形
  JSON、缺字段、`sessionid` 为空一律安全失败且不产生半初始化结果。

**服务端 `CallManager` 状态机（doctest）**

- 仅已接通态允许切换；呼出中 / 响铃中 / 已结束一律拒绝。
- 非通话双方的请求被拒。
- 目标类型与当前相同时幂等返回成功且不推送。
- 双方同时请求时后到者返回当前状态。

**客户端切换状态机（Catch2）**

- 超时未收到推送时回落到原媒体类型。
- 切换途中收到挂断推送时，挂断优先、切换请求作废。

### 8.2 不可自动化（须实测，如实标注）

引擎启停（摄像头开关、音频不中断）、UI 媒体层重建、窗口尺寸稳定性、双端画面一致性
——这些依赖真实设备与消息循环，只能用两个真实客户端手动验证，不计入自动化覆盖。

## 9. 开发顺序

1. 先读引擎实现，确认 2.4 的推测（音视频链路可独立启停）。若不成立，回到第 6 节重做设计。
2. 定下第 3 节的三项待定决策。
3. 写协议编解码与状态机的测试用例，**与用户确认覆盖范围后**再写产品代码。
4. 服务端：`CallManager` 切换校验 + 双向推送。
5. 客户端：协议编解码 → 消息路由（注意第 4.3 节的两个坑）→ UI 媒体层重建 → 引擎启停。
6. 两个真实客户端联调。

## 10. 风险

- **引擎耦合风险**：若音视频链路无法独立启停，切换会导致音频瞬断，用户体验明显劣化，
  届时需要评估是否值得为此重构引擎。
- **摄像头设备风险**：切换到视频时摄像头被其它程序占用是常见情况，兜底路径必须走通，
  否则会从"切换失败"恶化成"通话中断"。
- **协议兼容风险**：新命令对旧版本客户端不可见。旧客户端收不到 1709 推送，会停留在原
  媒体类型，需要确认这种不一致的表现是否可接受，或在 `cmd_call_invite` 阶段协商能力。
