# 音视频通话：网络状况标识方案

本文描述一对一音视频通话窗里「网络状况标识」的技术方案：在通话中实时显示当前线路的质量（类似手机信号格），
质量变差时提示用户，并让开发者能从日志看出声音、画面在哪一段出了问题。群通话可在本方案落地后复用同一套统计与评级。

编写日期：2026-10-05

---

## 1. 目标

1. 通话窗底部栏显示一个四格信号图标，按线路质量显示 4 / 3 / 2 / 1 格并配色（绿 / 绿 / 橙 / 红），断流时显示灰色。
2. 鼠标悬停在图标上时显示具体数值：往返时延、丢包率、抖动、卡顿率，以及两个方向（我收对方、对方收我）各自的情况，
   还有当前线路（局域网直连 / 打洞直连 / 中转）。
3. 质量降到「较差」及以下时，在画面区浮出一句提示：本端收得差时提示「当前网络不佳，通话可能卡顿」，
   对方收得差时提示「对方网络不佳」。同一次降级只提示一次。
4. 每 5 秒在日志里记一条通话质量统计，排查「听不到」「卡顿」时能直接看出是采集、发送、网络、接收还是播放出了问题。

不在本方案范围：根据网络状况自动调整码率、分辨率（第 4 期之后另议，见第 9 节）。

---

## 2. 现状（据实证）

本节记的是 2026-10-05 起草时的现状。此后音频包的时间戳改为按帧序号计的媒体时间戳（《音视频通话方案》第 9.9.1、9.9.8 节），
播放端也有了补静音计数（第 11 节第 1 期）。

| 项目 | 现状 | 出处 |
| --- | --- | --- |
| 线路类型 | 已知：通话窗在走 P2P 时显示「P2P」徽章 | `BalloonCallDlg::SetLinkPath`、`P2PBadge.h` |
| P2P 链路统计 | DLL 提供 `m_rttMs`、`m_lossPermille`、`m_queuedBytes`，但往返时延与丢包率取自**可靠通道**的复用层（平滑往返时延、重传段数 / 发送段数）；通话只用数据报通道，这两个数**不能代表通话的实际质量** | `FlamingoP2PApi.h:164-165`、`P2PLinkSession.cpp:409-411` |
| P2P 音频序号 | 每个音频包带序号，接收端已能算出中间丢了几个（用于丢包补偿），但没有累计成丢包率 | `CallP2PFraming.cpp` `CallAudioSeqTracker` |
| 中转路径 | TCP 到 imgserver，不会丢包，但会积压、延迟变大；音频包**没有序号**，只有时间戳 | `CallMediaFraming.h` |
| 时间戳 | 两条路径上每个音视频包都带「会话相对毫秒」时间戳（发送端时钟） | `CallMediaSession::OnEncodedAudio` |
| 播放端 | 多路混音器取不够采样时补静音，但**没有统计补了多少** | `AudioStreamMixer::Mix` |
| 反馈通道 | 没有：发送端不知道对方收得怎么样 | — |
| 统计日志 | 没有：整条声音链路没有任何运行期计数 | — |

结论：画「网络状况」所需的原始数据大部分都能在现有收发点上就地采集，缺的是三样东西——**接收端的窗口统计、
发给对方的质量报告（顺带测往返时延）、把数值换算成档位的评级规则**。

## 3. 指标定义

每个统计窗口 1 秒，评级用最近 2 个窗口的数据。所有指标都在**接收端**测量，再通过质量报告告诉发送端。

| 指标 | 定义 | 测量位置 |
| --- | --- | --- |
| 丢包率 | 窗口内「应收音频包数 − 实收数」/ 应收数，千分比。P2P 由序号缺口算；中转路径恒为 0（TCP 不丢） | `CallMediaSession::OnDatagram` |
| 抖动 | RFC 3550 的到达间隔抖动：对每个音频包算 D = (到达时刻差) − (发送时间戳差)，J += (\|D\| − J) / 16，单位毫秒 | `OnDatagram` / `OnRelayData` |
| 卡顿率 | 播放端在「这一路仍在通话」时要采样却取不到、只能补静音的比例，千分比。这是用户最能直接感知的指标 | `AudioStreamMixer::Mix` |
| 往返时延 | 质量报告回带对方上一份报告的发送时刻与在本端的停留时长，RTT = 现在 − 回带时刻 − 停留时长（与 RTCP 的 LSR / DLSR 相同做法，不要求两端时钟同步） | 收到质量报告时 |
| 断流 | 连续 3 秒没有收到对方任何消息（音频、视频或质量报告）。不能只看音频：对方关麦克风时采集停止、音频包随之停发，但质量报告每秒照发 | 统计线程 |

发送端另记两项本地数据，只进日志、不参与评级：P2P 数据报发送失败次数（`m_p2pSendFailures`，已有）、
中转一次 `SendData` 的最长耗时（TCP 积压时会变长）。

## 4. 质量报告（新增的一种消息）

### 4.1 格式

两条路径各新增一种消息类型，负载相同，固定 24 字节、网络字节序：

| 偏移 | 长度 | 字段 | 含义 |
| --- | --- | --- | --- |
| 0 | 1 | 版本 | 当前为 1；收到更高版本时只读认识的字段 |
| 1 | 1 | 档位 | 本端对「我收对方」评出的档位（第 5 节，防抖后）；第 3 期之前填 0xFF（未评级），第 3 期起每份都填实际档位 |
| 2 | 2 | 丢包率 | 千分比 |
| 4 | 2 | 抖动 | 毫秒 |
| 6 | 2 | 卡顿率 | 千分比 |
| 8 | 8 | 回带时刻 | 上一次收到的对方报告里的发送时刻（对方的会话毫秒）；还没收到过时为 0 |
| 16 | 4 | 停留时长 | 上一次收到对方报告到发出本报告之间的毫秒数 |
| 20 | 2 | 播放缓冲延迟 | 毫秒：这一秒正常播放时抖动缓冲中已收到、还没播放的平均时长（2026-10-06 起占用原保留字段，《音视频通话方案》第 9.9.9 节） |
| 22 | 1 | 标志位 | 按位或：0x01 本端能接收电脑声音，0x02 本端正在共享电脑声音；旧版本为 0（2026-10-06 起，《音视频通话方案》第 10 节） |
| 23 | 1 | 保留 | 填 0 |

本报告自身的发送时刻沿用两种封装头里已有的时间戳字段。

- 中转路径：`CallMediaKind` 新增 `call_media_kind_stats = 3`，分片标志恒为 whole。
- P2P 路径：`CallP2PKind` 新增 `call_p2p_kind_stats`，序号字段填报告序号。

每秒发一份。报告很小，每秒约 50 字节，对带宽没有影响。

### 4.2 不考虑老版本客户端

2026-10-05 用户决定：不需要兼容不支持质量报告的老版本客户端。接通后每秒都发报告，不做试探、不停发，
也不判断对方是不是老版本。还没收到对方报告时（刚接通，或对方的报告在路上），往返时延与「对方收我」两项暂时没有数据。

（附注：据实证，老版本遇到这种未知类型不会出功能问题——中转路径的分流只返回错误、不重置视频重组状态，P2P 路径只记一条
警告后丢弃——只是每收到一份报告记一行日志。按上面的决定，不再为此做处理。）

## 5. 评级规则

档位取值：4 良好、3 一般、2 较差、1 很差、0 断流。按下表从上往下判，**同时满足**某一行所有条件即取该档：

| 档位 | 往返时延 | 丢包率 | 抖动 | 卡顿率 |
| --- | --- | --- | --- | --- |
| 4 良好 | < 200 ms | < 2% | < 30 ms | < 2% |
| 3 一般 | < 400 ms | < 5% | < 60 ms | < 5% |
| 2 较差 | < 800 ms | < 15% | < 120 ms | < 15% |
| 1 很差 | 其余情况 | | | |
| 0 断流 | 连续 3 秒没收到对方任何消息 | | | |

2026-10-06 起另加第五项「播放缓冲延迟」，门限 120 / 250 / 500 毫秒（良好 / 一般 / 较差），见《音视频通话方案》第 9.9.9 节。

往返时延未知时按良好处理（只看其余各项）。以上门限参考的是常见 VoIP 质量经验值；第 3 期 3d 在中转路径上做了弱网实测，
各档按门限正常切换，门限暂未调整（见第 11 节 3d 的结论 5）。

**防抖**：变差立即生效会让图标频繁跳动。规则是——降档需要连续 2 个窗口都落在更低档；升档需要连续 3 个窗口都落在
更高档；断流立即生效、恢复收包后立即解除。

**显示哪个方向**：图标显示两个方向中**较差**的那一档（「我收对方」由本端算，「对方收我」取对方报告里的档位），
因为任何一个方向差，通话体验都差。提示文字按差在哪个方向分别措辞（第 1 节第 3 条）。

评级是纯函数（输入窗口指标与上一次的档位、连续计数，输出新档位），不碰窗口与网络，可以直接写单元测试。

## 6. 模块划分

| 模块 | 类型 | 职责 |
| --- | --- | --- |
| `Call/CallNetStats.h/.cpp` | 纯逻辑 | 接收端窗口统计（丢包、抖动、断流计时），质量报告的编码与解析，往返时延计算 |
| `Call/CallNetQuality.h/.cpp` | 纯逻辑 | 第 5 节的评级与防抖；档位到图标格数、颜色、提示文字的映射 |
| `AudioStreamMixer` | 小改 | 每路新增「补静音的采样数」与「请求的采样数」计数，供卡顿率使用 |
| `CallAudioEngine` | 小改 | 透出发送包数、各路接收与卡顿计数、本人采集电平（已有）的快照接口 |
| `CallMediaSession` | 改 | 在 `OnDatagram` / `OnRelayData` 收包处喂统计；新增一个统计线程，每秒结算窗口、发质量报告、每 5 秒写日志；向 UI 线程投「档位变化」事件 |
| `CallController` | 小改 | 收到档位变化事件后转给通话窗 |
| `BalloonCallDlg` | 改 | 底部栏新增信号图标（`DuiImage` + `DuiToolTipMgr`，位图用 GDI+ 预画，不动 balloonui）、画面区的降级提示 |

统计线程独立于采集线程与 UI 线程：麦克风静音时采集线程停了，UI 线程忙时定时器会延后，两者都不适合驱动统计。

## 7. 日志

统计线程每 5 秒记一条（英文，符合日志规范），例如：

```
call stats: session=..., path=p2p, sent audio=250 video=150, recv audio=248 lost=2 (8 permille), jitter=12 ms,
stall=0 permille, rtt=34 ms, peer: grade=4 loss=0 stall=0, my grade=4, capture rms=812
```

一条就能看出：本端是否在发（sent）、对方的包是否到了（recv / lost）、播放端是否断粮（stall）、麦克风有没有声音
（capture rms）。今天排查「听不到声音」时最缺的正是这一行——它要是存在，日志里会直接显示两端都在以无设备模式运行、
采集电平恒为 0。

另外，无设备模式（`FLAMINGO_CALL_NO_AUDIO=1`）启动时改记 WARNING，并在通话窗画面区显示一行「调试模式：未使用麦克风和扬声器」，
避免再被误认为故障（此项与网络状况无关，可单独先做）。

## 8. 测试用例

### 8.1 可自动化（纯逻辑，FlamingoUnit，标签 `[callnet]`）

- **NS1 丢包率**：序号连续时为 0；中间缺 5 个、共应收 100 个时为 50‰；序号回绕（0xFFFFFFFF → 0）不误算。
- **NS2 抖动**：到达间隔与发送间隔完全一致时抖动为 0；到达间隔交替 10 / 30 ms（发送间隔 20 ms）时抖动收敛到约 10 ms。
- **NS3 断流**：最后一个包之后 2.9 秒判为未断流，3 秒判为断流；收到新包立即恢复；只有质量报告、没有音频包（对方关了麦克风）时不判断流，丢包率为 0。
- **NS4 质量报告编解码**：编出 24 字节，各字段原样解回；长度不足拒绝；版本更高时只读前面的字段。
- **NS5 往返时延**：回带时刻 1000、停留 30 ms、现在（对方时钟换算后）1100 → 70 ms；回带时刻为 0 时不更新。
- **NQ1 评级**：表中每一档的边界值（如往返时延 199 / 200 ms）分别落在正确的档；往返时延未知时只看其余三项。
- **NQ2 防抖**：一个窗口变差不降档、连续两个降档；升档要连续三个；断流立即生效。
- **NQ3 两个方向取较差**：我收 4、对方收 2 时显示 2，提示文字是「对方网络不佳」。
- **NQ4 不考虑老版本**：一直收不到对方报告时每份报告照常填写、回带字段为 0、没有往返时延；收到后下一份开始回带。
- **ASM6 卡顿计数**：一路只推入半帧时，混音一帧后该路的补静音计数为半帧。

### 8.2 半自动（实网，`[.live]`）

- 用 CL1 / CL2 的双账号框架，两端跑无设备模式的通话 10 秒，断言双方都收到对方的质量报告、往返时延非 0、档位为良好。

### 8.3 不可自动化

- 弱网下的实际观感：用 Windows 上的弱网工具（如 clumsy）对 imgserver 端口或 P2P 端口注入 5% / 15% 丢包、200 ms 延迟，
  人工核对图标档位、悬停数值与提示文字是否与体感一致，并据此调整第 5 节的门限。

## 10. 风险

- **门限是经验值**：第 5 节的数字只在中转路径上实测过（第 11 节 3d），P2P 路径的丢包门限仍未实测。
- **中转路径看不到丢包**：TCP 下网络差表现为延迟与卡顿而不是丢包，所以中转路径主要靠往返时延与卡顿率判断；
  这是 TCP 中转本身的特性，不是统计缺陷。
- **统计线程与收包线程并发**：计数用原子变量或在统计对象内加锁，窗口结算时一次性取走，避免收包线程等待。
- **不兼容老版本**：按第 4.2 节的决定，与不支持报告的老版本通话时，对方每秒会多记一行日志，本端没有往返时延与「对方收我」的数据。

## 11. 落地记录

### 第 1 期（2026-10-05）：接收端统计、统计日志、无设备模式提示

| 内容 | 实现 | 测试 |
| --- | --- | --- |
| 接收端窗口统计（丢包、抖动、断流） | 新增纯逻辑 `Call/CallNetStats.h/.cpp`（`CallRecvStats`），与第 3 节的定义一致；断流门限 `kCallSilentMs` = 3000 | NS1~NS3（`[callnet]`） |
| 播放端补静音计数 | `AudioStreamMixer::GetPlayoutCounters`：每路累计「请求采样数 / 补静音采样数」 | ASM6 |
| 发送计数 | `CallAudioEngine::EncodedPacketCount`、`IsWithoutDevices`；会话里计发出与收到的视频帧数 | CAE1 补了断言 |
| 会话接入与统计日志 | `CallMediaSession`：两条收包路径把音频包交给 `CallRecvStats`（P2P 带序号、中转不带），其它消息只刷新断流计时；路径确定时复位统计（连接阶段不算断流）；新增统计线程，每秒检查断流（状态变化时记 WARNING / INFO），每 5 秒记一条 `call stats:` 日志；`Stop` 时最先停掉统计线程 | 2026-10-06 两个客户端实际通话的日志里每 5 秒一条 `call stats:`（见 `bugs.md` BUG-118 的现象一节） |
| 无设备模式提示 | `FLAMINGO_CALL_NO_AUDIO=1` 时改记 WARNING 并投递 `call_relay_no_audio_devices`，通话窗在大画面顶部画琥珀色提示条「调试模式：未使用麦克风和扬声器（FLAMINGO_CALL_NO_AUDIO=1）」（`CallVideoCanvas::SetBannerText`） | CVB1（`[callux]`）；事件链路只编译通过 |

统计日志示例（字段含义见第 7 节）：

```
call stats: session=..., path=p2p, link path=1, audio=devices, mic=on, volume=100%, sent audio=250 video=0,
p2p send failures=0, recv audio=249 lost=1 (4 permille) late=0 video=0, jitter=3 ms, playout concealed=12 permille,
capture rms=640, peer silent=0.
```

- `audio=no-devices` 即无设备模式，`audio=stopped` 表示音频引擎没有启动成功；`capture rms` 恒为 0 说明麦克风没有声音（设备静音、隐私设置禁止或关了麦）。
- `playout concealed` 是这 5 秒播放端补静音的比例；对方关麦或断流时会接近 1000，须结合 `recv audio` 一起看（第 3 期评级时处理）。
- 验证方法：两个客户端互拨一通，在两边的 `Logs/flamingo.*.log` 里搜 `call stats:`，应每 5 秒一条，`sent audio` 与对方的 `recv audio` 都约为 250。

### 第 2 期（2026-10-05）：质量报告与往返时延

| 内容 | 实现 | 测试 |
| --- | --- | --- |
| 报告编解码 | `CallNetStats.h` 的 `CallQualityReport` / `BuildCallQualityReport` / `ParseCallQualityReport`，格式与第 4.1 节一致；档位第 3 期之前填 0xFF（未评级） | NS4 |
| 往返时延 | `CallReportExchange`：回带对方上一份报告的发送时刻与停留时长，RTT = 收到时刻 − 回带时刻 − 停留时长；不考虑老版本，接通后每秒都发 | NS5、NQ4 |

**实网用例 CRL1**（`Source/Tests/CallReportLiveTests.cpp`，标签 `[.live][callreport]`，默认不运行）：两个 `CallMediaSession` 在同一进程里经一台真实 imgserver 中转互连（无设备模式、自签中转令牌，不登录账号、不联 chatserver），断言双方各收到至少 3 份对方报告、都算出了往返时延且小于 1 秒，日志里有 `call stats:` 与 `first quality report from peer`。运行前设三个环境变量（没设时自动跳过）：

```
FLAMINGO_TEST_RELAY=127.0.0.1:<imgserver 的 relaylistenport>
FLAMINGO_TEST_RELAY_TOKENKEY=<该 imgserver 的 relaytokenkey>
FLAMINGO_TEST_SERVER_PUBKEY_FILE=<该 imgserver 的 etc/server_key.pub>
FlamingoUnit.exe "[callreport]"
```

2026-10-05 用一台只跑 imgserver 的私有实例（端口 29102～29105）运行通过，日志实录：两端都记了 `first quality report from peer, version=1`；统计行为 `path=relay, audio=no-devices, ... peer silent=0, rtt=0 ms, peer reports=4`（去掉老版本兼容后的复测结果）。没有音频包（无设备模式下没有采集）时仍未判为断流，说明报告刷新断流计时生效。

**已知局限**：会话时间戳取自 `GetTickCount64`（精度约 16 毫秒），本机中转的往返时延短于这个精度，显示为 0；真实网络的往返时延通常在几十毫秒以上，暂不影响。若第 3 期要细分局域网直连的时延，改用高精度时钟。

### 第 3 期 3d（2026-10-06）：弱网校准（自动测量部分）

**方法**：新用例 CRL2（`Source/Tests/CallReportLiveTests.cpp`，标签 `[.live][callcal]`，默认不运行）在同一进程里开主叫、被叫两个 `CallMediaSession`，经一台私有 imgserver 走中转；音频用无设备模式，两端各开一个线程每 20 毫秒经 `CallMediaSession::FeedTestCapture` 喂一帧 440Hz 正弦波、经 `PullTestRender` 取一帧播放（运行期间 `timeBeginPeriod(1)`，节奏均匀），让音频包真的在中转上流动；每秒记录双方的档位、往返时延、丢包、抖动、卡顿，写成 CSV。中转连接前面夹一个弱网代理（两个方向加固定延迟、不乱序的随机抖动、周期性卡顿）。注意两端都经过代理，往返要过四道延迟，**往返时延约为单向延迟参数的 4 倍**。

**结果**（每种条件 20 秒，取后半段、两端合计；往返时延与抖动单位毫秒，卡顿单位千分比）：

| 条件 | 往返时延 | 抖动 | 卡顿 | 稳定档位 |
| --- | --- | --- | --- | --- |
| 基线 | 2 | 3.0 | 1.0 | 4 良好 |
| 单向延迟 60 | 268 | 8.0 | 0 | 3 一般 |
| 单向延迟 120 | 497 | 8.8 | 0 | 2 较差 |
| 单向延迟 250 | 1019 | 6.0 | 0 | 1 很差 |
| 单向延迟 450 | 1834 | 7.0 | 0 | 1 很差 |
| 随机抖动 0～40 | 124 | 15.2 | 0 | 4 良好 |
| 随机抖动 0～80 | 242 | 21.0 | 0 | 3 一般 |
| 随机抖动 0～160 | 479 | 23.6 | 1.0 | 2 较差 |
| 每 2 秒卡 200 | 123 | 3.4 | 0 | 4 良好（前段有 4 秒为一般） |
| 每 2 秒卡 500 | 0 | 6.2 | 0 | 4 良好 |

**结论**：

1. 指标链路是对的：往返时延随注入的延迟线性增长，各档位按第 5 节的门限切换，条件不变时档位稳定、没有来回跳。
2. 中转走 TCP，网络抖动主要表现为往返时延变大；RFC 3550 抖动值远小于注入的随机延迟（TCP 不乱序，晚到的包把后面的包一起拖住），所以抖动门限在中转路径上很少起作用，档位主要由往返时延决定。
3. **校准中发现并修复了一个缺陷**：中转握手只等 500 毫秒，握手往返超过 0.5 秒时通话直接连不上（`bugs.md` BUG-109）。修复前单向延迟 250、450 与每 2 秒卡 500 三种条件都没有建立通话，修复后都能建立。远程桌面与文件夹传输的中转客户端有同样的写法，未改。
4. **发现评级的一个盲区**：当时播放端的抖动缓冲只增不减，一次卡顿后延迟被永久抬高（最多 1 秒），卡顿率只在第一次取空时有数，往返时延又不含播放缓冲。每 2 秒卡 500 毫秒时图标一直显示「良好」。2026-10-06 已修复：改用 speexdsp 抖动缓冲，并把播放缓冲延迟纳入质量报告与评级，见《音视频通话方案》第 9.9.8、9.9.9 节。
5. 门限暂未调整：数据说明门限按设计工作，但「多大的往返时延算良好」是体验判断，测量回答不了。可参考 ITU-T G.114（单向 150 毫秒以内对大多数应用透明），把「良好」的往返时延上限由 200 放宽到 300，待用户决定。

**未覆盖**：
- 丢包：中转是 TCP，丢包恒为 0；P2P 直连（UDP，会丢包）在同一台机器上走局域网直连，没有插代理，丢包门限仍未实测。
- 人工核对听感与界面：需要正式编译整个客户端后，由用户在真实通话中核对。
