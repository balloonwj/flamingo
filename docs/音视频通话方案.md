# 音视频通话方案与开发计划

> 作者：balloonwj@qq.com　起草日期：2026-06-11
> 用途：记录给 flamingoclient 接入音视频聊天（参考 RustDesk）的整体方案、分期路线，以及第一期的详细开发计划与测试用例场景。后续每期开工前据此细化、收尾后回填实际结果。

---

## 1. 背景与目标

给 flamingoclient（Windows MFC + balloonui 客户端）接入 1 对 1 音视频通话，参考 RustDesk 的传输与信令思路，但结合本仓库已有的基础设施落地，尽量复用、少造轮子。

最终形态是摄像头 + 麦克风的双向音视频通话；按风险从低到高分期推进，第一期只打通信令与中转骨架。

---

## 2. 现状盘点（据实证，均已核对代码位置）

本节记的是 2026-06-11 起草时的现状，行号与「尚未实现」「完全没有」一类的说法只对当时的代码成立。

### 2.1 协议号段早已为音视频预留

`flamingoserver/chatserversrc/Protocol.h:170-177` 已经定义好音视频通话信令枚举（`1701-1707`），但服务端与客户端都尚未实现：

| 号 | 枚举 | 含义 |
| --- | --- | --- |
| 1701 | `cmd_call_invite` | 发起语音/视频通话 |
| 1702 | `cmd_call_invite_notify` | 推送：收到通话邀请 |
| 1703 | `cmd_call_response` | 接听/拒绝通话 |
| 1704 | `cmd_call_cancel` | 取消呼叫（接通前） |
| 1705 | `cmd_call_hangup` | 挂断（接通后） |
| 1706 | `cmd_call_state_notify` | 推送：通话状态变更 |
| 1707 | `cmd_call_signaling` | RTC 信令透传（SDP/ICE/屏幕共享控制） |

错误码方面，`Protocol.h` 注释约定 `700-799` 段为音视频域，目前尚未填具体值。

### 2.2 远程桌面是最佳参考范本，已达生产级完成度

远程桌面功能（`balloonwj@qq.com 2026-06-08`）的传输架构与音视频高度相似，可直接对标仿写：

- 信令（`1710-1716`）走 chatserver 主连接（端口 20000）。
- 字节流（`cmd_rd_relay_hello=1853` 握手 / `cmd_rd_relay_data=1854` 数据）走 imgserver 上一个独立的中转端口。
- `RelayToken`（`utils/RelayToken.h`，HMAC-MD5 签名、`payload = sessionid|role|uid|peeruid|expire`，5 分钟有效期）做配对鉴权。
- imgserver 端 `RelayHub`（配对表）/ `RelaySession`（会话）/ `RelayServer`（独立端口）做纯字节透传——不解析、不解压、不转码，只按 sessionid 把两条连接配对后原样转发整帧。

关键代码位置：

- 客户端信令编解码：`flamingoclient/Source/net/RemoteDesktopProtocolClient.h`
- 服务端会话管理：`flamingoserver/chatserversrc/RemoteDesktopManager.h`
- 令牌：`flamingoserver/utils/RelayToken.h`
- 中转会话：`flamingoserver/imgserversrc/RelaySession.cpp`（`onRead` 按帧 `cmd` 区分握手/数据，`onData` 原样转发）
- 中转配对表：`flamingoserver/imgserversrc/RelayHub.h`
- 中转服务器：`flamingoserver/imgserversrc/RelayServer.h`

**对工作量影响最大的发现：** `RelaySession` 对承载内容完全不解析（屏幕帧还是音频帧对它都是黑盒字节），因此 `RelayHub` / `RelayToken` / `RelayServer` 几乎可以零改动复用，只需让 `RelaySession::onRead` 认识音视频的两个新 cmd。

### 2.3 客户端目前完全没有音视频能力

经核查，客户端没有摄像头采集、麦克风采集、任何编解码（H.264/VP8/Opus 都没有）、DirectShow / Media Foundation 接入。第三方库只链接了 jsoncpp、zlib、sqlite、WTL，没有任何媒体相关库。唯一沾边的是 `NotificationSound` 模块，但它只是用 `sndPlaySound` 放提示音 wav，跟实时音视频管线无关。

所以媒体管线是真正要从零搭的部分，也是整个功能 80% 的工作量和风险所在——这是分期把它后置的根本原因。

### 2.4 客户端独立服务器连接可作模板

客户端连第二条服务器连接已有成熟做法：`Source/net/FileTransfer.cpp` 的 `FileServerConn`（独立 TCP、握手、收发、销毁，群文件用了最多 3 条并发连接池）。音视频的中转独立连接可仿照它，更直接的是仿远程桌面的 `RdRelayClient`。

## 3. RustDesk 对照（参考 references/rustdesk/）

RustDesk 的核心思路：rendezvous（信令）服务器做对端发现，优先 P2P 打洞直连，打洞失败回落 relay 服务器中转；视频用 libvpx（VP8/VP9）或硬件编码，音频用 Opus，音频处理用 WebRTC 的回声消除模块。

需要注意：RustDesk 本质是远程桌面/屏幕共享工具，而本功能要做的是摄像头 + 麦克风的双向通话。传输、信令、中转这几层两者高度相似（flamingo 的远程桌面其实已把这套思路实现了一遍），真正差异在采集源（摄像头/麦克风 vs 抓屏）和音频处理（通话必须做回声消除，屏幕共享不用）。

## 4. 关键决策（已与用户对齐）

| 决策项 | 选择 | 说明 |
| --- | --- | --- |
| 传输路径 | 先纯服务器中转，预留 P2P 接口 | 第一版只做中转跑通，但信令与接口按将来能插入 P2P 打洞的方式设计，第四期再补打洞回落 |
| 编解码选型 | libvpx(VP8) + Opus | 贴近 RustDesk；第一期纯语音只需 Opus，libvpx 留到第三期做视频 |
| 首期功能范围 | 1 对 1 纯语音通话先打通 | 先把信令、中转、抖动缓冲、回声消除这些最难的基础设施跑通，视频作为第二/三期叠加 |
| 首期交付边界 | 先协议层 + 中转骨架 | 对齐远程桌面一期节奏，媒体管线后置 |

## 5. 分期路线图

- **第一期——信令协议层 + 中转骨架（本期）。** 打通"呼叫→振铃→接听→建立中转通道→挂断"的信令与通道链路，中转通道上用假数据验证转发通了，不接真实音频。
- **第二期——音频媒体管线（纯语音端到端可通话）。** 引入 Opus 编解码、回声消除/降噪（WebRTC APM 或 speexdsp 的 AEC/AGC/NS）、WASAPI 麦克风采集与播放、抖动缓冲、丢包隐藏，配 balloonui 的振铃窗与通话中窗。交付标准是两台机器真实语音通话、无明显回声。
- **第三期——视频（libvpx VP8）。** 引入 libvpx，接摄像头采集（Media Foundation 优先），做 VP8 编解码、音视频时间戳同步、码率自适应，加本地预览 + 远端画面的视频通话界面。
- **第四期——兑现预留的 P2P 接口 + 优化。** 经 `cmd_call_signaling(1707)` 交换候选地址做 STUN 式打洞，打洞失败回落到中转链路；视情况再做群组会议。

## 6. 第一期详细设计

### 6.1 范围界定

要做到：两端完整走完「主叫发起 → 被叫振铃 → 接听 → 双方各自连上 imgserver 中转通道并握手配对成功 → 在中转通道上互发测试帧验证转发通了 → 挂断收尾」，覆盖拒绝、取消、超时、对方离线、对方忙这些分支。

明确不做：真实麦克风采集、Opus 编解码、回声消除、声音播放（都属第二期）。中转通道第一期发的是假测试字节帧，只为验证「令牌配对 + 字节透传」链路真的通。

### 6.2 协议契约（客户端 / 服务端共享，须先定死）

信令 body 全部为 JSON，64 位 userid 一律按字符串编码（避免大整数精度丢失，这是远程桌面已踩过的坑）：

| 消息 | 方向 | body |
| --- | --- | --- |
| `cmd_call_invite` 1701 | 主叫→server | 请求 `{"peerid":"<被叫id>","media":1}`；应答 `{"code":0,"msg":"ok","sessionid":"<uuid>"}` |
| `cmd_call_invite_notify` 1702 | server→被叫 | `{"sessionid":"...","fromid":"<主叫id>","fromname":"昵称","media":1}` |
| `cmd_call_response` 1703 | 被叫→server | 请求 `{"sessionid":"...","accept":1}`（1接受/0拒绝）；应答 `{"code":0,"msg":"ok"}` |
| `cmd_call_cancel` 1704 | 主叫→server | `{"sessionid":"..."}`（接通前撤回） |
| `cmd_call_hangup` 1705 | 任一端→server | `{"sessionid":"..."}`（接通后挂断） |
| `cmd_call_state_notify` 1706 | server→双方 | `{"sessionid":"...","state":<n>,"msg":"..."}` |
| `cmd_call_signaling` 1707 | server→双方 | 第一期承载中转参数 `{"sessionid":"...","role":<n>,"relayip":"...","relayport":N,"token":"..."}`；第四期复用此通道传 SDP/ICE |

`media` 字段第一期固定为 1（纯音频），现在就留好，第三期视频置 2，协议不必再改。

新增枚举（对标远程桌面 `rd_state` / `rd_role`）：

- 通话状态 `call_state`（随 1706 推送）：响铃中=1、已拒绝=2、已取消=3、对方离线=4、超时=5、已接通=6、已结束=7、对方忙=8。
- 通话角色 `call_role`（随 1707 下发）：主叫=1、被叫=2。

错误码用 `700-799` 段，第一期需要：对方离线、对方忙、会话不存在。

新增中转字节流 cmd（紧挨远程桌面的 1853/1854）：

- `cmd_av_relay_hello` = 1855（连上 imgserver 中转后首帧握手，body 带令牌，与 1853 同结构）。
- `cmd_av_relay_data` = 1856（音频帧透传，imgserver 原样转发不解析，与 1854 同处理）。

完整信令时序：

```
主叫A                  chatserver                   被叫B
  │── 1701 invite ────────→│                          │
  │←─ 应答(sessionid) ──────│── 1702 invite_notify ───→│
  │←─ 1706 state(响铃) ─────│                          │ (弹振铃框)
  │                         │←──── 1703 response(接受) ─│
  │                         │ 建会话、给双方各签RelayToken
  │←─ 1707 signaling(中转参数)│ 1707 signaling(中转参数) →│
  │←─ 1706 state(已接通) ────│ 1706 state(已接通) ──────→│
  │                                                    │
  │═══ 连 imgserver:中转端口, 1855 握手, 1856 互发 ═══════│ (第一期发测试帧)
  │                                                    │
  │── 1705 hangup ─────────→│── 1706 state(已结束) ────→│
```

分支：被叫拒绝走 `state(已拒绝)`、主叫取消走 `state(已取消)`、振铃超时走 `state(超时)`、被叫不在线走 `state(对方离线)`、被叫已在另一通话走 `state(对方忙)`。

### 6.3 服务端开发任务

1. `Protocol.h`：新增 1855/1856 两个中转 cmd、`call_state` / `call_role` 枚举、700 段错误码（纯定义）。
2. `chatserversrc/CallProtocol.{h,cpp}`（仿 `RemoteDesktopProtocol`）：1701-1707 信令的 JSON 编解码。
3. `chatserversrc/CallManager.{h,cpp}`（仿 `RemoteDesktopManager`）：会话表 + 状态机 + UUID sessionid 生成 + 接听后给双方签 `RelayToken` + 下发中转地址；含振铃超时清理与「对方忙」判断（被叫已在活跃会话里）。
4. `ChatSession.cpp`：增加 `onCallInvite/onCallResponse/onCallCancel/onCallHangup` 分发分支（对标现有 `onRemoteDesktop*`），以及给对端推 1702/1706/1707 的发送逻辑。

7. `main.cpp` / 配置：`CallManager` 单例初始化，复用现有 `relaytokenkey` 与 imgserver 中转地址配置。

### 6.4 客户端开发任务

（下面的 `Source/...` 路径与 `CMainDlg` 是起草时的位置。2026-08-19 `CMainDlg` 删除；2026-10-02 一对一通话的客户端代码整体搬进 FlamingoMedia.dll：`CallProtocolClient`、`CallRelayClient` 现在在 `flamingoclient/FlamingoMedia/Call/`，信令路由与通话状态机由同目录的 `CCallController` 负责。）

2. `Source/net/CallProtocolClient.{h,cpp}`（仿 `RemoteDesktopProtocolClient`）：信令编解码，纯逻辑、配 Catch2 单测。

### 6.5 开发顺序（按依赖关系）

先做协议层（服务端 `CallProtocol` + 客户端 `CallProtocolClient`，各带单测，可独立验证）→ 服务端会话状态机 `CallManager`（带单测）→ 接 `ChatSession` 分发 → 中转层 `RelaySession` 扩展（带单测验配对）→ 客户端 `IUSocket` 信令接口 + `CMainDlg` 路由 → `CallRelayClient` → 最小 UI。每一层先让单测绿了再往上接。

## 7. 第一期测试用例场景

测试框架沿用现成的——客户端 Catch2、服务端 doctest，都不新引入。

### 7.1 客户端 `CallProtocolClient`（Catch2）

- 邀请请求编码：`buildInvite(peerId, media)` 产出 JSON 含字符串型 peerid、整型 media。
- 邀请应答解析：正常含 code/sessionid 能解出；缺 code 返回 false；非法 JSON 返回 false。
- 邀请推送解析：正常解出 sessionid/fromid/fromname/media；重点验大 userid（如 10000000000000001）按字符串解析不丢精度。
- 应答（接受/拒绝）请求编码：accept 字段正确为 1/0。
- 取消 / 挂断请求编码：sessionid 原样带回。
- 状态推送解析：8 种 state 都能解出；缺 sessionid 返回 false。
- 中转参数（1707）解析：role/relayip/relayport/token 都能解出；缺 token 返回 false。
- 中转握手帧编码 + 握手应答解析：与远程桌面同结构。

### 7.2 服务端 `CallManager` 状态机（doctest）

- 发起邀请：建会话、状态=响铃、返回非空 UUID sessionid、sessionid 不含 `.` / `|`（令牌分隔符）。
- 被叫接听：会话转「已接通」，给主叫和被叫各签出一枚 RelayToken，两枚 token 的 sessionid 相同、role 相反、uid/peeruid 对调。
- 被叫拒绝：会话被清除，再查不到。
- 主叫接通前取消：会话被清除。
- 任一端挂断：会话被清除。
- 振铃超时：超过时限的会话能被超时清理逻辑识别并清除。
- 对方忙：被叫已在活跃会话里时，新邀请返回「对方忙」、不建新会话。
- 幂等/防御：对已清除会话再 hangup/response 不崩、返回失败。

### 7.3 服务端 `RelayToken` 复用（doctest）

- 新增的 `role_caller` / `role_callee` 能正确签发与校验、role 字段回填正确。
- 篡改签名校验失败；过期（now ≥ expire）校验失败；缺字段/格式非法校验失败。

### 7.4 服务端 `RelayHub` 音视频配对（doctest）

- 同一 sessionid 的主叫端、被叫端先后 join，彼此能 `getPeer` 取到对端。
- 音视频会话 sessionid 与远程桌面会话 sessionid 不串话（各自只配对自己那条）。
- 同角色重复 join 失败；会话满两端后第三方 join 失败。
- 一端断开后 `leaveByConn` 返回对端供连带关闭。

### 7.5 端到端联调（需两个真实客户端，手动验证，不在自动化测试内）

接通后双方各自连上 imgserver 中转端口、1855 握手配对成功、A 经 1856 发一帧测试数据 B 能原样收到；任一端挂断后双方 UI 正确收尾。第一期收尾时人工跑，并按测试规范在连接生命周期、握手、配对、转发各处打 `LOGI` / `LOGF`。

## 8. 风险与待办

- 媒体管线（第二、三期）是最大的技术不确定性来源：回声消除、抖动缓冲、音视频同步、码率自适应每一项都有坑。第二期开工前应先做一个本地回环的技术验证（采集→编码→解码→播放）再铺开。
- 第二期需评估引入 Opus + 回声消除库（WebRTC APM 或 speexdsp）的工程接入方式（源码内嵌还是预编译 lib），并与用户对齐。
- 第三期引入 libvpx 同理。
- 中转服务器要承担所有音视频码流的带宽，纯中转方案在公网大规模下的成本需在第四期 P2P 打洞时一并评估。

> 认知诚实声明：第 2 节「现状盘点」各结论均已核对代码位置（据实证）；第 8 节关于性能、带宽、各编解码库接入难度的判断目前仍是据推测，尚未在本项目实测，第二期动手前会先做技术验证。

## 9. 增强：自适应抖动缓冲（2026-10-06，用户选定方案 B，已实施）

### 9.1 现状（据实证，均已核对代码）

- 每一路远端声音一个 `PcmRingBuffer`，容量 1 秒（`FlamingoMedia/Call/AudioStreamMixer.cpp` 第 17、52 行）。收到的包在收包线程上解码，整帧（48 kHz 单声道 960 个采样，20 毫秒）写入（`PushEncoded`）；声卡的播放线程每次按声卡缓冲的空余量取数据（`Mix`，`WasapiAudioIo.cpp` 第 501～514 行），有多少取多少，不够的部分补零、计为卡顿。
- 没有起播门槛、没有目标深度、没有任何降延迟的处理；只有缓冲满时丢掉新来的数据（`AudioPcmUtils.cpp` 第 95～104 行）。
- 后果（弱网校准实测，见《音视频通话-网络状况标识方案》第 11 节 3d）：网络卡一下之后，积压的数据一次到达，把缓冲垫高一截，收发速率相同，此后不再回落——**声音延迟被永久抬高，最多 1 秒**；之后同样长度的卡顿都被吸收，卡顿率只在第一次取空时有数，信号图标看不出来。
- 共用这套混音器与缓冲的有三处：一对一通话（`CallMediaSession`）、屏幕共享的语音与电脑声音（`ShareAudioSession`，每个席位两路）、群通话（`GroupCallMediaSession`，内部也是 `ShareAudioSession`，开了 DTX）。语音消息与录屏各有自己的缓冲，不受影响。
- 回声消除的参考信号取的是 `Mix` 之后实际送往声卡的声音（`CallAudioEngine.cpp` 第 460～489 行），所以在 `Mix` 里丢弃或调整数据不会让回声消除失准。

### 9.2 目标

1. 一次卡顿之后，几秒内把多出来的延迟降回目标深度，而不是一直挂着。
2. 目标深度随网络自适应：网络平稳时小（延迟低），抖动大时自动加大（少卡顿）。
3. 降延迟尽量听不出来：优先丢静音段，不得已时才在有声段丢，并做淡入淡出。
4. 把「播放缓冲深度」作为一项指标，进入日志、质量报告、悬停详情与评级，延迟变大时图标能反映出来。
5. 一对一通话、屏幕共享、群通话一起受益，每一路独立调整。

不在本期：时间伸缩（WSOLA 等变速不变调算法）、Opus FEC、中转路径上的丢包补偿。

### 9.3 方案对比

| | A. 在 PCM 缓冲上加自适应策略（推荐） | B. 换用 speexdsp 的包级抖动缓冲（`jitter.c`，已编进 `speexdsp_static`） |
| --- | --- | --- |
| 做法 | 解码仍在收包线程、仍写入 PCM 缓冲；`Mix` 取数据前按策略决定起播、丢静音、丢有声段 | 收到的包按时间戳放进 speexdsp 抖动缓冲，播放线程按节拍取包再解码；取不到时调 Opus 丢包补偿 |
| 改动范围 | `AudioStreamMixer` 与 `PcmRingBuffer`，三处使用方不用改 | 解码挪到播放线程；三处使用方都要给每个包带上时间戳（屏幕共享与群通话的帧是否都有，须另查）；`AudioStreamMixer` 重写 |
| 能力 | 解决延迟只增不减；不处理乱序、丢包 | 同时处理乱序、迟到、丢包（中转路径也能有丢包补偿），自适应延迟是现成的 |
| 风险 | 小，可分步落地、逐步验证 | 大，播放线程上多了解码的耗时；speexdsp 的抖动缓冲参数要另行摸索 |

推荐 A：声音延迟被永久抬高的根因是「没有目标深度、不会回落」，A 正好对症，改动集中在一个类里。B 留作以后需要中转路径丢包补偿时再议。

**2026-10-06 用户选定方案 B**，详细设计见第 9.9 节；下面 9.4～9.8 是方案 A 的设计，保留作对照，不实施。

### 9.4 方案 A 的设计

每一路一个策略对象（纯逻辑类，暂名 `JitterBufferPolicy`，不碰音频与线程，可直接写单元测试），在播放线程每次 `Mix` 时调用：

- **目标深度 T**：初值 60 毫秒，范围 40～400 毫秒。
  - 取空（卡顿）时立即加大：T 取「当前 T + 20 毫秒」与「这次断流时长 + 20 毫秒」中的较大者。
  - 连续 5 秒没有卡顿时减小 10 毫秒，慢降。
- **起播门槛**：一路刚开始或取空之后，缓冲深度攒到 T 才开始播放，避免一点点数据断断续续地播。取空的那一刻做 5 毫秒淡出，恢复时做 5 毫秒淡入，避免咔哒声。
- **多余延迟的判定**：记录最近 2 秒里缓冲深度的最小值 M。M 是这 2 秒里一直没被用上的部分，M > T + 20 毫秒时，多出来的 M − T 就是可以去掉的延迟。
- **降延迟的方法**：
  - 优先丢静音：取数据前先看缓冲最前面 10 毫秒的能量，低于静音门限（约 −40 dBFS）就整段丢掉。对话里停顿很多，这样一般听不出来。
  - 退而求其次：连续 3 秒都有多余延迟、却等不到静音时（如屏幕共享里的音乐），在有声段丢 10 毫秒，前后用 2.5 毫秒交叉淡化接上。
  - 限速：每 100 毫秒的播放最多丢 10 毫秒，相当于最多快放 10%。按这个速度，卡顿 500 毫秒之后约 5 秒能降回目标。
- **`PcmRingBuffer`** 新增 `Peek`（只看不取）与 `Skip`（丢弃最前面若干采样）两个方法，不改现有方法的行为，回声消除参考与录屏用到的缓冲不受影响。
- **群通话的 DTX**：对方不说话时不发包，缓冲会被取空。这种取空不应让 T 变大，也不应计为卡顿。判断依据是缓冲取空前一段时间里收到的最后一帧是否为静音；判断不了时按卡顿处理，但 T 只按普通卡顿的步长加大。

### 9.5 指标与显示

- `AudioStreamMixer` 为每一路提供：当前深度、目标深度、累计丢弃时长（分静音与有声两类）、取空次数。
- 日志：5 秒一条的 `call stats:` 末尾加 `playout buffer=… ms target=… ms trimmed=… ms (silent … ms)`。
- 质量报告：用第 4.1 节的保留字段（偏移 20 起 2 字节）带上「播放缓冲深度（毫秒）」，版本号不变（不考虑老版本）。
- 悬停详情：「我收对方」「对方收我」两行各加一项「缓冲 N ms」。
- 评级：播放缓冲深度作为第五项指标进入第 5 节的门限表。门限据推测可先取 120 / 250 / 500 毫秒（良好 / 一般 / 较差），用弱网校准用例 CRL2 实测后再定。

### 9.6 测试用例

- **JB1** 到达均匀：深度稳定在初始目标附近，不丢任何数据。
- **JB2** 卡顿后回落：模拟卡 500 毫秒后积压数据一次到达，按 10% 的限速，约 5 秒内深度降回 T + 20 毫秒以内。
- **JB3** 持续抖动：到达间隔在 0～80 毫秒间随机时，T 升到能覆盖抖动；之后不再频繁取空，也不来回大幅丢弃。
- **JB4** 限速：任何 100 毫秒内丢弃不超过 10 毫秒。
- **JB5** 优先丢静音：缓冲最前面是静音时先丢静音；全程有声时等满 3 秒才丢有声段，丢之前做交叉淡化，接缝处没有阶跃。
- **JB6** 取空与慢降：取空后 T 立即加大；连续 5 秒没有卡顿后每次降 10 毫秒，不低于 40 毫秒。
- **JB7** 起播门槛与淡入淡出：取空后深度攒到 T 才恢复播放；取空与恢复处的波形有 5 毫秒淡出、淡入。
- **APU8** `PcmRingBuffer::Peek` 不改变可读数量，`Skip` 丢弃正确的个数（含环形回绕）。
- **ASM7** 混音器集成：一路先卡后突发，深度按策略回落，输出连续；**ASM8** 两路各自独立调整，互不影响。
- **CRL2 复测**：每 2 秒卡 200 / 500 毫秒时，每次卡顿后深度都降回目标，卡顿率每次都有数（不再只出现一次），档位随之变化；基线与纯延迟条件下深度稳定、不丢有声段。
- 现有 `[audiomix]`、`[shareaudio]`、`[callnet]` 用例全部照常通过。
- **人工**：真实通话中经弱网代理制造卡顿，听降延迟时有没有可察觉的破音或跳字；屏幕共享时播放音乐，听有声段丢弃的效果。

### 9.8 风险

- 有声段丢弃在音乐上可能听得出来：限速、交叉淡化，并且只在等不到静音时才用；J4 人工核对。

### 9.9 方案 B 的详细设计（用户选定，已实施，落地记录见 9.9.8、9.9.9）

#### 9.9.1 前提：每个音频包要带「媒体时间戳」（据实证，已核对代码）

speexdsp 的抖动缓冲按时间戳排队、判断迟到与丢失：时间戳要以采样为单位，并且反映发送端的采集时间线（第几帧），不是墙上时间。现状三条路径都不满足：

| 路径 | 现状 | 问题 |
| --- | --- | --- |
| 一对一中转（TCP） | `[kind][chunk][ts 8 字节 毫秒][opus]`，没有序号；ts = `GetTickCount64() − 起点`（`CallMediaSession.cpp` 第 604 行） | `GetTickCount64` 精度约 16 毫秒，与 20 毫秒的帧间隔对不齐，相邻两帧的差会是 16 或 31 毫秒 |
| 一对一 P2P（UDP） | 有 32 位序号；ts 同上 | 同上 |
| 屏幕共享、群通话（TCP 或可靠的 P2P 流） | ts = 已发送帧数 × 20000 微秒（`ShareAudioSession.cpp` 第 350～351、282～283 行） | 只数真正发出去的帧；群通话开了 DTX（`GroupCallMediaSession.cpp` 第 67 行），不说话时不发包、ts 不前进，接收端会把说话恢复后的包当成迟到丢掉 |

**做法**：发送端改为按「采集帧序号」打时间戳——每采集一帧（20 毫秒）序号加 1，DTX 没有发出的帧也照样加。封装格式不变，只是 ts 字段的含义变了：

- 一对一（中转与 P2P）：ts 改为「采集帧序号 × 20」毫秒。接收端换算成采样数：`ts × 48`。第 2 期的接收端抖动统计（`CallRecvStats`）照用这个 ts，算出的抖动反而更准（发送间隔恒为 20 毫秒）。
- 屏幕共享与群通话：ts 改为「采集帧序号 × 20000」微秒（含 DTX 没发的帧），麦克风与电脑声音两条轨各自计数。需要音频引擎把采集帧序号交给发送方（`CallAudioEngineSink` 的回调多带一个参数，或引擎提供查询接口）。
- **不考虑老版本**（沿用第 4.2 节的决定）：新老客户端互通时，老版本发来的 ts 不规则，会偶尔出现补帧或跳帧，但不会无声。

#### 9.9.2 抖动缓冲封装：`CallJitterBuffer`（新类）

- 包装 speexdsp 的 `JitterBuffer`：它本身没有任何加锁（`jitter.c`），这里用一把互斥锁保护——收包线程放、播放线程取。
- 时间单位为采样（48 kHz），步长 960（一帧 20 毫秒），`JITTER_BUFFER_SET_CONCEALMENT_SIZE` = 960。
- 接口：
  - `Put(data, len, tsSamples)`：收包线程调用，拷贝负载入队。
  - `GetFrame(out)`：播放线程每要一帧调用一次，返回三种结果——拿到一个包、这一帧缺失、要插入一帧（speexdsp 想加大延迟）。随后由封装内部调用 `jitter_buffer_tick`。
  - 统计：当前缓冲延迟（最近放入的时间戳 − 播放指针，换算成毫秒）、缺失帧数、迟到丢弃数、为降延迟跳过的帧数。
- 延迟自适应用 speexdsp 自带的：`MAX_LATE_RATE`（允许的迟到比例，默认 4%）、`LATE_COST`（0 = 自动权衡）、`DELAY_STEP`（默认一帧）。具体取值在 B5 用弱网校准确定。

#### 9.9.3 接入 `AudioStreamMixer`

- `PushEncoded(streamId, data, len, tsSamples)`：只做 `Put`，**解码挪到播放线程**。四处调用方（一对一中转、一对一 P2P、屏幕共享、群通话，以及调试用的回环）都要传入 ts。
- `Mix(frames)`：每一路维护一个已解码 PCM 的小缓冲；不够 `frames` 时循环取帧：
  - 拿到包：Opus 解码 960 个采样；
  - 缺失：连续缺失 3 帧（60 毫秒）以内用 Opus 丢包补偿（`Decode(NULL, 0)`），超过后改为静音（长时间补偿会发出怪声）；
  - 插入：同样用丢包补偿或静音补一帧，不消耗包；
  - 发现返回的包时间戳不连续（speexdsp 为降延迟跳过了帧）时，用 2.5 毫秒交叉淡化接上，减轻咔哒声。
- 解码在播放线程上做：一帧 Opus 解码的耗时远小于声卡周期（10 毫秒级），群通话多路时也只是多几次解码；B3 时实测耗时并写进日志。
- 一对一 P2P 路径原先的 `CallAudioSeqTracker` 在收包线程上为缺口补帧（`CallMediaSession.cpp` 第 500～504 行），改由抖动缓冲统一处理后去掉这部分补帧；序号仍用于丢包率统计。
- 卡顿统计：丢包补偿与静音都计入「补静音」，与第 3 期的卡顿率口径一致；对方关麦或群通话 DTX 期间没有包、按第 3 期的规则不参与评级。

#### 9.9.4 指标与显示

同第 9.5 节：当前缓冲延迟进日志、质量报告的保留字段（偏移 20 起 2 字节，毫秒）、悬停详情（「缓冲 N ms」）与评级（门限 B5 实测后定）；另记缺失帧、迟到丢弃、为降延迟跳过的帧数，只进日志。

#### 9.9.5 测试用例

- **JBB1** 封装基本行为：按顺序放入、按节拍取出，不缺失、不插入；缓冲延迟稳定在一两帧。
- **JBB2** 乱序：在延迟范围内乱序到达的包按时间戳顺序取出，不算缺失。
- **JBB3** 丢包：中间少一个包时，到点返回「缺失」；之后的包照常取出。
- **JBB4** 卡顿后回落：模拟卡 500 毫秒后积压的包一次到达，若干秒内缓冲延迟回落到卡顿前的水平附近（具体秒数以 speexdsp 的行为实测为准，写进用例）。
- **JBB5** 长时间没有包（对方关麦、DTX）：之后的第一个包到达时缓冲重新开始，不会把它当迟到丢掉。
- **JBB6** 线程安全：一个线程放、一个线程取，跑若干秒不崩溃、取出的包不重复不丢失。
- **AMB1～AMB4** 混音器集成（用真实 Opus 编码的正弦波）：均匀到达时输出连续、不补帧；丢包时用丢包补偿、连续缺失超过 3 帧改静音；时间戳跳变处有交叉淡化；多路互不影响。
- **TS1～TS3** 发送端时间戳：一对一的 ts 每帧恰好加 20；群通话 DTX 期间没发包，恢复后 ts 已经越过这段静音；屏幕共享两条轨各自计数。
- 现有用例：`[audiomix]` 的 ASM1～ASM6（推入后立即混音的预期要按抖动缓冲的起始延迟改写）、`[shareaudio]` 的 SSAU1～SSAU8、`[callp2p]`、`[callnet]` 改到全部通过。
- **CRL2 复测**：十种弱网条件，确认卡顿后延迟能回落、卡顿每次都有数；另加一种 P2P 丢包条件（需要 UDP 代理，B5 时再定是否做）。
- **人工**：真实通话、屏幕共享放音乐、群通话中轮流说话，听有没有破音、跳字、开头被吞。

#### 9.9.7 风险

- **改了发送端时间戳的含义**：新老客户端互通时声音偶有补帧或跳帧（不考虑老版本，见上）。
- **解码挪到播放线程**：播放线程的截止时间紧，解码异常耗时会造成声卡欠载；B3 实测耗时，必要时把解码放回收包线程，抖动缓冲改存解码后的 PCM。
- **speexdsp 降延迟是整帧跳过**：在有声段可能听得出来；靠交叉淡化缓解，B5 人工核对。
- **speexdsp 的抖动缓冲多年没有更新**，参数含义只能看源码；它在 Mumble 等开源项目里长期使用，基本行为可靠。
- **改动面**：一对一通话、屏幕共享、群通话的收发路径都要改，三者的现有用例与联调都要重新过一遍。

**B4 改动**：
- `CallJitterBuffer` 每取到一个包量一次缓冲深度（已收到、还没播放的时长），累计和与次数进 `CallJbStats`；缺失时不量，对方没在说话的时段不拉低平均值。

- 评级新增第五项「播放缓冲延迟」，门限 120 / 250 / 500 毫秒（良好 / 一般 / 较差）；与丢包、抖动、卡顿一样，窗口内没有应收的音频包时不参与。

- 5 秒一条的 `call stats:` 末尾加 `playout buffer=… ms, jb missing=… inserts=… late=… resets=…, plc frames=…, silence frames=…, peer buffer=… ms`；本端档位变化的日志加 `buffer=… ms`。
- 用例：NS4（报告字段）、NQ1（缓冲门限边界）、NQ5（详情文字与快照组装）、JBB7（缓冲深度只在取到包时量）、AMB6（每一路的统计）。

**B5 参数校准**（CRL2，每种条件 20 秒，取后半段、两端合计；卡顿单位千分比，缓冲为播放缓冲延迟，单位毫秒）：

| 条件 | 允许迟到 4%（speexdsp 默认）：卡顿 / 缓冲 | 允许迟到 2%：卡顿 / 缓冲 | 允许迟到 1%（选定）：卡顿 / 缓冲 |
| --- | --- | --- | --- |
| 基线 | 5.0 / 2 | 0 / 1 | 0 / 1 |
| 单向延迟 60 | 17.0 / 0 | 12.0 / 0 | 0.9 / 20 |
| 单向延迟 120 | 27.0 / 0 | 0 / 19 | 0 / 20 |
| 随机抖动 0～40 | 0.9 / 33 | 1.0 / 34 | 0 / 33 |
| 随机抖动 0～80 | 22.0 / 41 | 8.0 / 43 | 1.0 / 61 |
| 随机抖动 0～160 | 2.0 / 78 | 0 / 92 | 0 / 88 |

| 每 2 秒卡 500 | 134.0 / 413 | 1.0 / 430 | 0 / 429 |

结论：
- 取「允许迟到 1%、不加余量」（`CallJitterBuffer.cpp` 的 `kMaxLateRatePercent`、`kMarginSamples`）。speexdsp 默认的 4% 在网络平稳时几乎不留缓冲，轻微的到达不均匀就造成 1%～3% 的断续；1% 时同样条件下卡顿降到约 1‰，代价是多留约 20 毫秒缓冲。
- 每 2 秒卡 200 毫秒这种周期性卡顿下，各组的卡顿率都高（37～96‰），档位如实显示为较差，属于期望的行为；三组之间的差异据推测主要来自两次运行之间的随机性，未再细究。
- 播放缓冲延迟的门限保留 120 / 250 / 500 毫秒：平稳到中度抖动时缓冲在 0～90 毫秒，评为良好；反复卡半秒时缓冲涨到约 430 毫秒，评为较差，两类情况能区分开。往返时延的门限没有改动（是否按 ITU-T G.114 放宽「良好」的上限，仍待用户决定）。

## 10. 增强：通话中共享电脑声音（2026-10-06，用户已确认，按 10a～10d 实施）

### 10.1 目标

一对一语音或视频通话接通后，本人可以随时打开「共享电脑声音」，把电脑上其它程序播放的声音（音乐、视频的声音等）连同自己的说话声一起发给对方；再点一次停止。不需要先发起屏幕共享。群通话不在本期范围内。

### 10.2 现状（据实证，均已核对代码）

- 屏幕共享已有「共享电脑声音」：`Share/ShareSystemAudioCapture` 优先用「排除本进程树的回环采集」，只采 Flamingo 以外所有程序的声音，我们自己播放的对方说话声从源头上就不会被采进去；接口不可用时退回普通回环（`ShareSystemAudioCapture.h` 文件头）。回调在它自己的线程上，交出 48 kHz 单声道 16 位采样。
- 屏幕共享把电脑声音作为单独一路发送：单独的 Opus 编码器，音乐模式、64 kbps（`ShareAudioSession.cpp` 的 `kSysRate` / `kSysFrame` / `kSysBitrate`）；退回普通回环时，别人在说话就把电脑声音压到 10%（`kGainDucked`，`ShareAudioSession::DuckingGainPercent`）。
- 一对一通话的接收端已是多路混音：`AudioStreamMixer::PushEncoded(streamId, …)` 每路一个抖动缓冲（第 9.9 节），目前只用第 1 路。
- 中转封装只认音频、视频、质量报告三种类型（`CallMediaFraming.h` 的 `CallMediaKind`）。旧版本收到未知类型时 `CallMediaDemux::Feed` 返回 `call_demux_error`（`CallMediaFraming.cpp` 约第 168 行），会话每收到一个就记一条 ERROR 日志（`CallMediaSession::OnRelayData`）；P2P 解析遇到未知类型直接丢弃（`CallP2PFraming.cpp` 约第 67 行）。
- 质量报告最后 2 字节（偏移 22 起）仍是保留字段、恒填 0（NS4 用例）。
- 回声消除的参考信号只有本端播放的混音（`CallAudioEngine::OnAudioNeeded` 推入 `m_farRef`）。

### 10.3 设计

**发送端**

- 打开开关时启动一个 `ShareSystemAudioCapture`（同一个 DLL 内直接复用），回调里攒满 20 毫秒一帧，用单独的 Opus 编码器（音乐模式、64 kbps，与屏幕共享相同）编码，按新类型发出：中转 `call_media_kind_system_audio = 4`，P2P `call_p2p_kind_system_audio = 5`。时间戳是这一路自己的帧序号 × 20 毫秒，从打开开关时的 0 开始。
- 说话声这一路不变（仍是语音模式、24 kbps、回声消除与降噪）。两路分开，是为了让音乐不经过降噪与语音编码，也让对方能把两路分开计数。
- 退回普通回环时沿用屏幕共享的闪避规则：对方在说话时电脑声音压到 10%。
- 静音只关麦克风，不影响电脑声音；挂断时一并停止。
- 外放时，电脑声音会从扬声器传进本人的麦克风，对方会听到两遍（一遍直接发过去的，一遍经麦克风延迟到达的）。处理办法：共享电脑声音期间，把采到的电脑声音也加进回声消除的参考信号。据推测效果有限：笔记本常见的音效增强是非线性处理，屏幕共享方案第 5.7 节实测类似场景只能衰减约 7 dB。因此开关的提示文字里建议戴耳机。

**能力协商**

- 质量报告偏移 22 的字节改为能力位，第 0 位表示「能接收电脑声音」；新版本每份报告都带上。旧版本这里是 0。
- 只有收到过对方能力位为 1 的报告后才真正发送；对方是旧版本时点开关会提示「对方的版本不支持接收电脑声音」，不发送。这样旧版本不会因为不认识的类型每秒记 50 条错误日志。

**接收端**

- 电脑声音进 `AudioStreamMixer` 的第 2 路，有自己的抖动缓冲，与说话声混音后播放；混音结果仍作为回声消除的参考，所以对方外放时我们的麦克风不会把电脑声音再送回去。
- 电脑声音这一路不参与丢包率、卡顿率与网络评级（它可能随时开关）；5 秒统计日志另记这一路的收发包数。

**界面**

- 接通态的底部操作栏（语音、视频都有）新增「共享电脑声音」按钮，位置在「共享屏幕」与「挂断」之间；正在共享时为激活态。图标：一台显示器旁边带声波，由 `CallButtonArt` 绘制。提示文字「共享电脑声音（建议佩戴耳机）」/「停止共享电脑声音」。
- 对方开始共享时，通话窗画面区上方的提示条提示一次「对方开始共享电脑声音」，停止时提示「对方已停止共享电脑声音」（实施时
  改为在开、停两个时刻各提示一次，与网络变差的提示共用同一个提示条，不另占位置）。
- 与屏幕共享的电脑声音互斥：通话中已在共享电脑声音时，再发起屏幕共享并勾选「共享电脑声音」，通话这一路自动停止并在提示里说明；反过来，屏幕共享正在共享电脑声音时打开通话的开关，屏幕共享那一路停止。避免对方听到两遍。
- 视频态按钮从 6 个增加到 7 个，最小窗口宽度下放不下时加大最小宽度。实施时算得视频态底部栏最宽需要 776 像素，超过了
  默认宽度 720，用户选定把默认宽度一并改为 776（`CallingLayout.h` 的 `kCallDlgWidth`，画面区高度不变）。

### 10.6 风险

- 外放时的回授只能减轻、不能消除（见 10.3），所以提示文字建议戴耳机。
- 电脑声音的发送同样走中转的那把发送锁（bugs.md BUG-118），会多占中转连接约 64 kbps；BUG-118 修好之前，开摄像头加共享电脑声音时说话声的断续可能更明显。
- Win10 2004 之前的系统没有「排除本进程树的回环采集」，只能退回普通回环加闪避，对方说话时可能隐约听到自己的回声。
